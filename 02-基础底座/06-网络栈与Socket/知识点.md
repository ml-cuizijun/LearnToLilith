## 1. 基本概念

逻辑服、网关**不能直接读写网卡**。进程能做的只有 `socket` / `bind` / `listen` / `accept` / `read` / `write`——每一记都是 syscall。包到了机器上，不等于进了你的进程（和 [01](../01-内核与系统/) 同一扇门）。

**值班里怎么认现象**：

| 玩家/监控说的 | 技术含义 | 你的第一刀 |
|---------------|----------|------------|
| 新玩家进不去、在线还在 | 新挂旧不挂 | conntrack -C |
| 网关 CPU 不高但接不进 | backlog 满 / accept 慢 | `ss -lntp` |
| 长连接还在但响应慢 | 应用没 read | ESTAB Recv-Q |
| 支付/鉴权 HTTP 偶发失败 | 出站端口 / TW | ip_local_port_range |

| 在 socket / 协议栈里 | 不在这一层 |
|----------------------|------------|
| Recv-Q / Send-Q、LISTEN backlog、ESTAB 缓冲 | 应用业务错误码 |
| SYN_RECV、TIME_WAIT、CLOSE_WAIT | 安全组误改（新旧通常一起死） |
| conntrack 条目、本机出站端口 | 对端应用死锁根因（只能看见 Send-Q） |
| epoll 就绪集合 | HTTP 状态码、TLS 握手 RTT |

三个「队列」不要混：

| 队列 | 单位 | ss 里看哪 |
|------|------|-----------|
| **半连接**（SYN_RECV） | 连接个数 | `ss -s` 的 syn-recv |
| **全连接**（等 accept） | 连接个数 | **LISTEN** 的 Recv-Q |
| **socket 缓冲** | 字节 | **ESTAB** 的 Recv-Q / Send-Q |

游戏网关与逻辑服是**长连接**：小时级 ESTAB，TIME_WAIT 通常不多。登录、支付回调才是短连接 HTTP，才会堆 TIME_WAIT、打满 conntrack。

**打个比方**：网卡是小区大门，conntrack 是门卫登记本，LISTEN backlog 是前台等候区，ESTAB Recv-Q 是已经进房间但客人还没处理的快递堆——新玩家进不去可能是登记本满了（conntrack），也可能是前台满了（backlog），别一进来就修房间窗户（TCP 窗口）。

> **记住**：新挂旧不挂，先想队列和 conntrack，不是网卡坏了。ESTAB Recv-Q 涨 = 应用没 `read`，不要先调 TCP 窗口。

**面试怎么说**：「新挂旧不挂我先 conntrack；LISTEN Recv-Q 是连接个数，ESTAB Recv-Q 是字节，混了就会用 rmem 治 accept 慢。」

## 3. 原理

### 3.1 Recv-Q / Send-Q：两种含义

**一句话：** LISTEN 的 Q 是**连接个数**，ESTAB 的 Q 是**字节**——混了就会用 rmem 治 accept 慢。

**打个比方**：LISTEN 的 Recv-Q 像餐厅门口等叫号的**人数**；ESTAB 的 Recv-Q 像已经入座但厨房还没上菜的**盘子堆**——门口人多要加前台和 accept，桌上盘子堆要加工人 read，别给门口加更大的餐盘（rmem）。

**现场走一遍**（网关新连接进不来，在线玩家还在）：

1. 先看 LISTEN：

```bash
ss -lntp
```

2. 屏幕出现：

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port  Process
LISTEN 128    128    0.0.0.0:8080       0.0.0.0:*          users:(("gateway",pid=28451,fd=8))
```

3. Recv-Q=128 且 Send-Q=128 → **全连接队列顶满**，128 个已握手连接还没 accept，上限也是 128。
4. 再看 ESTAB（别混）：

```bash
ss -antp | head
```

5. 屏幕出现：

```text
ESTAB  256000  0   10.0.0.5:8080  10.0.0.12:54321  users:(("gateway",pid=28451,fd=1024))
```

6. ESTAB Recv-Q=256000 → 内核堆了 **256KB** 应用还没 read——这是字节，不是 256000 个连接。
7. LISTEN 顶满 → 加大 backlog + 加速 accept；ESTAB Recv-Q 涨 → 查线程/GC，**加大 rmem 治不了 LISTEN**。

**输出解读**：

| 状态 | Recv-Q | Send-Q | 涨了说明什么 |
|------|--------|--------|--------------|
| **LISTEN** | 已握手、还没 accept 的**连接个数** | backlog 上限 | 顶满 → accept 慢或 somaxconn 太小 |
| **ESTAB** | 内核里应用还没 read 的**字节** | 已发出、对端未 ACK 的**字节** | Recv-Q 涨 → 应用卡住；Send-Q 涨 → 对端慢/ZeroWindow（08） |

```mermaid

    A["LISTEN Recv-Q 顶满"] --> A1[accept 慢或 somaxconn 太小]
    B["ESTAB Recv-Q 涨"] --> B1[应用卡住，没 read]
    C["ESTAB Send-Q 涨"] --> C1[对端 ZeroWindow · 见 08]

    classDef a fill:#D97706,stroke:#92400E,color:#fff

    class B,B1 b

```

**面试怎么说**：「LISTEN Recv-Q 是等 accept 的连接个数，ESTAB 是字节；LISTEN 顶满我改 backlog 和 accept，不会加大 rmem。」

### 3.2 半连接与全连接队列

**一句话：** 有效全连接队列 = **`min(listen backlog, somaxconn)`**，只改一边等于没改。

**打个比方**：半连接像「预约登记」（SYN_RECV），全连接像「已预约在门外等入场」（等 accept）——有效容量取「餐厅门口大小」和「市政规定上限」的**较小值**，只扩一边没用。

**现场走一遍**（活动高峰 syn-recv 暴涨，新玩家 SYN 像丢包）：

1. 看全局计数：

```bash
ss -s
netstat -s | grep -i overflow
```

2. 屏幕出现：

```text
TCP:   12450 (estab 11800, closed 500, orphaned 0, timewait 150)
       3200 synrecv
    15234 times the listen queue of a socket overflowed
     8921 SYNs to LISTEN sockets dropped
```

3. syn-recv **3200** + ListenOverflows **15234** → 半连接或全连接长期满。
4. 查 somaxconn 和应用 listen：

```bash
cat /proc/sys/net/core/somaxconn
ss -lntp
```

5. somaxconn 128、应用 listen(128) → 有效 backlog = min(128,128)=128，**生产过小**。
6. **一起改**：应用 `listen(4096)` + `net.core.somaxconn=4096`；容器里改 Pod sysctl 或进程 listen，改宿主机不一定进 Pod。

**输出解读**：

```mermaid
flowchart TB
    SYN[SYN 到达] --> half["半连接 SYN_RECV<br/>tcp_max_syn_backlog"]
    half -->|ACK 完成| full["全连接 等 accept<br/>min backlog, somaxconn"]
    full -->|accept| est[ESTABLISHED]

    classDef a fill:#0891B2,stroke:#155E75,color:#fff
    classDef b fill:#2563EB,stroke:#1E3A8A,color:#fff
    classDef c fill:#16A34A,stroke:#14532D,color:#fff
    class SYN,half a
    class full b
    class est c
```

半连接满：SYN 丢弃或 SYN Cookie，表现像丢包，应用日志往往什么都没有。`tcp_abort_on_overflow=1`：满时直接 RST（快失败）；默认 **0** 是丢握手、客户端重试。SYN Cookie 防 SYN Flood，正常负载不应长期靠 Cookie。

**面试怎么说**：「有效 backlog 是 min(listen, somaxconn)，只改一边无效；容器 somaxconn 是命名空间里的值，改宿主机不一定进 Pod。」

### 3.3 TIME_WAIT 与 CLOSE_WAIT

**一句话：** TW 是主动关方的正常现象（短连接）；CW 持续涨是应用忘了 `close()`，修代码不调内核。

**打个比方**：TIME_WAIT 像挂断电话后等 60 秒确认对方也挂了——短连接狂打会占满电话线（本地端口）；CLOSE_WAIT 像对方挂了但你没放听筒——泄漏，调 `tcp_fin_timeout` 盖不住。

**现场走一遍**（支付回调 HTTP 短连狂打，连外部鉴权失败）：

1. 看 TW 和端口：

```bash
ss -s
ss -antp state time-wait | wc -l
cat /proc/sys/net/ipv4/ip_local_port_range
```

2. 屏幕出现：

```text
TCP:   ... timewait 28500 ...
32768    60999
```

3. time-wait **28500**，端口范围约 **3 万个** → 主动关闭的短连接把本地端口 + TW（~60s）占满。
4. 治理：**Keep-Alive / 连接池**，不是改 2MSL=5s，不是 `tcp_tw_recycle`（**已删除**，NAT 有害）。
5. 出站客户端必要时 `tcp_tw_reuse=1` + **`tcp_timestamps=1`**，关 timestamps 不安全。

**CLOSE_WAIT 现场**：

```bash
ss -antp state close-wait | awk '{print $NF}' | sort | uniq -c | sort -rn
```

持续增长 = 泄漏，**修代码**，不调 `tcp_fin_timeout`。

**输出解读**：

```mermaid
flowchart TB
    A[本机当 HTTP 客户端狂短连] --> B["每个主动关闭占本地端口<br/>TIME_WAIT ~60s"]
    B --> C[ip_local_port_range 用尽]
    C --> D[连外部失败：支付、鉴权 HTTP]
    D --> E[Keep-Alive / 连接池]

    classDef bad fill:#DC2626,color:#fff
    classDef ok fill:#16A34A,color:#fff
    class C,D bad
    class E ok
```

**面试怎么说**：「TIME_WAIT 多先连接池，tw_recycle 已死不能提；CLOSE_WAIT 涨是应用没 close，修代码不调 fin_timeout。」

### 3.4 conntrack、fd、端口：三个「满」

**一句话：** conntrack 满 = **新挂旧不挂**；fd 看进程 limits，端口看出站四元组——网关 CCU ≈ `min(ulimit-n, 内存, conntrack, 端口)`。

**打个比方**：conntrack 是门卫登记本——本满了新客进不来，已在场的不用重登记；fd 是进程手里攥的钥匙数量；出站端口是出门带的门禁卡号——三个「满」症状像，钥匙不对症。

**现场走一遍**（K8s 节点：新玩家进不去，在线战斗还在）：

1. 上节点查 conntrack：

```bash
conntrack -C
cat /proc/sys/net/netfilter/nf_conntrack_max
dmesg -T | grep conntrack
```

2. 屏幕出现：

```text
65536 out of 65536
nf_conntrack: table full, dropping packet
```

3. **65536/65536** + dmesg table full → **conntrack 满**，新连接在 PREROUTING 被丢，已有 ESTAB 通常还在——典型**新挂旧不挂**。
4. 止血：调大 max；长期 `nf_conntrack_tcp_timeout_established=3600`（默认 **5 天**太长）+ 使用率告警 **80%**。
5. 只调大 max 不治超时，风暴来了照样满——要治短连接模式和超时。

**fd 耗尽现场**：

```bash
ls /proc/<pid>/fd | wc -l
cat /proc/<pid>/limits | grep "open files"
```

顶 Max open files → Too many open files（02）。

**输出解读**：

```mermaid
flowchart LR
    A[新连接全挂、旧长连接还在] --> B[conntrack / 表类故障]
    C[新旧一起死] --> D[更像安全组 / 进程没了]

    classDef a fill:#D97706,stroke:#92400E,color:#fff
    classDef b fill:#DC2626,stroke:#7F1D1D,color:#fff
    class A,B a
    class C,D b
```

**面试怎么说**：「新挂旧不挂是 conntrack 满，K8s 节点必查；CCU 上限是 min(ulimit, 内存, conntrack, 端口)，只提 ulimit 不够。」

### 3.5 epoll：网关为什么能扛万级 CCU

**一句话：** epoll 只返回就绪集合，万级 CCU 必须 epoll；ready ≠ 已 read，线程卡死时 Recv-Q 照样涨。

**打个比方**：select/poll 像每次开会点名全公司——几百人还行；epoll 像只通知「今天有事的部门」——万级连接睡在 `epoll_wait` 上，进程 STAT 全是 **S**，**不进 Load**（02）。但 epoll 说「有数据可读」不等于你已经 read 了——线程卡 GC 时 Recv-Q 照样堆。

**现场走一遍**（网关 1.2 万 ESTAB，Load 很低但 Recv-Q 涨）：

1. 看连接和软中断：

```bash
ss -s
ss -antp | awk '$1=="ESTAB" && $2>100000'
mpstat -P ALL 1
```

2. ESTAB 11800，部分 Recv-Q > 100000 字节；`mpstat` 里 **%si 单核不高** → 不是收包处理不过来，是**应用没消费**。
3. 若 `%si` 单核 100% → 收包处理不过来，调多队列 RSS（03），不是调应用 read。
4. ET 模式必须读到 EAGAIN，漏读就静默。

**输出解读**：

| | select / poll | epoll |
|--|---------------|-------|
| 规模 | 几百 fd | 网关万级标配 |
| 通知 | 每次拷整个集合 | 就绪列表 |
| ET | — | 必须读到 EAGAIN，漏读就静默 |

**面试怎么说**：「网关万级 CCU 用 epoll；Recv-Q 涨且 si 正常是应用没 read，si 打满调多队列不是调消费。」

> **别混**：`%si` 满 vs Recv-Q 涨——前者调网卡/多队列，后者调应用消费。

## 4. 落地

### 4.1 生产怎么选

| 项 | 选 | 不选 |
|----|----|------|
| 网关模型 | 长连接 + epoll + 显式 backlog | 短连接扫、select |
| somaxconn | 4096～65535，与 listen 一起改 | 默认 128 |
| TIME_WAIT | Keep-Alive / 连接池；必要时 tw_reuse | recycle、2MSL=5s |
| conntrack | 使用率告警 80%；established 3600s | 只调大 max 当根治 |
| CCU 容量 | min(ulimit-n, 内存, conntrack, 端口) | 只把 ulimit 提到 65535 |
| 容器 backlog | Pod sysctl 或进程 listen(65535) | 只改宿主机 somaxconn |

验收：必须 `ss -lntp` 看到在听、Listen Recv-Q 不顶满、`ss -s` 的 syn-recv / time-wait 在预期、conntrack 使用率 < 80%。不要只探 TCP 端口通。

### 4.2 容器里你实际看到什么

`somaxconn`、conntrack、端口范围在容器里是**网络命名空间**里的值。K8s 用 `securityContext.sysctls` 或入口进程 `listen(65535)`。conntrack 表在**宿主机节点**上，查 `conntrack -C` 要上节点。

## 5. 核心配置

只动有证据的项。改 sysctl 走评审（18）。`tcp_tw_reuse` 必须同时确认 timestamps。

| 参数 | 默认 | 生产怎么用 | 改错会怎样 |
|------|------|------------|------------|
| `net.core.somaxconn` | 常 **128** | 与 listen 一起加大 | 只改一边无效；容器是自己的 ns |
| `net.ipv4.tcp_max_syn_backlog` | 发行版各异 | 防半连接打满 | 过小 SYN 丢，像丢包 |
| `net.ipv4.tcp_syncookies` | 常开 | SYN Flood 时靠它 | 长期靠 Cookie = 半连接长期满 |
| `net.ipv4.tcp_abort_on_overflow` | **0** | 网关选快失败还是让客户端再试 | 1 = 满时 RST |
| `net.ipv4.tcp_tw_reuse` | 0 | 仅出站客户端；要 timestamps=1 | 关 timestamps 不安全 |
| `tcp_tw_recycle` | **已删除** | 不要提 | NAT 下丢连接 |
| `nf_conntrack_max` | 常 65536 级 | 按 CCU 规划；告警 80% | 只加大不治超时 |
| `nf_conntrack_tcp_timeout_established` | **5 天** | 生产常降到 3600 | 长连接+5 天最容易堆满 |
| `net.ipv4.ip_local_port_range` | 约 3 万个 | 短连接客户端要够 | 范围不够 + TW = 连外部失败 |

> **记住**：有效 backlog = min(listen, somaxconn)；recycle 已死。

## 6. 命令与操作

**生产优先 `ss`。** `netstat` 来自 net-tools，很多发行版已弃用。内核计数仍常用 `netstat -s` 或 `nstat`。

### 6.1 值班第一眼

```bash
ss -s
ss -lntp
ss -antp | head
netstat -s | grep -i overflow
conntrack -C
cat /proc/sys/net/netfilter/nf_conntrack_max
mpstat -P ALL 1
```

### 6.2 读 ss：两种 Q

```bash
ss -lnt
# LISTEN：Recv-Q=12  Send-Q=128  → 12 个已握手还没 accept，上限 128
ss -antp | head
# ESTAB：Recv-Q=256000  → 内核堆了 256KB 应用还没 read
```

| 目的 | 命令 | 看什么 | 正常/异常 |
|------|------|--------|-----------|
| 听没听、Listen 两个 Q | `ss -lntp` | Recv-Q=未 accept 个数 | Recv-Q=Send-Q 顶满 |
| 状态分布 | `ss -s` | estab / syn-recv / time-wait | syn-recv 几千 |
| ESTAB + 进程 | `ss -antp` | Recv-Q 是字节 | >100KB 且涨 |
| TW 条数 | `ss -antp state time-wait \| wc -l` | 先确认是不是真的 TW | 接近端口范围 |
| CW 归属 | `ss -antp state close-wait` | 哪个进程没 close | 持续增长 |
| overflow | `netstat -s \| grep -i overflow` | ListenOverflows | 有计数 = 队列满过 |
| conntrack | `conntrack -C` | 使用率 vs max | 顶满 + 新挂旧不挂 |
| fd | `ls /proc/<pid>/fd \| wc -l` | 对 Max open files | Too many open files |

### 6.3 常见操作

**加大 backlog：** 应用 `listen()` 和 `somaxconn` **一起改**；容器改 Pod sysctl 或进程 `listen(65535)`；队列加大只是缓冲，accept 太慢还是会满。

**TIME_WAIT：** `ss -s` 确认 → Keep-Alive / 连接池 → 出站客户端必要时 `tcp_tw_reuse=1` + timestamps。不要 recycle，不要把 2MSL 改成 5s。

**CLOSE_WAIT：**

```bash
ss -antp state close-wait | awk '{print $NF}' | sort | uniq -c | sort -rn
```

持续增长 = 泄漏，修代码。

**conntrack：** 止血调大 max；长期降 established 超时、短连接改池子、告警 80%。K8s 节点必查。

活动高峰短连鉴权把 conntrack 打满：新玩家进不去、在线还在跑——最像 conntrack。确认长连接还在 → 停短连接风暴 / 救表 → **不要重启还活着的战斗服**。

## 7. 生产排障

和 01 同一套三问：进程还在不在？还能不能接新连接？已有长连接还通不通？

**conntrack / Listen 队列满 = 新玩家进不去，不是立刻踢在线。**

```mermaid
flowchart TB
    A[新玩家进不去 / 连不上] --> B{ss -s / ss -lntp}
    B -->|LISTEN Recv-Q 顶满| C[overflow / somaxconn / accept]
    B -->|ESTAB Recv-Q 涨| D[应用没 read，别调窗口]
    B -->|syn-recv 涨| E[半连接 / SYN Flood / Cookie]
    B -->|新挂旧不挂| F{conntrack -C vs max}
    F -->|顶满| G[调 max + 降 established 超时]
    B -->|Too many open files| H[fd：进程 limits]
    B -->|出站失败| I[端口：TW / ip_local_port_range]
    B -->|%si 单核 100%| J[RSS / 多队列 · 03]

    classDef bad fill:#DC2626,color:#fff
    classDef ok fill:#16A34A,color:#fff
    class G,C bad
    class D,J ok
```

| 现象 | 先做 | 别做 |
|------|------|------|
| LISTEN Recv-Q 顶满 | overflow、somaxconn、加速 accept | 加大 rmem |
| ESTAB Recv-Q 涨 | 看线程 / GC，strace | 先调 TCP 窗口 |
| ESTAB Send-Q 涨 | 对端 Recv-Q / ZeroWindow（08） | 加大本端 sndbuf 当根因 |
| TIME_WAIT 万级 | 连接池 / Keep-Alive，再 tw_reuse | recycle、2MSL=5s |
| CLOSE_WAIT 涨 | 修代码 | 调 tcp_fin_timeout |
| 新挂旧不挂 | conntrack -C vs max | 先改安全组 |
| `%si` 100% 丢包 | 多队列 RSS（03） | 当成 Recv-Q 去调应用 |
| Recv-Q 涨且 `%si` 正常 | 调应用消费 | 扩容复制卡死 |
| 容器 overflow | Pod 内 somaxconn / listen | 只改宿主机 |

## 8. 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| LISTEN Recv-Q 和 ESTAB Recv-Q 是一回事 | 错 | 一个是连接个数，一个是字节 |
| LISTEN 顶满加大 rmem | 错 | 那是 backlog，治 accept 和 somaxconn |
| 只改 listen(1024) 或只改宿主机 somaxconn | 错 | 有效值 = min；容器是自己的 ns |
| TIME_WAIT 多是内核 bug | 错 | 短连接正常；优先连接池 |
| CLOSE_WAIT 调 tcp_fin_timeout | 错 | 应用没 close，修代码 |
| 开 tcp_tw_recycle 治 TW | 错 | 已删除，NAT 有害 |
| tw_reuse 可关 timestamps | 错 | reuse 依赖 timestamps |
| 把 2MSL 改成 5s | 错 | 串话风险 |
| conntrack 满会踢掉在线长连接 | 错 | 新挂旧不挂 |
| 只调大 conntrack max 就根治 | 错 | 要治超时和连接模式 |
| 游戏长连接会 TW 爆炸 | 错 | 正常不会；爆炸说明短连接打在这台 |
| fd 耗尽和端口耗尽是一回事 | 错 | 一个看 limits，一个看出站四元组 |
| `%si` 满和 Recv-Q 涨都调应用 | 错 | si 调多队列，Recv-Q 调消费 |
| 网关只把 ulimit -n 提到 65535 就够 | 错 | CCU ≈ min(ulimit, 内存, conntrack, 端口) |

数字：somaxconn 常默认 **128**；2MSL 常 **60s**；conntrack established 默认 **5 天**；使用率告警 **80%**；`tcp_abort_on_overflow` 默认 **0**。

易混：LISTEN Q vs ESTAB Q；半连接 vs 全连接；TIME_WAIT vs CLOSE_WAIT；tw_reuse vs recycle；conntrack 满 vs 安全组；`%si` vs Recv-Q；fd vs 端口；宿主机 somaxconn vs 容器 ns。
