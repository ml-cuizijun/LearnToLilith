## 1. 基本概念

玩家点「登录」。这条 HTTPS 至少经过 APP、边缘、网关、上游四层。每一层都有自己的超时。**码写在网关 access.log 里，痛发生在最先超时的那一层。**

**值班里怎么认现象**（先听玩家/监控怎么说，再对表）：

| 玩家/监控说的 | 技术含义 | 你的第一刀 |
|---------------|----------|------------|
| 「闪退、立刻失败」 | 502 / 503 / TLS 握手失败 | error.log 关键字 |
| 「一直转圈然后失败」 | 504 或 APP 8s 超时 → 499 | 对超时谁更短 |
| 「部分渠道能登、部分不能」 | 缺中间证 / SNI 错 | openssl verify |
| 「CDN 绿锁但 502」 | 回源证过期，不是入口证 | 回源 IP + Host + SNI |
| 「高峰新建 HTTPS 慢」 | TLS 握手 CPU / 短连接 | Keep-Alive + ECDSA |

游戏 HTTP 入口（登录、支付、公告）走这张图；战斗长连接走 TCP/KCP，和 HTTP Keep-Alive 不是一层（08）。

| 在 HTTP / TLS 里 | 不在这一层 |
|------------------|------------|
| 499 / 502 / 504 / 503 / 500 语义 | iptables、conntrack（06/15） |
| 超时链、Keep-Alive、证书链、SNI | Nginx 指令细节（23） |
| TLS 1.2 2-RTT / 1.3 1-RTT / 0-RTT | 完整 curl -w 五段 SOP（11） |

三个码不要混：

| 码 | 含义 |
|----|------|
| **502** | 网关没拿到合法 HTTP 响应 |
| **504** | 已经转发出去，等上游超时 |
| **499** | 客户端先断开 |

入口证书和回源证书是**两套**。CDN 回源 HTTPS 过期只打 502，浏览器访问边缘仍然绿锁。

**打个比方**：超时链像接力赛——APP 跑 8 秒就交棒放弃了，网关还举着棒等 60 秒，上游 SQL 还在跑——玩家已经失败了，DB 还在被打。证书像两扇门：玩家看到的是 CDN 大门（入口证），CDN 回源敲的是源站侧门（回源证），大门绿锁不能证明侧门钥匙还有效。

> **记住**：超时必须从外到内递减。反过来会 499/504 满天飞，打到 DB 的查询还在跑。入口证书和回源证书是两套。

**面试怎么说**：「502 是上游没给合法 HTTP，504 是等到 proxy_read_timeout，499 是客户端先走。超时 APP 最短，从外到内递减。入口证和回源证是两套，边缘绿锁不能证明回源证 OK。」

## 3. 原理

### 3.1 502、504、499：必须能举日志

**一句话：** 502 是上游没给出合法 HTTP；504 是等超时了；499 是客户端先走——先对 error.log，不要只看 access 数字。

**打个比方**：502 像快递员到了仓库，门开着但没人给正规发货单（非法 HTTP）；504 像货已经在路上，等到约定时间还没送到；499 像买家先取消订单，卖家还在打包。

**现场走一遍**（活动高峰登录失败）：

1. 监控网关 502 率飙升，access.log 里也有 499。
2. 先看 error.log 关键字：

```bash
grep -E ' 502 | 504 | 499 ' /var/log/nginx/access.log | tail -20
grep -E 'connect\(\) failed|invalid header|prematurely closed|upstream timed out|no live upstreams' /var/log/nginx/error.log | tail -20
```

3. 屏幕出现：

```text
# error.log
upstream prematurely closed connection while reading response header from upstream
upstream timed out (110: Connection timed out) while reading response header from upstream
# access.log
203.0.113.1 - - [28/Aug/2026:14:00:01] "POST /login HTTP/1.1" 502 150 ...
203.0.113.2 - - [28/Aug/2026:14:00:02] "POST /login HTTP/1.1" 499 0 ...
```

4. `prematurely closed` → **502 一族**，查上游 OOM/KILL（04），不要先加超时。
5. `upstream timed out` → **504**，先绕过网关测上游 RT。
6. 499 多：若上游 P99 高 → 真慢，对齐超时；若上游很快 → 网络抖动或玩家取消。

**输出解读：**

| 码 | 含义 | error.log 关键字 | 第一刀 |
|----|------|------------------|--------|
| **502** | 没拿到合法 HTTP | `connect() failed` / `invalid header` / `prematurely closed` | 进程、端口、OOM |
| **504** | 等上游超时 | `upstream timed out` | 上游 RT、SQL |
| **499** | 客户端先断开 | 无或 client closed | 谁超时更短 |
| **503** | 无健康上游/限流 | `no live upstreams` | 健康检查 |
| **500** | 上游返回业务错 | — | 应用日志 |

监控只看网关 5xx：APP 8s 已失败、网关还在打到 60s 才 504，5xx 会偏低。要以 **APP 失败率和上游 P99** 为准。

**面试怎么说**：「502 看 prematurely closed 还是 connect failed；504 是 upstream timed out；499 先对 APP 超时和上游 P99。偶发 502 加 prematurely closed 查 OOM，不要先加 timeout。」

> **记住**：prematurely closed 是 502，不是 504。

### 3.2 超时链：从外到内递减

**一句话：** 外层先停、内层有余量砍请求——timeout=300s 不是修复，是把慢查询藏得更久。

**打个比方**：像俄罗斯套娃超时——最外层 APP 8 秒就放弃了，中间网关还傻等 60 秒，最里面 SQL 没设 deadline 能跑 300 秒——玩家早就关 APP 了，DB 还在被慢查询打。

**现场走一遍**（登录从 200ms 变成 12s，499 满天飞）：

1. 活动 SQL 慢查询，登录 P99 从 200ms → 12s。
2. 核对各层超时：

```text
APP 客户端：8s
CDN/边缘：  未设或 60s
Nginx：     proxy_read_timeout 60s
上游 Java： 无硬超时 / 300s
```

3. 玩家 8s 放弃 → access.log 记 **499**；网关还在等 → 60s 后可能记 **504**；上游 SQL 还在跑。
4. 正确链路：

```text
APP 8s < 边缘 10s < 网关 12s < 上游硬超时 15s
```

5. 504 先优化/扩上游，再考虑超时是否合理。**不要把 timeout 改成 300s 当修复。**

**输出解读：**

```mermaid
flowchart TB
    subgraph wrong ["错"]
        w["APP 8s < 网关 60s < 上游无 / 300s"]
        w --> w2[玩家已失败，查询还在打 DB]
    end
    subgraph right ["对"]
        r["APP 8s < 边缘 10s < 网关 12s < 上游硬超时 15s"]
        r --> r2[最外层先停，内层有余量砍请求]
    end

    classDef bad fill:#DC2626,color:#fff
    classDef ok fill:#16A34A,color:#fff
    class w,w2 bad
    class r,r2 ok
```

| 层 | 常见值 | 角色 |
|----|--------|------|
| APP | **8s** | 最短，玩家体验 |
| 边缘 | 10s | 略长于 APP |
| 网关 | 12–60s | 留余量但别过长 |
| 上游 | 15s 硬超时 | SQL/RPC deadline 必须设 |

**面试怎么说**：「超时从外到内递减，APP 最短。499 多且上游 P99 高是真慢，对齐超时或异步化。timeout=300s 不是修复，是把慢查询藏得更久。」

### 3.3 Keep-Alive：短连接会把 TW 和 TLS CPU 一起打爆

**一句话：** 入口和上游都要复用连接；只开一边，TW 和握手 CPU 还会爆。

**打个比方**：短连接像每次购物都重新办会员卡、过安检——TLS 1.2 要 **2-RTT** 握手，高峰每秒 1 万新连接，光「办手续」就把网关 CPU 打满。Keep-Alive 像会员卡刷一下直接进。

**现场走一遍**（高峰网关 worker CPU `%us` 打满）：

1. 活动开始，网关 16 核 `%us` 飙到 95%，新建 HTTPS QPS 1 万。
2. 查连接复用：

```bash
ss -s | grep -i estab
grep keepalive /etc/nginx/nginx.conf
# upstream 块有没有 keepalive
```

3. 若只开了客户端 Keep-Alive、upstream 没连接池 → 每个请求仍要对上游新建 TCP+可能 TLS。
4. TLS 1.2 握手约 **2-RTT**，1.3 约 **1-RTT**——不开复用，CPU 花在握手上。
5. 修复：入口 + upstream 都开 Keep-Alive；换 ECDSA + TLS 1.3 + session 复用（见 3.5）。

**输出解读：**

```mermaid
flowchart LR
    subgraph short ["短连接每次"]
        s[TCP 三次握手 → TLS → HTTP → 挥手 → TIME_WAIT]
    end
    subgraph ka ["Keep-Alive"]
        k[握手一次，后续请求只走 HTTP]
    end

    classDef a fill:#DC2626,color:#fff
    classDef b fill:#16A34A,color:#fff
    class s a
    class k b
```

| 配置 | 作用 | 漏配后果 |
|------|------|----------|
| 入口 Keep-Alive | 客户端复用 | TW + TLS CPU 爆 |
| upstream keepalive | 网关→上游连接池 | 只开入口不够 |
| `keepalive_timeout` | 过长占 fd，过短=短连接 | 要调平衡 |

战斗长连接是 TCP/KCP（08），不是 HTTP Keep-Alive。

**面试怎么说**：「短连接把 TW 和 TLS CPU 一起打爆。入口和 upstream 都要 Keep-Alive。TLS 1.2 是 2-RTT，1.3 是 1-RTT，高峰必须复用。」

### 3.4 HTTP/1.1 vs HTTP/2 vs HTTP/3

**一句话：** HTTP/2 解的是**应用层**排队，**TCP 丢包仍堵所有 stream**——公网弱网要解队头，才轮到 HTTP/3。

**打个比方**：HTTP/1.1 像单车道收费站——一个请求没走完，后面排队。HTTP/2 像一条路上多开几个窗口（stream）——窗口内不互相等，但**路本身（TCP）堵了，所有窗口一起停**。HTTP/3 像每条 stream 有独立小路（QUIC/UDP），一条路堵不影响别的。

**现场走一遍**（内网 gRPC 用 HTTP/2，公网弱网仍卡）：

1. 内网微服务 gRPC over HTTP/2，连接数从 5000 降到 50，应用层排队解决了。
2. 公网玩家走 HTTP/2 登录，弱网丢包时所有 stream 一起等 TCP 重传——**传输层队头还在**。
3. 战斗长连接不是 HTTP/2——解法是拆 UDP+TCP 或 KCP（08）。
4. HTTP/3（QUIC）丢包只堵那条 stream，但要客户端和证书栈支持。

**输出解读：**

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|--|----------|--------|--------|
| 传输 | TCP | TCP | QUIC / UDP |
| 一条连接 | 一次一个请求 | 多 stream 并行 | 多 stream，流独立 |
| 应用层排队 | 一个响应没完后面排队 | **已解决** | 已解决 |
| TCP 丢包 | 整条停 | **所有 stream 仍等重传** | 只堵那条 stream |
| 游戏入口 | 登录/支付常见 | 内网 gRPC 常用 | 公网看客户端 |

**面试怎么说**：「HTTP/2 解应用层排队，不解 TCP 队头阻塞。上了 HTTP/2 不等于不堵。公网弱网才考虑 HTTP/3。战斗长连接用 TCP/KCP，不是 HTTP Keep-Alive。」

### 3.5 TLS：握手、证书链、为什么变慢

**一句话：** 过期全挂、缺中间证部分挂、SNI 错拿到默认证；边缘绿锁不能证明回源证还活着。

**打个比方**：证书链像介绍信——站点证（我）→ 中间 CA（部门盖章）→ 根 CA（总部备案在浏览器里）。中间证必须你随身带，不能指望对方自己查档案。SNI 错像敲错门——拿到的是隔壁的默认证，域名对不上。

**现场走一遍**（部分渠道登录 TLS 失败，边缘仍绿锁）：

1. 国内渠道全挂，海外正常；CDN 控制台入口证有效。
2. 用 curl 五段 + openssl 测真正握手路径：

```bash
curl -o /dev/null -s -w \
  'dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total} code:%{http_code}\n' \
  https://login.example.com

openssl s_client -connect login.example.com:443 -servername login.example.com </dev/null 2>&1 | \
  grep -E 'Verify return code|subject=|issuer=|Not After'
```

3. 屏幕出现：

```text
dns:0.018 tcp:0.022 tls:0.045 ttfb:0.120 total:0.125 code:200
Verify return code: 0 (ok)
subject=CN = login.example.com
Not After : Dec 15 23:59:59 2026 GMT
```

4. 若 verify 非 0：

```text
Verify return code: 21 (unable to verify the first certificate)
```

→ 缺中间证，部分客户端会自己下载中间证所以「部分渠道能登」。

5. IP 直连不带 SNI：

```bash
openssl s_client -connect 203.0.113.5:443 </dev/null 2>&1 | grep subject
# subject=CN = default.ssl.example.com  ← 域名不匹配
```

6. CDN 502 但源站 localhost 正常 → 测「CDN 回源 IP + Host + SNI」那一跳（10）。回源 HTTPS 过期只打 502，边缘仍然绿锁。

**输出解读：**

| 问题 | 表现 | 修复 |
|------|------|------|
| 过期 | 几乎所有客户端握手失败 | 换证，告警 **14 天** |
| 缺中间证 | 部分客户端失败 | 服务器带全链 |
| SNI 错 | 默认证，域名不匹配 | `--resolve` 排障，Host=SNI |
| RSA 高峰 CPU | 网关 `%us` 高 | ECDSA + TLS 1.3 + session |

```mermaid
flowchart TB
    leaf[站点证] --> mid[中间 CA]
    mid --> root[根 CA · 系统/浏览器内置]

    leaf -.->|过期| f1[几乎所有客户端握手失败]
    mid -.->|服务器必须带上| f2[缺中间证：部分客户端失败]
    leaf -.->|SNI 错| f3[拿到默认证，域名不匹配]

    classDef a fill:#2563EB,color:#fff
    classDef c fill:#DC2626,color:#fff
    class leaf,mid,root a
    class f1,f2,f3 c
```

TLS 1.3 握手约 **1-RTT**；会话恢复可达 **0-RTT**（有重放，**支付/登录态变更禁止**）。TLS 1.2 是 **2-RTT**。

curl -w 做差：tls 段 = `time_appconnect - time_connect`；tls 高查证书链/RSA CPU/session 复用。ttfb 高查应用/DB（完整五段见 11）。

**面试怎么说**：「证书链三截：站点、中间、根。中间证必须服务器带上。SNI 错拿默认证。入口证和回源证两套，边缘绿锁不能证明回源 OK。支付禁止 0-RTT。」

> **别混**：tls 段慢（握手/证书）vs ttfb 段慢（应用/DB）。

### 3.6 和网关相关、但本章只点到为止

**一句话：** 504 先问上游慢还是缓冲盘满；支付 POST 不要靠网关自动重试止血。

**打个比方**：`proxy_buffering on` 像网关有个临时仓库——上游发货快、玩家收货慢，仓库堆满也会超时（504），不只是上游慢。`proxy_next_upstream` 自动重试像支付按钮按两次——非幂等 POST 可能扣两次款。

**现场走一遍**（504 但上游 localhost curl 很快）：

1. error.log 有 `upstream timed out`，但 `curl http://127.0.0.1:8080/health` 200 且 <100ms。
2. 查是否 buffering 盘满或响应体极大、客户端极慢。
3. 另：502 率飙 + 配置了 `proxy_next_upstream` 对 502 重试 → 非幂等 POST（支付）可能重复提交，**禁止盲目重试**。
4. CDN 502、源站 localhost 正常 → 回源 IP + Host + SNI（10）。

**输出解读：**

| 配置 | 风险 | 口径 |
|------|------|------|
| `proxy_buffering on` | 盘满也 504 | 不只查上游慢 |
| `proxy_next_upstream` | 502 重试雪崩 | 支付 POST 禁止 |
| CDN 回源证过期 | 边缘绿锁、CDN 502 | 两套证分开查 |

**面试怎么说**：「504 不一定上游慢，可能是 proxy_buffering 盘满。支付 POST 禁止网关盲目重试。CDN 502 源站 localhost 正常，查回源 IP+Host+SNI。」

## 4. 落地

### 4.1 生产怎么选

| 项 | 选 | 不选 |
|----|----|------|
| 超时 | APP < 边缘 < 网关 < 上游硬超时 | 网关 300s 当修复 |
| Keep-Alive | 入口和上游都开 | 只开一边 |
| HTTP 版本 | 内网 gRPC 用 HTTP/2；公网弱网再考虑 HTTP/3 | 「上了 HTTP/2 就不会堵」 |
| TLS | ECDSA + TLS 1.3 + session 复用 | 高峰仍用 RSA 当唯一入口 |
| 0-RTT | 静态资源才考虑 | 支付 / 登录态变更 |
| 证书 | 全链；入口证与回源证分开；告警 14 天 | 只看磁盘文件日期 |
| 登录域 vs 包体域 | 分开证书 | 和频繁 Purge 的 CDN 证绑在一起 |
| 战斗通道 | TCP/KCP（08） | 用 HTTP Keep-Alive 回答战斗长连接 |

### 4.2 证书落地你实际看到什么

边缘（CDN）一张证，源站回源另一张。nginx/网关 `ssl_certificate` 必须带全链（站点+中间）。client 双向 TLS 的 client cert 单独监控。

验收：`openssl s_client -servername` verify 为 0；`Not After` > 14 天；用 `--resolve` 测真正 VIP。不要只探 TCP 443。

## 5. 核心配置

Nginx 指令细节在 23。本章只钉语义。

| 参数 | 默认 / 常见 | 生产怎么用 | 改错会怎样 |
|------|-------------|------------|------------|
| APP 超时 | 常 **8s** | 最短 | 比网关长 = 499 满天飞仍打 DB |
| `proxy_read_timeout` | 常 **60s** | 对齐外层，留余量 | 先改 300s = 藏慢查询 |
| 上游硬超时 | 必须有 | SQL / RPC deadline | 只靠网关，超时后查询还在 |
| 入口 keepalive | HTTP/1.1 默认开 | 必须开；timeout 别过短 | 关 = TW + TLS CPU |
| upstream keepalive | 常忘 | 必须开连接池 | 只开入口不够 |
| TLS 版本 | 1.2 / 1.3 | 标配 1.3 | 1.2 多 1-RTT |
| 0-RTT | 可开早期数据 | **支付禁止** | 重放 |
| 证书链 | — | 服务器带中间证 | 部分客户端失败 |
| 告警 | — | **14 天** + 真握手路径 | 只看文件日期会漏 |

> **记住**：HTTP/2 不解 TCP 队头阻塞；支付禁止 TLS 1.3 0-RTT。RSA 高峰换 ECDSA + TLS1.3 + session 复用。

## 6. 命令与操作

### 6.1 值班第一眼

```bash
grep -E ' 502 | 504 | 499 ' access.log | tail
grep -E 'connect\(\) failed|invalid header|prematurely closed|upstream timed out|no live upstreams' error.log | tail
curl -sv --connect-timeout 2 http://upstream:port/health
openssl s_client -connect host:443 -servername host </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

典型 error.log 片段：

```text
upstream prematurely closed connection while reading response header from upstream
upstream timed out (110: Connection timed out) while reading response header from upstream
```

`prematurely closed` = 502 查 OOM；`timed out` = 504 查上游 RT。正常：error.log 无持续报错；异常：同一关键字每秒数十条。

### 6.2 速查表

| 目的 | 命令 | 看什么 | 正常/异常 |
|------|------|--------|-----------|
| 分 502/504 | access + error.log 关键字 | prematurely closed vs timed out | 持续飙 |
| 绕过网关 | `curl` 打上游 health | 2s 内必须有响应 | 超时 = 上游慢 |
| 证书日期/主体 | `openssl s_client` + `x509 -dates` | Not After、issuer | <14 天告警 |
| 缺中间证 | verify 非 0 | `unable to verify the first certificate` | 部分渠道失败 |
| TLS vs 业务 | `curl -w`：tls = appconnect − connect | 完整五段见 11 | tls 高 vs ttfb 高 |
| 强制 1.2 | `openssl s_client -tls1_2` | 对比 1.3 RTT | — |

curl -w 做差（时间戳从开始累计）：

| 字段 | 含义 | 本段 |
|------|------|------|
| time_namelookup | DNS | DNS |
| time_connect | 累计到 TCP 完成 | tcp = connect − dns |
| time_appconnect | 累计到 TLS 完成 | tls = appconnect − connect |
| time_starttransfer | 累计到首字节 | ttfb = starttransfer − appconnect |

tls 段高：证书链、RSA CPU、没开会话复用。ttfb 段高：应用/DB，不是公网。

### 6.3 常见操作

**分状态码：** 先 error.log 再 access。偶发 502 查 OOM。持续 502 查进程端口。504 先测上游 RT。499 对超时谁更短。503 看 live upstream / 限流。

**对齐超时：** 从外到内递减，每层留余量，上游必须有硬超时。504 先优化/扩上游。不要 timeout=300s。

**开 Keep-Alive：** 入口和上游都开。战斗长连接是另一层（08）。

**查证书链：** `s_client` + `-servername` + `-dates`。换证必须带全链。入口证和回源证是两套。告警 14 天，测真正握手路径。排障用 `--resolve`。

**TLS CPU：** 先确认慢在 TLS 段，再换 ECDSA / TLS 1.3 / session。Keep-Alive 也能少握手。

## 7. 生产排障

**登录 HTTP 挂了 ≠ 战斗长连接断了。** 先分通道。

```mermaid
flowchart TB
    A[登录/公告失败] --> B{access + error.log}
    B -->|502| C[进程 / RST / 缺头 / OOM]
    B -->|504| D[上游 RT；先别加超时]
    B -->|499| E{上游 P99}
    E -->|高| F[对齐超时 / 异步]
    E -->|低| G[抖动或玩家取消]
    B -->|503| H[no live upstreams / 限流]
    B -->|TCP 通 TLS 失败| I[过期 / 缺链 / SNI]
    B -->|新建 HTTPS 慢 %us 高| J[RSA → ECDSA + 1.3 + session]
    B -->|CDN 502 源站 localhost 正常| K[回源 IP + Host + SNI · 10]

    classDef bad fill:#DC2626,color:#fff
    classDef ok fill:#16A34A,color:#fff
    class C,I bad
    class D,F ok
```

| 现象 | 先做 | 别做 |
|------|------|------|
| 502 + prematurely closed | 上游 OOM | 先加超时 |
| 504 | 绕过网关测 RT | timeout=300s |
| 499 多、5xx 看起来还好 | 对 APP 超时 vs 网关 | 当客户端无脑重试忽略 |
| 503 | live upstream / 限流 | 按 502 去查 RST |
| 缺中间证部分渠道失败 | 带全链 | 只换站点证 |
| 边缘绿锁、CDN 502 | 回源证 / 安全组 / Host+SNI | 只 curl 源站 localhost |
| RSA 高峰 %us 满 | ECDSA + 1.3 + session | 先加机器当根因 |
| 支付偶发失败 | client cert Not After | 和服务器证混一个告警 |
| HIT 还 502 | 边缘脏缓存（10） | 当回源问题 |

## 8. 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| 502 和 504 都是上游挂了 | 错 | 502 没合法响应；504 等超时 |
| prematurely closed 是 504 | 错 | 502 一族 |
| 499 一定是服务端 bug | 错 | 先对谁超时更短 |
| 只看网关 5xx 就能代表失败率 | 错 | 499 不算 5xx；看 APP 失败率 |
| 把 timeout 改成 300s 消灭 504 | 错 | 藏慢查询、打满 DB |
| 只给客户端开 Keep-Alive 够了 | 错 | 上游连接池也要开 |
| HTTP Keep-Alive 就是战斗长连接 | 错 | 两层；战斗见 08 |
| 上了 HTTP/2 就不会堵 | 错 | TCP 丢包仍堵所有 stream |
| 支付可以开 0-RTT | 错 | 重放风险 |
| 边缘绿锁证明源站证没问题 | 错 | 两套证 |
| 缺中间证一定全量失败 | 错 | 部分客户端会下中间证 |
| SNI 错会过期 | 错 | 拿到默认证，域名不匹配 |
| 证书只看磁盘日期 | 错 | 测真正握手路径；告警 14 天 |
| RSA 高峰先加机器就根治 | 错 | 换 ECDSA + 1.3；加机器只是摊 CPU |

数字：APP 常见 **8s**；Nginx `proxy_read_timeout` 常 **60s**；TLS 1.2 **2-RTT**、1.3 **1-RTT**；证书告警 **14 天**。

易混：502 vs 504 vs 499 vs 503；入口证 vs 回源证；HTTP/1.1 vs 2 vs 3 队头；0-RTT vs session 复用；Keep-Alive vs 战斗长连接；tls 段 vs ttfb 段。
