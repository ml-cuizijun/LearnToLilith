## 1. 基本概念

### 用户态 vs 内核态

| 层 | 能干什么 | 不能干什么 |
|----|----------|------------|
| **用户态** | 跑业务代码（逻辑服、Nginx、Java） | 直接碰 CPU 调度、磁盘、网卡 |
| **内核态** | 调度、内存、IO、网络、cgroup | — |

程序碰硬件，只能走 **syscall（系统调用）**——唯一正门：

| 你想干什么 | 典型 syscall |
|------------|--------------|
| 读/写文件、打日志 | `open` / `read` / `write` |
| 建 TCP 连接 | `socket` / `connect` / `sendto` |
| 创建线程/进程 | `clone` |
| 锁在内核里等 | `futex` |

> **记住：** 用户态不能直接写磁盘、不能直接收网卡包。

### top 五个格子

`top` / `mpstat` 五个格子 = **CPU 时间在干什么**（合计约 100%）：

| 格子 | 含义 | 常见误判 |
|------|------|----------|
| `%us` | 用户态算业务 | 「不高就不慢」——可能 `%wa` 在等盘 |
| `%sy` | 进内核（syscall） | 不是内核 bug，是**进门次数多** |
| `%wa` | CPU 闲着等磁盘 | Load 高、`%us` 低时先看这个 |
| `%si` | 软中断（常见网卡收包） | **和 `%sy` 不是一回事** |
| `%id` | 真空闲 | 容器 throttle 时整机 `%id` 仍可能很高 |

### cgroup（先认脸）

**cgroup** = 给一组进程设配额：CPU 超 → **throttle**；内存超 → 这组被 OOM 杀。K8s `limits` 就是它。细节 → [07](../07-cgroup与容器/)。

## 3. 原理

### 3.1 一次 write 走哪条路

**一句话：** 每次 `write` 都要进内核（计 `%sy`）；数据先进内存缓冲，真正打盘在后面——小日志既烧 `%sy` 又打满 IOPS。

```mermaid
sequenceDiagram
    participant App as 用户态
    participant Kern as 内核
    participant Disk as 磁盘

    App->>Kern: write(1字节) → 计入 %sy
    Kern->>Kern: 进 page cache
    Kern-->>App: 返回（看起来很快）
    Kern->>Disk: 稍后 fsync/回写 → IOPS 在这里爆
```

| 写法 | syscall 次数 | 结果 |
|------|-------------|------|
| 每条日志 write 1 字节 | ~100 万 | `%sy` 爆 + IOPS 爆 |
| 攒 8KB 再 write | ~125 | 正常 |

进门约 **100～300ns**（CPU 时间）。100 万次 1B write ≈ **0.1～0.3s CPU** → `%sy` 高、`%us` 不高。

> **记住：** 日志场景「盘被打满」通常是 **IOPS 打满**，不是容量写满。

### 3.2 `%sy` 高了怎么证

**一句话：** 先分 `%sy` 和 `%si`，再用 `strace -c` 看 **calls 列谁最多**。

```mermaid
flowchart TB
    A["%sy 高、%us 不高"] --> B{%si 也高?}
    B -->|是| C[网卡收包 → 03、06]
    B -->|否| D[strace -c -p PID]
    D --> E{calls 谁最多}
    E -->|write| F[合并日志写]
    E -->|futex| G[查锁竞争]
    E -->|epoll_wait| H[查事件循环超时]
```

```bash
pgrep -af myapp          # 确认 PID
strace -c -p 28451       # 5～10 秒 Ctrl-C
```

典型输出（小日志场景）：

```text
% time     seconds  usecs/call     calls    errors syscall
 62.31    0.182341          12     15234           write
 18.42    0.053891         892        60           futex
```

**只看 calls 列：** `write` 1.5 万次 → 改日志缓冲，不是加核。活动服勿长时间 strace。

### 3.3 五域归类

**一句话：** 告警先归格，别先改 sysctl、别先重启。

```mermaid
flowchart TB
    A[慢 / 挂 / 连不上] --> B{哪一格?}
    B --> C[调度 → 03]
    B --> D[内存 → 04]
    B --> E[磁盘 → 05]
    B --> F[网络 → 06]
    B --> G[cgroup → 07]
```

| 域 | 第一眼 |
|----|--------|
| 调度 | load、`%us/%sy/%st`、`cpu.stat` |
| 内存 | MemAvailable、RSS、dmesg OOM |
| 磁盘 | `%wa`、await |
| 网络 | `%si`、`ss -s` |
| cgroup | `memory.max` / `cpu.max` |

### 3.4 journal 与 dmesg

**一句话：** journal 看**应用和退出码**；dmesg 看**内核为什么杀/为什么盘挂**。两边都要看。

| | journal | dmesg |
|--|---------|-------|
| 谁写的 | systemd + 应用 stdout | **内核** |
| 看什么 | 退出码、连库失败、配置错 | OOM、I/O error、网卡 reset |
| 命令 | `journalctl -u myapp` | `dmesg -T` / `journalctl -k` |
| OOM 典型句 | `status=9/KILL` | `Out of memory: Killed process 28451 (java)` |

**进程突然没了——三条命令：**

```bash
systemctl status myapp
journalctl -u myapp -n 80 --no-pager
dmesg -T | tail -30
```

**journal 示例（被系统杀）：**

```text
myapp.service: Main process exited, code=killed, status=9/KILL
myapp.service: Failed with result 'signal'.
```

→ 被 SIGKILL 了，但**不知道为啥** → 查 dmesg。

**journal 示例（应用自己错）：**

```text
myapp[28451]: ERROR: connect mysql: connection refused
myapp.service: Main process exited, code=exited, status=1/FAILURE
```

→ 进程自己 `exit(1)`，查应用日志和依赖。

**dmesg 示例（同一次 OOM）：**

```text
Out of memory: Killed process 28451 (java) anon-rss:2096128kB
```

→ 整机内存不够，杀了 java，RSS 约 2G。

**交叉结论：**

| journal | dmesg | 结论 |
|---------|-------|------|
| `status=9/KILL` | 有 OOM 行 | 整机 OOM → [04](../04-内存与OOM/) |
| `status=9/KILL` | 无 OOM | cgroup 限额或人工 kill → `memory.events` |
| `status=1/FAILURE` | 无 | 应用逻辑错，查 journal 里 ERROR |
| `connection refused` | 无 | MySQL 未就绪 → 查依赖、§5.1 |

退出码：**137 = 128 + 9 = SIGKILL**。常用 journal 参数：`-b` 本次开机、`-b -1` 上次开机、`--since "10:00"`。

### 3.5 容器里 free 为什么撒谎

**一句话：** 容器里 `free` 读的是**宿主机** `/proc/meminfo`；真限额在 **cgroup memory.max**。

```mermaid
flowchart LR
    free["free → 64G<br/>宿主机视图"] -.->|≠| cg["memory.max → 2G<br/>真限额"]

    classDef bad fill:#DC2626,color:#fff
    classDef ok fill:#16A34A,color:#fff
    class free bad
    class cg ok
```

`nproc` 同理返回宿主机核数 → Go `GOMAXPROCS` 过大 → **throttle** → 宿主机 `%id` 很高，容器 P99 仍炸。

**结案：** 看 `memory.max` / `cpu.stat`，不用容器内 free/top。

## 4. 落地

### 4.1 包和内核升级

内部源；内核升级 = 变更（窗口、值守、grub 留上一版）；验收 `uname -r` + dmesg 无 oops。

### 4.2 fstab 写错 → SSH 不通

**一句话：** fstab 是开机挂载表；写错 → 卡在挂载 → systemd/sshd 起不来 → ping 通但 SSH 超时。

```mermaid
flowchart LR
    A[内核] --> B[挂 /]
    B --> C[fstab 挂其它盘]
    C --> D[systemd → sshd]
    C -->|写错| X[emergency<br/>SSH 不通]

    classDef ok fill:#16A34A,color:#fff
    classDef bad fill:#DC2626,color:#fff
    class A,B,D ok
    class X bad
```

**怎么认：** ping 通 + SSH 超时；VNC 见 `Emergency mode`；刚改过 fstab。

**修复五步（rd.break）：**

| 步 | 做什么 | 命令 |
|----|--------|------|
| 1 | 云 VNC / 串口 | 不是 SSH |
| 2 | GRUB 按 `e`，linux 行末加 `rd.break`，`Ctrl+X` 启动 | — |
| 3 | 切根、改可写 | `switch_root /sysroot /bin/bash`<br>`mount -o remount,rw /` |
| 4 | 查 UUID、改 fstab | `blkid`<br>注释坏行或改 `UUID=...` |
| 5 | 验证、重启 | `mount -a`（无报错）→ `reboot -f` |

```text
# 坏：/dev/sdb1  /data  xfs  defaults  0  0     ← 盘符会变
# 好：UUID=a1b2c3d4-...  /data  xfs  defaults  0  0
```

已能 SSH 时直接改 fstab + `mount -a`，不必进救援。细账 → [14](../14-文件系统与inode/)。

### 4.3 主机名

`hostnamectl set-hostname game-s1-logic-03`；云上用 cloud-init 钉死。

## 5. 核心配置

完整 unit → [13](../13-Systemd与服务管理/)。

### 5.1 After / Requires / Wants

**一句话：** 这三个词写在 unit 的 `[Unit]` 段，管**启动顺序**和**依赖关系**——最容易混。

```ini
[Unit]
After=network-online.target mysqld.service   # 排序：等 MySQL 之后再启我
Requires=mysqld.service                      # 硬绑：MySQL 挂我也停
Wants=redis.service                            # 软绑：Redis 挂我继续
```

| 词 | 白话 | 管顺序？ | 对方挂了？ |
|----|------|:--------:|:----------:|
| **After** | 等它**启动完**再启我 | 是 | **不管**——它后来挂了我照跑 |
| **Requires** | 没它我不能活 | 否（可能并行起） | **我也被停** |
| **Wants** | 有它更好 | 否 | **我继续跑** |

```mermaid
sequenceDiagram
    participant M as mysqld
    participant L as logic

    Note over M,L: ✗ 只有 Requires → 并行起，logic 连不上库
    par 并行
        M->>M: 还在 listen 前
        L->>L: 已启动 · 连库失败
    end

    Note over M,L: ✓ After + Requires → MySQL 先 ready
    M->>M: listen
    L->>L: After 满足后启动
    L->>M: 连接成功
```

**硬依赖写法：** `After=mysqld.service` + `Requires=mysqld.service` 一起写。

游戏服常见折中：只 `After=mysqld`，应用层重连；Requires 留给「没有绝对不能跑」的本地 agent。MySQL 抖一下 + Requires → 逻辑服全停。

### 5.2 Restart 死亡螺旋

**一句话：** `Restart=always` + `RestartSec=0` → OOM 137 → 立刻重启 → JVM 冷启动 → 再 137 → 循环。

```mermaid
flowchart LR
    A[137 被杀] --> B[立刻 Restart]
    B --> C[JVM 冷启动]
    C --> D[再 137]
    D --> A

    classDef bad fill:#DC2626,color:#fff
    class A,B,C,D bad
```

`always` 连 `exit 0`（热更）也会拉回来 → 抢端口。

**生产写法：**

```ini
Restart=on-failure
RestartSec=5s
StartLimitBurst=3
StartLimitIntervalSec=60
```

### 5.3 Type 与 PIDFile

| Type | 什么时候用 |
|------|------------|
| **simple** | 进程前台跑（Nginx `daemon off`）——**默认首选** |
| **forking** | 启动脚本 fork 后父进程退出；必须配对的 **PIDFile** |

PIDFile 路径错 → systemd 认为没起来 → unit failed，旧进程仍占端口。看生效配置：`systemctl cat myapp`。

## 6. 命令与操作

### 6.1 服务不可用第一眼

**不要先 top、不要先重启。** 顺序：**影响面（30s）→ status → 双日志留证 → 再拉起**。

```mermaid
flowchart TB
    A[不可用] --> B{systemctl status}
    B -->|挂了| C{退出码}
    C -->|9 / 137| D[dmesg / memory.events]
    C -->|1 等| E[journal · 应用 ERROR]
    C -->|15 / 143| F[发版 / 正常停]
    B -->|活着| G[ss -lntp → curl → 06 网络]
    A -->|只是慢| H[curl -w · 11]
```

### 6.2 命令速查

```bash
# 状态
systemctl status myapp
systemctl cat myapp

# 双日志（见 3.4 示例输出）
journalctl -u myapp -n 80 --no-pager
journalctl -u myapp -b -1          # 上次开机
dmesg -T | tail -50
journalctl -k -n 50

# %sy 证明（见 3.2）
strace -c -p <PID>                  # 5～10 秒，看 calls 列
```

| 退出表现 | 含义 | 下一步 |
|----------|------|--------|
| `status=9/KILL` / 137 | SIGKILL | dmesg / memory.events |
| `status=15/TERM` / 143 | 正常停 / 发版 | 对变更窗口 |
| `status=1` | 自己 exit | journal 里 ERROR |

`status` 片段：`code=killed, signal=KILL` → dmesg；`code=exited, status=1` → journal。

## 7. 生产排障

| 现象 | 先做 | 别做 |
|------|------|------|
| 不可用 | status → 双日志 | 先重启 / 先 top |
| 9/KILL、137 | dmesg；容器 memory.events | 只看应用日志 |
| 反复 start+137 | 改 Restart，再查内存 | 只 reset-failed |
| `%sy` 高 `%us` 不高 | 分 sy/si → strace -c | 先加核 |
| 容器 free 很大 | cgroup limit | 信 free |
| SSH 不上 + 刚改 fstab | VNC → UUID → mount -a | 空转 SSH |
| unit failed 端口有人听 | PIDFile / Type | 再 start 抢端口 |

## 8. 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| 用户态直接写磁盘 | 错 | 只能 syscall |
| `%sy` 高 = 内核 bug | 错 | 进门次数多 |
| `%sy` = `%si` | 错 | sy=syscall；si=软中断 |
| 不可用先 top/重启 | 错 | 先 status + 留证 |
| After = 对方挂自己不起 | 错 | After 只排序 |
| 只有 Requires | 错 | 可能并行连未就绪库 |
| always + RestartSec=0 | 错 | 死亡螺旋 |
| 只看 journal 定 OOM | 错 | 杀手在 dmesg |
| 容器 free 大 = 够用 | 错 | 看 cgroup |
| fstab 写 sdb1 | 错 | 用 UUID |
| throttle 时整机很闲 | 对 | 卡的是容器配额 |

数字：syscall **100～300ns**；100 万次 1B write ≈ **0.1～0.3s CPU**；**137 = 128 + 9**。

易混：journal vs dmesg；`%sy` vs `%si`；After vs Requires；IOPS 满 vs 容量满。
