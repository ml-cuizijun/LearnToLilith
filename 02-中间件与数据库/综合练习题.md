## MySQL

### Q1：B+ 树 vs 哈希 vs B 树？回表怎么消？

**★★★★★**

**场景**  
开场就问：「InnoDB 为什么默认 B+？二级索引叶子上是什么？」有人开始背页大小 16KB。

**完整解答**

先画叶链表，再点名聚簇和回表。

```
  非叶：只存键，扇出大、树矮

  叶：双向链表
  [id=1 整行] <-> [id=2 整行] <-> [id=3 整行]
```

1. **B+**：非叶只导航，范围和排序沿叶链表一次扫完。
2. **B 树**：数据散在各层，范围要反复回根。InnoDB 不用。
3. **哈希**：等值最快，不支持范围、排序、前缀。Memory 引擎才用。
4. **回表**：主键叶存整行；二级索引叶只存主键，`SELECT *` 再查聚簇。覆盖索引把查询列都放进二级，`Extra: Using index`。

低频状态列（0/1）不要单独建索引。`SELECT *` 在大表上几乎总会回表。

**再追问：`type=index` 是胜利吗？**  
不是。那是扫整棵索引，只是没扫数据页。真正要用 `key` 和 `key_len` 看走了几列。

### Q2：最左前缀和失效场景各举两个。

**★★★★★**

**场景**  
表上有 `(zone_id, name, created_at)`。有人写 `WHERE name='张三'` 抱怨没走索引。另一条 `WHERE zone_id>1 AND name='张三'` 也慢。

**完整解答**

`(a,b,c)` 必须从 a 连续用。跳列只用到跳点之前。范围条件后面的列基本用不上。

```
  用 a,b:     zone_id=1 AND name='张三'
  不用:       name='张三'                 （没从最左开始）
  只用 a:     zone_id=1 AND created_at>?  （跳了 name）
  a 范围:     zone_id>1 AND name='张三'   （name 基本失效）
```

再举失效：`YEAR(created_at)=2024`（函数）、`phone=13800138000`（varchar 喂 int）、`name LIKE '%张'`（左模糊）。右模糊 `LIKE '张%'` 可以走。

观测：`EXPLAIN` 的 `key` 和 `key_len`。`key=NULL` 或 `type=ALL` 就是没走。

**再追问：怎么确认走了几列？**  
看 `key_len`。优化器 ICP 可能在范围后仍过滤，但不要把 ICP 当联合索引还能往后用。

### Q3：RR 下 MVCC 和 Next-Key 各防什么？混用呢？

**★★★★★**

**场景**  
库存扣减用普通 `SELECT` 看余量，再 `UPDATE`。有人说「RR 不是可重复读吗，怎么超卖了？」

**完整解答**

每行 `trx_id` + undo 链。事务用 ReadView 找可见版本。RR 整事务一个 ReadView，快照读反复跑结果相同。

```
  快照读  --> MVCC     防：不可重复读（本事务里普通 SELECT 看见同一批行）
  当前读  --> Next-Key 防：当前读路径上的插入（幻行）
  先 SELECT 再 FOR UPDATE --> 仍可能看见快照后新插入的行
```

1. 快照读靠 MVCC，看不到快照后插入的行。
2. 当前读（`FOR UPDATE` / UPDATE / DELETE）靠 Next-Key 挡插入。
3. **先快照再当前读仍可能幻读。** RR 不是「这个事务里任何读都防幻」。

库存扣减用当前读或乐观锁 `version`，不要假设普通 SELECT 能锁住行。互联网很多业务用 RC；游戏账单/库存常留 RR 或显式加锁。

**再追问：undo 膨胀常见原因？**  
长事务不提交，purge 清不掉历史版本。合服比对挂着事务半小时，比一条慢 SQL 更难发现。

### Q4：主从延迟，`Seconds_Behind_Master=0` 就能读从吗？

**★★★★★**

**场景**  
活动发奖后从库延迟跳到 600 秒。玩家刚买的礼包在背包列表里看不见。群里有人要重启从库。`Seconds_Behind_Master` 已经回到 0。

**完整解答**

不能当真理。先画复制路径，再对号入座。

```
  主库提交
     |
     v
  binlog  -->  从库 IO 线程  -->  relay log  -->  SQL 回放
                                                   ↑
                                         大事务在这里卡死
```

1. IO / SQL 线程是不是 Yes，`Last_SQL_Error` 有没有。
2. GTID 差、`Relay_Log_Pos` 还动不动。
3. 主库 `INNODB_TRX` 有没有跑了数分钟的事务。
4. 从库磁盘是否和备份抢 IO。

`Seconds_Behind_Master` 是 SQL 线程时钟差：大事务回放中会跳变，并行复制会低估。并行 worker 只能并行**不同事务**；一个 10 分钟 `UPDATE` 百万行，从库至少卡 10 分钟。游戏买道具「刚写就读」走从库会脏 → **该接口读主**。

止血：切读主；活动暂停刷表。根因常是合服/发奖大事务。不要为了「做点什么」去重启从库。

**再追问：并行复制开了延迟还在？**  
单事务内部串行。先拆事务，再调 worker。

### Q5：误 DELETE 怎么 PITR？回档只回 MySQL？

**★★★★★**

**场景**  
运营误跑了 `DELETE FROM mail WHERE 1=1`。发现时已经过了 40 分钟。有人说从库上还有数据。

**完整解答**

生产全量用 **xtrabackup**（或云一致性快照），binlog **实时归档**到另一台。dump 只适合小库。

```
  全量（xtrabackup）          binlog 连续归档
         |                           |
         +------ PITR：恢复全量，再放到错操作前的 GTID / 时间
```

1. 停写，冻结相关活动。
2. 全量恢复到**新实例**，不要在主库上试修。
3. 重放 binlog 到 DELETE 之前。
4. 对账后再切。

从库能当源，但主从一起误 DDL 会一起坏。延迟从库才能扛「几小时后才发现」。没做过 restore 演练的备份不算数。`expire_logs_days` 必须覆盖发现窗口。

**游戏回档不能只回 MySQL。** Redis 背包缓存、对象存储邮件附件、发货状态要对齐位点，只回 MySQL 会脏。完整流程见 08-07。

**再追问：从库能当唯一备份吗？**  
不能。独立备份 + 延迟从库都要。主从一起执行的错误 DDL，两边一起坏。

### Q6：2000 万行表加索引？

**★★★★★**

**场景**  
开服第三天，`player` 两千万行。有人准备高峰直接 `ALTER TABLE player ADD INDEX ...`。

**完整解答**

禁止高峰锁表 ALTER。copy 算法会双倍磁盘并阻塞写。8.0 先在从库验证是否 `INSTANT` / `INPLACE, LOCK=NONE`，不要信文档「都能 inplace」。INPLACE 仍可能持 MDL。

```
  原表 --binlog--> gh-ost 追增量 --> 影子表
                                      |
                                Rename 切表（秒级）
                                      |
                                旧表先留着，别立刻 drop
```

1. 控速，避开开服/活动整点。
2. 切表盯 MDL 和主从延迟。
3. 杀一半的 OSC 要清影子表。

pt-osc 用触发器，写放大、和业务触发器冲突。gh-ost 读 binlog，更适合高写表。`chunk-size` 开太大一样把主库 CPU 打满。

**再追问：INSTANT 加列之后从库延迟呢？**  
INSTANT 本身秒级，但统计信息没更新时计划可能变差。加完要看慢日志，不是「秒级就等于无影响」。

### Q7：无索引 UPDATE 为什么能把开服打挂？

**★★★★**

**场景**  
活动补发：`UPDATE player SET flag=1 WHERE note='summer'`（note 无索引）。登录接口开始大面积超时，错误日志里有 1213。

**完整解答**

无索引 UPDATE/DELETE 在 RR 下是当前读：扫全表 + Next-Key 锁大量间隙，等于锁表。无关的登录 SQL 被堵住，复制延迟跟着爆炸。

```
  无索引 UPDATE（RR）
       |
       v
  当前读扫全表 + Next-Key 锁间隙
       |
       v
  等于锁表 → 登录等待 / 连环死锁 / 从库回放再卡一截
```

WHERE 必须走主键或二级索引。查死锁：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`。生产开 `innodb_print_all_deadlocks`。

止血：确认业务重试是否吃掉 1213；必要时 `KILL QUERY`，先报业务。治理：统一加锁顺序、短事务、禁止无索引刷表。

**再追问：`KILL QUERY` 前先看什么？**  
回滚成本。合服中途杀连接，回滚可能比原语句更久，undo 打满、从库再卡一截。QUERY 只杀语句；KILL 连接回滚整事务。

## Redis 与缓存

### Q8：fork 如何打出 P99 尖刺？

**★★★★★**

**场景**  
晚高峰每到整点游戏心跳超时一批。`latest_fork_usec` 到 25 万。刚好 AOF 重写阈值到了。有人准备改成 `SAVE`「快一点写完」。

**完整解答**

BGSAVE / AOF 重写都要 fork。内存越大、写越密，父进程卡得越久。

```
  BGSAVE / BGREWRITEAOF
       |
       v
  fork 复制页表（内存越大越慢）
       |
       +-- 父进程：命令全部排队  →  P99 尖刺
       +-- 子进程：写盘；父改页则 COW
       +-- 磁盘打满：父进程 fsync 也被拖
```

把 `latest_fork_usec` 和客户端超时对齐。>10 万 μs 当故障看。`SAVE` 同步冻住，生产禁止。高峰禁手动 BGSAVE；重写窗口挪到低峰。根因：单实例内存过大、AOF 重写太勤、数据盘 IO 打满。

**再追问：SAVE 和 BGSAVE？**  
SAVE 同步冻住，生产禁止。BGSAVE 仍会 fork，只是不在前台死等。缓存可丢用 RDB；要少丢开 AOF `everysec` + 混合 preamble。

### Q9：Cluster 能否解决热 key？大 key 迁槽？

**★★★★★**

**场景**  
3 主 Cluster。活动配置一个 key，其中一台 CPU 90%，另外两台 10%。迁槽之后热点还在同一台。有人准备再加节点。

**完整解答**

不能。Cluster 只按 slot 分片，一个 key 仍在一个主上。迁槽只是把这个 slot 搬到另一台，热点跟着走。

```
  CRC16("activity:config") % 16384 = 固定 slot
                |
                v
         永远打同一主；加节点没用
```

热 key：L1 挡住读，或拆成 `hot:id:{0..N}` 随机读。大 key：`--bigkeys` 低峰采样，先拆再 reshard，否则迁槽卡死。红线经验：String > 10KB，集合元素 > 5000。删除用 `UNLINK`，不要 `DEL` 大对象。

Cluster 吃的是多核和容量。一个大 key / 热 key 仍在一个核上。

**再追问：读写比极高的配置怎么做？**  
逻辑过期 + L1；几乎不给物理 TTL，避免整点击穿。架构层预热、回源限流见 03。

### Q10：排行榜用什么？全服一个 ZSet？

**★★★★★**

**场景**  
全服战力榜一个 key `rank:global`，`ZRANGE 0 -1` 给客户端拉全量。开服一周 member 到 50 万，活动开始 Redis P99 炸。发奖以这个 ZSet 为准。

**完整解答**

用 ZSet。score 排序 + `ZREVRANGE` / `ZRANK` 是 `O(log n)`。问题不在结构，在**一个 key 扛全服**。

```
  rank:global
       |
       +-- 热 key（所有逻辑服打同一 slot）
       +-- 无限长大
       +-- ZRANGE 0 -1 = 阻塞单线程
```

按服拆 `rank:s1` / `rank:s2`；只留 Top N，`ZREMRANGEBYRANK` 裁尾。同分用时间戳做小数位。跨服榜离线汇总，逻辑服不要直打同一热 key。

**榜不是账本。** 发奖以 MySQL / 对账为准。把发奖资格写在 ZSet 里，切主丢几秒写就会错发或漏发。

**再追问：ZSet 能当消息队列吗？**  
能做简陋延迟队列，没有消费组、没有积压治理。核心链路用 Kafka。

### Q11：穿透/击穿/雪崩 + 先写谁？

**★★★★★**

**场景**  
开场就问「缓存三大问题」。有人把 Redis 挂了说成击穿，把扫号说成雪崩。商城改完价格，有人在写路径里 `SET` 新对象。

**完整解答**

必须分清「几个 key、缓存里有没有过、DB 有没有」。三大问题是**用法**，不是 Redis HA。

```
  穿透：id 根本不存在
    请求 --> L2 miss --> DB miss --> 再来仍 miss

  击穿：一个热 key 刚好过期
    并发 miss --> 全部打 DB 同一行

  雪崩：大量 TTL 对齐，或 Redis 挂了
    全部 miss --> DB QPS × N
```

穿透：空值短 TTL / 布隆 / 网关限流。击穿：互斥锁重建或逻辑过期。雪崩：TTL + random、限流、HA、预热。

写：**先提交 DB，再 DEL 缓存**。写路径 SET 容易旧值盖新值。先删再写，空窗里读会把旧行回填。

**再追问：先删再写呢？**  
空窗里并发读会把旧行 SET 回去，脏得更久。生产默认先写再删。关键路径写后读主。

### Q12：DB QPS×5 但 Redis up=1？

**★★★★★**

**场景**  
活动开始 2 分钟，MySQL 连接打满。Redis `ping` 通，CPU 不高。全局命中率还显示 97%。刚发过一版，改了序列化。

**完整解答**

Redis alive 不等于命中率正常。全局 97% 会掩盖单个接口全 miss。告警盯**回源 QPS**，不要只盯 Redis up。

```
  发版改 key 前缀 / 序列化
       |
       v
  新代码 GET 全 miss（旧 key 还在，对不上）
       |
       v
  回源 ×5 → DB 连接打满
```

按接口看 miss。对齐时间线：发布 / 活动 / flush / 切主。也查：超时被当成 miss、`latest_fork_usec`、`evicted_keys`、慢 SQL。

止血：限流、延长 TTL、打开 L1、熔断非核心回源。发版改序列化换 key 版本，禁止 `FLUSHALL`。

**再追问：fork 和 miss 有什么关系？**  
父进程卡住超时，应用当 miss 打 DB，表现为雪崩。Redis 进程还活着。

### Q13：Redis 挂了怎么止血？

**★★★★**

**场景**  
哨兵切主失败，Redis 集群不可写。登录和商城一起打 MySQL，连接打满。有人要立刻把全部流量切回源「先顶住」。

**完整解答**

无降级开关就会第二次雪崩。先保登录和支付，非核心接口熔断或返回缓存旧值。

```
  Redis 挂
     |
     +-- 无开关：全部回源 → DB 二次雪崩
     +-- 有开关：限流 / 降级 / 只放登录支付
                    |
                    v
              恢复后预热再放量
```

1. 限流直连 DB 或降级非核心。
2. 保登录、支付；排行榜、邮件列表可以旧。
3. 恢复后先预热热点，再按比例放量。
4. 钱包 / 道具以 MySQL 为准，切主丢的缓存回源回填即可。

Cluster / 哨兵解决的是进程挂了谁顶上，不解决「应用超时当 miss」。

**再追问：恢复后立刻全量放量？**  
不要。冷缓存全 miss 等于再雪崩一次。预热热点、按比例放量。

### Q14：分布式锁能保证支付幂等吗？

**★★★★**

**场景**  
支付回调用 `SETNX order_lock` 再处理。TTL 5 秒，偶尔回调超过 5 秒，出现双入。有人建议上 Redlock。

**完整解答**

不能。`SET key uuid NX PX ttl` + Lua 校验 uuid 再 `DEL`，只减并发。不要 `GET` + `DEL`。

```
  锁过期 / failover 丢锁 / 分区双主
       |
       v
  两个回调都以为拿到锁 → 双入
```

过期太短业务没完会并发；太长故障恢复慢。failover 丢锁、TTL 到期、Redlock 在分区下的争议，都会双入。

支付幂等用 **DB 唯一键**（订单号）。锁是辅助，不是账本。核心交易不靠 Redis 锁当事务。

**再追问：Redlock 呢？**  
多实例锁争议大。核心交易不靠它。答到「唯一约束才是幂等，锁是辅助」就够。

## 网关

### Q15：502 vs 504 vs 499。

**★★★★★**

**场景**  
活动开始入口 5xx 上涨。有人重启逻辑服，有人调大 `proxy_read_timeout`。error.log 里既有 `Connection refused` 也有 `upstream timed out`，还有一批 499。

**完整解答**

先画谁没等到谁，再对 error.log 关键字。不要一上来重启。直连后端端口核对。

```
  网关把请求交给上游
       |
       +-- 连不上 / 空响应 / 协议错 ----> 502
       +-- 连上了，读超时 --------------> 504
       +-- 客户端先断开 ----------------> 499
```

502：没拿到合法上游 HTTP 响应。看刚发版、探针杀了进程、Endpoints 空。  
504：连上了，读超时。治本是后端，调超时是止血。  
499：客户端先断开。常是 SLB / SDK 超时比网关短。不是后端没启动。

观测：`$upstream_response_time`、`$upstream_addr`。`limit_req` 超限是 503，不要当成 502。

**再追问：499 按 502 去重启后端？**  
不要。先对更上游的 deadline。客户端已经走了，重启只会拆掉还活着的连接。

### Q16：超时链怎么排？

**★★★★★**

**场景**  
CDN 30s、网关读 60s、应用 40s、MySQL 慢查询 50s。用户看到错误页，网关一堆 499，应用线程池仍被慢查询占满。

**完整解答**

从外到内一跳比一跳短：外层必须能等到内层返回错误。反了就会入口先 504/499、后端还在跑。

```
  对：玩家/CDN 60s > 网关读 50s > 应用 40s > DB 30s
                    504 出在网关，后端来得及返回错误

  错：CDN 30s < 网关 60s < DB 50s
       → 玩家先走，网关 499，应用白跑，连接占满
```

`proxy_connect_timeout` 短（几秒）；`proxy_read_timeout` 按接口 P99 留 2～3 倍。长轮询 / WS 单独 location，不能全局 60s。

**调大超时是止血。** 治本是后端慢。超时过长会让 worker 被慢请求占满，故障放大。Ingress 要看注解最终渲染的值。

**再追问：调大超时是不是就好了？**  
止血可以。治本是后端。过长会放大故障。和缓存「超时当 miss」是同一类时间预算错误。

### Q17：为何必须 upstream keepalive？

**★★★★**

**场景**  
网关 QPS 上去之后，后端 `TIME_WAIT` 爆炸、短暂端口耗尽。另一环境 `max_fails=1`，一次抖动后 `no live upstreams`，全站 502。

**完整解答**

默认对上游短连接，高 QPS 打满后端 TIME_WAIT 和本地端口。必须 `keepalive` + HTTP/1.1 + 空 `Connection` 头。

```
  短连接：每次请求握手 + 四次挥手 → TIME_WAIT 堆积
  keepalive：复用到上游的连接，QPS 上去才扛得住
```

玩家到战斗服的长连接是另一件事，不要混。开源 Nginx 只有被动 `max_fails` / `fail_timeout`，真实请求失败才摘，有探伤窗口。过严会雪崩摘空 → `no live upstreams`。

keepalive 可能粘在已坏节点上，要和探活、`$upstream_addr` 一起看。

**再追问：开源 Nginx 健康检查？**  
只有被动，有探伤期。阈值太小，抖动时 502 从一台扩散成全部。主动探活要 Plus / 云 LB / APISIX / Envoy。

### Q18：APISIX 相对 Nginx 只记什么？etcd 挂了？

**★★★★★**

**场景**  
「APISIX 也是 Nginx 吧，超时题可以按 02-23 答。」etcd 抖动，有人要重启全部 APISIX Pod。

**完整解答**

只记三件事：etcd watch 热配、插件链、不用 reload。数据面仍是 OpenResty，502/504/超时链同一套。Envoy 对照一句话：xDS 热配置。

```
  Admin / CI → etcd → Watch → worker 内存里的路由 → 转发
```

etcd 挂了：**已有路由继续转**，Admin 不能改配置。不会立刻全站 502。**不要重启数据面**——内存路由会丢，若无法再 watch 才会真正中断。etcd 原理和选举见 04-02，本章不展开。

不是一定要上 APISIX。需要频繁热更新、细粒度插件时才值得。纯反代 Nginx 更简单。

**再追问：所以一定要上 APISIX？**  
不必。热配和插件是理由。超时链、502/504 在两种数据面上是同一套题。

### Q19：战斗长连接挂七层 HTTP？

**★★★★**

**场景**  
大厅 HTTP 已经在 Nginx。有人把战斗 WebSocket 也接进去，全局 `proxy_read_timeout 60s`。心跳 20s。限流按 IP 100r/s，握手和心跳算进同一桶。

**完整解答**

大厅 HTTP 可以。战斗 WS / TCP 默认 60s 读超时会踢人；reload 会断线。

```
  大厅 / 商城 HTTP     →  七层网关
  战斗长连接           →  四层 LB 或专用网关
                         单独读超时 ≥ 心跳 × 2～3
                         Upgrade / Connection
                         心跳不要进 API 限流桶
```

必须单独 location 拉长超时和 Upgrade，或走四层。心跳别进 API 限流桶，否则整服 NAT 一个出口 IP 会被误伤。Ingress-nginx 查注解最终渲染的 `proxy_read_timeout`。

**再追问：Ingress-nginx 超时对不上？**  
查注解渲染出来的值。数据面仍是 Nginx，码和超时链同一套。见 Q39。

## Kafka

### Q20：加消费者一定降 Lag 吗？

**★★★★★**

**场景**  
发奖 Topic 3 个分区，Lag 到了几百万。有人把消费组副本从 3 扩到 10，Lag 几乎没动，还多了 7 个空转的 Pod。下游 MySQL 已经慢。

**完整解答**

并行度上限 = 分区数。同一时刻一个分区只能被组内一个消费者拉。加消费者之前先比生产/消费速率。

```
  Topic reward-event
     P0  P1  P2
      |   |   |
      v   v   v
  Group 里最多 3 个消费者真正在拉
  第 4～10 个：没有分区，空转
```

1. 分区数不够才扩分区（只增不减）。
2. 下游已经慢，加消费者会把 DB 打死。
3. 单分区热点（3 个里只有 1 个 Lag 爆）加消费者没用。

带 key 扩分区后 `hash(key) % n` 变了，依赖顺序的消费组要评估。

**再追问：无 key 的消息顺序还保得住吗？**  
保不住。无 key 轮询打到不同分区，跨分区无序。要同订单有序，用 `order_id` 做 key。见 Q24。

### Q21：可靠写三件套还可能丢？

**★★★★★**

**场景**  
支付发货 Topic 有人觉得「acks=all 就等于不丢」。活动中一台 Broker 磁盘慢，ISR 掉到只剩 Leader。消费组开了自动提交，客诉有的邮件没到。

**完整解答**

`rf=3 min.isr=2 acks=all` 只管**进 Kafka**。后面三层仍可能丢。

```
  进 Kafka：rf=3, min.isr=2, acks=all, 看 callback
       |
       +-- 消费先提交 / 自动提交 / 异常被吞仍提交  → 丢
       +-- retention 到期、磁盘删段              → 丢
       +-- 误 --reset-offsets to latest          → 丢
```

`acks=all` 等的是 ISR 全部确认，不是集群每一台。ISR 只剩 1 时 `min.isr=2` 会拒写——这是保数据，不要降 min.isr 换吞吐。

Exactly once：Kafka 事务只在 Kafka 链路内。进 MySQL 仍要唯一键。生产口头：**At least once + 幂等消费**。

**再追问：拒写的时候业务怎么办？**  
Producer 失败进补偿表，限非核心 Topic 保发货，修 Follower 让 ISR 回来。不要降 min.isr。

### Q22：Lag 排查顺序。

**★★★★★**

**场景**  
活动整点，`reward-worker` 平均 Lag 看起来还行，但有一个分区 Lag 在直线涨。有人准备把消费者再加一倍。

**完整解答**

按层查，不要先加机器。平均 Lag 会骗人。

```
  1. describe 组：哪个分区在涨？
  2. 生产速率 vs 消费速率：差为正才是还在恶化
  3. 消费者在不在、是不是一直 rebalance（Lag 锯齿）
  4. 下游耗时：慢 SQL、Redis、HTTP、线程池打满
  5. 单分区热点：key 是不是都是同一个活动 id
  6. Broker：磁盘、URP、生产/拉取 P99
```

```
  produce --------->  partition log  ---------> consume
       速率↑              Lag = 差                  速率↓
                         只看平均值会漏掉单分区直线涨
```

止血：下游慢 → 限产或扩下游。毒消息进死信。热点改 key。分区不够再扩分区。

**再追问：Lag 锯齿涨跌是什么？**  
反复 rebalance。消费者进进出出、处理超时被踢，停下来查会话超时和下游 hang，不要加副本掩盖。

### Q23：怀疑丢消息怎么分层？

**★★★★**

**场景**  
客诉「有的邮件没到」。群里有人说 Kafka 丢了，有人说业务过滤了。没有分层就在 Broker 上翻盘。

**完整解答**

从外到内四层，不要一上来怪 Broker。

```
  1. Producer  回调失败？重试？acks？有没有进补偿表
  2. Broker    ISR / acks / 磁盘 / retention 是否到期
  3. Consumer  先提交再处理？reset 到 latest？乱序提交跳过
  4. 业务      过滤条件、幂等表挡掉、发奖接口自己失败
```

先对 offset 和时间戳：这条消息进过 Topic 没有、消费组提交过没有。处理函数抛异常但自动提交已经往前走，是真丢。消费多线程乱序提交，中间那条会被跳过，也是真丢。

核心组关掉自动提交，处理成功再提交。埋点、可丢失的打点才开自动提交。

**再追问：自动提交能不能开？**  
埋点可以。发奖、支付、合服流水禁用。

### Q24：同订单有序怎么做？

**★★★★**

**场景**  
支付成功和发货两条消息，偶发「先发货后扣款」的乱序。Topic 有 16 个分区。有人要把分区改成 1「全局有序」。

**完整解答**

分区内有序、跨分区无序。同订单用 `order_id` 做 key，哈希进同一分区，该分区上串行消费。

```
  key=order_id  -->  hash % N  -->  同一分区
                                      |
                                      v
                               该消费者串行处理
```

全局有序 = 单分区，吞吐打成一条队列，不要。无 key 轮询打到不同分区，顺序保不住。扩分区会改变 `hash % n`，依赖顺序的组要评估。

下游还要幂等：Kafka 至少一次，重复消息用 DB 唯一键挡，玩家看到的是 DB 状态不是消息次数。

**再追问：分区内多线程消费还能保序吗？**  
不能。同一分区交给一个消费者，这个消费者内部也要按 offset 串行，或按 key 再分队列且不能乱序提交。

## Prometheus 与日志

### Q25：Counter 为什么不能直接比阈值？

**★★★★★**

**场景**  
有人写了 `http_requests_total > 10000` 当告警。活动开始一直响。另一条 P99 用了 Histogram 但没 `by (le)`，数字完全不对。

**完整解答**

Counter 只增不减。绝对值跨进程重启、跨时间没有含义。告警用 `rate()`（区间均值，稳）；看板突发用 `irate()`（最近两点，跳）。

```
  错：http_requests_total > 10000          只增，阈值无意义
  对：rate(http_requests_total[5m])        每秒增量

  Histogram P99 必须保住 le：
  histogram_quantile(0.99,
    sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
```

没有 `by (le)` 会把不同桶混在一起，分位数算错。`increase()` 注意 Counter 重置。游戏 HTTP 用 RED；机器和中间件用 USE。不要只靠 CPU 当业务告警。细节见 04-18。

**再追问：为什么延迟不看平均值？**  
平均值被长尾淹没。P99 才能看见「少数人卡死」。必须从 Histogram / Summary 算，Counter 没有分位数。

### Q26：高基数一个错例。

**★★★★★**

**场景**  
有人给登录接口加了 `http_requests_total{role_id=...}`。Prometheus 开始 OOM。有人说上 Thanos 就能扛。

**完整解答**

一条 series = 指标名 + 全套 label。`role_id` / `user_id` / `order_id` 当 label，会把 TSDB 打爆。

```
  错：http_requests_total{role_id="100861"}   每个玩家一条 series
  对：http_requests_total{code, method, route}  低基数枚举
      role_id 进日志 / Trace
```

id 进日志和 Trace，不要进 metrics。`prometheus_tsdb_head_series` 做容量告警。远程存储（Thanos / VM）解决留存和全局查询，**不解决**乱打 label。先 drop relabel、停错误指标，再谈扩存储。

**再追问：Loki 能用 role_id 当 label 吗？**  
不能。Loki 高基数 label 一样炸。见 Q28。

### Q27：告警风暴三件套 + 该不该叫人。

**★★★★★**

**场景**  
磁盘 82%、某测试 NS 一个 Pod 重启、生产支付 5xx 到 8%，三条一起响。值班不知道先接哪条。有人准备无限期 silence。

**完整解答**

三件套：group / inhibit / silence（有时限）。叫人同时满足：用户或收入正在受损、有可执行动作、不是同一故障的回声。

```
  P0  用户/收入正在受损 + 可行动     电话
  P2  CPU 90% 但 SLO 健康           不叫，工作时间
  节点挂了 --inhibit--> 该节点 PodDown（回声）
  维护窗口 silence，结束必须解开
```

支付 5xx 8% 是 P0/P1。磁盘 82% 是 P2。测试 NS 重启是 P3 或不告。CPU 90% 但登录 SLO 健康不叫。每条要有 Runbook。`for` 防抖。无限期 silence 等于拆掉告警。细节策略见 03-Kubernetes/18-监控与可观测性。

**再追问：P0 能不能定义为 CPU >90%？**  
不能。CPU 高不一定有用户损伤。P0 用 5xx、登录失败、支付挂这类症状。

### Q28：Loki vs ES vs 云日志。

**★★★★★**

**场景**  
领导想「日志、检索、留存报表一个集群搞定」。账单已经很难看。有人把 `role_id` 做成 Loki label。

**完整解答**

排障按 label 拉一段时间 → Loki / 云日志。全文、关键词、客服搜玩家 → ES。亿级聚合、漏斗 → ClickHouse（不单开章，答到选型即可）。

```
  按服 / level / pod 拉日志     --> Loki（便宜，见 K8s 19）
  全文、客服搜、异常 IP         --> ES
  运营报表、group by 全服付费   --> CH，不要逼 ES
```

`role_id` 不当 Loki label，正文检索走 ES。人少选 SLS/CLS，盯扫描费，查询 `*` 能把月预算打穿。可以并存：热搜进 ES，长期进 Loki 或对象存储。不要一个集群扛所有。

**再追问：游戏生产怎么拆？**  
应用日志 Loki；需要搜内容的行为/客服 ES；运营报表 CH。

### Q29：ES yellow vs red。

**★★★★**

**场景**  
健康值 Yellow。有人重启了一台 Data。随后变 Red，部分日志搜不到。另有人要缩副本「先变绿」。

**完整解答**

Yellow = 主分片都在，**能搜全**，只是缺副本。Red = 有主分片没了，**数据缺**，当 P0。不要为了变绿乱缩副本、乱重启。

```
  Yellow：主在、副本没位置        能搜，先 explain
  Red：   有主分片没了            缺数据，P0
  flood： 磁盘约 85% 只读         先清盘，再摘 read_only
```

先 `GET _cluster/allocation/explain`，再动手。单节点集群没有地方放副本，会一直黄，这是拓扑不是故障。磁盘满了采集还在推，ES 拒写；清旧索引或 ILM，然后**手动摘** `read_only_allow_delete`。先别重启 Filebeat。

**再追问：磁盘满了会怎样？**  
约 85% 只读，95% 更狠。flood 先处理磁盘，不要为变绿乱缩副本。

### Q30：日志成本第一刀砍哪？

**★★★★**

**场景**  
ES / Loki 账单翻倍。有人准备加节点。应用刚加了 DEBUG，网关 access 全量开着。某接口死循环打日志。

**完整解答**

第一刀：**DEBUG 和全量 access**。体积 × 保留 × 副本，砍这三项比加机器快。

```
  成本 = 写入量 × 保留天数 × 副本数
           ↑
     DEBUG / 全量 access / 死循环
```

暴涨先认应用死循环（同一 `trace_id` 刷屏、同一错误每秒几千行），再扩集群。热数据 7 天、冷归档对象存储。采样 access，业务错误日志全留。Loki 不要用高基数 label 放大 series。云日志盯扫描费。

**再追问：先扩集群行不行？**  
能顶一阵，账单和堆一起涨。先砍写入和保留，死循环不处理加多少节点都会再满。

## SLO 与综合

### Q31：给登录写 SLI/SLO/错误预算。

**★★★★★**

**场景**  
产品要把可用性写成 99.99%。研发想周五晚上发战斗服热更。没有人能说出这个月还能「坏」多久。有人把 SLI 定义成 CPU <80%。

**完整解答**

SLI 是怎么量，SLO 是目标，Error Budget = 1 − SLO。不是 CPU。

```
  SLI：28 天内，登录成功且 <3s 的比例
  SLO：99.9%  →  预算约 43 分钟/月
  成功定义：超时、5xx、连不上都算失败
```

热更 / 合服 / 滚动踢玩家计入非自愿断线，不能开除。SLO 用近三个月实际再留余量，不是拍 9999。活动高峰单独看燃烧率，避免被月平均掩盖 10 分钟崩溃。预算谁用：研发拿它排期，SRE 看消耗速率。细节见 04-18。

**再追问：只看 28 天慢烧够不够？**  
不够。再加短窗口高燃烧率，正在崩时要立刻叫人。两套窗口一起用。见 Q32。

### Q32：燃烧率短窗口 vs 长窗口。

**★★★★★**

**场景**  
压测 10 分钟 5xx 拉高，值班被叫起来。另一周每天漏 2 分钟登录失败，28 天预算快烧完了，没有人打电话。

**完整解答**

短窗口高燃烧 = 正在崩，叫人。长窗口慢烧 = 上班处理。只看瞬时 5xx 或只看 28 天都会错。

```
  短窗口（1–2h）燃烧率高  -->  正在崩，立刻叫人
  长窗口（28d）慢烧       -->  预算在漏，工作日处理、冻发布
  只看瞬时 5xx            -->  压测误叫
  只看 28 天              -->  正在崩时太晚
```

错误预算可以预借（活动窗口、合服），写进变更单，事后用低峰稳定性还。两套窗口一起配 Alertmanager，不要用一条 5xx 阈值代替 SLO。

**再追问：活动高峰要不要单独看？**  
要。月平均 99.9% 能掩盖整点 10 分钟崩溃。高峰用独立燃烧率。

### Q33：OTel 解决什么不解决什么？

**★★★★**

**场景**  
「我们上了 OpenTelemetry，可观测性就齐了。」自动插桩开太全，Collector 被打满。战斗服用 C++，没有自动库。

**完整解答**

OTel 统一采集和传播：一份 SDK 打点，OTLP 进 Collector（Receive → 采样/脱敏 → Export），换后端不换埋点。

```
  解决：SDK / 传播 / 换后端不换埋点
  不解决：没 SLO、乱采样打挂后端、没业务语义
  战斗服 C++：常常只能手埋出入口和 DB/Redis
```

不解决没 SLO、乱采样打挂后端、敏感字段没剥。自动插桩开太全会把 Collector 和存储打爆，采样要在入口做。OTel 不是可观测性本身。游戏战斗服常要手埋。细节见 04-18。

**再追问：自动插桩会不会踩高基数？**  
会。框架把 `role_id` 打进 span attribute / metrics label，一样炸。入口采样 + Collector 脱敏。

### Q34：活动高峰先扩哪一层？不能扩哪？

**★★★★★**

**场景**  
周年庆整点。有人把逻辑服副本 ×2，有人把 Kafka 消费者 ×3，有人说主库再加从库就能写。缓存没预热。错误预算这周已经烧了一半。

**完整解答**

无状态入口/大厅可扩。有状态逻辑服、单热 key、单分区、主库写，扩副本没用。

```
  可扩：大厅 / 网关 / 无状态 API
  扩了没用：
     有状态逻辑服（身份、内存局）
     全服一个 ZSet / 活动配置热 key
     Kafka 3 分区再加第 4 个消费者
     主库写入（从库只分担读）
```

先预热缓存、限回源、保支付 Topic。错误预算可以预借，写进变更单。高峰不要做大表 DDL、不要 `KEYS`、不要扩一个已经热点的分区。

**再追问：错误预算不够还能发吗？**  
可以预借，写进变更单，事后用低峰稳定性还。不是偷偷发。

### Q35：一次故障里 Metrics → Trace → Logs 怎么走？

**★★★★★**

**场景**  
登录 P99 从 200ms 跳到 3s。Grafana 红了。有人直接翻全部 INFO 日志。没有人带着 `trace_id`。

**完整解答**

RED 告警定服务和时间 → Trace 找慢 Span → `trace_id` 拉日志。缺 Trace 就靠网关 access 里的 `trace_id` 字段。

```
  Metrics（RED）  哪个服务、哪几分钟、错误还是慢
       |
       v
  Trace           哪个 Span：网关 / 应用 / Redis / MySQL
       |
       v
  Logs            用 trace_id 精确拉，不要 grep 全量 INFO
```

不要一上来翻全量日志。没有 Trace 时：网关 `$request_time` vs `$upstream_response_time` 判断慢在哪一层，再用时间窗 + `role_id` 收敛。三条信号对不上，通常是时钟或没注入传播头。NTP 见 02-19。

**再追问：只有 Metrics 没有 Trace 呢？**  
靠网关耗时拆分和慢日志。事后补传播头，不要每次故障都全量 grep。

### Q36：读写分离 vs 缓存 vs 分库，游戏库怎么选？

**★★★★**

**场景**  
角色表 8000 万行，加一列 DDL 要小时级。有人说「上 TiDB」，有人说先加从库，有人说先上 Redis。慢 SQL 还没加索引。

**完整解答**

先索引和一服一库。不要一步上分库。

```
  1. 索引 / 慢 SQL / 一服一库     大多数游戏已经拆过
  2. 读多且可脏 → 从库；刚写就读 → 读主
  3. 读放大 / 热点 → 缓存（先 DB 再删）
  4. 写爆了、DDL 锁太久 → 再垂直拆，最后水平分表
```

读多且可脏用从库；买道具刚写就读要读主。读放大用缓存。写打满 CPU/IO、单表亿行 DDL 锁太久，再分表。垂直（账号/支付/玩法分库）先于水平。数据量没到、慢 SQL 没索引，先看 01。

**再追问：只分表不分库够不够？**  
能减单表体积和 DDL，写入和连接还在同一实例上。写满 CPU/IO 必须分库或换实例。

### Q37：哪些命令/操作生产要拒绝或审批？

**★★★★**

**场景**  
高峰有人 `KEYS *mail*`，有人准备 `ALTER` 加索引，有人 `kafka-consumer-groups --reset-offsets` 没 dry-run，还有人把 Alertmanager silence 设成了 90 天。

**完整解答**

这些不是「最好别用」，是生产拒绝或走审批：

```
  Redis     KEYS * / FLUSHDB / FLUSHALL / 高峰 SAVE / 长时间 MONITOR
  MySQL     高峰 ALTER 锁表 / 无索引刷表 / KILL 长事务不评估回滚
  Kafka     --reset-offsets 无 dry-run / 核心组 reset to latest
  Nginx     kill -9 master / 高峰对战斗长连接 reload
  ES        Red 时乱缩副本、乱重启 Data
  告警      无限期 silence
```

替代：`SCAN`、gh-ost、`--dry-run`、`UNLINK`、有时限的 silence。高峰变更默认拒绝，低峰也要变更单。杀一半的 OSC / 重置消费组之前先能回滚。

**再追问：低峰就可以 KEYS 吗？**  
大实例低峰 `KEYS` 也会卡住单线程。一律 `SCAN`。低峰也不是免费通行证。

### Q38：主从延迟、缓存脏读、Kafka 重复，对「玩家刚买的道具」分别怎么解释？

**★★★★★**

**场景**  
玩家付款成功，背包列表没有道具。群里三派：从库落后、缓存没删、Kafka 发了两次。有人要同时重启 MySQL、Redis、消费者。

**完整解答**

三套机制都不是账本，账本在 MySQL。先对订单行，再解释玩家看见的现象。

```
  从库落后     刚写走从库 → 读主（或关这条链路的从库路由）
  缓存未删     先 DB 再 DEL；删失败补；关键路径读主
  Kafka 重复   发货幂等（订单号唯一键）；玩家看到的是 DB 状态，不是消息次数
```

1. 订单表有这一行且已发货 → 展示层脏，读主或删缓存。
2. 订单没有 → 支付回调/写入失败，不是缓存问题。
3. Kafka Lag 或重复 → 查消费幂等表，不要按消息次数给玩家补发。

不要三套一起重启。先读主核对订单，再动缓存和消费者。

**再追问：切 Redis 主之后钻石看不见，订单是成功的？**  
异步复制切主会丢几秒缓存写。钱包以 MySQL 为准，回源回填。AOF 救的是该节点重启，不是已经切到落后从库。

### Q39：Ingress-nginx 超时和你在虚机 Nginx 上学的是不是一套？

**★★★**

**场景**  
「集群里的 Ingress 超时应该跟虚机 Nginx 不一样吧？」YAML 写了注解，线上 `proxy_read_timeout` 仍是 60s，战斗 WS 被踢。

**完整解答**

是一套。数据面仍是 Nginx，502/504/499、超时链、keepalive 同一套判断。差别在配置从哪来：虚机看 `nginx.conf`，Ingress 看**控制器渲染出来的** `proxy_read_timeout`。

```
  注解 / ConfigMap  -->  Ingress controller 渲染 -->  worker 里的 Nginx
                         以渲染结果为准，不要假设和集群默认一致
```

查最终 ConfigMap / `nginx -T` 等价物，不要只看 YAML 意图。长连接单独 Ingress 或走四层。超时链外短内长，和 Q16 相同。细节 02-23 + 04-14。

**再追问：改了注解为什么没生效？**  
控制器没渲染进去，或被 ConfigMap 默认值盖掉。先看数据面实际值，再改 YAML。

### Q40：如果你只能盯三条中间件相关 SLO，带哪三条？

**★★★**

**场景**  
看板已经有 Redis QPS、ES 堆、节点 CPU、网关连接数。值班被这些指标叫起来，真正影响玩家的登录和支付却没有人认领。

**完整解答**

带用户能感知的三条，不要带资源水位。

```
  1. 登录 / 进战斗：成功且够快（SLI 带超时）
  2. 支付到账：下单到发货成功
  3. 错误预算燃烧率：短窗口叫人、长窗口冻发布
```

不要带 CPU、Redis QPS、ES 堆。那些是 USE，用来定位，不是叫人理由。中间件挂了会反映在这三条里：Redis 雪崩 → 登录变慢；主从延迟 → 背包读旧；Kafka Lag → 发货晚。看板可以留中间件指标，P0 必须绑 SLO。

**再追问：Redis 命中率要不要进 SLO？**  
当诊断指标，不当 SLO。命中率掉而登录仍然快，不必叫人；命中率还行但登录超时，必须叫人。
