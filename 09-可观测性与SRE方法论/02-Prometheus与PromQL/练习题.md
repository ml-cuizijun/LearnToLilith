## Q1

**★★★★★｜Prometheus 为什么要用 pull，而不是改成 push？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、抓取：pull 为什么是对的](知识点.md)

### 场景

面试官先说："我觉得 pull 模型很反直觉，服务部署在容器里 IP 总变，push 明显更自然。" 然后再问短任务和 Pushgateway 的事。


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：pull 让「采不到」本身就是一种告警信号，push 下客户端挂了只会静默丢失。

| 模式 | 谁主动 | 关键差异 |
|------|--------|----------|
| **pull** | Prometheus Server | scrape 失败 → `up == 0` 自然告警；配置、版本集中在服务端；curl 就能排障 |
| **push** | 客户端主动上报 | 防火墙友好，但服务端不知道"谁该来"，丢了数据要先发现客户端没上报 |

容器 IP 变不是问题，用 **服务发现**（service discovery）自动填 target 列表：K8s ServiceMonitor/PodMonitor、Consul、DNS、文件发现。scrape 仍然是 pull。

```bash
curl -sS http://gateway:8080/metrics | grep '^http_requests_total'
# http_requests_total{method="GET",status="200"} 12345  # ← 能 curl 通说明暴露层活着
```

> ⚠️ **别混**：Prometheus 不是"不能 push"，而是"不以 push 为主"。**Pushgateway** 只给短命任务（CI Job、一次性批处理）当临时中转，推完要清理；长服务推进去会因为序列不过期而"假活"。

> 📝 **面试**：先承认 push 在 firewall/NAT 场景有优势，再强调"没数据比假数据好"——pull 把可达性变成了 `up` 指标本身。

### 再追问

**那短任务怎么采？**——用 Pushgateway：任务结束时把指标推上去，Prometheus 再去拉 Pushgateway。但 Job 结束要删，否则序列一直存在，后续查询会误以为任务还在跑。

**生产上 pull 遇到防火墙怎么办？**——优先做网络规划让 Prometheus 能到达 target；真做不到再评估 Pushgateway 或 Prometheus Agent mode。**不要**因为"push 省事"就把长服务改成 push。

## Q2

**★★★★★｜Counter、Gauge、Histogram、Summary 各自什么时候用？Histogram 和 Summary 到底差在哪？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、暴露：/metrics 与四种指标类型](知识点.md)

### 场景

面试里常见连珠炮："在线人数用什么？请求数用什么？我要看集群 P99 延迟该用哪个？为什么？"


Counter vs Gauge。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：Counter 只增、Gauge 可上下、Histogram 服务端算分位可聚合、Summary 客户端算分位不能跨实例加。

| 类型 | 行为 | 该用的地方 |
|------|------|------------|
| **Counter** | 只增不减（可重置） | 请求总数、错误数、处理字节数 |
| **Gauge** | 可增可减 | 在线人数、队列长度、CPU 利用率、内存 |
| **Histogram** | 分桶 + 总和 + 总数 | 延迟、请求大小；要算**集群 P99** 必须用它 |
| **Summary** | 客户端直接算分位 | 只看单实例 P99；想跨实例聚合会错 |

Histogram 暴露的是桶计数：

```text
http_request_duration_seconds_bucket{le="0.005"} 200
http_request_duration_seconds_bucket{le="0.01"}  350
http_request_duration_seconds_bucket{le="+Inf"}  1000
```

服务端用 `histogram_quantile()` 在桶间线性插值算分位，并且可以先 `sum by (le)` 把所有实例的同桶计数加起来，得到**真正的集群 P99**。

Summary 暴露的是：

```text
http_request_duration_seconds{quantile="0.99"} 0.087
```

这个 0.087 只是当前实例的 P99。把 10 个实例的 P99 取平均**不是**集群 P99，因为高延迟可能在某个实例集中。

> ⚠️ **别混**：Summary 不是"不能用"，是"不能聚合"。单机进程内部看 P99 用 Summary 很合适；集群口径必须用 Histogram。

> 📝 **面试**：背口诀——"Counter 水表、Gauge 油表、Histogram 全班身高分布、Summary 只报门口最高的人"。

### 再追问

**Counter 为什么不能直接告警？**——因为 Counter 只增。`http_requests_total > 1e8` 永远 firing。必须用 `rate()` 或 `increase()` 看变化率。**不要**对 Counter 写直接阈值比较。

**Histogram 的 le 桶能查询时改吗？**——不能。`le` 桶在客户端定义好就固定了，查询只能在这些桶上插值。桶设计要覆盖业务真实分布，太宽插值不准、太多存储贵。

## Q3

**★★★★☆｜Counter 进程重启归零后，rate 会算出负值吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

发布时网关进程重启，有人担心 Grafana 上的 QPS 会突然变成负数或出现一个深坑。也有人建议在 exporter 里自己维护"持久化 Counter"。


rate / irate。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：不会，`rate()` 和 `increase()` 内部会检测 Counter 重置并自动修正。

```text
时间线：  1000 → 1200 → 1400 → [重启] → 0 → 50 → 100
rate 看到：
  1400→0  这一段被识别为"重置"
  实际按 (0 + 50) - 0 或 (100 + 1400 - 1400) 计算，不会返回负数
# ↑ Prometheus 内置 Counter 重置处理逻辑
```

所以进程重启对 rate 查询基本透明，不需要在业务层做持久化 Counter。

> ⚠️ **别混**：rate 能处理的是"Counter 归零再递增"。如果你把指标类型设成 Gauge（可上可下），然后用来计数，rate 算出来就没有意义，还可能出现负值或异常尖刺。**不要**为了"省类型"把 Gauge 当 Counter 用。

### 再追问

**多副本同时重置会不会有问题？**——每个 instance 的 series 是独立的，rate 在每个 series 内部处理重置，互不影响。

**Pushgateway 里的 Counter 重置怎么处理？**——这是 Pushgateway 最麻烦的地方。多个短命任务都把 Counter 推到同一个 series，Prometheus 看不到清晰的"进程生命周期"，重置语义会混乱。**不要**让不同任务共用同一个 Pushgateway 序列。

## Q4

**★★★★★｜rate、irate、increase 有什么区别？rate 窗口为什么要 ≥ 2×scrape 间隔？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

告警表达式写成 `rate(errors[10s])`， scrape_interval 是 15s，结果半夜频繁抖动。面试官还问告警该用 rate 还是 irate。


高基数。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：rate 看窗口内平均每秒增长，irate 只看最近两点，increase 看窗口内总增量；告警用 rate，看板突发可用 irate。

| 函数 | 算什么 | 适用场景 | 告警 |
|------|--------|----------|------|
| **rate** | 窗口内平均每秒增量 | 告警、面板 | ✅ 稳定 |
| **irate** | 最近两个样本的瞬时增量 | 面板看突发 | ❌ 容易抖动误报 |
| **increase** | 窗口内总增量 | 1h/1d 统计总量 | ✅ 按总量阈值 |

#### 为什么窗口要 ≥ 2×scrape_interval

scrape_interval=15s 意味着每 15 秒一个点。窗口 10s 内可能只包含 0 个或 1 个点，rate 根本算不出稳定的变化率。窗口至少 30s（2×15s）才能保证至少两个样本。

```promql
rate(http_requests_total[30s])   # ← 下限，刚好 2 个点
rate(http_requests_total[1m])    # ← 常用，4 个点，较稳
rate(http_requests_total[5m])    # ← 告警常用，平滑
```

> ⚠️ **别混**：irate 不是"更精确的 rate"。它只取最近两个点，对采样抖动极其敏感，**不适合告警**。面试官常故意说"irate 更精确所以告警用它"，这是错的。

> 📝 **面试**：答"rate 窗口 ≥ 2×scrape，告警用 rate 不用 irate"，基本就过关。

### 再追问

**窗口越大越好吗？**——不是。窗口越大越平滑，但对真实故障的反应越慢。告警通常 3m–5m，面板看趋势可用 1h。**不要**为了"图好看"把告警窗口拉到 30m，会延迟发现。

**rate 能套在 Gauge 上吗？**——不能。Gauge 用 `deriv()` 看变化趋势，或直接比较阈值。对 Gauge 用 rate 没有物理意义。

## Q5

**★★★★★｜histogram_quantile 算 P99 的原理是什么？为什么 le 桶要预定义好？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

面试官让你在白板上写 P99 查询，并追问"为什么不能直接对 Summary 取平均"、"聚合顺序是什么"。


聚合与匹配。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：histogram_quantile 在预定义的 le 桶之间做线性插值估算分位数；必须先按 le 聚合所有实例，再算分位。

三个关键点：

1. **`le` 桶预定义**：Histogram 在客户端暴露时就把 `0.005`、`0.01`、`0.025` ... `+Inf` 这些桶定好了，查询不能临时改桶。
2. **聚合顺序**：先 `sum by (le)` 把所有实例的同桶计数加起来，再套 `histogram_quantile`。顺序反了会错。
3. **桶间线性插值**：落在某个桶内的第 N 个样本，按桶边界线性估算具体延迟。

```promql
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="gateway"}[5m]))
)
```

```text
假设总数 1000，P99 要找第 990 个样本
le=0.01  有 350 个
le=0.025 有 800 个
990 落在 [0.01, 0.025] 桶内
线性插值：0.01 + (0.025-0.01) × (990-350)/(800-350) ≈ 0.0213
# ↑ 这就是 histogram_quantile 返回的估算值
```

> ⚠️ **别混**：这个 P99 是**估算值**，不是精确值。桶越宽，插值误差越大。如果业务延迟主要集中在 0.01s 和 1s 两个桶，中间线性插值会失真。

> 📝 **面试**：写查询时大声说出"sum by (le) 在最里面，histogram_quantile 在最外面"。

### 再追问

**为什么不能对 Summary 的 P99 取平均？**——每个实例的 P99 只反映该实例。集群 P99 是"所有请求里排 99% 的值"，不是"各实例 P99 的平均"。慢请求可能集中在某个热点实例，取平均会掩盖这个问题。

**histogram_quantile 对 Counter 能用吗？**——不能。它只对 Histogram 的 `_bucket` 指标有意义。对 Summary 或 Counter 用会报错或无意义。

## Q6

**★★★★★｜label 基数爆炸怎么查？user_id 能不能当 label？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、落库：label 就是索引](知识点.md)

### 场景

Prometheus 半夜 OOM，head series 280 万。业务方说"把 user_id 打进去方便按用户下钻"，运维准备直接给 Prometheus 加内存。


histogram_quantile。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：label 是 TSDB 的索引，每个不同 value 都新增一条时间序列；user_id 进 label 会让 series 数量爆炸。

查基数三步：

```bash
# 1. 看总 series 数
curl -s http://prometheus:9090/api/v1/status/tsdb | jq '.data.headStats'
# {
#   "numSeries": 2847391
# }
# ← 超过 ~200 万就要警惕

# 2. 找出哪个指标 series 最多
curl -sG http://prometheus:9090/api/v1/query \
  --data-urlencode 'query=topk(10, count by (__name__) ({__name__=~".+",job!=""}))'
# {__name__="http_requests_total"} 1843200

# 3. 看哪个 label 值多
curl -sG http://prometheus:9090/api/v1/label/user_id/values \
  --data-urlencode 'match[]=http_requests_total' | jq '.data | length'
# 983421
# ← user_id 有近百万不同值，确认是高基数 label
```

定责：**立刻停止这条指标写入**，加 relabel drop 或改代码把 `user_id` 迁到日志/Trace。

> ⚠️ **别混**：relabel 只能阻止新样本带这个 label，已经写进 TSDB 的 series 不会自动消失。OOM 时先停指标，再谈 relabel。

> 📝 **面试**：答"查 headStats → topk count by name → label values 数量"，三步缺一不可。

### 再追问

**哪些字段适合当 label？**——低基数枚举：status code（几十种）、method（GET/POST/PUT/DELETE）、job、instance、环境。高基数唯一 ID 去日志或 Trace。

**cardinality 和基数是同一个意思吗？**——是。cardinality 就是"基数"，指某个 label 的不同 value 数量，或某个 metric 的时间序列总数。

## Q7

**★★★★☆｜staleness 是什么？为什么实例下线了 Grafana 上还画了一段时间的直线？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、生病：基数爆炸、staleness、rate 误用、Counter 重置](知识点.md)

### 场景

灰度发布时摘掉一个 Pod，Grafana 上该实例的 QPS 没有立刻归零，而是水平画了 5 分钟直线。有人怀疑 Prometheus 缓存了旧数据。


recording rules。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：staleness 是 Prometheus 故意保留消失序列约 5 分钟，让查询不会因为 target 突然消失而跳变。

```text
10:00  target 被摘掉
10:01  查询仍看到最后非 stale 值
10:05  之后序列从查询结果中彻底消失
# ↑ 这 5 分钟内 Grafana 可能显示平线，不是真的有流量
```

设计意图：在 K8s 滚动更新等场景下，Pod 替换过程中旧实例指标不会"断崖式"消失，聚合查询更平滑。

> ⚠️ **别混**：staleness 不代表 Prometheus 还在采这个 target。`up == 0` 会立刻反映 scrape 失败；只是历史 series 在查询侧保留 5 分钟。**不要**把平线当成"服务还有请求"。

### 再追问

**怎么确认是 staleness 还是真的有流量？**——看 `up{instance="xxx"}` 是否为 0，同时该 instance 的 `http_requests_total` 是否不再增长。

**可以调短 staleness 时间吗？**——可以，但不建议。全局调短会让正常滚动更新时的图也变得抖动。如果某个业务场景需要立刻消失，更应该在应用层设计明确的"下线"指标或状态。

## Q8

**★★★★☆｜sum by、avg without、topk 怎么用？group_left 是干什么的？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

面试官让写几个 PromQL：按状态码看 QPS、按 job 看平均 CPU、找出 QPS 最高的 5 个实例。还追问 group_left 的用法。


空结果骗图。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`sum by` 保留指定维度求和；`avg without` 去掉指定维度后平均；`topk` 取前 N；`group_left` 多对一匹配时保留左表粒度。

```promql
# 按 status 聚合 QPS
sum by (status) (rate(http_requests_total{job="gateway"}[5m]))

# 按 job 看平均空闲 CPU（去掉 instance 维度）
avg without (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

# QPS 最高的 5 个实例
topk(5, sum by (instance) (rate(http_requests_total{job="gateway"}[5m])))
```

`avg without (instance)` 等价于：按除了 instance 之外的所有 label 做 avg。当只有 mode 一个其他 label 时，结果就是按 mode 平均。

`group_left` 用于**多对一**的向量匹配。例如 kube_pod_info 有很多 Pod，node_exporter 每个节点一条记录，要把 Pod 指标挂到节点标签上：

```promql
some_pod_metric
* on (instance) group_left (nodename)
node_uname_info
# ↑ 左表（pod_metric）粒度更细，右表（node）粒度更粗，保留左表 nodename
```

> ⚠️ **别混**：`group_left` 不是"左连接"的日常用法，只在**向量匹配粒度不一致**时才用。一对一匹配用 `on(...) / ignoring(...)` 就够了，不要逢 join 就加 group_left。

> 📝 **面试**：写 topk 时注意 `topk` 是**按时间序列**取 top，不是按整个矩阵。表达式 `topk(5, sum by (instance))` 会在每个时间点取前 5，图可能会"跳"。

### 再追问

**sum by 和 sum 后再 by 有区别吗？**——`sum by (status) (x)` 等价于 `sum(x) by (status)`，只是语法糖。

**为什么聚合前要先 rate？**——对 Counter 必须如此。`rate(sum(x))` 和 `sum(rate(x))` 结果不同：前者会丢失 Counter 重置信息，后者不会。**不要**写成 `rate(sum(...))`。

## Q9

**★★★☆☆｜recording rules 什么时候该建？**

**覆盖**：必会 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

团队里有人给每个面板都建 recording rule，导致规则文件庞大、Prometheus 启动变慢。面试官问你怎么把握建的时机。


联邦与长期存储。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：查询很贵、调用频繁、告警和面板共用同一套表达式时，才建 recording rule。

适合建：

- 复杂聚合被多个面板/告警反复查询。
- 大时间范围的统计（如 30 天错误率）实时算太慢。
- 告警和面板需要严格同源，避免两套阈值。

不适合建：

- 一次性探索查询。
- 本身就很轻的即时查询。
- 为了"看起来规范"给每个面板都建。

```yaml
groups:
  - name: gateway.rules
    interval: 30s
    rules:
      - record: job:gateway_qps:rate5m
        expr: sum by (job) (rate(http_requests_total{job="gateway"}[5m]))
```

命名习惯：`level:metric:operation`，如 `job:gateway_qps:rate5m`。

> ⚠️ **别混**：recording rule 降低**查询侧**负载，**不解决 ingest 侧高基数**。OOM 时先查基数，不是加 recording rule。

### 再追问

**recording rule 算出来的新指标会被 Alertmanager 直接用吗？**——不会。recording rule 只是生成新时间序列；要告警还要再写 alert rule。但 alert rule 可以引用 recording rule 的结果，减少实时计算。

**rule group 的 interval 怎么定？**——通常 ≥ scrape_interval，且要覆盖查询所需的粒度。不要设得太短，否则 Prometheus 会频繁计算，反而增加负载。

## Q10

**★★★★★｜写一段完整 PromQL：P99 延迟、错误率、QPS、topk 实例。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、查询：PromQL 三层](知识点.md)

### 场景

面试白板题：给你 `http_requests_total` 和 `http_request_duration_seconds_bucket`，分别写出这四个查询。


抓取失败。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：Counter 先 rate，Histogram 先 sum by (le) 再 histogram_quantile，聚合顺序不能反。

```promql
# 1) P99 延迟
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="gateway"}[5m]))
)

# 2) 错误率
sum by (status) (rate(http_requests_total{job="gateway",status=~"5.."}[5m]))
  / sum by (status) (rate(http_requests_total{job="gateway"}[5m]))

# 3) QPS 按实例
sum by (instance) (rate(http_requests_total{job="gateway"}[5m]))

# 4) topk 5 实例
topk(5, sum by (instance) (rate(http_requests_total{job="gateway"}[5m])))
```

```text
{instance="10.0.0.3:8080"}  1250.4
{instance="10.0.0.5:8080"}   980.2
{instance="10.0.0.7:8080"}   875.1
# ↑ topk 返回每个时间点的前 5
```

> ⚠️ **别混**：错误率的分子分母都要 `rate()`，不能`rate(分子) / 原始分母`；P99 的 `sum by (le)` 必须在 `histogram_quantile` 里面。

> 📝 **面试**：白板写这四个时，嘴里念叨"Counter 先 rate、Histogram 先 sum by le、histogram_quantile 在最外"。

### 再追问

**如果想看按 path 的 P99 呢？**——把 `by (le)` 改成 `by (le, path)`，让聚合保留 path 维度。

```promql
histogram_quantile(0.99,
  sum by (le, path) (rate(http_request_duration_seconds_bucket{job="gateway"}[5m]))
)
```

**错误率能不能不用 status label，用返回码？**——可以，用 `code=~"5.."` 或 `status=~"5.."`，取决于你的 label 命名。关键是正则匹配。

## Q11

**★★★★★｜Prometheus OOM 了，怎么快速定责？**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [七、作战：指标不对 / 查不出 / OOM 定责](知识点.md)

### 场景

生产环境 Prometheus 内存持续上涨直到 OOM，团队第一反应是"加内存"。面试官问你的完整排查步骤。


开头现场三种骗法。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：OOM 先看 head series 和哪个 label 在爆炸，停错误指标，不是只加内存。

三步定责：

```bash
# 1. 看 TSDB 概览
curl -s http://prometheus:9090/api/v1/status/tsdb | jq '.data.headStats'
# {
#   "numSeries": 2847391
# }
# ← 超过 ~200 万就是高基数嫌疑

# 2. 找出 top 指标
curl -sG http://prometheus:9090/api/v1/query \
  --data-urlencode 'query=topk(10, count by (__name__) ({__name__=~".+",job!=""}))'
# {__name__="http_requests_total"} 1843200

# 3. 下钻 label
curl -sG http://prometheus:9090/api/v1/label/user_id/values \
  --data-urlencode 'match[]=http_requests_total' | jq '.data | length'
# 983421
```

如果 `http_requests_total{user_id="..."}` 是元凶，立即：

1. 停掉业务侧打 user_id 的代码或配置。
2. 加 `metric_relabel_configs` drop 掉 user_id。
3. 监控 numSeries 下降趋势。
4. 之后再评估是否需要扩容或分片。

> ⚠️ **别混**：加内存只能暂时缓解，不能阻止指数级增长的 user_id。高基数是"漏桶"，加内存是"往漏桶里灌水"。

> 📝 **面试**：答"先查 /api/v1/status/tsdb 的 numSeries，再用 topk 找指标，最后看 label values 数量"，三步到位。

### 再追问

**如果 numSeries 正常还 OOM 怎么办？**——看 scrape 样本数是否过多（太多 target 或 scrape_interval 过短）、查询是否太重（大聚合没有 recording rule）、WAL  replay 占用内存。但多数生产 OOM 都是高基数。

**已经 OOM 的 Prometheus 怎么止血？**——临时加内存让它起来，然后立刻 drop 高基数 label。也可以缩短 retention 让旧数据快点清，但不如直接停错误指标。

## Q12

**★★★☆☆｜Prometheus 单机瓶颈怎么破？Thanos、VictoriaMetrics、Mimir 一句话怎么讲？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [八、收口](知识点.md)

### 场景

面试官问："你们 Prometheus 单机能存多久？超过怎么办？高可用怎么做？"


OOM。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：单机 Prometheus 解决短期存储和实时告警；长期、全局视图、高可用要引入 Thanos / VictoriaMetrics / Mimir，但它们不治乱打 label。

| 方案 | 解决什么 | 一句话 |
|------|----------|--------|
| **双 Prometheus + Alertmanager 去重** | 高可用 | 两副本各自 scrape，Alertmanager 去重，不会打两通电话 |
| **remote write** | 把样本写到远程长期存储 | Prometheus 只留近期，历史送到 Thanos/VM/Mimir |
| **federation** | 层级聚合 | 边缘 Prometheus 汇总到中心，只拉聚合后的指标 |
| **Thanos** | 长期存储 + 全局查询 | Sidecar/Receive/Query/Store/Compactor 组件，S3 存历史 |
| **VictoriaMetrics** | 高性能长期存储 | 单节点或集群，兼容 PromQL，写入和查询性能高 |
| **Mimir** | Grafana Labs 的托管级长期存储 | 云原生分布式，兼容 PromQL |

> ⚠️ **别混**：远程存储和高可用方案**不解决 ingest 侧高基数**。如果你把 user_id 打进去，Thanos 一样会被打爆。先治指标设计，再谈扩展。

> 📝 **面试**：答"先双副本 HA，长期用 Thanos/VictoriaMetrics/Mimir 做 remote write 或 federation，但高基数 label 要先在采集端治理"。

### 再追问

**federation 和 remote write 什么区别？**——federation 是拉聚合后的指标（ hierarchical 汇总），remote write 是主动推原始样本。federation 适合"总部看各集群摘要"，remote write 适合"长期全量保留"。

**VictoriaMetrics 和 Thanos 怎么选？**——VM 部署更简单、性能更高；Thanos 生态更完整（和 Grafana 深度集成、有 compactor、bucket 工具）。新公司/小团队可先 VM，大厂多云可 Thanos。

## Q13

**★★★★★｜写一段游戏登录链路的 PromQL：QPS、5xx 错误率、P99 延迟。**

**覆盖**：必会 · 常考 · 🔧实操 ｜ **对应**：知识点 [五、查询：rate 与 histogram_quantile](知识点.md)

### 场景

白板题：「`http_requests_total` 和 `http_request_duration_seconds_bucket` 都有了，怎么写三条规则？」


定责决策树。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：Counter 用 rate 看变化率，Histogram 先 sum by (le) 再 histogram_quantile。

```promql
# QPS（按 method 过滤登录）
sum(rate(http_requests_total{service="gateway",handler="/login"}[5m]))

# 5xx 错误率
sum(rate(http_requests_total{service="gateway",handler="/login",code=~"5.."}[5m]))
/ sum(rate(http_requests_total{service="gateway",handler="/login"}[5m]))

# P99 延迟
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{service="gateway",handler="/login"}[5m]))
)
```

> ⚠️ **别混**：`histogram_quantile` 必须包在最外层；`sum by (le)` 要在 `rate` 之后、quantile 之前。

> 📝 **面试**：白板先写 rate 窗口 `[5m]`，再写错误率分子分母同源 label，最后写 P99 三层嵌套。

### 再追问

**为什么错误率分母不能漏 handler label？**——漏了会把其他接口的请求混进分母，错误率被稀释。**不要**用全局 QPS 当分母除非告警范围就是全接口。

## Q14

**★★★★★｜综合：一个 Counter 从业务埋点到 Grafana 告警，全链路会卡在哪？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [一、一张图：一个指标的一生](知识点.md) · [合上书](知识点.md)

### 场景

「充值成功率告警没响，但玩家已经在骂了。」


综合口述。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：沿「暴露 → scrape → TSDB → 查询 → 告警规则 → Alertmanager → 人」逐段查，多数漏告卡在**埋点缺失**或**label 过滤错了**。

```text
① 暴露：/metrics 里有没有 pay_callback_total？status label 对不对？
② 抓取：up{job="pay"} == 1？scrape 失败会静默
③ 查询：rate 窗口够吗？Counter 重置了吗？
④ 规则：阈值/for 是否过松？是否用了 irate 误报后被人 silence？
⑤ 路由：critical 是否发到 oncall 组？
```

> 📝 **面试**：「先 curl metrics 确认序列存在，再查 up，再查规则 evaluate，最后查 AM 路由——不要一上来改阈值。」

### 再追问

**recording rule 在这条链路里放哪？**——在「查询贵且重复」时，把复杂 PromQL 预计算成新 metric，告警和面板共用。**不要**用 recording rule 掩盖埋点缺失。
