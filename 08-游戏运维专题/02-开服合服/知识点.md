开新服玩家已经能在列表里点进去，库却是空的——运维说「Pod 全 Running 了」。合服迁到一半，运营在群里要「再给 20 分钟」，另有人建议「反向再迁回去」。**目录是总闸；合服回滚 = 恢复两份备份，不是反向再迁。**

**本章主线（执行就按这三步想）：**

1. **开服**：预检 → 数据面 → 服务面 → 冒烟 → **最后才写目录**；每段失败阻断。
2. **合服**：摘目录踢线写 QPS=0 → 双备份 → 映射迁移 → 三道校验 → 只开目标服。
3. **回滚**：开服未写目录拆脏环境；已写目录先摘；合服失败 = 恢复两份备份，**禁止反向再迁**。

**读完你能：** 把开服讲成五段且只有最后一步对玩家可见；合服冲突按表处理并永久留映射；失败回滚是恢复两份备份；窗口超时拒绝加时。

## 1. 基本概念

**值班里什么时候碰到：**

| 场景 | 玩家/运营说的 | 你的第一刀 |
|------|---------------|------------|
| 开服日 | 「能点进新服但创角失败」 | 冒烟过了没？还是目录写早了 |
| 合服夜 | 「号没了」「公会解散了」 | 映射表 + 目录跳转 |
| 合服中断 | 「再给 20 分钟就能迁完」 | 看变更单，到点回滚 |
| 开服失败 | 「apply 成功了啊」 | 五段卡在哪 |

| | 开服 | 合服 |
|--|------|------|
| 本质 | 复制一套分服环境并最后写目录 | 合并两份分服权威库 |
| 权威 | 新建带 `server_id` 的库 | MySQL；**Redis 作废重建** |
| 对玩家可见 | 只有写目录那一步 | 目录切目标服、源服标已合并 |
| 失败回滚 | 未开放拆脏环境；已开放先摘目录 | **恢复合服前两份备份** |
| 窗口 | 可以白天（新服没人） | 低峰；超时回滚，不现场加时 |

| 对象 | 干什么 |
|------|--------|
| **`server_id`** | 分服身份；分配落库；回收写手册 |
| **映射表** | `old(server_id,id) → new_id`；永久保留 |
| **目录** | 总闸；没写进去外面看不到 |

> **记住：** apply 成功不是开服成功。合服回滚 = 恢复两份备份，不是反向再迁。

**面试怎么说**：「开服五段，只有写目录对玩家可见。合服先停写写 QPS=0、双备份、映射迁移——失败恢复两份备份，禁止反向再迁。」

## 3. 原理

### 3.1 开服五段

**一句话：** 只有⑤写目录对玩家可见；`kubectl get po` 全 Running 只说明③过了。

**打个比方**：开服像新店开业——装修（预检建库）、招人（部署）、试营业（冒烟）都做完，**最后才挂招牌（写目录）**。

**现场走一遍**（S105 开服，玩家反馈「能进空服」）：

1. 查任务表 checkpoint：`stage=deploy_done`，`smoke=failed`，`dir_written=true`。
2. 查库：`SELECT COUNT(*) FROM role WHERE server_id='S105'` → 0。
3. 冒烟日志：创角步骤 500，静态表未导入。
4. 结论：④ 冒烟没过就写了⑤ 目录——**玩家可见但库是空的**。
5. 止血：**先摘目录** → 标 dirty → 从②重建，不要「再导一次表当没事」。

| 段 | 做什么 | 失败 |
|----|--------|------|
| ① 预检 | 镜像/配置钉死；配额、IP；中心服健康；`server_id` 未占用 | 修配额重跑 |
| ② 数据面 | 建库/Schema；导静态表；初始化 Redis（活动默认关） | 删脏 Schema |
| ③ 服务面 | Gate/大厅/逻辑；**尚未挂公网目录** | 拆 Deployment |
| ④ 冒烟 | 测试账号：登录→创角→战斗结算→邮件 | 标 dirty，不开放 |
| ⑤ 开放 | 目录写入；打开注册/创角 | 已可见→先摘目录 |

耗时：单服 8～15 分钟。并行开 N 服要有 `server_id`/IP 锁；先卡镜像、配额、建库、目录写，不是 Logic CPU。

**面试怎么说**：「apply 成功不是开服成功。我盯任务表 checkpoint 和冒烟路径，不是 Pod Running。已写入服列表失败必须先摘目录。」

### 3.2 合服冲突策略

**一句话：** 主键必须映射，外键全跟着改；排行重算不拼接。

**打个比方**：合服像两本独立账本合并——**不能直接把两本的页码叠在一起**，必须重新编号并写对照表。

**现场走一遍**（S101+S102 合到 S101，迁完排行异常）：

1. 运营反馈：「两个第一名」「公会成员数翻倍」。
2. 查迁移脚本：排行表做了 `UNION ALL` append。
3. 查公会：两个同名「龙之翼」，成员表 uid 没走映射。
4. 正确做法：排行**合服后重算**；公会同名加后缀；成员 uid 全走映射表。
5. 映射表必须落盘、进备份——丢了 = 数据事故，停一切改库。

| 冲突 | 常见做法 | 不能做的 |
|------|----------|----------|
| 区内 uid | 映射表改所有外键 | 两边主键直接 insert |
| 角色名 | 被合入方加后缀+改名卡 | 静默改名 |
| 公会 | 同名加后缀；成员按映射重写 | 两个同名公会叠成员 |
| 排行 | 合服后重算 | 分数 append/UNION |
| 唯一道具 | 全局唯一约束，冲突走工单 | 复制一份给两人 |
| 经济 | 原样迁移+事后监控 | 现场调平衡 |

三道校验：① 计数（角色/充值/道具）② 金额（储值累计）③ 抽样（高 V、会长、未领邮件）。

**面试怎么说**：「两个 dump 直接进目标库是错的。主键映射、外键全改、排行重算。映射表永久保留，不是 `/tmp` 临时文件。」

### 3.3 为什么停写，不是在线双写

**一句话：** 有状态+强一致经济，在线双写对账成本高于数小时维护。

**打个比方**：两家银行合并，你不会让两个柜台同时改同一本账——**停业几小时清账，比边营业边对账便宜**。

**现场走一遍**（产品提「在线合服不停服」）：

1. 评估：战斗房间钉进程、背包行锁、拍卖未结算——在线双写需要冲突策略 + 对账 + 回档预案。
2. 成本：对账脚本覆盖 P2P、邮件、拍卖 → 研发+测试 ≥ 2 周；停写窗口演练 4 小时。
3. 结论：选停写——T-0 前关跨服入口，避免窗口里跨服写回本服（01）。
4. 门禁：`server_id` 业务写 QPS = 0 才算 T-0 过了。

**面试怎么说**：「在线双写不是更先进。有状态加强一致经济，停写+双备份+映射是主流。Redis 不是合服权威，库为准、Redis 重建。」

### 3.4 窗口

**一句话：** 窗口 = 演练耗时 × 1.5；超时到点回滚，不现场加时。

**打个比方**：手术排期定了 4 小时——**超时不是「再给 20 分钟」，是缝合失败回滚**。

**现场走一遍**（合服窗口 02:00–06:00，04:30 迁移到 60%）：

1. 变更单写：窗口 4h，演练 2.5h，系数 1.5。
2. 04:30 进度 60%，运营要「再给 20 分钟」。
3. 评估：继续 = 可能 06:30 才校验完，早高峰玩家醒来看到半成品。
4. 动作：**拒绝加时** → 停迁移 → 双备份恢复两服 → 公告延期。
5. T-48h 公告；版本不一致、备份未验证、映射未 dry-run、没演练过 → **拒绝合服**。

**面试怎么说**：「窗口超时到点回滚，不现场加时。国内合服常见 02:00–06:00，公告 ≥ 48h。」

## 4. 落地

| 项 | 选 | 不选 |
|----|----|------|
| 开服可见点 | 冒烟通过后才写目录 | apply 完就挂列表 |
| 合服 | 停写+双备份+映射 | dump 直进、在线双写、反向再迁 |
| 窗口 | 低峰、演练×1.5、超时回滚 | 版本夜顺便做、现场加时 |
| 并行开服 | 分批、镜像预热、锁 | 20 路齐发 |

验收：开服必须冒烟路径通；合服必须三道校验过、目录只放目标服。

## 5. 核心配置

| 参数 | 生产怎么用 | 改错会怎样 |
|------|------------|------------|
| 镜像/配置 | 钉 digest，禁 latest | 开完才发现上周镜像 |
| 目录写入 | 独立事务、有锁 | 和选服共用无保护写路径 |
| 合服超时 | 写进变更单，到点回滚 | 现场加时放出半成品 |
| 映射表 | 落盘+进备份，禁 `/tmp` | 丢了=数据事故 |
| 源服写路径 | 合服后不起 | 「方便对账」误写 |

## 6. 命令与操作

### 6.1 T-0 门禁

```bash
# 合服 T-0：确认两服写已经停
mysqladmin processlist | grep -c Query
# 以业务库为准：该 server_id 业务写 QPS = 0
```

**输出解读**（T-0 门禁）：

| 看什么 | 正常 | 异常 |
|--------|------|------|
| 业务写 QPS | = 0 持续 2min+ | >0 → 踢线未完成，禁止备份 |
| processlist 业务写 | 无 UPDATE/INSERT | 有 → 查哪条连接在写 |
| 备份 restore 演练 | 旁路 restore 后三道校验对得上 | 从没 restore = 没有备份 |

| 目的 | 看什么 |
|------|--------|
| T-0 停写 | 业务写 QPS = 0 |
| 备份可用 | 旁路 restore 后三道校验对得上 |
| 开服进度 | 任务表 checkpoint，不是 Job 绿了 |
| 映射 | 文件在备份链上，不是跳板机 `/tmp` |

### 6.2 开服失败回滚

| 失败点 | 玩家可见 | 动作 |
|--------|:--------:|------|
| 预检/建库/部署/冒烟 | 否 | 标 dirty，重建 |
| 已写入服列表 | **是** | **先摘目录** |

### 6.3 合服窗口步骤

1. T-48h 公告；T-4h 预检+关跨服；T-0 摘目录踢线写=0。
2. 全量备份 A、B（逻辑+binlog 位点）。
3. 按映射迁：角色→背包→公会→关系→邮件。
4. 三道校验 → 只开目标服。
5. 失败：双备份恢复两服；已开放有新经济 → 摘目录进 07。

### 6.4 周边系统

目录跳转、跨服战区重配、支付按新 ID 发、GM 经映射查、数仓合服日打标——漏一项就是事故。

## 7. 生产排障

| 现象 | 先做 | 别做 |
|------|------|------|
| apply 成功但进空库 | 先摘目录 | 再导一次表当没事 |
| 冒烟失败 | 标 dirty 重建 | 跳过开放 |
| 合服迁到一半 | 停；双备份恢复 | 反向再迁 |
| 运营再给 20 分钟 | 拒绝，按变更单回滚 | 现场加时 |
| 玩家说号没了 | 目录跳转、映射表 | 先怀疑库没迁完 |
| 映射在 `/tmp` | 当丢失风险，落盘进备份 | 当留存 |

> **记住：** 写 QPS=0、备份能拉起来跑校验 SQL，才叫门禁过了。

## 8. 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| `kubectl apply` 成功就是开服成功 | 错 | 冒烟通过后才写目录 |
| 合服两个 dump 直接进目标库 | 错 | 主键映射，外键全改 |
| 排行直接 append/UNION | 错 | 按合并后角色重算 |
| 合服失败反向再迁就是回滚 | 错 | 回滚=两份备份分别拉起 |
| 映射表用完可以删 | 错 | 永久留 |
| 在线双写比停写更先进 | 错 | 有状态+强一致，对账成本更高 |
| 窗口超时再给 20 分钟 | 错 | 到点回滚 |
| Redis 是合服权威 | 错 | 库为准，Redis 重建 |
| 库迁完合服就完成了 | 错 | 目录、跨服、支付、数仓 |
| 一天开 20 服先卡 Logic CPU | 错 | 镜像、配额、建库、目录、锁 |
| 经济现场调平衡 | 错 | 裸改 |
| 冒烟失败可以先开放再补 | 错 | 跳过冒烟是人为事故 |
| 已开放失败可以同 ID 立刻再开 | 错 | 先摘目录；回收写手册 |
| 源服可以起写路径方便对账 | 错 | 最多只读 |

数字：单服开服 8～15 分钟；公告 ≥ 48h；窗口 = 演练 × 1.5；国内合服 02:00–06:00；校验三道（计数/金额/抽样）。

易混：开服回滚 vs 合服回滚；未开放 vs 已开放；映射表 vs 备份；停写合并 vs 在线双写。
