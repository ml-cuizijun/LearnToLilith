## Q1

**★★★★★｜活动流量为什么要拆成三峰，而不是一个 CCU？**

**覆盖**：核心 · 必会 · 常考

### 场景

策划只给了「预计 5 万 CCU」。机器按 CCU 备了 Gate 和逻辑。整点全服发奖，主库锁等待先炸，登录其实还没到峰值。

### 完整解答

登录峰打账号 / 排队 / Gate；玩法峰打房间和跨服；发奖峰打 DB 写和邮件。三峰常叠在整点，只报 CCU 会买错机器、漏掉写库硬顶。

```
  登录 / 重连  --> 账号、排队、Gate     日常 20×+，秒级尖峰
  玩法         --> 房间、跨服、Redis     单接口 10×～50×
  发奖 / 结算  --> DB 写、邮件、背包锁   比 CCU 更危险
```

买量 + 新服 + 活动同一天是事故配方。容量账分开：CCU → Gate/大厅；玩法 QPS → 该玩法进程；发奖条数/秒 → 写和锁；跨服房间数与本服 CCU 解耦。结算和强更抬闸错开。看板必须能分开三座峰，不要被 CPU 大盘带跑。

### 再追问

哪座峰最容易资损？——发奖 / 结算写错或重复发。玩法进不去是体验；钱和道具错是 P0。

## Q2

**★★★★★｜有状态扩容的边界在哪？HPA 为什么救不了战斗？能不能把战斗服当 Deployment 滚？**

**覆盖**：核心 · 必会 · 常考

### 场景

活动 BOSS 房间打满，战斗 CPU 90%。HPA 不断加出来空 Pod。有人说再加点 Redis 节点就能救全服榜那个热 key。另有人准备滚动重启战斗「释放一下」。

### 完整解答

新副本是空的，已绑定房间还在旧进程爆。活动前按预报预开空房间进程。HPA 给登录和大厅。单服写和热 key 活动中途不能靠加节点解决。不要把战斗服当 Deployment 滚——和 01 同一纪律，活动中滚动等于砍在线局。

```
  能扩：登录、目录、Gate 连接、大厅、空战斗进程、跨服房间池（提前）
  不能：已开战的房间迁走、活动中途分库、现场给热 key 加分片救命、滚动重启有局进程
```

Gate 扩了不会迁走已有连接。MySQL 加从库只救读。全服榜一个 key 加 Redis 分片救不了已有热点。运维对「全服同时发奖」要有否决权。

### 再追问

战斗能不能按空闲房间数扩？——可以，扩出来的是空进程给新匹配。对已开的局没有帮助。活动前预热比现场扩有用。

## Q3

**★★★★★｜降级顺序怎么排？举你用过的开关。排行延迟必须保吗？回执不齐怎么办？**

**覆盖**：核心 · 必会 · 常用

### 场景

跨服和本服一起抖。有人要全服维护。排行刷新延迟 30 秒，运营觉得是 P0。配置中心显示开关已发，20% 进程没回执。

### 完整解答

保登录、重连、结算正确、支付；再保活动本身；先关跨服、排行、实时邮件、非必要推送。开关走配置热更，恢复顺序相反。回执不齐当失败，不要假定全服已降级（03）。

```
  1 登录 + 已有角色进服 + 重连
  2 战斗结算 / 背包权威
  3 支付发货（可排队，不能丢）
  4 活动玩法
  5 跨服、排行、聊天、推送
  6 动画 / 实时榜刷新频率
```

具体开关：关跨服入口、排行定时刷新或只读缓存、邮件改批量、匹配超时打 AI / 单机、降广播和 Tick、停发奖入口。新玩家延长排队需产品签字。降级也是变更，写 runbook。恢复：先结算和支付缓冲，再跨服和排行，最后动画。反着开，主库会再被锁一次。

### 再追问

排行延迟算不算必须保？——不算。可改定时刷新或只读缓存。结算和背包权威必须保。目录不要因为跨服挂了就把本服标维护。

## Q4

**★★★★★｜压测最小集合有哪些？为什么 /health 绿了不算？压测绿线上炸先怀疑什么？**

**覆盖**：核心 · 必会 · 常用

### 场景

预发 `/health` 和登录 HTTP 压测全绿。上线后渠道鉴权超时、CDN 未预热、全服榜一个 key 把 Redis 打成单线程。机器人全程没建长连接。

### 完整解答

登录与排队曲线、进服背包、活动主循环、结算发奖、支付沙箱真路径、重连风暴。health 不走 Tick、不走写、不走渠道。

```
  最低集合
    ① 登录 + 排队放行曲线
    ② 进服 + 拉角色 / 背包
    ③ 活动主循环（BOSS / 转盘 / 推图）
    ④ 结算 + 发奖 + 邮件
    ⑤ 支付沙箱（真代码路径）
    ⑥ 重连风暴（随机踢 30%）
```

开服用新号，活动用老号。混用会测错索引和缓存。数据要有背包和邮件体积。禁止对生产主库写。通过标准给出可承载 CCU 和每秒发奖。

压测绿线上炸，先怀疑：渠道鉴权、CDN 未预热、热 key、机器人不走战斗、预发关了日志 / 风控。不要先怀疑「机器还是不够」。

### 再追问

压测绿线上炸，你先怀疑什么？——渠道 SDK 和真实鉴权、CDN 未预热导致登录曲线变形、热 key / 全服锁没打到、机器人只打 HTTP、预发关风控和日志。

## Q5

**★★★★★｜活动中战斗进程内存高，能重启吗？能不能当 Deployment 滚？**

**覆盖**：核心 · 必会 · 常考

### 场景

周年庆值班。战斗进程内存曲线往上走。有人准备滚动重启「释放一下」。房间还在打。

### 完整解答

先看是房间堆积还是泄漏。有局在打就不要自动重启。先降级新进、等结束或产品同意强制结算。重启可能二次结算。不要把战斗服当 Deployment 滚（01）。

```
  内存高
     |
     +-- 房间数 × 人均内存对得上 --> 容量，扩空进程 / 降级新进
     +-- 对不上 / 空房间不回     --> 泄漏或未释放，仍不要杀有局进程
     +-- 确认死锁且可强制结算   --> 产品签字后再杀
```

和 01 章同一纪律。活动值班禁止「看起来高就重启」。

### 再追问

怎么快速判断堆积还是泄漏？——房间数 × 人均内存是否对得上；空房间是否内存不回。对得上是容量，对不上是泄漏或未释放。对得上就不要重启。

## Q6

**★★★★☆｜全服同时发奖打爆主库，现场能做什么？加从库呢？**

**覆盖**：必会 · 常用 · 常考

### 场景

排名结算同一秒给全服发奖。主库行锁等待爆了。有人要挂只读从库抗发奖，有人要现场分库。

### 完整解答

停发奖入口，改批量 / 延迟邮件，保结算正确。不能现场分库。之后逼产品改节奏。从库救不了写。

```
  现场：停入口 → 批量 / 延迟邮件 → 保已发出的结算不错
  不能：活动中途分库、加从库抗写、重启战斗碰运气
  事后：分片发奖、错峰、把「全服同时」改成可承载的每秒条数
```

这是运维对产品的否决权。没有「可承载发奖每秒」数字就不要接「全服实时」。

### 再追问

已经发出去的错奖怎么办？——停产出后按 07 走数据修复 / 回档，评估新充值和已消耗。不是再热更一个补偿系数当没发生（03）。

## Q7

**★★★★☆｜活动值班 T-7 / T-1 / T0 你检查什么？**

**覆盖**：必会 · 常用

### 场景

T0 才发现降级开关没演练过，CDN 没预热，还有人在发无关热更。看板开了一屏幕，登录成功率和发奖失败率不在第一屏。

### 完整解答

T-7 容量和降级演练、压测签字。T-1 预扩、CDN 预热、冻无关发布。T0 只盯登录成功率和发奖失败率。炸了先降级再扩能扩的。

```
  T-7d  容量评审、降级开关演练、压测报告签字
  T-1d  登录 / Gate / 跨服预扩、CDN 预热、冻无关发布
  T0    登录成功率、发奖失败率
  炸了  先降级，再扩能扩的；不重启有局战斗进程
```

活动中不发无关版本。经济错误按数据事故走 07。

### 再追问

T0 还能不能改排队阈值？——可以按预案降速（成功率掉了就降），不要涨速清队列，不要改推荐算法。阈值变更也要有人记账。

## Q8

**★★★★☆｜跨服活动挂了，本服还要不要关？**

**覆盖**：必会 · 常用 · 常考

### 场景

跨服战场集群 OOM。有人把目录里所有服标成维护，本服大厅其实还能玩。

### 完整解答

关跨服入口，本服玩法继续。目录不要把本服标维护。除非跨服回写卡住本服停写，那是另一类（合服窗口，见 02）。

```
  跨服挂 --> 关跨服入口，本服大厅 / 已有角色可玩
  本服库挂 --> 该区不可玩，跨服回写必须停
  不要用全渠道维护去盖一个跨服故障
```

### 再追问

跨服回写还在飞，本服已经要停写怎么办？——先冻跨服入口和回写，确认写 QPS = 0，再动本服。窗口里还让跨服写，合服和回档都会脏。

## Q9

**★★★☆☆｜压测环境为什么必须和线上同构 Redis 版本？规格能外推吗？**

**覆盖**：常用 · 常考

### 场景

预发 Redis 小规格、版本落后一个大版本。压测报告写「热 key 不明显」。生产 fork 和淘汰把 P99 打穿。机器人思考时间 0。

### 完整解答

热 key、淘汰、fork 造成的延迟和版本 / 内存策略相关。版本不一致会测出假绿。规格也要同档，不能预发小规格外推。

配置、机器规格、Redis 版本与生产同构。用生产从库打读可以，禁止对生产主库打写。报告要写哪一层先破，不是只交最大 CCU。

### 再追问

机器人思考时间 0 有什么问题？——QPS 形状是方波，线上是尖峰 + 长尾。会高估平稳吞吐、低估登录尖峰和发奖尖刺。思考时间、背包体积、房间分布都要按真实分布，否则报告变假。其它作弊：不走 CDN、只打 HTTP、空背包、全员同一房间或全员分散。

## Q10

**★★★☆☆｜你凭什么否决一个「全服实时榜」需求？压测中止条件写什么？**

**覆盖**：必会 · 常考

### 场景

海报已经印了「全服实时」。预发压测还没跑。研发说先上线再看。有人想对生产主库打一发「验证一下」。

### 完整解答

给出该 key 的预估 QPS 和单线程瓶颈，给替代：分片榜、定时刷新、只展示前 N。没有数字的否决像抬杠，有数字是容量负责。

压测是变更：目标数字、禁止项（生产主库、生产支付）、观察人、中止条件。中止后留现场指标，不要「再加机器续压」把预发打成不可恢复。

```
  中止条件（写进指令）
    错误率破线
    主库锁等待超阈值
    误打到生产
```

活动设计服从可承载发奖每秒，不服从海报文案。

### 再追问

压测当天告警能不能静默？——不能。压测当天当活动值班。登录 / DB 告警要看得见，否则中止条件等于没写。静默会把误打生产的时间窗拉长。

## Q11

**★★★★☆｜容量账怎么交？压测报告只写最大 CCU 够不够？**

**覆盖**：必会 · 常用 · 常考

### 场景

压测报告一页纸：最大 CCU 8 万。没有发奖每秒，没有哪一层先破，没有建议的开关默认值。策划按 8 万排了全服实时发奖。

### 完整解答

不够。要交：哪一层先破、破的指标、可承载 CCU、可承载发奖每秒、降级后还能保哪条 SLO、建议的活动开关默认值。

账本拆开：Gate/大厅按 CCU；登录按 QPS×重试；战斗按预热空房间；发奖按每秒条数和行锁；热 key 按单线程；跨服按同时房间数，与本服 CCU 解耦。策划改的是这个，不是再要两台机器的愿望清单。

### 再追问

开服压测和活动压测模型为什么不能混？——开服用新号创角，活动用老号进服。混用会测错索引和缓存。空号测不出背包 / 邮件体积带来的慢查询。
