## Q1

**★★★★★｜设计一个新游开服的技术保障方案。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、第一题：设计开服系统](知识点.md)

### 场景

新游定档下月开服，运营预期首服峰值 10 万 CCU。有人方案里只写了「多买 20 台 Gate」，没有排队和战斗预开 room；也有人准备开服当天一次性把所有新服写进目录。


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：开服系统 = 版本/CDN → 目录推荐打散 → 排队令牌桶削峰 → Gate 预扩 → 战斗空 room 预开 → DB 连接池限流，失败时未开放可拆环境、已开放先摘目录。

先问约束：预期 **CCU**、滚服还是单一大服、排队容忍、客户端版本策略、是否与活动叠窗。10 万 CCU 不等于 10 万长连接——要加重连率和机器人余量。

骨架：

```text
客户端 → CDN/版本 → 目录 server_list → 排队服（按 server_id 发票） → Gate 长连接 → 大厅/匹配 → 战斗服 → MySQL/Redis
```

关键机制：

- **排队**：**令牌桶**定速放行，每秒进入 Gate 的人数可控，避免登录洪峰冲垮 DB。
- **预热**：Gate 提前扩副本、战斗进程提前预开空 room、CDN 资源提前 HIT、静态表提前导入。
- **目录**：新服标「推荐」，老服「爆满」只拦新创角；开放目录是最后一道可见闸。
- **回滚**：未写目录前可标记 dirty 拆环境；已写目录则先摘目录或标维护，避免玩家继续涌入。

> ⚠️ **别混**：**下载峰 ≠ 在线峰**。CDN **预热**和 Gate 预扩是两本账；只扩 Gate 不排队，DB 会在开服瞬间被打满。

> 📝 **面试**：「我会先确认 CCU、服型、叠窗。骨架是 CDN→目录→排队→Gate→战斗，令牌桶削峰，预热预扩，失败先摘目录。」

### 再追问

**如果运营说「玩家不接受排队」怎么办？**——不是取消排队，而是提高 **drain_rate** 和 Gate/DB 容量，用成本换体验；但完全不排队意味着要把 DB 和战斗容量买到能扛瞬时登录尖峰，通常不经济。也可以做 VIP 快速通道、老玩家重连快通道等分层策略。

**开服当天发现战斗 room 不够，HPA 来得及吗？**——来不及。HPA 扩出来的是空 Pod，没有空 room；战斗 room 必须预开，新 Pod 要 warmup 并注册到匹配器。**不要**靠 HPA 救已开服缺 room 的问题。

## Q2

**★★★★☆｜开服瞬间排队 10 万人，怎么办？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [二、第一题：设计开服系统](知识点.md)

### 场景

开服 30 秒后排队深度到 10 万，运营在群里喊「全放进去」，开发说「排队服务是不是 Bug 了」。有人准备直接改排队服务把 R 调到无限大。


开服骨架——承接 Q1 通用动作。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：排队 10 万说明入口洪峰来了——先看 Gate 和 DB 能不能扛，再决定是加 drain_rate、加 Gate，还是维持排队保护后层。

60 秒内分三步：

1. **看资源余量**：Gate 连接数离上限多远、MySQL Threads_running 多少、登录成功率是否下跌。
2. **看队列行为**：排队是否匀速下降（drain_rate 生效）还是越排越多。
3. **决策**：
   - 后层富裕 → 可适当提高 drain_rate，同步加 Gate 副本。
   - Gate/DB 已红 → 维持或降低 drain_rate，先扩后层，不能硬放。

> ⚠️ **别混**：**排队长 ≠ 排队服务坏了**。没有排队，10 万人会同时砸 DB 和 Gate，登录成功率会雪崩。**不要**把 drain_rate 调到无限当「优化体验」。

> 📝 **面试**：「我会先盯 Gate 连接、DB Threads_running、登录成功率。后层有余才提 drain_rate；后层红了，排队本身就是在保护系统。」

### 再追问

**怎么让玩家不觉得排队很蠢？**——界面显示预计等待、VIP/重连快通道、排队期间预加载资源、分服推荐把玩家导向负载较低的新服。

**排队服务自己挂了怎么办？**——排队服要有主备或分片，降级策略：若排队服务不可达，Gate 启用本地硬限流（如每服每秒 N 个），宁可慢进不能冲垮。

## Q3

**★★★★★｜设计一套游戏服监控告警体系。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、第二题：设计监控告警体系](知识点.md)

### 场景

团队已经部署了 Prometheus + Grafana，但告警规则都是「CPU > 80%」「内存 > 85%」。开服当晚 CCU 腰斩半小时，值班手机没响——因为 CPU 和内存都正常。


三道削峰闸。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：游戏告警体系要围绕「玩家废了什么」建 SLI——登录成功率、进战斗成功率、支付到账率、CCU 完整性，再用 Alertmanager 做分组抑制和静默，而不是堆机器指标。

先问约束：监控范围（全局/分服/分玩法）、CCU 规模、值班模式、告警渠道、存储成本。

SLI 四件套：

- **登录成功率**（5 分钟窗口）：开服和版本日第一指标。
- **进战斗成功率**：登录绿但进不了房间，要独立看。
- **操作 P95/P99**：核心玩法延迟，比 CPU 更直接反映卡顿。
- **CCU 完整性**：相对预测或环比腰斩，是全服静默故障的哨兵。

架构：

```text
业务埋点 / node-exporter / kubelet → Prometheus/VM → Alertmanager（分组/抑制/静默）→ 电话/工单/IM
                                      ↓
                                   Grafana + 日志/Trace 下钻
```

游戏特有指标：CCU、**帧频**/tick 延迟、room 数、empty_rooms、匹配队列深度。

> ⚠️ **别混**：**指标多 ≠ 监控好**。告警必须是可行动的——收到后知道先查哪一层。CPU 80% 不告诉你是玩家登录失败还是战斗卡顿。

> 📝 **面试**：「我围绕登录、进战斗、支付、CCU 完整性定 SLI，用 Alertmanager 分组抑制开服风暴。游戏特有指标是 CCU、tick、room 数。」

### 再追问

**开服期间告警被打爆怎么办？**——三件事：**分组**（同一 server_id 合并）、**抑制**（登录成功率低时抑制下游派生告警）、**静默**（维护窗口/压测期间提前静默）。同时做告警分级：P0 电话、P1 工单、P2 次日看。

**tick 指标怎么埋？**——战斗主循环每帧统计逻辑耗时，窗口聚合后上报 P99，不要每帧打一条日志或写一个时序点。采样或分桶上报，控制基数。

## Q4

**★★★★☆｜开服期间告警电话被打爆，怎么压告警风暴？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [三、第二题：设计监控告警体系](知识点.md)

### 场景

开服 5 分钟后，值班收到 300+ 条告警：Gate CPU 高、多个服登录失败、DB 连接池满、Redis 超时、玩家投诉登录排队。有人要把所有规则改成「持续 30 分钟才告警」。


监控三件套分工。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：告警风暴的根因是一条根故障触发了几十条派生告警，解决靠分组、抑制、静默和分级，而不是拉长告警持续时间。

具体做法：

1. **分组**：按 server_id、severity、玩法维度合并。一个服 20 台 Gate CPU 高合并成一条「S101 Gate 高负载」。
2. **抑制**：登录成功率低时，抑制「创角失败」「进战斗失败」等下游告警——它们大概率是同一根因。
3. **静默**：维护窗口、压测、版本发布期间提前静默预期内告警。
4. **分级**：P0（电话，立即）/ P1（工单，15 分钟）/ P2（次日）。不是每条 CPU 高都是 P0。
5. **收敛**：相同告警 5 分钟内只发一次，升级时才重复通知。

> ⚠️ **别混**：**拉长 for 持续时间**只会让你发现得更晚，不能减少告警条数。真正要减少的是「派生告警」和「重复通知」。

> 📝 **面试**：「我会用 Alertmanager 的 group_by、inhibit_rules 和 silence。根告警是登录成功率，其他抑制掉；P0 只保留影响玩家核心循环的 SLI。」

### 再追问

**如果 P0 也太多怎么办？**——检查 SLO 是否定得太松或 SLI 是否覆盖过宽。P0 应该只在「登录/战斗/支付/CCU 腰斩」时触发。把 CPU 80% 调成 P2 或趋势告警，不要夜间电话。

**运维值班不敢关静默怎么办？**——静默走变更单，写明时间窗和责任人，自动到期。不要手动一条条 ack。

## Q5

**★★★★★｜给你 50 万 CCU 的预期，算算要多少机器。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、第三题：设计容量模型](知识点.md)

### 场景

面试官丢来一个数字：「50 万 CCU」。有人说「每台 Gate 5 万，10 台够了」；有人说「战斗服一台 1 万人，50 台」。都没问玩法类型、登录峰、带宽和 DB。


游戏特有指标：CCU/tick/room/漏斗。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：50 万 CCU 不能直接除，要先拆登录峰、玩法峰、发奖峰，再逐层算 Gate、战斗、带宽、MySQL，最后乘 0.7 安全系数。

估算过程（面试现场敢给数）：

```text
1. 登录峰 QPS
   登录 QPS ≈ CCU × 重连率 × 活动系数
   取 0.5 → 25 万登录/分钟 ≈ 4,200 QPS，瞬时尖刺 ×2 按 8,000 QPS 设计

2. Gate 连接数
   50 万 CCU ≈ 55 万长连接（含重连/机器人）
   单 Gate 4 万连接 → 55/4 ≈ 14 台，按 0.7 余量 → 20 台

3. 战斗服
   假设 60% 玩家同时在对局，每 room 10 人
   需要 room 数 ≈ 50 万 × 0.6 / 10 = 3 万 room
   单进程 100 room → 300 进程；α=0.7 → 约 430 进程

4. 带宽
   下行 10 kbps/玩家 → 50 万 × 10 kbps = 5 Gbps
   加 30% 余量 → 约 7 Gbps

5. MySQL 主库写
   发奖/结算与登录峰不共用，单独按玩法设计 5,000～20,000 TPS
```

> ⚠️ **别混**：**一个 CCU 数字不能买所有层**。登录峰买 Gate/排队，玩法峰买战斗/Redis，发奖峰买 MySQL 主库写。漏一层就会在活动当晚炸。

> 📝 **面试**：「50 万 CCU 我先问口径和三峰。估算：Gate 约 20 台、战斗进程约 430、带宽 7Gbps、DB 写单独压测，最终数字来自压测 ×0.7。」

### 再追问

**如果面试官追问「你凭什么说单 Gate 4 万」？**——这是经验值，受语言、buffer、玩法包大小影响；真实数字必须靠 **压测** 校准。面试可以这样答：「按我们之前压测，单 Gate 在 CPU 70% 时约 4 万连接；这个数字要回到贵司压测报告校准。」

**为什么乘 0.7 而不是 0.9？**——0.7 留 30% **余量**给发布窗口、弱网重连、活动尖刺、机器故障。0.9 太薄，一次小抖动就可能破 SLO。

## Q6

**★★★★☆｜容量模型里为什么留 30% 余量？能不能留 10%？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [四、第三题：设计容量模型](知识点.md)

### 场景

老板说「服务器太贵，余量从 30% 压到 10%」。也有人认为「云计算可以秒扩，不需要余量」。


容量算例。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：30% 余量不是浪费，是给发布、弱网重连、活动尖刺、单点故障留的缓冲；云弹性救不了有状态战斗服和主库写瓶颈。

余量要覆盖：

- **发布窗口**：升级或回滚期间部分节点不可用。
- **弱网重连**：玩家断线重连会瞬间拉高登录 QPS。
- **活动尖刺**：运营临时加活动、推送，流量高于日常建模。
- **单点故障**：一台战斗节点挂掉，其他节点要承接其 room。
- **压测偏差**：预发环境和生产总有差异，通常预留 15% 修正。

云弹性的限制：

- Gate 可以 HPA，但启动 + 注册到负载均衡需要时间。
- 战斗服扩出来的是空 room，不能救已开 room。
- MySQL 主库写不是加机器能线性扩容的。

> ⚠️ **别混**：**余量 ≠ 浪费**。没余量意味着任何超建模都会破 SLO；余量是给稳定性的保险。

> 📝 **面试**：「30% 是常见底线，覆盖发布、重连、活动、故障四类抖动。战斗和 DB 层云弹性有限，不能靠缩余量省钱。」

### 再追问

**什么情况下可以用 20% 或 40%？**——业务成熟、压测和生产长期偏差 小于 5%、无大型活动时可用 20% 省钱；新业务、压测不准、活动频繁时用 40% 更稳。关键是「这个数字要进变更单，不是口头拍」。

**容量水位告警怎么设？**——实际 D 达到 C 的 70% 时黄色预警（提前准备扩容），达到 85% 时红色告警（必须立即动作），而不是等到 100% 才响。

## Q7

**★★★★★｜K8s 集群升级，战斗服不能集体掉线，怎么设计？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、第四题：设计集群升级方案](知识点.md)

### 场景

要把 K8s 从 1.28 升到 1.29。有人建议直接 `kubeadm upgrade apply` 然后所有节点一起 drain；也有人说「战斗服 RollingUpdate 就行」。


三峰与 α=0.7——就是 Q6 的坑。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：战斗服 room 钉在进程内存，不能像 Web 一样滚——升级必须分节点池：网关/登录可滚，战斗池先 cordon、停新局、等 room 空、再 drain。

升级顺序：

1. **控制面先升**：API Server、etcd、scheduler。kubelet 可旧不可新。
2. **节点池分组**：
   - 网关/登录节点池：PDB + 滚动 drain，长连接断后重连快通道恢复。
   - 大厅节点池：session 放 Redis，可重建。
   - 战斗节点池：**单独窗口**，不和其他池并行 drain。
3. **战斗优雅下线**：
   - cordon 节点，禁止新 Pod 调度。
   - 匹配器停止分配新 room 到该节点。
   - 等存量 room 自然结束（按 P99 对局时长估算）。
   - 超时长局维护窗口内统一强踢 + 补偿。
   - 确认无战斗 Pod 后再 drain。

> ⚠️ **别混**：**cordon 只关门，drain 才清场**。战斗节点 drain 前必须先「空服」，否则 PDB 会卡住或导致 room 被强制终止。**不要**用 `kubectl delete pod` 强删战斗 Pod。

> 📝 **面试**：「战斗服有状态，升级分组做：网关可滚，战斗池先 cordon、停新局、等 room 空、再 drain。控制面先升，战斗池单独窗口。」

### 再追问

**如果老板说「最多接受 30 秒断线」？**——大厅/登录可以蓝绿或快速滚动，30 秒内切流完成；战斗服 30 秒不够等 room 结束，需要业务层支持 room 状态快照到 Redis 并在新进程恢复，或者走维护窗口强踢。

**跨服战斗怎么办？**——跨服战斗池与本服战斗池分开升级，避免全球玩法同时中断。跨服 room 的迁移和排空策略与本服一致。

## Q8

**★★★★☆｜战斗服优雅下线要怎么做？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、第四题：设计集群升级方案](知识点.md)

### 场景

发版时战斗 Pod 被 RollingUpdate 终止，玩家局中掉线、判负。事后复盘发现有人把战斗服和登录服放进了同一个 Deployment。


集群升级分组。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：战斗服优雅下线 = 不再分配新局 + 等老局结束 + 超时强踢 + 最后 drain，四步缺一不可。

四步：

1. **不再分配新 room**：匹配器/目录层把待升级节点标记为不可分配。
2. **等存量 room 结束**：自然排空，平均时长按 P99 对局时间估算。
3. **flush 与持久化**：结算数据、room 快照先写 Redis/MySQL，避免 kill 丢数据。
4. **超时强踢 / drain**：维护窗口到期后统一踢掉超长对局，确认无战斗 Pod 再 drain 节点。

> ⚠️ **别混**：**liveness 探针不能当排空信号**。liveness 只表示进程活着，不代表可以安全终止。需要业务层暴露「room_count=0」或「draining=true」接口，作为 readiness/终止条件。

> 📝 **面试**：「战斗服下线的正确顺序：停新局 → 等老局 → flush → 超时强踢。RollingUpdate 直接杀 Pod 等于判负。」

### 再追问

**怎么判断可以安全 drain 了？**——查询该节点所有战斗 Pod 的 room_count，全部为 0 且持续 30 秒无新 room，才能执行 drain。不要只看 Pod 状态 Running。

**如果一局打了 2 小时还没结束？**——维护窗口设计时就要约定「最大对局时长 + 超时补偿」。超长对局不能无限等，到点统一结算并补偿玩家。

## Q9

**★★★★★｜设计一个游戏发布系统：支持灰度和一键回滚。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、第五题：设计发布系统](知识点.md)

### 场景

团队现在发版靠人工 `kubectl set image`，回滚靠 `rollout undo`。一次发版后登录成功率掉，undo 后还是坏，最后发现是 ConfigMap 也被改了但 undo 回不来。


优雅下线四步。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：发布系统 = CI 钉死 digest/version → 灰度漏斗（按服/uid 白名单/区）→ 全量 → SLI 门禁 → 回滚；回滚对象可能是 digest、配置 version、CDN 指针或 min，不是同一个按钮。

先问约束：发布频率、回滚时限、游戏服状态、客户端协议是否兼容、灰度维度。

架构：

```text
CI pipeline → 制品库（镜像 digest + 配置 version + 资源 manifest）
                ↓
            灰度层
              · 内网验证
              · 指定服
              · uid 白名单 1% → 5% → 20%
              · 按区/渠道
                ↓
            全量 + SLI 观察
                ↓
            异常 → 回滚（按类型选对象）
```

发布通道：

- **大厅/登录 HTTP**：滚动更新或蓝绿，看 readiness 和 P99。
- **配置/活动数值**：热更 reload，对账 loaded_version，**不配 RollingUpdate**。
- **战斗二进制**：摘流四步——停新局、等老局结束、flush、换 digest。
- **客户端资源**：CDN 指针切换，配合强更/热更。
- **协议强更**：客户端版本门闸，服务端双协议兼容。

> ⚠️ **别混**：**灰度 ≠ 只发 1% 副本**。副本比例不等于流量比例；精确的灰度要靠入口 weight 或 uid 白名单。按源 IP 灰度会被加速器/NAT 打偏。

> 📝 **面试**：「发布系统分四层：CI 钉制品、灰度漏斗、全量观察、按类型回滚。战斗走摘流四步，配置热更独立，灰度按 uid/服/区。」

### 再追问

**灰度通过了，全量后还出问题怎么办？**——灰度样本可能不包含某些机型/网络/渠道。全量后要保留「快速回切」能力：蓝绿可秒切，滚动可 `rollout undo`，配置可重载旧 version。同时全量后 30～120 分钟是观察窗口。

**发布和活动整点冲突吗？**——冲突。活动整点前后 ±30 分钟冻结无关变更。只有 hotfix 可发布，且要经过审批。

## Q10

**★★★★☆｜热更与冷更的边界是什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、第五题：设计发布系统](知识点.md)

### 场景

策划要「热更」改一个掉落概率，开发说改枚举值必须强更；另一个团队把战斗二进制镜像更新当成「热更」发了，结果进行中的局全部判负。


发布四层与回滚分型。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：热更是进程不重启的变更；能热更的只有配置和脚本；改结构体、协议字段含义、二进制镜像都属于冷更/强更。

分类：

- **配置热更**：活动开关、掉落率、数值表。进程 reload，对账 loaded_version。
- **脚本热更**：Lua/热补丁。可改分支逻辑，但改不了结构体布局；进行中的局要统一版本或强制结算。
- **二进制冷更**：战斗逻辑镜像。必须摘流四步或维护窗口。
- **协议强更**：改枚举含义、删必填字段、改握手。必须客户端版本门闸 + 服务端双协议。
- **资源替换**：CDN 指针切换，服务端要兼容新旧资源协议。

> ⚠️ **别混**：**热更 ≠ 滚动更新**。滚动更新是换 Pod，会杀进行中的 room；热更是进程内 reload。把战斗二进制更新叫「热更」是重大事故隐患。

> 📝 **面试**：「能热更的只有配置和脚本；二进制和协议变更必须冷更或强更。判断标准：进程是否需要重启、协议是否兼容、进行中的局是否会不一致。」

### 再追问

**配置热更后，部分服没加载到新配置怎么办？**——以对账 loaded_version 回执为准，不齐不能开活动。否则半服新规则半服旧规则会导致资损或玩家投诉。

**脚本热更进行到一半的局怎么办？**——按房间切版本，或维护窗口强制结算。禁止一局内一半玩家用新公式、一半用旧公式。

## Q11

**★★★★☆｜发布出问题了，按一个「一键回滚」按钮够吗？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、第五题：设计发布系统](知识点.md)

### 场景

一次发版后 CCU 掉，值班按了「回滚」。undo 后登录还是坏，后来发现 ConfigMap 和 CDN 指针都没回，部分玩家已经装上了新客户端包。


热更 vs 冷更。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：不够。`rollout undo` 只回工作负载 revision；ConfigMap、Secret、CDN 指针、客户端 min、DB schema、热更配置都要单独回，经济产出错了还要停产出 + 回档。

回滚对象清单：

- **镜像 digest**：`kubectl rollout undo`。
- **配置 version**：热更通道重载旧 version，对账回执。
- **CDN 指针**：把 `version.json` 打回上一版，确认旧包 HIT。
- **客户端 min**：先恢复服务端双协议，再降 min。
- **DB schema / 数据**：如果新代码已经写了新列，undo 代码前要先处理数据；经济产出错了要走数据回档流程。

> ⚠️ **别混**：**代码回滚 ≠ 数据回滚**。新代码已经写了一批错误数据，undo 镜像不会自动修数据。

> 📝 **面试**：「回滚不是一键。要分清坏的是 digest、配置 version、CDN 指针、min，还是数据。镜像 undo 只解决工作负载。」

### 再追问

**怎么设计才能回滚更快？**——发版前把回滚对象清单写进变更单；蓝绿部署秒切；配置与镜像分离发布；revisionHistoryLimit ≥ 5；保持旧镜像 30 天不删。

**灰度 5% 时发现崩溃翻倍，要等什么吗？**——不等，立刻停灰度。5% 已经坏说明问题真实存在，不要观察到 100%。

## Q12

**★★★★★｜综合：面试官让你设计整服 SRE 技术保障体系。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一场系统设计面试的通用动作](知识点.md) · [七、作战：五题共同的翻车点决策树](知识点.md)

### 场景

面试官最后 5 分钟说：「如果把前面几个问题合起来，让你从零设计一套游戏 SRE 保障体系，你会怎么讲？」


五题共同翻车点。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：整服 SRE 体系 = 稳定性定标（SLI/SLO）→ 容量建设（压测+分层账本）→ 变更控制（发布/升级/活动窗口）→ 可观测（监控告警）→ 事故响应（P0 流程），五块闭环。

按 20 分钟节奏组织：

1. **定标**（2 分钟）：登录成功率、进战斗成功率、支付到账率、CCU 完整性四条 SLI；5 分钟窗口 SLO。
2. **容量**（5 分钟）：目标 CCU 拆登录/玩法/发奖三峰；分层算 C/D；**全链路压测**校准；α=0.7 写进 runbook。
3. **架构**（5 分钟）：客户端 → CDN → 目录 → 排队 → Gate → 大厅/战斗 → MySQL/Redis；战斗服有状态单独设计。
4. **变更控制**（4 分钟）：发布灰度/回滚、集群升级分组、活动整点冻结无关变更。
5. **可观测与响应**（4 分钟）：Prometheus + Alertmanager 分组抑制；P0 唯一指挥官；对外四句模板。

收尾一句话：「这套体系的目标不是永不故障，而是知道先坏哪层、旋钮在哪、回滚多快。」

> ⚠️ **别混**：**SRE 不是运维换个名字**。核心是用 SLI/SLO 和错误预算管理稳定性，用工程化手段减少 toil，而不是堆人力值班。

> 📝 **面试**：「我会从定标、容量、架构、变更、可观测响应五块讲。关键是分层、压测、灰度、回滚 RTO，以及战斗服有状态不能当 Web 滚。」

### 再追问

**如果预算有限，哪块可以砍？**——不能砍 SLI/SLO 和错误预算（这是 SRE 的核心）；可以砍非核心监控指标、减少保留时长、用采样 trace 代替全量。但容量压测和发布回滚不能省。

**怎么向老板证明这套体系有价值？**——用数字：发版 RTO 从小时降到分钟、P0 数下降、开服成功率提升、活动当晚值班告警数下降。SRE 的价值要能量化。

## Q13

**★★★★★｜五题里「战斗服有状态」怎么答才加分、怎么答会翻车？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、第一题：设计开服系统](知识点.md) · [05、第四题：集群升级](知识点.md)

### 场景

面试官追问：「你们战斗服在 K8s 里 Deployment 滚动更新不行吗？」


60 秒抢救。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：战斗 room 钉进程内存——**不能**抄 Web 的 `maxUnavailable`；要答 drain、cordon、空服升级、回滚 RTO。

加分答法：

```text
① 状态边界：room 在进程内，滚更 = 对局死亡
② 升级策略：新池预热 → 老池 cordon → 停新局 → 等 room 空 → drain
③ 超时：强踢 + 补偿规则要写进设计
④ 回滚：镜像 digest + 配置 version 分开回滚
```

翻车答法：「HPA 自动扩、RollingUpdate 25%」——面试官会判不懂游戏。

> 📝 **面试**：「战斗服是 Stateful 逻辑，K8s 编排要配合业务 drain，不是无脑 Deployment。」

### 再追问

**和 Gate 的区别？**——Gate 无状态可百分比滚；战斗有 room 状态。**不要**混为一谈。

## Q14

**★★★★★｜综合白板：15 分钟讲清「新游开服系统」——从约束到回滚。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、第一题：设计开服系统](知识点.md) · [七、作战](知识点.md)

### 场景

最后一轮系统设计，只给 15 分钟。


本套题收尾：五题 30 秒口径。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：3min 约束 + 3min 容量 + 4min 架构（目录/排队/Gate/战斗）+ 3min 削峰（令牌桶/预热/摘目录）+ 2min 回滚 RTO。

必画骨架：

```text
客户端 → CDN/版本 → 目录 server_list → 排队 → Gate → 大厅/战斗 → Redis/MySQL
三道闸：排队、令牌桶登录、目录维护态
失败先摘目录，别让用户无限重试打穿 Gate
回滚：镜像 + version.json + 配置指针，写进变更单
```

数字示例：10 万 CCU 开服峰，登录 QPS 3 万，Gate 按 2× 预留 + 排队。

> 📝 **面试**：收尾——「开服不是扩容这么简单，是入口受控放量 + 有状态战斗单独升级策略。」

### 再追问

**排队体验怎么答？**——透明 ETA、VIP/老玩家通道、维护公告——**不要**只说「加个 Redis 队列」。
