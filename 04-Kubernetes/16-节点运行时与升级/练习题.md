## Q1

**★★★★★｜cordon、drain、uncordon 分别干什么？drain 要注意什么？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.2


### 场景

活动前要给战斗服节点换盘。有人准备直接 reboot。群里在问 drain 会不会把 DaemonSet 也赶走。

### 完整解答

**一句话**：cordon 拒新调度，drain=cordon+驱逐业务 Pod，DaemonSet 通常 `--ignore-daemonsets` 留下。

cordon 只拒绝新调度，已有 Pod 还在。drain = cordon + 驱逐业务 Pod，控制器在别处重建。uncordon 开门再接新活。

```bash
kubectl drain <node> \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --grace-period=60 \
  --timeout=300s
```

卡住先查，不是 `--force`：PDB、裸 Pod、emptyDir / local PV、STS RWO。游戏单进程区服：drain 前迁玩家。drain 发 SIGTERM，长连接直接断。裸关机等于不给 grace，还可能双节点同时失联，PDB 也救不了。

DaemonSet 通常留下：本节点还要 CNI、日志采集。drain 清的是可在别处重建的业务副本。

### 再追问

`--disable-eviction`？——拆 PDB，生产留变更记录。窗口不够就改窗口或先扩节点。

## Q2

**★★★★★｜节点 NotReady 的时间线？kubelet 挂了，已有游戏服还在吗？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.3


### 场景

某战斗节点 kubelet 卡死。监控打 NotReady。有人要重启该节点上所有逻辑服 Pod。玩家还在对局。

### 完整解答

**一句话**：kubelet 挂了进程通常还在；约 40s NotReady，默认约 5min 才驱逐，先救 kubelet 不杀业务。

三问：进程还在不在、能不能变更、会不会被赶走。kubelet 挂了 **进程通常还在**。约 40s 标 NotReady，打 NoExecute 污点；默认容忍约 5min 才驱逐。这窗口里长连接可能还活着。先 ssh 救 kubelet、磁盘、CNI、证书、PLEG，**不要先杀业务进程**。

OOMKilled 是本容器超 memory limit。NotReady 驱逐是节点失联或节点压力。先看 `describe node` Conditions。

### 再追问

DiskPressure 已经在 Evict，还要不要等 5 分钟？——那是本机压力驱逐，不是失联那条 5 分钟。先清盘。两条时间线不要混。

## Q3

**★★★★★｜集群升级顺序？kubelet 能不能比 API Server 新？kubeadm 敲什么？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.5 · §4.2


### 场景

要把 1.28 升到 1.29。有人想先把节点 kubelet 升完「少停机」。战斗服和无状态网关在同一节点池。

### 完整解答

**一句话**：先升控制面再 drain 升 kubelet；kubelet 不能比 API Server 新，可落后约 2 个小版本。

先备份，`kubeadm upgrade plan`，第一台控制面 `upgrade apply`，其它 `upgrade node`。Worker **先 drain** 再升 kubelet。**kubelet 不能比 API Server 新**，可落后约 2 个小版本。控制面新、节点旧是允许的 skew。反过来会出现奇怪的 API 错误。

再升 CNI / CoreDNS / metrics-server。一次并行 drain 多台是事故。先升 1 台非战斗节点，观察 15–30 分钟。不要跳小版本。不要在 kubeadm 之外抢改静态 Pod 镜像。

### 再追问

控制面已经升了、节点还没升，能不能干活？——能。这是规定允许的 skew。

## Q4

**★★★★★｜为什么排障用 crictl 不是 docker？ImagePullBackOff 怎么查？**

**覆盖**：核心 · 必会 · 常用
**对应**：知识点 §3.1


### 场景

1.26 集群上 `docker ps` 是空的。业务 Pod ImagePullBackOff。有人说仓库挂了，但别的节点同镜像是好的。

### 完整解答

**一句话**：1.24+ 无 dockershim，排障用 crictl；ImagePull 在出问题节点上 pull 复现。

1.24 起无 dockershim，kubelet 直连 containerd。看 K8s 容器用 crictl，ctr 要加 `-n k8s.io`。ImagePull 在 **出问题的那台节点** 上 `crictl pull` 复现：tag / digest、imagePullSecrets、该节点到仓库的网络、磁盘满。`IfNotPresent` + 同 tag 覆盖推：节点不拉新层。生产钉 digest。不要在生产用 `crictl rm` 代替 kubectl。

pause 忘同步：新节点 `RunPodSandbox` 失败。升级 K8s 常换 pause 小版本。

### 再追问

containerd 要盯哪几个配置？——SystemdCgroup=true、sandbox_image、CRI socket 与 kubelet endpoint 对上。不背全集。

## Q5

**★★★★☆｜Allocatable 和 Capacity 差在哪？不预留会怎样？**

**覆盖**：必会 · 常用 · 常考
**对应**：知识点 §3.4


### 场景

节点 `kubectl top` 看起来还有 CPU，但新 Pod 一直 Insufficient cpu。另一台没留 kubeReserved 的节点，kubelet 自己 OOM 了。

### 完整解答

**一句话**：Scheduler 只看 Allocatable，不是 Capacity 也不是 top 瞬时空闲。

Capacity 是整机。Allocatable = Capacity − kubeReserved − systemReserved − eviction。**Scheduler 只看 Allocatable**。`top` 是实际用量，调度看 request。不预留：业务 request 把节点吃满，kubelet 没资源，节点集体 NotReady。`describe node` 看 Allocated。

eviction-hard 从 Capacity 扣一块，让 kubelet 在打满之前有空间赶 BestEffort、清镜像。磁盘阈值配了却不预留内存，一样会把控制面组件饿死。

### 再追问

Pending 时 top 还有空闲？——调度看 request 之和，不看瞬时空闲（06）。

## Q6

**★★★★☆｜drain 卡住十分钟，能不能 --force？**

**覆盖**：必会 · 常用
**对应**：知识点 §3.2 · §8


### 场景

换盘窗口只剩 20 分钟。`kubectl drain` 停在 waiting for PDB。有人准备加 `--force --disable-eviction`。

### 完整解答

**一句话**：drain 卡住先看 PDB/裸 Pod/emptyDir/STS RWO，不要第一刀 `--force`。

先看挡住的是谁。PDB：先扩副本或等滚动。裸 Pod：确认能否删。emptyDir / local PV：确认可丢再 `--delete-emptydir-data`。STS RWO：目标节点能否挂同一块盘。

游戏大厅 PDB 是故意挡你的。窗口不够就改窗口或先扩节点。`--force` 对裸 Pod 是允许删；`--disable-eviction` 拆 PDB，生产留变更记录。DaemonSet 常规 `--ignore-daemonsets`。

### 再追问

双节点同时 reboot？——PDB 也救不了。不要裸关机。

## Q7

**★★★☆☆｜cgroup driver 不一致会怎样？PLEG unhealthy 呢？**

**覆盖**：常用 · 常考
**对应**：知识点 §3.1 · §8


### 场景

刚装完的新节点，Pod 全是 CreateContainerError。另一台老节点 kubelet 日志刷 PLEG is not healthy，节点 NotReady，游戏进程还在。

### 完整解答

**一句话**：kubelet 与 containerd cgroup driver 必须一致；PLEG unhealthy 先重启 kubelet 不杀业务。

kubelet 用 systemd、containerd 仍 cgroupfs → 起容器失败。两边都改成 systemd，重启 kubelet 和 containerd。`crictl info` 能看到 runtime 的 driver。只改一边等于没改。

PLEG 是 kubelet 用来「看见」容器状态的。不健康 = 上报失败 = NotReady。常见 containerd 卡住或节点很卡。重启 kubelet / containerd，**先别杀业务进程**。

### 再追问

和证书过期像不像？——都是心跳 / 上报失败。`kubeadm certs check-expiration`。

## Q8

**★★★☆☆｜战斗服节点怎么升级？能和无状态节点同一批 drain 吗？**

**覆盖**：必会 · 常用 · 常考
**对应**：知识点 §7.3


### 场景

升级窗口只有凌晨两小时。计划把网关池和战斗池一起并行 drain。另一晚还要发战斗服新版本。

### 完整解答

**一句话**：战斗节点单独窗口 drain，先空服迁玩家；不能与无状态节点同一批，与发版窗口错开。

不能同一批。战斗服有状态、有长连接，drain 等于踢玩家。独立节点池、独立窗口；先空服 / 迁玩家 / 停匹配；单节点 drain → 升 → 验证 CCU → 再下一台。

云上更稳：加一台新版本节点进池，drain 旧机，回滚就是把流量打回旧节点。有状态本地盘只能原地或先迁盘。托管不会帮你空战斗服。

与 15 发版窗口错开：不要同一晚既滚战斗服又 drain 战斗节点。

### 再追问

surge 节点谁排？——你。问清 PDB、有状态盘、空服节奏再点托管升级按钮。

## Q9

**★★★☆☆｜只改了 kubelet maxPods，新 Pod 报 FailedCreatePodSandBox，为什么？**

**覆盖**：常用
**对应**：知识点 §8 · §5


### 场景

节点还挺空，把 maxPods 从 64 调到 110。多出来的 Pod 全部 sandbox 失败，CNI 报 IP 不够。

### 完整解答

**一句话**：maxPods 和每节点 Pod CIDR 容量必须一起改，只改 maxPods 会 FailedCreatePodSandBox。

maxPods 是 kubelet 愿意管多少个 Pod。每个 Pod 还要一张 CNI 发的 IP。每节点 Pod CIDR 的容量必须一起改（10）。只改 maxPods，调度器以为还能塞，CNI 没地址就 FailedCreatePodSandBox。Events 会写 sandbox / CNI，不要先怀疑业务镜像——sandbox 失败发生在起业务容器之前。专有仓还要确认 pause 能拉。

### 再追问

改 maxPods 和改 ENI 辅助 IP 要同一张变更单吗？——要。

## Q10

**★★★☆☆｜升级后节点起不来，你按什么顺序查？**

**覆盖**：必会 · 常用
**对应**：知识点 §8


### 场景

控制面 1.29 已经好了。第一台节点升完 kubelet 后 NotReady，kube-system 里 pause 拉不下来，containerd 日志在报 cgroup。

### 完整解答

**一句话**：升级后 NotReady 按 skew/cgroup/pause/CNI/证书顺序查，不要从业务镜像查起。

按升级引入的差异对，不要从业务镜像查起：kubelet 版本 > API → 先退 kubelet；cgroup driver 不一致 → 两边 systemd；pause 拉不到 → 专有仓同步；CNI 不兼容 → 按矩阵升 CNI；证书过期 → certs check-expiration。

这台如果是战斗节点，uncordon 之前确认 Ready 和 CNI。回滚用旧包或未升的新节点顶上，不要在半残节点上继续批量。

### 再追问

为什么先升控制面能避免大部分奇怪 API 错误？——新 kubelet 用新字段；旧 API 不认。旧 kubelet 对新 API 一般向前兼容。
