## 1. 基本概念

01 说过：数据包不经过 kube-proxy 用户态，它只负责 **更新** 本机转发规则。Cilium 用 eBPF 把「更新规则」和「转发」都放进内核 hook，不再走漫长的 iptables 链。agent 挂了，和 kube-proxy 挂了同类：**存量往往还在，规则不再更新。**

eBPF 是内核里的可编程虚拟机：在 hook 点跑经过 **verifier** 的程序，不改内核源码、不加载任意 ko。verifier 拒绝越界、死循环、乱调辅助函数，这是能上生产的前提。过不了验证就上不了机，不会当后门 ko 用。不是「内核 JavaScript 随便写」。

| hook（运维相关） | 典型用途 |
|------------------|----------|
| XDP / TC / socket / cgroup | 网络：更早拦包、DNAT、策略 |
| kprobe / uprobe / tracepoint | 观测：系统调用、延迟 |
| LSM | 安全：进程/文件/网络强制 |

Cilium 还是 CNI：配 Pod IP、连通、NetworkPolicy。和 Calico/Flannel 的差别不只「另一种插件」，而是数据面从「路由 + iptables」换成 eBPF。附带 Hubble 和 L7，传统 CNI 要另装。

> **记住**：转发在内核 hook 上跑，agent 只负责下发；verifier 过不了就上不了机。

## 3. 原理

原理只保留动手和面试会用到的：规则为什么慢、Hubble 看见什么、eBPF 不等于安全银弹、L7 开在哪。

**本节 4 块：** 3.1 路径 · 3.2 Hubble · 3.3 可观测 vs 安全 · 3.4 L7

### 3.1 为什么 iptables 会慢

kube-proxy iptables：每个 Service、每个 Endpoints 都是链上的规则，查找近似 O(n)，更新常整表刷新。Service × Pod 到几万、几十万规则，延迟和 CPU 随规模涨。IPVS 好一些（哈希），仍有多次内核跳转。08 的结论：大集群评估 IPVS；再往上，eBPF 在更早 hook 直接 DNAT。

玩家打大厅 ClusterIP，包已经到某台 Worker 的网卡：

| | 传统 iptables | Cilium eBPF |
|--|---------------|-------------|
| 拦包 | PREROUTING / KUBE-SERVICES | 更早的 sock/TC/XDP |
| 查找 | 按 Service 一条条匹配 | map：ClusterIP → 后端 Pod |
| 谁更新 | kube-proxy Watch 后改链 | agent Watch 后更新 map |
| 这一包经不经用户态 | 不经 | 不经 |

你眼睛看到的差别：小集群几百行规则体感不明显。到几万规则，CPU `%si` 和尾延迟一起涨，滚动一次 Endpoints 变化还要整表刷新。

老内核程序装不上或功能残缺。hook 和辅助函数是内核逐步加的。这是选 Cilium 的硬前提（16 升级也要看）。

### 3.2 Hubble：无 sidecar 的流量图

NetworkPolicy 上线后部分匹配失败。tcpdump 看不清是不是策略 drop。Hubble 用 eBPF 在内核看连接：谁连谁、L3/L4/L7、丢弃原因、延迟和重传。不改应用、不给每个 Pod 塞 Envoy。排障「网络不通」和 NetworkPolicy 拒绝，能看到 **断在哪、哪条策略 drop**。

```mermaid
flowchart LR
    a[hubble observe] --> b[src / dst / port]
    b --> c[verdict forwarded / dropped]
    c --> d[drop 带 policy 名]
    d --> e[可选 L7 path / method / topic]

    classDef a fill:#7C3AED,stroke:#4C1D95,stroke-width:2px,color:#fff
    class a,b,c,d,e a
```

```bash
hubble status
hubble observe -f
hubble observe --type drop -n battle
```

| 你看到的 | 含义 | 下一步 |
|----------|------|--------|
| drop + policy 名 | 就是这条策略拒的 | 改 CNP / 原生 NP，不要先关 CNI |
| forwarded 但应用超时 | 网络层过了 | 回到 17：localhost → EP → ClusterIP |
| Hubble 没数据 | agent 不健康，观测先瞎 | 先救 agent，不要说网络全死 |

和 Istio sidecar 比：省资源、少一跳。代价是复杂熔断/重试/流量拆分仍不如 Istio。Istio Ambient 也在往 eBPF/ztunnel 靠，方向是减 sidecar。大规模集群里「每个战斗服再加一个 Envoy」的 CPU 账，Hubble 这种路径更对游戏场景。

没有 Hubble 时仍走 17 的分层：localhost → EP → ClusterIP → 跨节点。跨节点不通先怀疑 CNI（10），不要一上来重装 Cilium。

> **记住**：Hubble 无 sidecar 看拓扑和 policy drop；没 Hubble 就退回 17 的分层。

### 3.3 eBPF：可观测 vs 安全

同一套机制，三条产品线不要混成一句「上了 eBPF 就安全」。

| 方向 | 做什么 | 典型 | 不是什么 |
|------|--------|------|----------|
| **网络数据面** | LB、DNAT、NetworkPolicy、替代 kube-proxy | Cilium | 不是 WAF |
| **可观测** | 连接、延迟、drop 原因、L7 可见 | Hubble | 不是 SLO 本身（18） |
| **运行时安全** | 进程执行、文件、syscall、网络 LSM | Tetragon / Falco（部分 eBPF） | 不是替代 RBAC/准入（13） |

可观测：在 hook 上看「发生了什么」，默认不拦截。安全：在 LSM/策略点 **拒绝** 非预期行为。Hubble 看到 drop 多半是 NetworkPolicy；Tetragon 拦住的是「这个容器不该 exec / 不该读这块密钥」。verifier 保证程序自己不把内核打挂，**不保证** 你的策略写对了。

游戏集群：先用 Hubble 把 NP 和延迟讲清楚，再决定要不要上运行时安全。战斗服全量 syscall 跟踪是税；支付/GM 节点、CI runner 更值得。不要用「有 eBPF」代替 13 的 RBAC 和 03 的准入。

### 3.4 L7 策略：比原生 NP 多一层

支付网关只该打 `POST /v1/charge`。原生 NP：只能 IP / 端口 / 标签（10）。CiliumNetworkPolicy 可在允许的端口上再限制 HTTP method/path、Kafka topic、DNS query。不是所有流量都开 L7 解析，只给敏感路径开，省 CPU。

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: pay-api-only
spec:
  endpointSelector:
    matchLabels: { app: game-pay }
  ingress:
    - fromEndpoints:
        - matchLabels: { app: game-gateway }
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http:
              - method: POST
                path: "/v1/charge"
```

Hubble 对这次 drop 能打出 policy 名和 HTTP path。内核态解析比用户态 sidecar 便宜，仍有开销。支付、GM 接口、管理 Kafka 适合；战斗服心跳全量 L7 检查通常不划算。YAML 里把 SQL SELECT 写成 http method 是错的——按协议用 HTTP/Kafka/DNS 各自的 L7 rule。

sidecarless Mesh：eBPF 做基础 L7 可见与策略。要完整 Service Mesh 治理仍选 Istio（或 Gateway API 的实现）。Cilium 也可做 Gateway API 后端——那是南北向入口，和东西向 eBPF 策略是两层。选型：完整治理 → Istio；轻量可观测 + L7 墙 → Cilium。已有 Istio 重治理，不必为了 Mesh 再换 CNI，可并存评估，职责写清。不要两个都当「唯一数据面」却互不知情。不要用 Mesh 当 CNI 的唯一理由。

> **记住**：L7 策略按需开在敏感路径；战斗服心跳全量解析通常不划算。

## 4. 安装部署

生产怎么选：

| 项 | 选 | 不选 |
|----|----|------|
| 节点少、NP 只到端口、内核老 | Calico/Flannel + kube-proxy | 为简历全面 eBPF |
| 规则爆炸、要 Hubble、要 L7、延迟敏感 | Cilium eBPF | 小集群交调试税 |
| 已有 Istio 重治理 | 并存评估，职责写清 | 为了 Mesh 再换 CNI |
| 已有 IPVS | 按 Hubble/L7/更短路径加税 | 「IPVS 不能用」 |

落地硬前提：内核够新，对 Cilium 兼容矩阵（16）。eBPF 程序比 iptables 难一眼看懂；升级要匹配内核能力；大规模还要规划 Cilium 自己的状态存储。

验收：Hubble 能 observe；ClusterIP / NodePort / 外部流量在 replacement 下测过再关 kube-proxy。不要只测 ClusterIP。很多登录走 Ingress/LB（14），NodePort 仍在的节点上要单独测。

## 5. 核心配置

| 项 | 生产怎么用 | 改错会怎样 |
|----|------------|------------|
| kube-proxy-replacement | 覆盖三种流量再关 kube-proxy | NodePort 不通 |
| Hubble | 开；L7 可见性按需 | 全开吃 CPU |
| L7 policy | 支付/GM/管理 Kafka | 心跳全量解析 |
| agent 内存 | OOM 先给 agent 加，不给战斗服加 | CrashLoop，map 不更新 |
| Host 防火墙 | 不要和 eBPF 抢 | 外部流量黑盒 |
| 兼容矩阵 | kubelet / 内核 / Cilium 一张表 | hook 装不上 |

> **记住**：回滚 replacement 是重新拉起 kube-proxy，不是重启业务。

## 7. 常用操作

### 7.1 kube-proxy-replacement

确认 Cilium 已覆盖原 kube-proxy 的 ClusterIP/NodePort/外部流量模式，内核与配置支持 replacement，Host 防火墙没有和 eBPF 抢。分批：先观察 Hubble 和延迟，再关 DaemonSet。回滚是重新拉起 kube-proxy 并关 replacement，不是重启业务。关了之后 NodePort 不通——replacement 没覆盖全。先核对流模式，再分批回滚 kube-proxy，不要先重启游戏进程。

### 7.2 游戏集群落地

```mermaid
flowchart LR
    a[对内核兼容矩阵] --> b[非战斗池开 replacement]
    b --> c[看 Hubble / P99 / NodePort]
    c --> d[大厅 / 网关池]
    d --> e[战斗服单独窗口空服]
    e --> f[三种流量都覆盖再关 kube-proxy]

    classDef a fill:#2563EB,stroke:#1E3A8A,stroke-width:2px,color:#fff
    classDef b fill:#16A34A,stroke:#14532D,stroke-width:2px,color:#fff
    class a,b,c a
    class d,e,f b
```

注意点：

1. **agent 挂了 ≈ 规则不更新。** 存量长连接往往还在；新登录、重连、滚动后旧后端会出问题。拉起 agent，核对 EndpointSlice。不要先重启战斗服——会主动拆掉还活着的长连接。
2. **战斗服最后切。** 先非战斗池、再大厅、再战斗窗口。
3. **L7 不要打在心跳上。** 支付/GM 开；UDP/心跳只到端口。
4. **Hubble 代替每 Pod Envoy** 做东西向看见。完整金丝雀仍走 15。
5. **日志/etcd 同盘是另一章的税**（19、02）；数据面 CPU `%si` 高才是 iptables 链的问题。
6. **maxPods 和每节点 CIDR 没一起改**，FailedCreatePodSandBox 看起来像 CNI 坏了，其实是 16。

活动扩容滚动后，某节点 cilium-agent OOM。已在对局的长连接还在，新匹配进这节点失败。拉起 agent 后 Hubble 看到后端 map 追上 EndpointSlice。若当时重启战斗服，等于自己踢完还活着的玩家。

## 8. 生产排障

不要答「Cilium 挂了网络全死」。先拆三问：已有连接、新连接、Endpoints 已变之后。userspace 转发早已废弃（08）；谁当「规则下发器」，谁挂了都是「不再更新」。

```mermaid
%%{init: {"flowchart": {"padding": 16, "nodeSpacing": 28, "rankSpacing": 48}, "theme": "base"}}%%
flowchart TB
    subgraph gate ["先分叉"]
        A[网络 / 登录异常] --> B{agent / 策略 / 跨节点?}
    end

    subgraph agent ["下发器"]
        B -->|CrashLoop / OOM| C[拉起 agent · 加内存]
        B -->|map 旧 IP| D[等 Ready · 对 EndpointSlice]
    end

    subgraph pol ["策略"]
        B -->|Hubble drop + policy| E[改 NP / CNP]
        B -->|forwarded 仍超时| F[走 17]
    end

    subgraph cni ["连通"]
```

| 现象 | 先做什么 | 不要做什么 |
|------|----------|------------|

| Hubble 没数据 | 先救 agent | 说网络全死 |

## 9. 必会 · 常考

白板和追问高频，能一口回：

| 说法 | 对错 | 口径 |
|------|:----:|------|
| Cilium 在用户态拦每一包 | 错 | 转发在 hook；agent 只下发 |
| eBPF 等于乱加载 ko | 错 | verifier 过不了上不了机 |
| 小集群必须上 Cilium | 错 | 规则不多不必交调试税 |
| 上了 IPVS 就不能用 Cilium | 错 | 理由变成 Hubble/L7/更短路径 |
| agent 挂了游戏长连接立刻死 | 错 | 存量往往还在；规则不再更新 |
| Hubble 必须插 sidecar | 错 | 内核看流，不改应用 |
| 有 Hubble 就不用 17 | 错 | forwarded 仍超时要分层 |
| 有 eBPF 就安全了 | 错 | 观测 ≠ LSM 拦截 ≠ RBAC |
| L7 对战斗心跳全开 | 错 | 只给敏感路径；按真实协议 |
| sidecarless 能替代 Istio 金丝雀 | 错 | header 切 5% 仍是 14/15 |
| 关 kube-proxy 只测 ClusterIP | 错 | NodePort / 外部流量也要覆盖 |
| 回滚 replacement 靠重启业务 | 错 | 重新拉起 kube-proxy |
| FailedCreatePodSandBox 一定是 Cilium | 错 | 先看 maxPods / CIDR |
| Gateway API 和东西向策略是一回事 | 错 | 南北 vs 东西两层 |
| 为简历换 CNI | 错 | 内核版本和调试是税 |

数字：iptables 规则随 Service×Pod 涨；verifier 是硬门槛；L7 按需；战斗池最后切。

易混：agent 挂 vs 数据面死；iptables vs IPVS vs eBPF map；Hubble drop vs 应用超时；可观测 vs 运行时安全；原生 NP vs Cilium L7；kube-proxy 下发 vs Cilium 下发（影响面同一张图）。
