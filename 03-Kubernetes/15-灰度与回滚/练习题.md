## Q1

**★★★★★｜滚动更新怎样接近零停机？配错就绪探针会怎样？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.1


### 场景

大厅滚动，maxUnavailable 默认 25%，没有 readiness。发版窗口 502 一片。有人说 Ingress 坏了。

### 完整解答

**一句话**：零停机靠四件套：maxUnavailable=0、readiness、preStop+grace、minReadySeconds；没 readiness 就滚动 502。

四件套：`maxUnavailable=0` 先起后杀；readiness 未就绪不进 Endpoints；preStop + SIGTERM，grace 够，抽干旧连接；minReadySeconds 防 Ready 立刻挂。

没有 readiness，K8s 把 Running 当可接流量 → 滚动 502。探针永远失败 → 滚动卡死。liveness 过严会在滚的过程中杀新 Pod。见 04、05。PDB 和 maxUnavailable=0 一起，才是少副本时「先起后杀」仍成立。

### 再追问

pause 干什么？——停在当前比例观察。有问题 undo，没问题 resume。手工金丝雀。

## Q2

**★★★★★｜蓝绿、金丝雀、流量镜像怎么选？回滚 RTO 差在哪？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.2 · §3.3 · §3.4


### 场景

支付 HTTP 要秒级回切，预算允许双倍副本。大厅要先 5% 看登录成功率。有人全用滚动「省事」。另有人用镜像代替金丝雀。

### 完整解答

**一句话**：蓝绿秒级切流要双倍资源；金丝雀改 weight；镜像只验证读路径，不能代替金丝雀。

```mermaid
flowchart TB
    bg[蓝绿 · 切 selector · 秒级 · 双倍资源]
    ca[金丝雀 · 改 weight · 5% 已坏归零]
    mi[镜像 · 拷请求丢响应 · 不碰用户]

    classDef a fill:#16A34A,stroke:#14532D,stroke-width:2px,color:#fff
    classDef b fill:#7C3AED,stroke:#4C1D95,stroke-width:2px,color:#fff
    classDef c fill:#D97706,stroke:#92400E,stroke-width:2px,color:#fff
    class bg a
    class ca b
    class mi c
```

蓝绿：两套齐活，schema 必须双版本兼容。金丝雀：小比例或 header；没有指标门禁 = 人工碰运气。滚动默认省资源，回滚是 undo，分钟级，不是秒级切流。

镜像只验证读路径，**不能**代替金丝雀；支付 / 写库存会双写。无状态 RTO **2–5 分钟**写进发布单。有状态定不了就不要高峰发。

### 再追问

Gateway weight 和 14 章？——入口给路由能力，Rollouts 按指标改权重。实现在 22 / 05。

## Q3

**★★★★★｜游戏有状态服为什么不能按 Web 滚动？表已经 migrate 了？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.5


### 场景

战斗 Deployment 按大厅的方式滚动。对局中玩家掉线。另一边道具表已经加了新列并写了数据，代码 undo 回去后读崩。

### 完整解答

**一句话**：战斗服对局在内存，不能当 Web 滚；schema 已 migrate 禁止盲 undo 代码。

对局在内存，滚 = 杀进程。新副本不会接手旧房间。大厅 / 支付 HTTP 可以滚动 / 金丝雀 / 蓝绿；匹配小比例且协议必须兼容；房间 / 战斗：新开空服接新房间，禁止对局中替换；强更是客户端门闸；热更进程不杀，≠ Deployment 滚动。

数据已用新 schema 写过：先停写，评估正向修数据还是用备份。禁止盲 undo 代码。兼容窗口：先加列 → 发代码 → 再删旧列。道具表乱改是回滚死局。

热更过了还要管这次滚动：热更改的是进程内脚本，滚动仍会杀进程。两套通道写在同一张发布单上。

### 再追问

节点升级窗口能和战斗发版同一晚吗？——不要。错开。drain 战斗节点见 16。

## Q4

**★★★★★｜`rollout undo` 够不够？什么时候不够？**

**覆盖**：核心 · 必会 · 常用
**对应**：知识点 §7.2


### 场景

undo 之后大厅还是坏的。CM 里开关是新的，Ingress 还指着 canary，HPA 把副本又打回 3。

### 完整解答

**一句话**：rollout undo 只回 workload revision，不含 CM/Secret/DB/入口权重；historyLimit 生产 ≥5。

undo 只回工作负载 revision。不包含：CM / Secret / CR / DB schema / 客户端版本 / 入口权重。historyLimit=0 时连 revision 都没有。HPA 可能再改 replicas。

清单：应用、配置、数据、入口。env 型配置回 Deploy 还要回 CM（12）。金丝雀要先把 weight 归零。revisionHistoryLimit 生产 ≥5。

### 再追问

镜像影子 Deploy 要 undo 吗？——停 RequestMirror 即可，用户没吃影子响应。

## Q5

**★★★★☆｜回滚看哪些指标？Ready 全绿能不能宣布成功？**

**覆盖**：必会 · 常用 · 常考
**对应**：知识点 §7.2 · §8


### 场景

金丝雀 10%，所有新 Pod Ready。登录成功率已经掉，CCU 开始滑。有人说再观察 10 分钟。

### 完整解答

**一句话**：发布门禁看 5xx/P99/登录/CCU，Ready 全绿不等于业务成功。

看 5xx、P99、登录成功、充值、CCU 突降。不只看 Ready 副本。Ready 是调度和探针，不是业务。

金丝雀 10% 时 Ready 全绿、登录已经掉，该停。开服日 CCU 跌 50% 直接按 P0 切流 / 停匹配。错误率升而 Ready 仍满 → 立刻 undo / 切流。只有新版本 Pending：停滚，修镜像 / 调度。还没切流则业务仍在旧版本，不必回。

### 再追问

三问？——对局进程还在？还能不能变更？登录 / 战斗流量还通？先止血再查新 Pod。

## Q6

**★★★★☆｜Ingress 权重和 Deploy 副本比例哪种金丝雀更准？**

**覆盖**：必会 · 常用
**对应**：知识点 §3.3


### 场景

用 1 个 canary 副本对 9 个稳定副本「当 10%」。长连接玩家几乎没打到 canary，新登录却打得偏。

### 完整解答

**一句话**：入口 weight 比副本比例准；长连接会粘在旧 Pod，1:9 副本不等于 10% 流量。

入口权重准（14 的 HTTPRoute weight / Ingress 注解）。副本比例依赖 kube-proxy 近似均分，1/10 副本 ≈ 10% 但不稳，长连接更偏——旧连接粘在旧 Pod。内部号要用 header / cookie 圈，不要只滚服务端让外网 100% 打新入口。

### 再追问

和流量镜像一起用？——先镜像压读，再小流量金丝雀。写路径不要镜像。

## Q7

**★★★★☆｜开服当天能不能灰度？战斗异常时继续 rollout 吗？**

**覆盖**：必会 · 常用
**对应**：知识点 §7.3


### 场景

开服高峰，现场想推一个「小修复」滚动。匹配开始报错，发布还在 resume。

### 完整解答

**一句话**：开服/大活动默认冻结发版；战斗异常停匹配禁新进，不要继续 rollout。

开服、大活动、合服当晚默认冻结。容量是预案，不是现场 HPA + 新版本。必须热修走审批通道。战斗异常：**停匹配、禁新进**，不要继续 rollout。先止血再谈灰度。

破窗：写进发布单的 hotfix 通道和审批人。没有名单就等于谁都能滚。

### 再追问

和节点升级窗口？——错开。不要同一晚既发战斗服又 drain 战斗节点（16）。

## Q8

**★★★★☆｜发前检查单有哪些？缺一项为什么不要点？**

**覆盖**：必会 · 常用
**对应**：知识点 §7.1


### 场景

镜像用了 latest，没人看 Grafana 哪块板，也不知道 undo 是谁执行。

### 完整解答

**一句话**：发前七项：digest、探针/PDB、HPA、CM/Secret、有状态、回滚人、schema 兼容，缺一项不要点。

1. 镜像 digest（不是 latest）
2. readiness / PDB / grace
3. HPA 会不会把副本打回去
4. CM / Secret 是否同版本
5. 有状态是否停匹配
6. 回滚命令是谁执行、观察哪块板
7. schema 是否双版本兼容

缺一项就不要点。latest 和扫描见 05-03。

### 再追问

PDB 和滚动？——防止一次杀太多。和 maxUnavailable=0 一起看。见 05。

## Q9

**★★★☆☆｜Recreate 适合什么？和滚动怎么选？**

**覆盖**：常用 · 常考
**对应**：知识点 §5


### 场景

协议硬断，新旧不能共存。有人仍用 RollingUpdate，双版本互打把匹配打崩。

### 完整解答

**一句话**：不能双版本共存用 Recreate 接受中断；能共存用滚动/蓝绿/金丝雀。

不能双版本共存（独占 RWO、协议硬断）用 Recreate：先杀光再起，接受中断并公告。能共存用滚动 / 蓝绿 / 金丝雀。战斗协议不兼容时不要「小比例金丝雀互打」。Recreate 的 RTO 等于停服窗口，不是分钟级 undo。写进公告。

### 再追问

独占盘能不能蓝绿？——两套都要盘时往往不能。先迁或接受 Recreate 窗口。

## Q10

**★★★☆☆｜蓝绿切完全挂，selector 怎么回？schema 不兼容为什么蓝绿也救不了？**

**覆盖**：常用 · 常考
**对应**：知识点 §3.2


### 场景

绿已切上，立即 5xx。蓝还在，副本没删。绿已经用新 schema 写了部分订单。

### 完整解答

**一句话**：蓝绿切回 selector 秒级止血；若绿已写新 schema，切回蓝也救不了数据。

流量切回蓝（改 selector / Ingress backend），RTO 秒级。然后查绿的配置。

若绿已经写了新 schema，切回蓝会让旧代码读新数据——蓝绿解决的是进程版本，不是数据兼容。先停写，评估正向修。这就是「双版本兼容」写在蓝绿前提里的原因。

### 再追问

镜像流量写了订单怎么办？——所以写路径禁止镜像。已经双写只能停镜像 + 数据修复，和金丝雀回滚不是同一条。
