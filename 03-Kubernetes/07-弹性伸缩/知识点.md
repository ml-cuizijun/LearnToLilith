# 弹性伸缩

> 大家好。上一章讲完 Pending 怎么定责；这一章讲**副本数怎么自动变**——以及为什么同一套 HPA，挂在大厅是救命，挂在战斗服是事故。
> 开讲之前，先带大家回到两个现场：活动开服，大厅 CPU 90%，HPA 指标栏却是 `<unknown>`——群里有人喊「把 maxReplicas 加大」；另一边战斗服被好心人挂了个 70% CPU 的 HPA，低峰一缩，正在打仗的进程被删，玩家掉线，匹配还在往里塞人。
> 这一章讲完，你会知道这两个人各自错在哪——unknown 为什么加 max 没用，以及战斗服第一刀为什么是删 HPA 而不是等算法自己扩回来。
> **本章回答的问题**：一次扩容决策的一生——指标从哪来、副本怎么算、replicas 怎么被改、Pod 怎么调度就绪——以及这条链在哪一环会卡住、为什么它救不了有状态游戏服。
> **本章不讲**：探针、preStop、grace 时序 → [04](../04-Pod生命周期/)；控制器怎么建删 Pod、PDB 数字 → [05](../05-工作负载控制器/)；Pending 与 Filter/Score、Allocatable → [06](../06-调度机制/)；APIService 与 API Server 内部 → [03](../03-API-Server/)；本地盘跟节点走 → [11](../11-存储/)；声明式与 Git 纪律 → [01](../01-集群架构/)；PromQL 写法 → [09-02](../../09-可观测性与SRE方法论/02-Prometheus与PromQL/)。

**标记**：🎯重点 · 🔥难点 · ⭐常考 · 🔧实操

**怎么听这场分享**：第一节是扩容主图；二到五节顺着采指标 → 算副本 → 防抖 → 落地；第六节专门讲战斗服边界——开篇第二个现场的正解；第七节定责。

## 一、一张图：一次扩容决策的一生

> 🎯 **一句话**：HPA 只干半件事——读指标、算副本、改一个数字；数字变成容量，还要走调度、就绪、接流量三段。

```mermaid
flowchart LR
    A["① 采指标<br/>kubelet → metrics-server<br/>Prometheus → Adapter / KEDA"] --> B["② 算副本<br/>HPA 每 ~15s 一环<br/>ceil(n × current / target)"]
    B --> C["③ 改 replicas<br/>patch 工作负载<br/>夹在 min ~ max"]
    C --> D["④ 调度 + 就绪<br/>控制器建 Pod → 选节点<br/>→ readiness 过"]
    D --> E["⑤ 接流量<br/>进 Endpoints<br/>玩家连得上"]
    C -.->|缩容| F["控制器删 Pod：摘流 → preStop → grace（04）"]
    D -.->|Pending：节点不够| G["Cluster Autoscaler 加节点 · 分钟级"]
```

**读图**：

- 从左往右就是一次扩容的一生：①②是 HPA 自己的地盘，③只写一个字段，④⑤归调度器和就绪探针管——**HPA 不是 Scheduler，也不加节点**。
- 值班定责先问「卡在哪一段」：指标 `<unknown>` 卡在 ①，有指标不扩卡在 ②，扩了但 Pending 卡在 ④，Pod Ready 了没人连卡在 ⑤。
- 两条虚线是反向路径：缩容不是「副本消失」，是先摘流再删进程；节点不够时救场的是 CA，不是再调 HPA。

三个角色从头到尾只有一个分工，全章不再变：

- **HPA**：算副本，patch 工作负载的 `spec.replicas`。
- **工作负载控制器**（Deployment / StatefulSet，[05](../05-工作负载控制器/)）：按 replicas 建 Pod、删 Pod——**真正删进程的是它**。
- **指标供应方**（metrics-server / Prometheus Adapter / KEDA）：把指标登记成 Metrics API，HPA 只消费，不生产。

> 💡 **打个比方**：HPA 像餐厅经理看排队长度决定开几个窗口——他只负责喊「加两个窗口」，服务员入职（调度）、上岗（就绪）归别人管；他不改每个服务员端多少菜（那是 VPA），也不租新店面（那是 CA）。

口诀先记：⭐ **HPA 只改一个数字，不加节点、不起容器**。开篇那位喊加大 max 的——如果卡在指标链，加多少都没用。好，先看指标从哪来。

本节对应练习题 Q1、Q6。

## 二、采指标：Metrics API 三条路

> 🎯 **一句话**：HPA 从不直连 kubelet 和 Prometheus，只读三条 Metrics API——谁把指标登记进来，HPA 才消费谁。

开篇大厅 unknown——大家想想：加大 maxReplicas 会让指标突然出现吗？不会。先顺着三条路找断点。

**HPA（Horizontal Pod Autoscaler，水平 Pod 自动伸缩器）** 是 kube-controller-manager 里的一个控制器，每 ~15s 一轮去读指标。指标从哪来，取决于谁向 API Server 注册了对应的 **APIService**（把一组聚合接口挂进 API 的机制，[03](../03-API-Server/)）。三条路：

- **资源指标（Resource）**，API 组 `metrics.k8s.io`：每个 Pod 的 CPU / 内存用量。链路是 kubelet 在每节点采集容器用量 → **metrics-server（集群级聚合组件，把全节点汇总成 Metrics API，`kubectl top` 的数据源）** → HPA。这是「按 CPU 利用率扩」的全部来源。
- **自定义指标（custom metrics）**，API 组 `custom.metrics.k8s.io`：集群内、能挂到 Pod 上的业务指标——每 Pod 的 QPS、连接数、房间数。典型链路：Prometheus 采集 → **Prometheus Adapter（把 PromQL 查询结果翻译成 Metrics API 的组件）** 登记。
- **外部指标（external metrics）**，API 组 `external.metrics.k8s.io`：不挂在某个 Pod 上、甚至在集群外——Kafka lag、云队列深度、大厅排队人数。通常由 KEDA 或 Adapter 提供。

```mermaid
flowchart LR
    kl[kubelet :10250] --> ms[metrics-server]
    prom[Prometheus] --> adp[Prometheus Adapter]
    src[Kafka lag · 云队列 · cron] --> keda[KEDA]
    ms --> res["metrics.k8s.io<br/>Resource：CPU / 内存"]
    adp --> cus["custom.metrics.k8s.io<br/>Pods / Object：QPS · 连接数"]
    keda --> ext["external.metrics.k8s.io<br/>External：队列深度 · 排队人数"]
    res --> hpa[HPA 控制器]
    cus --> hpa
    ext --> hpa
    keda -.->|创建并管理一条 HPA| hpa
```

**读图**：左边是三类数据源，中间是三条 API，右边只有一个消费者。任何一条没登记好，HPA 那头就是 `<unknown>`——所以 unknown 永远先查中间这层，不是去改 HPA 的 max。

**为什么游戏服常要自定义/外部指标**：网关是长连接，CPU 20% 时连接可能已经打满——只盯 CPU 会「该扩不扩、该缩乱缩」。大厅更贴的信号是排队人数、登录 QPS；匹配/回放 worker 更贴的是队列深度。

**KEDA（Kubernetes Event-Driven Autoscaling）** 值得在这里先认一眼：它不是另一个伸缩器，而是「指标搬运工 + HPA 管理员」。你写一个 **ScaledObject（KEDA 的 CRD：声明盯哪个事件源、目标值多少）**，KEDA 的 scaler 把事件源读数变成 external metrics，再**创建并管理一条真正的 HPA**——公式不变，只是 current 换了来源。它还支持 **scale to 0**（HPA 的 minReplicas 不能写 0，KEDA 靠自己的逻辑把副本收到 0，来事件再拉起），空闲队列消费者、回放任务用它省资源。**但 scale to 0 也是删 Pod**——有对局的战斗服照样不能碰（六节）。

> ⚠️ **别混**：**metrics-server 挂了 ≠ API Server 挂了**。metrics-server 只影响 `kubectl top` 和资源类 HPA，业务对象的读写（建 Pod、改 Service）一切正常，别上报成「控制面挂了」（[03](../03-API-Server/)）。反过来，`top` 正常也不代表 custom/external 能读——那是 Adapter 和 KEDA 的事。

> 🔍 **现场**：HPA 显示 unknown，值班三连先确认指标链路哪段断了。

```bash
kubectl top pods -n hall
# error: Metrics API not available        # ← 连 top 都失败：资源指标整条链路断

kubectl get apiservice v1beta1.metrics.k8s.io
# NAME                     SERVICE                       AVAILABLE
# v1beta1.metrics.k8s.io   kube-system/metrics-server    False   # ← False = metrics-server 没接上

kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1" | head
# 404 / 空列表 = Adapter 没登记或 PromQL 对不上    # ← 自定义指标查这条

kubectl get apiservice | grep metrics
# v1beta1.metrics.k8s.io           kube-system/metrics-server                  True   # ← 资源
# v1beta1.custom.metrics.k8s.io    monitoring/custom-metrics-adapter           True   # ← 自定义
# v1beta1.external.metrics.k8s.io  keda/keda-operator-metrics-apiserver        True   # ← 外部
# 三条 Available 一目了然，比逐条查快
```

**追问预备：为什么不让 HPA 直读 Prometheus？** Metrics API 是聚合层解耦：HPA 一个消费者对接任意多家供应方，权限走 APIService 背后的 RBAC，HPA 不用拿 Prometheus 的地址和凭据；哪天换了监控栈，也不用动 HPA。

**安装与验收**（自建集群常缺，托管 ACK / EKS 通常自带但仍要验收）：

- metrics-server：验收标准是 **APIService Available=True 且 `top` 出数**，进程在跑不算数。它自身要多副本——单副本挂了，所有资源 HPA 同时瞎。别部署到业务 Worker 上抢资源。自建集群常见坑是 kubelet **10250** 端口证书没配对，metrics-server 拉不到数据——修证书，不是重启 API。
- Prometheus Adapter：装完验「HPA 能读到 custom.metrics」；**PromQL 写错或指标名对不上，表现也是 unknown**——那是查询问题，不是公式坏了。别用高基数指标（每玩家一条线）去打爆 Metrics API（[03](../03-API-Server/)）。
- KEDA：验收 `kubectl get scaledobject` Ready=True，且底下能 `get hpa` 看到它建的 HPA。
- CA / Karpenter：等真有了「扩了会 Pending」的节点组才装；验收不看进程，看「造一个超配请求，能不能等到新节点」，并确认节点组最大实例数留了余量、云账号有开机器权限。

> 📝 **面试**：问「HPA 指标从哪来」，答三条 API：资源走 `metrics.k8s.io`（metrics-server ← kubelet），自定义走 `custom.metrics.k8s.io`（Prometheus Adapter），外部走 `external.metrics.k8s.io`（KEDA / Adapter）；HPA 只消费不采集，哪条断了都是 `<unknown>`。

指标读到了，下一站：怎么算出该要几个副本。

本节对应练习题 Q2、Q3。

## 三、算副本：HPA 公式与多指标

> 🎯 **一句话**：期望副本 = ceil(当前副本 × 当前指标 / 目标指标)；多指标各算一遍取 max，利用率的分母是 request。

大家先别背五种 metric——先问一句：多指标是取平均还是取 max？很多人答平均——⭐ 这是高频错答，听更忙的那个。

HPA 的核心就一个公式，白板必考 ⭐：

```text
期望副本 = ceil( 当前副本 × 当前指标值 / 目标指标值 )

例：3 副本，CPU 平均利用率 90%，目标 60%
    ceil( 3 × 90 / 60 ) = ceil(4.5) = 5      # ← 下一环 HPA 把 replicas patch 到 5
```

**多指标**：配了 CPU 60% 又配了每 Pod QPS 1000，就各算一遍——CPU 说 5 个、QPS 说 7 个，**取 max 听更忙的那个**，不是取平均（取平均得 6，紧张的那条信号被稀释，该扩不扩）。

**autoscaling/v2 的五种 metric 类型**（⭐ 面试常列）：

- **Resource / ContainerResource**：CPU、内存。前者按 Pod 整体，后者指定 Pod 里某个容器；目标写法是**利用率** `target.averageUtilization`（旧文档常写作 targetAverageUtilization，分母是 request）。v1 时代这个字段叫 `targetCPUUtilizationPercentage`，v1 的 Pods 型叫 `targetAverageValue`——字段名换了两代，机制没变。
- **Pods**：全体 Pod 上某个自定义指标的**平均值**，如每 Pod QPS；目标是 `averageValue`，不是百分比。
- **Object**：某个集群对象上的指标，如某 Ingress 的每秒请求数。
- **External**：集群外信号，如队列深度——KEDA 走的就是这条。

```yaml
- type: External                          # ← 外部指标：回放队列深度
  external:
    metric: {name: replay_queue_depth}
    target: {type: AverageValue, averageValue: "500"}   # ← 每副本分摊 500 条
```

```yaml
- type: Pods                              # ← 自定义指标：每 Pod QPS
  pods:
    metric: {name: http_qps}
    target: {type: AverageValue, averageValue: "1000"}
```

describe 里两类目标的长相也不同：

```text
resource cpu on pods  (as a percentage of request):  90% / 60%   # ← 利用率：带百分号
"http_qps" on pods:                                1464 / 1k      # ← 平均值：裸数
```

> 💡 **打个比方**：利用率的分母是 request，像「实际用电 ÷ 报装容量」。报装容量写 1 度（request=1m），实际用 100 度，表上显示 10000%——HPA 以为要扩到天上去。所以 request 必须接近真实用量：写 1m 既骗调度器（超卖爆节点），又让 HPA 乱跳。🔥

大家想想：为什么没写 requests 会 unknown，而不是按 0 算？因为利用率公式里分母不能是 0——HPA 直接认怂报 unknown。

**分母是 request，不是 limit，更不是实际用量**：没写 `resources.requests`，利用率算不出来，HPA 直接 `<unknown>`——这是最高频的 unknown 根因。

**容差与节奏**：

- **容差（tolerance）约 ±10%**：current 落在 target ±10% 内就不动（63% vs 60% → 比例 1.05，不扩），防止指标毛刺引发来回扩缩。
- **同步周期约 15s**：HPA 每 ~15s 读一次指标、算一次——所以「流量瞬间打满」它必然慢一拍（四节）。

> 🔍 **现场**：`describe hpa` 是这一环的 X 光，公式、指标、三个 Conditions 都在里面。⭐

```bash
kubectl describe hpa hall-hpa -n hall
```

```text
Metrics:                                               ( current / target )
  resource cpu on pods  (as a percentage of request):  90% / 60%   # ← 当前值 / 目标值
Min replicas:                                          3
Max replicas:                                          40
Deployment pods:       3 current / 5 desired           # ← 公式算出 5，正在等控制器建
Conditions:
  AbleToScale     True    ReadyForNewScale             # ← 能算、能 patch
  ScalingActive   True    ValidMetricFound             # ← 指标读得到；False = unknown
  ScalingLimited  False   DesiredWithinRange           # ← True = 撞上 min 或 max
Events:
  Normal  SuccessfulRescale  horizontal-pod-autoscaler  New size: 5; reason: cpu resource utilization above target
```

**三个 Conditions 各管一段**：AbleToScale 管「算得出、改得动」（目标工作负载不存在会 False）；ScalingActive 管「指标读得到」（False 就是 unknown，回二节查链路）；ScalingLimited 管「到没到 min/max」（True 且 Pod 还在 Pending = 节点不够，去五节）。

> ⚠️ **别混**：「不扩」有两种，对策完全不同——**unknown**（ScalingActive=False）是指标链路断了，修 metrics-server / requests / Adapter，加大 max 没用；**没超目标**（指标健康、比例在容差内）是 target 定太松，调 target。

target 怎么定：资源类常见 **60～70%**，留突发余量；定太紧（50% 以下）副本会狂抖（四节）。网关、长连接服务**别只用 CPU**——换连接数 / QPS / 排队（二节）。

> 📝 **面试**：「HPA 公式是 `ceil(n × current / target)`，多指标各算一遍取 max 不是平均；利用率分母是 request，没写 requests 就 unknown；容差约 10%，同步约 15s。」

口诀：⭐ **多指标取 max；利用率分母是 request；unknown 别加 max**。算出数字还不够——扩缩得有节奏，不然副本会狂抖。

本节对应练习题 Q1、Q3。

## 四、防抖：behavior、冷却与扩快缩慢

> 🎯 **一句话**：扩快缩慢——扩容等不起，缩容要等摘流、等下一波可能回来的流量。

指标在目标附近天然抖动，容差（三节）只能吸收小毛刺；更大的防抖靠 **behavior（autoscaling/v2 里控制扩缩速率的字段）**。先看生产配置 ⭐：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hall-hpa
  namespace: hall
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hall
  minReplicas: 4
  maxReplicas: 40
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60        # ← v1 时代叫 targetCPUUtilizationPercentage
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0   # ← 扩：不等，立刻生效
      policies:
      - type: Percent
        value: 100                     # ← 每 60s 最多翻倍
        periodSeconds: 60
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300 # ← 缩：回看 300s 的推荐，取最大那个
      policies:
      - type: Percent
        value: 10                      # ← 每 60s 最多缩 10%
        periodSeconds: 60
```

**读法**：`policies` 限制每一小段（periodSeconds）里最多变多少——`Percent` 是比例、`Pods` 是绝对个数，`selectPolicy: Max` 取两者放宽的那个；`stabilizationWindowSeconds` 是稳定窗口。

**不写 behavior 时的官方默认**（不是「无约束」）：

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - {type: Percent, value: 100, periodSeconds: 60}   # ← 每分钟可翻倍
    - {type: Pods, value: 4, periodSeconds: 60}        # ← 或加 4 个
    selectPolicy: Max                                   # ← 两者取放宽的
  scaleDown:
    stabilizationWindowSeconds: 300                     # ← 缩容默认就有 300s 窗口
    policies:
    - {type: Percent, value: 100, periodSeconds: 60}   # ← 本身不限速，靠窗口防抖
```

也就是说「没配 behavior 的 HPA」缩容依然带回看窗口；很多狂抖恰恰来自手写 behavior 时把窗口改得比默认还短、把 policy 放得比默认还宽。官方默认值：scaleUp 窗口 0、每 60s 可翻倍或 +4 个 Pod（取大）；scaleDown 窗口 **300s**。

**min / max 怎么定**：min 是「最坏情况下的保底容量」——无状态 ≥2，活动期按预案提（下一小节）；max 不是「写着好看」的 1000，要对着节点池能供给的上限定，否则顶到 max 时全是 Pending，监控上看还像「扩容成功」。定完用一次真实压测把链条走通：指标涨 → 扩到 max → 节点跟得上。

> 💡 **打个比方**：稳定窗口不是「缩容前干等 300 秒」，是「**回头看最近 300 秒里所有推荐，取最高的那个执行**」。流量掉下去又弹回来，窗口内曾有过「要 20 个」的推荐，它就绝不缩到 20 以下——像电梯关门前的防夹：不是不让关，是有人刚伸手就不关。🔥

很多人会答「等 300 秒再缩」——⭐ 错了，是回看取最大，不是干等。

| 对比 | **scaleUp** | **scaleDown** |
|------|-------------|---------------|
| 窗口 | 0，要扩立刻扩 | ≥300s，回看取最大推荐 |
| 节奏 | 允许短时翻倍 | 每分钟最多缩一小截（如 10%） |
| 改错会怎样 | 进服瞬间来不及 | 快缩 → 摘流不干净 → 502（[04](../04-Pod生命周期/)、[08](../08-Service与kube-proxy/)） |

缩容慢不只为省钱，是给**摘流**留时间：HPA 减副本 → 控制器删 Pod → readiness 先把 Pod 摘出 Endpoints、IPVS/iptables 规则更新、preStop、SIGTERM、grace（[04](../04-Pod生命周期/)）。窗口太短，流量还打在旧 Pod 上就 502。

**抖动（oscillation）怎么治**：副本在两个值之间来回跳，先找三处——① target 定太紧，提高；② scaleDown 窗口太短，拉长；③ Adapter 的 PromQL 只算瞬时值，改用 `rate` 算 1～2 分钟均值。三招都是「让信号更钝感」，**不要**靠频繁手动 scale 去压。冷却（cooldown）在 CA 侧也有同款：加完节点后一段时间内不许缩（五节）。

### 开服不能等 15 秒环 🔧⭐

活动开服是阶跃流量：一分钟几万人进服，HPA 要「指标涨 → 15s 算一环 → 建 Pod → 拉镜像 → 调度 → 就绪」，分钟级才补齐，**一定迟到**。预案是提前把 min 拉到峰值的 **1.2～1.5 倍**：

```bash
kubectl patch hpa hall-hpa -n hall -p '{"spec":{"minReplicas":24}}'
kubectl get hpa hall-hpa -n hall
# NAME       REFERENCE         TARGETS     MINPODS   MAXPODS   REPLICAS   AGE
# hall-hpa   Deployment/hall   22%/60%     24        40        24         30d  # ← REPLICAS 已顶到 min
```

配套四件事：**镜像预热**（新节点提前拉好）、**确认节点够**（不够先开 CA，五节）、**min ≥ PDB minAvailable**（否则 drain 永远赶不走，[05](../05-工作负载控制器/)）、**活动后把 min 降回去**（不然长期烧钱）。另有一条底线：无状态服务 **min ≥ 2**——min=1 还开自动缩，一次抖动就是单副本裸奔。

> 📝 **面试**：「扩快缩慢：scaleUp 窗口 0，scaleDown 默认 300s 回看取最大，一是防流量回弹雪崩、二是给摘流留时间。开服不靠 15s 环，预案把 min 提到峰值 1.2–1.5 倍，配镜像预热和节点预留。」

口诀：⭐ **扩快缩慢；开服靠提 min，不靠 15s 环**。数字写进 replicas 之后，容量还要过三关。

本节对应练习题 Q4、Q5。

## 五、落地：改 replicas、调度、就绪与节点层

> 🎯 **一句话**：HPA 只写一个数字，数字变成容量要过控制器、调度器、就绪探针三关；节点不够时轮到 CA。

大家想想：HPA 显示已到 max、新 Pod 全 Pending——再加大 max 有用吗？听完这一节你就知道该叫 CA，不该加 max。

### patch 之后发生什么

HPA patch 了 `spec.replicas`，后面的路它一步都管不了：工作负载控制器看到期望与现状的差 → 建/删 Pod（[05](../05-工作负载控制器/)）→ 调度器为新 Pod 选节点（[06](../06-调度机制/)）→ kubelet 拉镜像、起容器 → **readiness 过了才进 Endpoints**，Service 才开始往它转流量（[08](../08-Service与kube-proxy/)）。缩容反着走：控制器删 Pod，仍要摘流、preStop、grace（[04](../04-Pod生命周期/)）。

> ⚠️ **别混**：**PDB（PodDisruptionBudget）拦的是 drain / 节点驱逐这类「自愿中断」，拦不住 HPA 改 replicas**——HPA 直接改期望值，控制器删 Pod 不走 PDB 这条路。想保护战斗服别指望 PDB，答案是不挂自动缩（六节）。⭐ 口诀：**PDB 拦 drain，不拦 HPA**。

### 谁还在写 replicas：Git 会抢 ⭐

`spec.replicas` 是个多方都想写的字段。活动期 HPA 把 hall 扩到 20，Git 里 YAML 还写着 `replicas: 3`——一次无关的配置发布 `kubectl apply`，声明式对齐把容量当场打回 3，玩家堵登录：

```bash
kubectl get deploy hall -n hall -o jsonpath='{.spec.replicas}{"\n"}'
# 20                      # ← HPA 扩的
kubectl apply -f hall-deploy.yaml      # YAML 里 replicas: 3
kubectl get deploy hall -n hall -o jsonpath='{.spec.replicas}{"\n"}'
# 3                       # ← 被 apply 打回去了
```

修法三条：YAML 干脆**不写 replicas**（apply 不碰这个字段）；或用 server-side apply 让 HPA 当该字段的 FieldManager；GitOps 场景给 ArgoCD 配 `ignoreDifferences` 忽略 replicas（[23](../23-GitOps-ArgoCD与Tekton/)）。应急 `kubectl scale` 可以，但**当天补 Git**，否则下次同步把热修覆盖掉（[01](../01-集群架构/)）。

### 扩到 max 仍 Pending：轮到节点层 🔍

> 🔍 **现场**：HPA 显示已到 max，新 Pod 却全 Pending——先确认这不是「再加 max」能救的。

```bash
kubectl describe hpa hall-hpa -n hall | grep -i limited
# ScalingLimited  True  ...  the desired replica count is more than the maximum replica count
kubectl get po -n hall | grep Pending
kubectl describe po hall-xxx -n hall | grep -A3 Events
# Warning  FailedScheduling  0/12 nodes are available: 12 Insufficient cpu.  # ← 节点 Allocatable 不够
```

结论：**要的是更多节点，不是更大的 max**。再调 maxReplicas 只会多造 Pending。这时候出手的是 **Cluster Autoscaler（CA，集群自动伸缩器）**。

**CA 怎么工作**：盯着不可调度的 Pod（FailedScheduling）→ 模拟「把它塞进哪个节点组能行」→ 调云厂商 API 扩节点组（AWS ASG / 阿里云 ESS 伸缩组）→ 新节点启动、注册、可调度，整条链路**分钟级**。反方向：CA 每 ~10s 扫一轮，利用率低于阈值（默认 50%）且「没人需要」**持续 10 分钟**的节点，先排空（尊重 PDB）再删；加完节点后还有 ~10 分钟冷却不许缩——和 HPA 的防抖一个思路，只是慢一个量级。

**分钟级花在哪**（追问常考）🔥：新机器开机 → kubelet 注册进集群 → Pod 调度上去 → 首次拉镜像。前三步是固定开销，最后一步可以用镜像预热和「缓存盘」压一压。选节点组的逻辑是**模拟调度**：拿 Pending Pod 的约束（资源量、亲和、污点容忍）对每个节点组的模板试一遍，放得下的候选里再按均衡策略挑——所以节点组模板配错（比如规格太小），CA 会「看着着急但就是不动」。缩容排空同样有保护：尊重 PDB、尊重带本地盘的 Pod、尊重 `cluster-autoscaler.kubernetes.io/safe-to-evict=false` 注解——这也是「有的节点明明空了很久却不被删」的常见原因。

```mermaid
flowchart LR
    A[HPA 顶 max] --> B[新 Pod Pending]
    B --> C{"CA 每 ~10s 扫：有没有不可调度 Pod"}
    C -->|模拟调度：某节点组放得下| D[调云 API 扩节点组]
    D --> E[新节点 Ready · 分钟级]
    E --> F[Pod 调度成功 → 就绪 → 接流量]
    C -->|污点 / 亲和 / 配额都放不下| G[扩节点也没用：先修约束 → 06]
```

**读图**：入口永远是「有 Pending 且是资源不够」。右路提醒：如果模拟调度也过不去（硬反亲和、污点没人容忍、PVC 绑不上），CA 加了机器也是白加——先回 [06](../06-调度机制/) 看 Events。**有状态 + 本地盘**的更直接：新节点来了旧盘也挂不过去，CA 解决不了（[11](../11-存储/)）。

**Karpenter**：AWS 原生的节点层方案，不走固定节点组，按 Pod 的需求直接开机器，比 CA 更快更灵活；阿里云环境主流仍是 CA。面试知道分工即可。

### VPA：改规格的那一位

**VPA（Vertical Pod Autoscaler，垂直 Pod 自动伸缩器）** 不改数量，改单个 Pod 的 **requests/limits**：Recommender 算推荐值，Updater 重建 Pod 应用，Admission Controller 在创建时注入。三个模式按介入程度排：**Off** 只出推荐不改东西；**Initial** 只在 Pod 创建时注入推荐，之后不动；**Auto** 由 Updater 重建存量 Pod 应用新值——重建有重启代价，要配 PDB 控节奏。

```bash
kubectl describe vpa hall-vpa -n hall | grep -A6 Recommendation
# Recommendation:
#     Container Name: hall
#     Target:    587m (cpu) / 1171Mi (mem)    # ← 推荐值：拿来人工调 request
#     Lower Bound: 300m / 600Mi                # ← 低于这个会缺资源
#     Upper Bound: 1200m / 2400Mi              # ← 高于这个纯浪费
```

> ⚠️ **别混**：**VPA 和 HPA 同时盯 CPU 会打架**——VPA 把 request 调大 → 利用率分母变大 → HPA 觉得不忙要缩 → 缩完更挤 → 两者对着振荡。生产主流是 **HPA + 人手调 request**；VPA 开 **Off** 模式只出推荐，当调 request 的参考，不当场动手。VPA 唯一能安全配 HPA 的情形是 HPA 用自定义指标、VPA 管 CPU——别在同一个信号上闭环。

### 收束：弹性四件套，各改什么

> 🎯 一句话收拢：HPA 改副本、VPA 改规格、CA 改节点、KEDA 喂指标——公式从头到尾没变过。

```mermaid
flowchart TB
    R["弹性的四个抓手"] --> H["HPA · 改 replicas<br/>无状态大厅 / 网关 / HTTP 商城"]
    R --> V["VPA · 改 requests/limits<br/>Off 出推荐，别和 HPA 同盯 CPU"]
    R --> C["CA · 改 Node<br/>Pending 触发，分钟级"]
    R --> K["KEDA · 喂 external metrics<br/>ScaledObject 创建 HPA，可 scale to 0"]
```

**读图**：四个抓手各管一层，从上到下是「副本 → 规格 → 节点 → 信号源」。只有 KEDA 不亲自伸缩——它换的是 HPA 公式里 current 的来源。值班问「该动哪个」，先看卡在哪层：指标不对动信号源（二节），副本数不对动 HPA，Pod Pending 动节点层。

> ⚠️ **别混**：**弹性不保证容量**——扩出副本 ≠ 有人连（匹配不调度、连接不迁移，新 Pod 就是空壳，六节）；加了节点 ≠ 能调度（污点/亲和/盘，见上面读图）。「数字变大了」和「容量变大了」是两件事。

> 📝 **面试**：四件套按「改什么」分组背：HPA 改副本、VPA 改规格、CA 改节点、KEDA 只喂指标不换公式；再补两句边界——同时盯一个信号会打架（VPA vs HPA），数字变大不等于容量变大。

口诀：⭐ **HPA 改副本、VPA 改规格、CA 改节点、KEDA 喂指标**。无状态讲完了——开篇第二个现场：战斗服为什么绝对不能挂 CPU 自动缩。

本节对应练习题 Q6、Q7、Q8、Q11。

## 六、边界：为什么弹性救不了有状态游戏服

> 🎯 **一句话**：HPA 的全部前提是「副本可互换、杀谁都行、状态在外面」——战斗服一条都不满足。⭐

开篇那位好心人给战斗服挂了 70% CPU HPA——咱们带着问题听：低峰 CPU 低，算法会怎么做？会缩。缩的是什么？正在打仗的进程。

> 💡 **打个比方**：大厅像连锁快餐——关一家店客人去隔壁就行；战斗服像单机棋牌桌——玩家都坐在桌上，HPA 按「哪家店人少」随机关店，等于连桌子一起掀了。

HPA 眼里的世界只有三件事：指标、数字、副本可互换。它**看不见**哪个 Pod 里有对局、哪条连接属于谁。三个假设拆开看：

| 对比 | HPA 的假设 | 战斗 / 房间服的现实 |
|------|-----------|---------------------|
| 状态在哪 | 在外面（DB / 缓存），副本无状态 | **状态在内存**：对局、房间、玩家快照都在进程里 |
| 杀谁 | 杀谁都一样，随机选 | 随机杀 = **踢掉正在打的玩家**，新进程接不回旧会话 |
| 扩容效果 | 新副本立刻分担负载 | 新副本不会自动分走已有房间；连接不迁过来，**扩了也是空壳** |

三条现实对应三个词：

- **状态在内存**：缩容 = 控制器删 Pod，Pod 里的对局跟着没——没有「先把这桌打完」的机制，K8s 不知道、也不关心哪个 Pod 有对局。
- **连接迁移**：玩家的长连接挂在具体进程上。扩出的新副本接不到旧连接；缩掉旧副本，连接只能断——「平滑迁移」要靠业务自己做（断线重连 + 会话恢复），不是 HPA 的能力。
- **扩容 ≠ 容量**：新 Pod 起来是空的——匹配服不往里派房间、接入层不往它分连接，它就一个玩家都没有。扩出来没人连，容量并没有涨；反过来缩容也一样，得先让实例自然打空。

**所以**：大厅、网关、HTTP 商城这类无状态服务，HPA 完全合理（配慢缩 + PDB）；战斗 / 房间 / 有对局的逻辑服，**不要挂自动缩的 HPA**。被缩光的止血动作见七节；长期方案是业务层的：扩容按 CCU 预案在活动前手动加实例（[07-03](../../07-游戏运维专题/03-活动高峰与压测/)），缩容只缩 **CCU=0 的空实例**（业务自己判空，不是看 CPU），或先把对局状态外置（落 Redis/DB + 断线重连），再谈水平弹性。**KEDA 的 scale to 0 救不了这个**——它收的也是 Pod，只是收得更狠。

**追问：非要给战斗服挂弹性呢？** 信号换成业务量（CCU / 房间数，自定义指标），且**只敢扩、缩必须过业务闸门**：业务侧确认某实例 CCU=0、标记「可回收」，HPA 才允许把它缩掉——相当于把「杀谁」的决定权从 K8s 手里拿回业务手里。即便如此，缩掉的也只是确认空掉的壳，不是「按利用率缩」。

> 🔍 **现场**：告警「战斗 shard 副本从 8 掉到 2」，先确认是谁干的。

```bash
kubectl get hpa -n game
kubectl describe hpa battle-hpa -n game | tail -5
# Normal  SuccessfulRescale  ...  New size: 2; reason: cpu resource utilization below target
# ← 是 HPA 按 CPU 缩的：低峰没打架，CPU 当然低
```

止血顺序（展开在七节 60 秒剧本）：**立刻把 min 拉回预案值或直接删掉这个 HPA** → 停匹配，别让新人进正在沉的船 → 当故障广播 → 保住还活着的进程，**不要重启它们**。事后复盘：战斗服去掉自动缩。

> 📝 **面试**：「战斗服不能挂 CPU HPA 自动缩：状态在内存、连接不迁移、扩容不等于容量，缩容随机杀 Pod 等于踢人。PDB 也挡不住 HPA。被缩光第一刀是拉 min 或删 HPA，不是等算法自己扩回来。」

口诀：⭐ **战斗服不挂自动缩；被缩光先删 HPA / 拉 min，不停匹配**。边界清楚了，收作战定责。

本节对应练习题 Q9、Q10、Q12。

## 七、作战：定责

> 🎯 **一句话**：先问三句——指标读到了吗？算对了吗？落地那几关（调度 / 节点 / 流量）过了吗？

对应主图五段：`<unknown>` 是 ①，不扩/乱扩是 ②④（公式、behavior、min/max），Pending 是 ④，没人连是 ⑤。

```mermaid
flowchart TB
    A["症状：弹性不对"] --> B{"kubectl get hpa：指标列"}
    B -->|"<unknown>"| U{"kubectl top 有没有数"}
    U -->|top 失败 / APIService False| U1["修 metrics-server / kubelet 10250 证书"]
    U -->|top 有数| U2["补 requests（分母）"]
    U -->|自定义 / 外部| U3["查 Adapter PromQL / KEDA ScaledObject"]
    B -->|有值但不扩| C{"describe hpa Conditions"}
    C -->|没超目标 ± 容差| C1["target 太松，调 target"]
    C -->|ScalingLimited| C2{"有 Pod Pending?"}
    C2 -->|是| C3["节点不够：CA / 加节点，别加 max"]
    C2 -->|否| C4["已到 max 且够用：容量规划问题"]
    C -->|指标在抖| C5["防抖：提 target / 拉长 scaleDown 窗口"]
    B -->|扩了但没用| D{"新 Pod 有流量吗"}
    D -->|Ready 但没人连| D1["匹配 / 接入层没调度新实例"]
    D -->|没 Ready| D2["探针 / 镜像拉不下来 → 04"]
    B -->|战斗服副本掉| E["P0：拉 min 或删 HPA，停匹配"]
    B -->|扩完被打回 3| F["Git 抢 replicas：停 apply → 05 节"]
```

**读图**：第一刀永远看 `get hpa` 的指标列——`<unknown>` 往指标链路查（左树），有值不扩往公式和边界查（中树），「扩了没用」往业务调度查（右树）。战斗服副本掉和打回 3 是两条独立的急症，不进常规分支。

### 现象 · 先做 · 别做

| 现象 | 先做 | 别做 |
|------|------|------|
| 指标 `<unknown>` | top / APIService / requests 三连 | 先加大 max |
| 有指标但不扩 | Conditions：target / Limited / 窗口 | 先重启 API Server |
| 副本狂抖 | 提 target、拉长 scaleDown 窗口、查 VPA | 再开一个 VPA Auto 一起盯 CPU |
| 顶 max 仍 Pending | CA / 加节点 / 查污点亲和 | 继续调大 max |
| 扩完又缩回 3 | 停 apply；YAML 别写死 replicas | 以为 PDB 能挡 apply |
| 战斗服被缩光 | **拉 min 或删 HPA**，停匹配，保活进程 | 等 15s 环；重启还活着的 |
| 新 Pod 没人连 | 查匹配 / 接入层是否调度新实例 | 继续加副本 |
| 网关 CPU 低但不扩 | 换连接数 / QPS / 排队指标 | 继续降 CPU target |

**告警分级参考**：战斗服副本非预期下降 = **P0**（玩家在掉）；`<unknown>` 和 ScalingLimited+Pending = P1（弹性已失效）；副本狂抖 = P2（烧钱但没死人）。

### 60 秒剧本 🔧

> 🔍 **现场**：接到「弹性不对」报障，60 秒走完这条线再动手。

```text
① 0–10s   kubectl get hpa -n {ns}                # 指标列：<unknown>？CURRENT/DESIRED 差多少？
② 10–30s  kubectl describe hpa {name} -n {ns}    # Conditions 三个 + Events 最后一句原因
③ 30–45s  分叉：unknown → top + apiservice + requests；不扩 → target/Limited/窗口；
          Pending → kubectl describe po 看 FailedScheduling 原因
④ 45–60s  定第一刀：修 metrics-server / 补 requests / 调 target / 开 CA；
          战斗服被缩 → 立刻 patch min 或 delete hpa，同时停匹配
```

现在再看开篇两个人——加大 max 救 unknown、给战斗服挂 CPU HPA——你知道该怎么拦住他们了。收口。

### 命令速查 🔧

```bash
kubectl describe hpa {name} -n {ns}                       # 公式输入、Conditions、Events

kubectl top pods -n {ns}                                  # 没数 = 资源 HPA 算不了
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1"   # 自定义指标登记了没
kubectl get scaledobject -A                               # KEDA：Ready？trigger 对不对
kubectl get deploy <n> -n {ns} -o jsonpath='{.spec.replicas}{"\n"}'  # 看 replicas 被谁写了
kubectl get deploy <n> -n {ns} -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"\n"}{end}'  # replicas 之争：谁最后写的
kubectl patch hpa {name} -n {ns} -p '{"spec":{"minReplicas":N}}'     # 开服提 min / 止血
kubectl scale deploy/<n> --replicas=N -n {ns}             # 应急扩；当天补 Git
kubectl logs -n kube-system deploy/cluster-autoscaler | tail          # CA 有没有动作
kubectl describe vpa {name} -n {ns} | grep -A6 Recommendation         # VPA Off 的推荐：调 request 的参考
```

### 面试锚点

遮住右列自问自答，卡壳的行回去重读对应小节——能讲出来才算会，看着答案点头不算。

| 问 | 30 秒答 |
|----|---------|
| HPA 怎么算副本？ | `期望 = ceil(当前副本 × 当前指标 / 目标)`；多指标各算取 max；夹在 min~max；容差 ±10%，~15s 一环。 |
| 五种 metric 类型？ | Resource/ContainerResource 看利用率（分母 request），Pods/Object/External 看平均值（AverageValue）；字段写法不同。 |
| 为什么必须有 requests？ | 利用率分母是 request；没写就 unknown；写 1m 会显示上万百分比乱扩。 |
| 指标从哪来？ | 三条 Metrics API：资源（metrics-server←kubelet）、自定义（Prometheus Adapter）、外部（KEDA/Adapter）；HPA 只消费。 |
| unknown 怎么查？ | 先看是资源还是自定义：`top` + APIService 查 metrics-server，requests 查分母，Adapter 查 PromQL；不是加 max。 |
| behavior 怎么配？ | 扩快缩慢：scaleUp 窗口 0、允许翻倍；scaleDown 默认 300s 回看取最大 + 每分钟限速。 |
| 稳定窗口是什么语义？ | 不是延迟执行，是回看窗口内所有推荐取最高——防流量回弹被缩没。 |
| 开服怎么扩？ | 预案把 min 提到峰值 1.2–1.5 倍 + 镜像预热 + 节点预留；不靠 15s 环在进服瞬间猜。 |
| HPA / VPA / CA / KEDA 差在哪？ | 副本 / 规格 / 节点 / 信号源；KEDA 不换公式；VPA 和 HPA 别同盯 CPU。 |
| 扩到 max 仍 Pending？ | 节点 Allocatable 不够，上 CA 或加节点；加 max 只多造 Pending。 |
| CA 怎么工作？ | 扫不可调度 Pod → 模拟调度 → 扩节点组，分钟级；缩看 10 分钟无人用 + 冷却。 |
| VPA 模式怎么选？ | Off 只出推荐、Auto 重建应用；别和 HPA 同盯 CPU；生产先 Off 跑两周看推荐。 |
| KEDA 是什么？ | 事件源 → external metrics → 创建并管理 HPA；可 scale to 0；公式不变。 |
| 战斗服能自动缩吗？ | 不能：状态在内存、连接不迁移、扩容≠容量；缩容随机杀 Pod = 踢人。 |
| PDB 能挡 HPA 吗？ | 挡不住：PDB 拦 drain 类自愿中断，HPA 是直接改 replicas。 |
| 扩出的新 Pod 没人连？ | 扩容≠容量：匹配/接入层没调度新实例；先查业务分派，不是继续加副本。 |
| Git 和 HPA 抢 replicas？ | apply 写死 replicas 会打回扩容；YAML 不写该字段或 SSA/ignoreDifferences；应急 scale 当天补 Git。 |
| metrics-server 挂了影响？ | top 和资源 HPA 瞎，业务对象读写正常——不是控制面挂。 |

### 易错一句话对照

- HPA 改的是 request → 只改 replicas，改规格是 VPA
- 没写 requests 也能算利用率 → 分母是 request，没写就 unknown
- 多指标取平均 → 各算一遍取 **max**
- 开服可以等 15s 环自动补齐 → 预案提 min 到峰值 1.2–1.5 倍
- 稳定窗口是「缩容前等 300 秒」→ 是回看 300s 推荐取最大
- 战斗服挂 CPU HPA 低峰自动缩省钱 → 缩容即踢人
- PDB 能禁止 HPA 缩战斗服 → PDB 拦 drain，不拦改 replicas
- KEDA 换了一套伸缩公式 → 只喂 external metrics，公式不变
- KEDA scale to 0 可以收战斗服 → 收的也是 Pod，对局照样没
- 扩到 max 仍 Pending 再加大 max → 加节点 / CA
- VPA + HPA 同时盯 CPU 更稳 → 规格和副本对着振荡
- Git 写死 `replicas: 3` 没关系 → 一次 apply 把扩容打回去
- 应急 scale 完就算修好了 → 当天补 Git，否则下次同步覆盖
- metrics-server 挂了 = API 挂了 → 业务对象仍可读写
- Karpenter 是阿里云默认 → AWS 原生；阿里云主流是 CA
- 扩出 Pod 就是容量涨了 → 没人连就是空壳，先查匹配/接入层
- maxReplicas 写 1000 更保险 → 要按节点池供给定，否则顶 max 时全是 Pending
- Pods 型指标的目标也是百分比 → 是 AverageValue 裸数，利用率只有 Resource 型

### 数字墙

> 同步周期 **~15s** · 容差 **±10%** · 公式 **ceil(n × current / target)** · scaleDown 稳定窗口默认 **300s** · 开服 min **1.2–1.5×** 峰值 · 无状态 **min ≥ 2** · 资源 target 常见 **60–70%** · CA 扫描 **~10s** · CA 缩容需闲置 **10min**、加节点后冷却 **~10min** · request=1m 实际 100m → 利用率 **10000%**
