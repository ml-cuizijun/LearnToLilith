# etcd

> 活动高峰，`kubectl` 全部超时，API 的 CPU 却一点不忙——群里已经有人重启了两台战斗服，另一个在问「能不能直接格式化 etcd 的数据盘」。

## 一、一张图：一份状态数据的一生

> 🎯 **一句话**：每个对象都要过「出生（API 写入）→ 共识（Raft）→ 落盘（fsync）→ 日常（compact/备份）→ 换命（换节点/升级）」，定责先问卡在哪一段。

```mermaid
flowchart LR
    K["kubectl apply 一个 Deployment"] --> API["kube-apiserver<br/>唯一入口 · 客户端口 2379"]
    API --> BORN["出生<br/>写进 /registry"]
    BORN --> VOTE["共识<br/>Raft 选主 · 多数派复制"]
    VOTE --> DISK["落盘<br/>WAL fsync · 全链路最贵一步"]
    DISK --> LIVE["日常<br/>compact · defrag · 备份"]
    LIVE --> CHANGE["换命<br/>换节点 · 滚动升级"]
    LIVE --> DEAD["灾难<br/>丢 quorum → snapshot restore"]
    DEAD -.->|同一份快照 + 新 token| BORN
```

**读图**：主线是一次写入的一生——先挤过 API 这个唯一入口，再由 Leader 用 Raft 复制到多数派、fsync 落盘才算 commit。「日常」之后分两条岔路：多数派还在走换节点，多数派没了才轮到 restore。值班排查先问「卡在哪一段」：共识段看 Leader，落盘段看 fsync，日常段看 alarm。

## 二、出生：唯一入口与它的家

> 🎯 **一句话**：只有 API Server 读写 etcd；kubelet、控制器、业务全部只连 API。

etcd 是一个**分布式、强一致的 KV 存储**，共识靠 **Raft（共识算法：选一个 Leader 协调写入，多数派同意才算提交）**，多版本靠 MVCC，另提供 Watch 与 Lease。在 Kubernetes 里，它不是 Redis，也不是消息队列，是控制面的**唯一状态库**。

> 💡 **打个比方**：etcd 像游戏服的「账号数据库」——只有登录网关（API Server）能改；战斗进程（kubelet）直连库改装备，RBAC 和审计就全被绕过了。

### 分工：谁连 2379 ⭐

```mermaid
flowchart TB
    subgraph clients ["① 客户端 · 全部只连 API"]
        kubectl["kubectl / CI"]
        sch["Scheduler"]
        cm["Controller Manager"]
        kl["kubelet"]
    end
    api["kube-apiserver<br/>认证 · 鉴权 · 准入后才读写"]
    subgraph etcd ["② etcd 集群"]
        L["Leader"]
        F1["Follower"]
        F2["Follower"]
        L ---|"成员互访 2380"| F1
        L ---|"成员互访 2380"| F2
    end
    kubectl --> api
    sch --> api
    cm --> api
    kl --> api
    api -->|"客户端口 2379 · HTTPS 双向认证"| L
```

**读图**：图的关键在**没有的东西**——没有任何箭头从 kubelet、Controller、业务指向 etcd。**2379** 是客户端口，生产只放行 API Server 网段；**2380** 是成员口，成员之间的 Raft 心跳与日志复制走这里，只放行成员。业务连 2379 也算直连。

写进 etcd 的对象都在 ``/registry/{resource}/{namespace}/{name}`` 下：Pod、Deployment、Service、Node、Secret、CR 的 spec 与 status，以及 Event、Completed Job，都在；**容器进程、容器可写层、节点上的 iptables 规则、已建立的长连接、业务库、镜像，都不在**。三个角色别混：etcd 把写成功的对象存住、多副本一致；API Server 是唯一入口，认证鉴权准入后才读写 etcd；Scheduler、Controller、kubelet、kubectl、CI 全部只连 API。

etcd 的能力 K8s 怎么用：强一致 Put/Get 持久化每个对象；**revision（全局递增的版本号，MVCC 的「版本」）** 对应 K8s 的 resourceVersion，List-Watch 靠它对齐；Watch 经 API 变成 Informer 的增量通知，控制器不直连 etcd 做 Watch；**Lease（租约，带有效期的活 KV）** 承载节点心跳（kube-node-lease），大集群里租约续期是不小的写入来源，业务别把 etcd 当锁服务打满。

> ⚠️ **别混**：Secret 进 etcd **默认是明文 JSON**——保护它的是 2379 的 TLS 和网络隔离；静止加密（EncryptionConfiguration）是 API Server 层的事。「etcd 走了 HTTPS 所以 Secret 安全」是把传输加密和存储加密混为一谈，静止加密见 [12](../12-配置与密钥/)。

> 🔍 **现场**：值班动 etcd 只有四类命令：health / status / member / snapshot（外加 alarm）。`etcdctl get /registry/...` 只在 API 已死、做只读确认时用；`etcdctl put` 手改 `/registry` 等于事故。

### 家：静态 Pod、三个路径、验收 🔧

kubeadm 集群的 etcd 是一个**静态 Pod（static Pod，kubelet 盯着 manifests 目录直接拉起，不经调度器）**：

```text
/etc/kubernetes/manifests/etcd.yaml   ← kubelet 保证这个 Pod 在；改参数 = kubelet 自动重建
/etc/kubernetes/pki/etcd/             ← CA、server、peer、healthcheck 证书
/var/lib/etcd/                        ← 这才是数据：WAL + bbolt 库文件；备份备的就是它
```

三种生产形态故障域不同，装的时候选，挂的时候别混：

- **Stacked（kubeadm 默认）**：每台控制面 = API + 一个 etcd 成员，一台挂 = 两个一起掉。3 台 Stacked + LB 就是生产最小 HA，不是「没做高可用」。
- **External**：API 一组、etcd 一组，故障域干净，盘和证书要有人盯。
- **托管（ACK / EKS）**：ssh 不进控制面，但上线前问清四件事——备份 RPO 多少、谁来 restore、升级是否滚动 etcd、磁盘是否独立。停变更的时候，停的是你的业务。

选型只有五项：节点 **3 或 5**（为什么，三节）；磁盘**本地 NVMe/SSD 独立盘**，不机械盘、不和游戏日志/容器盘混用；网络**同城多 AZ**，RTT ≪ election-timeout，**不跨地域**（跨地域 RTT 会拖垮选举，三节）；形态用静态 Pod 或托管，**不在业务 Worker 上顺手跑 etcd**；证书独立 CA、peer/client 分开、双向认证，**2379 不对整个 VPC 裸奔**。独立 systemd 部署，要求完全相同。

静态 Pod 参数最少长这样：

```yaml
- --advertise-client-urls=https://10.0.1.11:2379
- --listen-client-urls=https://127.0.0.1:2379,https://10.0.1.11:2379   # ← Stacked 的 API 走 127.0.0.1，同生共死，不是配错
- --listen-peer-urls=https://10.0.1.11:2380
- --initial-cluster=ctrl1=https://10.0.1.11:2380,ctrl2=https://10.0.1.12:2380,ctrl3=https://10.0.1.13:2380
- --data-dir=/var/lib/etcd
- --client-cert-auth=true        # ← 2379 客户端证书双向认证
- --peer-client-cert-auth=true   # ← 2380 成员证书双向认证
```

External 形态则每个 API 的 `--etcd-servers` 写满 3 个地址，一台挂了其余还连得上。

验收不是「进程起来了」：

```bash
etcdctl endpoint health --cluster   # ← 每个成员都 healthy，不是只有本机 true
kubectl get --raw /readyz           # ← API 自检包含 etcd 链路
# 只探 TCP 2379 不算验收：端口活着 ≠ 能提交写入
```

Kubernetes 的 RBAC **管不到 etcd**：证书合法就能读写 `/registry`。所以 2379 网络层只放行 API 网段、2380 只放行成员——这一道才是真正的访问控制。

## 三、共识：Raft 选主与日志复制

> 🎯 **一句话**：同一 term 多数派投票出 Leader，写要多数派 fsync 才 commit——所以最多一个 Leader，不会脑裂。

### 选举：term、投票、超时 🔥⭐

**term（任期号）** 是 Raft 全局单调递增的轮次编号，每发起一次选举就开一个新 term；所有请求都带 term，**带着旧 term 来的请求一律拒绝**。选举由超时触发：

```mermaid
sequenceDiagram
    participant A as 节点A（Leader，term=7）
    participant B as 节点B（Follower）
    participant C as 节点C（Follower）
    Note over A: 定期发心跳（空 AppendEntries，默认 100ms）
    Note over A: A 宕机 / 被隔离
    Note over B: election timeout 到点 → 转 Candidate<br/>term=8，先投自己一票
    B->>C: RequestVote(term=8)
    B--xA: RequestVote(term=8)（A 收不到，没关系）
    C->>B: VoteGranted（term=8 里 C 只有这一票）
    Note over B: 2/3 多数票 → B 成为 Leader，term=8
    B->>C: 心跳 + 后续 AppendEntries
```

**读图**：三个细节决定选举不会乱。① 各节点的选举超时**带随机抖动**，不会同一时刻集体参选、互相分票；② **同一 term 内每个节点只有一票、先到先得**，选不出两个；③ 票数必须过半——3 节点要 2 票，A 失联不妨碍 B、C 选出自己的 Leader。新 Leader 上任先发心跳，压住别人的参选念头。

再加一条安全规则：**只有日志最全的节点才能当选**——投票时对比候选人最后一条日志的 term 和 index，自己的更新就拒绝投票，保证不会选出「落后分子」。于是同一 term 至多一个 Leader。`endpoint status` 里的 `RAFT TERM` 就是当前任期：三台一致说明刚达成过共识；**某台落后很多，说明它被分区过或刚恢复**。

> 💡 **打个比方**：像三人记账小组选「执笔人」——笔（term）要多数票才能换手，一个任期只有一个人拿到笔；一个被锁在会议室（隔离）不影响另外两人换笔继续记账；他出来一看自己手里的笔编号小了，乖乖当 Follower。

> ⚠️ **别混**：网络 2+1 分裂**不会出现双 Leader 双写**——少数派凑不出多数票，永远选不出 Leader、也提交不了写；多数派照常工作。这和 MySQL 那种旧主还自认为在位的脑裂不同：Raft 的分裂里**至多一边可写**。

日志里反复 `lost leader` → 查 election-timeout、成员 RTT、磁盘，**千万别三台一起重启**——那等于把刚选出的状态全砸了重来。

### 复制：一次写入的三步 🔥

```mermaid
sequenceDiagram
    participant API as kube-apiserver
    participant L as Leader
    participant F1 as Follower 1
    participant F2 as Follower 2
    API->>L: Put /registry/...（2379）
    Note over L: ① 追加本地 WAL + fsync
    L->>F1: AppendEntries（2380）
    L->>F2: AppendEntries（2380）
    Note over F1: 写 WAL + fsync
    Note over F2: 写 WAL + fsync
    F1->>L: ACK
    F2->>L: ACK
    Note over L: ② 多数派（2/3）ACK → commit
    Note over L: ③ apply 到 bbolt，revision 推进
    L->>API: 写成功
    Note over F1,F2: 下次心跳带上 commit index，各自 apply
```

**读图**：写永远打 Leader；**Follower 收到写请求会转给 Leader**，自己不办。三步里最贵的是 fsync（① 和两个 ACK 之前，四节展开）。对客户端返回「成功」的那一刻，含义是**多数派已把这条日志写进 WAL**——此后哪怕 Leader 立刻挂掉，新 Leader 的日志也必然包含这条（选举的日志完整性规则），所以不丢。

**WAL（Write-Ahead Log，预写日志）**：改状态之前先把日志追加落盘，这是 Raft 持久性的地基；**fsync** 指强制等磁盘真正写完再返回，不是扔进页缓存就走。**bbolt**（BoltDB 的后继，嵌入式 B+ 树数据库）是 etcd 的状态机，commit 的日志最终 apply 到它——`/var/lib/etcd` 里的库文件就是它。

两个参数钉住选举和复制的节奏，**三台必须一致**：

```text
--heartbeat-interval=100ms   ← Leader 心跳间隔；同城保持默认。过大检测慢，过小心跳打满网络
--election-timeout=1000ms    ← Follower 多久没收到心跳就发起选举；取心跳的 5~10 倍，且必须 > 成员间 RTT
```

election-timeout 过小 → 网络抖一下就重选，日志里一片 `lost leader`；过大 → 宕机检测慢。它按**同城 RTT** 设，不是拿来扛跨地域的——跨地域部署选举抖动是常态，无解。

### quorum：为什么必须奇数 ⭐🔥

**quorum（多数派）** = `floor(N/2) + 1`，提交和选举都要凑够这么多台：

```text
N=1   quorum=1   能同时挂 0 台   仅开发
N=3   quorum=2   能同时挂 1 台   生产最小
N=4   quorum=3   能同时挂 1 台   容错和 3 一样，纯浪费——偶数没有收益
N=5   quorum=3   能同时挂 2 台   要抗 2 个故障域才上
N=7   quorum=4   复制更重、写更慢，K8s 生产只用 3 或 5
```

> 💡 **打个比方**：三人投票至少两票通过——加到四人还是要至少三票，容错没多一个，反而多一张要复制的嘴。

两条最常考的推论：**3 丢 1 → 换节点**（quorum 还在，六节），**3 丢 2 → restore**（quorum 没了，五节）；3 扩到 5 **写不会更快**——写仍过 Leader，5 只是多抗一台。

> 📝 **面试**：「为什么奇数」答「quorum = floor(N/2)+1，偶数容错和少一台相同：4 节点要 3 票，容错仍是 1，复制还更重，所以生产 3 或 5」。追问「上 7 台更稳？」答不——commit 要 4 台 ACK，写延迟更高，复制流量更大。

### 现场：集群健康怎么看 🔧

> 🔍 **现场**：怀疑丢 Leader，先别重启——两条命令看完再说话。

证书先设成环境变量（全章命令通用）：

```bash

export ETCDCTL_ENDPOINTS=https://127.0.0.1:2379
export ETCDCTL_CACERT=/etc/kubernetes/pki/etcd/ca.crt
export ETCDCTL_CERT=/etc/kubernetes/pki/etcd/server.crt
export ETCDCTL_KEY=/etc/kubernetes/pki/etcd/server.key
```

```bash
etcdctl endpoint health --cluster
etcdctl endpoint status --cluster -w table
```

```text
+------------------------+--------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
|        ENDPOINT        |   ID   | VERSION | DB SIZE | IS LEADER | IS LEARNER | RAFT TERM | RAFT INDEX | RAFT APPLIED INDEX | ERRORS |
+------------------------+--------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
| https://10.0.1.11:2379 | 8e9... | 3.5.10  | 1.2 GB  | true      | false      |         7 |    892341  |             892341 |        |
| https://10.0.1.12:2379 | cf2... | 3.5.10  | 1.2 GB  | false     | false      |         7 |    892341  |             892341 |        |
| https://10.0.1.13:2379 | 1ab... | 3.5.10  | 1.2 GB  | false     | false      |         7 |    892341  |             892341 |        |
+------------------------+--------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
IS LEADER          ← 恰好一个 true；0 个 = 没选出主，查盘 / NTP / 证书 / 2380
RAFT TERM          ← 三台一致；某台落后很多 = 被分区过或刚恢复
RAFT INDEX         ← Raft 日志进度，差距小才健康；某台长期落后查它的盘和网
RAFT APPLIED INDEX ← 已 apply 到状态机的进度，与 INDEX 差太多 = 这台 apply 慢
DB SIZE            ← 逼近 quota（默认 2GiB）就该想 compact/defrag（四节）
IS LEARNER         ← 学习者（六节）为 true，不占 quorum

```

加上 `etcdctl member list -w table` 和 `etcdctl alarm list`，这四条就是**值班先跑的四条**。判读：恰好 **一个** `IS LEADER=true`、三台 term 一致、INDEX 接近 = 集群健康。

### 收束：etcd 凭什么「强一致」 🎯⭐

面试问「etcd 怎么保证强一致 / Raft 原理」，答这张五件套：

```mermaid
flowchart TB
    R["etcd 强一致"] --> G1["① 唯一 Leader<br/>一个 term 至多一个"]
    R --> G2["② term 单调递增<br/>旧 term 请求一律拒绝"]
    R --> G3["③ 多数派投票<br/>每 term 每人一票、先到先得"]
    R --> G4["④ 日志完整性<br/>日志最全才能当选"]
    R --> G5["⑤ 多数派 commit<br/>WAL fsync 过半才算成功"]
```

**读图**：①②③ 保证「谁说了算」，④ 保证「算数的人手里数据最全」，⑤ 保证「说过的话收不回」——多数派已 fsync 的写入，换 Leader 也不会丢。

> ⚠️ **别混**：强一致 **≠ 高可用**——quorum 一丢立刻停写，它是拿可用性换「宁可不服务，也不给错数据」；也 **≠ 无限容量**，bbolt 的天花板就在那（四节）。

> 📝 **面试**：五件套按「谁能写（①③）→ 写什么（④）→ 写了不能赖（②⑤）」分组记，最后补一句「所以 2+1 分裂不会脑裂：少数派永远选不出 Leader」。

## 四、落盘：WAL、fsync 与容量

> 🎯 **一句话**：每次写都要 Leader + Follower 各自 WAL fsync，盘慢全集群卡写；容量靠 compact、defrag、quota 三道关。

### 最贵一步是 fsync 🔥⭐

三节的复制链摊开成本：一次写要 **Leader 本地 WAL fsync + 多数派 Follower 各自 fsync**，任何一块盘卡，全集群的写都排队。

> 💡 **打个比方**：像每笔转账都要三个人各自锁自己的保险柜（fsync）——一个人的柜门卡住，全队转账排队。

红线：**WAL fsync P99 > 25ms，磁盘不合格**（生产就该是本地 NVMe/SSD 独立盘）。日志里有两个签名：

> 🔍 **现场**：API CPU 不忙但 `kubectl` 全超时——先别给 API 加核，先看 etcd 的盘。

```bash
kubectl get --raw /readyz?verbose          # ← etcd 项 failed 或超时，矛头指向 etcd
df -h /var/lib/etcd
iostat -x 1 3 /dev/nvme0n1                 # ← await / %util 高 = 盘卡
kubectl -n kube-system logs etcd-ctrl1 --tail=50 | grep -iE "took too long|wal"
```

```text
{"level":"warn","msg":"apply request took too long","took":"892ms","expected-duration":"100ms"}
# ← apply 892ms，超 25ms 红线三十多倍
{"level":"warn","msg":"wal: sync duration","duration":"450ms"}
# ← WAL fsync 450ms，盘在拖全集群
```

游戏侧最常见的根因：**etcd 和游戏日志/容器同盘**，高峰 IO 被抢走；其次是云盘突发限流。治法是把 etcd 挪到独立 NVMe，不是给 API 加 CPU。

**读路径另说**：大部分 List/Watch 被 API 的 Watch Cache 挡掉，cache miss 和写才真打 etcd；etcd 默认读是**线性一致读（linearizable read，经 Leader 保证读到最新）**，`serializable` 读可以读本地 Follower、快但可能旧，控制面不靠这条分担负载。很多「读慢」其实夹着 Event、status 的写。

### MVCC 与 revision：Watch 为什么能用

etcd 用 **MVCC（多版本并发控制）** 存数据：每次修改不是覆盖，而是追加一个新版本，**revision（全局递增版本号）** 随每次事务推进。K8s 的 resourceVersion 就是 revision——List 拿到「哪个版本的快照」，Watch 从某个版本开始订阅增量。

历史版本不能无限留，三道关管理它们：

| 对比 | **compact** | **defrag** |
|------|-------------|------------|
| 做什么 | 删指定 revision 之前的历史版本 | 整理 bbolt，**物理回收空间** |
| 效果 | 文件**不缩小**，`du` 不降 | 该成员文件真正变小 |
| 副作用 | 旧 revision 的 Watch 报 `too old revision` | **阻塞该成员**，窗口逐台做 |
| 顺序 | 先 | 后 |

**compact 不等于腾空间**：它只删逻辑上的旧版本，bbolt 文件原样大，必须 defrag 才瘦。

> ⚠️ **别混**：`too old revision` **不是数据损坏**——是客户端（Informer）的 Watch 起点已被 compact，客户端会自动重新 List 追上，正常自愈，别看见它就想去 restore。

> ⚠️ **别混**：两个「snapshot」不是一回事：`--snapshot-count`（默认 10000，3.4+ 默认 100000）是 **Raft 内部快照**——累计这么多已提交条目就拍一份状态、截断之前的 WAL，方便慢 Follower 追赶；`etcdctl snapshot save` 是**集群级备份文件**（五节）。同名不同物。

### NOSPACE：quota 三道关 ⭐🔧

`--quota-backend-bytes` 默认 **2GiB**（大集群建议 **8GiB**），超了触发 **NOSPACE** 告警，**写入被拒（读仍可用）**。处理顺序固定：

```bash
etcdctl alarm list
# memberID:8e9... alarm:NOSPACE        # ← quota 满，写已停
etcdctl compact {revision}             # ← 通常 auto-compaction 在跑，手动补一刀
etcdctl defrag                         # ← 窗口内逐台：这台 health 追上再做下一台；高峰 --cluster 一把 = 主动摘节点
etcdctl alarm disarm                   # ← 体积下来之后才能解除
```

然后回头查体积根因：**Event 风暴**（每次异常重建都写 Event）、**Completed Job 没设 TTL**、**超大 CR**。紧急时可先把 quota 提到 8GB 止血，但只加不治理会再满——quota 是容量措施，根治是少写。

`--max-request-bytes`（默认 **1.5MiB**）是单次写入上限，别为塞肥对象盲目加大。`--auto-compaction-retention`（自动 compact，常见配 5m）**必须开**，关了 db 只涨不缩。最后一句定位：etcd **不是水平扩展的写存储**——容量靠少写、快盘、按时 compact，不是加节点；内存按**工作集约 2 倍**预留（bbolt 的索引树常驻），quota 8GB 配 4GB 内存会先 OOM。

## 五、保险：备份与 restore

> 🎯 **一句话**：备份 = 异地快照 + restore 演练；quorum 没了才 restore，没备份就没得 restore。

### 怎样才算有备份 🔧

```bash
etcdctl snapshot save /backup/etcd-$(date +%Y%m%d-%H%M).db
# {"level":"info","msg":"Snapshot saved at /backup/etcd-20260901-0300.db"}
etcdctl snapshot status /backup/etcd-20260901-0300.db -w table
```

```text
+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 2a1c...  |   892341 |      18432 |     1.2 GB |
+----------+----------+------------+------------+
# ← REVISION 是快照那一刻的版本号；文件非空、读得出这张表，才算保存成功
```

四条纪律：**至少每 6 小时一份**；**发版、扩控制面、合服前加打一份**；**异地保留 7~30 天，本机 cron 不算备份**（机器死了，cron 的产物跟着死）；**每季度做一次 restore 演练并记下 RTO**。一句话：**没有演练 = 没有备份**。**RPO（Recovery Point Objective，最多能丢多少数据）** ≈ 距上次成功快照的间隔，不是 0；**RTO（Recovery Time Objective，多久能恢复）** 只有演练过才知道。

### 什么时候 restore：quorum 没了 ⭐

3 丢 2、5 丢 3，或数据目录整体损坏——才轮到 restore。**quorum 还在绝不 restore**：restore 会生成**全新的成员身份**（新 member ID、新集群），多数派还活着时 restore，等于丢掉还在呼吸的日志另起炉灶，而且往往组不成群。

> 💡 **打个比方**：三人记账小组还有两人在正常记账，你却翻出上月旧账本、叫两个新人另组一队——活着那两位的账往哪放？正解是换个新搭档进来（member 替换，六节）。

```mermaid
flowchart LR
    A["① 停全部 API 和 etcd<br/>广播：控制面停止变更"] --> B["② 各节点 restore<br/>同一份快照 + 同一个新 token"]
    B --> C["③ 先拉起 etcd<br/>endpoint health 全 true"]
    C --> D["④ 再拉起 API<br/>readyz 通过"]
    D --> E["⑤ 验证<br/>kubectl get nodes / 抽查对象"]
```

**读图**：两个「同一」是命门——**同一份快照文件、同一个新 `--initial-cluster-token`**（必须用新 token，不能沿用旧的：防止旧集群的成员串进来、把新旧两拨人搅在一起）；每个节点各自的 `--name` 和 `--data-dir`（建议用新目录，验证通过前别覆盖旧数据）。顺序不能乱：先停写、etcd 先起、API 后起。

```bash
# 每台各跑一次（3.5+ 官方推荐用 etcdutl，etcdctl 这套写法旧版仍通用）
etcdctl snapshot restore /backup/etcd-xxx.db \
  --name=ctrl1 \
  --initial-cluster=ctrl1=https://10.0.1.11:2380,ctrl2=https://10.0.1.12:2380,ctrl3=https://10.0.1.13:2380 \
  --initial-cluster-token=etcd-restore-20260901 \
  --initial-advertise-peer-urls=https://10.0.1.11:2380 \
  --data-dir=/var/lib/etcd-new
```

两种卡住：health 通了但 API 仍超时 → 查 API 的 `--etcd-servers` 和客户端证书；etcd 组不成群 → 先对 token 和 peer URL，**不要反复 `member add`**——每 add 一次集群配置就变一次，越加越乱。

> ⚠️ **别混**：**没有备份的 restore 不叫 restore**——那只剩重建集群一条路：重新 init、YAML 重刷，PV 里的业务数据也许还在，但集群对象没了。「有 cron、没演练过」和没备份一个待遇。

## 六、换命：成员变更与滚动升级

> 🎯 **一句话**：quorum 在就换节点，别 restore；升级滚动一台台，回滚靠升级前快照。

### 换坏节点：member remove / add 🔧⭐

3 丢 1、5 丢 1~2（quorum 仍满足），标准流程：

```bash
etcdctl member list -w table                 # ← 记下坏节点 ID，如 1ab2c3
etcdctl member remove 1ab2c3                 # ← 集群变 2 成员；3 的 quorum=2 恰好仍满足，动作别拖
# 新机器：挂独立数据盘、放好证书、配好 peer URL，然后：
etcdctl member add ctrl3-new --peer-urls=https://10.0.1.14:2380
# ← 输出新的 ETCD_INITIAL_CLUSTER，抄给新节点的启动参数
# 新节点启动：--initial-cluster=<上面那份> --initial-cluster-state=existing
etcdctl endpoint health --cluster            # ← 全部 healthy 才算完
```

两个细节：新节点要带 `--initial-cluster-state=existing`（加入现有集群，不是新建）；数据量大或跨 AZ 的新节点，先以 **Learner（学习者，3.4+ 引入的非投票成员）** 加入——不占 quorum、先后台追日志，追上后再 `member promote` 成投票成员，避免新人复制太慢拖垮全集群的写。

| 对比 | **member 替换** | **snapshot restore** |
|------|-----------------|----------------------|
| 条件 | quorum 还在（3 丢 1 / 5 丢 1~2） | quorum 没了（3 丢 2 / 5 丢 3） |
| 身份 | 集群身份不变，换一个人 | 全员新身份（新 member ID / 新 token） |
| 数据 | 不丢（活着的成员有完整日志） | 回退到快照时刻（丢 RPO） |
| 业务 | 短暂抖动，无需停写 | 停写窗口，全员广播 |

迁移只记三岔，别混：**换机器** = 本节的 remove / add；**只换盘** = 先 snapshot → 停该成员 → 拷 `/var/lib/etcd` 到新盘 → 拉起；**只改 IP** = `etcdctl member update <id> --peer-urls=...`，yaml 里 advertise/listen 一起改。Stacked 改 External 是个项目，活动期不要做。

> ⚠️ **别混**：**成员变更 ≠ 扩容**——加成员不提升写吞吐（写仍过 Leader，三节），只多一个读端点和一份容错。「etcd 扛不住了加两台」是错方子。

### 滚动升级：Follower 先，Leader 后 ⭐

升级先对 **Kubernetes 支持的 etcd 版本**（不能凭「最新 etcd」硬上），然后四步：

1. **先 snapshot**，异地留一份——这是回滚唯一的出路。
2. **滚动**：逐台升 Follower（停 → 换镜像 → 起 → health 且 INDEX 追上，再做下一台），**Leader 放最后**（或先 `etcdctl move-leader <别的成员ID>` 把 Leader 让出去）。全程保 quorum。
3. 不要三台同时换镜像（集群直接没 quorum），不要跳大版本。
4. kubeadm 集群 `kubeadm upgrade apply` 会带着 etcd 一起升，不要在它之外抢改静态 Pod 镜像；集群级升级节奏见 [17](../17-节点运行时与升级/)。

**回滚只有一条路**：数据目录升级之后，**不能靠换回旧二进制降级**（新版数据格式旧版不认）。回滚 = 用**升级前那份快照**按五节 restore（停全部 API 和 etcd，同一份快照 + 同一个新 token，先 etcd 后 API）。没有升级前快照 = 没有回滚。升级后一台 INDEX 落后：先查这台盘和网，必要时按本节摘掉重加，**不要三台一起把镜像改回去**。

### 证书轮转（一句）

`kubeadm certs check-expiration` 看剩余天数，**< 14 天按 P1**；`kubeadm certs renew` 之后**必须重启控制面静态 Pod**——只换 pem 不重启，进程还拿着旧证。两种症状分清：**peer 证书过期 = 成员拆伙**（组不成群、没 Leader）；**client 证书过期 = API 连不上 etcd**（readyz 的 etcd 项失败）。证书体系见 [14](../14-证书与kubeconfig/)。

## 七、作战：定责

> 🎯 **一句话**：先问「etcd 挂了什么还活着」，再 health 看 quorum、alarm 看 quota、iostat 看盘。

### 影响面先说清：什么还在 ⭐

**etcd 不可用 = 不能变更，不是立刻踢玩家。** 和 [01](../01-集群架构/) 同一套三问——进程还在不在？还能不能变更？已有流量还通不通？答案：在、不能、通。

| 对比 | **通常还在** | **立刻停** |
|------|--------------|------------|
| 有什么 | 已运行的容器进程、已有 iptables/conntrack、已建立的长连接、业务库 | apply/发版/合服/扩缩容、节点挂了之后的 Pod 重调度与自愈 |
| 为什么 | 规则和进程在节点内核与内存里，etcd 只存「期望状态」 | 所有写都要经 API 进 etcd，写路径断了 |

所以**别去重启还活着的战斗服**——重启要从 API 拉 spec，拉不出来就是「不能变更」变「真的挂了」。已有规则在内核里，不会因 etcd 挂而蒸发，只是不再更新。控制面组件挂了的总影响面见 [01](../01-集群架构/)。

### 定责决策树

```mermaid
flowchart TB
    A["kubectl 超时 / 变更失败"] --> R["kubectl get --raw /readyz?verbose"]
    R --> B{"etcdctl endpoint health --cluster"}
    B -->|"有成员 unhealthy"| C{"healthy 还剩几台？"}
    C -->|"满足 quorum（3剩2 / 5剩3）"| D["换节点：member remove / add<br/>查坏机的盘 / 证书 / 时钟"]
    C -->|"不满足 quorum（3剩1）"| E["停写广播 → snapshot restore（五节）"]
    B -->|"全 healthy 但慢"| F{"endpoint status + alarm list + 日志"}
    F -->|"NOSPACE"| G["compact → 窗口逐台 defrag → disarm"]
    F -->|"took too long / fsync 高"| H["etcd 数据盘：iostat，挪独立 NVMe"]
    F -->|"DB SIZE 逼近 quota"| I["清 Event/Job + 确认 auto-compaction"]
    B -->|"全 healthy 且不慢"| J["不是 etcd：Webhook / APF / 大 List → 03"]
```

**读图**：入口永远是 `endpoint health --cluster`，三个出口——**不健康的数 quorum**（左），**健康但慢的看 quota 和盘**（中），**健康且不慢的别赖 etcd**（右）。「有 Leader 的慢」永远不等于「要 restore」。

### 现象 · 先做 · 别做

| 现象 | 先做 | 别做 |
|------|------|------|
| `etcd_server_has_leader==0` / IS LEADER 全 false | health/status；查盘、NTP、证书、2380 | 三台一起重启；重启业务 Pod |
| NOSPACE | compact + 窗口逐台 defrag；清 Event/Job | 格式化数据盘；只 disarm 不治理 |
| API 慢、仍有 Leader | etcd 盘 fsync；再查 Webhook | 先给 API 加核 |
| 单台 unhealthy、另两台 true | member remove / add | restore |
| 只剩一台 healthy | 停写，snapshot restore | 对残存节点 member add |
| `too old revision` | Informer 自愈重新 List，观察 | 当数据丢失去 restore |
| 升级后一台 INDEX 落后 | 查这台盘和网，必要时摘掉重加 | 三台一起回滚二进制 |
| kubectl 超时但 etcd 全健康 | Webhook / APF / 大 List → [03](../03-API-Server/) | 当 etcd 坏去 restore |
| 活动高峰写超时 | 确认进程在 → 停发版停重启 → 救盘 / quorum / quota | 重启战斗服 |

监控告警线（Prometheus 指标体系见 [19](../19-监控与可观测性/)）：`etcd_server_has_leader == 0` 是 P0；`etcd_disk_wal_fsync_duration_seconds` 的 P99 > 25ms 是 P0/P1；DB SIZE / quota > 0.8 是 P1（到 1.0 就是 NOSPACE）；证书剩余 < 14 天是 P1。日志关键字速配：`took too long` / `wal: sync duration` = 盘；`database space exceeded` = quota；`lost leader` = 选举或网络。

### 60 秒剧本 🔧

> 🔍 **现场**：接到「kubectl 超时」告警，60 秒走完这条线再开口。

```text
① 0–10s   kubectl get --raw /readyz?verbose；etcdctl endpoint health --cluster
          → etcd 的事还是 API 的事，在这里分叉
② 10–30s  etcdctl endpoint status --cluster -w table；etcdctl alarm list
          → Leader 唯一吗 / INDEX 齐吗 / DB SIZE 满没满 / 有没有 NOSPACE
③ 30–45s  定型：不健康数 quorum（换节点 or restore）；慢看 iostat 和日志（fsync / took too long）
④ 45–60s  按决策树动手并验证：换完 health 全 true；restore 先 etcd 后 API；
          fsync 高挪独立盘并停变更窗口。恢复后先 kubectl get nodes 确认，再放控制器自愈
```

## 八、收口

### 命令速查 🔧

```bash
# 证书环境变量见三节。值班四条：
etcdctl endpoint health --cluster                    # 每成员健康
etcdctl endpoint status --cluster -w table           # Leader / term / INDEX / DB SIZE
etcdctl member list -w table                         # 成员 ID 和 peer URL
etcdctl alarm list                                   # NOSPACE 在这里
# 备份与恢复：
etcdctl snapshot save /backup/etcd-$(date +%Y%m%d-%H%M).db   # 备份
etcdctl snapshot status {file} -w table              # 验证备份可读
etcdctl snapshot restore {file} --name=... --initial-cluster=... \
  --initial-cluster-token=<新token> --data-dir=<新目录>      # 停写后用（五节）
# 容量治理：
etcdctl compact {revision}                           # 删历史版本（通常交给 auto-compaction）
etcdctl defrag                                       # 物理瘦身，窗口逐台
etcdctl alarm disarm                                 # 治理完之后解除告警
# 成员变更：
etcdctl member remove {id}                           # 换节点第一步
etcdctl member add {name} --peer-urls=...            # 换节点第二步
etcdctl member update {id} --peer-urls=...           # 只改 IP
etcdctl move-leader {id}                             # 升级前让出 Leader
# 只读探活（API 已死时确认 etcd 还能答）：
etcdctl get / --prefix --keys-only --limit=1
```

### 面试锚点

| 问 | 30 秒答 |
|----|---------|
| etcd 是什么？ | 分布式强一致 KV，控制面唯一状态库；只有 API Server 读写，其余组件禁止直连。 |
| 谁读写 etcd？ | 只有 API Server；直连绕过认证、鉴权、准入、审计，2379 只放行 API 网段。 |
| Raft 怎么选主？ | Follower 选举超时 → Candidate，term+1 先投自己 → RequestVote，多数票当 Leader；每 term 一票先到先得，超时随机抖动防同时参选。 |
| term 是什么？ | 全局单调递增的任期号，每选举一次 +1；旧 term 请求被拒，保证一个 term 至多一个 Leader。 |
| 一次写怎么提交？ | 写打 Leader → 本地 WAL fsync → AppendEntries 复制 → 多数派 ACK → commit → apply 到 bbolt 才回成功。 |
| quorum 是什么？ | floor(N/2)+1；3→2、5→3；偶数没收益，4 节点容错仍是 1。 |
| 3 丢 1 / 3 丢 2？ | 丢 1 quorum 在，换节点；丢 2 quorum 没了，停写 snapshot restore。 |
| 2+1 分裂会双 Leader 吗？ | 不会；少数派凑不出多数票选不出主、写不了，不是 MySQL 脑裂。 |
| 写入哪步最贵？ | WAL fsync；P99 > 25ms 盘不合格。API CPU 低但写超时，先查 etcd 盘，不给 API 加核。 |
| compact 和 defrag？ | compact 删历史版本不缩文件；defrag 物理回收但阻塞该成员，窗口逐台。 |
| NOSPACE 怎么处理？ | compact → 窗口逐台 defrag → alarm disarm，再查 Event/Job/大 CR；quota 默认 2GiB、大集群 8GiB。 |
| too old revision？ | Watch 起点被 compact 了，客户端重新 List，正常现象不是损坏。 |
| 怎样才算有备份？ | snapshot save + 异地 7~30 天 + 定期 restore 演练；本机 cron 不算，没演练 = 没备份，RPO ≈ 快照间隔。 |
| restore 的关键？ | 停全部 API 和 etcd；同一份快照 + 同一个新 token + 各自新 data-dir；先 etcd health 再 API；restore 生成新成员身份。 |
| 升级 etcd 怎么做？ | 先 snapshot 异地；滚动：Follower 先 Leader 后（或 move-leader）；保 quorum，不同时换镜像、不跳大版本。 |
| 升级失败怎么回滚？ | 不能换回二进制降级，用升级前快照 restore；没有升级前快照就没有回滚。 |
| etcd 挂了游戏服还在吗？ | 在；进程和已有规则都在节点上，只是不能变更（扩缩容/自愈停摆），别重启战斗服。 |
| Secret 在 etcd 加密吗？ | 默认明文 JSON；TLS 只是传输层，静止加密是 API Server 的 EncryptionConfiguration。 |
| Lease 干什么用？ | 租约，带有效期的活 KV；节点心跳（kube-node-lease）用它，别拿 etcd 当锁服务打满。 |
| learner 有什么用？ | 非投票成员，不占 quorum 先追日志，追上再 promote；大数据量换节点更安全。 |

### 易错一句话对照

- kubelet 可以直连 etcd 拉 spec → 所有组件只连 API，直连绕过认证和审计
- etcd 挂了游戏服进程立刻没了 → 进程还在，只是不能变更
- 4 台比 3 台稳 → 4 节点 quorum=3，容错仍是 1，浪费
- 控制面 etcd 可以跨 region → RTT 拖垮选举，频繁重选
- 3 丢 1 马上 snapshot restore → 换节点；restore 生成新身份，扔掉还活着的日志
- WAL fsync 慢，先给 API 加 CPU → 先给 etcd 挪独立 NVMe
- 3 扩到 5 写入变快 → 写仍过 Leader，5 只是多抗一台
- compact 之后 du 一定降 → 物理缩小要 defrag
- too old revision 是数据损坏 → compact 后正常，客户端重新 List
- Secret 进 etcd 是加密的 → 默认明文，静止加密在 API 层
- 托管就不用管备份 → 停变更的是你的业务，RPO 仍是你的
- 三台同时换镜像省窗口 → 必须滚动，保 quorum
- 升级失败换回旧二进制 → 数据目录不能降级，靠升级前快照 restore
- NOSPACE 只需 alarm disarm → 先 compact + defrag 把体积降下来
- etcd 扛不住就加成员 → 成员变更 ≠ 扩容，写吞吐不涨
- etcd 有 TLS 所以 Secret 安全 → 传输加密 ≠ 静止加密
- 无 Leader 和 NOSPACE 是一回事 → NOSPACE 可能仍有 Leader（写拒读还在）
- 2+1 分裂会双主双写 → 少数派选不出 Leader，至多一边可写
- 「API 慢」直接查 etcd → 先分 Watch Cache/大对象（API 层）还是 etcd 写慢（fsync），readyz 和 health 分叉
- quorum 没了还能 member add 救 → quorum 没了只能 restore，乱 add 越加越乱

### 数字墙

> quorum：3→**2** · 5→**3** · 心跳 **100ms** · election-timeout **1000ms**（心跳 5~10 倍、> RTT、三台一致）· snapshot-count **10000**（3.4+ 默认 100000）· WAL fsync P99 红线 **25ms** · quota **2GiB** 默认 / **8GiB** 大集群 · max-request-bytes **1.5MiB** · 备份 **每 6h** + 异地 **7~30 天** · 证书告警 **14 天** · 端口 **2379** 客户端 / **2380** 成员 · auto-compaction 常见 **5m** · 内存 ≈ 工作集 **2 倍** · `--enable-v2` 保持关闭（3.4+ 默认关，打开无收益）
