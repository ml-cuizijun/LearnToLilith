## Q1

**★★★★★｜K8s 网络三原则？CNI 和 kube-proxy、CoreDNS 怎么分工？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §1 基本概念 · §2 架构

### 场景

开场就问：「Pod 和 Pod 通信要不要 NAT？VIP 是谁分配的？」有人开始背 Flannel 版本号。

### 完整解答

**一句话**：三原则：每 Pod 一 IP、Pod 间无 NAT、节点可达所有 Pod；CNI 管 Pod IP，kube-proxy 管 VIP。

1. 每个 Pod 一张 IP（pause 持有 netns）。
2. Pod 之间直接通信，**无 NAT**——抓包看到真实 Pod IP。
3. 节点 Agent 能访问所有 Pod。

```mermaid
flowchart TB
    a[名字 CoreDNS · 09]
    b[VIP kube-proxy / Service · 08]
    c[Pod IP CNI · 本章]
    d[入口 Ingress / LB · 14]
    e[东西向墙 NetworkPolicy · 本章]
    classDef a fill:#0891B2,stroke:#155E75,stroke-width:2px,color:#fff
    classDef b fill:#2563EB,stroke:#1E3A8A,stroke-width:2px,color:#fff
    classDef c fill:#7C3AED,stroke:#4C1D95,stroke-width:2px,color:#fff
    class a,d a
    class b b
    class c,e c
```

CNI 管 **Pod IP 和跨节点路由**（以及可选的 NP）。kube-proxy 管 **Service VIP → Pod**。不要让 CNI 去背 VIP，也不要让 proxy 去发 Pod IP。对端 IP 真实，conntrack、抓包、NP 才好做。

### 再追问

- 为什么要无 NAT？——NAT 迷宫里策略只能写节点，拦不住东西向。

## Q2

**★★★★★｜Pod 创建时网络怎么建立？FailedCreatePodSandBox 是什么？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.1 Pod IP

### 场景

新战斗服一直 ContainerCreating。应用镜像日志还没有。Events 里 `FailedCreatePodSandBox`。有人说调度坏了。

### 完整解答

**一句话**：sandbox 失败在 kubelet 调 CNI 阶段，业务容器还没起——查 CNI agent 和 IPAM。

Scheduler 已经写了 nodeName。失败发生在 kubelet 调 CNI 这一步，业务容器不会起：

```
kubelet 起 pause netns
  → 读 /etc/cni/net.d，调 /opt/cni/bin
  → IPAM 分配 → veth + 路由
  → 业务容器 join     ← sandbox 失败则走不到这里
```

查：CNI agent 是否 Running、`/etc/cni/net.d`、IP 池是否耗尽、节点磁盘、路由。不是应用日志问题，也不是 Scheduler 的责任（01、06）。Pod IP 来自 CNI 的 IPAM，不是 kube-proxy，也不是 API Server。

### 再追问

- `get po -o wide` 已经有 IP 说明什么？——sandbox 成功。再不通才分同节点 / 跨节点。

## Q3

**★★★★★｜Calico 和 Flannel 怎么选？谁支持 NetworkPolicy？Cilium 呢？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.3 CNI 选型

### 场景

小集群先上了 Flannel。安全要 default-deny。apply 了 NetworkPolicy，支付 NS 还是能被随便扫到。

### 完整解答

**一句话**：裸 Flannel 默认没有 NetworkPolicy；YAML 能 apply 不代表策略生效。

| | Flannel | Calico | Cilium |
|--|---------|--------|--------|
| 跨节点 | VXLAN / Host-GW | BGP / IPIP / VXLAN | eBPF |
| NetworkPolicy | **默认没有** | 有 | 有，还可 L7 |
| 适合 | 简单小集群 | 生产常用 | 可观测 / 替 kube-proxy |

YAML 能 apply 不代表生效。纯 Flannel 上 NP 是死数据。要策略：Canal 或换 Calico / Cilium。云上安全组要放行封装口（VXLAN UDP 4789、IPIP 协议 4）或 BGP 179。Host-GW 要二层打通。

Cilium 的 eBPF、Hubble、替换 kube-proxy 见 **23**。本章答到「能选、知道比 Flannel 多策略和可观测」即可。上了 NP 还通三种：CNI 不支持、selector 没匹配到、另一条 NP 并集放行了。

### 再追问

- 新生产还上 Canal 吗？——过渡。直接 Calico / Cilium 更干净。

## Q4

**★★★★★｜NetworkPolicy 默认行为？Namespace 是安全边界吗？上线顺序为什么先放行 53？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 §3.4 NetworkPolicy

### 场景

「支付单独一个 NS 就合规了吧？」安全又要求 default-deny。上线当天全集群 DNS 挂，IP ping 还通。

### 完整解答

**一句话**：无 NP 全通；被选中后该方向默认拒；上 NP 必须先放行 kube-system egress 53。

**NS 不是安全边界。** 跨 NS 默认三层能通。NP 才是东西向的墙；RBAC 管的是 API，不管包。同一 NS 里两个 Deployment 默认通。

```
无任何 NP：hall <-> battle <-> pay  全通
Pod 被 Ingress 规则选中 → 入站默认拒，只放行写出的 from
Pod 被 Egress 规则选中 → 出站默认拒，只放行写出的 to
多条 NP = 并集（一条放行就通）
```

上线顺序：① 确认 CNI 支持 NP ② 核心 NS 默认拒 ③ **先放行 kube-system:53** ④ 放行网关，再放行 backend→DB。一步 default deny 不放 DNS，就是「刚上 NP 全网名字挂」（09）。egress 只放行 DNS 后，支付公网也会被默拒，要再放目标 CIDR。

### 再追问

- 改 NP 要不要滚动业务 Pod？——不要。即时生效。误加 deny-all 的回滚就是改 / 删这条策略，秒级。

## Q5

**★★★★☆｜跨节点不通怎么拆？同节点对照图怎么画？**

**覆盖**：必会 · 常用
**对应**：知识点 §7 生产排障 · §3.2

### 场景

新建集群，同节点 ping 通，跨节点全丢。有人开始查应用端口。

### 完整解答

**一句话**：同节点通、跨节点不通 → 查隧道/BGP/安全组/MTU，不要一上来查应用端口。

```
Pod-A (node-1) --ping--> Pod-C (node-1)   通  → 本机 veth/NP 大致好
Pod-A (node-1) --ping--> Pod-B (node-2)   不通 → 隧道 / BGP / 安全组 / MTU
```

1. 看该节点 calico-node / flannel / cilium 是否 Running。
2. 云安全组：UDP 4789（VXLAN）、协议 4（IPIP）、TCP 179（BGP）。
3. `ip route`、两台节点互 ping，再 ping 隧道口。
4. 最后才查 NP——若同节点也不通，才优先怀疑 NP 或本机 veth。

只有大包丢、小包通：MTU。VXLAN 要把 MTU 减封装头。`ping -M do -s 1400`。TCP 会表现为奇怪超时。

### 再追问

- VIP 不通、Pod IP 通呢？——那是 08，不是本章三层。

## Q6

**★★★★☆｜Overlay 和 Underlay 差在哪？游戏长连接跨 AZ 要注意什么？**

**覆盖**：必会 · 常用
**对应**：知识点 §3.2 Overlay / Underlay

### 场景

战斗服和 Redis 被调度到两个 AZ，P99 抖。网络说「K8s 自己的 VXLAN 问题」。

### 完整解答

**一句话**：Overlay 有封装和 MTU 代价；跨 AZ 长连接要多算一跳，能同拓扑调度就同拓扑。

Overlay：Pod 包封进 Node IP 再走物理网。改物理网少，有封装损耗和 MTU 问题。Underlay：BGP 把 Pod CIDR 宣告给物理网，包直接路由。快，要网络配合。

云上经常被迫 IPIP / VXLAN。跨 AZ 每条长连接多一跳封装，CPU 和延迟都要算。能同拓扑调度就同拓扑（06），不要让战斗包每条都钻隧道跨区。

小集群用 Flannel：上手快、组件少。代价是默认没有 NP，以及 VXLAN 的 MTU / 封装。要策略就别停在裸 Flannel。

### 再追问

- 战斗服和 Redis 为什么要同 AZ？——少一跳封装，P99 少抖。这是调度拓扑（06），不是再换一个 CNI 口号。

## Q7

**★★★★☆｜IP 池耗尽是什么现象？和 maxPods 什么关系？**

**覆盖**：必会 · 常用
**对应**：知识点 §3.1 · §5 配置

### 场景

某节点还能调度，新 Pod 全部 sandbox 失败。别的节点正常。

### 完整解答

**一句话**：节点 CNI CIDR 耗尽会 sandbox 失败；要和 maxPods 和 pod-network-cidr 对齐规划。

该节点分配给 CNI 的 CIDR 用完了，或 IP 泄漏没回收。新 Pod 过不了 CNI ADD。

规划：全集群 /16，每节点 /24，和 kubelet maxPods 对齐。/24 理论 256，去掉网关等，默认 110 够用；把 maxPods 拉到 250 而不改掩码会耗尽。`pod-network-cidr` 和 CNI 清单必须一致。监控使用率 >80%。扩 ippool、清泄漏、不要拿 /24 当全集群 CIDR。

改了 CNI YAML 里的 CIDR，存量 Pod **不会**自动迁。改池是一次迁移，不是 apply 完魔法生效。

### 再追问

- 为什么别的节点正常还能调度？——调度看的是 CPU/内存 Pending，不看该节点 CNI CIDR 用完。表现就是「能调过来，sandbox 失败」。

## Q8

**★★★★☆｜东西向和南北向谁管？只在 Ingress 做认证够不够？**

**覆盖**：必会 · 常考
**对应**：知识点 §3.4 · §1 概念

### 场景

支付库只在 Ingress 上了鉴权。集群里任意 NS 的 Pod 都能直接连支付 Pod IP。

### 完整解答

**一句话**：Ingress 拦南北向；NetworkPolicy 拦东西向；RBAC 管 API，不管包。

- 南北向（用户进集群）：云 LB + Ingress + 安全组 → 14
- 东西向（Pod ↔ Pod）：CNI + NetworkPolicy → 本章
- API 操作：RBAC → 13

只在 Ingress 做认证拦不住集群内横向。支付库必须 NP default-deny，只放行该放的 from。有 kubectl 权限也不等于能连上 DB——那是另一层；反过来，能连上包也不等于能 kubectl。RBAC 配好了还要 NP：一个管 API，一个管包。

### 再追问

- 有状态战斗服和支付同集群最低配？——独立 NS、最小 RBAC、NP 默认拒、污点 / 独立节点池（01）。不是只建一个 NS。

## Q9

**★★★★☆｜HostNetwork 的代价？和 CNI 三原则什么关系？**

**覆盖**：必会 · 常用
**对应**：知识点 §3.4 · §5 配置

### 场景

有人给战斗服开 hostNetwork「降延迟」。端口和 Ingress 抢 443，NP 看起来不生效，短名 DNS 也没了。

### 完整解答

**一句话**：hostNetwork 绕过部分 CNI/NP 模型，还要改 dnsPolicy，能不用就不用。

hostNetwork 用节点网络栈：

1. 占节点端口，和 NodePort、Ingress hostNetwork 冲突。
2. 绕过部分 CNI / NP 模型，排障更像管一台裸机。
3. dnsPolicy 要改成 `ClusterFirstWithHostNet`，否则短名全废（09）。
4. PSS baseline 默认禁 hostNetwork，要例外写单独 NS（13）。

三原则对这类 Pod **部分失效**。能不用就不用。CNI DaemonSet 滚动时 agent 重启期间隧道 / eBPF 会空窗，maxUnavailable 要小，不要一次滚光。

### 再追问

- 同节点 veth 不通先看什么？——先看是不是 NP，再看是否 agent 重启中。

## Q10

**★★★★☆｜egress 只放行了 DNS，支付公网为什么挂？**

**覆盖**：必会 · 常用 · 常考
**对应**：知识点 §3.4 NetworkPolicy

### 场景

上 NP 后集群名解析好了，大厅调支付网关 `api.pay.com` 超时。CoreDNS 里 nslookup 该域名是通的。

### 完整解答

**一句话**：解析通只说明 53 放了；egress 默认拒时 HTTPS 出站还要单独写目标 CIDR。

解析通只说明 53 放行了。真正的 HTTPS 出站是另一条 egress。写了 egress 规则的 Pod **出站默认拒**，没写支付 CIDR 就被切。

```
Pod --UDP/53--> CoreDNS     通（已放行）
Pod --TCP/443--> 支付公网    拒（egress 没写）
```

补目标 CIDR 或固定 egress 网关。不要回到 09 把 CoreDNS 当替罪羊。改 NP 不要滚动业务 Pod。误加 deny-all 的回滚就是改 / 删这条策略，秒级。

### 再追问

- 名挂、IP 通，和「解析通、HTTPS 挂」差在哪？——前者多半没放行 53；后者 53 有了、443 没有。

## Q11

**★★★★☆｜Flannel Host-GW 和 VXLAN 怎么选？**

**覆盖**：常用 · 常考
**对应**：知识点 §3.2 Host-GW vs VXLAN

### 场景

同机房二层是通的，有人仍上了 VXLAN，大包游戏状态同步经常重传。

### 完整解答

**一句话**：二层通选 Host-GW 无封装；跨三层/云上常用 VXLAN，记得调 MTU。

Host-GW：节点把 Pod CIDR 写成路由，二层直达，无封装，MTU 好说话。前提是 **节点二层打通**。VXLAN：不依赖二层，有封装和 MTU 折损。

二层通、要性能 → Host-GW。跨三层 / 云上不保证二层 → VXLAN 或 Calico IPIP。选了 VXLAN 就把 MTU 减下来，不要 1500 硬扛。

### 再追问

- 云上 VPC 为什么常用 VXLAN / IPIP？——通常不保证节点二层打通，Host-GW 前提不成立。
