## Q1

**★★★★★｜排障三问、三宝各看什么？为什么不能一上来重启？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 [1. 基本概念](知识点.md) · [6. 命令与操作](知识点.md)

### 场景

夜班游戏服 CrashLoop。有人已经准备 `kubectl delete pod --all`。Events 还没人看过。

先自己试试：不看下面，先口述三问、三宝和「为什么不能先重启」，再往下对。

### 完整解答

> 🎯 **一句话**：三问定影响面，三宝 describe/logs --previous/exec 落盘；不要先重启盖证据。

三问：进程还在不在？还能不能变更？已有流量还通不通？和 01 / 02 同一套，先定影响面。

三宝：`describe` 看 Events / 探针 / 退出码 / 调度失败；`logs --previous` 看上次崩溃；`exec` 进容器验证端口、DNS、文件。定域顺序是 Events → spec/status → 节点/CNI/CSI → 应用日志。

不要先重启：`--previous` 会被盖掉；Events 约一小时，先落盘；有状态重启 = 踢玩家；全员重启依赖可能扩散。exec 走 API → kubelet，403 和 NP 都会失败。多容器必须 `-c`。

### 再追问

镜像 distroless？——`kubectl debug -it --image=netshoot --target=`。临时 run 无关 Pod **不**共享问题 Pod 的网络和存储——Q11 专门拆这个坑。

## Q2

Q1 钉死了「先落盘」；这道题进树 A——Pending 第一问是有没有 nodeName。

**★★★★★｜Pod 一直 Pending，完整怎么查？**

**覆盖**：核心 · 必会 · 常用
**对应**：知识点 [3. 原理](知识点.md)

### 场景

`kubectl apply` 之后游戏匹配服一直 Pending。有人说调度坏了。Events 还没贴出来。

先自己试试：不看下面，先画 Pending 分流（有无 nodeName），再对答案。

### 完整解答

> 🎯 **一句话**：Pending 先看有无 nodeName：无则查调度，有则查 ImagePull/sandbox/CNI/挂卷。

先看有没有 `nodeName`。没有：Insufficient（Allocatable 不是 top）、affinity、污点、unbound PVC / WFFC、全体 Pending 看 scheduler。有 nodeName：ImagePull 在该节点 crictl pull、sandbox 看 CNI/pause/CIDR、挂卷看 CSI。不要先改业务镜像。0/N 通常是几条叠在一起，不是「集群没节点」。

### 再追问

Scheduler 成功了但事件是拉镜像，谁的责任？——kubelet + 运行时。Scheduler 只写 nodeName（01、16）。

## Q3

Q2 是「还没起来」；这道题是「起来过又反复退出」——树 B。

**★★★★★｜CrashLoopBackOff 第一刀？和 OOM 怎么区分？**

**覆盖**：核心 · 必会 · 常用
**对应**：知识点 [3. 原理](知识点.md)

### 场景

登录服重启次数在爬。群里有人说「内存不够加 limit」。Last State 还没人贴。

先自己试试：第一刀敲什么？137 怎么分？

### 完整解答

> 🎯 **一句话**：CrashLoop 第一刀 logs --previous + 退出码；137 分 OOM 与 SIGKILL，liveness 误杀也会 CrashLoop。

第一刀：`logs --previous` + Last State 退出码。137 + OOMKilled → 树 C。137 无 OOM → grace 强杀。1/2 应用退出。139 段错误。Events Unhealthy → liveness 误杀。游戏服先排除 liveness 打还没起来的依赖。CrashLoop 没机会 exec：`debug --copy-to` 改命令。

liveness 失败会重启 → CrashLoop。readiness 失败只摘 EP，Pod 仍 Running。

### 再追问

143？——SIGTERM，正常被停，不是 OOM。下一题专门拆 OOM vs Evicted——别跟 137 混。

## Q4

就是 Q3 里「137 + OOMKilled」那条分支的展开——再加 Evicted，别混。

**★★★★★｜OOMKilled 和 Evicted 差在哪？只重建 Pod 行不行？**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 [3. 原理](知识点.md)

### 场景

战斗服 Pod 没了。有人看见 Reason 里有 Killed，准备把 limit 加倍。节点 Conditions 没人看。

先自己试试：OOM 和 Evict 谁杀的？只重建行不行？

### 完整解答

> 🎯 **一句话**：OOMKilled 是本容器超 limit；Evicted 是节点压力赶人，只重建会再被赶。

OOMKilled：本容器超 **memory limit**。Evicted：节点 Memory/Disk/PID Pressure，kubelet 赶人。只重建 Evicted 的 Pod 会再被赶。看 limit 和 RSS 曲线：泄漏 vs limit 过小 vs 堆外。Java/Go 留 30–50% 给堆外。不要只说加内存。DiskPressure 常是 overlay 和容器日志（16、19）。BestEffort 先被 Evict，Guaranteed 后（04）。

### 再追问

CPU 高且新 Pod Pending 一次重启？——两套域（top vs Allocated），还会踢玩家——Q9 就是这个坑的完整版。

## Q5

前面四棵树讲「起不来 / 死了」；这道题是 Running 但访问不通——树 E。

**★★★★★｜Service 访问失败，Endpoints 为空？有 Endpoints 仍不通呢？**

**覆盖**：核心 · 必会 · 常用
**对应**：知识点 [3. 原理](知识点.md)

### 场景

大厅能解析 Service 名，但连不上。有人要重启 kube-proxy。`kubectl get ep` 还没跑。

先自己试试：空 EP 第一刀是什么？六层顺序能背吗？

### 完整解答

> 🎯 **一句话**：Endpoints 空先对 selector/readiness；有 EP 再分层 localhost→EP→ClusterIP→跨节点→DNS→Ingress。

Endpoints 空 = kube-proxy 没有后端可转，重启 proxy 没用。先对 selector 和 readiness。有 EP 再分层：localhost → EP → ClusterIP → 跨节点 → DNS → Ingress。同节点通、跨节点不通 → 10。名不通、IP 通 → 09。VIP 不通但有 EP → 08。502 → 14。临时 netshoot 要和问题 Pod 同 NS。

滚动后 502：能 undo 先止血（15），同时看新 Pod Ready、EP 新 IP、旧 Pod 是否瞬间没了。

### 再追问

Label 打在 annotation 上？——Service 不认。describe 一眼能看出来（01）。Q13 是这题的网络单节点版。

## Q6

五棵树之外：节点红了——不在树上，先救 kubelet。

**★★★★☆｜节点 NotReady，你上节点看什么？能杀业务进程吗？**

**覆盖**：必会 · 常用
**对应**：知识点 [7. 生产排障](知识点.md) · [8. 必会 · 常考](知识点.md)

### 场景

战斗节点 NotReady。kubelet 日志刷 PLEG。有人要把该节点 Pod 全删。

先自己试试：上节点看什么？能不能删业务？

### 完整解答

> 🎯 **一句话**：NotReady 上节点查 kubelet/盘/CNI/PLEG，先不杀业务；DiskPressure 驱逐不等 5 分钟。

ssh：`systemctl status kubelet`、`df`、`free`、`dmesg`、CNI Pod、证书、PLEG。**先不杀业务进程**。时间线见 16：约 40s NotReady，约 5min 驱逐。PLEG unhealthy = kubelet 看不见容器。DiskPressure 已在 Evict 是本机压力，不等 5 分钟。

### 再追问

和 01「kubelet 挂了进程还在」？——同一类影响面。三问里进程往往还在——就是开篇那位要「对齐状态」的人踩的坑。

## Q7

**★★★★☆｜同集群有的人 403、有的通，先怀疑谁？**

**覆盖**：必会 · 常用
**对应**：知识点 [8. 必会 · 常考](知识点.md)

### 场景

CI 机器人 apply 失败 403。你用自己的 kubeconfig 是通的。有人说 API Server 挂了。

先自己试试：403 和 API 挂了差在哪？第一刀敲什么？

### 完整解答

> 🎯 **一句话**：403 用 can-i --as 复现身份差异；PSA 拒绝不是 403。

403 是鉴权，不是 API 挂了（挂了是超时 / 5xx）。`kubectl auth can-i --as=<那个身份>`。查 RoleBinding、SA、是否绑到了错的 Namespace（13）。全员不能 apply、错误像 Webhook 超时：走 03。口诀：⭐ **401 是「我不认识你」，403 是「我认识你，但你不能这么干」**。

### 再追问

PSA 拒绝是 403 吗？——不是。准入拒创建（13）。

## Q8

Q5 提过「同 NS」；这道题专门钉死调试负载放哪。

**★★★★☆｜为什么临时调试 Pod 要注意 Namespace 和权限？**

**覆盖**：必会 · 常用
**对应**：知识点 [6. 命令与操作](知识点.md) · [7. 生产排障](知识点.md)

### 场景

网络不通，有人在 default 里 `kubectl run netshoot`，测游戏 Namespace 的 Service 名解析失败，判断 DNS 坏了。

先自己试试：为什么 default 里测会误判？

### 完整解答

> 🎯 **一句话**：调试 Pod 要放问题 NS，DNS/NP 跟源 NS 走；distroless 用 debug --target。

CoreDNS 搜索域、NetworkPolicy 都跟源 Pod 的 Namespace 走。要测哪套策略，调试负载就放在哪个 NS。用完 `--rm`。不要把特权 + hostNetwork 当习惯。更准的是 `kubectl debug` 注入到问题 Pod。节点级问题才 `debug node/`。Ephemeral 不受业务 limit 管，审计会记谁注入了。

### 再追问

生产谁都能 debug 吗？——不能。受 RBAC 管。敏感环境当变更。Q11 继续拆 debug vs run。

## Q9

就是 Q4 再追问里那个坑——CPU 高 + Pending，一次重启修不了。

**★★★★☆｜CPU 很高、新 Pod 又 Pending，能不能重启一次都修好？**

**覆盖**：必会 · 常用
**对应**：知识点 [8. 必会 · 常考](知识点.md)

### 场景

活动高峰。节点 CPU 90%，新匹配 Pod Pending Insufficient cpu。有人准备重启 kubelet「清一下」。

先自己试试：两个域分别是什么？重启会怎样？

### 完整解答

> 🎯 **一句话**：CPU 高和 Pending 是两个域：top 看用量，Allocated 看 request 占满，一次重启修不了。

两个域：已有 Pod 在烧 CPU（`top` / cAdvisor），新 Pod 进不去是 request 把 Allocatable 占满（`describe node` Allocated）。一次重启修不了两件事，还会踢玩家。止血：扩节点或降非关键 request；根因再看漏设 limit、HPA 没跟上（07）。调度看 request 之和，不看瞬时空闲。

### 再追问

三问这里怎么答？——进程还在（在烧 CPU）；变更受阻（Pending）；流量可能还通。不要为了对齐状态重启。

## Q10

前面都是单点；这道题要你把整条排障口述串起来。

**★★★☆☆｜口述一次生产排障，要包含哪些步？**

**覆盖**：必会 · 常考
**对应**：知识点 [7. 生产排障](知识点.md)

### 场景

复盘会让你讲上周登录服故障。只有「我重启好了」过不了关。

先自己试试：口述七步结构，有状态先做什么？

### 完整解答

> 🎯 **一句话**：口述排障：现象→影响面→变更→三宝→止血→根因→预防；有状态先停匹配。

现象（报错、CCU、哪个 NS）→ 影响面（几条连接、是否还在对局）→ 最近变更 → 三宝结论 → 止血（undo / 扩容 / 关错误探针 / 停匹配）→ 根因 → 怎么防（监控、限流、PDB、runbook）。没有精确数字就说分钟级、量级变化，不要编。有状态先停匹配再动进程。指标发现层（18），日志对时间线（19），网络 Hubble（23）。决策树仍是五棵。

### 再追问

开服冻结窗口还在滚版本？——先停发版（15），再按树查，不要并行两个爆炸半径。

## Q11

就是 Q1 / Q8 埋的坑——debug 和 run 到底差在哪。

**★★★☆☆｜`kubectl debug` 和 `kubectl run netshoot` 怎么选？**

**覆盖**：常用
**对应**：知识点 [6. 命令与操作](知识点.md)

### 场景

distroless 业务镜像，要看它能不能解析 Redis 域名、进程卡在哪个 syscall。

先自己试试：三种场景分别用哪条命令？

### 完整解答

> 🎯 **一句话**：共享 netns/PID 用 debug --target；测 Service 用同 NS run --rm；改入口用 --copy-to。

要共享问题 Pod 的 netns / PID → `debug --target`。只要一个客户端测 Service → 同 NS `run --rm`。容器起不来、要改入口命令 → `debug --copy-to`。要看节点内核 / 磁盘 → `debug node/` 或 ssh（16）。

### 再追问

注入容器会不会把节点吃满？——可能。不受业务 limit 管。用完即走。

## Q14

把前面十多道题收成 60 秒白板——各现象一条命令定界。

**★★★★★｜口述：Pending、CrashLoop、403、NotReady 各第一刀**

**覆盖**：核心 · 必会 · 常考
**对应**：知识点 [8. 必会 · 常考](知识点.md)

### 场景

白板题：各现象一条命令定界，不说废话。

先自己试试：四条命令各写什么？

### 完整解答

> 🎯 **一句话**：Pending→describe Events；Crash→logs --previous；403→auth can-i；NotReady→kubelet 日志。

```text
Pending      → kubectl describe pod
CrashLoop    → kubectl logs --previous
403          → kubectl auth can-i
NotReady     → journalctl -u kubelet
```
