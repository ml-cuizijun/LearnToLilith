## Q1

**★★★★★｜「五种 Service 各自干什么？和 Ingress 的边界在哪？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、选门：五种 Service](知识点.md)

### 场景

新服上线评审，有人提议「每个服务单独开一个云 LoadBalancer，互相隔离更稳」，客户端组则想让玩家直连 NodePort 省掉网关。两个方案都会在账单、安全和扩缩容上翻车。

### 完整解答

> 🎯 **一句话**：对内 ClusterIP，有状态直连 Headless，对外收敛到 LB/Ingress；Ingress 不是 Service 类型。

按「谁来访问、要不要指定单个 Pod」选：

- **ClusterIP**（默认）：VIP 仅集群内可达，Pod 间互访、大厅调逻辑服用它；
- **NodePort**：每节点监听 30000-32767 的一个高端口，外部打 `节点IP:NodePort` 入——生产不留，理由见 Q11；
- **LoadBalancer**：云厂商建外部 LB，`EXTERNAL-IP` 即 LB 地址，底下仍垫着 NodePort + ClusterIP；
- **Headless**（`clusterIP: None`）：DNS A 记录直接返回 Ready Pod IP 列表，StatefulSet 用 `pod序号.svc名.ns.svc.cluster.local` 直连指定序号；
- **ExternalName**：CoreDNS 返回一条 CNAME 指向集群外域名，无 VIP、不经 kube-proxy，方向是「集群内访问外部名字」。

**Ingress / Gateway API 是七层路由对象**，需要 Ingress Controller 才生效，通常前面挂一个共享 LB——它不是第六种 Service。对外 HTTP 全部收敛到「一个 Ingress + 一个 LB」，四层用少量 NLB。

> ⚠️ **别混**：Headless 的 `CLUSTER-IP: None` 不等于「没有 Service」——照样有 selector、Endpoints 和 DNS 记录；ping 通 ClusterIP 也说明不了后端健康（IPVS 模式下 VIP 挂在 `kube-ipvs0` 上，内核自己回 ping）。

> 📝 **面试**：口径按「对内/有状态/对外」三档背：集群内互访 ClusterIP；STS 要 Pod IP、连指定序号 Headless；对外 HTTP 收敛 Ingress + 一个 LB，别每服务一个云 LB；客户端永远不直打，走网关。

### 再追问

- 「连 `mysql-0` 为什么走 ClusterIP 连不上？」——ClusterIP 只做随机负载均衡，指定序号必须走 Headless 的 `mysql-0.svc名.ns.svc.cluster.local`。**不要**用 sessionAffinity 硬凑「固定后端」，粘性解决不了指定序号。
- 「`EXTERNAL-IP` 一直 Pending 怎么办？」——`kubectl describe svc` 看 Events，多半是云配额/权限/地域不支持，去云控制台处理。**不要**反复删建 Service 碰运气，那只会一直卡在 Pending。

## Q2

**★★★★★｜「玩家全连不上，一看 Endpoints 是空的，你第一步做什么？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、立名单：Endpoints 与 EndpointSlice](知识点.md)

### 场景

开新服后登录全失败，`kubectl get ep` 返回 `<none>`。群里第一反应是「重启 kube-proxy 试试」，第二反应是「把 Service 删了重建」。

### 完整解答

> 🎯 **一句话**：名单由「selector 命中 + Ready」填；为空先对 label 和探针，不动 kube-proxy。

名单是 EndpointSlice 控制器填的：Service 的 `selector` 匹配 Pod 的 **label**，且 Pod **Ready**（readiness 过、Init 完）才写入。为空四原因按命中率排：

1. **selector 对不上**——label 差一个字母、大小写错，或把 selector 写进了 annotation；
2. **Running 但 Ready=False**——readiness 探针没过（依赖没起、启动慢）→ [04](../04-Pod生命周期/)；
3. **Init 容器没跑完**；
4. **查错了 Namespace**。

```bash
kubectl get ep,endpointslice -n game
# endpoints/logic-svc   <none>   2h        # ← 名单空：所有新连接被拒，和内核规则无关
kubectl get pods -n game --show-labels
# logic-6d5e4f-y2  0/1  Running  app=logics  # ← 多了个 s，selector 永远命不中
kubectl describe pod logic-6d5e4f-y2 -n game | grep -A5 Conditions
#   Ready  False                             # ← 探针没过，看 Events 找原因
```

名单不空仍不通才往下查：`targetPort` 写错、容器没监听、NetworkPolicy、个别节点规则没同步、CNI——刀法是先 Pod 内 `curl 127.0.0.1:targetPort`，再从别的 Pod 打 ClusterIP。

> ⚠️ **别混**：Running ≠ 进名单，条件是「被选中 + Ready」双满足；名单不是 kube-proxy 填的，重启它没用。

### 再追问

- 「Pod 明明都 Ready，Endpoints 还是空，还能查哪？」——看 EndpointSlice 是不是也空（兼容期老控制器只写 Endpoints、新 proxy 只看 Slice，两个都查）；再确认没查错 Namespace。**不要**直接改 kube-proxy 的 mode「试试」。
- 「把选择器写进 annotation 行不行？」——不行，`spec.selector` 只认 label。**不要**用 annotation 模拟 selector。

## Q3

**★★★★☆｜「从 Pod A 访问一个 Service，到请求落在后端 Pod，完整讲一遍路径。」**

**覆盖**：核心 · 常考 ｜ **对应**：知识点 [一、一张图：一次访问 Service 的请求的一生](知识点.md)

### 场景

白板题。候选人说「请求先到 kube-proxy 进程，由它挑一个 Pod 转发」——把控制面当成了数据面，整题的分就没了。

### 完整解答

> 🎯 **一句话**：名字 → VIP → 内核 DNAT → Pod；包不进 kube-proxy，回程靠 conntrack。

四段：① CoreDNS 把 `svc.ns.svc.cluster.local` 解析成 **VIP**（ClusterIP）；② 包进入**本节点内核**，nat 表 `KUBE-SERVICES` 链命中 `VIP:port`，跳进 `KUBE-SVC-*` 链按概率随机选后端，`KUBE-SEP-*` 链执行 **DNAT** 把目的地改成 `Pod IP:targetPort`；③ 若后端在别的节点，由 CNI 负责跨节点送达（→ [10](../10-CNI与网络策略/)）；④ 回程按 **conntrack** 条目反向还原，客户端全程只看见 VIP。

kube-proxy 全程不在数据路径上：它只是 watch API、把名单翻译成上面这些内核规则的 DaemonSet。一个旁证：`kubectl get` 能用但 `kubectl exec` 不行，问题在 API Server → kubelet 那条路（→ [03](../03-API-Server/)），根本不在 Service 转发链路上。

> 📝 **面试**：按「名字、名单、内核规则、后端」四段讲，强调两个「不」：包不进 kube-proxy 进程，Service 对象不做健康检查。

### 再追问

- 「ping 得通 ClusterIP，能说明服务正常吗？」——不能：IPVS 模式 VIP 挂 `kube-ipvs0`，内核自己回 ping；判断健康用 `get endpoints` + 业务探针。**不要**拿 ping 当健康检查。
- 「`port` 和 `targetPort` 不一致会怎样？」——客户端拨的是 `port`，DNAT 落点是 `targetPort`；写错表现为「连得上但拒接/超时」。**不要**靠改防火墙猜，先 `get svc` 对端口。

## Q4

**★★★★★｜「iptables 和 IPVS 模式有什么区别？nftables 呢？什么时候该切？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、写规则的人：kube-proxy 三种模式](知识点.md)

### 场景

集群几千个 Service，每次滚动发布 kube-proxy CPU 飙升、新 Pod 生效慢。有人提议「给 kube-proxy 加 8 核」，有人说「直接全集群切 IPVS，就现在」。

### 完整解答

> 🎯 **一句话**：三种模式包都不出内核；差别是规则怎么存——链式 O(n) 全量重写、哈希 O(1) 增量、集合元素更新。

| 维度 | iptables | IPVS | nftables |
|------|----------|------|----------|
| 查找 | 链式顺序匹配，O(n) | 哈希，O(1) | 集合（set），O(1) |
| 端点变更 | 全量重写 KUBE-* 规则 | 增量增删后端 | 只更新集合元素 |
| 前置 | 无（默认） | `ip_vs` 系列模块 | 较新版本（1.31 试用、1.33 成熟） |
| 观察 | `iptables-save` | `ipvsadm -Ln` / `kube-ipvs0` | `nft list ruleset` |

切 IPVS 的 SOP：

```bash
lsmod | grep ip_vs || modprobe ip_vs ip_vs_rr ip_vs_wrr ip_vs_sh
# ↑ 模块没加载，切了模式规则也建不起来——切换失败第一查这里   # ←
kubectl -n kube-system edit cm kube-proxy        # mode: "ipvs"；MetalLB 场景加 strictARP: true
kubectl -n kube-system rollout restart ds kube-proxy
ipvsadm -Ln | head -5                            # 每节点验证，空白 = 没切成功
```

触发条件：Service/Endpoint 规模上千、滚动时规则更新明显滞后。**给 kube-proxy 加 CPU 救不了数据面**——包不经过它，瓶颈在「全量重写规则」这个组织方式上。userspace 模式（包真进过进程）已废弃，提一句即可。

> 📝 **面试**：口径——「三种模式的包都不出内核、不进 kube-proxy 进程，区别只在规则怎么存、怎么更新；大集群从顺序匹配换哈希/集合，换的是查找和更新成本」。

### 再追问

- 「切完 `ipvsadm` 还是空的，为什么？」——八成是 `ip_vs` 模块没加载，或该节点 kube-proxy 没重启到（`rollout status` 看）。**不要**在活动高峰全集群一把切，先低峰、非关键节点池灰度。
- 「IPVS 调度算法怎么选？」——默认 rr，长连接业务可评估 lc（最少连接）；但游戏房间负载天然不均，**不要**指望换算法解决分布问题，那是业务层的事。

## Q5

**★★★★★｜「某节点 kube-proxy 挂了，存量长连接和新登录分别会怎样？你怎么处理？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、写规则的人：kube-proxy 三种模式](知识点.md)

### 场景

监控报某节点 kube-proxy 进程不在，战斗服正跑在该节点上。有人主张「先重启这台的战斗服，长痛不如短痛」——这会把还活着的几千条战斗连接主动掐断。

### 完整解答

> 🎯 **一句话**：规则在内核里，存量长连接基本照旧；坏的是新连接和滚动同步；先拉 proxy，别杀业务。

拆开看：转发规则写在**每个节点的内核**里，不依赖进程存活；存量连接走 **conntrack** 条目，不重新查规则。所以：

| 状态 | 存量长连接 | 新连接 / 滚动之后 |
|------|-----------|-------------------|
| 进程挂、规则还在 | 基本照旧（conntrack 在） | 新后端进不来；摘除的后端规则还留着 |
| 名单变了规则没同步 | 继续打旧 Pod | 新连接可能打中已删 Pod |

处置顺序：**先拉起 kube-proxy**（看该节点 proxy Pod 状态/日志，比对 EndpointSlice 与本机 `ipvsadm -Ln`/`iptables-save`），**不要动游戏进程**——重启业务会把「局部规则滞后」升级成「全员掉线」。用 Cilium eBPF 替换的集群，agent 挂掉的影响面与「规则不更新」同类（→ [25](../25-eBPF与Cilium/)）。

> 📝 **面试**：「存量靠内核规则 + conntrack 兜着，受影响的是增量和同步；先拉 kube-proxy，别重启业务进程。」

### 再追问

- 「Endpoints 已经摘了旧 Pod，但某节点规则没同步，新连接会打到哪？」——会按旧规则打中已删除的 Pod（连接被拒/重置）。验证：该节点 `ipvsadm -Ln` 与 Slice 比对。**不要**误判成「CNI 全挂了」去回滚发布。
- 「怎么确认这台节点的规则确实滞后了？」——登节点 `ipvsadm -Ln | grep <VIP>`（或 `iptables-save | grep <VIP>`），后端列表比 Slice 旧即滞后。**不要**只看 kube-proxy 日志不下节点。

## Q6

**★★★★★｜「滚动发布时玩家连到了旧 Pod，日志一堆 502，为什么？怎么防？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、摘流：与发布的赛跑](知识点.md)

### 场景

发版后几分钟内登录失败率飙升，网关日志显示请求打到了 Terminating 的旧 Pod。有人提议「把 `maxUnavailable` 设成 0 就无感了」。

### 完整解答

> 🎯 **一句话**：删 Pod 的瞬间，名单摘除和各节点规则同步在赛跑；窗口内新连接按旧规则打中旧 Pod。

两条并行时间线：① 控制器删 Pod → EndpointSlice 立刻移除旧 IP → **各节点** kube-proxy 异步更新内核规则（数十毫秒~秒级）；② 同一时刻 kubelet 走 preStop → SIGTERM → 优雅退出。规则还没跟上的节点，新连接仍会 DNAT 到正在退出的旧 Pod——这就是 502 窗口。

防护三件套：

1. **readiness 探针反映真实可服务能力**，让旧 Pod 先从名单摘除（时序 → [04](../04-Pod生命周期/)）；
2. **`preStop: sleep 5-15s`**，给规则同步争取时间；
3. **`terminationGracePeriodSeconds` 足够长**，覆盖存档、断连通知、房间移交。

三个补充口径：`maxUnavailable=0` 只保副本数，**不保证数据面摘干净**（→ [05](../05-工作负载控制器/)）；Service 对象本身不等容器；存量长连接摘流摘不掉，游戏战斗连接靠业务主动断开/迁移。对外服务还要叠加云 LB 健康检查的摘除延迟。

> ⚠️ **别混**：「摘流」摘的是新连接的去向，不是掐断已有连接；把两件事混在一起，处方就会开错。

### 再追问

- 「为什么开了 `sessionAffinity: ClientIP` 反而更容易连到旧 Pod？」——粘性让同源新连接持续选中旧后端，滚动时把人粘在将死的 Pod 上。**不要**用粘性当「防掉线」手段。
- 「preStop 里只放一个业务存档脚本，不 sleep，行吗？」——不行，脚本跑完就进 SIGTERM，规则同步窗口照样裸奔；存档要放，sleep 也要放。**不要**把「业务收尾」和「等规则同步」混成一步。

## Q7

**★★★★☆｜「活动高峰新连接随机超时，老连接都没事，Endpoints 也正常，查什么？」**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [七、作战：定责](知识点.md)

### 场景

高峰时段网关侧新登录间歇失败，有人按「Endpoints 为空」的思路查了半天名单，又有人准备重启 kube-proxy——名单和规则其实都没问题。

### 完整解答

> 🎯 **一句话**：查 conntrack 表满——`dmesg` 找 `table full`，`count/max` 看水位。

现象指纹：**间歇**失败 + **老连接无恙** + 名单正常 = 账本层。conntrack 表（默认上限常见 65536，按内存浮动）打满时，**新连接建不了条目**被丢包，已有连接按旧条目照走。实锤命令：

```bash
dmesg | grep -i conntrack
# nf_conntrack: table full, dropping packet   # ← 有这行就是表满，不用猜
cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
# 260113  262144                              # ← count 贴住 max，水位 >80% 就该告警
```

处方：`sysctl -w net.netfilter.nf_conntrack_max=262144` 先止血，再查为什么涨（连接泄漏、TIMEOUT 与游戏长连接空闲时间不匹配），把 `nf_conntrack_max` 和超时一起调。机制细节 → [01-17](../../01-基础底座/17-iptables与conntrack/)。

> ⚠️ **别混**：conntrack 表满（后端都在、间歇失败）≠ Endpoints 为空（名单没人、一律失败）——一个查账本，一个查名单。

### 再追问

- 「为什么老连接完全不受影响？」——它们已有 conntrack 条目（存根），不再新建。**不要**因此误判「网络没问题」——只是存量没暴露。
- 「只调大 max 就完了吗？」——不行，泄漏不查迟早再满，还要按业务空闲时长调 TIMEOUT。**不要**把调参当根治。

## Q8

**★★★★☆｜「部分节点上访问某 Service 不通，其他节点正常，可能是什么？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：定责](知识点.md)

### 场景

某可用区的玩家登录全失败，其他区正常。有人直接喊「发布有问题，回滚」——回滚完故障还在，因为坏的是某个节点的规则。

### 完整解答

> 🎯 **一句话**：每节点一套内核规则；部分节点不通，先比对该节点的规则与 EndpointSlice。

「部分节点」这个现象已经把责任劈到**该节点的数据面**：

1. **规则没同步**——登该节点 `ipvsadm -Ln | grep <VIP>`（或 `iptables-save | grep <VIP>`），后端列表与 EndpointSlice 比对；滞后说明该节点 kube-proxy 有问题（挂了/没重启到/被 iptables 规则冲突挡住），先拉起来；
2. **打中已删 Pod**——滚动窗口 + 该节点规则滞后（五节）；
3. **跨节点通路**——同节点内访问通、跨节点不通，矛盾指向 CNI 而非 kube-proxy（→ [10](../10-CNI与网络策略/)）。

> 📝 **面试**：「全节点不通查名单和后端，部分节点不通查该节点规则」——两句把排障树劈开。

### 再追问

- 「怎么区分是 kube-proxy 的锅还是 CNI 的锅？」——规则与 Slice 一致但仍不通，且同节点互通、跨节点不通，是 CNI/路由问题；规则对不上才是 proxy。**不要**一上来就重启 kube-proxy，先比对。
- 「该节点 kube-proxy 进程确实挂了，下一步？」——先拉起它，观察规则是否追上；期间**不要**重启该节点上的游戏进程，存量连接本来还活着。

## Q9

**★★★★☆｜「游戏网关要拿玩家真实源 IP 做风控，应该怎么配？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、选门：五种 Service](知识点.md)

### 场景

风控要真实玩家 IP。有人把七层 Ingress 的 `X-Forwarded-For` 当成四层入口的解药，也有人直接全集群改 `externalTrafficPolicy: Local` 后收到「部分玩家直接连不上」的报障。

### 完整解答

> 🎯 **一句话**：四层入口用云 NLB + `externalTrafficPolicy: Local`，同时保证空节点被 LB 摘除。

| 维度 | Cluster（默认） | Local |
|------|----------------|-------|
| 源 IP | SNAT 成节点 IP，真实玩家 IP 丢 | 保留真实客户端 IP |
| 分发 | 可跨节点二跳 | 只发本节点上的 Pod |
| 空节点 | 照常收、二跳转发 | 直接丢包（黑洞） |

选 Local 的代价：没有该后端 Pod 的节点会变成黑洞，必须靠云 LB 的健康检查把空节点摘掉，或保证每节点都有副本。集群内流量想省东西向一跳，用 **internalTrafficPolicy: Local**（同款思路，副本不足时不通）。七层入口的真实客户端 IP 是另一条路：Proxy Protocol / X-Forwarded-For → [15](../15-Ingress与流量管理/)。

> ⚠️ **别混**：externalTrafficPolicy 作用在 kube-proxy 写规则这一层（NodePort/LoadBalancer），管不到七层反代；「四层保源 IP」和「七层透传 IP」是两套机制。

### 再追问

- 「改成 Local 后为什么有玩家直接超时？」——落到了没有后端 Pod 的空节点被丢包。**不要**只改策略不配健康检查摘除，顺序反了就是线上事故。
- 「ClusterIP 类型的服务也想只走本节点，改 externalTrafficPolicy 吗？」——那是 `internalTrafficPolicy`，注意别混用字段。**不要**拿 external 的字段管集群内流量。

## Q10

**★★★☆☆｜「EndpointSlice 和 Endpoints 是什么关系？为什么要搞分片？」**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [三、立名单：Endpoints 与 EndpointSlice](知识点.md)

### 场景

集群升级后出现诡异现象：`kubectl get ep` 显示有地址，服务却不通。有人怀疑是缓存，反复重启 kube-proxy 无效。

### 完整解答

> 🎯 **一句话**：Slice 是 Endpoints 的分片版（每片默认 ≤100 端点）；kube-proxy 默认 watch Slice。

Endpoints 是单一对象：服务越大对象越大，一次端点变化要整体重写、整体推送给所有 watcher——大集群下 etcd 写放大、watch 风暴。EndpointSlice 把名单切成每片默认 **100** 个端点的小对象，变化只动受影响的片。kube-proxy 新版本默认 watch 的是 Slice。

升级题的坑在**兼容**：老控制器只写 Endpoints、新 kube-proxy 只看 Slice（或反过来），于是「get ep 有地址、服务不通」。排障时 `get ep` 和 `get endpointslice -l kubernetes.io/service-name=<svc>` 两个都查，再看控制器版本。

### 再追问

- 「只看 Endpoints 有地址能下结论吗？」——不能，要以 kube-proxy 实际 watch 的 Slice 为准。**不要**拿旧对象的健康代替新对象。
- 「为什么每片上限是 100 这种『小』数？」——为了把单对象写放大和 watch 推送控制住，片数多是廉价的。**不要**为了减少片数去调大上限而不评估 etcd 压力。

## Q11

**★★★★☆｜「玩家客户端在集群外，流量怎么进来？NodePort 有什么坑？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [二、选门：五种 Service](知识点.md)

### 场景

客户端组想直连战斗服端口，方案是「每个游戏服开一个 NodePort，安全组把 30000-32767 全放开」。上线后安全扫描告警一片，扩容节点后玩家连接配置全失效。

### 完整解答

> 🎯 **一句话**：对外收敛到 LoadBalancer/Ingress；NodePort 三大坑，只留调试不进生产。

集群外进来的正规路径：**LoadBalancer**（四层云 LB，游戏长连接首选，配 Local 保源 IP）和 **Ingress**（HTTP(S) 收敛，前面挂一个共享 LB）。NodePort 只是「每个节点开个 30000-32767 的高端口」，三大坑：

- **一服务占一口**：全集群共用 ~2700 个端口，服务多了分配撞车；
- **安全组难收敛**：要开整段范围，暴露面大；玩家直连 = 把节点 IP 暴露给客户端；
- **拓扑外泄**：节点扩缩容后客户端手里的地址作废；默认 `Cluster` 策略还可能跨节点二跳 + SNAT，源 IP 丢失。

> 📝 **面试**：「生产对外用 LB/Ingress 收敛，NodePort 只用于临时调试」——再补一句「客户端永远不直打节点」。

### 再追问

- 「为什么玩家客户端不能直连 NodePort？」——节点 IP 暴露给客户端、扩缩容地址失效、安全组口子收不住。**不要**用「扩一下端口范围」来缓解，坑在架构不在范围。
- 「NodePort 和 LoadBalancer 是什么关系？」——LB 底下垫着 NodePort + ClusterIP，LB 只是替你把入口收敛到云负载均衡。**不要**以为用了 LB 就没有 NodePort 层。

## Q12

**★★★★☆｜「`sessionAffinity: ClientIP` 是干什么的？能保证游戏长连接滚动不掉吗？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [四、内核转发：DNAT、conntrack、粘性](知识点.md)

### 场景

有人为了「滚动发布不掉线」给大厅服务开了 `sessionAffinity: ClientIP`，发布后反而出现同一玩家反复连到旧 Pod、登录卡住。

### 完整解答

> 🎯 **一句话**：它管「新连接粘哪个后端」（默认 10800s）；长连接稳定靠 conntrack，粘性滚动时帮倒忙。

机制：`sessionAffinity: ClientIP` 让同一源 IP 的**新连接**在超时（默认 **10800s**）内选中同一后端，四层粘性、作用在规则层。游戏长连接的稳定性来自另一套：**conntrack** 条目——第一个包 DNAT 后记账，后续包按存根走，不重新抽后端。所以：

- 存量战斗连接在滚动中不断，是 conntrack 的功劳，不是 sessionAffinity；
- 开了粘性，滚动时玩家新连接反而持续粘在将死的旧 Pod 上；
- 房间归属本来就由业务自己绑（连上某个后端后状态都在那条连接里）。

> ⚠️ **别混**：sessionAffinity = 新连接的**选路粘性**；conntrack = 已有连接的**状态**。前者滚动时是负资产，后者才是长连接的保命符。

### 再追问

- 「旧 Pod 都从名单摘了，为什么还有玩家打它？」——conntrack 存根还在 + 粘性可能叠加，直到旧 Pod 真退出。**不要**靠「摘名单」去断存量连接，要业务主动迁移。
- 「哪些场景才真的需要 sessionAffinity？」——无状态但依赖本地缓存的短连接场景；游戏长连接场景基本不需要。**不要**把它当通用「防抖」开关。

## Q13

**★★★☆☆｜「上了 Service Mesh 或 Cilium，还需要 kube-proxy 吗？」**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [五、写规则的人：kube-proxy 三种模式](知识点.md)

### 场景

Mesh 改造项目里有人说「kube-proxy 太慢了，先给它加到 8 核 16G」；另一人说「反正要换 Cilium，kube-proxy 挂不挂无所谓了」。

### 完整解答

> 🎯 **一句话**：它们替换的是「写规则的人」，不是「规则要干的事」；加 CPU 给 proxy 永远不会让数据面变快。

分两条线：

- **Service Mesh**：sidecar（Envoy）拦截服务间流量，可以直接按服务发现连 Pod IP，绕过 ClusterIP 的 DNAT 路径——那是另一套数据面（→ [24](../24-ServiceMesh-Istio与Envoy/)）。
- **Cilium**：用 eBPF 在内核实现 Service 转发，替代 kube-proxy 写 iptables/IPVS 规则（→ [25](../25-eBPF与Cilium/)）。

两个口径：① **给 kube-proxy 加 CPU 没用**——包不经过它的进程，瓶颈在规则组织方式（模式）和账本（conntrack），不在算力；② 替换后「名单变了要有人更新数据面」这件事没消失：Cilium agent 挂了，影响面与「规则不更新」同类——存量照旧、增量失效。

### 再追问

- 「换成 Cilium 后，节点上 agent 挂了，现象是什么？」——存量连接靠内核已有映射照走，新后端/摘除不生效，滚动窗口打旧 Pod。**不要**以为「没有 kube-proxy 就没有这类故障」。
- 「Mesh 直连 Pod IP，还需要 Endpoints 那套吗？」——Mesh 用自己的服务发现（注册/istiod 下发），但集群内非 Mesh 流量仍走 Service。**不要**假设 Mesh 覆盖了全部东西向流量。

## Q14

**★★★★★｜Service 有 EP 但不通、部分节点不通、长连接掉线，60 秒分流**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [八、作战：定责](知识点.md)

### 场景

支付回调 502；只有 AZ-B 节点访问 `ClusterIP` 超时；发版时长连接全断。

### 完整解答

> 🎯 **一句话**：EP 空→selector；部分节点→kube-proxy/CNI；长连接→滚动+grace；源 IP→externalTrafficPolicy。

```text
0–10s   kubectl get svc,ep,endpointslices -n prod
10–30s  EP 空 → 查 selector 与 Pod labels/readiness
        EP 有 → 从故障节点 curl ClusterIP:port
30–60s  节点差 → kube-proxy pod / iptables-nft 模式
        长连接 → 发布策略 + preStop（04、16）
```

```bash
kubectl get endpointslices -n prod -l kubernetes.io/service-name=pay -o yaml
kubectl logs -n kube-system -l k8s-app=kube-proxy --field-selector spec.nodeName=<node>
```

> 📝 **面试**：玩家的包**经过** kube-proxy（或 Cilium 替代）；**不是**直连 Pod IP 进集群。

### 再追问

Headless Service 和 ClusterIP 在 StatefulSet 里各干什么？——Headless 给稳定 DNS 名；ClusterIP 做负载均衡（09）。
