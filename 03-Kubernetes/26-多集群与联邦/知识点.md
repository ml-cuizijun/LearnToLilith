# 多集群与联邦

> 大家好，欢迎来到这次分享。开讲之前，先带大家回到一个很多值班同学都经历过的现场：
> 国服活动模板要同步到东南亚，有人直接 `kubectl --context=sea apply` 同一套 YAML，结果 `StorageClass` 名对不上、镜像拉取 Secret 过期、战斗服 `nodeSelector` 指向了不存在的机型——群里在吵「上 Karmada 还是 Argo 多集群」，没人说得清 **一次变更到底要经过哪几步才算落地**。手已经伸向下一轮全量 apply。
> 这一章讲完，你会知道当时那个人错在哪，以及卡住时该先问「没下发、没落地、还是流量没来」。
> **本章回答**：一次跨集群变更的一生——为什么拆多集群、GitOps 与 Karmada/fleet 各管哪段、配置如何保持一致、流量怎么跨集群、游戏多区服怎么挂在这条主线上。
> **不讲**：单集群 Service / Ingress → [08](../08-Service与kube-proxy/) · [15](../15-Ingress与流量管理/)；GitOps 单集群细节 → [23](../23-GitOps-ArgoCD与Tekton/)；证书与 kubeconfig context → [14](../14-证书与kubeconfig/)；全球 DNS 与 CDN → [01-15](../../01-基础底座/15-DNS与CDN/)；游戏分区架构 → [07-01](../../07-游戏运维专题/01-游戏服务器架构/)。这些都有专门的章节，本章只在用到时点到为止。

**标记**：🎯重点 · 🔥难点 · ⭐常考 · 🔧实操

**怎么听这场分享**：咱们先看第一节的主图，把「一次跨集群变更的一生」装进脑子；第二到第六节顺着动机 → 意图分发 → 一致性 → 流量 → 游戏区服往下走；作战节专门讲定责，也就是开头那个现场的正确解法。每一节讲完都会提示对应练习题，学完就去练。

## 一、一张图：一次跨集群变更的一生

> 🎯 **一句话**：跨集群变更走六段——意图声明 → 分发（GitOps/Karmada）→ 各集群准入 → 落地差异修正 → 健康与流量切换 → 回滚/对账；卡住必在其中一段。

咱们先不急着选 Karmada 还是 Argo。学多集群最怕的就是「同一套 YAML 到处 apply」。先看图，把六段装进脑子里：

```mermaid
flowchart LR
    I["① 意图<br/>Git / Karmada 模板"] --> D["② 分发<br/>Argo CD ApplicationSet / PropagationPolicy"]
    D --> A["③ 各集群 API<br/>准入 · 配额 · CRD 版本"]
    A --> L["④ 落地<br/>镜像 · SC · 节点标签差异"]
    L --> H["⑤ 验证<br/>健康检查 · 合成监控"]
    H --> T["⑥ 流量<br/>DNS/GSLB · MCS/Submariner"]
    T -.->|失败| R["回滚<br/>Git revert / Override"]
    R -.-> I
```

**读图**：带着三个问题看这张图，比吵产品名有用得多：**控制面（谁下发期望状态）** 与 **数据面（玩家连哪）** 分开想。GitOps/Karmada 解决「多个 API Server 收到同一份或派生后的对象」；DNS/GSLB（全局负载均衡）解决「玩家进哪个区」。排障先问：是 **没下发**、**下发了没落地**、还是 **落地了流量没来**。

> 💡 **打个比方**：多集群像连锁门店——总部菜单（Git）要发到各店，但华东店没有「麻辣锅底」（StorageClass），得用 **Override（覆盖）** 换本地等价物；开业（切流量）前各店自检，不能总部一按键全国同时开火。

## 二、动机：为什么要多集群

> 🎯 **一句话**：拆集群是为了 **故障域、合规、地域延迟、团队边界、升级节奏**——不是为了简历上的「联邦」二字。

### 常见驱动力 ⭐

1. **故障域隔离**：活动服炸在 A 集群，B 集群大厅仍可用——单集群 etcd/control plane 挂了是「全服不能变更」，多集群把爆炸半径切开（见 [02](../02-etcd/) 影响面）。
2. **地域与合规**：国服、东南亚、欧美 **数据驻留** 要求物理或逻辑隔离；玩家就近接入靠地域集群 + [01-15](../../01-基础底座/15-DNS与CDN/) GSLB。
3. **团队与租户**：平台组管 `platform` 集群，游戏线管 `game-cn` / `game-sea`，RBAC 与变更窗口分离（[13](../13-RBAC与安全/)）。
4. **版本与风险**：金丝雀集群先升 K8s 1.30，全量集群滞后两周（[17](../17-节点运行时与升级/)）。
5. **规模天花板**：单集群节点/Pod 上限、etcd 对象数、API QPS——到了再拆，不是第一天就拆。

| 对比 | **单集群多命名空间** | **多集群** |
|------|----------------------|------------|
| 隔离强度 | 软隔离（RBAC/NP） | 硬隔离（独立控制面） |
| 运维成本 | 低 | 高（N 倍控制面 + 对账） |
| 跨区延迟 | 不适用 | 每区一套数据面 |
| 典型场景 | 中小团队 | 多地域、多合规域、大规模 |

> 📝 **面试**：「多集群首要动机是故障域和合规，不是 kube-apiserver 性能不够；能单集群 ns 隔离就别急着多集群。」

## 三、出生：意图从哪来——GitOps 与 Karmada

🔥 群里吵「上 Karmada 还是 Argo」——**高频错答是先选产品**。大白话：**GitOps 管「期望从 Git 同步到集群」；Karmada 管「一份模板派生到多集群并 Override」**。口诀：**「先分清管哪段，再选工具」**（练习题 Q3、Q4）。⭐ 面试必考。

> 🎯 **一句话**：**GitOps（Git 为唯一事实源，控制器自动同步）** 管「发什么」；**Karmada（开源多集群编排，CNCF 孵化）** / **GKE Fleet（谷歌多集群舰队）** 管「发到哪些集群、怎么差异化」。

### GitOps 多目标 🔧⭐

[23](../23-GitOps-ArgoCD与Tekton/) 单集群用 `Application`；多集群用 **ApplicationSet（应用集，按集群列表/generator 批量生成 Application）**：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: lobby-all-clusters
  namespace: argocd
spec:
  generators:
  - list:
      elements:
      - cluster: cn-prod
        url: https://api.cn.example.com:6443
      - cluster: sea-prod
        url: https://api.sea.example.com:6443
  template:
    metadata:
      name: 'lobby-{{cluster}}'
    spec:
      project: game
      source:
        repoURL: https://git.example.com/game-k8s.git
        path: overlays/{{cluster}}/lobby
        targetRevision: main
      destination:
        server: '{{url}}'
        namespace: game
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

**读图**：**一个 Git 仓、多套 overlay（Kustomize 按集群覆盖）** 是主流——不是 twelve 份复制粘贴。`prune: true` 删 Git 里已删的对象，多集群误删会 **同时删所有区**，变更要走 MR + 审批。

```bash
argocd app list | grep lobby
# lobby-cn-prod   Synced   Healthy
# lobby-sea-prod  OutOfSync Degraded   ← 先看 sea 集群差异，别急着改 cn
kubectl config get-contexts
# 多集群 kubeconfig 见 [14]；值班先确认 current-context
```

### Karmada：联邦式控制面 🔥⭐

Karmada 在 **Host 集群** 跑统一 API，用户提交 **PropagationPolicy（传播策略，声明资源要发到哪些成员集群）**：

```yaml
apiVersion: policy.karmada.io/v1alpha1
kind: PropagationPolicy
metadata:
  name: lobby-propagation
  namespace: game
spec:
  resourceSelectors:
  - apiVersion: apps/v1
    kind: Deployment
    name: lobby
  placement:
    clusterAffinity:
      labelSelector:
        matchLabels:
          region: ap
    replicaScheduling:
      replicaDivisionPreference: Weighted
      weightPreference:
        staticWeightList:
        - targetCluster:
            clusterName: sea-prod
          weight: 60
        - targetCluster:
            clusterName: cn-prod
          weight: 40
```

**读图**：Host 上的 `Deployment` 是 **模板**，Karmada 控制器在各 **Member 集群** 生成真实 workload。**OverridePolicy（覆盖策略）** 改成员集群差异——如 `imagePullSecrets` 名、`replicas`、`nodeSelector`。

| 对比 | **GitOps 多 Application** | **Karmada PropagationPolicy** |
|------|---------------------------|-------------------------------|
| 控制面 | 每集群仍独立 API | Host 统一提交，再分发 |
| 差异 | Kustomize overlay / Helm values | OverridePolicy |
| 适合 | 团队已深度 Argo、集群异构大 | 要统一 API、多集群调度副本 |
| 风险 | Argo 挂了各集群仍跑旧状态 | Host 挂了无法下发新变更 |

**GKE Fleet** 是云厂商托管的类似思路：舰队 Hub 注册集群、统一策略（Config Sync、Policy Controller）——面试知道「Fleet = 谷歌版多集群治理面」即可，原理与 Karmada 同类。

> ⚠️ **别混**：**Karmada ≠ 旧版 kube Federation v2 的直接替代品名词**——面试说「多集群编排」指 Karmada/Fleet/ApplicationSet 这一代；**不要背联邦 v1 CRD**（综合练习也写明不背）。

## 四、同步：配置一致性怎么保

> 🎯 **一句话**：**没有银弹**——靠 Git 评审 + 自动化对账 + 集群级 override + CRD/版本矩阵，接受「结构一致、参数因地而异」。

### 必须一致的 vs 允许不同的 ⭐

**应一致（结构层）**：
- Deployment 模板、探针语义、HPA 行为、NetworkPolicy 逻辑
- 镜像 **tag 策略**（如都跟踪 `release-662.0`，不是每区乱 tag）

**必须不同（落地层）**：
- `StorageClass` 名、LB annotation、镜像仓库地域副本
- `replicas`（SEA 玩家少）、`resources`（机型不同）
- `ConfigMap` 里的区服 ID、Redis 地址、时区

```yaml
# overlays/sea-prod/kustomization.yaml
resources:
- ../../base/lobby
patches:
- patch: |-
    - op: replace
      path: /spec/replicas
      value: 20
- patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources/limits/memory
      value: 2Gi
```

### 对账与漂移 🔧

```bash
# GitOps 对账
argocd app diff lobby-sea-prod
# 显示 live vs desired

# 多集群同一对象是否同 revision（概念上）
kubectl --context=cn-prod get deploy lobby -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | shasum
kubectl --context=sea-prod get deploy lobby -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | shasum
# 哈希不同未必是事故——overlay 本就不同；要比的是「是否符合 Git」
```

**Config Management Template（配置管理模板）** 实践：base 只放与地域无关部分；每区 `config.env` 进 Kustomize `configMapGenerator`；**禁止** ssh 进集群 `kubectl edit` 改生产——改了就是漂移，下次 sync 被 Argo 打回或永远 OutOfSync。

> 📝 **面试**：「一致性靠 Git 单源 + Kustomize/Helm 参数化 + CI 渲染检查；允许 replica/SC/LB 不同，不允许 hand-edit 线上。」

### CRD 与版本矩阵 🔥

多集群最大坑：**集群 A 已装 Istio 1.22 CRD，集群 B 还是 1.20**——同一份 YAML apply 到 B 失败。矩阵表要维护：

```text
组件          cn-prod   sea-prod   备注
K8s           1.29      1.29
Istio         1.22      1.20       ← sea 滞后，VS API 字段不同
Argo CD       2.10      2.10
```

升级顺序：**先金丝雀集群验证 CRD 变更，再推广**（与 [17](../17-节点运行时与升级/) 同节奏）。

## 五、联通：跨集群流量与服务发现

> 🎯 **一句话**：跨集群 **服务调用** 靠 **MCS（Multi-Cluster Services API，多集群服务 API）** / **Submariner** / **云厂商全球 Service Mesh** / **显式网关**——不要假设 ClusterIP 能跨集群魔法互通。

### 玩家流量 vs 服务流量 ⭐

```mermaid
flowchart TB
    P["玩家"] --> DNS["GSLB / GeoDNS<br/>01-15"]
    DNS --> CN["cn Ingress / LB"]
    DNS --> SEA["sea Ingress / LB"]
    CN --> PodCN["cn 集群 Pod"]
    SEA --> PodSEA["sea 集群 Pod"]
    PodCN -.->|"跨区后台 API"| GW["east-west 网关 / MCS"]
    GW -.-> PodSEA
```

**读图**：**南北向**（玩家）用 DNS 分到最近区；**东西向**（集群互调）默认 **不通**——要建专线/VPN、ServiceExport/Import，或统一走 **API 网关 + 公网/专线 URL**。战斗服调「全球排行」若硬编码对端 ClusterIP，跨集群必挂。

### MCS 与 Submariner（知道机制）

**MCS API**（`net.kubernetes.io/serviceexport` / `serviceimport`）：
- 在源集群 **Export** 一个 Service
- 目标集群出现 **Import 的 ClusterSet IP**，DNS 形如 `my-svc.my-ns.svc.clusterset.local`
- 实现依赖 **ClusterSet 实现**（GKE Fleet MCS、Submariner、Cilium Cluster Mesh）

**Submariner** 用隧道把多集群 Pod CIDR 拉通，配合 Lighthouse 做 DNS——运维要维护 **Pod/Service CIDR 不重叠**（与 [10](../10-CNI与网络策略/) 规划一体）。

> 🔍 **现场**：跨集群调不通先查 CIDR 与 DNS。

```bash
kubectl --context=cn-prod get serviceexports -A
kubectl --context=sea-prod get serviceimports -A
# Export 没有 / Import 没有 Endpoints → 控制面未同步
kubectl --context=sea-prod get endpointslices -n game imported-svc -o yaml
# 应看到源集群后端 IP；空 = 隧道或 MCS agent 问题
```

| 对比 | **GSLB 分玩家** | **MCS/Submariner 互调** |
|------|-----------------|-------------------------|
| 对象 | 外部用户 | 集群间 Service |
| 典型 | 国服/SEA 入口 | 跨区排行榜、合服后台 |
| 失败现象 | 解析到错误区 | ClusterIP 不可达 / 无 Endpoints |

> ⚠️ **别混**：**多集群复制 Deployment ≠ 跨集群 Service 自动发现**——Karmada 复制了 Pod，玩家仍要 DNS 切到对应区；后台互调还要 MCS 或网关。

### 安全与密钥：每区独立

- **镜像拉取 Secret**：cn 用阿里云 ACR token，sea 用 GCR/ECR——**不能**把 cn 的 `dockerconfigjson` 复制到 sea。
- **TLS 证书**：Ingress 证书按区域域名签发（`cn.example.com` vs `sea.example.com`），见 [14](../14-证书与kubeconfig/) 与 [15](../15-Ingress与流量管理/)。
- **RBAC**：Argo CD 对每集群用 **不同 ServiceAccount token**，最小权限；一个 token 泄漏不应能删所有集群。

```bash
kubectl --context=sea-prod get secret -n game | grep pull
# sea-acr-pull   kubernetes.io/dockerconfigjson
# 若只有 cn-acr-pull → overlay 漏了 patch
```

### 变更窗口与 blast radius（爆炸半径）

跨集群 **同一 MR 合并** 不等于 **同一时刻生效**——用 Argo **sync wave** 或 Pipeline 阶段：

```text
wave 0：cn-staging 验证
wave 1：sea-staging
wave 2：cn-prod（国服活动前低峰）
wave 3：sea-prod（观察 30min 无告警再 sync）
```

Karmada 侧用 **PropagationPolicy 的 cluster affinity** 先选金丝雀成员。回滚 = **Git revert + 各集群 sync**，不是只回滚一个区留下永久 skew。

> 🔍 **现场**：活动前 24h 冻结 **PropagationPolicy / ApplicationSet** 变更，只允许热修分支；防止「全球同时滚 Deployment」与游戏服自己的活动开关冲突。

| 合服/跨服 | 数据 merge + DNS 权重 | 仅 kubectl scale |

**区服标识** 建议贯穿三层：Git overlay 目录名（`sea-prod`）、K8s label（`region=sea`）、应用 ConfigMap（`ZONE_ID=SEA`）——告警和日志用同一套，on-call 不会把东南亚当国服查。

### 与 Istio 多集群（高级一句）

Istio **多主（multi-primary）** 或 **主从（primary-remote）** 可把 Mesh 扩到多集群——east-west 跨集群仍走 mTLS，但运维复杂度再上一个台阶。多数游戏公司 **区内 Mesh、区间网关** 就够；面试知道「Istio 能多集群，但通常不如 GSLB + MCS 直白」即可 → [24](../24-ServiceMesh-Istio与Envoy/)。

## 六、游戏：多区服怎么挂在这条主线上

> 🎯 **一句话**：**一区一集群（或一区一命名空间+强隔离）** 最常见；合服/跨区排行是 **数据与流量** 双问题，不是 kubectl 多 `--context` 能解决。

### 典型拓扑 ⭐🔧

```text
国服 cn-prod 集群：大厅 + 战斗 + 国服 DB
东南亚 sea-prod：大厅 + 战斗 + 本地 DB（活动配置从 Git 同步）
全球 global 集群：排行/匹配/支付回调（只放跨区服务）
```

**活动同步**：模板 YAML（ConfigMap/CR）走 GitOps main 分支；**开服时间**用区服 `values` 注入；**热更**仍走游戏服自有通道，K8s 只负责进程与配置载体（见 [07-03](../../07-游戏运维专题/03-活动高峰与压测/)）。

**合服**：K8s 层是 **缩容旧区 Deployment + DNS 权重切走**；数据层是 DB merge——**先数据后流量**，顺序反了会双写。跨集群变更窗口：**先非玩家路径（GM/支付回调）验证，再 GSLB 切玩家**。

### 与 Mesh / Ingress 的衔接

- 区内玩家 → [15](../15-Ingress与流量管理/) Ingress
- 区内服务互调 → [08](../08-Service与kube-proxy/) 或 [24](../24-ServiceMesh-Istio与Envoy/) Mesh
- 跨区后台 → MCS/网关，**不要**指望 Ingress 穿透集群

> 📝 **面试**：「游戏多区是 DNS 分玩家 + 每区独立数据面；配置用 GitOps 同源异构；跨区 API 用显式网关或 MCS，ClusterIP 不能跨集群。」

### 收束：多集群治理三件套 🎯⭐

```mermaid
flowchart TB
    G["多集群治理"] --> X["① 下发<br/>GitOps / Karmada"]
    G --> Y["② 一致<br/>base + overlay + 对账"]
    G --> Z["③ 联通<br/>GSLB + MCS/网关"]
```

**读图**：① 解决「变更怎么传播」；② 解决「怎么不漂移」；③ 解决「用户和服务怎么找到对的地方」。缺任一都会在「一次跨集群变更」里暴雷。

> ⚠️ **别混**：**多集群高可用 ≠ 单集群多副本**——两个集群各 3 副本，不会自动合成 6 副本抗单集群 etcd 挂；是 **控制面与故障域** 分开。

### 单集群多区域 vs 真多集群

| 对比 | **单集群多 AZ** | **多集群多地域** |
|------|-----------------|------------------|
| 控制面 | 一套 | 每地域一套 |
| etcd | 共享（02） | 隔离 |
| 延迟 | 同城 AZ ms 级 | 跨地域 RTT 大 |
| 合规 | 同法域 | 可数据驻留 |
| 运维 | 简单 | 复杂 |

游戏 **同城三 AZ** 用单集群 + Pod 反亲和（[06](../06-调度机制/)）往往够；**跨国** 才上多集群。

### 成本与人力诚实账 ⭐

多集群不是免费午餐：

```text
控制面：N 倍 API Server / etcd / 证书 / 升级窗口
GitOps：N 个 cluster credential 轮换与 RBAC 审计
可观测：Thanos/Cortex 多集群联邦查询（19）
on-call：告警要带 cluster 标签，否则不知道是哪国
```

面试敢说不值得：**三个服、两个区、团队五人**——先 **单集群 + 命名空间 + NetworkPolicy**，等业务和合规真逼到再拆。

### Helm 与 Kustomize 在多集群中的位置

同一 chart **不同 values 文件**：

```text
charts/lobby/
  values-cn-prod.yaml    # replicas: 80, storageClass: alicloud-ssd
  values-sea-prod.yaml   # replicas: 30, storageClass: gp3
```

ApplicationSet generator 把 `values-{{cluster}}.yaml` 传给 Helm source——与 Kustomize overlay **二选一或组合**（Helm 外包 Kustomize）。原则不变：**渲染结果进 Git 或 CI artifact**，值班不在笔记本上 `helm template | kubectl apply` 打生产。

### 灾难恢复：单集群挂了怎么办

多集群的 **DR（灾难恢复）** 不是自动的——要预先定义：

```text
RPO：Git 里最后一次合并的 desired state
RTO：在备用集群 Argo sync + GSLB 切流的时间
数据：游戏 DB 仍要跨区复制/备份（31 章备份），K8s 对象恢复 ≠ 玩家数据恢复
```

某成员集群 **控制面全挂**：玩家若仍解析到该区 GSLB，入口 502——监控要有 **per-cluster 合成**，并在 runbook 里写 **DNS 权重置零** 步骤（[01-15](../../01-基础底座/15-DNS与CDN/)）。

> 📝 **面试**：「多集群 DR = Git 恢复 workload 定义 + 数据库自己的跨区方案 + GSLB 切走；不是 Karmada 自动把玩家瞬移。」

### 命名与标签规范（落地层）

多集群没有统一命名，值班会疯。建议最低限度：

```yaml
metadata:
  labels:
    platform.moonton/cluster: sea-prod
    platform.moonton/region: ap-southeast-1
  annotations:
    argocd.argoproj.io/tracking-id: lobby:game/lobby
```

Prometheus `external_labels`、Loki `cluster` 字段、告警路由 **必须与 kubeconfig context 同名**。合成大盘按 `cluster` 分组，否则「国服挂了」可能在东南亚仪表盘里被平均掉。

### Member 集群离线演练 🔧

季度演练清单：

```text
1. 从 Argo 摘掉一个 member（或 Karmada  cordon cluster）
2. 确认该区存量 Pod 仍运行、GSLB 可切走
3. Git 合并一条小变更，确认离线区不 sync、在线区正常
4. 恢复 member，diff 对齐，无手工漂移
```

**读图**：演练验证的是 **控制面断开时数据面能撑多久**，不是「把集群删了能否重建」——后者是备份/DR 另一条线。

### sync wave 示例（Argo）

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "2"   # 数字小的先 sync；先 ConfigMap 后 Deployment
```

配合 ApplicationSet 可对 **staging 集群 app** 设 wave 0，prod 集群 wave 1——实现「先金丝雀集群、后全量」而不写多套 Pipeline。

### 观测：多集群告警必须带 cluster 标签

```promql
sum by (cluster) (rate(http_requests_total{status=~"5.."}[5m]))
# 没有 cluster 标签会把国服异常稀释进全球均值
```

日志同理：Loki/ES 索引里 `cluster=sea-prod` 与 kubeconfig context **同名**。on-call runbook 第一条：**`kubectl config current-context`**。

## 七、作战：定责

> 🎯 **一句话**：跨集群故障先分 **下发（Argo/Karmada）/ 落地（集群差异）/ 流量（DNS/MCS）** 三支，别在错误集群上 kubectl。

### 决策树

```mermaid
flowchart TB
    A["跨区功能异常"] --> B{"Argo/Karmada<br/>Synced?"}
    B -->|"OutOfSync / Failed"| C["看 diff / PropagationPolicy 事件<br/>修 Git 或 Override"]
    B -->|"Synced"| D{"目标集群 Pod Ready?"}
    D -->|"否"| E["describe Pod：镜像拉取 / SC / 节点标签<br/>区服 overlay 问题"]
    D -->|"是"| F{"玩家还是后台？"}
    F -->|"玩家"| G["GSLB/DNS 指向哪<br/>证书/SAN 是否覆盖该区域名"]
    F -->|"后台"| H["ServiceExport/Import<br/>隧道 CIDR 是否重叠"]
```

### 现象 · 先做 · 别做

| 现象 | 先做 | 别做 |
|------|------|------|
| 一区 Synced 另一区 Degraded | `argocd app diff` 只看坏区 | 在好区重复 apply「修复」 |
| SEA 镜像 PullBackOff | 该区 registry secret / 镜像地域 | 强行改全球用 cn 镜像地址 |
| 跨区 API 超时 | CIDR、MCS Endpoints、防火墙 | 在业务里写死对端 ClusterIP |
| Host Karmada 挂了 | 成员集群仍跑，暂停变更 | 以为全服下线 |
| 活动配置不一致 | Git commit 与 Argo revision 对齐 | 手工 kubectl edit 某一区 |
| GSLB 切流后 502 | 该区 Ingress Endpoints（08/15） | 先动另一区集群 |

### 60 秒剧本 🔧

```text
① 0–10s   确认 context；argocd app get <app> 或 karmada kubectl get propagationpolicy
② 10–30s  坏区：app diff / kubectl get pods -n game；好区对比 overlay 差异
③ 30–45s  玩家问题 → dig GSLB；后台问题 → serviceexports/imports + endpointslices
④ 45–60s  修 Git/Override 再 sync；切流前该区健康检查与监控合成视图通过
```

### 面试锚点

遮住右列自问自答，卡壳的行回去重读对应小节——这张表就是本章的「30 秒口径速查」。

| 问 | 30 秒答 |
|----|---------|
| 为什么多集群？ | 故障域、合规驻留、地域延迟、团队边界、升级金丝雀；不是apiserver不够就先拆。 |
| GitOps 多集群怎么做？ | ApplicationSet + 每集群 overlay；Git 单源，Argo 对各集群 sync。 |
| Karmada 干什么？ | Host 统一 API，PropagationPolicy 选集群，OverridePolicy 做差异，Member 落地。 |
| Fleet 是什么？ | GKE 多集群舰队/治理面，类似统一注册与策略下发。 |
| 配置怎么一致？ | base 同构 + Kustomize/Helm 参数化；禁止 hand-edit；Argo diff 对账。 |
| 跨集群流量？ | 玩家用 GSLB/GeoDNS；服务用 MCS/Submariner/网关，ClusterIP 不跨集群。 |
| MCS 是什么？ | ServiceExport/Import，clusterset.local DNS，需 ClusterSet 实现。 |
| 多集群最大坑？ | CRD/版本不一致、CIDR 重叠、Secret/SC 名不同、误 prune 全集群。 |
| 游戏多区？ | 一区一集群/强隔离；活动 Git 同步；合服先数据后 DNS；跨区用网关。 |
| 联邦 v2 要背吗？ | 不背；主流 GitOps + Karmada/Fleet。 |

### 易错一句话对照

- 多集群 = 复制 kubectl apply → 要有 overlay 与对账
- Karmada 替代 GitOps → 常组合使用，不是二选一
- 复制 Deployment 就能跨集群调用 → 还要 MCS/网关
- ApplicationSet prune 无害 → 误删 Git 对象会全集群删资源
- 两集群 CIDR 可重叠 → 隧道互调必须不重叠
- Host 挂了成员全停 → 成员仍跑，只是不能下发新变更
- GSLB 解决服务间调用 → 只解决玩家入口
- 手工改一区 ConfigMap 快 → 漂移，下次 sync 覆盖或永久 OutOfSync
- 联邦 API 是面试重点 → 重点是 GitOps/Karmada 这一代
- 多集群自动更高可用 → 是故障域隔离，运维复杂度上升

### 数字墙

> 建议 **单集群节点 小于 5000 / Pod 小于 150k** 量级再评估拆（视云厂商）· **GitOps sync** 失败先 diff 再看集群 · **GSLB TTL** 切流常留 **30–300s** 观察 · **MCS DNS** 后缀 **`svc.clusterset.local`** · Karmada **Host 1 + Member N** · 变更顺序 **金丝雀集群 → 全量集群**
