# 配置与密钥

> 运营在大群里甩了一张 `kubectl get secret -o yaml` 的截图问「这密码是不是加密了」——base64 一串，谁 decode 谁拿到生产库；另一半人改了活动开关的 ConfigMap 半小时，充值入口还是关着的，因为那是 envFrom 注入，有人已经在骂 kubelet 坏了。
> **本章回答**：一份配置从 Git 到容器进程的一生——怎么出生（ConfigMap/Secret）、怎么进容器（四种注入）、改了什么时候生效（热更新）、Secret 到底安不安全、怎么轮换与应急，以及游戏服配置（开服表、活动开关）怎么下发。
> **不讲**：etcd Raft、quorum、备份与直连禁令 → [02](../02-etcd/)；RBAC 收权、automount 策略、PSS 文件权限 → [13](../13-RBAC与安全/)；证书体系与 kubeconfig → [14](../14-证书与kubeconfig/)；ImagePullBackOff 与 containerd → [17](../17-节点运行时与升级/)；Helm values 与 checksum 模板 → [22](../22-Helm与Kustomize/)；GitOps 同步策略 → [23](../23-GitOps-ArgoCD与Tekton/)；发布单与灰度 → [16](../16-灰度与回滚/)；游戏热更与开服流程 → [07-05](../../07-游戏运维专题/05-热更新与版本发布/)、[07-06](../../07-游戏运维专题/06-开服合服/)。

**标记**：🎯重点 · 🔥难点 · ⭐常考 · 🔧实操

## 一、一张图：一份配置的一生

> 🎯 **一句话**：配置也有生老病死——来源、户口、注入、生效、变更轮转；出了问题先问「卡在哪一段」。

```mermaid
flowchart LR
    SRC["① 来源<br/>Git 只放引用 · KMS/Vault 管值"] --> OBJ["② 户口<br/>ConfigMap / Secret<br/>API Server 写入 etcd"]
    OBJ --> INJ["③ 注入<br/>env · envFrom · 卷挂载 · 命令行"]
    INJ --> LIVE["④ 生效<br/>热更新？还是必须滚动？"]
    LIVE --> CHG["⑤ 变更 · 轮转<br/>新对象 → 切引用 → 滚动 → 删旧"]
    OBJ -.->|起不来| X2["describe Events<br/>引用不存在 / key 错 / 错 NS"]
    LIVE -.->|改了没生效| X1["exec env / cat 文件<br/>先分支注入方式"]
    OBJ -.->|以为加密了| X3["get secret -o yaml<br/>base64 一眼到底"]
```

**读图**：主线从左到右是一份配置的五个阶段，二到八节各讲一段。三条虚线是值班最常见的三种报障入口——「起不来」查引用、「改了没生效」先分支注入方式、「以为加密了」直面 base64 真相。`kubectl exec / describe / get` 就是这章的探针：不换器官，只照「这份配置现在卡在哪一段」。

## 二、出生：值从哪来、落进哪个对象

> 🎯 **一句话**：非敏感进 ConfigMap、敏感进 Secret；两者都落 etcd，Secret 默认不加密。

**ConfigMap** 存非敏感配置（开关、地址、版本号），**Secret** 存敏感值（密码、证书、token）。两者的「户口」完全一样：都是 API Server 里的一个普通对象，**都写进 etcd**。Secret 的特殊之处只有两个——注入时可以控制文件权限、定位上「默认该被 RBAC 收紧」；**存储层面它默认只是 base64 编码，不是加密**（五节细讲）。

**值从哪来**是出生段第一问。生产答案几乎总是：**Git 里只放引用，不放值**。明文值放 KMS / Vault / 云密钥服务，由 ExternalSecret 一类的控制器在集群里生成 Secret；Git 仓库里提交的只是「去哪取值」的声明。反面教材有两个：把密码写进 YAML 的 `stringData` 推进 Git（base64 与否都是明文密码本），以及把开服配置直接打进镜像（八节细讲）。

`stringData` 只是提交时的方便字段——你写明文，API Server 收存时照样转成 `data`（base64）存 etcd。所以「用 stringData 看起来不是密文」不构成任何安全性，进了 Git 就等于进了密码本。

**出生时的三条硬边界**：

- **单对象 1MiB**（1048576 字节）上限，来自 etcd 单请求大小（对齐 [02](../02-etcd/) 的 `--max-request-bytes`，常见 1.5MiB）。整张技能表塞不进来，apply 直接报 too long——大表放对象存储，CM 只留指针（八节）。
- **跨 Namespace 不能引用**。CM/Secret 是命名空间级对象，Pod 只能引用**同 NS** 的；要跨就复制一份或用外部同步（ExternalSecret 从同一外部源生成多份）。这不是 bug，是边界。
- **Secret 有类型**。最常用 **Opaque**（任意键值）；`kubernetes.io/tls`（固定 `tls.crt` / `tls.key` 两键）；`kubernetes.io/dockerconfigjson`（专给 imagePullSecrets 拉镜像，三节）。二进制值放 `binaryData`，别把 PEM 再 base64 一层塞进 Opaque 让应用解两遍。

> 🔍 **现场**：值班最常见的第一步就是把对象造出来、看一眼长什么样。

```bash
kubectl create configmap game-switch -n game \
  --from-literal=PAYMENT_ENABLED=true \
  --from-literal=ACTIVITY_ID=summer2026
# configmap/game-switch created

kubectl create secret generic db-pass -n game \
  --from-literal=password='Pr0d_MySQL_2026!'
# secret/db-pass created
```

```bash
kubectl get secret db-pass -n game -o yaml
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-pass
  namespace: game
type: Opaque                            # ← 最常见类型；另有 kubernetes.io/tls、dockerconfigjson
data:
  password: UHIwZF9NeVNRTF8yMDI2IQ==    # ← base64 编码，不是密文（五节）
```

> 📝 **面试**：问「ConfigMap 和 Secret 的区别」，别只答「一个存敏感一个不存」，要补两句：**两者都进 etcd、都受 1MiB 限制、都不能跨 NS 引用**；Secret 多的只是注入时的权限控制空间和「默认该被 RBAC 收紧」的定位。

## 三、注入：四条通道进容器

> 🎯 **一句话**：配置进容器有四条通道——env、envFrom、卷挂载、命令行；选哪条，决定了后面热不热更。⭐

**注入（injection）** = 把 CM/Secret 里的值交给容器进程。四条通道的写法与脾性各不相同，这是全章的岔路口：

```yaml
# ① env：单键引用，一次一个值
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:            # ← Secret 用 secretKeyRef；ConfigMap 用 configMapKeyRef
      name: db-pass
      key: password

# ② envFrom：整对象展开成环境变量，键名即变量名
envFrom:
- configMapRef:
    name: game-switch        # ← CM 里每个 key 都变成一个环境变量

# ③ 卷挂载：对象变成目录里的文件
volumeMounts:
- name: cfg
  mountPath: /etc/game       # ← CM 的每个 key 变成 /etc/game 下一个文件

# ④ 命令行：先有 env，再在 args 里用 $( ) 展开
env:
- name: PAYMENT_ENABLED
  valueFrom:
    configMapKeyRef: { name: game-switch, key: PAYMENT_ENABLED }
args: ["--payment=$(PAYMENT_ENABLED)"]   # ← kubelet 创建容器时展开，本质仍是 env
```

**第四条命令行通道常被漏掉**：`command`/`args` 里的 `$(VAR)` 由 kubelet 在**创建容器时**用 Pod 的环境变量展开，值仍来自 `env`——所以它的热更新脾性和 env 完全一样：出生即定死，改 CM 必须滚动。

| 方式 | 值以什么形式进进程 | 热更新 | 典型用途 |
|------|--------------------|--------|----------|
| `env` / `envFrom` | 环境变量，创建时写入 | **否**，必须滚动 | 开关、端口、简单键 |
| 卷挂载 | 文件，kubelet 持续同步 | 文件**会变**，进程要 reload | 配置文件、证书 |
| 命令行 `$(VAR)` | 展开进启动参数 | **否**，必须滚动 | 启动参数引用配置 |
| `imagePullSecrets` | 不进业务进程 | — | 只给 kubelet 拉私有镜像 |

> ⚠️ **别混**：`imagePullSecrets` 和业务 env 里的仓库密码**不是一回事**——前者给 kubelet 拉镜像用（类型 `kubernetes.io/dockerconfigjson`），后者给应用自己用。ImagePullBackOff 报 401 先查 Pod 的 imagePullSecrets 和节点运行时配置（[17](../17-节点运行时与升级/)），别先去改业务环境变量。

### 卷挂载的两个细节：权限与 subPath

**Secret 卷建议 `defaultMode: 0400`**（只有属主可读）。但 0400 要和容器的 `runAsUser`/`fsGroup` 对上——非 root 容器 uid 对不上文件属主就会 Permission denied，而且 Events 不一定点名是 Secret 的问题。不要为了省事改 0777，那等于把密码贴在容器门口。

**subPath** = volumeMount 里把卷内**单个文件**挂到容器某个路径（而不是挂整个目录）：

```yaml
volumeMounts:
- name: cfg
  mountPath: /etc/game/payment.yaml
  subPath: payment.yaml      # ← 只挂这一个文件
```

它让应用不用吃下整个目录，但代价是**热更新基本失效**：不少版本里 kubelet 只同步整目录卷，subPath 挂出去的单个文件**不会跟着变**（四节）。用 subPath 的配置，默认当「必须滚动」。

### projected 与 SA token

**projected volume** 能把 CM、Secret、DownwardAPI（把 Pod 名、NS、资源 request 等元信息注入文件或 env，打日志标签用，不必再配一份 CM）合成一个目录。**ServiceAccount Token 也是 projected 注入的**——1.24+ 默认改用 **Bound Token**（绑定 SA、有过期时间、自动轮换），老的永不过期 Secret Token 少用：泄露后无法靠过期自愈，攻击者拿着能长期打 API。不需要调 API 的业务 Pod 应关掉自动挂载（`automountServiceAccountToken: false`，细节见 [13](../13-RBAC与安全/)）。

> 📝 **面试**：问注入方式，四条通道按「**值以什么形式进进程**」说：环境变量（env/envFrom）、文件（卷挂载）、启动参数（命令行，本质还是 env）；再补一条 imagePullSecrets 不进业务进程。热更新差异留到下一节讲，别在这里抢答「卷挂载都会热更」。

## 四、生效：热更新，改了什么时候变

> 🎯 **一句话**：卷挂载的文件会变但进程要 reload；env 出生即定死必须滚动；subPath 当不热更。🔥⭐

**热更新（hot update）** = 改了 CM/Secret 后，不重建 Pod 就让进程用上新值。它成立与否**完全由注入方式决定**，这是本章最高频的报障——「我明明 apply 了，为什么没生效」。

> 💡 **打个比方**：env 像出生证上的名字——生出来就定了，改户口得重生（重建 Pod）；卷挂载像办公室的公告板——kubelet 会定期来换纸，但员工（进程）得自己抬头看（reload），否则干的还是旧规矩。

**为什么卷挂载的文件会自己变？** 节点上的 kubelet 持续 watch（观察）本节点用到的 CM/Secret，对象一变就把卷里的文件同步成新内容。同步不是瞬间的：受 watch 延迟与本地缓存 TTL 影响，常见**秒级到分钟级**（kubelet 的 `configMapAndSecretChangeDetectionStrategy` 常见取值 Cache + TTL）。刚 apply 立刻 `exec cat` 可能还是旧文件——等一轮再判断「热更新坏了」。

**为什么 env 永远不热更？** 环境变量是**创建容器那一刻**写进进程的，之后没有任何机制去改一个已运行进程的环境。CM 改了、etcd 里早就是新的，老 Pod 的进程环境仍停在出生时刻——必须滚动出新 Pod。

```mermaid
flowchart TB
    A["kubectl apply 新 ConfigMap"] --> B["etcd 里对象已是新的"]
    B --> C["env / envFrom / 命令行<br/>进程环境停在出生那一刻 → 必须滚动"]
    B --> D["卷挂载（整目录）<br/>kubelet 秒到分钟级同步文件"]
    D --> E["文件新了 ≠ 行为新了<br/>进程要自己 reload"]
    B --> F["subPath 挂单文件<br/>不少版本根本不同步 → 当不热更"]
```

**读图**：从「apply 成功」进图——etcd 新了只走完一半，后半程三条岔路各有各的卡点。env 那条路终点是「必须滚动」；卷挂载那条路还有第二跳，**文件新了不等于行为新了**，进程不 reload 一切照旧；subPath 那条路最短——直接当不热更处理。

> ⚠️ **别混**：「卷挂载会热更新」只对**文件**成立，对**进程行为**不成立。文件更新（kubelet 干的）与行为更新（进程 reload 才算）是两件事；很多应用只有启动时读一次配置，卷挂载对它们来说同样「不热更」。也别说「凡是 volume 都会热更」——subPath 是例外。

> 🔍 **现场**：运营改了支付开关 CM，半小时了充值入口还关着。一步步走：

```bash
kubectl get deploy payment -n game -o yaml | grep -A3 'envFrom'
# envFrom:
# - configMapRef:
#     name: game-switch          ← env 型注入：改 CM 不会自动改进程环境

kubectl get cm game-switch -n game -o yaml | grep PAYMENT_ENABLED
#   PAYMENT_ENABLED: "true"      ← CM 已是新的

kubectl exec deploy/payment -n game -- env | grep PAYMENT_ENABLED
#   PAYMENT_ENABLED=false        ← 容器里还是旧的：没滚动
```

确诊后滚动：

```bash
kubectl rollout restart deploy/payment -n game
# deployment.apps/payment restarted
kubectl rollout status deploy/payment -n game
# deployment "payment" successfully rolled out   ← 新 Pod 全量，再 exec env 才是 true
```

若是卷挂载型，apply 后等一轮 sync 再 cat；文件已新但行为仍旧，就去治进程的 reload（发信号、调接口、或同样滚动）。

### 把「改配置」自动变成「滚 Pod」

手工滚动靠自觉，生产常用两个自动化：**Helm 的 checksum annotation**（把 CM 内容的校验和写进 Pod template，CM 一变 template 就变，Deployment 自动滚动，模板写法见 [22](../22-Helm与Kustomize/)）和 **Reloader**（独立控制器，盯着带注解的工作负载自动 `rollout restart`）。

但自动化是双刃剑：**误改也会被自动推全集群**。活动高峰期有人手抖改错开关，checksum 会忠实地把坏配置滚进每一台。所以活动期间要么冻结 CM 变更，要么让 Reloader 只盯非生产。

> 📝 **面试**：「改了 ConfigMap 进程没变怎么排查」——先问注入方式：env/envFrom/命令行必须 `rollout restart`；卷挂载等 kubelet 同步（秒到分钟级）再确认进程有没有 reload；subPath 直接当不热更。千万别说「kubelet 坏了」，也别说「凡是卷挂载都会热更」。

## 五、真相：Secret 不是保险箱

> 🎯 **一句话**：Secret 默认只是 base64；能 get 就能看明文，盘上明文要靠 API Server 的静止加密。🔥⭐

> 💡 **打个比方**：Secret 像把密码写在信封里——信封（base64）不是保险柜，有权限拆信（`get secret`）的人一眼就能读；静止加密才是给金库加锁，但钥匙还在 API Server 手里，拆信照旧。

**base64 是编码，不是加密**：它是可逆的、无密钥的、谁都能解的。`kubectl get secret -o yaml` 拿到 `data` 字段，`base64 -d` 一步还原：

```bash
kubectl get secret db-pass -n game -o jsonpath='{.data.password}' | base64 -d; echo
# Pr0d_MySQL_2026!        ← 能 get 就能 decode
```

所以「密码放 Secret 里所以安全」不成立。谁能看明文有两层：**有 get/list secrets 权限的人**（API 层），以及**没开静止加密时能碰控制面数据目录/快照的人**（盘层，能碰 ≈ 能读所有 Secret）。生产补丁要叠着上，先记住五层，本节末尾收成清单。

**第一层：RBAC 少给 get / list secrets**。先查现状：

```bash
kubectl auth can-i get secrets -n game --as=system:serviceaccount:game:default
# yes        ← 默认 SA 能读本 NS 全部 Secret？该收
kubectl auth can-i list secrets -n game --as=dev-user
# no         ← 逐个审：谁真的需要读
```

权限最小化的完整规则在 [13](../13-RBAC与安全/)，本章只钉一句：**对 API 来说，能 get 就等于能看明文**，与加不加密无关。

**第二层：静止加密（Encryption at Rest），配在 API Server，不在 etcd**。🔥

> 💡 **打个比方**：API Server 像银行柜台——钱（Secret）进金库（etcd）前先装密封袋（加密）；etcd 只管存袋子，不知道也不关心袋子里是什么。所以加密开关在柜台的规章制度里（`--encryption-provider-config`），不在金库大门上。

**EncryptionConfiguration** 是 kube-apiserver 的加密配置：写 etcd 前加密、从 etcd 读出后解密。etcd 自己的 TLS（证书）管的是**谁能连 2379**，不管盘上是不是明文——两件事别混。

```mermaid
flowchart LR
    A1["kubectl apply Secret"] --> A2["API Server<br/>链首第一个能加密的 provider 加密"] --> A3["etcd 盘上：密文<br/>k8s:enc:aescbc:v1:..."]
    B1["kubectl get secret"] --> B2["API Server<br/>沿 provider 链逐个试解密"] --> B3["返回明文 JSON<br/>data 字段仍是 base64"]
```

**读图**：上下两条路——写路径只有一处加密（链首第一个能加密的 provider 负责新写）；读路径整条链都参与解密（旧 key 要留到存量改写完）。注意右下角——**开了静止加密，`get secret` 仍能看明文**，因为 API 解密后才给你；加密挡的是盘、快照、etcdctl 直读，不是 API 视图。

```bash
grep encryption-provider-config /etc/kubernetes/manifests/kube-apiserver.yaml
# - --encryption-provider-config=/etc/kubernetes/enc.yaml   ← 每台控制面都要有、路径一致
```

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
    - secrets
    providers:
    - aescbc:
        keys:
        - name: key2          # ← 新密钥排第一：新写用它
          secret: <base64-32-bytes>
        - name: key1          # ← 旧密钥留下：存量还要靠它解密
          secret: <base64-old>
    - identity: {}            # ← 排最后：兜底解密尚未加密的旧明文
```

**provider 链的规则**（面试逐条背）：

- `aescbc`（AES-CBC，key **32 字节**）/ `aesgcm`（AES-GCM，更现代）/ `kms`、`kmsv2`（信封加密，DEK 交给云 KMS，轮换不用碰静态文件）都能当加密 provider；`identity` = 明文。
- **链上第一个能加密的 provider 负责新写**——所以新 key 永远插第一。
- **整条链都用来解密**——旧 key 必须留到存量全部改写完；`identity` 留在链尾兜底尚未加密的旧明文，**放到第一 = 新写又变明文**，等于关掉加密。
- 改配置必须**重启所有 API Server**——只改文件不重启，进程还拿着旧链。
- 只需加密 `secrets` 资源；把 Pod 也加密收益小、密钥轮换面更大。

> ⚠️ **别混**：**开了静止加密 ≠ get 不到明文**。加密护的是盘上数据与 etcd 快照，API 读时解密后照样返回明文；所以 RBAC 仍要少给 get，两层各挡各的。反过来，**没开加密时**，`etcdctl` 直读或拿到一份快照就等于拿到全服密码。也别把 etcd TLS 当静止加密——TLS 管谁能连，不管盘上明文。

```bash
# 维护窗口只读抽查（02 章禁令：生产 etcd 不要 put）
ETCDCTL_API=3 etcdctl get /registry/secrets/game/db-pass --print-value-only | head -c 40
# k8s:enc:aescbc:v1:key2:...      ← 开了加密：密文前缀
# {"apiVersion":"v1","data":...   ← 明文 JSON：没开，或 identity 在第一
```

**第三层：值不进 Git**（ExternalSecret / Sealed Secrets + KMS）。**第四层：审计 `get secret`**，谁在什么时候读过要留痕。**第五层：`immutable`**（六节）禁止原地改，变更 = 新对象，审计链干净。托管集群（ssh 不进控制面）则问清两件事：Encryption at Rest 是否默认开、key 由谁轮换。

### 收束：Secret 到底靠什么护住

```mermaid
flowchart TB
    S["Secret 防护五层"] --> L1["① RBAC<br/>get/list secrets 最小化"]
    S --> L2["② 静止加密<br/>EncryptionConfiguration 护盘与快照"]
    S --> L3["③ 值不进 Git<br/>ExternalSecret / Sealed + KMS"]
    S --> L4["④ 审计<br/>谁 get 过 secret 留痕"]
    S --> L5["⑤ immutable<br/>禁原地改 · 变更即新对象"]
```

**读图**：五层各挡一个入口——①挡 API 视图（能 get 就能看），②挡盘和快照（控制面被摸、备份流出），③挡仓库历史（Git 泄露），④负责事后追溯，⑤把「改」变成「新对象」让前三层的审计有抓手。值班说「我们 Secret 很安全」，按这五层逐层问。

> ⚠️ **别混**：五层**不保证**「已经泄露的值能收回来」——截图、Git 历史、旧快照一旦流出，加密和权限都只是亡羊补牢，必须走七节的轮转与应急，把旧值**失效**。也不要把希望寄托给「上 Vault 就完事」：外部保险箱只解决第③层，注入、滚动、静止加密仍是本章的事。

> 📝 **面试**：问「Secret 怎么才算安全」，按「**API 层挡读、盘层挡裸、源头挡漏、事后能查、变更可审**」五组背：RBAC / EncryptionConfiguration / ExternalSecret+KMS / 审计 / immutable。最后一定补「默认只是 base64，能 get 就能 decode」——这句是分水岭。

## 六、变更：改配置就是一次发布

> 🎯 **一句话**：改 ConfigMap 要不要重启，全看注入方式；把每次改配置当一次发布管。⭐

「改了 ConfigMap 要不要重启 Pod」没有统一答案，判据就是四节的分叉：**env 型必须滚动；卷挂载型文件会变，确认进程能 reload 就可以不滚，不能 reload 同样滚；subPath 当不热更，滚**。改配置和发版走同一套纪律：先 diff、再小范围、可回滚。

**标准动作五步**：

```text
① Git 改 CM/Secret（或 ExternalSecret 引用）          ← 仓库是唯一事实源
② kubectl diff 预检；确认引用它的工作负载有哪些
③ env 型：rollout restart；volume 型：确认进程 reload
④ exec 核对容器内值与 Git 一致                       ← 验证到进程，不是到对象
⑤ 失败：undo Deploy + 回上一版 CM（两条通道，见下）
```

**`immutable`：把「改」变成「发新对象」**。给 CM/Secret 声明 `immutable: true` 后，`data` 不允许再修改，要变更只能删除重建（实践里直接发一个新名字的对象，如 `game-switch-v20260901`）。三个好处：误改直接被 API 拒绝；kubelet 不必再 watch 它的原地变更（大规模集群明显减负）；审计上「变更 = 新对象 + 切引用」清清楚楚。它与「只发新对象」的轮转纪律（七节）天然配套。

> ⚠️ **别混**：`immutable` 防的是**篡改与误改**，不是保密——对象内容照样能被 get、能 decode，五层防护里它只是第⑤层。

**生产 `kubectl edit` 的债，当天必须还**。应急时直接 edit 集群里的 Secret 是允许的止血手段，但若 Git 仍是旧值，下一次 GitOps 同步（[23](../23-GitOps-ArgoCD与Tekton/)）会把你的新密码**盖回旧值**——业务连不上，还以为是数据库挂了。纪律：应急可以改集群，当天内让仓库与集群一致。

**回滚是两条通道**：

- checksum 在 Pod template 里 → `rollout undo` 会连同**旧的 CM 引用**一起带回；
- 只改了 CM、靠进程 reload → 回上一版 CM，并**确认进程真的 reload 回去了**。

热更指针和 Deploy 滚动不是同一条通道，回滚只回其中一个 = 半回滚，发布单上要把两条回滚路径都写清（发布与灰度见 [16](../16-灰度与回滚/)）。

> 📝 **面试**：「你们改配置怎么保证不出事故」——仓库唯一事实源、diff 预检、按注入方式决定滚不滚、exec 验证到进程、回滚双通道写进发布单；敏感对象开 immutable。

## 七、轮转：换密钥与泄露应急

> 🎯 **一句话**：轮转永远走「新对象→切引用→滚动→删旧」；泄露先让旧值失效，再谈别的。🔥

### 业务密码轮转四步（顺序不能反）

```text
① 新建 Secret（新密码）
② 改 Deploy / STS 的引用，指向新 Secret
③ 滚动，验证新 Pod 连得上
④ 删旧 Secret
```

反序的代价很具体：先删旧或先改源头密码，会有一批还没滚到的 Pod **拿旧密码打新库**，连接错误一片。日常轮转不要 `kubectl edit` 原地改——原地改不产生新对象，审计断链、回滚无路，还会被 GitOps 盖回（六节）。

### EncryptionConfiguration 的 key 轮转

加密密钥本身也要换（合规周期、人员变动）。流程与业务轮转同构，口诀：**新 key 插第一 → 重启全部 API → rewrite 存量 → 确认后再撤旧 key**。

```bash
# rewrite 存量：读出再写回，逼每个 Secret 用链首新 provider 重新加密
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
# 维护窗口执行，会打 API；完了用 etcdctl 抽查已是新前缀
```

**永远不要先删旧 key**——存量还指着它解密；删早了，一批 Secret 谁都读不出。同理，改完配置文件不重启 API Server 等于没改（进程拿着旧链）。

### 泄露应急：先失效，再轮转，后堵渠

> 💡 **打个比方**：钥匙被人拍照了，换锁（轮转）是必须的但不够——照片（截图、Git 历史、快照）还在外面，得确认「照片打不开门」：旧钥匙作废、门芯换掉、再查照片流向了谁。

以「有人把 `get secret -o yaml` 的明文截图发进大群」为例：

```text
① 定范围   哪个 key、谁看过、传到了哪（群 / Git / 快照 / 个人设备）
② 先失效   在源头系统改密码、吊销 token —— 不是先去删 K8s 对象
③ 再轮转   新 Secret → 切引用 → 滚动 → 删旧（上面四步）
④ 查流向   审计日志拉 get/list secrets 记录；etcd 快照是否已带明文流出
⑤ 堵渠道   Git 历史清理、旧快照作废；撤回截图只是补救，别当成已止血
```

两条铁律：**别只轮 K8s 不轮源头**——数据库密码要在数据库侧改掉，否则旧密码在 K8s 外依然有效；**别把「删了那条消息」当止血**——值一旦离开过边界，就按已泄露处理。还要记住五节的边界：事后才开静止加密，救不回已经流出的旧快照。

**SA token 的轮转**交给机制：1.24+ 的 Bound Token 自带过期与自动轮换；若还在用老的永不过期 Secret Token，泄露窗口是无限的，应尽快迁移并关掉不必要的自动挂载（[13](../13-RBAC与安全/)）。

> 📝 **面试**：「密码泄露了怎么办」——先失效（源头改密/吊销）→ 再轮转（新对象四步）→ 查审计与快照流向 → 堵渠道复盘；补一句「事后开加密救不回旧快照，所以静止加密要提前开」。

## 八、下发：游戏配置怎么进服

> 🎯 **一句话**：开服配置别打进镜像，大表别进 etcd，开关别每秒 apply；热更指针与滚动是两条通道。⭐

游戏服配置有三个特色场景，全是值班真坑：

**① 开服：配置跟着服走，不跟着镜像走。** 每开一个新服都是一套配置（开服表：开服时间、渠道参数、初始活动）。常见误操作是把开服配置打进镜像——改一个参数要重新构建、推仓库、滚全部同镜像的服，把「配置变更」绑架成「版本发布」。正解：配置是对象不是代码——按服生成 ConfigMap/Secret（Helm/Kustomize 模板渲染，[22](../22-Helm与Kustomize/)），镜像只含程序；开服的完整流程见 [07-06](../../07-游戏运维专题/06-开服合服/)。

**② 大表：1MiB 挡在门口，指针才是正路。** 运营要把整张技能表塞进 CM：

```bash
kubectl apply -f skill-table-cm.yaml
# Error from server (Invalid): configmaps "skill-table" is invalid:
# data: Too long: must have at most 1048576 bytes   ← 单对象 1MiB 硬顶
```

正解：表放对象存储，CM 只存版本指针；进程 watch 指针，拉取后安全 reload：

```yaml
data:
  SKILL_TABLE_VERSION: "v20260828"
  SKILL_TABLE_URL: "s3://game-config/skill/v20260828.json"
```

好处不止绕开上限：回滚的是**版本指针**而不是整份 YAML；表的多版本天然共存；etcd 不被大对象拖慢（对齐 [02](../02-etcd/)）。

**③ 活动开关：低频、可审计、别拿 etcd 当消息队列。** 运营平台每秒改一次开关 CM = 每秒打一次 etcd 写 + 推一轮 watch，高基数更新会把控制面拖出毛刺。开关变更应是**低频的发布动作**：改一次、滚一轮、记一笔。活动高峰期还要冻结 CM 变更或只允许白名单 key——checksum/Reloader 会把一次手抖自动推全集群（四节）。

**两条通道写进同一张发布单**：热更指针（改 CM 里的版本号，进程 watch 后自己 reload）与 Deploy 滚动（换镜像、重建 Pod）是**两条独立通道**——热更成功不等于进程是新的，下一次发版滚动仍会带着旧镜像配置杀进程。逻辑表结构变了更要按热更方案走，那不是 K8s 自动完成的。发布单写法与灰度约束见 [07-05](../../07-游戏运维专题/05-热更新与版本发布/)、[16](../16-灰度与回滚/)。

> 📝 **面试**：问「游戏配置怎么下发」——小配置走 CM/Secret 四种注入；大表走对象存储 + CM 指针；开服配置模板化生成、不进镜像；开关低频变更；热更与滚动两条通道同写一张单。

## 九、作战：定责

> 🎯 **一句话**：三类现象三条入口——起不来查引用，改了不生效先分支注入方式，密钥问题先问「谁能看」。

```mermaid
flowchart TB
    A["配置 / 密钥出问题"] --> B{哪一类现象}
    B -->|Pod 起不来<br/>CreateContainerConfigError| C["describe Events 看引用<br/>对象不存在 / key 错 / 错 NS"]
    B -->|改了没生效| D{什么注入方式}
    D -->|env / envFrom / 命令行| E["exec env 仍旧 = 没滚动"]
    D -->|卷挂载 整目录| F["文件新了？没新 = 等 sync<br/>新了行为旧 = 进程没 reload"]
    D -->|subPath 单文件| G["当不热更，直接滚动"]
    B -->|密钥安全| H{什么症状}
    H -->|base64 当加密| I["能 get 就能 decode<br/>查 RBAC + EncryptionConfiguration"]
    H -->|明文截图 / 泄露| J["先失效源头再轮转<br/>查审计与快照流向"]
    H -->|apply too large| K["1MiB 硬顶<br/>拆对象或对象存储 + 指针"]
    H -->|GitOps 盖回旧值| L["edit 没补 Git / 没开 immutable"]
```

**读图**：第一刀按现象分三类。「起不来」这条最简单——业务容器还没开始创建，**别先看应用日志**，Events 里写得明明白白。「改了没生效」先分支注入方式再动手，三个分支的处方完全不同。「密钥安全」四个症状各有去向，别混着治。

| 现象 | 先做 | 别做 |
|------|------|------|
| CreateContainerConfigError | describe Events；先 apply 配置再发工作负载 | 先看应用日志 |
| env 型改了不生效 | `exec env` 对比 CM，确认后 `rollout restart` | 怪 kubelet 坏了 |
| 卷挂载文件新了行为旧 | 确认进程支持并真的 reload | 说「凡是 volume 都热更」 |
| 0400 后非 root 读不了 | 对上 runAsUser / fsGroup | 改 0777 图省事 |
| 跨 NS 想用别人的 Secret | 复制对象或 ExternalSecret 同源生成 | 改引用路径硬指 |
| apply 报 too large | 拆小对象或对象存储 + 指针 | 抬 etcd 写入硬顶 |
| 明文截图 / 泄露 | 源头失效 → 轮转 → 审计流向 | 撤回消息就当止血 |
| checksum 把坏配置推全集群 | undo Deploy + 回上一版 CM，两条通道都回 | 只回其中一个 |
| 开了加密 get 仍能看 | 正常，API 解密后给你 | 以为没开成功，identity 挪第一 |

**60 秒剧本** 🔧

> 🔍 **现场**：接到「配置没生效 / 起不来」，按这条线走完再下结论。

```text
① 0–10s   kubectl describe pod <p> -n {ns} | sed -n '/Events/,$p'
          ← CreateContainerConfigError？先查引用（对象/key/NS），别碰应用日志
② 10–30s  kubectl get cm <名> -o yaml 与 kubectl exec <p> -- env / cat 文件 对比
          ← 容器里旧 = 注入之后没人动过：没滚动 / 没等 sync / 没 reload
③ 30–45s  分支定责：env 型 → 没滚动；卷挂载 → sync 未到或进程没 reload；subPath → 当不热更
④ 45–60s  rollout restart + rollout status 验证；密钥问题先 auth can-i 收权限，再谈其余
```

## 十、收口

### 命令速查 🔧

```bash
# 对象长什么样
kubectl get cm <名> -n {ns} -o yaml
kubectl get secret <名> -n {ns} -o yaml              # data 字段是 base64
kubectl get secret <名> -n {ns} -o jsonpath='{.data.password}' | base64 -d
# 进程里是什么（验证到进程，不是到对象）
kubectl exec <p> -n {ns} -- env | grep KEY           # env 型：旧 = 没滚动
kubectl exec <p> -n {ns} -- cat /etc/game/xxx.yaml   # 卷挂载：刚 apply 可能还是旧的
# 起不来第一刀
kubectl describe pod <p> -n {ns} | sed -n '/Events/,$p'   # CreateContainerConfigError 看引用
# 变更与回滚
kubectl rollout restart deploy/{d} -n {ns}           # env 型变更后必做
kubectl rollout status deploy/{d} -n {ns}
kubectl rollout undo deploy/{d} -n {ns}              # checksum 场景会带回旧 CM 引用
# 权限与加密
kubectl auth can-i get secrets -n {ns} --as=<user 或 SA>
grep encryption-provider-config /etc/kubernetes/manifests/kube-apiserver.yaml
ETCDCTL_API=3 etcdctl get /registry/secrets/{ns}/<名> --print-value-only | head -c 40
# rewrite 存量（维护窗口）
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
```

### 面试锚点

| 问 | 30 秒答 |
|----|---------|
| ConfigMap 与 Secret 区别？ | 非敏感/敏感；都进 etcd、都有 1MiB、都不能跨 NS；Secret 多的只是注入权限控制与 RBAC 收紧定位。 |
| Secret 是加密的吗？ | 不是，默认 base64 编码；能 get 就能 decode；静止加密在 API Server 的 EncryptionConfiguration。 |
| 静止加密配在哪？ | kube-apiserver `--encryption-provider-config`，不在 etcd；写前加密、读时解密，每台控制面同一份。 |
| 开了加密 get 还能看？ | 能，API 解密后给你；加密挡的是盘、快照、etcdctl 直读，RBAC 仍要少给 get。 |
| provider 链规则？ | 链首第一个能加密的负责新写；整链解密；新 key 插第一；identity 兜底留最后；改完重启全部 API。 |
| 四种注入？ | env（configMapKeyRef/secretKeyRef）、envFrom（整对象展开）、卷挂载（文件）、命令行 $(VAR)（本质是 env）。 |
| 改 ConfigMap 要重启吗？ | 看注入方式：env/命令行必须滚；卷挂载文件会变但要进程 reload；subPath 当不热更。 |
| 为什么卷挂载文件会变？ | kubelet watch + 缓存 TTL 同步，秒到分钟级；刚 apply 立刻 cat 可能还旧。 |
| subPath 什么坑？ | 只挂单文件，不少版本不随源对象同步，默认当不热更，滚动解决。 |
| immutable 干什么？ | 禁原地改，变更=新对象；防误改、减 kubelet watch、审计清晰；不防读。 |
| 密码轮转顺序？ | 新 Secret → 切引用 → 滚动验证 → 删旧；反序=旧密码打新库；不要原地 edit 当日常。 |
| 生产 edit secret 会怎样？ | 止血可以，当天必须补 Git，否则下次 GitOps 同步盖回旧值。 |
| 泄露应急怎么走？ | 源头失效 → 四步轮转 → 审计与快照查流向 → 堵渠道；撤回消息不算止血。 |
| 为什么有 1MiB？ | etcd 单请求上限；大表放对象存储，CM 存版本指针，回滚的是指针。 |
| 跨 NS 引用 Secret？ | 不行，命名空间边界；复制对象或 ExternalSecret 同源生成。 |
| imagePullSecrets？ | 只给 kubelet 拉私有镜像（dockerconfigjson），不是业务 env 里的仓库密码。 |
| SA token 怎么管？ | 1.24+ Bound Token 有过期自动轮换；永不过期老 token 少用；不调 API 的 Pod 关自动挂载。 |
| 游戏开服配置怎么下发？ | 模板化生成每服 CM/Secret，不进镜像；大表走对象存储；开关低频变更；热更与滚动两条通道同写发布单。 |

### 易错一句话对照

- Secret 进 etcd 默认加密 → 默认明文 JSON，静止加密在 API Server
- base64 就是加密 → 编码；能 get 就能 decode
- etcd TLS 等于静止加密 → TLS 管谁能连 2379；EncryptionConfiguration 管盘上是否明文
- EncryptionConfiguration 配在 etcd.yaml → kube-apiserver `--encryption-provider-config`
- identity 放第一更安全 → 新写又变明文，必须链尾
- 新 key 追加在列表最后 → 链首才负责新写
- 改了配置文件就自动加密 → 必须重启所有 API Server
- 轮换时立刻删旧 key → 存量还要靠旧 key 解密
- env 改 CM 立刻生效 → 必须滚动
- 凡是卷挂载都会热更 → 进程要 reload；subPath 常常不热更
- 跨 NS 改个路径就能引用 → 复制或 ExternalSecret，这是边界
- Git 里放 stringData 图省事 → API 仍存 data；明文进了密码本
- imagePullSecrets 就是业务密码 → 只给 kubelet 拉镜像
- 大表塞进 CM → 1MiB 硬顶；对象存储 + 指针
- 长期 edit secret 不补 Git → 下次同步盖回旧值
- 回滚只回 CM 就够 → env 型要 undo/滚动；两条通道都回
- immutable 等于保密 → 只防篡改，内容照样能 get 能 decode
- 开服配置打进镜像最省事 → 改参数要重构建滚全服；配置是对象不是代码

### 数字墙

> 单对象 **1MiB**（1048576 字节；etcd `--max-request-bytes` 常见 1.5MiB）· kubelet 配置同步常见**秒到分钟**级 · aescbc 密钥 **32 字节** · SA Bound Token 自 **1.24+** 默认 · Secret 卷建议 **0400** · 业务轮转 **4** 步 · 防护 **5** 层 · 注入 **4** 条通道

1. **默画一节的主图**：来源 → 户口（CM/Secret → etcd）→ 注入 → 生效 → 变更轮转；三条虚线各对应哪种报障入口。
