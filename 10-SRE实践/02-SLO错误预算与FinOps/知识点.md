## 1. 基本概念

四个词是一份合同，不是四个同义词。平台 / SaaS 口径先立住；游戏 5 分钟登录、进战斗、支付分条表只在这里点一句：**去 [08-09](../../08-游戏运维专题/09-游戏SRE稳定性/)，不要用月历网关 200 冒充。**

**值班里怎么认这四个词**（周会、发布争议、财务对账都会碰到）：

| 词 | 是什么 | 对谁说 | 值班第一刀 |
|----|--------|--------|------------|
| **SLI** | 怎么量：成功事件 / 有效事件 | 工程 | 用户有感、可测、能告警 |
| **SLO** | SLI 的内部目标 | 团队 | 破了吃 Error Budget、卡发布 |
| **SLA** | 对外契约，常带赔偿 / 补偿 | 客户、法务 | 通常松于 SLO |
| **Error Budget** | `1 − SLO` | 产品 + SRE | 还能承受多少失败；管变更权 |

例：SLO 99.9% → 预算 0.1%。30 天窗口里大约 **43 分钟**可以失败（§3.1）。预算是变更权，不是躺平权。

| 在这份合同里 | 不在这里当主指标 |
|----------------|------------------|
| 请求成功、延迟达标、正确性、关键写成功 | CPU、机器台数、Ready 副本数 |
| 短窗口 + 燃烧率 | 只用月底日历平均 |
| 成本 SLI：GPU 闲置、request vs usage、流量异常 | 财务一张「省了 30%」无分项 |

好 SLI 三条，缺一条就不要上看板当刹车：

| 条件 | 意思 | 反例 |
|------|------|------|
| **用户有感** | 失败时用户废了某次操作 | CPU 90%、磁盘 80% |
| **可测** | 有事件流或探针，分母清楚 | 「体验好」「机器够」 |
| **能告警** | 能设窗口和阈值，能路由到人 | 季度满意度问卷 |

**打个比方**：SLI 是体温计读数，SLO 是医生定的「正常范围」，SLA 是保险合同写的赔付线，Error Budget 是「这个月还能发烧几次」。拿 CPU 当 SLI，就像拿室温当体温——房间热不代表你没发烧。

坏 SLI 不是「完全不看」，是**不能当 SLO 的输入**。CPU 给容量和 HPA 用（04-07）；机器台数给容量规划用。拿它们当可用性，集群全绿、下单全失败时你还在说没破线。

> **记住**：SLI 量用户；SLO 卡团队；SLA 卡合同；Error Budget = `1 − SLO`。CPU 和「机器台数」不是 SLI。成本是架构问题，不是财务周才出现的表。

**面试怎么说**：「我们内部用 SLO 和错误预算管发布，对外 SLA 另写更松的数。SLI 必须用户有感、可测、能告警，不用 CPU 冒充可用性。」

## 3. 原理

### 3.1 可用性算术：99.9 换成分钟

**一句话：** 99.9% ≈ 30 天 43 分钟可失败；预算是变更权不是躺平权。

**打个比方**：像手机流量套餐——99.9% 是「这个月还能用 43 分钟 2G 超速」，不是「全年不能断网一秒」。多一个 9，额度不是少 10%，是从 43 分钟掉到 4.3 分钟。

**现场走一遍**（周会，产品拿月历说「我们 99.95% 还能发」）：

1. 打开 SLO 看板，选 **30 天滚动窗口**。
2. 屏幕显示：

```text
SLO target:     99.9%
SLI (30d avg):  99.92%     ← 月历看起来「还行」
SLI (1h):       94.2%      ← 短窗已经红了
Error Budget:   remaining 12%  (burned 88%)
```

3. **口算分钟**：30 天 ≈ **43200 分钟**；失败预算 = `(1 − 0.999) × 43200` ≈ **43 分钟**。
4. 查事件：上周二开服 **10 分钟全红** + 昨天发布 **8 分钟 5xx** = 已用 18 分钟，还剩约 25 分钟额度。
5. 结论：月历 99.92% 掩盖了短窗事故；**短窗燃烧率**才是值班第一刀。

**输出解读**：

| SLO | 月失败预算 | 口算 |
|-----|------------|------|
| 99% | ≈ 7.2 小时 | 太松，内部很少当目标 |
| 99.9% | ≈ **43 分钟** | 面试默认档 |
| 99.95% | ≈ 21.6 分钟 | 再严一档 |
| 99.99% | ≈ **4.3 分钟** | 一次发布窗口就能烧光 |
| 99.999% | ≈ 26 秒 | 没有极强控制别写进 SLO |

| 屏幕字段 | 怎么读 | 高了找谁 |
|----------|--------|----------|
| SLI (30d avg) | 月历对账用 | 不能当唯一告警 |
| SLI (1h) | 正在发生的用户影响 | 短窗燃烧率 |
| remaining 12% | 还能发多少功能 | < 20% 冻实验 |
| 已用 18/43 分钟 | 口算消耗 | 哪次发布 / 故障烧的 |

99.9 → 99.99 不是「再加一个 9」。预算从 43 分钟掉到 4.3 分钟，**发布、滚动、演练、多 AZ 故障切换**都要重新计价。

**面试怎么说**：「99.9% 约 43 分钟/月失败预算，99.99% 约 4.3 分钟。月历平均会掩盖 10 分钟全红，所以用短窗和燃烧率告警。」

> **记住**：99.9% ≈ 43 分/月，99.99% ≈ 4.3 分/月。月历平均不是告警。

### 3.2 错误预算：停什么不停什么

**一句话：** 预算烧光停非必要发布；紧急安全补丁和止血变更不停。

**打个比方**：像信用卡刷爆了——停买新鞋（功能发布），但医院急诊（hotfix）仍得刷卡，不能把卡冻死。

**现场走一遍**（预算将尽，版本经理要发 A/B 实验）：

1. 看板：`Error Budget remaining: 8%`，长窗燃烧率 **1.2x**（慢烧）。
2. 版本经理：「还剩 8%，还能发吧？」
3. SRE 查冻结政策：

| 预算状态 | 停 | 不停 |
|----------|----|------|
| 还在（如 > 20%） | 仍受变更窗口约束 | 功能、实验、常规灰度 |
| 将尽（< 20%） | **A/B、新玩法、非必要扩面** | hotfix、回滚、安全修复 |
| 烧完（< 5%） | **功能发布、实验** | **hotfix、回滚、救 SLO 的变更** |

4. A/B 实验 = 功能发布 → **拒绝**，等预算回充或下窗口。
5. 同时有支付路径 hotfix → **绿色通道**，仍走金丝雀，但不冻。

**输出解读**：

```mermaid
flowchart LR
    A[预算还在] --> B[可发功能 / 实验]
    C[预算烧完] --> D[停功能发布和实验]
    D --> E[hotfix / 回滚仍放行]
    B --> F[不等于活动整点可以胡来]

    classDef ok fill:#16A34A,stroke:#14532D,stroke-width:2px,color:#fff
    classDef bad fill:#DC2626,stroke:#7F1D1D,stroke-width:2px,color:#fff
    classDef warn fill:#D97706,stroke:#92400E,stroke-width:2px,color:#fff
    class A,B,E ok
    class C,D bad
    class F warn
```

预算还在 **≠ 活动整点可以胡来**。游戏整点、战斗热更、合服窗口纪律在 [08-09](../../08-游戏运维专题/09-游戏SRE稳定性/)。

**面试怎么说**：「预算烧光停功能发布和实验，不停 hotfix 和回滚。预算还在不等于活动可以胡来，窗口纪律另算。」

### 3.3 燃烧率：短窗叫人，长窗冻变更

**一句话：** 燃烧率短窗（1h/6h）叫人，长窗（3d/30d）冻变更。

**打个比方**：短窗像心电图——现在是不是心梗；长窗像体检报告——这周还能不能熬夜。只看心电图会误报；只看体检报告，心梗时已经晚了。

**现场走一遍**（凌晨告警：登录 5xx 上升）：

1. 告警页显示：

```text
SLO: 99.9%  →  allowed error rate: 0.1%
Current error rate (5m): 1.44%
Burn rate (1h):  14.4x    ← 按这速度 1h 烧掉月预算 2%
Burn rate (6h):   6.0x
Burn rate (30d):  0.9x
```

2. **口算燃烧率**：`1.44% / 0.1% = 14.4` → 燃烧率 **14.4x**。
3. 对照政策表：

| 意图 | 典型组合 | 动作 |
|------|----------|------|
| 正在崩 | 短窗口（约 1h）× **高燃烧（如 14.4x）** | **立刻叫人** |
| 真故障但稍慢 | 约 6h × **中燃烧（如 6x）** | 仍叫人 / 升 P1 |
| 慢漏 | 长窗口（约 3d～28d）× 燃烧率 ~1 | **周会冻变更**，不半夜叫 |

4. 本例：1h × 14.4x → **P0 叫醒**，不是等月底报表。
5. 若只有 30d 0.9x 绿、1h 也绿 → 周会讨论节奏，不半夜叫人。

**输出解读**：

| 数字 | 含义 | 动作 |
|------|------|------|
| 14.4x | 1h 烧月预算约 2% | 立刻叫人 |
| 6x | 6h 级别真故障 | P1 |
| ~1x 长窗 | 匀速慢烧 | 周会冻变更 |
| 0.9x 长窗 + 14.4x 短窗 | 正在崩但月历还绿 | **信短窗** |

两条窗口**同时满足**才叫，是为了：只看瞬时 5xx，压测和毛刺会误叫；只看 28 天，正在崩时太晚。

**面试怎么说**：「燃烧率 = 当前错误率除以允许错误率。短窗高燃烧叫人，长窗约 1x 冻变更。月底 99.9% 绿不能否定正在崩的 10 分钟。」

### 3.4 FinOps 即可靠性：浪费的核就是扩不动

**一句话：** 闲置核和 over-provision 是可靠性问题——扩不动、HPA 顶满。

**打个比方**：像停车场——70% 车位被废弃车占着，真正来的车没位停（Pending）。不是「车位够」，是**有效余量**没了。

**现场走一遍**（高峰前，推理服务 Pending，财务说 GPU 利用率低）：

1. `kubectl get pod -n inference` → 多个 **Pending**，事件：`Insufficient nvidia.com/gpu`。
2. `kubectl top pod -n dev-gpu` → 开发环境 8 张卡，usage SM **< 5%**，但占满 quota。
3. `kubectl get pod -n gateway -o custom-columns=NAME:.metadata.name,REQ:.spec.containers[*].resources.requests.cpu,USAGE:` + top →

```text
NAME          REQ    USAGE
gw-1          4000m  320m     ← request 虚高
gw-2          4000m  280m
```

4. `kubectl get hpa -n gateway` → `desired=50, max=50` → **顶满 max**。
5. 结论：不是「没卡」，是闲置 dev 卡 + request 虚高 + HPA 打满，**付了钱却扩不动**。

**输出解读**：

| 浪费 | 可靠性怎么爆 | 第一刀 |
|------|----------------|--------|
| 核 / 卡闲置 | quota 被占满；要扩时 Pending | 回收闲置 + owner 标签 |
| **request 虚高** | 调度按 request 扣账 | rightsizing 当变更 |
| **HPA 乱扩** | 超时重试打满 max = **账单事故** | 限流 / 降 max / 修重试 |
| 流量走错路 | NAT / 跨 AZ 烧钱 | 路径优化，不是加副本 |

成本 SLI 举例：

| 成本 SLI | 用户 / 系统废了什么 |
|----------|---------------------|
| GPU 闲置率（SM / 显存长时间极低） | 付钱占着 quota，推理要扩时没卡 |
| request vs usage 比 | 调度骗自己；节点看起来满、应用很闲 |
| NAT / 公网 / 跨 AZ 字节阶跃 | 路径错了；延迟和账单一起坏 |

**面试怎么说**：「FinOps 不是财务表。闲置 GPU 占 quota 导致推理 Pending，request 虚高导致调度以为没资源——这是可靠性事故，不是省钱话题。」

> **记住**：闲置不是「财务不高兴」，是高峰没有余量。request 虚高是调度事故。HPA 打满是账单事故。

### 3.5 这条 SLO 值这笔钱

**一句话：** SLO 越紧成本越高；用错误预算和产品谈「这条线值多少钱」。

**打个比方**：像买保险——多 AZ 是意外险，双 Prom 是医疗险，sidecar 是每单抽成。不是险种越多越好，是问「这条 SLO 断了赔多少」。

**现场走一遍**（财务要砍 30%，提议关多 AZ）：

1. 登录 SLO **99.99%**（月预算 **4.3 分钟**）。
2. 问：单 AZ 故障切换要多久？RTO 记录 **6 分钟** → 一次 AZ 挂就超预算。
3. 算账表：

| 买什么 | 为哪条 SLO | 不值的时候 |
|--------|------------|------------|
| 多 AZ | 登录 / API / 支付要抗单 AZ | 每个区服计算面都跨 AZ，流量费接近计算本身 |
| 双 Prometheus | 告警必须活着 | 两套独立电话、两套高基数 |
| Istio sidecar | 需要网格：mTLS、拆分、熔断 | 每 Pod 固定税；没消费网格能力 |

4. 结论：登录 99.99% **值** 多 AZ；可以砍的是 **闲置 dev GPU** 和 **request 虚高**，不是多 AZ。
5. 30% 拆四桶（§6.4），每桶有回滚，不靠关 HA 凑数。

**面试怎么说**：「从 99.9 提到 99.99 要先问 4.3 分钟预算够不够覆盖滚动和一次故障。多 AZ、双 Prom 要讲清为哪条 SLO 服务；降本拆闲置和 rightsizing，不卖 SLO。」

## 4. 落地

### 4.1 生产怎么选

| 项 | 选 | 不选 |
|----|----|------|
| 主 SLI | 用户操作成功 / 延迟 / 正确性 | CPU、机器台数、网关探活 200 |
| 窗口 | 短窗 + 燃烧率；月历只做对账 | 只用 30 天平均当告警 |
| SLO vs SLA | 内部严、对外松；数字分开写 | 合同 99.9 直接当值班刹车 |
| 预算政策 | 烧完停功能 / 实验；不冻 hotfix | 烧完连回滚都停；或预算还在就整点胡来 |
| 金丝雀 | 自身错误率对 **baseline** | 对集群均值 |
| 成本 | 四桶可回滚；CMP 标签是手段 | 只报一个 30%；财务周直接点控制台 |
| 游戏口径 | 短窗口登录等 → 08-09 | 用本章 SaaS 表冒充游戏全表 |

拍 99.99 之前先量三个月实际错误率，再留余量。没有基线的 9 是口号。

### 4.2 政策落地你实际看到什么

不是再装一套 Prometheus。落地是三份能在周会打开的东西：

| 落地物 | 必须能回答 |
|--------|------------|
| SLO 看板 | 本窗口 SLI、剩余预算、短窗 / 长窗燃烧率 |
| 错误预算政策 | 烧到阈值停哪些发布；谁有权放行 hotfix |
| 成本看板 | 闲置、request/usage、流量异常；标签能归因到 owner |

看板最小集（版本周必须能投屏）：

| 板 | 必须有 |
|----|--------|
| 可用性 | 短窗成功率和燃烧率，不是月底一个数 |
| 发布 | 金丝雀 vs baseline；预算剩余 |
| 容量 | request vs usage；HPA desired / max |
| 成本 | GPU 闲置、流量阶跃；按 owner，不按「公司总计」 |

缺燃烧率：你会用月底 99.9 顶正在崩的 10 分钟。缺 request vs usage：你会一边喊扩容一边占满调度。

## 5. 核心配置

只动有证据的项。改 SLO 数字、改 request、改 HPA max，都是变更。

| 项 | 生产怎么用 | 改错会怎样 |
|----|------------|------------|
| SLO 目标 | 有基线再留余量；SLA 另写更松的数 | 拍 99.99 → 每次滚动都破 |
| 短窗 | 5m～1h 级看用户有感 | 只用 30d 平均 |
| 燃烧率 | 高燃烧短窗叫人；~1x 长窗进周会 | 只看瞬时 5xx 或只看月末 |
| Error Budget 阈值 | 如剩余 < 20% 冻功能发布 | 没有阈值 = 政策是 PPT |
| 金丝雀比较 | vs 同期 baseline / 旧版本 | vs 含金丝雀的集群均值 |
| `resources.requests` | 贴近 usage + 合理 buffer | 虚高 → 调度以为没资源 |
| HPA min / max | min 保底 SLO；max 防账单 | max 无上限 + 重试风暴 |
| CMP 标签 | `env` / `owner` / `cost-center` / `ttl` | 无标签则 30% 无法归因 |
| 成本 SLI 阈值 | GPU 闲置、NAT 字节阶跃 | 细节阈值和扫单 → 07-06 |

> **记住**：SLO、request、HPA max、标签，改哪一项都要能回滚。CMP 没有 owner 标签，FinOps 只是口号。

## 6. 命令与操作

值班先看合同，不是先重启、也不是先打开折扣计算器。

```bash
# 调度是否被 request 骗了
kubectl top pod -n <ns>
kubectl get pod -n <ns> -o custom-columns=\
NAME:.metadata.name,REQ_CPU:.spec.containers[*].resources.requests.cpu,REQ_MEM:.spec.containers[*].resources.requests.memory

# HPA 有没有顶满（账单事故候选）
kubectl get hpa -A
kubectl describe hpa <name> -n <ns>
```

| 目的 | 看什么 | 正常 / 异常 |
|------|--------|-------------|
| 本窗口还绿不绿 | 短窗 SLI + 燃烧率 | 短窗红 = 叫人，不管月底 |
| 还能不能发 | 剩余 Error Budget、长窗慢烧 | < 20% 冻实验 |
| 调度还有没有余量 | request vs usage、Pending | usage 0.3c、request 4c = 虚高 |
| HPA 是不是在烧钱 | `desired` 顶 `max` | desired=max = 账单 P0 |
| 成本哪一桶 | GPU 闲置、流量产品行、owner | 一个总计百分比 = 没答 |

典型 `kubectl top` + request 输出解读：

```text
NAME    CPU(cores)   MEMORY(bytes)
gw-1    32m          256Mi          ← 实际用量
REQ_CPU: 4000m                         ← request 是 usage 的 125 倍
```

燃烧率口算：`当前错误率 / (1 − SLO)`。99.9% 时错误率 1.4% → 约 **14x**，短窗该叫人。

值班口述四句：

1. 哪一条 SLI、哪个窗口、燃烧率多少
2. 剩余预算够不够撑过这次发布
3. 容量：request / HPA / Pending，不是「机器还很多」
4. 成本：闲置还是路径，owner 是谁；优化进变更单

### 6.1 预算周会

```
  剩余预算
       |
       +-- 充足 → 功能发布按原窗口；仍看短窗燃烧率
       +-- 将尽（如 <20%）→ 冻实验、冻非必要灰度
       +-- 烧完 → 停功能发布；hotfix / 回滚仍走绿色通道
```

### 6.2 金丝雀门禁：对 baseline，不对均值

```mermaid
flowchart LR
    A[金丝雀流量] --> B[canary 错误率]
    C[稳定流量] --> D[baseline 错误率]
    B --> E{canary 明显差于 baseline?}
    D --> E
    E -->|是| F[weight 归零 / 回滚]
    E -->|否| G[下一档]

    classDef bad fill:#DC2626,stroke:#7F1D1D,stroke-width:2px,color:#fff
    classDef ok fill:#16A34A,stroke:#14532D,stroke-width:2px,color:#fff
    class F bad
    class G ok
```

对集群均值的错：金丝雀 5% 流量、错误率 20%，全集群可能只从 0.1% 漂到 1.1%，均值仍「看起来还行」。

```yaml
gate:
  compare: canary_sli vs baseline_sli
  not: canary vs cluster_mean
  abort_if: burn_rate_short_window 过高 或 canary 连续差于 baseline
```

### 6.3 降本当变更

| 动作 | 观察 | 回滚 |
|------|------|------|
| request rightsizing | 调度 Pending、HPA 利用率、P99 | 改回旧 request |
| 降规格 / 减卡 | 延迟、队列、GPU SM | 改回机型 |
| 降 HPA max / min | 峰值是否 Pending、是否破 SLO | 改回 max |
| 收闲置环境 | 是否误伤备用 / 演练环境 | 标签 `ttl` 未到期不删 |

### 6.4 30% 怎么拆

| 桶 | 典型来源 | 不是这个桶 |
|----|----------|------------|
| **闲置回收** | 停掉的环境、零流量 LB、闲置 GPU | 把生产 buffer、多 AZ 当闲置砍 |
| **规格 rightsizing** | request 贴近 usage、机型降档、HPA 目标校正 | 把 HPA max 砍到峰值必挂 |
| **存储生命周期** | 日志 / 备份 TTL、冷热分层 | 关服立刻删备份（07-06） |
| **流量路径** | 镜像内网、少跨 AZ、少 NAT | 财务周乱改 CDN TTL |

四桶之和才是 30%。靠「我们很注重成本」没有数字 = 没答。

## 7. 生产排障

三问：哪一条 SLI 在哪个窗口破了？剩余预算还够不够发？钱是闲置、虚高 request、HPA 打满，还是路径烧的？


| 现象 | 先做什么 | 不要做什么 |

| 10 分钟全红，月历仍 99.9% | 短窗燃烧率；P0 | 「没破 SLO」 |

| 优化后 P99 炸 | 回滚变更 | 财务周继续点 |

## 8. 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| SLI / SLO / SLA 是一回事 | 错 | 测量 / 内部目标 / 对外契约 |
| Error Budget 是「能挂多久」 | 错 | `1 − SLO`，管变更权 |
| CPU、机器台数是好 SLI | 错 | 用户有感、可测、能告警 |
| 99.9% 就是全年不能挂 | 错 | 月约 **43 分钟**失败预算 |
| 月底 99.9% 绿就没事故 | 错 | 短窗口 + 燃烧率 |
| 预算烧完连回滚都停 | 错 | 停功能 / 实验，不冻 hotfix |
| 预算还在就可以活动整点乱发 | 错 | 窗口纪律仍在；游戏见 08-09 |
| 金丝雀看集群平均即可 | 错 | 对 baseline，防稀释 |
| FinOps 是财务的表 | 错 | 浪费的核 = 高峰扩不动 |
| request 越大越稳 | 错 | 虚高骗调度，Pending |
| HPA 自动扩所以没容量问题 | 错 | 打满 max 是账单事故 |
| 30% 报一个总数就够 | 错 | 闲置 / rightsizing / 存储 / 流量 |
| 多 AZ / 双 Prom / sidecar 都该砍 | 错 | 先问这条 SLO 值不值 |
| 优化可以财务周直接点 | 错 | 生产变更，要回滚 |

数字：99.9% ≈ **43 分/月**；99.99% ≈ **4.3 分/月**；30 天 ≈ **43200 分**；燃烧率 14.4x / 1h ≈ 月预算的 **2%** 一小时烧完；Error Budget = **1 − SLO**；金丝雀对 **baseline**；降本四桶。

易混：SLI vs SLO vs SLA；月底平均 vs 短窗燃烧率；停功能 vs 停 hotfix；集群均值 vs baseline；闲置 vs 生产 buffer；request vs usage；HPA 扩容 vs 账单事故；CMP 标签 vs FinOps 本身；多 AZ 成本 vs 该 SLO 的故障域。
