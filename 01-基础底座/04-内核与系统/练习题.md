## Q1

**★★★★★｜「你在白板上画一下 Linux 的分层结构，讲讲一次 write() 从业务代码到磁盘的路径。」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图：一次 write 的一生](知识点.md)、[四、干活：一次 write 在内核里](知识点.md)

### 场景

二面白板题，面试官画了个框说「这是你的业务进程，这是磁盘，中间有什么」。旁边候选人的图上画了一条从「业务」直连「磁盘」的箭头。

### 完整解答

> 🎯 **一句话**：业务在用户态跑，唯一通道是系统调用；write 先进 page cache 立刻返回，稍后批量回写磁盘。

分层从上到下：用户态（业务进程）→ 系统调用（唯一正门）→ 内核态（调度、内存、VFS/IO、网络栈，cgroup 限额横着卡）→ 硬件。讲 write 路径时按顺序点四步：

1. 业务线程调 `write(fd, buf, n)`——从用户态进内核态，耗时计入 `%sy`；
2. 内核把数据拷进 **page cache（页缓存）**，`write` 立刻返回「成功」——**此时还没落盘**；
3. 内核回写线程稍后攒一批刷盘——IOPS 的压力在这一步才出现；
4. 掉电会丢 page cache 里的数据，`fsync` 才强制落盘。

关键一句收尾：**这张图上没有任何箭头从业务直连硬件**——这就是「用户态能不能直接写磁盘」的图上答案。旁听那位候选人画的直连箭头，第一问就出局了。

> ⚠️ **别混**：write 返回成功 ≠ 数据落盘——「写日志没报错但宕机后丢了几秒日志」的根因就是 page cache。

### 再追问

- **「为什么日志把盘打满，通常是 IOPS 打满不是容量打满？」** —— 每条日志一次小 write，回写时是大量小 IO；治理方向是攒 8KB 批量写、减少次数，不是扩容量。
- **「怎么证明是写太勤？」** —— `strace -c -p <PID>` 短窗口看 `calls` 列，write 几万次就是了；**不要**先加核，加核不减少进门次数。

## Q2

**★★★★★｜「用户态和内核态是什么？系统调用的时候发生了什么？它和上下文切换是一回事吗？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、穿门：用户态、内核态与系统调用](知识点.md)

### 场景

一面八股连环问。前一问答完「内核帮我们干活」，面试官直接跟了这句——很多人栽在第三小问的等号上。

### 完整解答

> 🎯 **一句话**：CPU 特权级分 ring 0 / ring 3，业务在低特权级碰不了硬件，只能走系统调用这条受控通道。

三层展开：

- **用户态 / 内核态**：CPU 的两种特权级（**protection ring**，x86 上内核 ring 0、业务 ring 3）。内核态能碰硬件，用户态不能；对应虚拟地址空间的**用户空间 / 内核空间**两块。
- **系统调用（system call，syscall）发生时**：进程主动陷入内核，从用户空间切到内核空间执行内核代码，干完活返回——一次往返约 **100～300ns**，时间记在 `%sy` 里。典型：`open/read/write`、`socket/connect`、`clone`、`futex`。
- **和上下文切换的区别**：**不是一回事**。系统调用是**同一个进程**在两种特权级之间切（mode switch）；**上下文切换（context switch）** 是调度器把 CPU 从一个进程换给另一个进程，要保存/恢复寄存器，`vmstat` 的 `cs` 列，代价更高。

> ⚠️ **别混**：系统调用是**主动**切特权级；中断是硬件**被动**叫门（硬中断 hardirq 是硬件拉线，软中断 softirq 是内核推迟批量做的活，如收包）；上下文切换是**换进程**。三件事三个主语。

> 📝 **面试**：「用户态是餐厅前台，内核态是后厨，系统调用是传菜窗口——前台不能自己进后厨动火，每递一次菜扣一点时间账。」

### 再追问

- **「futex 是干什么的？」** —— 锁没抢到时进程在内核里睡眠等锁，一次锁竞争就是一次 futex 系统调用 + 等待；strace 里 futex 单次耗时高（usecs/call 大）就是锁竞争，往拆锁/06 查，**不要**归咎内核。
- **「一次 syscall 才几百 ns，为什么会成为事故？」** —— 单次可忽略，百万次就是 0.1~0.3 秒 CPU 被吃掉；账要算次数，不是算单次。

## Q3

**★★★★★｜「top 里的 %sy 和 %si 有什么区别？%sy 40% 你怎么排查？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、干活：一次 write 在内核里](知识点.md)

### 场景

活动高峰战斗服 top 显示 `%Cpu(s): 8 us, 40 sy, 0 wa, 0.5 si`，群里有人说「内核出问题了，重装吧」，有人说「先加 8 核」。

### 完整解答

> 🎯 **一句话**：%sy 是进程主动做系统调用，%si 是软中断（收包常见）；%sy 高先 strace 数次数，不加核、不重装。

| | `%sy` | `%si` |
|--|-------|-------|
| 谁在干活 | 进程**主动**做系统调用 | 内核**软中断**（网卡收包最常见） |
| 典型场景 | 百万次小 write、锁竞争 futex | 进站包打满、常单核接近 100% |
| 第一刀 | `strace -c -p PID` 看 calls | `mpstat -P ALL 1` 看哪个核 |

`%sy` 40%、`%us` 8% 的走读：先看 `%si` 高不高（不高，排除收包）→ `strace -c -p 28451` 采 5~10 秒 → 输出 `calls` 列 write 一万多次 → 结论是**进门太勤**。治理：日志攒到 8KB 批量写，100 万次降到约 125 次；不是加核，更不是内核 bug。

```text
% time     seconds  usecs/call     calls    errors syscall
 62.31    0.182341          12     15234           write      ← calls 第一：进门太勤
 18.42    0.053891         892        60           futex      ← 单次 892μs：锁竞争
```

> ⚠️ **别混**：`vmstat` 输出里的 `si/so` 是 swap in/out（换页），和 top 的 `%si`（软中断）共用两个字母、完全两码事。

> 📝 **面试**：「%sy 高不是内核坏了，是系统调用次数多——strace -c 看 calls 列，write 多就合并写，futex 高是锁竞争，epoll_wait 多查事件循环超时。」

### 再追问

- **「生产上 strace 能随便挂吗？」** —— 不能。`strace -c` 也要限定 PID + 短窗口（5~10 秒）采完就撤；活动服上 `strace -e trace=all` 长挂会明显拖慢进程。函数热点用 perf / 火焰图（→ 06、21），**不要**用 strace 找函数热点。
- **「%si 高、且只有一个核 100% 呢？」** —— 软中断打满单核，典型网卡收包中断集中；`mpstat -P ALL 1` 确认后往 06（软中断 CPU 侧）和 12（网络栈）走，strace 业务进程是白忙——收包活不在业务线程里。

## Q4

**★★★★★｜「journalctl 和 dmesg 分别看什么？journal 里显示 9/KILL，你能直接定 OOM 吗？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、死亡：退出码、双日志与死亡螺旋](知识点.md)

### 场景

凌晨逻辑服挂了，值班同学贴出 journal 的 `status=9/KILL` 就在群里写「内存不够，OOM 了，申请加内存」。你是复核人。

### 完整解答

> 🎯 **一句话**：不能——journal 只证明死法是 SIGKILL，凶手要去 dmesg 找；两本账交叉才算结案。

两本账的分工：**journal**（`journalctl -u 服务名`）收 systemd 和应用 stdout/stderr，能证明**退出码**和应用的 ERROR；**dmesg**（`journalctl -k`）是内核说的，OOM、I/O error、网卡 reset 都在这。

交叉结案四象限：

- journal `9/KILL` + dmesg 有 `Out of memory: Killed process 28451`（PID 对得上）→ 整机 OOM → 07；
- journal `9/KILL` + dmesg 干净 → **不是整机 OOM**，查 cgroup `memory.events` 的 oom 计数（限额杀）或审计人手 `kill -9` → 10；
- journal `1/FAILURE` + dmesg 干净 → 应用自己 exit(1)，翻 journal 里的 ERROR（连库、配置）；
- journal 有 `connection refused` → 依赖没就绪，查 unit 的 After/Requires。

> ⚠️ **别混**：SIGKILL 的来源不止 OOM Killer——人手 kill -9、kubelet 强杀都是 9；「9 = OOM」这个等号不成立。

> 📝 **面试**：「journal 是前台小票，记录顾客怎么走的；dmesg 是后厨监控，记录是不是保安把人架出去的——小票上只有 9 的时候，必须调监控。」

### 再追问

- **「容器里 dmesg 是空的，怎么看？」** —— 很多镜像不挂宿主 kmsg，容器内 dmesg 本来就可能是空；上**宿主机**看，或看 K8s 事件的 `OOMKilled` 和 cgroup `memory.events`。**不要**因为容器内 dmesg 空就下「没有 OOM」的结论。
- **「怎么看上一次开机的日志？」** —— `journalctl -b -1`；本次是 `-b`，时间段用 `--since "10:00"`。

## Q5

**★★★★★｜「凌晨收到『服务不可用』告警，你的第一眼是什么？为什么不能先重启？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、死亡：退出码、双日志与死亡螺旋](知识点.md)

### 场景

告警是「s3-logic 不可用」，群里已经有人敲「重启试试」，有人已经在开 top 找 CPU。你是值班负责人，60 秒内要给出方向。

### 完整解答

> 🎯 **一句话**：先问影响面，再 systemctl status 看退出码，双日志对上、证据落盘，最后才拉起——重启会毁证据。

60 秒四步：

```text
① 0–10s  影响面：单机还是整组？刚发版/刚改 unit？进不去还是进得去但卡？
② 10–30s systemctl status s3-logic：进程在不在？退出码 9 / 1 / 15？
③ 30–45s journalctl -u s3-logic -n 80 --no-pager + dmesg -T | tail -30，落盘留证
④ 45–60s 定责拉起：9→对 dmesg/memory.events；1→查 ERROR 和依赖；活着→ss -lntp、本机 curl
```

为什么不能先重启/先 top：top 只能看「活着的进程在干什么」，服务都挂了它什么都照不到；重启会清掉死前的内存形态、fd 数量、dmesg 时间线——**恢复手段同时是毁证手段**。退一步的底线：真要抢恢复，也先摘流量再 restart。

三问常备：**进程还在不在？还能不能变更？已有流量还通不通？**——只是慢用 `curl -w` 分段计时（→ 16）。

> 📝 **面试**：完整口径就是上面四步 + 一句收尾「不可用先 status 后日志，慢才 top；证据落盘再动手」。

### 再追问

- **「重启确实能恢复，难道不重启吗？」** —— 恢复优先级高时可以重启，但顺序是先落盘证据、先摘流量；且重启后必须补根因，**不要**把「重启能好」当结案。
- **「进程还在、端口也在听，但玩家连不上？」** —— 本机 `curl 127.0.0.1:port` 通不通：通 → 问题在中间链路（→ 12、16）；不通 → 进程假活/线程池卡死，抓栈（→ 05）。

## Q6

**★★★★★｜「容器里 free 显示 64G，Pod limit 2G 还是 OOM 被杀了，为什么？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、看世界：/proc、uname 与 cgroup 的两本账](知识点.md)

### 场景

开发拿着容器内 `free -h` 的截图（62Gi available）来找你「机器内存明明够」，同时 Pod 已经第三次 `OOMKilled`（退出码 137）。有人提议给机器加内存。

### 完整解答

> 🎯 **一句话**：free 读的是宿主机的 /proc/meminfo，容器真限额在 cgroup——两本账，OOM 只看后者。

机制：`/proc/meminfo` 是内核渲染的**宿主机**视图，容器没有换掉这份视图，所以 free 显示整机内存；而 K8s `limits` 落在 cgroup 上：

```bash
cat /sys/fs/cgroup/memory.max    # cgroup v2；v1 是 memory/memory.limit_in_bytes
# 2147483648                      ← 字节 = 2GiB，这组进程超过它就被杀（137）
```

结论：第三次 OOM 的根因是**容器实际用量顶到 2GiB 限额**，加机器内存没用。判断依据：监控看 `container_memory_working_set_bytes` 对比 limit；日志侧用 Q4 的交叉法（宿主机 dmesg 或 `memory.events` 的 oom 计数）。

> ⚠️ **别混**：整机指标（free、`%id`）结不了容器的事——`nproc` 同理返回宿主机核数，limit 1 核的容器里 Go 默认 `GOMAXPROCS` 跟着宿主机走，结果是 CPU **throttle**：宿主机很闲、容器 P99 照炸。

> 📝 **面试**：「容器里 free/top/nproc 读的都是宿主机账；真限额两处——内存 `memory.max`、CPU `cpu.max`；OOM 137 先对 limit，CPU 问题看 cpu.stat 的 throttled，不要信 free 结案。」

### 再追问

- **「top 里容器 CPU% 看着不高，为什么还慢？」** —— top 的百分比可能按宿主机核数做分母，天然偏低；以 `cpu.stat` 的 `nr_throttled/nr_periods` 为准。
- **「怎么在 K8s 侧快速确认是限额杀？」** —— `kubectl describe pod` 看 `Last State: OOMKilled`，配合 `memory.events`；**不要**只看容器内应用日志说「崩了」。

## Q7

**★★★★★｜「After / Requires / Wants 有什么区别？服务依赖 MySQL，unit 应该怎么写？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、出生：开机、systemd 与 fstab](知识点.md)

### 场景

逻辑服 unit 只写了一行 `Requires=mysqld.service`，每次机器重启后 logic 都先起来、连库失败刷屏几十秒——开发说「我明明声明依赖了」。

### 完整解答

> 🎯 **一句话**：After 管顺序、Requires 管生死、Wants 软绑；硬依赖必须 After + Requires 一起写。

| 指令 | 白话 | 管顺序？ | 对方挂了自己？ |
|------|------|:---:|------|
| After | 等它启动完再启我 | 是 | 照跑 |
| Requires | 没它不能活 | 否（可能并行起） | 被 systemd 停掉（发 SIGTERM） |
| Wants | 有它更好 | 否 | 继续跑 |

刷屏的根因：**Requires 只绑生死不绑先后**——systemd 可能并行拉两个，logic 起来时 MySQL 还没 listen。正确写法：

```ini
[Unit]
After=network-online.target mysqld.service   # 排序：等 MySQL 之后
Requires=mysqld.service                      # 硬绑：它挂我也停
Wants=redis.service                          # 软绑：Redis 挂我降级继续跑
```

游戏服常见折中：对 MySQL 只写 `After` + 应用层重连（数据库抖两秒不该整组逻辑服陪葬——Requires 会连坐）；`Requires` 留给「没有绝对不能跑」的本地 agent。

> ⚠️ **别混**：「有了 Requires 就不用 After」和「After 了就保险」都是错的——两者管的维度不同，一个都不能省。

### 再追问

- **「Requires 的对方挂了，我的服务会怎么样？」** —— systemd 给依赖方发 SIGTERM（15）停掉，所以硬依赖写太狠会造成连坐；**不要**对所有上游都无脑 Requires。
- **「Wants 的服务 enable 失败会阻断我启动吗？」** —— 不会，Wants 是软依赖，装不上/起不来都不阻断。

## Q8

**★★★★☆｜「Restart=always 加 RestartSec=0 有什么风险？生产的重启策略应该怎么写？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、死亡：退出码、双日志与死亡螺旋](知识点.md)

### 场景

某服务内存泄漏周期性 OOM，unit 写了 `Restart=always` + `RestartSec=0` 想「自愈」。结果凌晨机器 Load 冲高、同机其他服务被拖死，最后这个 unit 反而停在 failed，「自愈」失效。

### 完整解答

> 🎯 **一句话**：OOM + 秒级重启 = 死亡螺旋——杀、拉、吃满、再杀，最后 StartLimit 用尽停在 failed。

螺旋每一环都在放大事故：137 被杀 → RestartSec=0 立刻冷启动 → JVM 初始化把 CPU/内存打满 → 更快地再被杀；同机服务被冷启动的峰值拖死。更隐蔽的坑：热更脚本让进程正常退出（`exit 0`）换新包，`always` 把**旧进程**拉回来和新进程抢端口。生产写法：

```ini
Restart=on-failure          # 正常退出（发版热更）不拉回
RestartSec=5s               # 给机器和依赖喘息
StartLimitBurst=3           # 60 秒内最多试 3 次
StartLimitIntervalSec=60    # 超限进 failed，切断螺旋
```

进了 failed 的处理：`systemctl reset-failed myapp && systemctl start myapp`——**先**看为什么连续失败（dmesg、cgroup、配置），再 reset；只 reset 不修根因，起来再撞一次。

> ⚠️ **别混**：`always` ≠ 更稳——它连 `exit 0` 都拉回；OOM 场景里秒级重启是把「自愈」写成「自杀循环」。

### 再追问

- **「StartLimit 触发后停在 failed，算好事还是坏事？」** —— 好事，它切断螺旋；但必须配告警，否则就是「服务静默消失」。处理顺序是查根因 → reset-failed → start，**不要**上来就 start。
- **「发版脚本怎么和 Restart 策略配合？」** —— 热更走正常退出 + `on-failure` 不拉回旧进程；或 unit 显式 `ExecReload`。**不要**靠 kill 进程再赌 always。

## Q9

**★★★☆☆｜「systemctl 显示服务 failed，但端口明明有进程在听，怎么回事？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：开机、systemd 与 fstab](知识点.md)

### 场景

老服务迁机器，unit 照搬过来 `Type=forking`，`systemctl start` 两分钟后 failed。有人提议再 start 一次「重试」。

### 完整解答

> 🎯 **一句话**：Type=forking 靠 PIDFile 认主——PIDFile 路径写错/写晚，systemd 认为失败，但 fork 出的子进程还活着占端口：幽灵进程。

链路：`Type=forking` 的启动命令会 fork 出真服务、父进程退出；systemd 按 **PIDFile** 指的主进程 PID 追踪——路径写错或文件还没落盘，追踪超时 → unit failed；但那个子进程不在 systemd 视野里，**端口还 LISTEN 着**。此时再 start 就是两个进程抢端口（`Address already in use`）。

处理顺序：`ss -lntp | grep <port>` 找到幽灵 PID → kill 它（或确认它就是要保留的实例）→ `systemctl cat` 核对 Type 和 PIDFile 路径 → 再 start。根治：能前台跑就 `Type=simple`（Nginx `daemon off`）；反过来，配了会 fork 的老脚本却写 simple，父进程一退出 systemd 会把整棵 cgroup 杀掉——两个方向都错不得。

> ⚠️ **别混**：unit failed ≠ 没有进程；unit active（running）也不代表端口在听——两件事两套证据（systemctl / ss）。

### 再追问

- **「怎么避免 drop-in 把我的配置改了都不知道？」** —— `systemctl cat myapp` 看的是**生效后**的合并配置（含 `/etc/systemd/system/*.service.d/` 下的 drop-in）；改完 `daemon-reload`。**不要**只 cat 原文件。
- **「为什么配错 Type 会整棵进程树被杀？」** —— systemd 按 cgroup 管进程组，主进程退出就清理整组；fork 脚本配 simple 时主进程退出得太早，子进程还在跑就被连带清理。

## Q10

**★★★★☆｜「机器慢，你会怎么归类排查？」（附四张工单速答）**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [七、作战：五域归类与定责](知识点.md)

### 场景

你值班时四张工单同时进来：① Load 40、idle 70%；② 逻辑服 137、宿主机还有内存；③ %sy 40%、%us 20%；④ 容器里 free 显示 64G。组长要求你一句话派单。

### 完整解答

> 🎯 **一句话**：慢的先归五域（调度/内存/磁盘/网络/cgroup），挂的先 status 看退出码——归对格再开对应章。

五域第一眼：Load 高 + `%us` 高 → 调度（06）；MemAvailable 低 / dmesg OOM → 内存（07）；`%wa` 高 / await 高 / vmstat `b` 高 → 磁盘（08）；`%si` 高 / `ss -s` 异常 → 网络（12）；容器 P99 炸、宿主机闲 → cgroup（10）。

四张工单的答案：

- **①** Load 40、idle 70% → **高 Load 低 CPU**：`vmstat 1 5` 看 `b` 列（D 状态等 IO）和 `%wa` → 08/05。**别加核**，加核治不了等 IO。
- **②** 137、宿主机有内存 → 不是整机 OOM：交叉 dmesg 与 cgroup `memory.events` → 限额杀，07/10。
- **③** `%sy` 40% → 系统调用：分 si/sy 后 `strace -c` 看 calls → 本章四节。
- **④** 容器 free 64G → cgroup 结案：看 `memory.max` → 本章五节。

`vmstat` 读法（丢第一行累计值）：`r` 是可运行队列、`b` 是 D 状态进程数、`wa` 是等盘时间——`r=2, b=18, wa=18` 就是「不是算力型，是等盘」的签名。

> 📝 **面试**：「急诊分诊——发烧归内科、骨折归骨科；先分诊再挂号，别一上来就改 sysctl（抗生素）或重启（截肢）。」

### 再追问

- **「为什么 Load 高但 CPU 闲，加核没用？」** —— Load 统计的是「运行 + 不可中断等待」的进程数，`b` 高说明在等 IO，核再多也得等盘；**不要**用 Load 高直接推导加核。
- **「第一刀你敲什么命令？」** —— 挂的 `systemctl status`，慢的 `vmstat 1 5` + `mpstat -P ALL 1`——两条就把五域过了一遍。

## Q11

**★★★★☆｜「昨天加了块数据盘改了 fstab，今早重启 SSH 上不去了，怎么办？另外内核升级你怎么验收？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：开机、systemd 与 fstab](知识点.md)、[五、看世界：/proc、uname 与 cgroup 的两本账](知识点.md)

### 场景

fstab 里写的是 `/dev/sdb1 /data xfs defaults 0 0`。机器 ping 得通、SSH 超时。有人建议「等一会儿再试」。

### 完整解答

> 🎯 **一句话**：fstab 挂载失败卡在 emergency，sshd 排在挂盘后面——签名就是「ping 通 + SSH 超时 + 刚改过 fstab」，走 VNC 救援改 UUID。

开机顺序：BIOS/UEFI → GRUB 选内核 → 内核挂 `/` → systemd（PID 1）→ 按 fstab 挂其它盘 → network-online → sshd。fstab 挂载失败卡在「挂其它盘」，sshd 根本轮不到启动。救援五步：

```text
① 云 VNC / 串口登录（不是 SSH）
② GRUB 按 e，linux 行末加 rd.break；已部分起来可 systemctl isolate rescue.target
③ mount -o remount,rw /
④ blkid 查 UUID；注释坏行或改成 UUID=a1b2c3d4-...
⑤ mount -a    # 必须无报错再 reboot
```

坏行的坑是 `/dev/sdb1` 这种**设备名重启后会变**（sdb1→sdc1），UUID 稳定。机器还能 SSH 时直接改 fstab + `mount -a` 验证即可。

内核升级验收：`uname -r` 到位 + `dmesg` 无 oops；grub **留上一版**可回滚；当变更管理——有窗口、有值守，关掉无人值守自动升级，不在活动窗口升。

> ⚠️ **别混**：fstab 里设备名和 UUID 不是写法偏好——设备名重启漂移是实打实的故障源，这是「会挂」和「不会挂」的区别。

### 再追问

- **「改完 fstab 怎么验证不重启？」** —— `mount -a` 无报错 + `findmnt` 确认挂上；**不要**靠「下次重启见分晓」。
- **「怎么确认我没登错机、内核对不对？」** —— `uname -a`（主机名 + 内核版本 + 架构）和 `hostnamectl`；云上主机名被 cloud-init 改回去、`/etc/hosts` 本机名对不上导致 sudo 慢，都是这台命令的延伸排查。

## Q12

**★★★★☆｜「systemd 是什么？它和 cgroup 什么关系？你怎么跟面试官概括一台 Linux 服务器？」**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [五、看世界：/proc、uname 与 cgroup 的两本账](知识点.md)

### 场景

面试官连续追问「systemd 凭什么管所有服务」「K8s 的 limits 最终落在哪里」，最后补了这句开放题。很多人只会背「systemd 是 init」。

### 完整解答

> 🎯 **一句话**：systemd 是 PID 1，管三件事——拉服务、收 journal、挂 cgroup；概括一台服务器就是骨架五件套。

- **拉服务**：`systemctl start/stop/status`，按 unit 依赖图（After/Requires/Wants，Q7）决定拉起顺序；
- **收 journal**：应用的 stdout/stderr 和退出码都进 journal（Q4、Q5）；
- **挂 cgroup**：每个服务一个 cgroup 组，CPU/内存限额落在这——**K8s 的 limits 本质就是 cgroup 参数**（Q6 的 `memory.max` / `cpu.max`），所以「systemd 凭什么管服务」的底层答案是 cgroup 分组 + 信号。

收束到「一台服务器的骨架」五件套（合上书要能默画）：**一堵墙**（syscall 唯一门，业务不能直连硬件）、**一个管家**（systemd = PID 1，上面三职）、**两本账**（journal 应用+退出码 / dmesg 内核 OOM/盘/网卡）、**一层限额**（cgroup：throttle、限额 OOM）、**五格分诊**（调度/内存/磁盘/网络/cgroup → 06 07 08 12 10）。

> ⚠️ **别混**：骨架不回答「为什么慢」——五格只是分诊台，格内细账在对应章；也别拿整机指标（free、%id）结案容器的事。

> 📝 **面试**：按「墙、管家、账、限、诊」五个字背，每个字都能再展开一层——这就是「讲讲 Linux 系统分层」的完整结构。

### 再追问

- **「cgroup 先认哪个文件？」** —— 内存 `memory.max`、CPU `cpu.max`（v2）；看被限没限看 `cpu.stat` 的 throttled 计数、`memory.events` 的 oom 计数。细账 → 10。
- **「为什么说『重启试试』会坏事？」** —— 它同时清掉 journal/dmesg 的时间线、内存形态和 fd 状态（Q5）；恢复和毁证是同一个动作。

## Q13

**★★★★☆｜vmstat 一屏怎么分到五域？60 秒剧本四步？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：五域归类与定责](知识点.md)

### 场景

Load 高、有人要重启。你只有 60 秒决定甩 06/07/08/12/10 哪一章。

### 完整解答

> 🎯 **一句话**：**r/b/wa 定域 → 每域一眼指标 → 带一行证据甩章**；没分型就重启 = 毁证。

```bash
vmstat 1 3    # 丢第一行
free -h
df -h && df -i
```

| vmstat | 域 | 下一刀 |
|--------|-----|--------|
| r 高 us/sy 高 | CPU | mpstat → 06 |
| b↑ wa↑ | 磁盘 | iostat → 08 |
| available 低 | 内存 | dmesg → 07 |
| 四线全平 | 网络/cgroup | → 02/10/12 |

### 再追问

- 为什么先 vmstat 再 top？——分型比盯一个进程快（Q10）。
