## Q1

**★★★★★｜「一台生产机怎么加固？」把三层五闸讲全。**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [一、一张图：一台裸机的加固一生](知识点.md)

### 场景

面试开场题。追问准备：「哪道闸最重要」「为什么叫纵深防御」。

整章地基——三层五闸。

先自己试试：入口/权限/发现三层各有哪些闸？

### 完整解答

> 🎯 **一句话**：入口、权限、发现三层五闸，纵深防御——一道被突破，下一道还在。

十个阶段收三层：**入口层**（①减面关服务关端口 ④SSH key only ⑤默认 DROP 的墙）、**权限层**（②实名账号 ③sudo 白名单 ⑥SELinux Enforcing）、**发现层**（⑧auditd 离机 + AIDE + fail2ban），外加贯穿的 ⑦安全 sysctl、⑨漏洞闭环、⑩入侵响应。第一刀命令按层背：`sshd -T`+`iptables -L`、`sudo -l`+`getenforce`、`ausearch`+`aide --check`。

> 📝 **面试**：「按三层五闸背，每道闸一句『拦什么、第一刀查什么』；追问哪道最重要，答纵深——没有最重要，只有最薄弱。」

### 再追问

- 五道闸都过了就安全吗？——不保证；应用层 0day 从 80 直进业务进程，五闸管的是系统侧与提权侧。
- 值班拿到「auth 暴涨」告警先干嘛？——先分哪一层，再动手；别先改端口、别先 `setenforce 0`。

## Q2

**★★★★★｜加固第一步是什么？「最小化」怎么做？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [二、减面：少开门——服务、端口与 SUID](知识点.md)

### 场景

新一批机器装机验收，安全组问「你们这台开了 30 个监听端口，每个都是业务必需吗」。

减面三刀。

先自己试试：关服务、关端口、清 SUID，先做哪？

### 完整解答

> 🎯 **一句话**：先减面再装闸——关服务、关端口、清 SUID，把攻击面压到业务必需。

```bash
systemctl list-unit-files --state=enabled   # 逐个问「这台要它干嘛」
ss -tulpn                                   # 每行监听都要答「谁在听、给谁服务」
find /usr/bin /usr/sbin /tmp /data -perm /4000 -ls   # SUID 排查；/tmp 下出现 = 大概率被入侵
```

`avahi-daemon`、`cups`、`bluetooth`、无 NFS 时的 `rpcbind` 是经典该关；`/tmp` 下出现 SUID 文件不是「配置问题」而是**入侵信号**，先隔离再查。SUID 原理与 `/4000` 写法在 [25](../25-用户权限与特殊位/)，本章背结论。

> ⚠️ **别混**：减面是少开门（服务不跑），防火墙是门上加闸（服务还在、包进不来）——墙不能替代减面，一个没人维护的老服务挂 127.0.0.1，一次 SSRF 就摸到。

### 再追问

- 为什么不留着服务、只靠墙挡？——本地进程、SSRF、提权后都不走墙；服务本身在就是攻击面。
- `find -perm /4000` 的 `/` 什么意思？——任意权限位匹配（详讲在 [25](../25-用户权限与特殊位/)）。

## Q3

**★★★★☆｜空密码怎么扫？失败锁定怎么配？锁定、过期、删除什么时候用哪个？**

**覆盖**：必会 · 常用 · 常考

**对应**：知识点 [三、管人：账号治理——每个人一把实名钥匙](知识点.md)

### 场景

等保扫描报「存在空密码账号、密码策略不合格」；另外有个外包账号三个月后就不该再能登录。

管人——空密码与锁定。

先自己试试：passwd -S 怎么读？faillock 干什么？

### 完整解答

> 🎯 **一句话**：login.defs 定策略、faillock 锁失败、空密码零容忍；锁定/过期/删除各管一段。

```bash
awk -F: '($2==""){print $1}' /etc/shadow   # 空密码扫描，输出必须为空
passwd -S deploy                            # PS=有密码 LK=锁定 NP=空密码(事故)
chage -M 90 deploy; chage -E 2026-12-31 o  # 90 天换密码；到期不可登录(外包)
usermod -L deploy                           # 锁定
```

`/etc/login.defs` 四项：`PASS_MAX_DAYS 90`、`PASS_MIN_DAYS 2`、`PASS_MIN_LEN 8`、`ENCRYPT_METHOD SHA512`；失败锁定在 `/etc/security/faillock.conf`：`deny=5 / unlock_time=600 / fail_interval=900`（RHEL 8+ 的 pam_faillock，老的 pam_tally2 已废弃）。`/etc/shadow` 第二列速记：`$6$...` 有密码、`!`/`*` 锁定、**空 = 事故**。

> ⚠️ **别混**：**锁定**（可恢复，取证用）≠ **过期**（`chage -E` 到点自动失效，外包/临时账号）≠ **删除**（uid 可能被复用）。取证先锁定，治理用过期，确认无用再删。

### 再追问

- login.defs 改了为什么老账号没生效？——它只管**新用户/新密码**的默认值，存量要 `chage` 单独改。
- 离职账号什么时候收？——**当天**；通道侧（堡垒、key）同一条时间线，见 [28](../28-堡垒机与跳板机/)。

## Q4

**★★★★★｜`NOPASSWD: ALL` 为什么是事故？visudo 写错了怎么救？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [四、收权：sudo 白名单与文件底线](知识点.md)

### 场景

活动周有人提工单：「每次重启 nginx 都要找人，给 deploy 配个免密 sudo 吧」，写法就是那行著名的 `deploy ALL=(ALL) NOPASSWD: ALL`。

就是开头 NOPASSWD ALL。

先自己试试：白名单怎么写？visudo 锁死怎么救？

### 完整解答

> 🎯 **一句话**：sudo 白名单到具体命令；ALL 一旦写上，往往永远忘收回。

```text
Cmnd_Alias NGINXCTL = /bin/systemctl restart nginx, /bin/systemctl reload nginx
deploy ALL=(root) NGINXCTL
deploy ALL=(root) !/bin/su, !/bin/bash, !/bin/sh
Defaults timestamp_timeout=5
```

验收看**实际生效**不是看文档：`sudo -l -U deploy` 出现 `(ALL) NOPASSWD: ALL` = 加固等于没做。临时要 root 的正道是审批 + 堡垒限时授权 + 录屏（[28](../28-堡垒机与跳板机/)）。

visudo 语法错 = sudo 全体失效，逃生三条：改前留 root 会话或云 console；只用 `visudo`（自带检查）；改完 `sudo -l -U` 核对。**重启不会修好它**。

> ⚠️ **别混**：`!/bin/bash` 黑名单挡不住所有逃逸（`less`/`vim`/`find -exec` 都能弹 shell）——白名单的正解是「只放业务必需的二进制和参数」，黑名单只是第二道网。

### 再追问

- 共享一个 ops 账号行不行？——不行，`sudo -l` 分不清人，审计全拆。
- 文件底线数字？——配置 640、目录 750、`chmod 777` 是事故开头；`umask 022`（原理 → [25](../25-用户权限与特殊位/)）。

## Q5

**★★★★★｜SSH 加固核心是哪几件？改完怎么验证不锁死自己？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [五、锁门：SSH 加固清单](知识点.md)

### 场景

安全组抽查发现某台机器 `permitrootlogin yes`、`passwordauthentication yes`，负责人辩解「我端口改成 2222 了」。

就是开头「改 22 端口」。

先自己试试：SSH 加固底线哪几条？为什么只改端口不够？

### 完整解答

> 🎯 **一句话**：禁密码、禁 root、限来源、key only 四件；改端口只减扫描噪音。

```bash
sshd -T | grep -E 'permitrootlogin|passwordauthentication|allowusers|maxauthtries'
# 三个 no/限源是底线：permitrootlogin no / passwordauthentication no / allowusers deploy@10.0.0.0/8
sshd -t && systemctl reload sshd   # 语法检查后 reload，不掐现有会话
```

不锁死五步：留 console 后路 → `sshd -t` → **reload** 不是 restart → **另开新会话**验证（当前 ESTABLISHED 会话骗得了你）→ 防火墙同步新端口。协议细节与逐项深配在 [26](../26-SSH与远程访问/)。

> ⚠️ **别混**：改端口治**噪音**（日志刷多少），认证方式治**撞库面**（能不能被试出来）——拿改端口当加固完成是这章最经典的错答。

### 再追问

- key 被盗了怎么办？——从 `authorized_keys` 拿掉公钥 → 堡垒侧吊销 → 轮换可能被拷走的 key → 查 auditd/录像；**只改 passphrase 没用**，旧公钥还躺在 200 台机器上。
- `ClientAliveInterval 300 / CountMax 2` 管什么？——踢掉僵死会话释放 fd，不是安全闸但属清单项。

## Q6

**★★★★☆｜防火墙怎么做才算「白名单化」？从家里还能直连业务机说明什么？**

**覆盖**：必会 · 常用 · 常考

**对应**：知识点 [六、筑墙：防火墙白名单化](知识点.md)

### 场景

值班用家里的网络试了一下，居然能直接 ssh 到一台游戏服的 22 端口，群里有人安慰「反正你也有 key」。

筑墙——防火墙白名单化。

先自己试试：默认 DROP 怎么放行必要来源？

### 完整解答

> 🎯 **一句话**：默认 DROP + 白名单放行；从家还能直连 = 入口事故，不是口头提醒级别的事。

```text
iptables -L INPUT -n -v --line-numbers | head
# Chain INPUT (policy DROP ...)            ← policy DROP 才算白名单化
# 1  12M 890M ACCEPT all ... state RELATED,ESTABLISHED   ← 回包总闸在最前
# 2  456 27K ACCEPT tcp ... 10.0.0.0/8 tcp dpt:2222      ← SSH 来源是堡垒网段，不是 0.0.0.0/0
```

最小化清单：INPUT 默认 DROP；先放 `ESTABLISHED,RELATED`；SSH 只放堡垒 CIDR；业务口只放 LB/内网上游；非路由器 `ip_forward=0`；**出站也收**（NTP/DNS/制品库显式放）；改完另开会话验；`iptables-save` 持久化。改墙防锁死六步与 [17](../17-iptables与conntrack/) 同口径；云安全组与主机墙两层串联，优先收安全组。

> ⚠️ **别混**：**当前会话还在 ≠ 没锁死**——它是 ESTABLISHED 靠总闸活着；验证必须**另开一条新 ssh**。

### 再追问

- 「加了 ACCEPT 还是登不上」九成是什么？——规则顺序：`-A` 排到了 DROP 后面，用 `-I` 插队（命中即停 → [17](../17-iptables与conntrack/)）。
- 安全组和主机墙都要写吗？——两层串联；别在 ECS 里堆第二套本地墙「求稳」，健康检查源、CDN 回源网段最容易漏放。

## Q7

**★★★★☆｜安全向 sysctl 拧哪些？`kptr_restrict`、`dmesg_restrict` 防什么？**

**覆盖**：必会 · 常考

**对应**：知识点 [七、拧内核旋钮：安全向 sysctl](知识点.md)

### 场景

CIS 扫描报「内核指针可读、dmesg 未限制」；同事问「这不就是看个日志吗，至于吗」。

安全向 sysctl。

先自己试试：redirects/rp_filter 各防什么？

### 完整解答

> 🎯 **一句话**：安全 sysctl 收两件事——不被当跳板（forward/redirects）、少泄露内核布局（kptr/dmesg）。

```text
# /etc/sysctl.d/99-security.conf
net.ipv4.conf.all.accept_redirects = 0    # 不听 ICMP 重定向
net.ipv4.conf.all.accept_source_route = 0 # 不收源路由
net.ipv4.tcp_syncookies = 1               # SYN Flood 缓解
net.ipv4.ip_forward = 0                   # 非路由器不开转发
net.ipv4.conf.all.rp_filter = 1           # 反向路径校验
kernel.kptr_restrict = 2                  # 内核指针打码，/proc/kallsyms 全是 0
kernel.dmesg_restrict = 1                 # dmesg 仅 CAP_SYSLOG
kernel.yama.protected_symlinks = 1        # /tmp 竞态软链提权防护
```

内核地址布局是**提权利用的前置情报**——kallsyms/dmesg 泄的地址帮攻击者绕过地址随机化。`dmesg_restrict=1` 后普通用户 `dmesg` 报 `Operation not permitted` 是**正常表现**，排障用 `sudo dmesg`。改完 `sysctl --system`，机制与落盘在 [24](../24-内核参数与sysctl/)。

> ⚠️ **别混**：`syncookies=1` 只是 SYN Flood 缓解，不是防火墙替代品；**安全 sysctl 和性能 sysctl 分两份文件**（99-security vs 99-web），别混成「万能优化清单」。

### 再追问

- 禁 ping 要开吗？——可选项：开了探活/排障会疼，扫描项书面风险接受即可。
- 容器里改 sysctl 算数吗？——namespaced 的才生效，落盘与作用域细节在 [24](../24-内核参数与sysctl/)。

## Q8

**★★★★★｜Nginx 反代 502，本机 curl 8080 通——DAC 过了为什么还拦？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [八、第二道墙：SELinux 与 AppArmor](知识点.md)

### 场景

面试白板题。追问准备：「你的 shell 为什么不拦」「AppArmor 上同样的题怎么答」。

就是开头 setenforce 0——DAC vs MAC。

先自己试试：502 但 curl 通，第一刀查什么？

### 完整解答

> 🎯 **一句话**：DAC 问属主同不同意，MAC 问策略允不允许——root 也拦。

进程以 `nginx` 用户跑，读写文件 DAC 全过；但 SELinux 看**标签**：`httpd_t` 域默认不允许 `name_connect` 到任意端口 → AVC denied。你的交互 shell 不是 `httpd_t` 域，所以 **curl 通、Nginx 502**——「服务连不上但进程在」的 MAC 签名。

| 对比 | DAC | MAC |
|------|-----|-----|
| 谁说了算 | 属主/组/other 的 rwx | 内核里的强制策略 |
| root | 通常全能 | 仍可能被拦 |
| 拦了怎么修 | chmod/chown | 补布尔/策略，不是关 MAC |

> 📝 **面试**：「DAC 是房主同意就能进，root 是万能钥匙；MAC 是大厦门禁制度——房主本人也拦。chmod 解决不了 MAC 的拒绝。」

### 再追问

- AppArmor 同款题怎么答？——路径+profile 模型，`aa-status` 看 profile，enforce 拦 complain 只记。
- 「502 但进程在」还有别的可能吗？——上游挂了、keepalive 配错、墙没放上游口；先 `ausearch -m AVC` 分流。

## Q9

**★★★★★｜被 SELinux 拦了，第一刀敲什么？为什么不能先 `setenforce 0`？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [八、第二道墙：SELinux 与 AppArmor](知识点.md)

### 场景

反代上线 502，群里已经有人把 `setenforce 0` 的命令打出来等着发了。

被 SELinux 拦了。

先自己试试：ausearch 怎么查？怎么正确放行？

### 完整解答

> 🎯 **一句话**：getenforce → ausearch -m AVC → setsebool；关 Enforcing 是事故不是修复。

```bash
getenforce                    # Enforcing
ausearch -m AVC -ts recent
# avc: denied { name_connect } for comm="nginx"
#   scontext=system_u:system_r:httpd_t:s0    ← 谁想干
#   tcontext=system_u:object_r:http_port_t:s0 ← 碰什么
setsebool -P httpd_can_network_connect on    # 缺布尔的正修法
```

修法优先级：布尔值 `setsebool -P` → 评审后 `audit2allow` 生成策略模块（不盲装）→ 临时 Permissive 只给这台、当天回。标签看不懂不要瞎 `chcon -R`，先 `getsebool -a | grep httpd`；恢复默认上下文用 `restorecon -Rv`。看标签：`ls -Z`（文件类型）、`ps -eZ`（进程域）。

> ⚠️ **别混**：`setenforce 0|1` 只切 Enforcing/Permissive，**回不到 Disabled**（要改配置重启）；`setenforce 0` 之后就没人拦了——它是排查窗口不是修复。

### 再追问

- audit2allow 直接装有什么风险？——把「当前被拒的能力」整条写进策略，等于自己开面。
- 为什么 curl 不被拦？——你的 shell 域不是 `httpd_t`，策略按域不按用户。

## Q10

**★★★★☆｜Enforcing/Permissive/Disabled 差在哪？上了 K8s 还要 SELinux 吗？**

**覆盖**：必会 · 常考

**对应**：知识点 [八、第二道墙：SELinux 与 AppArmor](知识点.md)

### 场景

同事说「我们节点都上 K8s 了，SELinux 早就关了，宿主机加固无所谓」。

三模式与容器。

先自己试试：Enforcing/Permissive/Disabled 差在哪？

### 完整解答

> 🎯 **一句话**：Enforcing 拦且记、Permissive 只记不拦、Disabled 连审计都没有；容器不豁免宿主机。

- **Enforcing**：拦 + 记 AVC，生产目标状态。
- **Permissive**：只记不拦——排查窗口可用，**当天回**；它不是「开着 SELinux 在防护」。
- **Disabled**：连审计都没有，等于拆除，**不要写进生产镜像**。

K8s 节点常见关 SELinux 是 runtime/CSI 兼容性的**现实妥协**，不是最佳实践；两条纪律：不能拿「上了 K8s」当关 MAC、开密码登录的理由（容器隔离 PSS/RBAC → [03-13](../../03-Kubernetes/13-RBAC与安全/)，不替代宿主机 MAC——宿主机被拿下，容器隔离只是减速带）；能 Enforcing 的宿主机尽量保持。

> ⚠️ **别混**：Permissive ≠ Enforcing——它只记不拦；Permissive 还能看到 AVC（排查用），Disabled 什么都没有。

### 再追问

- 怎么把一台机器临时切成排查窗口？——`setenforce 0`，**当天回** `setenforce 1`；`sestatus` 看 config 与当前模式两个值。
- AppArmor 的对等三态？——enforce / complain / 无 profile。

## Q11

**★★★★★｜history 空了能结案吗？AIDE 什么时候 init？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [九、站岗：fail2ban、auditd 与文件完整性](知识点.md)

### 场景

安全事件复盘：涉事机器 `history` 是空的，有人建议「重新做一次 AIDE 基线」收尾。

留痕——auditd vs history。

先自己试试：AIDE 什么时候 --init？

### 完整解答

> 🎯 **一句话**：history 可清可改，追责靠 auditd 离机；AIDE 只能在确认干净时 init。

**auditd** 是内核审计子系统：`-w` watch 路径、`-p wa` 写/属性、`-k` 检索钥匙；`ausearch -k sudoers` 直接查谁动了 sudoers。`history` 只是用户 shell 里的记事本，`history -c` 一秒清空、root 能改日志——本机 audit.log 也不够，必须**离机转发**（→ [23](../23-日志运维/)）。

AIDE 基线是**出厂照片**：干净安装后 `aide --init`，之后 `aide --check` 对差异；**中招后再 init = 把后门写进信任根**。报变了先**对变更单**：补丁窗口、发版对得上 → 更新基线留记录；对不上 → 隔离取证。只监控 /etc 不够，后门常在 /usr/bin。md5sum 手工基线是土办法版；IMA 是内核侧度量架构，知道它是「更靠近内核的同类」即可。

> ⚠️ **别混**：AIDE 报变 ≠ 入侵——先对变更单；auditd 事件 ≠ 有人工登录——按账号和来源 IP 再对一层。

### 再追问

- auditd 该 watch 哪些路径？——passwd/shadow/sudoers/sshd_config 至少四个，`-k` 分钥匙。
- `last` / `lastb` 各看什么？——成功登录 / 失败尝试；`Accepted publickey` 来自非堡垒 IP = 入口事故。

## Q12

**★★★★☆｜fail2ban 挡得住什么、挡不住什么？**

**覆盖**：必会 · 常用

**对应**：知识点 [九、站岗：fail2ban、auditd 与文件完整性](知识点.md)

### 场景

`fail2ban-client status sshd` 显示 `Total banned: 120`，负责人以此为据说「入口没问题」。

fail2ban 边界。

先自己试试：挡得住什么？挡不住什么？

### 完整解答

> 🎯 **一句话**：fail2ban 挡的是失败尝试（扫描/撞库），挡不住失窃的合法 key。

机制：tail 认证日志 → `findtime` 窗口内失败满 `maxretry` → 调 iptables/nftables 封 `bantime` → 到期解封。三个数字：`maxretry=3 / findtime=600 / bantime=3600`。`Total banned` 高说明扫描多，**不证明入口合格**——仍要核对密码通道关没关、从家能不能直连。

> ⚠️ **别混**：加大 `bantime` 治不了失窃 key——合法 key 的操作一次失败都没有；失窃 key 的解法是吊销 + MFA + 查录像（[28](../28-堡垒机与跳板机/)）。

### 再追问

- 为什么 fail2ban 要能写防火墙？——它的封禁动作就是调 iptables/nftables 加 DROP。
- 发现入侵的信号除了日志还有什么？——AIDE 对不上变更单、未知 SUID、非预期外连、auditd 对关键文件的异常写。

## Q13

**★★★★☆｜漏洞怎么管？CIS 扫描几十条不过，每条都要修吗？**

**覆盖**：必会 · 常考

**对应**：知识点 [十、闭环：漏洞管理与安全基线](知识点.md)

### 场景

安全部发来漏洞周报：本部门 37 个 CVE、CIS 基线 52 条不合格；老板问「下周能全清吗」。

闭环——漏洞与 CIS。

先自己试试：扫描 → 评估 → 补窗口怎么走？

### 完整解答

> 🎯 **一句话**：扫描给的是清单不是工单——评估定优先级，补窗口落地，CIS 分三类处理。

流程四步：① 扫描（OpenSCAP/Nessus/厂商 CVE 通告，镜像用 Trivy）→ ② 评估（CVSS × 暴露面 × 资产重要性，有公开 EXP 的优先）→ ③ 补窗口（维护窗口打补丁、灰度、回滚；应急用限源/WAF/关功能顶住；高危补丁要有明文 SLA）→ ④ 复核（AIDE 对预期 diff，更新基线）。

CIS/等保基线三类：**高危必修**（密码登录、root SSH、SELinux Disabled、777、无审计）；**架构冲突书面接受**（NAT 机就是要 `ip_forward=1`，文档+扫描白名单）；**噪音书面接受**（banner、禁 ping）。等保是合规底线不是安全上限。正解是**加固基线镜像出厂**滚动换机，中招机器重装基线，不在染毒机上「修到绿」。

> 📝 **面试**：「扫描过了 ≠ 不会被入侵，基线不是 IDS——发现入侵靠站岗三件（auditd/AIDE/fail2ban）。」

### 再追问

- 打完补丁 AIDE 全红怎么办？——对变更单：预期变更 → 更新基线留记录；这才是流程闭环。
- 新机验收过线标准？——`sshd -T` 三项、Enforcing、`sudo -l`、policy DROP、auditd/chronyd enabled，最后**办公网直连应失败**。

## Q14

**★★★★★｜发现入侵第一步做什么？接到安全告警 60 秒怎么走？**

**覆盖**：核心 · 必会

**对应**：知识点 [十一、出事：入侵响应与定责](知识点.md)

### 场景

凌晨 AIDE 报 /usr/bin/ssh hash 变了、对不上任何变更单；`last` 里有一条非值班窗口的登录。

就是开头 Failed password 炸群——入侵响应。

先自己试试：60 秒四步怎么走？

### 完整解答

> 🎯 **一句话**：先网络隔离不关机——内存里有活证据；60 秒三问先分层再动手。

四步：① **网络隔离**（拔安全组/改 iptables，**不关机**——关机丢内存证据；不先 kill 后门，防外联靠断网）→ ② 快照取证（磁盘/内存/日志）→ ③ 影响面（支付库？横向了哪几台？key 被拷走多少？）→ ④ 清理收尾（轮换密钥、**重装基线镜像**，不在染毒机上修到过线）。

```text
① 0–20s  门还在不在？sshd -T 关键项；iptables -L INPUT -n | head；办公网直连试一把（应失败）
② 20–40s 权拆没拆？sudo -l 是不是 ALL；getenforce；ausearch -m AVC 有没有新拒绝
③ 40–60s 看得见吗？auditd 是否 active；日志离机路径；aide --check 对不对得上变更单
```

> ⚠️ **别混**：中招后 `aide --init` 重建基线 = 把后门写进信任根；「history 空 = 没人来过」= 结案事故。

### 再追问

- 为什么不能先 `ps` 找到后门进程 kill 掉？——断网已防外联；先 kill 会惊动/销毁证据，取证优先。
- 清理为什么是重装不是查杀？——染毒机永远无法自证干净；重装基线镜像 + 轮换密钥才是闭环。
