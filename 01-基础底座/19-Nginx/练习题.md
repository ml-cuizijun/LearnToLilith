## Q1

**★★★★★｜活动开服登录 502，怎么在 60 秒内定责？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [一、一张图：一个请求在 Nginx 里的一生](知识点.md) · [六、归宿：200，还是 499/502/504/503](知识点.md) · 决策树见 [八、作战：5xx 与慢的定责](知识点.md)

### 场景

活动开服瞬间登录全 502。有人喊「重启 Nginx」，有人已经开始重启全部逻辑服。你只有跳板机。

### 完整解答

> 🎯 **一句话**：502 = 没拿到合法上游响应；第一刀 error.log 关键字，不动 Nginx。

502 的子类全写在 error.log 里，一个关键字一种病：

```bash
tail -100 /var/log/nginx/error.log
```

```text
connect() failed (111: Connection refused) while connecting to upstream   ← 没人 listen，起后端
connect() failed (110: Connection timed out) while connecting to upstream ← 路径不通，查安全组/路由
upstream sent invalid header while reading response header               ← 上游不是 HTTP，curl -v 看首字节
upstream prematurely closed connection                                   ← 上游崩/OOM 或 keepalive 错配
no live upstreams while connecting to upstream                           ← 全摘了，503 的近亲
```

```bash
ss -tlnp | grep 8080                              # 上游端口在不在听
curl -v http://10.0.1.20:8080/health              # 直连复现：refused / 慢 / 非 HTTP
```

**读数**：`111` 说明进程没起来或端口换了——去上游机起进程/修发布，不是重启 Nginx，更不是重启战斗服。只有 error.log 指向 Nginx 自己（fd 满、worker 异常）才动 Nginx，而且也不是 restart，是先 `nginx -t` 再 reload。

> ⚠️ **别混**：502 是「没拿到合法上游响应」，**不是**「上游超时」——连上了但读超时是 504。「连没连上」一分家，第一刀就定了。

> 📝 **面试**：「502 我先 tail error.log：111 起后端、110 查网络、invalid 看首字节、premature 查崩溃和 keepalive；no live upstreams 是 503。」

### 再追问

- 502 集中在发布后的一分钟？——max_fails 被动摘有滞后：先 down 摘机再停进程，就不会吃这段 502 雨。
- 上游进程在、端口在、还是 502？——换关键字看方向：invalid header 查上游是否直接吐了非 HTTP 内容（裸文本堆栈）。

## Q2

**★★★★★｜502 和 504 到底怎么分？各自的常见根因？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、归宿：200，还是 499/502/504/503](知识点.md)

### 场景

面试官：「都是 5xx，502 和 504 你怎么一句话分清？各举三个根因。」

### 完整解答

> 🎯 **一句话**：502 连不上或响应非法；504 连上了但 proxy_read_timeout 到点没读完。

| 对比 | 502 Bad Gateway | 504 Gateway Timeout |
|------|-----------------|---------------------|
| 本质 | 没拿到合法上游响应 | 连上了，等响应超时 |
| error.log | 111 / 110 / invalid header / prematurely closed | upstream timed out |
| 典型根因 | 后端挂、安全组拦、上游裸文本、上游 OOM 崩连接、keepalive 池错配 | 慢查询、下游依赖卡、超时链没对齐、缓冲落盘/盘满拖时间 |
| 第一刀 | `ss -tlnp` + `curl -v` 直连上游 | 两列时间做差 + 慢查询 |

504 的「假象」单独记：`$upstream_response_time` 很小、`$request_time` 顶到 timeout——上游早回完了，时间耗在 Nginx 侧（缓冲写临时文件、盘满、写慢客户端），`df -h /var` 一眼。

> ⚠️ **别混**：把 504 全归给「上游慢」——rt≫urt 的 504 锅在 Nginx 侧；加大 timeout 只是延长判决，不是治疗。

### 再追问

- 只把 Nginx 的 read_timeout 从 25s 调到 300s？——APP 15s 先超时，499 照飞；先对齐外短内长（语义 → [14](../14-HTTP与TLS/)）。
- 504 和 499 同时出现？——上游真慢 + 客户端更早放弃；优化方向在上游/依赖，不在 Nginx。

## Q3

**★★★★☆｜access.log 里刷 499，是谁的锅？怎么治？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [六、归宿：200，还是 499/502/504/503](知识点.md)（超时链语义 → [14](../14-HTTP与TLS/)）

### 场景

开服 P99 报警，access.log 一排 `499 rt=15.001 urt=14.9xx`。有人提议「把 Nginx 超时加大到 300s」。

### 完整解答

> 🎯 **一句话**：499 = 客户端先断开，锅不在 Nginx 也不在上游；治法是对齐超时链。

499 是 Nginx 的私有码：上游还没回，客户端（APP/SLB）先关了连接。`rt=15.001` 说明 APP 的 15s 超时先到——加大 Nginx 超时改变不了 APP 先放手。

正确姿势是「外短内长」从外到里逐层放宽：

```text
APP 15s < SLB 20s < Nginx proxy_read_timeout 25s < Java 硬超时 30s
```

外长内短 → 玩家看到失败而中间层还没到点，日志全是 499/504 假象；只调中间一层永远治不好。

> 📝 **面试**：「499 是客户端主动断开的 Nginx 私有码；先看两列时间确认上游是不是真慢，真慢优化上游，不慢对齐外层超时。」

### 再追问

- 499 的 urt 可以很大吗？——可以，「客户端不等了」和「上游慢」经常同时出现，别见 499 就说上游没问题。
- 499 的 rt 为什么正好等于外层超时值？——外层（SLB/APP）先到点先断，Nginx 才记 499；这个数字本身就是「谁先放手」的证据。

## Q4

**★★★★★｜request_time 和 upstream_response_time 怎么做差读法？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [六、归宿：200，还是 499/502/504/503](知识点.md)

### 场景

领导：「登录接口 P99 到 8 秒，是 Nginx 慢还是 Java 慢？」你的 access.log 里有 `rt=$request_time urt=$upstream_response_time` 两列。

### 完整解答

> 🎯 **一句话**：差值 rt−urt 就是耗在 Nginx 自己和客户端身上的时间——urt≈rt 打后端，rt≫urt 查本机。

```text
499 3.498 3.495    ← urt≈rt 且大：上游真慢，客户端不等了
504 30.001 29.998  ← urt≈rt 顶到 read_timeout：上游/依赖慢
502 0.002 -        ← urt 为 -：根本没连上，502 子类那套
504 30.001 0.045   ← rt≫urt：上游早回完，慢在 Nginx 侧（缓冲/盘/慢客户端）
200 0.045 0.042    ← 正常
```

聚合版一眼看全量：

```bash
awk '$9==504 {print $(NF-1), $NF}' access.log | sort | uniq -c | sort -rn | head
# 左列 rt 右列 urt：两组数贴在一起 = 上游慢；rt 大 urt 小 = Nginx 侧
```

前提是 log_format 里真打了这两列——没有它们等于蒙眼排障，查 P99 之前先补格式。

> ⚠️ **别混**：`$request_time` 从收到客户端第一个字节起算（含收请求体、等上游、写回客户端全程），不是「Nginx 处理耗时」；`$upstream_response_time` 含建连+发+等响应。502 的 urt 是 `-`（没连上），不要拿它做差。

> 📝 **面试**：「慢不先优 gzip：urt≈rt 打后端（慢查询/扩容），rt≫urt 查 Nginx 侧（df 查盘、缓冲、慢客户端）。」

### 再追问

- rt−urt 一直有 200ms 基线正常吗？——正常，收请求体+写客户端本来就耗时间；看突变不看绝对值。
- 这招和 curl -w 五段什么关系？——curl -w 是主动探测的做差（→ [02](../02-网络排查命令/)），两列时间是全量被动流水的做差；先被动后主动，口径一致。

## Q5

**★★★★★｜keepalive 三件套是什么？缺了会怎样？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、搭桥：upstream 池——选机、摘除与 keepalive](知识点.md)

### 场景

后端机器 TIME_WAIT 两万多，研发说「Nginx 加了 keepalive 32 为什么还这样」。

### 完整解答

> 🎯 **一句话**：三件套缺一不可——`keepalive N` + `proxy_http_version 1.1` + `Connection ""`。

```nginx
upstream lobby { keepalive 32; }
location /api/ {
    proxy_pass http://lobby;
    proxy_http_version 1.1;                # ② 到上游用 1.1
    proxy_set_header Connection "";        # ③ 清 hop-by-hop 头，连接才能回池
}
```

只写 ①：代理默认按旧版本转发、易带 `Connection: close`，每次请求新建 TCP——池等于没开，后端 TIME_WAIT 照样爆、高峰端口耗尽（TW 机制 → [13](../13-TCP与UDP/)，端口参数 → [24](../24-内核参数与sysctl/)）。

两个数字纪律：**池是每个 Worker 各一份**，`keepalive 32` × 8 Worker ≈ 256 条空闲连接，调到 2000 不是优化是把上游 fd 打满；上游空闲超时要**长于**池的复用周期，否则上游先关、Nginx 拿旧连接去用 → `prematurely closed` → 502。

> ⚠️ **别混**：`keepalive_timeout`（http 块，入口侧空闲保活，常 65s）≠ upstream 的 `keepalive N`（出口侧池大小）——一个管客户端到 Nginx，一个管 Nginx 到后端。

> 📝 **面试**：「三件套：upstream keepalive N、proxy_http_version 1.1、Connection ""；池按 Worker 各一份；上游空闲超时短于复用周期会打出 prematurely closed 502。」

### 再追问

- 怎么验证池生效？——后端 `ss -s` 看 TW 是否回落；Nginx 到上游的 ESTABLISHED 稳定在池量级，而不是每请求一条。
- 权重高的上游池要更大吗？——连接数随流量走，权重高的自然需要更多池连接，按「每 Worker 池 × Worker 数」和上游 fd 上限一起估。

## Q6

**★★★★★｜reload 和 restart 的区别？为什么改配置必须先 -t？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [七、换岗：reload 平滑换代](知识点.md)

### 场景

改了个 header，同事 `systemctl restart nginx`，大厅 HTTP 长轮询当场全断，玩家被踢回登录页。

### 完整解答

> 🎯 **一句话**：reload 换 Worker 不拆存量连接；restart 先停后起全拆。

reload（HUP）：Master 用新配置拉起新 Worker 接新连接，旧 Worker 不再接新、处理完存量再退（`worker_shutdown_timeout` 兜底强退）。restart：先停后起，所有连接重拆——长轮询/SSE 直接断线。

```bash
nginx -t                              # 语法检查：不过就不该 reload
nginx -s reload                       # 平滑换代
ps -o pid,ppid,etime,cmd -C nginx     # 确认新旧 Worker 交替（etime 一批新一批旧）
```

**为什么必须先 -t**：reload 时语法错 → 新 Worker 起不来，Master **拒绝换代**、旧配置继续服务——你以为换了其实没换上；`-t` 把这个坑变成桌面报错。日志切割用 `nginx -s reopen`（USR1，只重开日志 fd），不动配置不拆连接。

> ⚠️ **别混**：reload 平滑 ≠ 战斗 TCP 长连接能挂上来——reload 只救配置变更，救不了七层扛长连接的结构性错误，那要走四层 [18](../18-LVS与四层负载均衡/)/[20](../20-HAProxy与Keepalived/)。

### 再追问

- 回滚怎么做？——还原 conf → `nginx -t` → reload；不是 restart。
- USR2 是干嘛的？——热升级二进制（换 Master），进阶操作，要预演并写变更单，日常变更用不到。

## Q7

**★★★★☆｜proxy_buffering 开关各保护谁？盘满怎么拖出 504？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、搬运：缓冲、限流与静态](知识点.md)

### 场景

接口 504 但 Java 侧 P99 只有 40ms；`$request_time` 30s、`$upstream_response_time` 0.04s。有人要给 Java 扩容。

### 完整解答

> 🎯 **一句话**：rt≫urt 的 504 先查 Nginx 侧——`df` 看盘，缓冲写不进临时文件就能拖满总时间。

`proxy_buffering on`（默认）：先把上游响应收齐（内存不够落临时文件）再回客户端，**上游发完就解放**，不被慢客户端拖住。代价是落盘：盘满/慢盘时写 temp file 卡住，总时间被拖到超时——上游明明 40ms 就回完了。

```bash
df -h /var                     # 100% 就是它
ls /var/lib/nginx/proxy/       # 临时文件堆着没清
```

治法是清磁盘、治日志（[23](../23-日志运维/)），必要时 `proxy_max_temp_file_size 0` 禁落盘（大响应慎用）；不是给 Java 扩容，也不是加大 timeout。`off` 的场景：SSE/流式响应要边收边转，但慢客户端会更久地拖住 Worker——别把 off 当性能优化。

### 再追问

- 413 和这套什么关系？——姐妹篇：`client_max_body_size` 太小，热更大包报 413，`nginx -T | grep client_max_body_size` 一眼；和 502 无关。
- `proxy_request_buffering` 什么时候动？——大文件上传想边收边转上游时；默认先收齐再转，保护上游不被慢客户端拖住。

## Q8

**★★★★☆｜limit_req 的 rate/burst/nodelay 怎么配？429 和 503 什么关系？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、搬运：缓冲、限流与静态](知识点.md)

### 场景

领奖接口被脚本刷，Java CPU 100%。有人要「全站限流 1r/s」。

### 完整解答

> 🎯 **一句话**：`rate=100r/s burst=200 nodelay`——长期速率 + 桶深 + 突发立刻放行；超限默认 503，指定 429 更语义化。

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/s;
location /api/activity/ {
    limit_req zone=api_limit burst=200 nodelay;
    limit_req_status 429;
    proxy_pass http://lobby;
}
```

不写 `nodelay`：突发进桶**排队匀速**放行，延迟变差；写了：前 200 个立刻处理，超了直接拒。下载类按连接数限：`limit_conn conn_limit 10`。全站一刀切 1r/s 会把正常玩家全拒——限「接口 + 玩家维度」，不是限「全站」。

> ⚠️ **别混**：限流的 503（error.log 是 limit 相关）和「no live upstreams」的 503（上游全摘）是两回事——看日志分，不看码猜。NAT 出口会让 $binary_remote_addr 变成「按整栋楼」限流，要么换 key 要么上玩家 ID 限（[02-09](../../02-中间件与数据库/09-API网关与服务治理/)）。

### 再追问

- 为什么 429 比 503 好？——429 明确告诉调用方「你太快了，退避重试」；503 会被当成服务故障触发告警和熔断误判。
- burst 设多大？——按正常峰值突发估，宁小勿大：burst 是给正常抖动留的余量，不是给脚本留的。

## Q9

**★★★★☆｜Nginx 反代容量怎么估？fd 和哪些参数对齐？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：Master/Worker 进程模型与容量](知识点.md)

### 场景

面试官：「8 核机器扛反代，你能扛多少并发连接？写出依据。」

### 完整解答

> 🎯 **一句话**：一条反代请求占 2 个 fd，上限 ≈ worker_processes × worker_connections，还要和 nofile 对齐。

```text
反代并发上限 ≈ worker_processes × worker_connections ÷ 2   ← fd 成对占（客户端+上游）
对齐链：worker_connections ≤ worker_rlimit_nofile ≤ systemd LimitNOFILE ≤ ulimit
```

`worker_processes auto` = 核数（8 核 8 Worker）；`worker_connections 10240` 常见；`worker_rlimit_nofile 65535` 且 systemd 单元 `LimitNOFILE=65535` 要一致——中间任何一层小了都是隐形天花板。怀疑打满看 stub_status：`Active connections` 顶着上限、`handled` 明显小于 `accepts`（曾到达上限）；公网暴露必须 `allow/deny` 钉死。

> ⚠️ **别混**：Worker 多 ≠ 快——多 Worker 只为用多核，`auto` 就是上限口径，写多于核数是抢 CPU。Master 从不接业务连接。

### 再追问

- epoll 为什么扛得住？——单线程事件驱动，fd 就绪内核才叫醒，没有每连接一线程的切换开销；地基在 [12](../12-网络栈与Socket/)。
- 纯静态呢？——一条请求 1 个 fd，容量翻倍；且走 sendfile 不过 proxy（Q13）。

## Q10

**★★★☆☆｜upstream 算法怎么选？发布时怎么安全摘一台？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [四、搭桥：upstream 池——选机、摘除与 keepalive](知识点.md)

### 场景

三台 lobby 要发版。运维直接 `systemctl stop lobby`，然后 access.log 里 502 刷了一分钟。

### 完整解答

> 🎯 **一句话**：先 `down` 摘机 → `-t` → reload → 再停进程；直接杀进程会吃 max_fails 滞后的 502 雨。

算法选择：无状态同规格**轮询**（默认）；规格不一 **weight**；按源 IP 粘滞 **ip_hash**（玩家换 NAT/换网就破功）；长连接、单请求耗时不均 **least_conn**。被动摘除：`max_fails=3 fail_timeout=30s`——失败累计到 3 次摘 30s，窗口过后再试；**主动探活开源版很弱**，要主动 httpchk 上 HAProxy（[20](../20-HAProxy与Keepalived/)）。

正确发布顺序：

```nginx
server 10.0.1.20:8080 down;      # ① 人工确认摘除，不再接新流量
```

```bash
nginx -t && nginx -s reload      # ② 换代生效
# ③ 观察该机连接归零（ss / stub_status），再 systemctl stop lobby
```

`backup` 是「主池全挂才上」，不是热备轮询；全摘后 error.log 出现 `no live upstreams` → 503。灰度用 `weight=1` 对大 weight。**只加大 max_fails 掩盖故障** = 玩家多打几次死机，502 更多。

### 再追问

- ip_hash 粘得住吗？——按源 IP 哈希，玩家换出口 IP 就换机器；真要粘滞用应用层会话或 HAProxy 的 sticky（[20](../20-HAProxy与Keepalived/)）。
- 全摘为什么会 503 而不是 502？——没有可用上游时 error.log 写 `no live upstreams`，返回 503；502 是「打了但失败」。

## Q11

**★★★★☆｜location 优先级和 proxy_pass 尾斜杠，各翻什么车？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [三、认路：location 匹配、proxy_pass 与头改写](知识点.md)

### 场景

新机器 `.js` 请求全 404、登录接口 404。有人开始查 Java 代码。

### 完整解答

> 🎯 **一句话**：优先级 `=` > `^~`（跳过正则）> 正则按书写顺序 > 最长前缀；尾斜杠改写 URI。

```nginx
location = /health { return 200; }          # 精确命中即定
location ^~ /static/ { root /var/www; }     # 前缀命中后不再走正则
location ~* \.(js|css)$ { root /var/www; }  # 正则：谁先写谁先赢
location /api/ { proxy_pass http://lobby; } # 最长前缀
location / { proxy_pass http://lobby; }     # 兜底
```

没写静态块时 `.js` 被兜底反代吃进 Java——CPU 爆、还以为 Java 有 bug。`proxy_pass http://lobby/`（带尾斜杠）：location `/api/` 的前缀被**替换**，`/api/login` → 上游收到 `/login`；改错 URI 是**上游 404**，不是 502。验证不靠猜：`curl -v` + 上游 access 里的真实路径。

> ⚠️ **别混**：404 是「送错了地方」（URI 改写/路由错），502 是「地方对但没人应」——先分这两类再动刀。

### 再追问

- X-Forwarded-For 能信吗？——客户端可伪造，只信你管控的上一跳；`set_real_ip_from` + `real_ip_header` + `real_ip_recursive on` 收敛到真实玩家 IP。
- `^~` 为什么存在？——让前缀明确压过正则，静态目录不用和每条正则比大小。

## Q12

**★★★☆☆｜Nginx 的 TLS 怎么落？证书快过期怎么管？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [三、认路：location 匹配、proxy_pass 与头改写](知识点.md)（证书语义 → [14](../14-HTTP与TLS/)）

### 场景

玩家浏览器报证书过期，你才发现 fullchain 上周就该换了。

### 完整解答

> 🎯 **一句话**：fullchain + TLSv1.2/1.3 + 会话复用；blackbox 盯过期 7 天 P1，轮转走 -t + reload。

```nginx
listen 443 ssl http2;
ssl_certificate     /etc/nginx/ssl/fullchain.pem;   # 全链：缺中间证部分客户端失败
ssl_certificate_key /etc/nginx/ssl/privkey.pem;
ssl_protocols TLSv1.2 TLSv1.3;
ssl_session_cache shared:SSL:10m;                   # 会话复用，减握手
ssl_stapling on;
add_header Strict-Transport-Security "max-age=63072000" always;
```

轮转纪律：新 fullchain 放好 → `nginx -t` → `nginx -s reload`——**reload 不拆连接**，老连接继续、新握手用新证。过期监控用 [22](../22-监控与告警/) blackbox 的 `probe_ssl_earliest_cert_expiry`，**7 天 P1**，不等玩家报 expired。握手、证书链、SNI 语义全在 [14](../14-HTTP与TLS/)。

> ⚠️ **别混**：客户端到 Nginx 是 HTTP/2 ≠ Nginx 到上游也是 2——上游连接池常是 HTTP/1.1（keepalive 三件套，Q5）。

### 再追问

- 为什么必须 fullchain？——只发叶证书时部分客户端没有中间证可补，校验失败；链的语义 → [14](../14-HTTP与TLS/)。
- HSTS 是干什么的？——强制浏览器后续走 HTTPS（max-age 两年是常见值）；语义与风险 → [14](../14-HTTP与TLS/)。

## Q13

**★★★☆☆｜静态文件怎么优化？动静分离为什么能救 Java？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、搬运：缓冲、限流与静态](知识点.md)

### 场景

热更大包，出口带宽没满但登录接口 P99 翻倍——静态请求全在打 Java。

### 完整解答

> 🎯 **一句话**：静态走 `root` + sendfile 直接由内核发，不过 proxy 不占上游——这就是动静分离。

```nginx
location ^~ /static/ {
    root /var/www;
    sendfile on;                # 文件页直接进 socket，不进用户态来回拷贝
    tcp_nopush on;              # 和 sendfile 成对：攒满报文再发
    tcp_nodelay on;             # 关 Nagle，keepalive 上的小包不攒（Nagle → 13）
    gzip on;
    expires 30d;
    access_log off;             # 纯静态不打日志，减盘
}
```

sendfile 之所以快：数据从文件页直接进 socket，省掉「内核→用户态→内核」两次拷贝。可缓存的公共接口可上 `proxy_cache`（看 `X-Cache-Status`）；**玩家私有接口绝不 cache**——那是把 A 的数据发给 B 的事故。资源版本与 CDN 分发纪律 → [15](../15-DNS与CDN/)。

### 再追问

- 大文件 413？——`client_max_body_size` 不够，和 502 无关（Q7 追问同款）。
- tcp_nodelay 和 tcp_nopush 打架吗？——一个管「攒满再发」（大文件吞吐）一个管「小包别等」（低延迟），场景不同不冲突；机制 → [13](../13-TCP与UDP/)。

## Q14

**★★★★★｜白板：请求一生 + 499/502/504 定责 + 两列时间 + reload 纪律？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图](知识点.md) · [九、收口](知识点.md)

### 场景

白板综合：「活动 502 雨，从 error.log 到 upstream 到超时链，完整走读。」

### 完整解答

> 🎯 **一句话**：**出生→认路→搭桥→搬运→归宿→换岗**；两列时间做差；502 上游断/非法，504 网关等满，499 客户端先走。

```text
error.log: prematurely closed → 502
no live upstreams → 503
upstream timed out → 504
keepalive 三件套: upstream + proxy_http_version 1.1 + Connection ""
reload: nginx -t → reload → 验证；别 restart 砸长连接
```

| 码 | 第一刀 |
|----|--------|
| 502 | 上游退出码/OOM |
| 504 | rt≫urt 查上游慢 |
| 499 | 对齐超时链 → 14 |

> 📝 **面试**：动静分离救 Java 入口（Q13）。

### 再追问

- limit_req 429 vs 503？——主动保护 vs 无健康上游（Q8）。
