# HAProxy 与 Keepalived

> 防火墙一改两台都有 VIP，一半玩家打 A 一半打 B 会话全乱；haproxy 进程死了 VIP 还挂在本机，入口整段超时；还有人要把战斗 TCP 和登录 HTTP 一起塞进 Nginx「统一入口」。
> **本章回答**：一次故障里 VIP 的一生——平时谁挂它（VRRP）、主机倒了它怎么漂（GARP）、漂过去谁分流量（HAProxy）、后端坏了怎么摘（健康检查）、最坏时它怎么一分为二（脑裂）。
> **不讲**：LVS 的 NAT/DR/TUN 与 ipvsadm → [18](../18-LVS与四层负载均衡/)；Nginx 七层反代与 502/504 → [19](../19-Nginx/)；高可用总论与 RTO → [33](../33-高可用与容灾/)；超时链语义 → [14](../14-HTTP与TLS/)；抓包手法 → [16](../16-网络排障与抓包/)；云 SLB/专线 → [06](../../06-云平台/)。

**标记**：🎯重点 · 🔥难点 · ⭐常考 · 🔧实操

## 一、一张图：一次故障里 VIP 的一生

> 🎯 **一句话**：VIP 的一生六段——出生、上岗、故障、漂移、体检、脑裂；坏了先问它在哪一段。

```mermaid
flowchart LR
    A["出生<br/>VRRP 协商谁挂 VIP"] --> B["上岗<br/>GARP 宣告 · 玩家流量进来"]
    B --> C["故障<br/>track_script 发现主机/进程倒了"]
    C --> D["漂移<br/>backup 升主 · 再发 GARP · 流量切走"]
    D --> E["体检<br/>HAProxy 检查后端 · 摘/粘/分"]
    E -.->|通告被拦/分区| F["脑裂<br/>两台都有 VIP · 会话乱"]
    F -.->|止血| G["先停一台 keepalived"]
```

- 📖 **读图**
  - 🛤️ 主线是一条 VIP 在一次故障里的完整经历；Keepalived 管「VIP 在哪台」（出生/漂移/脑裂），HAProxy 管「流量怎么分」（体检）——**两层各管一段，混了就查不动**
  - 🩺 「体检」是常态段：VIP 没故障时 HAProxy 也在持续检查后端；值班大部分时间在管这一段
  - 💥 脑裂不是新故障，是「漂移」被掐断后的坏结局：该发生的切换只发生了一半

### 🧭 两层坐标系 🎯⭐

```mermaid
flowchart TD
    P["玩家"] --> V["VIP（Keepalived 决定在哪台）"]
    V --> H["HAProxy（frontend 收 → backend 选后端）"]
    H --> B["后端 server 池"]
```

- 📖 **读图**
  - Keepalived 的健康对象是「本机」（本机 HAProxy 活不活）
  - HAProxy 的健康对象是「后端」（server 活不活）
  - 两层检查、两层摘除，节奏不同：后端坏摘 server（秒级、常发生），整机坏摘 VIP（切主、低频大动作）

## 二、出生：VRRP 协商谁挂 VIP

> 🎯 **一句话**：VRRP 用优先级选主，谁的 priority 高谁挂 VIP；备机只在收不到通告时才上位。

**VRRP（Virtual Router Redundancy Protocol）**是 Keepalived 的心脏：几台机器共用一个虚拟 IP，一台 MASTER 挂着它，其余 BACKUP 待命。

- 📡 **VRRP 是 IP 协议号 112**，不是 UDP 也不是 TCP——防火墙写 `iptables -p vrrp` 或 `proto 112`；写成「放行 UDP 112」等于没放行，通告被拦 → 双方都觉得自己是主（脑裂引信，七节）。协议细节 → [17](../17-iptables与conntrack/)
- 📣 **通告走组播、只在二层**：主每 `advert_int 1s` 往 `224.0.0.18` 发一帧，**要求两台在同一二层广播域**。跨三层不可用——云上常禁组播，改单播：

```text
    unicast_src_ip 10.0.0.2        # 自己的物理 IP
    unicast_peer { 10.0.0.3 }      # 对端的物理 IP：两台互指
```

- 🧾 配置成对出现：两台 keepalived.conf **几乎完全一样**，只差 `state`（MASTER/BACKUP）和 `priority`（100/90）——VRID、auth_pass、VIP、网卡名任一不一致 =「互相听不懂」

> 💡 **打个比方**：两台像正值班和替补，靠班前会每秒喊到。替补连续几秒没听到，才顶上——**判定依据是「对方的声音」**，声音被捂住比人真倒下更危险。

### 📝 最小模板与三个字段 🔧⭐

```text
/etc/keepalived/keepalived.conf
vrrp_script chk_haproxy {           # 健康脚本（四节漂移的引信）
    script "killall -0 haproxy"     # 进程在不在（局限见三节）
    interval 2
    weight -30                      # 失败时 priority 减 30
}
vrrp_instance VI_1 {
    state MASTER                    # 初始姿态，不是权力
    interface eth0
    virtual_router_id 51            # VRID：同一二层内必须唯一
    priority 100                    # 真正的权力：100 > 90 者为主
    advert_int 1                    # 1s 一帧，失联判定 ≈ 3×advert
    authentication { auth_type PASS auth_pass 1111 }
    virtual_ipaddress { 10.0.0.100/24 }
    track_script { chk_haproxy }
}
```

- 🔑 **`priority` 决定一切**：高的当主；同优先级比 IP。**`state` 只是初始姿态**——写反了开机后照样按 priority 重选
- 🚪 **`virtual_router_id`（VRID）**：同一二层的 VRRP 房间号。两套集群撞 VRID → 互相抢主——**同网段多套必须错开**
- 🔐 **`auth_pass` 两台必须一致**，不一致 = 失联
- ⏱️ 失联判定 ≈ **3 个 advert 周期**（`advert_int 1s` 约 3s）
- 📬 通告帧带着发送者的 priority：备机「听帧比大小」——没有握手、没有协商
- 📏 priority 取值 1~255；VRRPv2 配 IPv4、VRRPv3 配 IPv6——两台版本行为要一致

> ⚠️ **别混**：**priority ≠ state**。面试答「state MASTER 的当主」只对开机一瞬间；运行中永远由（叠加 weight 后的）priority 说了算。

> 📝 **面试**：「VRRP 是 IP 协议 112、组播、只在二层；priority 选主，advert_int 1s、约 3 帧失联判切；VRID 同二层必须唯一，撞了互相抢主。」

### 🔍 现场：双机状态一眼对齐

> 🔍 **现场**：怀疑两台「不是一个 VRRP 实例」，跑这三条对齐。

```bash
grep -E 'state|priority|virtual_router_id|auth_pass' /etc/keepalived/keepalived.conf
journalctl -u keepalived -n 20 | grep -iE 'MASTER|BACKUP|FAULT'
tcpdump -ni eth0 vrrp -c 5
```

```text
state MASTER; priority 100; virtual_router_id 51; auth_pass 1111   ← 这台自认为是主
Keepalived_vrrp[812]: (VI_1) Entering MASTER STATE                 ← 最近一次升主动作
10.0.0.2 > 224.0.0.18: VRRPv2, Advertisement, vrid 51, prio 100    ← 只有 prio 100 在飞=单主正常
```

- 两台 vrid/auth 必须一致、priority 必须错开
- journalctl 里两台最近都有 `Entering MASTER STATE` → 脑裂或抢主已经发生过——时间点就是排查起点

## 三、上岗与故障：GARP 宣告，以及通告怎么停

🔥 haproxy 进程死了 VIP 还挂在本机——真凶往往是**没配 track_script**。大白话：**机器活着、通告照发，备机不知道该抢**。⭐（练习题 Q6）

> 🎯 **一句话**：VIP 生效 = 挂 IP + 发 GARP 刷全网 ARP 表；故障 = 通告消失，备机按 3 帧超时判定。

**GARP（Gratuitous ARP）**是 VIP 上岗的动作：对 VIP 发 ARP 应答（没人问也答），把「这个 IP 的 MAC 是我」刷进交换机和同网段 ARP 缓存。没有 GARP，IP 挂上了也没人知道该把包发给谁。

> 💡 **打个比方**：GARP 像搬家后在小区门口贴告示——主动广播「这间房现在归我」。谁家通讯录（ARP 表）没刷新，就还把信投去旧地址。

```bash
tcpdump -ni eth0 vrrp              # 看通告（proto 112）在不在飞
ip addr show eth0 | grep 10.0.0.100   # VIP 挂没挂在本机
```

```text
10.0.0.2 > 224.0.0.18: vrrp 10.0.0.2 > 10.0.0.3: VRRPv2, Advertisement, vrid 51, prio 100
# ← 主机每秒一帧；备机不发，只听
```

- 💀 **故障两种样子**
  - **整机挂**：通告戛然而止，备机 3 帧超时后升主（四节）
  - **进程挂**：机器活着、haproxy 死了，通告照发——这就是 `track_script` 存在的理由

#### ❓ 为什么 Keepalived 自己不知道 haproxy 死了？

- ❌ Keepalived 只关心「我还能不能发 VRRP 通告」——进程在、网卡在，通告就飞
- ✅ 同机 HAProxy 死活是**另一层**的事，必须用 `track_script` 翻译成 priority 下降
- 👉 `killall -0 haproxy` 只测**进程存在**——僵死不退出、listen 在但不干活（假活）测不出；要测「真能服务」写端口/HTTP 级脚本（`curl -sf http://127.0.0.1:8404/haproxy_health`）

> ⚠️ **别混**：`killall -0` ≠ 业务健康。假活要更深一层探活（六节 httpchk 同理）。

## 四、漂移：主机倒了，VIP 怎么搬到备机 🔥⭐

🔥 很多人以为 VIP 漂移连接无感——**错了**。大白话：**四层不会 mid-flight 把 TCP 搬到另一台；漂移瞬间打到旧 MAC 的帧会丢，客户端要重连**。⭐（练习题 Q3）

> 🎯 **一句话**：track_script 失败 → priority 100−30=70 < 90 → 备机升主挂 VIP 发 GARP → 流量整段切走。

```mermaid
sequenceDiagram
    participant K1 as Keepalived@主（prio 100）
    participant K2 as Keepalived@备（prio 90）
    participant SW as 交换机/玩家 ARP 表
    K1->>K1: chk_haproxy 失败 ×2（weight -30）
    Note over K1: 有效 priority 100−30=70 < 90
    K2->>K2: 3 帧通告没到（或收到低优先级通告）
    K2->>K2: 升 MASTER，ip addr add VIP
    K2->>SW: GARP：VIP 的 MAC 是我
    Note over SW: ARP 表刷新 1~2s<br/>整段切换 2~3s
    SW->>K2: 新连接全部打向备机
    Note over K1: 旧 TCP 连接随原进程死掉<br/>客户端重连后落到备机
```

- 📖 **读图**
  - 🧮 **weight 算术**：`weight -30` 让 100 变 70，**必须低于**对端 90 才切（200−30=170>90 就切不动）
  - ⏱️ **切换有感知**：GARP 刷 ARP 1~2s，整段 2~3s，期间新建可能丢一两次重试
  - 🔌 **旧 TCP 不搬家**：VIP 漂移救的是「新连接有地方去」，已建立连接随原进程断开、靠客户端重连——战斗 TCP 重连风暴就是这么来的

#### ❓ 为什么 VIP 漂了，旧 TCP 还是会断？

- ❌ VIP 只是「门口的门牌」——换门牌 ≠ 把屋里正在聊的人挪到隔壁屋
- ✅ TCP 四元组绑在原机进程/socket 上；备机是**另一台进程**，没有那份连接状态
- 👉 设计目标是「入口不因单点不可用」，不是「连接无感热迁移」；切主要低频、有预热

### 🔄 切完之后：抢不抢回 ⭐

原主修好重新加入，**默认抢占（preempt）**：priority 100 恢复 > 90，VIP 又切回来——刚稳定的会话再乱一次。低频会话用 **`nopreempt`** 配在 BACKUP 上：不主动抢回。代价：资源分布不再和 priority 对齐，要靠人工窗口切回。

> ⚠️ **别混**：**抢占 vs nopreempt** 是「修好后抢不抢回」，不是「故障时切不切」——故障切换永远会发生。

切主钩子：`notify_master` / `notify_backup` / `notify_fault`——升主时拉服务、发告警（[22](../22-监控与告警/)）：

```text
    notify_master "/usr/local/bin/vip_takeover.sh master"
    notify_backup "/usr/local/bin/vip_takeover.sh backup"
    notify_fault  "/usr/local/bin/vip_takeover.sh fault"
```

HAProxy 变更纪律：先 `haproxy -c` 再 reload，存量连接不拆（五节）。起不来先看 `journalctl -u haproxy -n 50`：常见死因是 bind 端口被占，其次是 backend 引用了不存在的 server 名。

> 📝 **面试**：「切主链：脚本失败 weight −30 → 有效优先级 70小于 90 → 备机升主挂 VIP → GARP 刷 ARP 1~2s → 新连接切走、旧 TCP 重连；修好默认抢回，要稳就 nopreempt。」

### ✅ 上线验收：切换必须演练过才算有 🔧⭐

```text
① tcpdump -ni eth0 vrrp -c 5        # 通告在飞、prio 是期望那台、vrid 正确
② 两台 ip addr show eth0            # VIP 只在主上一台；vrid/auth 一致、priority 错开
③ systemctl stop haproxy（主机）     # track_script 触发：watch ip addr 看 VIP 漂、计时 2~3s
④ systemctl start haproxy           # 恢复：观察抢回（或 nopreempt 不抢）
⑤ 外部 curl 入口 + Stats            # 新旧连接都落到该落的机器
```

- ③ 是关键一跳——**手工制造故障、亲眼看着 VIP 漂走再漂回**，比配置评审更有说服力
- 演练放低峰、通知业务；结论（耗时、告警风暴）写进上线记录

## 五、干活：HAProxy 怎么分流量

🔥 有人要把战斗 TCP 和登录 HTTP 一起塞进 Nginx「统一入口」——**别这么干**。口诀：**「长连接四层，HTTP 七层」**（练习题 Q2）。

> 🎯 **一句话**：frontend 收流量、backend 选后端；mode tcp 管四层、mode http 管七层。

```text
/etc/haproxy/haproxy.cfg
frontend lobby_fe
    bind *:443                       # 在 VIP 上听（VIP 在哪台由 Keepalived 决定）
    default_backend lobby_be
backend lobby_be
    balance roundrobin
    server s1 10.0.1.20:8080 check inter 2s rise 2 fall 3
    server s2 10.0.1.21:8080 check inter 2s rise 2 fall 3
```

- `check inter 2s rise 2 fall 3`：每 2s 查一次，连续 2 次成功算活、连续 3 次失败摘除——**rise/fall 抗抖动**
- 数字连起来背：摘一台最快 2s×3=**6s**，认活要 2s×2=**4s**——「摘得快、放得慢」防带病横跳
- global 常漏一行：`stats socket /var/run/haproxy/admin.sock level admin`——不开运行时接口，摘机只能改配置 reload

#### ❓ 为什么战斗 TCP 不该塞进 Nginx？

- ❌ 七层要解析/缓冲 HTTP；长连接、非 HTTP 协议会被当「异常慢请求」或缓冲炸
- ✅ 战斗 TCP / MySQL / Redis → **四层**（LVS 或 HAProxy `mode tcp`）；登录 HTTP → 七层
- 👉 「统一入口」≠「统一七层」——入口可以一个 VIP，协议层仍按四/七拆

### ⚖️ 四层还是七层：和 LVS、Nginx 的分界 ⭐🔥

| 对比 | HAProxy `mode tcp`（四层） | HAProxy `mode http`（七层） |
|------|----------------------------|------------------------------|
| 认什么 | 只认 IP:端口，转发字节流 | 认路径/头/Cookie，能改写、能粘会话 |
| 能扛 | 战斗 TCP、MySQL、Redis 等任意协议 | HTTP/HTTPS 卸载后 |
| 健康检查 | tcp-check（探端口） | httpchk（探真实接口） |

- **LVS** = 内核态四层（转发不过用户态，DR 回程直出，性能最强功能最少）→ [18](../18-LVS与四层负载均衡/)
- **HAProxy** = 用户态 LB（四/七层都行，回程必过它）
- **Nginx** = 七层反代（改头/缓冲/TLS 终结最顺手）→ [19](../19-Nginx/)

### 🎲 算法与超时 ⭐

- **balance roundrobin**：无状态同规格，默认
- **balance leastconn**：长连接、耗时不均——战斗服首选
- **balance source**：源 IP 哈希粘滞；换 NAT 出口就破功（和 Nginx ip_hash 同病）
- **sticky 另两条路**（七层）：`cookie insert indirect nocache`；`stick-table` + `stick on src`（六节）
- **maxconn**：并发上限三级——global 管进程、frontend/listen 管入口、server 行管单后端；到顶新连接被拒（可配 `timeout queue`）——对应关系 → [19](../19-Nginx/) 二节

```text
timeout connect 3s~5s     # 连后端
timeout client  17s~60s   # 与客户端（HTTP 量级）
timeout server  17s~60s   # 与后端（HTTP 量级）
timeout tunnel  分钟级     # WebSocket/升级后的长连接
timeout check   2s        # 健康检查
```

- 四层长连接（战斗 TCP）client/server 要给**分钟级**，别抄 HTTP 的 30s
- HAProxy 在「外短内长」链上：**客户端/SLB 超时 < HAProxy client/server < 后端硬超时**（[19](../19-Nginx/) 占七层那段），完整口径 → [14](../14-HTTP与TLS/)

### 🔀 ACL 与平滑摘机 🔧

```text
acl is_pay path_beg /api/pay
use_backend pay_be if is_pay
```

- 七层按需分流够用就停——动态路由、鉴权、灰度是 [02-09](../../02-中间件与数据库/09-API网关与服务治理/) 的事

```bash
echo "set server lobby_be/s1 state drain" | socat stdio /var/run/haproxy/admin.sock
# drain：存量连完、新流量不进；weight 0 / disabled 同族
echo "show stat" | socat stdio /var/run/haproxy/admin.sock | cut -d, -f1,2,18,19,24,25,34 | head
```

```text
lobby_be,s1,UP,1/3,2,1234,100        ← 后端/机器/状态/失败计数/检查号/最后变更秒/权重
```

- server 状态位：`backup`（主池全摘才上）、`disabled`（配置态摘除）、运行时 `state ready` 放回
- **摘机闭环**：drain 后盯 Stats 的 `scur` 归零再停进程——没归零就停 = 硬掐存量玩家
- 日志：`option httplog`；`option dontlognull` 压掉健康检查噪音（→ [23](../23-日志运维/)）
- **变更铁律**：`haproxy -c -f ...` 过了再动；`reload` = 老进程把 listen socket 移交给新进程，存量连完、新配置接新；`restart` 才全拆（同 [19](../19-Nginx/) 七节）
- MySQL 入口经典：`mode tcp` 拆 3306 写 / 3307 读——策略层在 [02-01](../../02-中间件与数据库/01-MySQL/)，本章只管入口

### 🚪 边界：正向代理与 VPN（点到为止）

HAProxy/Nginx 在这里是**反向代理**——**代表服务端**收玩家流量；**正向代理**代表客户端出网。配了正向代理的机器上 `curl` 会走代理，访问内网要设 `no_proxy`。跨机房互联走专线（[06](../../06-云平台/)），和 VIP 漂移是两套机制。

> ⚠️ **别混**：**正向 vs 反向**的区别是「代表谁」——代表服务端收流量是反向（本章），代表客户端出网是正向。别把「给客户端用的 VPN」叫反向代理。

本节对应练习题 Q2、Q10、Q11、Q12。流量会分了——后端挂了怎么摘？sticky 粘得住跨机吗？

## 六、体检：健康检查、摘除与 sticky

> 🎯 **一句话**：后端坏摘 server 是 HAProxy 层的事，整机坏摘 VIP 是 Keepalived 层的事——两层节奏别混。

### 🩺 两层摘除 🎯⭐

```text
后端进程死   → HAProxy：check 失败 ×fall → 摘这台 server（秒级，常发生）
本机 HAProxy 死 → Keepalived：track_script 失败 → weight -30 → 摘整个 VIP（切主，低频大动作）
```

- 一台后端挂 → 流量在 backend 内部重分配，VIP 不动
- HAProxy 本身挂 → 才触发 VIP 漂移
- 值班先分清「摘的是 server 还是 VIP」——前者看 Stats，后者看 `ip addr` 和 journalctl

### 🔬 tcp-check vs httpchk：假活是头号坑 🔥⭐

| 对比 | `option tcp-check` | `option httpchk GET /health` |
|------|--------------------|------------------------------|
| 测什么 | 端口能不能建连 | 路径返回对不对（配 `http-check expect status 200`） |
| 测不出 | 应用僵死（端口在、人没了）——**假活** | 探错页面（探了个恒 200 的静态页） |
| 适用 | MySQL/Redis/战斗 TCP | HTTP 后端 |

> 💡 **打个比方**：tcp-check 是**只看门牌号**——灯亮着就算有人；httpchk 是**敲门问一句**——真有人应答才算活。假活就是灯亮着但屋里的人已经昏迷。

- **假活**是四层检查固有盲区：TCP 握手成功只证明端口有人听
- HTTP 后端尽量 httpchk 并**探真实接口**；`/health` 200 但线程池全卡仍要应用深度检查
- 反向坑：httpchk 探了 nginx 默认页，Java 全挂检查照样绿——**探错页面 = 没检查**

### 📌 sticky：会话粘住的三条路 ⭐

```text
① balance source        源 IP 哈希——最粗，换出口 IP 就飞
② cookie insert indirect nocache   七层种 Cookie——认人不认 IP
③ stick-table + stick on src expire 30m size 200k   表驱动，可配过期和容量
```

#### ❓ 为什么 VIP 漂了，玩家还可能换后端机？

- ③ 的表是**每台 HAProxy 自己一份、在内存里**——切主后新主没有旧表，第一跳可能换机器
- ✅ VIP 漂移救的是「有地方去」，**不保证「回到原机器」**
- 👉 跨机共享要 peers 同步（进阶）；先记住「默认不共享」这个代价
- `expire 30m`：表项 30 分钟没更新淘汰；`size` 满了挤最旧的

> 💡 **打个比方**：stick-table 像健身房前台登记本。换了个前台（VIP 漂到备机），登记本是新的，老会员还得重新登记。

### 📊 Stats：一块面板看全局 🔧

> 🔍 **现场**：入口异常，先开 Stats 面板（`stats enable` + 鉴权，**别裸奔**）再敲命令。

```text
listen stats
    bind *:8404
    stats enable
    stats uri /haproxy?stats
    stats auth admin:<强密码>
```

- 看五列：**status**（UP/DOWN/MAINT）、**scur/scur max**、**chkfail**、**lastchg**、**weight**
- `show table` 看 stick-table；`dontlognull` 压检查噪音
- **MAINT = 人工摘除**（drain/disabled 的显示），不是故障——一片 MAINT 先问「谁在发布」
- drain 的机器仍显示 UP，但 `scur` 不再涨

### 收束：一个入口凭什么高可用 🎯⭐

面试问「入口怎么高可用」，答这张清单——**七件套，一件不落**：

```mermaid
flowchart TB
    R["一个入口凭什么高可用"] --> G1["① 两层分工<br/>VIP 归 Keepalived · 流量归 HAProxy"]
    R --> G2["② track_script 翻译进程死<br/>weight 要算够（100−30<90）"]
    R --> G3["③ 协议 112 放行<br/>防火墙别当 UDP 拦"]
    R --> G4["④ httpchk 探真页面<br/>防假活"]
    R --> G5["⑤ rise/fall 抗抖<br/>inter 2s rise 2 fall 3"]
    R --> G6["⑥ 超时分层<br/>四层分钟级 · 别抄 HTTP 30s"]
    R --> G7["⑦ 切主有感知<br/>GARP 1~2s · 旧 TCP 重连 · nopreempt 稳住"]
```

- 📖 **读图**
  - ①② 架构层（两层各管各的、引信算术要对）
  - ③ 网络层（通告飞得过去）
  - ④⑤⑥ 检查与参数层；⑦ 切换行为层
  - 事故十有八九是七件里缺一件

> ⚠️ **别混**：这套保证「入口不因单点不可用」，**不保证**：旧 TCP 不断、会话粘回原机、后端应用真健康（检查只到探的深度）。

> 📝 **面试**：背法按「**层 → 信 → 检 → 切**」：两层分工、引信与通告（track_script/112）、检查节奏（httpchk/rise/fall）、切换行为（GARP/nopreempt/重连）。

## 七、病上加病：脑裂 🔥⭐

🔥 防火墙一改两台都有 VIP，有人说「再等一会会自己好」——**错了**。口诀：**「双 VIP = 脑裂，先下一台」**（练习题 Q5）。

> 🎯 **一句话**：脑裂 = 两台都认为自己是主、都挂 VIP——通告被拦比主机真挂更常见。

### 🔇 成因：声音被捂住

一切让通告到不了对端的情况都会脑裂：防火墙把 proto 112 当 UDP 拦了（最常见）、交换机/线路分区、VRID 撞车、auth_pass 不一致。主机真挂反而**不会**脑裂——通告停了、备机正常接管，这正是设计场景。

### 🔬 现象与确认 🔧

> 🔍 **现场**：会话乱、两个机房各服务一半玩家，先看两台是不是都有 VIP。

```bash
ip addr show eth0 | grep 10.0.0.100     # 两台都执行：都有 = 脑裂实锤
ip neigh | grep 10.0.0.100              # 同一 VIP 出现两个 MAC
tcpdump -ni eth0 vrrp                   # 两台是不是都在发通告
```

```text
10.0.0.100 dev eth0 lladdr aa:bb:cc:00:00:01 REACHABLE   ← MAC 是主机的
10.0.0.100 dev eth0 lladdr aa:bb:cc:00:00:02 STALE       ← 同一 VIP 又一个 MAC = 两台都在挂
```

- **止血只有一条**：先停一台 keepalived（`systemctl stop keepalived`），让全网只剩一个 VIP 持有者——再修根因
- 不要在两台都活着时调 priority「抢」——那是在脑裂状态下再加一次切换

#### ❓ 为什么 VRRP 脑裂不会像 etcd 那样自动停写？

- ❌ etcd 有 quorum：少数派**停止服务**保一致（[03-02](../../03-Kubernetes/02-etcd/)）
- ✅ VRRP 两节点**没有仲裁**——只有「听没听到」，没有任何机制阻止双方都升主
- 👉 「脑裂自动停止服务」在 VRRP 这里**不成立**；只能监控 + 人工止血，或双 VIP 主主减爆炸半径（架构取舍 → [33](../33-高可用与容灾/)）

### 🛡️ 防御：仲裁、日志、双 VIP

- **预防**：放行 proto 112（改防火墙过检查单 [17](../17-iptables与conntrack/)）；同二层 VRID 错开；auth 对齐
- **发现**：监控「两台同时持有 VIP」直接 P1（[22](../22-监控与告警/)）——靠告警暴露，不靠玩家报障
- **架构**：双 VIP 主主把爆炸半径减半：

```text
双 VIP 主主（互为主备，各管一半）：
  VIP-A 10.0.0.100 → 主机持有（priority A=100/B=90）   ← 一半玩家
  VIP-B 10.0.0.101 → 备机持有（priority A=90/B=100）   ← 另一半
  任一台挂：对方把两个 VIP 都接住 → 最多影响一半 + 一次重连
```

- 两套 vrrp_instance、VRID 必须不同（51/52）、priority 交叉——平时两台都干活，故障时另一半接盘

> ⚠️ **别混**：**Keepalived 脑裂 ≠ etcd 脑裂**。etcd 少数派停写；VRRP 双方继续挂 VIP 服务流量。

> 📝 **面试**：「脑裂最常见根因是防火墙把 VRRP（IP 协议 112）当 UDP 拦了；确认看两台 `ip addr` 都有 VIP、`ip neigh` 同一 VIP 两个 MAC；止血先停一台；防御靠放行 112、双主告警、双 VIP——VRRP 两节点无仲裁，别拿 etcd quorum 套。」

本节对应练习题 Q5。现在看群里那句「统一入口塞进 Nginx」——60 秒怎么定责？

## 八、作战：入口故障定责

> 🎯 **一句话**：三问——VIP 在哪台（Keepalived）？HAProxy 活着吗（track_script）？后端摘了几台（Stats）？

### 🌳 定责决策树

```mermaid
flowchart TB
    A["入口故障：连不上 / 会话乱 / 超时"] --> B{"两台都有 VIP？"}
    B -->|是| C["脑裂：先停一台 keepalived<br/>再查防火墙/VRID/auth"]
    B -->|否| D{"VIP 在的机器 haproxy 活着？"}
    D -->|死| E["track_script 没生效或 weight 没算够<br/>手起 haproxy / 修引信"]
    D -->|活| F{"Stats 后端状态"}
    F -->|全 DOWN| F1["检查全挂：查后端/探活配错（假活反向）"]
    F -->|部分 DOWN| F2["摘除正常：查被摘的那几台"]
    F -->|全 UP 仍超时| G{"四层还是七层"}
    G -->|战斗 TCP 断| G1["timeout 抄了 HTTP 30s<br/>改分钟级 / tunnel"]
    G -->|HTTP 慢/错| G2["回 19 查上游与超时链"]
    A -->|切主后不通| H["GARP 没刷出去：ip neigh 看旧 MAC<br/>查交换机 ARP/云安全组"]
```

- 📖 **读图**
  - 入口永远先看 VIP 在哪、几台持有——把 Keepalived 层和 HAProxy 层切开
  - 再往下走 Stats 和超时；切主后「VIP 在但不通」看 GARP 刷没刷出去

> 🔍 **现场**：切主完成但外部还是打不通——多半是 ARP 表里还是旧 MAC。

```bash
ip neigh | grep 10.0.0.100                     # 在「交换机视角」的邻机上执行
```

```text
10.0.0.100 lladdr aa:bb:cc:00:00:01 REACHABLE  ← 还是旧主的 MAC：GARP 没刷到这台
10.0.0.100 lladdr aa:bb:cc:00:00:02 REACHABLE  ← 新主 MAC：刷新成功
```

- 邻机 ARP 还是旧 MAC → GARP 丢了或被拦——新主补发 `arping -U -I eth0 10.0.0.100`；云上查安全组/虚拟交换机对免费 ARP 的处理
- 抓包确认：`tcpdump -ni eth0 arp`（→ [16](../16-网络排障与抓包/)）

### 现象 · 先做 · 别做

| 现象 | 先做 | 别做 |
|------|------|------|
| 会话乱 / 一半进 A 一半进 B | 两台 `ip addr` 数 VIP | 调 priority 两边对抢 |
| 两台都有 VIP | 先停一台 keepalived | 修防火墙前先「切回主机」 |
| VIP 没漂 | 查 track_script 与 weight 算术 | 只看 keepalived 进程在不在 |
| VIP 漂了但不通 | `ip neigh` 看 VIP 的 MAC 换没换 | 反复 reload haproxy |
| 入口全超时、VIP 正常 | haproxy 进程 + `ss -tlnp` 端口 | 先动 keepalived |
| 后端全 DOWN | 后端本身 + 探活页面配错没 | 关 check 硬扛 |
| 一台 chkfail 涨 | 查那台（load/磁盘/假活） | 摘另一台「试试」 |
| 战斗 TCP 几十秒被掐 | timeout client/server/tunnel 分钟级 | 换成 HTTP 模式 |
| 切主后玩家飞服 | stick-table 不跨机，评估 peers | 以为 VIP 漂=会话不丢 |
| 修好主机抢回又抖 | nopreempt 或窗口期人工切回 | 反复重启 keepalived |
| 云上 VRRP 不工作 | 改 unicast_peer 单播 | 盯组播配置不放 |
| 代理机 curl 内网失败 | no_proxy 排除内网段 | 拆 HAProxy 配置 |

### 60 秒剧本 🔧

> 🔍 **现场**：接到「登录进不去/会话乱」报障，60 秒走完这条线再下结论。

```text
① 0–10s   两台 ip addr show | grep VIP：几个 VIP、在哪台——脑裂与否一票定方向
② 10–30s  VIP 在的机器：systemctl status haproxy + ss -tlnp ':443'
          journalctl -u keepalived -n 50 看最近有没有切主动作
③ 30–45s  Stats / show stat 看后端 status·chkfail·lastchg；战斗连接查 timeout 三件
④ 45–60s  定责 + 动作：停一台保脑裂止血 · 起 haproxy · 摘假活机 · 调超时；
          需要抓包时 tcpdump -ni eth0 vrrp（→16）
```

本节对应练习题 Q13、Q14。开头那三个现场——双 VIP、进程死 VIP 还在、战斗口塞七层——你已经知道该怎么拦住他了。

## 九、收口

### 命令速查 🔧

```bash
ip addr show eth0                          # VIP 挂没挂在本机（脑裂：两台都有）
ip neigh | grep <VIP>                      # VIP 的 MAC 换没换（GARP 刷没刷出去）
tcpdump -ni eth0 vrrp                      # 看 VRRP 通告（IP 协议 112）在不在飞
journalctl -u keepalived -n 50             # 切主记录：Entering MASTER/BACKUP STATE
systemctl status haproxy && ss -tlnp | grep -E ':443|:3306'
haproxy -c -f /etc/haproxy/haproxy.cfg     # 配置检查，reload 前必过
echo "show stat" | socat stdio /var/run/haproxy/admin.sock   # 后端状态
echo "show table lobby_be" | socat stdio /var/run/haproxy/admin.sock
echo "set server lobby_be/s1 state drain" | socat stdio /var/run/haproxy/admin.sock
systemctl reload haproxy                   # 平滑 reload 配置
```

### 面试锚点

| 问 | 30 秒答 |
|----|---------|
| Keepalived 和 HAProxy 各干什么？ | Keepalived 管 VIP 在哪台（VRRP）；HAProxy 管流量怎么分（frontend/backend）。 |
| VRRP 是什么协议？ | IP 协议 112，组播、只二层；云上改 unicast 单播。 |
| 谁当主谁当备？ | priority 高者主（100>90）；state 只是初始姿态。 |
| 切主怎么发生？ | 通告 3 帧超时或 track_script 失败 weight −30 → 有效优先级低于对端 → 备机升主挂 VIP 发 GARP。 |
| 切换要多久？玩家有感吗？ | GARP 刷 ARP 1~2s、整段 2~3s；新连接切走，旧 TCP 断开靠重连。 |
| track_script 为什么需要？ | Keepalived 不知道同机 haproxy 死活；脚本把进程死翻译成 priority 下降。 |
| killall -0 的局限？ | 只测进程在，测不出假活；要端口/HTTP 级脚本。 |
| 什么是假活？ | tcp-check 端口在但应用僵死；httpchk 探真页面 + expect status。 |
| 脑裂是什么、怎么防？ | 两台都挂 VIP，根因多是 112 被拦；止血先停一台；防御靠放行、双主告警、双 VIP；VRRP 两节点无仲裁。 |
| 怎么确认脑裂？ | 两台 ip addr 都有 VIP；ip neigh 同一 VIP 两个 MAC；tcpdump 看双方都在发通告。 |
| nopreempt 什么时候用？ | 修好原主不抢回，避免二次抖动；低频会话场景。 |
| HAProxy 和 LVS 怎么选？ | LVS 内核态四层性能最强、功能最少（DR 回程直出）；HAProxy 用户态四/七层、检查粘滞全；Nginx 七层最顺手。 |
| sticky 有几种？ | balance source / cookie insert / stick-table；表在内存不跨机，切主后可能换机。 |
| 平滑摘一台后端？ | `set server ... state drain`（存量连完新流量不进），Stats 看 scur 归零再停进程。 |
| MySQL 为什么用 mode tcp？ | 非 HTTP 协议；3306 写/3307 读按端口拆，四层只认 IP:端口。 |
| 正向和反向代理？ | 反向代表服务端收流量（本章）；正向代表客户端出网（no_proxy 那套）。 |
| maxconn 三级在哪给？ | global 管进程、frontend/listen 管入口、server 行管单台后端；超限排队或拒。 |
| haproxy reload 拆连接吗？ | 不拆：老进程把 listen socket 移交新进程，存量连完、新配置接新；restart 才全拆。 |

### 易错一句话对照

- VRRP 是 UDP 112 → 错，IP 协议 112，不封装在 UDP/TCP 里
- state MASTER 的当主 → 错，priority 决定，state 只是初始姿态
- 主机挂了会脑裂 → 错，通告正常停、备机正常接管；通告被拦才脑裂
- 脑裂了先修防火墙 → 错，先停一台止血，再修根因
- VIP 漂了 = 玩家连接不断 → 错，旧 TCP 断开靠重连，新连接才切走
- VIP 漂了 = 会话回到原机 → 错，stick-table 不跨机
- track_script 失败一定切主 → 错，weight 要算够（100−30=70小于 90 才切得动）
- killall -0 能测假活 → 错，只测进程存在
- httpchk 配了就不会假活 → 错，探错页面（恒 200 静态页）等于没检查
- 后端挂了要切 VIP → 错，后端归 HAProxy 摘 server；VIP 只管整机
- 战斗 TCP 超时抄 HTTP 的 30s → 错，四层长连接给分钟级
- 修好原主抢回是好事 → 错，刚稳的会话再乱一次；nopreempt 或窗口切回
- VRID 随便配 → 错，同二层撞车会互相抢主
- 云上组播不通是 Keepalived 坏了 → 错，云网络常禁组播，改 unicast_peer
- 把 HAProxy 当网关百科做路由鉴权 → 错，ACL 够用就停，那是 APISIX 的事
- VPN 是反向代理 → 错，正向（代表客户端出网）
- 两节点 VRRP 脑裂会自动停写 → 错，没有仲裁，只有监控+人工
- reload haproxy 会拆玩家连接 → 错，listen socket 移交、存量连完；restart 才全拆
- Stats 一片 MAINT 当事故 → 错，MAINT 是人工摘除的显示形态，先问谁在发布
- maxconn 只能在 global 配 → 错，三级都可给：global 进程 / frontend 入口 / server 单后端
- 检查 inter 调得越小越安全 → 错，检查自己也是流量，后端池大要放宽节奏

### 数字墙

> VRRP = IP 协议 **112** · advert **1s**（失联判定 ≈ **3** 帧）· priority **100 / 90** · weight **−30**（100−30=**70**小于 90）· GARP 刷 ARP **1~2s** · 整段切换 **2~3s** · VRID 例 **51**（同二层必须唯一）· check `inter **2s** rise **2** fall **3**` · timeout connect **3~5s** · HTTP client/server **17~60s** · 四层/战斗 **分钟级** · stick-table `expire **30m**` · MySQL **3306** 写 / **3307** 读 · 切主看 `journalctl` 的 Entering **MASTER STATE**
