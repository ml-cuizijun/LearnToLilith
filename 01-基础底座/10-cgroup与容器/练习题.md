## Q1

**★★★★★｜cgroup 和 namespace 分别解决什么？失效各什么样？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [三、看界：namespace 视图与 free/nproc 的谎言](知识点.md)

### 场景

有人把容器说成「微型虚拟机」。排障时在容器里看 `free` 说内存够，十分钟后 137。

### 完整解答

**一句话**：cgroup 管配额（OOM/throttle），namespace 管视图；容器是共享内核的进程隔离，不是微型 VM。

cgroup 限制用量，超了 OOM / throttle / pids / io。namespace 限制看见什么，失效会看到宿主机 PID / 网络。内核 panic 全机一起死，cgroup 挡不住。

```mermaid
flowchart TB
    subgraph k ["同一内核"]
        ns[namespace：你看见什么]
        cg[cgroup：你能用多少]
        lie[容器内 free/nproc：仍读宿主机 /proc]
    end
```

### 再追问

cgroup 能隔离内核崩溃吗？——不能。隔离故障域要虚机/节点池。

## Q2

**★★★★★｜为什么容器里 free / nproc 不能当配额？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [三、看界：namespace 视图与 free/nproc 的谎言](知识点.md)

### 场景

limit=2 核 / 2Gi。同事 `nproc` 得 32，`free` 还有 40G，据此说「资源够」。随后 throttle 和 137 都来了。

### 完整解答

**一句话**：free/nproc 读宿主机 `/proc`，不是 cgroup；真值看 `cpu.max` / `memory.max`。

namespace 没把 meminfo/cpuinfo 改成「只显示你的 limit」（别默认有 lxcfs）。左边谎言推不出右边配额——总图里谎言与真文件中间无桥。

| 谎言 | 真文件 |
|------|--------|
| `nproc=32` | `cpu.max` |
| `free` Available 很大 | `memory.max` / `memory.current` |

### 再追问

用 free 反驳 137 有没有哪怕一次成立？——没有。定性看 `memory.events` 的 `oom_kill`。

## Q3

**★★★★★｜CPU throttling 怎么发现？为什么 P99 会飙？**

**覆盖**：核心 · 必会 · 常用 · 常考

**对应**：知识点 [四、撞界：CPU 配额与 throttled](知识点.md)

### 场景

匹配服 limit=500m。宿主机 idle 60%。P99 从 30ms 到 400ms。有人要扩节点。

### 完整解答

**一句话**：throttle 看 `cpu.stat` 的 `nr_throttled` 增量；100ms 周期里 quota 用完就被踢出，等待算进 P99。

```mermaid
flowchart LR
    A["100ms 周期，quota=50ms（500m）"] --> B[跑 50ms]
    B --> C[等 50ms]
    C --> D[请求跨过边界，P99 加上等待]
```

读完 `cpu.max` 再做**定责算术**：两次采样 `cpu.stat` 做差——被踢比例 = Δnr_throttled / Δnr_periods（>5% 且 P99 同步涨才算故障）；平均晾多久 = Δthrottled_usec / Δnr_throttled，直接估出 P99 抬多少；最后用 quota / period = limit 核数反验一遍配额没看错。throttle 的表现是**毛刺**（P99/P999 抬、P50 不动），不是整体均匀变慢。

读 `cpu.max` 确认配额；两次采样 `nr_throttled`/`nr_periods` 做差。比例 **>5%** 且 P99 涨当故障。Prometheus 用 rate。只有 **limit** 造成 throttle；扩节点修不好本 cgroup 的 tight limit。

### 再追问

request 和 limit 哪个造成 throttle？——只有 limit。request=limit=1 核高峰仍可能 throttle。

## Q4

**★★★★★｜OOMKilled 但宿主机内存很多，怎么解释、怎么查？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 [五、撞界：内存配额与 cgroup OOM](知识点.md)

### 场景

Pod 137。节点 MemAvailable 20G。容器里 `free` 显示 64G。Java `-Xmx` 贴着 limit。

### 完整解答

**一句话**：碰到了 cgroup `memory.max`，读 `memory.events` 的 `oom_kill` 增量；跟节点剩余无关。

```mermaid
flowchart TB
    A[节点还空] --> B[不会走整机 OOM Killer]
    C[memory.max 到顶] --> D[memory.events 里 oom_kill 增加]
    D --> E[137]
```

describe 看 OOMKilled；节点上 host PID → `memory.current` vs `memory.max`、`memory.events`；`dmesg` 无 `Out of memory` 更像 cgroup。Java 堆外留 **30%+**（细节 07）。不要用 free 反驳。

三本账别混：`ps` 的 RSS 不含 page cache 也不含 sidecar 的账，RSS 加总永远对不上 `memory.current`（差值主要就是 file cache）；K8s 默认禁 swap（`memory.swap.max=0`），anon 无处可退——这是容器比虚机更容易 137 的结构性原因。杀只认 `memory.max`，图表走 working_set，两图对不齐先想口径差。

### 再追问

Guaranteed 还会 OOMKilled？——会。那是自己的 max，不是 QoS 选杀。

## Q5

**★★★★☆｜cgroup v1 和 v2 对内存排障差在哪？**

**覆盖**：必会 · 常考

**对应**：知识点 [二、出生：limit 从 YAML 到内核文件](知识点.md)

### 场景

v1 上 usage 已经贴 limit，anon 其实不高。迁 v2 之后同样负载不再轻易 OOM。

### 完整解答

**一句话**：v1 `usage_in_bytes` 含 cache 易误判；v2 能拆 file/anon，还有 PSI / `memory.high`。

v1 子系统分树；v2 统一树，`/proc/pid/cgroup` 常见 `0::/path`。`memory.high` 软顶（回收/PSI），`memory.max` 硬顶（OOM）。K8s **1.27+** 推 v2。

布局差异是排障天天踩的：v1 每控制器一棵树、`/proc/pid/cgroup` 多行、CPU 账和内存账**路径可能不一样**，每个控制器单独拼一次；v2 一棵树，`cpu.max`/`memory.max`/`pids.max` 并排一个目录全拿到。迁 v2 三个坑：**hybrid 混合挂载**（`mount | grep cgroup2` 有输出 ≠ 所有控制器都在 v2）；**v2 树根不养进程**（进程挂叶子，路径常以 `.scope` 结尾）；**工具链只认老文件名**（旧版 cadvisor/脚本迁完集体断流）。

### 再追问

怎么一眼看节点是 v1 还是 v2？——`mount | grep cgroup2`；或看 `/proc/1/cgroup` 是否单行 `0::`。

## Q6

**★★★★☆｜Docker 和 K8s 写配额有何同异？本章边界在哪？**

**覆盖**：必会 · 常考

**对应**：知识点 [二、出生：limit 从 YAML 到内核文件](知识点.md)

### 场景

追问「limit 写在 YAML / `docker run` 里，内核到底改了哪个文件？」不要展开 QoS 公式。

### 完整解答

**一句话**：两者都是写手；落到 `cpu.max`/`memory.max`；QoS/调度去 K8s 04。

| | Docker | K8s |
|--|--------|-----|
| 入口 | `--cpus` / `--memory` | `limits.cpu` / `limits.memory` |
| 写谁 | dockerd/containerd | kubelet |
| 多容器 | 通常一容器一 cgroup | Pod 内存常共享 |

`100m` → `cpu.max`=`10000 100000`。request 影响调度/shares，**不**造成 throttle。

### 再追问

不设 CPU limit 会怎样？——无 CFS throttle，可能吵邻居。延迟敏感服常用宽 limit/不设 + 节点隔离。

## Q7

**★★★☆☆｜核心游戏服要不要设 CPU limit？**

**覆盖**：必会 · 常考

**对应**：知识点 [四、撞界：CPU 配额与 throttled](知识点.md)

### 场景

匹配服 100m limit，平时能跑，活动全超时。宿主机空闲。

### 完整解答

**一句话**：延迟敏感有状态服倾向宽 limit 或只设 request；100m 突发必被 throttle。

100m = 每 100ms 只有 **10ms** 配额。批处理相反，紧 limit 保护节点。扩节点修不好——配额在这个 cgroup 上。

### 再追问

request=limit=1 还会 throttle 吗？——会，只要还有 quota 且突发顶满周期。

## Q8

**★★★☆☆｜sidecar 泄漏谁死？pids / io 各查什么？**

**覆盖**：必会 · 常用

**对应**：知识点 [六、撞界：pids、io 与 sidecar](知识点.md)

### 场景

逻辑服和日志 sidecar 一个 Pod。sidecar RSS 涨，主容器 137。另一台 `fork` 报 `Resource temporarily unavailable`，内存还够。同盘备份把邻居打满。

### 完整解答

**一句话**：Pod 共享内存 limit 时 sidecar 能带走主容器；fork 先查 pids；同盘慢查 io.max。

```mermaid
flowchart TB
    A[主容器 137] --> B[top --containers]
    B -->|sidecar 涨| C[共享 Pod memory.max]
    D[fork 失败] --> E{pids.current 贴 max?}
    E -->|是| F[pids]
    E -->|否 · 内存贴顶| G[ENOMEM / cgroup 内存]
    H[同盘全慢] --> I[谁没套 io.max]
```

Docker 裸机双子容器通常**不**共享同一 memory.max——那是 K8s Pod 叙事。pids 按 **task（线程）** 计数：Java 池里 3000 线程在 `ps` 是一个进程、在 `pids.current` 是 3000，头号嫌犯常是**线程泄漏**（症状：卡死但 CPU/内存都正常）；真 fork 炸弹耗光的是**整机** `pid_max`，sshd/kubelet 全 fork 失败——`pids.max` 防的是邻居和宿主机，K8s 由 kubelet `podPidsLimit` 下发。

### 再追问

io.max 能代替买盘吗？——不能，但能隔离邻居；机制在 cgroup。

## Q9

**★★★★☆｜容器里怎么看 CPU / 内存配额？路径从哪找？**

**覆盖**：核心 · 必会 · 常用

**对应**：知识点 [二、出生：limit 从 YAML 到内核文件](知识点.md) · [七、作战：从现象到文件定责](知识点.md)

### 场景

有人猜 `kubepods` 目录。另一台容器内 `/sys/fs/cgroup` 数字像宿主机根。

### 完整解答

**一句话**：不要猜路径：host PID → `/proc/pid/cgroup` → `/sys/fs/cgroup` 读 `cpu.stat`/`memory.events`。

```mermaid
flowchart TB
    A[kubectl / docker] --> B[crictl inspect / docker inspect → host PID]
    B --> C["cat /proc/hostpid/cgroup"]
    C --> D[拼到 /sys/fs/cgroup 读文件]
```

已挂 cgroupns 时可在容器内直接读自己的 `cpu.max` 等；没挂则可能读到根，必须回宿主机。v1 用 `cpu.cfs_quota_us`、`memory.limit_in_bytes`。`kubectl top` 不能替代 `memory.events`。

### 再追问

`nr_throttled` 看绝对值行不行？——不行，看增量 / rate。

## Q10

**★★★★☆｜nproc=32、limit=2 核对 Go/Java 意味着什么？**

**覆盖**：必会 · 常用 · 常考

**对应**：知识点 [三、看界：namespace 视图与 free/nproc 的谎言](知识点.md)

### 场景

游戏网关 P99 毛刺。镜像没设 `GOMAXPROCS`。进容器 `nproc` 是 32。

### 完整解答

**一句话**：nproc 是谎言核数；不对齐 limit 会大量 throttle。

默认按 32 开跑抢 2 核配额。Go：`GOMAXPROCS=2` 或 automaxprocs。Java：`ActiveProcessorCount`；堆外另留 **30%+**。

正道是**对齐**，不是把 limit 开到 32 迁就谎言。

### 再追问

只加 limit 到 32 核能替代设 GOMAXPROCS 吗？——能消 throttle，但会在节点上抢光 CPU；正道是对齐。

## Q11

**★★★★☆｜容器里 `free` 和 `memory.current` 对不上，OOM 该信谁？swap 默认关了吗？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [四、撞界·内存：cgroup OOM](知识点.md) · 三本账

### 场景

Pod `limits.memory=2Gi`，容器内 `free` 显示还有 800M，下一秒 Exit 137。有人按 `free` 说「明明够」。

### 完整解答

> 🎯 **一句话**：**cgroup 三本账**（RSS / memory.current / swap）才是 OOM 依据；K8s 默认**禁 swap**，`free` 是 namespace 谎言。

```bash
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.events | grep oom
# oom_kill 1  ← 铁证
```

| 读数 | 含义 |
|------|------|
| `memory.current` | cgroup 计费总量（含页缓存等） |
| RSS | 进程常驻，不含可回收 cache |
| `free` in 容器 | 常像整机，**不能当配额** |

137 + `memory.events` 有 `oom_kill` → cgroup OOM，去对齐 limit/Xmx/堆外，不是去加节点内存。

### 再追问

- Guaranteed Pod 还会 137 吗？——会，limit 就是硬顶；QoS 只影响**整机** OOM 时谁先被系统杀。

## Q12

**★★★☆☆｜`cpu.weight`（shares）和 `cpu.max`（quota）分别管什么？只有 shares 会 throttle 吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：limit 从 YAML 到内核文件](知识点.md)

### 场景

有人把 CPU request 拉到 8、limit 不设，说「争抢权重够大就不会慢」。P99 仍毛刺。

### 完整解答

> 🎯 **一句话**：**shares 只影响争抢比例，不产生 throttle**；**quota（cpu.max）才是硬顶**——没 limit 的 Pod 在节点忙时仍可能抢不过，但不会因为 quota 被踢出队列。

```text
requests.cpu → cpu.weight（v1: shares）  争抢时谁多分
limits.cpu   → cpu.max quota             超了 throttle（nr_throttled↑）
不设 limit   → cpu.max = max             永不因 quota 被 throttle
```

排障：`cpu.stat` 里 `nr_throttled` 增量 > 0 才是 quota 问题；只有 shares 不会看到这个。

### 再追问

- Burstable 和 BestEffort 差别？——调度与整机压力下谁先被驱逐，细节 → [03-Kubernetes](../../03-Kubernetes/04-Pod生命周期/)。

## Q13

**★★★★☆｜P99 毛刺 + 节点 CPU idle，怎么 60 秒从现象钉到 cgroup 文件？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：从现象到文件定责](知识点.md)

### 场景

匹配服延迟飙，宿主机 `top` 还有 60% idle。开发坚持「不是 CPU 问题」。

### 完整解答

> 🎯 **一句话**：**host PID → /proc/pid/cgroup → cpu.stat/memory.events**，30 秒内分清 throttle / cgroup OOM / pids / io。

```bash
PID=$(crictl inspect {id} | jq .info.pid)
CG=$(awk -F: '{print $3}' /proc/$PID/cgroup)
cat /sys/fs/cgroup${CG}/cpu.stat      # nr_throttled, throttled_usec
cat /sys/fs/cgroup${CG}/memory.events
cat /sys/fs/cgroup${CG}/pids.current
```

| 文件信号 | 定责 |
|----------|------|
| `nr_throttled` 增量 | CPU quota / GOMAXPROCS 不对齐 |
| `oom_kill` | memory.max / Xmx |
| `pids.current` ≈ `pids.max` | 线程泄漏 |
| `io.stat` 某设备 throttled | 同盘邻居 / 备份抢 IO |

### 再追问

- 扩节点为什么修不好 throttle？——每 Pod 仍只有 2 核 quota，搬家不增配额。

## Q14

**★★★★★｜白板：throttle、137、fork 失败、同盘全慢——四种撞界怎么一张表讲完？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图](知识点.md) · [十、收口](知识点.md)

### 场景

白板题：「容器资源问题你别猜 YAML，从文件给我定责。」

### 完整解答

> 🎯 **一句话**：**看界是谎言，撞界看文件**——四列签名、四列文件、四列处方，互不串台。

| 撞界 | 签名 | 读哪 | 处方 |
|------|------|------|------|
| CPU throttle | P99 炸、节点 idle | `cpu.stat` | 对齐 GOMAXPROCS/limit |
| cgroup OOM | 137、节点有空 | `memory.events` | limit/Xmx/堆外 |
| pids | fork 失败、线程暴涨 | `pids.current` | 修泄漏、调 pids.max |
| io | 同盘全 await 高 | `io.stat` / `io.max` | ionice、独立盘、cgroup io |

```mermaid
flowchart LR
    V[容器内 free/nproc] --> L[谎言]
    F[/sys/fs/cgroup 文件] --> T[真账]
```

> 📝 **面试**：背完表补一句「namespace 管看见什么，cgroup 管能用多少」。
