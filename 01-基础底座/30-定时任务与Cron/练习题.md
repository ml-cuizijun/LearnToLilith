## Q1

**★★★★☆｜crontab 五字段怎么读？「工作日 4:30」「每月 1 号和每个周一」怎么写？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：把任务写进 crontab](知识点.md)

### 场景

面试白板：面试官写了 `0 0 1 * 1 /opt/report.sh` 问你这条任务一个月跑几次。旁边的产品同学托你配一条「工作日下午 4 点半发日报」，还想要一条「每月 1 号，而且必须是周一才跑」。

### 完整解答

> 🎯 **一句话**：五字段「分时日月周」，三种写法 `*` / `*/n` / `a-b,c`；日和周同写具体值是「或」不是「且」。

| 写法 | 含义 |
|------|------|
| `*` | 每个（这一位任意值都匹配） |
| `*/n` | 每隔 n：`*/5` 在分位 = 每 5 分钟 |
| `a-b,c,d` | 范围加列表：`1-5` 工作日 |

白板那题 `0 0 1 * 1`：日位 `1`、周位 `1` **同时**是具体值，cron 语义是**并集**——每月 1 号跑一次，**加上**每个周一跑一次：一个月最多 5~6 次，最少 2 次。这是五字段里最阴的一个坑。产品同学的两条：

```text
30 16 * * 1-5   /opt/daily_report.sh      # 工作日 16:30
# 「1 号且是周一」cron 表达不了「且」：写每月 1 号，判断周几进脚本
0 0 1 * * /opt/monthly.sh                 # 脚本内 [ "$(date +%u)" = "1" ] || exit 0
```

> ⚠️ **别混**：`*/5` 在**分位**是每 5 分钟；写在**时位**就是每 5 小时——`*/n` 的含义跟着所在字段走。另外周日是 0 也是 7，`0 0 * * 0` 和 `0 0 * * 7` 等价。

### 再追问

**「每 30 秒」怎么写？**——写不了：cron 最小粒度 1 分钟。要么脚本内 `sleep 30` 循环两次，要么 systemd timer 的 `OnUnitActiveSec=30s`（→ [11](../11-Systemd与服务管理/)）。

**六个特殊字符串是什么？**——@reboot、@yearly、@monthly、@weekly、@daily、@hourly；其中只有 @reboot 不带时间语义（开机那一刻），其余都是固定时刻的糖。

## Q2

**★★★★☆｜想 crontab -e 手滑成了 -r 会怎样？/etc/cron.d 里照抄用户表的行为什么不跑？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [二、出生：把任务写进 crontab](知识点.md)

### 场景

同事抱怨「昨天改完定时任务，今天全没了」。翻他的 shell 历史看到 `crontab -r`。另一个人把 `0 2 * * * /opt/backup.sh` 原样放进 `/etc/cron.d/backup`，一次都没跑过。

### 完整解答

> 🎯 **一句话**：-r 无确认删整张表；三张表格式不同——/etc/cron.d 比 crontab 多一个「执行用户」字段。

**`-r` 是 remove**，删的是**当前用户整张 crontab**，没有任何确认，且和 `-e` 只差一个键位。预防姿势：改表前 `crontab -l > ~/crontab.bak`；被删后的恢复 = 拿备份 `crontab < 备份文件`（没有备份就翻 shell 历史/CMDB/别的机器慢慢重建——这也是「crontab 要进版本管理」的口号由来）。

**三张表**：用户表（`crontab -e`，五字段 + 命令，存 `/var/spool/cron/<用户>`）；**`/etc/crontab` 与 `/etc/cron.d/*`（系统表，五字段之后多一个用户字段，写明以谁的身份跑）**；`/etc/cron.daily/` 等目录（扔可执行脚本，anacron 驱动）。那位同事的行在 `/etc/cron.d/backup` 里没有用户字段——cron 把 `0` 后面的 `2` 当用户名，整行解析失败**静默不跑**，正确写法：

```text
0 2 * * * root /opt/backup.sh
#            ↑ 这个字段是 cron.d 独有的执行身份
```

> 🔍 **现场**：改完表必做的回读验证：
> ```bash
> crontab -l | tail -3          # ← 用户表：确认新行真的写进去了
> cat /etc/cron.d/backup        # ← 系统表：确认用户字段在、权限 644
> ```

> ⚠️ **别混**：用户表里**不要**写用户字段（`0 2 * * * root /opt/x.sh` 放进 `crontab -e` 会把 `root` 当命令的一部分）；系统表里**必须**写——位置决定格式，一张表一个规矩。

### 再追问

**/etc/cron.d 文件的权限有讲究吗？**——要 `0644`、属主 root：cron 出于安全会忽略权限过宽（如组/其他人可写）的文件——「文件在、内容对、就是不跑」的隐形坑之一。

**用户表和系统表该用哪张？**——业务任务跟人（业务用户）走用户表；运维/软件包安装的系统级任务走 cron.d——谁的任务谁的身份、谁的责任谁的表，混着放是排障时的额外迷雾。

## Q3

**★★★☆☆｜@reboot 到底是什么时机跑？为什么说「开机拉服务」不该用它？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：把任务写进 crontab](知识点.md) 与 [三、被读：crond 怎么调度到你](知识点.md)

### 场景

有人在 @reboot 里放了一条「开机后注册到服务发现」，反馈是「有时开机很久都没注册上」；还有一台机器重启完，@reboot 任务干脆没跑。

### 完整解答

> 🎯 **一句话**：@reboot = crond 自己启动那一刻触发一次——不等网络、不等业务，crond 没起它就不发生。

@reboot 的触发点不是「系统就绪」，是 **crond 服务被拉起的那一瞬间**。两个推论：① 那一刻网络可能还没配好、DNS 还不通、上游服务可能还没起——「注册服务发现」这种**依赖网络**的任务用它，天然时灵时不灵；② 前提是 crond 起来了——极端情况下机器起不来或 crond 挂了，@reboot 自然也无声消失。

「开机拉起守护」的正解是 **systemd service**（开机依赖、顺序、Restart 都有人管，→ [11](../11-Systemd与服务管理/)）；@reboot 合适的用途是**一次性收尾动作**：清理上次的临时文件、重置某个标记位——不依赖任何外部条件、晚一点早一点都无所谓的活。

> 📝 **面试**：答 @reboot 必带「crond 启动那一刻」这个准确定义，再补一句「开机拉服务应该用 systemd」——把「什么时候不用 cron」说清楚，比会写 @reboot 本身值钱。

### 再追问

**@reboot 会像其他任务一样重复跑吗？**——不会：它没有时间字段语义，每次 crond 启动只触发一次；crond 中途重启（比如你 `systemctl restart crond`）也会再触发一次——所以 @reboot 任务必须是**幂等**的。

**那「错过的时间点」cron 会补吗？**——不会，cron 的世界里错过的就是错过了（Q8 的关机家族）；补跑是 anacron / timer `Persistent=true` 的活（Q11）。

## Q4

**★★★★☆｜服务器是 UTC 时区，你按北京时间写的每天 2 点任务没跑，怎么回事？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [三、被读：crond 怎么调度到你](知识点.md)

### 场景

海外集群一台 UTC 机器，你给它配了 `0 2 * * *` 的日志归档，第二天上班发现「没跑」。去看 /var/log/cron，02:00 确实有一条 CMD——但那是谁的 2 点？

### 完整解答

> 🎯 **一句话**：cron 匹配的是机器本地时间——UTC 机器的 02:00 是北京时间上午 10 点，任务一直在准点跑，只是不在你以为的点。

crond 拿**系统本地时间**去匹配五个字段。`date` 显示 UTC 的机器上，`0 2 * * *` 触发在 UTC 02:00 = **北京时间 10:00**——所以日志里 02:00 的 CMD 是真跑了，你上班前看「北京时间 2 点归档文件没生成」当然找不到。归档其实每天上午 10 点（北京）都在发生。

修法两条路，选一：

```bash
# 路 A：把机器时区改成北京时间（集群统一口径时优先）
timedatectl set-timezone Asia/Shanghai && systemctl restart crond
# ↑ 改完必须重启 crond——它缓存时区，不重启还按旧表走

# 路 B：时区不动，任务换算成 UTC 写
0 18 * * * /opt/archive.sh     # ← UTC 18:00 = 北京时间次日 2:00
```

> 🔍 **现场**：给任何机器配定时任务前的第一问：
> ```bash
> date; timedatectl | grep 'Time zone'
> # Time zone: UTC (UTC, +0000)   ← 表是 UTC 的：北京时间 2:00 = 前一天 18:00
> ```

> ⚠️ **别混**：NTP 管的是**时间和北京时间差多少**（钟准不准），时区管的是**这张表怎么读**——时间再同步，时区标错照样差 8 小时。NTP 与时间的完整机制 → [32](../32-NTP与时间同步/)。

### 再追问

**为什么改完时区任务还是没按新时间跑？**——crond 启动时缓存时区，`timedatectl set-timezone` 只改了系统，crond 还拿着旧表——`systemctl restart crond`（或 cron）才生效。

**跨时区集群的最佳实践？**——统一时区口径（要么全 UTC 任务全换算，要么全北京时间）；「每台机器先 `date` 再写表」写进任务上线 checklist，比事后排障便宜一百倍。

## Q5

**★★★★★｜脚本手动跑得好好的，放进 cron 就跑不了——「手动能跑、定时跑不了」为什么？怎么修、怎么验证？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [四、干活：cron 的环境和你的环境是两个世界](知识点.md)

### 场景

值班经典工单：备份脚本手动执行完美出包，进了 cron 之后备份文件再没更新过。脚本第一行就是裸写的 `mysqldump`，装在 /usr/local/mysql/bin 下。

### 完整解答

> 🎯 **一句话**：cron 在「干净世界」里跑你的命令——非登录非交互的 /bin/sh，PATH 只有 /usr/bin:/bin，你 export 过的一切都不存在。

> 💡 **打个比方**：cron 是**凌晨来替班的实习生**——你工位上的东西（你 shell 里 export 的一切）他一概不知，只认识前台清单上的工具（系统默认 PATH）。你留字条「跑那个备份」，他找不到工具箱，只能在一张没人看的小票上写句 not found 塞进信箱。

机制：crond fork 的命令跑在**非登录、非交互 shell**里——`.bash_profile`、`.bashrc` 不被读，环境只有 `PATH=/usr/bin:/bin`、`HOME=/root`、`SHELL=/bin/sh` 这几项。本例的 `mysqldump` 在 `/usr/local/mysql/bin`——不在 cron 的 PATH 里，命令直接 not found，**而这行报错默认只进一封没人读的邮件**。修法三件套：

```bash
# 表里：绝对路径 + 输出落文件
0 2 * * * /opt/game/backup.sh >> /var/log/backup.log 2>&1
```
```bash
#!/bin/bash                    # ← 脚本头钉死 bash，防 /bin/sh 的 dash 语法坑
export PATH=/usr/local/mysql/bin:/usr/bin:/bin   # ← 自己造环境
cd /opt/game                   # ← 相对路径的锚点自己钉死
exec >> /var/log/backup.log 2>&1                 # ← 输出永远落到能查的地方
```

**验证**：`env -i /bin/sh -c '/opt/game/backup.sh'`——清空环境用 sh 跑，**能复现故障 = 坐实环境问题**；这样修完它跑通了，放进 cron 才有把握跑通。

> 📝 **面试**：30 秒口径：「cron 用非登录非交互的 /bin/sh 跑命令，PATH 只有 /usr/bin:/bin、不读 bashrc，所以裸写命令名会 not found。修法：脚本化 + #!/bin/bash + 脚本内 export PATH + cd 绝对目录 + 输出重定向。验证用 env -i /bin/sh -c 复现。」——这条是 11 章 timer 一节明确指过来的题，答不出等于没接住交接。

> ⚠️ **别混**：「手动能跑」的手动是在**你的交互 shell**里跑的，PATH 和变量是你攒了十年的家当；「定时跑不了」的定时是在**干净世界**里跑的——两个世界对同一行命令，本来就不该期望结果一样。

### 再追问

**怎么看到 cron 环境的真身？**——临时加一条 `* * * * * env > /tmp/cron-env.txt`，一分钟后打开看：PATH 多短、SHELL 是不是 /bin/sh、你 export 的变量一个都没有。

**输出不重定向会怎样？**——stdout/stderr 默认作为邮件发给任务属主（MAILTO），云上精简镜像多半没配 MTA，于是被静默丢弃——故障证据一起被丢掉。所以「输出落文件」不是洁癖，是排障的生命线。

## Q6

**★★★★☆｜同一个脚本挪进 cron 报语法错、找不到配置文件——除了 PATH 还有什么坑？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [四、干活：cron 的环境和你的环境是两个世界](知识点.md)

### 场景

脚本从手动迁到 cron 后两种报错交替出现：一种是 `[[: not found`；另一种不报错，但脚本读不到 `./config.yaml`，走了默认配置。

### 完整解答

> 🎯 **一句话**：除 PATH 外还有两坑——`/bin/sh` 不是 bash（bashism 语法报错）、HOME/cwd 与你以为的不同（相对路径和 ~ 悬空）。

**坑 ①：`[[: not found`**——crond 的 SHELL 是 `/bin/sh`，在 Debian/Ubuntu 上 sh 是 **dash**：`[[ ]]`、`source`、数组、`function` 关键字这些 bashism 全部语法错。所以调用姿势必须是**绝对路径调脚本本体**（`/opt/game/run.sh`），让脚本头 `#!/bin/bash` 决定解释器——而不是表里写 `sh /opt/game/run.sh` 强行用 sh 打开它。

**坑 ②：读不到 `./config.yaml`**——cron 里没有「你现在所在目录」这回事：cwd 不是脚本目录，HOME 也可能不是你以为的那个家。`./config.yaml`、`~/.my.cnf`、`backup/` 这种相对路径全部悬空——脚本**第一行 `cd` 到自己的绝对目录**，配置引用一律绝对路径。

```bash
#!/bin/bash
cd /opt/game                    # ← 所有相对路径的锚点，钉死
CONFIG=/opt/game/config.yaml    # ← 绝对路径，不猜 cwd
```

第三个次生坑记一句：**没有 tty**——cron 里没有终端，一些命令行为会变（分页器、颜色、按 tty 判断的逻辑），`mysql` 免交互要显式给参数或用 `--batch`。

> ⚠️ **别混**：坑 ① 的报错「看得见」（语法错会进输出/邮件/日志文件），坑 ② 往往**无声**（读不到配置就静默用默认值）——无声的更危险：任务「成功」跑完，产物是错的。

### 再追问

**怎么系统性验证脚本在 cron 里能跑？**——两步：`env -i /bin/sh -c '/opt/game/run.sh'` 复现干净环境；再临时放一条 `* * * * *` 的每分钟版本，盯着输出文件看一轮真实执行——通过后再改成正式时间。

**为什么 dash 还存在、不统一成 bash？**——历史与体积：dash 更小更快，是 Debian 系的 `/bin/sh` 默认；「sh 是 bash 的子集」这个假设在那些机器上不成立。写脚本要么 `#!/bin/bash` 要么老老实实写 POSIX sh，两头都占就两头挨打。

## Q7

**★★★★★｜cron 的日志去哪看？日志里有 CMD 能证明什么、不能证明什么？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [五、失败无声：日志与排障四步](知识点.md)

### 场景

工单升级：「备份没跑」。新人翻了半小时 /var/log/messages 找不到 cron 记录，得出结论「日志丢了」。老值班过来两行命令定位到：CMD 在日志里，但脚本输出文件三天没更新。

### 完整解答

> 🎯 **一句话**：cron 日志只记「到点触发了 CMD」，不记命令的成败——触发看 cron 日志，成败看任务自己的输出。

**日志位置按发行版分家**：RHEL/CentOS 系是 `/var/log/cron`；Debian/Ubuntu 系进 `/var/log/syslog`，或 `journalctl -u cron`。服务名两种拼法（crond / cron）都存在，两个都点名就不赌发行版——「日志丢了」多半是找错了地方：

> 🔍 **现场**：
> ```bash
> grep CMD /var/log/cron | tail -5
> journalctl -u crond -u cron --since '02:00' --until '02:05' | grep -i backup
> ```
> ```text
> Sep 01 02:00:01 log-srv01 CROND[28451]: (root) CMD (/opt/game/backup.sh)
> # ↑ 这行只证明：02:00:01 crond 开枪了
> # ↑ 它不证明：脚本存在、跑成功、跑完
> ```

> 💡 **打个比方**：cron 日志是**大楼门禁记录**——它记得「02:00 有人刷卡进了机房」，但这个人进去之后干成了活还是晕倒在里面，门禁一无所知。所以本例老值班的第二刀切向**任务自己的输出**：`tail /var/log/backup.log`——三天没新行，说明命令被 fork 出去后死了，往执行层（环境坑）查，不再在调度层浪费时间。

**任务自己留证据**两个姿势：表里 `>> /var/log/backup.log 2>&1`（首选）；或脚本里 `logger -t backup -p user.error '失败'`，把结果写进 journald 跟系统日志一起查（journald/rsyslog 的完整体系 → [23](../23-日志运维/)）。

> ⚠️ **别混**：「cron 日志里有 CMD 就是跑了」——只证明触发。「日志里连 CMD 都没有」才是调度层的事（时间写错/时区/关机/crond 死了）。一行日志，劈开两半现场。

### 再追问

**为什么 cron 不直接把成败记进日志？**——设计哲学：crond 只是闹钟，命令的输出属于任务属主（默认发邮件）。所以「让任务可观测」是任务作者的责任——模板里永远带 `>> logfile 2>&1`。

**日志里 CMD 都没有，先查什么？**——① `crontab -l` 行还在吗（-r 手滑）；② 时间字段和时区（Q4）；③ 那时刻机器活着吗（`uptime`/重启记录）；④ crond 活着吗（`systemctl status crond`）——四个方向对应判定链的四个叶子。

## Q8

**★★★★★｜「定时任务没跑」给你一套完整排查方法论——从接到工单到结案。**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [五、失败无声：日志与排障四步](知识点.md) 与 [八、作战：「定时任务没跑」定责](知识点.md)

### 场景

面试压轴题，或者值班真实工单：用户只给了一句「我配的定时任务没跑」。你要给出一套顺序清晰、每步有验证动作的方法论。

### 完整解答

> 🎯 **一句话**：四步排障——任务在吗 → 触发了吗 → 环境能复现吗 → 任务自己呢；每一刀把现场劈成两半。

```text
① 任务在吗？    crontab -l | grep 任务       ← root 和业务用户各查一遍
                  没有 → 没登记 / -r 误删 / 写错表（cron.d 忘用户字段）
② 触发了吗？    日志里那分钟有没有 CMD 那行
                  没有 → 时区差 8 小时？机器当时关机？crond 死了？
                  有   → 调度层无责，往下走
③ 环境能复现吗？ env -i /bin/sh -c '命令'    ← 能复现 = 环境三坑（PATH/HOME/sh）
④ 任务自己呢？   看任务自己的输出日志         ← 报错在这里，不在 cron 日志里
```

第一问要查**两个用户**的表——「root 表里没有、业务用户表里有」是新手最常漏的叶子。第二问是整条链的**分水岭**：CMD 在与不在，决定你往执行层查还是往调度层查——劈错方向就是一小时白干。第三问用 `env -i` 在干净环境复现，复现成功就坐实环境坑。第四问落在任务的输出文件上——前提是模板里带了重定向，没带的话这步空转，先补上重定向等下一轮。

结案口径四种典型：「没登记，已重建」「时区差 8 小时，已换算/已改时区并 restart crond」「关机无补跑，转 anacron/timer」「PATH 坑，脚本已加 export PATH」——每一种都对应一个「以后怎么防」的动作，工单才算真关。

> 📝 **面试**：把四步和「写入→被读→被触发→执行」的一生对应着讲——方法论背后有结构，不是背清单；结尾补「新任务模板四件：错峰分钟、flock、绝对路径、输出重定向」，从排障升级到预防，是最强收尾。

### 再追问

**这四步里哪步最容易被跳过？**——第 ① 步的「业务用户也查一遍」和第 ④ 步的「任务自己的日志」：一个觉得「root 肯定查过了」，一个没输出文件可看。跳过任何一步，链就断在半路。

**如果是「跑了一半」而不是「没跑」呢？**——四步照样走：② 会发现 CMD 在，④ 的输出文件里能看到死在多少行——部分成功把战场直接送到脚本层，环境坑与脚本逻辑五五开。

## Q9

**★★★★☆｜任务执行时间超过调度周期，发生了重叠——怎么防？为什么有人手搓锁文件反而死锁？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [六、防身：flock 防重叠与错峰纪律](知识点.md)

### 场景

每小时跑的数据归档，某天数据量翻倍跑了 90 分钟，下一个整点第二轮又启动了：两个进程写同一个文件、CPU 翻倍、下游被打爆。有人提议「脚本开头 touch 一个锁文件，结束删掉」，另一个人说他们以前这么干过，出过一次「任务再也不跑」的事故。

### 完整解答

> 🎯 **一句话**：cron 不管上一轮跑没跑完就开枪——防重叠用 `flock -n`：拿不到锁就放弃这一轮，锁随进程生死自动释放。

crond 每分钟无脑匹配就 fork，**没有「等上一轮」的概念**——重叠是设计使然，且只在任务偶尔变慢时出现（平时 40 分钟、高峰 90 分钟），测试期发现不了，是典型的「活动日才炸」。

> 💡 **打个比方**：`flock` 是**公共卫生间的门锁**：进门先锁（拿锁），锁被占着就**不等、直接走**（`-n`）——总比两个人挤进一个隔间强。而 touch 手搓锁是「门上贴纸条」：进程跑到一半被 kill（OOM、重启），**删锁的那行代码永远执行不到**，纸条永远贴在门上，后面每一轮都看见「有人」就退出——任务从此再也不跑，这就是那次事故的机制。

```bash
# -n：拿不到锁就放弃这一轮（上一轮还在跑，正好不要重叠）
0 * * * * /usr/bin/flock -n /var/run/archive.lock /opt/game/archive.sh >> /var/log/archive.log 2>&1
```

两句话记住：**`-n` 非阻塞**（防重叠场景永远用它，不加 -n 会变成排队，两个进程串行还是双倍负担）；**锁文件路径一个任务一把**（两个任务共用一把锁会互相误杀）。

> ⚠️ **别混**：flock 防「**同一任务**重叠」，错峰防「**不同任务**同时」——两个工具两个问题；也别用「缩短任务超时」对付重叠——超时杀任务和重叠是两个独立的风险，杀掉的半截任务同样伤数据。

### 再追问

**拿不到锁跳过这一轮，数据不就丢了？**——看任务语义：归档类下一轮会补上（幂等），跳过无损；真不能跳的任务要的就不是定时触发而是队列——cron 本来就不适合「必须不丢不重」的语义，那是 MQ 的地盘。

**flock 的锁文件需要提前创建、手动清理吗？**——不用：flock 自己创建，锁的持有绑定在进程的文件描述符上，进程退出（无论正常还是被杀）内核自动释放——这正是它比 touch 高一档的原因。

## Q10

**★★★☆☆｜全公司的定时任务都写在 0 点整，会发生什么？错峰纪律怎么定？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、防身：flock 防重叠与错峰纪律](知识点.md)

### 场景

巡检发现：所有机器的 crontab 里躺着一排 `0 0 * * *`——备份、日志切割、账单统计、证书续期。凌晨 0 点的监控曲线上，磁盘 util 和外网流量同时跳起一个尖峰。双 11 活动日当晚，凌晨的备份撞上了运维窗口。

### 完整解答

> 🎯 **一句话**：00:00:00 是全公司的默认撞点——分钟级错峰、机器级错峰，两级纪律各自拆一类惊群。

**分钟级错峰**（拆同一台机器上的任务）：`0 0 * * *` 改 `5 0 * * *`、`17 0 * * *`——备份、logrotate、统计别在同一分钟开枪。几分钟的偏移零成本，换的是磁盘 util 尖峰直接抹平（IO 饱和的定责 → [08](../08-磁盘与IO/)）。

**机器级错峰**（拆集群里同种任务）：100 台机器都是「每天 2 点备份」，下游存储和带宽是**共享的**——按机器尾号错开 2:00 / 2:10 / 2:20，惊群变细水长流。备份介质与带宽规划 → [31](../31-备份与恢复/)。

错峰的本质是承认一个事实：**cron 的五字段只能表达「什么时候跑」，表达不了「下游此刻忙不忙」**——所以把负载信息人工编码进分钟位。这也是它简陋但够用的地方。

> ⚠️ **别混**：错峰防的是「不同任务/机器同时」，防不了「同一任务自身重叠」——后者是 flock 的活（Q9）。指望把所有任务错开得永不相撞来替代锁，是拿日历当门锁用。

### 再追问

**logrotate 也是 0 点跑的吗？**——多数发行版默认 cron.daily 在凌晨（或 anacron 的 3 点档）；它和你的备份撞在同一块盘上时，就是「凌晨备份特别慢」的隐形原因之一——轮转体系 → [23](../23-日志运维/)。

**错峰要错到多细？**——同机任务分钟级就够；集群任务按下游容量定步长（存储能吃几路并发备份就分几档）。原则一句话：**错峰的粒度跟着下游的容量走，不是拍脑袋随机数**。

## Q11

**★★★★☆｜cron、anacron、systemd timer 三者什么关系？新任务该用哪个？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [七、另一条路：cron vs systemd timer](知识点.md)

### 场景

架构评审：新机器上要加一批定时任务，有人坚持「cron 谁都会写」，有人主张「全部上 timer」。另外有几台白天才开机的办公/备份机，问「错过的任务怎么办」。

### 完整解答

> 🎯 **一句话**：cron 赢在人人会写，timer 赢在日志统一、能补跑、能清点——新任务优先 timer，存量 cron 必须会修；anacron 专治不 7×24 的机器。

| 维度 | cron | systemd timer |
|------|------|---------------|
| 日志 | 自建文件 / `/var/log/cron` 只记触发 | `journalctl -u xxx.service` 全量统一 |
| 错过补跑 | 无（关机就没了） | `Persistent=true` 补跑 |
| 清点 | `crontab -l` 逐用户翻 | `systemctl list-timers` 一屏 |
| 秒级 | 不支持 | `OnUnitActiveSec=30s` 支持 |
| 上手成本 | 全员会写 | 要写一对 unit 文件 |

timer 机制深讲在 [11](../11-Systemd与服务管理/)（`.timer` 触发 `Type=oneshot` 的 `.service`），本章只管选型：**新任务优先 timer**——journal 统一收录（排障不用两头翻）、`Persistent=true` 补跑（关机错过的开机补）、`list-timers` 一屏清点（谁的 Next 停在昨天一眼看出没在跑）。**但存量 cron 巨大**，且任何一台机器都可能遇到别人留下的 cron——排障能力是刚需，这正是 11 章把环境坑指到本章的原因：不是让你继续用 cron，是让你接得住历史。

**anacron 一句**：给**不 7×24 开机**的机器按「天」补课——只认 daily/weekly/monthly 粒度，开机后检查「上次跑是什么时候」、隔够了就补一次；`/etc/cron.daily/` 目录正是它驱动的。那几台白天才开机的机器，答案就是 anacron（或干脆 timer + Persistent）。它是「cron 不补跑」的官方补丁，服务器常开用不上。

> 📝 **面试**：三件套各一句话定位——**cron：人人会写的存量标准；timer：systemd 时代的正选（journal/Persistent/list-timers）；anacron：不常开机机器的按天补课**。再加一句「新任务优先 timer、cron 排障必须会」，选型题满分。

### 再追问

**timer 的 Persistent=true 和 anacron 的补跑有什么差别？**——粒度与归属：timer 补**自己那一个**任务（每个 timer 独立记上次触发时间）；anacron 补的是**一类目录任务**（daily/weekly/monthly 三档，天级粒度）。要小时级补跑只有 timer 做得到。

**把存量 cron 迁 timer 值得吗？**——按痛点迁：排障时缺日志、被「关机错过」坑过的先迁；跑得好好的、没人 complain 的别为迁而迁——迁移本身也是变更风险。

## Q12

**★★★★★｜值班 60 秒：用户报「每天凌晨 2 点的备份连着三天没跑」，你怎么走？**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [八、作战：「定时任务没跑」定责](知识点.md)

### 场景

周三早上接单：游戏服每日备份三天没出包，手动跑脚本一切正常。背景信息：这台机器上周从北京时间统一改成了 UTC 口径，且前天凌晨有一次计划内重启。

### 完整解答

> 🎯 **一句话**：沿判定链四刀——登记、触发、环境、自身；这道题的线索（时区 + 重启）都埋在「没触发」那一半。

```text
① 0–10s   crontab -l | grep backup（root 和业务用户各一遍）
          → 在：0 2 * * * game /opt/game/backup.sh，登记无问题
② 10–30s  grep CMD /var/log/cron | tail；journalctl -u crond -u cron --since '02:00'
          → 三天里只有一天 02:00 有 CMD，另外两天没有 → 「没触发」家族
③ 30–45s  触发层三查：
          date && timedatectl          → 机器现在是 UTC：北京时间 2:00 = 表里的前一天 18:00
          uptime / last reboot         → 前天那次重启正落在备份窗口里（当天连 crond 都没起）
④ 45–60s  结案：三个根因可能同时成立——
          · 时区改了但 crond 没 restart（缓存旧时区）→ systemctl restart crond
          · UTC 口径下时间字段要换算成 0 18 * * * → 已改
          · 重启当晚错过 = cron 不补跑，属设计 → 补跑方案转 timer Persistent
          验收：次日 02:00（换算后的北京时间 10:00）看备份包 + 日志 CMD
```

这道题的「手动能跑」是个烟雾弹——它把新手往环境坑（Q5）引，而线索「改时区 + 凌晨重启」都指向**调度层**：第②刀的 CMD 日志一劈，现场立刻离开执行层。这就是判定链的价值：**先劈层，再看线索**，反过来就会被烟雾弹带着走。

> ⚠️ **别混**：改时区后 **crond 必须重启**才认新表——只 `timedatectl set-timezone` 不 restart crond，cron 还按旧时区跑，这是「改了时区还是没跑」的头号复发点。

> 📝 **面试**：综合题答题结构照抄这个剧本——**四步各报一句结论**（在/触发没触发/环境排除了/结案口径），每个结论带一条证据（一行命令的输出）。有结构的 60 秒胜过没有方向的半小时。

### 再追问

**这个案例里还有哪个隐患没处理？**——备份输出有没有落文件、有没有 flock（备份变慢重叠）——按新任务模板四件（错峰分钟、flock、绝对路径、输出重定向）顺手补齐，把「这次没跑」变成「这类问题不再来」。

**如果 ② 的结论反过来——三天 CMD 都在呢？**——战场立刻切到执行层：`env -i /bin/sh -c` 复现 + `tail` 备份日志——大概率 PATH 坑（Q5 的原题），「手动能跑」从烟雾弹变成主线索。同一句工单，一刀定两个方向，这就是 ② 是分水岭的原因。

## Q13

**★★★★☆｜`flock -n` 和手写 `touch lock` 为什么差一个天上一个地下？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、防身：flock 防重叠](知识点.md)

### 场景

备份脚本用 `[ -f /tmp/backup.lock ]` 防重叠，两台机器同时跑都创建了 lock，双写打爆 DB。

### 完整解答

> 🎯 **一句话**：**flock 是内核 advisory 锁，原子；touch 检查-创建有竞态，且崩溃不释放**。

```bash
flock -n /var/lock/backup.lock /opt/game/backup.sh
# 或 cron 行：
# 0 2 * * * flock -n /var/lock/backup.lock /opt/game/backup.sh >>/var/log/backup.log 2>&1
```

| 写法 | 问题 |
|------|------|
| touch lock | 竞态、进程死锁文件残留 |
| flock -n | 拿不到锁直接跳过，可审计 |

### 再追问

- 非 -n 的 flock？——会等锁，可能把 cron 窗口拖成重叠链。
