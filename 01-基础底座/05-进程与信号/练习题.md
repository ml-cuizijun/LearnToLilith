## Q1

**★★★★★｜kill -9 都杀不掉的进程，是怎么回事？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、挨打：信号怎么递送、谁能挡住](知识点.md)

### 场景

活动高峰 Load 40、CPU idle 70%，逻辑服卡住。有人已经 `kill -9 28451` 连发三次，PID 还在。群里有人说「再杀一次」「换 kill -STOP」「实在不行重启机器」——就是开头那个现场。

先自己试试：不看下面，你能说出为什么 `-9` 杀不掉、下一刀敲什么吗？说完再对答案。

### 完整解答

> 🎯 **一句话**：进程卡在 D（不可中断睡眠），信号要等它回到用户态才递送——SIGKILL 也在门口排队，修 IO 才是出路。

信号只在进程**从内核态返回用户态**的那一刻递送。`kill -9` 把 SIGKILL 挂进 pending 集合后，如果进程正处于 D 状态（内核里等 IO），它根本回不到用户态，KILL 就一直压着不生效。确认与定位：

```bash
ps aux | awk '$8 ~ /D/'
# game 28451  0.0 ... D  03:10  0:00 logic-server    ← STAT 主字母 D，不是 CPU 不够，别加核
cat /proc/28451/wchan
# nfs_wait_bit_uninterruptible                      ← 在等 NFS：对端抖了
cat /proc/28451/stack                               # 内核栈，多看一层
```

wchan 三种典型字样，各自对应修法，**没有一种是再 kill 一次**：`nfs_wait_*` 修 NFS 或 `umount -l`、日志改本地盘；`blk_mq_*` 本地/云盘 hang，换盘；`wait_on_page_writeback` 脏页写回卡住，降写入。大量 D 时普通 `reboot` 会卡在杀进程，要走云控制台**强制重启**；`gdb attach` 一个 D 进程同样会卡住，别试。NFS 挂载参数用 `soft,timeo=100,retrans=2`，宁可报错不要永远 D。

> ⚠️ **别混**：换 `kill -STOP`、`kill -TERM` 都一样没用——所有信号都卡在同一个「回用户态」检查上，问题在状态不在信号。

> 📝 **面试**：「kill -9 为什么杀不掉？」——先答信号递送时机（回用户态才递送，D 是反例），再答 SIGKILL 不可捕获≠立刻生效，最后用 wchan 给出修法路径。三段下来比背「D 杀不掉」结论高一档。

### 再追问

- **为什么内核不干脆把 D 的进程强拆掉？**——D 等的是不能中途拆的 IO（拆了破坏块设备或 NFS 协议一致性），这是保护不是 bug；正确做法是修 IO 路径，不要硬拆。
- **值班第一分钟敲什么？**——`ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'` 确认 D、看 wchan 定 IO 类型；不要一上来就再 kill、加 CPU、重启。

## Q2

**★★★★★｜僵尸进程怎么来的？怎么处理？为什么 kill 僵尸没用？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、死亡：exit、僵尸与退出码](知识点.md)

### 场景

这是 Q1「杀不掉」的姐妹题——一个卡在活着的 D，一个卡在已死的 Z。

机器上有几百个 `[curl] <defunct>`，`ssh` 开始报 `fork failed`。有人打算 `kill -9` 逐个清僵尸，有人想直接重启机器。

先自己试试：僵尸怎么来的？kill 僵尸 PID 管用吗？说完再对答案。

### 完整解答

> 🎯 **一句话**：子进程 exit 后父进程不 wait，内核保留进程表槽位等收尸——僵尸占的是 PID 不是内存，杀僵尸 PID 没用，要么父进程收，要么杀父让 PID 1 代收。

僵尸进程（zombie）= 子进程已 exit、用户内存已释放，内核只留**进程表槽位和退出状态**等父进程 `wait`/`waitpid`。它占的是 PID 号，所以堆多了顶到 `pid_max`（常见 32768），全机 fork 失败、连 sshd 都起不来。定位看 PPID，谁名下攒得多谁是罪魁：

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'
#   PID  PPID STAT COMMAND
# 28453 28451 Z    [curl] <defunct>       ← PPID 指着 28451：logic-server 没 wait
ps -eo ppid,stat | awk '$2 ~ /Z/ {print $1}' | sort | uniq -c | sort -rn
#    847 28451                               ← 28451 名下 847 个僵尸
cat /proc/sys/kernel/pid_max                 # 32768
```

典型来源：Java `Runtime.exec` 不 `waitFor`、shell 循环 fork 不收、容器 PID 1 不处理 SIGCHLD。处理分三层：**根治**是父进程修代码 wait/waitFor 或注册 SIGCHLD handler；**止血**是杀父进程——僵尸被 PID 1 收养并收尸（业务会断，先想清楚）；**容器**场景把 PID 1 换成 tini，自动 wait 子进程。预防：少在业务进程里 fork 外部命令，改 sidecar / IPC。

> ⚠️ **别混**：「僵尸很占内存所以机器变卡」——僵尸不占用户内存，`free` 看不出僵尸严重程度；它的杀伤是耗尽 PID。

### 再追问

- **为什么 `kill -9` 对僵尸无效？**——僵尸已经死了，没有可杀的实体；信号发给一个只剩槽位的 PID 无处递送。不要对着僵尸 PID 浪费时间，去查 PPID。
- **杀父进程为什么能清掉僵尸？**——父死后僵尸变孤儿，被 PID 1 收养，PID 1 会 wait 收尸。但这是止血不是根治——父进程的业务会断，能修代码就修 wait。

## Q3

**★★★★★｜有状态的游戏服怎么停？SIGTERM 和 SIGKILL 区别？OOM 时为什么不能优雅退出？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、挨打：信号怎么递送、谁能挡住](知识点.md)

### 场景

发版脚本里写着 `pkill -9 logic-server`，一次发版后玩家集体投诉回档。面试官追问：那正确的停法是什么？K8s 里又停在哪一步？

先自己试试：TERM 和 KILL 差在哪？正确停服链是什么顺序？

### 完整解答

> 🎯 **一句话**：TERM 是请求、应用可处理可刷盘；KILL 是处决、内核直接拆——停服先摘流量再 TERM，grace 内收尾 exit 0，超时才 KILL。

| 对比 | SIGTERM(15) | SIGKILL(9) |
|------|--------------|------------|
| 应用能处理吗 | 能，handler 收尾 | 不能，内核直接拆 |
| 谁在用 | systemctl stop / docker stop / kubelet 第一枪 | OOM Killer / grace 超时 / 人手 -9 |
| 刷盘、关连接 | 来得及 | 来不及，脏数据丢 |
| 退出码 | 自 exit 0 或 143 | 137 |

停服一条链，顺序即因果：**摘流量（LB / endpoint / preStop）→ SIGTERM → handler 收尾（停 accept、踢玩家、刷盘）→ exit 0**；grace 内没退完才补 SIGKILL。systemd 里 `TimeoutStopSec` 就是 grace，游戏服按刷盘量给 30～120s；journal 里 `status=0/SUCCESS` 是 TERM 后自己退干净，`status=9/KILL` 是超时或 OOM 强杀。K8s 同一条链：摘 endpoint / preStop → kubelet 对容器 PID 1 发 TERM → 等 `terminationGracePeriodSeconds`（默认 30s）→ SIGKILL。应用 handler 最小清单：置 shutting_down 停 accept → 通知玩家 → 刷角色脏数据（每步带超时）→ 关监听 fd、exit 0 → 打点「收到 TERM 到 exit」耗时校准 grace。

> ⚠️ **别混**：**OOM 发的是 SIGKILL**——没有 handler 可跑，「OOM 时优雅退出失败」不成立，根本没有优雅退出；想 OOM 前刷盘只能靠 limit 余量、探针、降载。

> 📝 **面试**：先答「TERM 可处理 / KILL 不可捕获」，再答停服链和 grace 数值，最后补 OOM=KILL 收尾——三层递进。

### 再追问

- **grace 给 10s 行不行？**——几乎必强杀：大服刷角色脏数据不止 10s，超时就是 137 回档。要用真实打点数据校准，不要拍脑袋，也不要一刀切加到 300s。
- **preStop 能替代应用处理 TERM 吗？**——不能。preStop 在 TERM 之前跑，适合摘注册中心；摘完流量进程还是得自己接住 TERM 收尾，两件事各干各的。

## Q4

**★★★★★｜为什么 docker stop 等 10 秒后总是强杀？容器里的进程收不到 SIGTERM？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、善终：优雅停服与容器 PID 1](知识点.md)

### 场景

游戏服容器化后，每次 `docker stop` 都要干等 10 秒才停（SIGKILL 强杀），玩家掉线不干净。看 Dockerfile：`CMD python app.py`。

先自己试试：为什么 docker stop 总等满 10 秒？TERM 卡在哪一层？

### 完整解答

> 🎯 **一句话**：容器的 PID 1 有两层坑——没注册 handler 的信号被内核直接丢弃；shell 当 PID 1 不转发 TERM。修法是 tini 或 CMD exec 形式 + 应用 Listen TERM。

内核对 PID 1（init）特殊保护：**它没注册 handler 的信号一律丢弃**。于是：① 应用自己是 PID 1 又没 Listen TERM——kubelet/docker 发的 TERM 被内核丢弃，等满 grace 后 SIGKILL 强杀；② `CMD python app.py` 常被包成 `/bin/sh -c python app.py`——**shell 是 PID 1 且不转发信号**，TERM 停在 sh 手里到不了 python。两层坑往往叠在一起。看进程树一眼分清：

```text
✗ root 1 /bin/sh -c python app.py      ← shell 当 PID 1，TERM 到不了 python
✗ root 1 /usr/bin/python app.py        ← 应用是 PID 1 但没 Listen TERM，内核丢信号
✓ root 1 /sbin/tini -- /app/server     ← tini 转发 TERM 给应用
```

修法三选一：镜像里放 **tini / dumb-init**、`docker run --init`、或 `CMD ["/app/server"]` **exec 形式**让应用直接当 PID 1 并注册 TERM handler。tini 还顺带处理 SIGCHLD、替你 wait 子进程——容器里的僵尸问题一并解决。

> ⚠️ **别混**：把 `terminationGracePeriodSeconds` 加到 300 不能治这个病——TERM 根本没送到，等更久只是等更久再被 KILL。也别拿 `shareProcessNamespace` 当停服方案，那是调试用的。

### 再追问

- **`CMD python app.py` 和 `CMD ["python", "app.py"]` 差在哪？**——前者经 `/bin/sh -c` 起一层 shell 当 PID 1，后者 exec 形式直接 exec、python 自己是 PID 1。改成 exec 形式后还要应用自己 Listen TERM，不要改完就以为完事。
- **tini 除了转发信号还有什么用？**——收养孤儿、wait 子进程，容器里 fork 出的子进程不会变僵尸。不要让业务进程裸当 PID 1 又不处理 SIGCHLD。

## Q5

**★★★★☆｜进程 S 状态和 D 状态什么区别？Load average 为什么不含 S？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [三、干活：五个状态 R/S/D/Z/T](知识点.md)

### 场景

还记得 Q1 那台 Load 40、idle 70% 的机器吗？根因签名就在 S/D 这一分。

网关机器上万个连接、`ps` 里一排 S，监控 Load 却接近 0；另一台机器 Load 40 但 CPU idle 70%。有人拿「S 太多」解释 Load 高。

先自己试试：S 和 D 差在哪？Load 含不含 S？口诀是什么？

### 完整解答

> 🎯 **一句话**：S 可中断（等 socket/锁/定时器，信号叫得醒）、D 不可中断（内核等 IO，信号进不去）；Load = R + D，S 不计入。

S（可中断睡眠）等的是**允许被打断**的事件——socket、用户态锁、sleep、epoll_wait，一发信号就醒来处理；D（不可中断睡眠）等的是**不能中途拆**的 IO——本地盘、云盘、NFS，拆了会破坏一致性，所以任何信号（包括 KILL）都递送不进去。**Load = 可运行队列（R）+ 不可中断睡眠（D）**：网关万连接全是 S，Load 可以接近 0；一排 D 把 Load 顶到 40 而 CPU idle 还很高——这是 IO 问题的招牌，不是 CPU 不够。值班口诀：一排 D + idle 高 → IO/NFS/脏页，看 wchan；一排 R + %us 高 → CPU 型；大量 S + Load 低 → 正常睡。

> ⚠️ **别混**：**Load 高 ≠ CPU 不够**——先 `ps` 分堆看是 R 撑的还是 D 撑的，别看 Load 40 就申请加 8 核。

### 再追问

- **那 T 状态呢？Load 算它吗？**——不算。T 是被 SIGSTOP 挂起的暂停态，`kill -CONT` 解开；生产少见，别当挂死去重装。
- **怎么一句话向面试官证明你懂？**——「万连接网关 S 一大片 Load 接近 0；NFS 一抖一排 D，Load 40 而 idle 70——Load 里的两股是 R 和 D。」不要背「Load 高就是 CPU 紧张」。

## Q6

**★★★★☆｜孤儿进程和僵尸进程的区别？看到 PPID=1 说明什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、死亡：exit、僵尸与退出码](知识点.md)

### 场景

Q2 清僵尸时会碰到 PPID=1——别和孤儿搞混，本题专门钉死。

巡检看到一批 `PPID=1` 的 worker 进程，同事说「都是僵尸了，赶紧清」。

先自己试试：孤儿和僵尸各看哪一列？PPID=1 一定是僵尸吗？

### 完整解答

> 🎯 **一句话**：孤儿活着、被 PID 1 收养（PPID=1 是它的标志）；僵尸已死、等父 wait（STAT=Z 是它的标志）——两码事。

**孤儿进程（orphan）** = 父进程先退出、还在运行的子进程，内核把它交给 PID 1 **收养**，PPID 变 1，继续正常跑——是兜底机制不是故障。故意变孤儿的经典是守护进程（daemon）：两次 fork + `setsid` 脱离终端；生产更常见 systemd `Type=simple` 前台跑。**僵尸** = 子进程已 exit、父不 wait，占 PID 槽位。判断只看两处：STAT 是不是 Z、PPID 指着谁。`PPID=1 且 STAT 不是 Z` → 孤儿，正常；`STAT=Z` → 僵尸，去查它 PPID 指着的那个父进程。一个配置坑：systemd `KillMode=process` 只杀主进程，把子进程全变孤儿占着端口——保持默认 `control-group`。

| 对比 | 孤儿 | 僵尸 |
|------|------|------|
| 还活着吗 | 活，还在跑 | 死，只剩槽位 |
| STAT | 通常 S/R | Z + `<defunct>` |
| PPID | 变 1（被收养） | 仍是没 wait 的父 |
| 处理 | 确认是否预期 | 修父 wait 或杀父止血 |

> ⚠️ **别混**：**PPID=1 ≠ 僵尸**——把孤儿当僵尸清掉，杀的是好好干活的进程；认僵尸只认 STAT=Z。

### 再追问

- **孤儿需要处理吗？**——一般不用，被收养后正常受管；真要避免就修 `KillMode` 或收敛 fork 行为，不要见一个杀一个。
- **孤儿会变僵尸吗？**——孤儿 exit 后由 PID 1（systemd/tini）wait 收尸，正常不会变僵尸；容器里 PID 1 是 shell 且不 wait，才会攒僵尸——那是修 PID 1，不是修孤儿。

## Q7

**★★★★☆｜退出码 137、139、143 分别是什么意思？139 的 core dump 怎么配？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、死亡：exit、僵尸与退出码](知识点.md)

### 场景

Q3 停服链的出口码就在这里：grace 超时是 137，正常 TERM 是 143。

`docker inspect` 里 `ExitCode: 137`，同事直接去 `dmesg` 找 OOM；另一次 139 也在 dmesg 里翻，什么都没翻到。

先自己试试：137/139/143 各查什么？139 去 dmesg 找 OOM 对不对？

### 完整解答

> 🎯 **一句话**：被信号杀死退出码 = 128 + 信号号——137=KILL 查 OOM/强杀，139=SEGV 查 core/hs_err，143=TERM 是正常 stop。

```text
137 = 128 + 9  (SIGKILL)  ← OOM、人手 -9、grace 超时强杀；查 dmesg / cgroup memory.events → 07
139 = 128 + 11 (SIGSEGV)  ← 段错误，查 core dump / Java hs_err，不是去 dmesg 找 OOM
143 = 128 + 15 (SIGTERM)  ← 正常 stop / 发版 / 驱逐，grace 内退出，一般无事
  1 = 进程自己 exit(1)    ← 不是信号；看 journal 和业务日志 → 04
```

139 要先让 core 能落盘，四检查：`ulimit -c` 非 0（常见默认 0）、systemd unit 的 `LimitCORE`、`/proc/sys/kernel/core_pattern` 指向可写目录、容器挂了 volume。落盘后 `gdb /path/to/bin core` → `bt` 看栈；**Java 看 `hs_err_pid*.log`，不是 Linux core**。core / 日志 / 热更不落 NFS——NFS 一抖全丢还可能 D（Q1）。dump 完立刻收走，别撑爆盘。

> ⚠️ **别混**：**137 不都是 OOM**——人手 -9 和 grace 超时强杀也是 137，先查 `dmesg` 和 `memory.events` 再定性；139 也别去 dmesg 找 OOM，它跟内存没关系，是段错误。

### 再追问

- **为什么是 128 + 信号号？**——约定：自 exit 的码 0~127，被信号杀的用 128+n 区分来源，shell 里 `$?` 一眼能分流。不要硬背三个数不讲来源。
- **core_pattern 指到 systemd-coredump 了怎么看？**——`coredumpctl list` 找到再 `coredumpctl gdb`；别只会翻文件系统。若 coredumpctl 无记录，先回头查 ulimit 和 LimitCORE，不要直接下「没 crash」的结论。

## Q8

**★★★★☆｜怀疑 fd 泄漏怎么查？为什么「重启就好」？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：STAT 第一眼定责](知识点.md)

### 场景

网关跑三天后新连接进不来，日志 `Too many open files`。有人提议把 ulimit 调到 100 万。

先自己试试：fd 泄漏第一刀数什么？只加 ulimit 行不行？

### 完整解答

> 🎯 **一句话**：fd 只增不减就是泄漏——`/proc/PID/fd` 计数看斜率、分类看 socket 还是文件；ulimit 只是推迟爆炸，重启只是止血。

```bash
ls /proc/28451/fd | wc -l                  # 隔 60s 数一次，稳着涨 = 泄漏
ls -l /proc/28451/fd | grep -c socket      # socket fd 涨 → 常伴 CLOSE_WAIT → 12
cat /proc/28451/limits | grep 'open files'
# Max open files  65535  65535             ← 计数逼近 65535 就爆 Too many open files
```

socket fd 涨多是对端关了、本地没 close（CLOSE_WAIT，排查见 [12](../12-网络栈与Socket/)）；普通文件 fd 涨是日志/上传没关。网关 fd 打满的表现是**只拒新连接**、老连接还活着——因为 accept 不了新的。「重启就好」是因为进程退出、内核回收它全部 fd——这证明泄漏在这个进程生命周期里，不证明根因消失，重启是止血不是修复；只调大 ulimit 同样只是推迟爆炸时刻。

> ⚠️ **别混**：**fd 列表看「已经打开了什么」，strace 看「正在调什么」**——泄漏类问题别用 strace 全量跟踪去抓。

### 再追问

- **ulimit 该不该调？**——短期缓解可以调，但要同时建 fd 数量告警；不要调完 100 万就当修好了，真泄漏照样会到顶。
- **怎么区分是泄漏还是流量真涨？**——看斜率是否与连接数/请求量同步回落：流量回落 fd 不回落才是泄漏。不要只看一个时刻的绝对值。

## Q9

**★★★★☆｜strace 看到一堆 futex 是什么意思？strace 和 fd 排查怎么分工？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：STAT 第一眼定责](知识点.md)

### 场景

逻辑服 P99 突然劣化，你 `strace -p` 挂上去看了半小时，输出刷屏看不懂，P99 更差了。

先自己试试：futex 爆炸说明什么？该加核还是减锁？

### 完整解答

> 🎯 **一句话**：futex 爆炸 = 用户态锁竞争，去减锁不是加核；strace 用 `-c` 统计模式跑 5~10 秒短窗口，别全量长挂。

```bash
timeout 8 strace -c -p 28451
# % time  seconds  calls  syscall
#  60.0   4.800    91231  futex            ← futex 爆炸 = 锁竞争，去减锁
#  25.0   2.000    88001  write            ← write/read 次数爆炸 = 小 IO，合并日志/加缓冲
#   5.0   0.400     1024  epoll_wait       ← 极多而业务空转 = 查超时/连接风暴
```

看的是**调用量级和分布**，不是逐行跟。分工：**卡死类**问题用 strace（进程在干什么 syscall、卡在哪个调用）；**泄漏类**问题用 fd 列表（已经打开了什么）。跟线程加 `-f`。strace 用 ptrace 实现、本身有开销——**战斗服不要长时间全量跟踪**，P99 被打高是操作者的责任；敏感路径换 perf / eBPF。

> ⚠️ **别混**：`-c` 统计和全量逐行是两种用法——找量级分布用 `-c` 短窗口，抓单次卡死才临时全量；不要默认全量挂一下午。

### 再追问

- **epoll_wait 次数特别多但业务量没涨，怀疑什么？**——超时设得太短或连接风暴导致空转；结合 fd 列表和连接数曲线看。不要直接归因为「内核慢」。
- **为什么 futex 高要去减锁而不是加核？**——futex 是用户态锁的等待调用，锁竞争靠拆临界区/分片；加核可能更糟（跨核争抢）。详见 [06](../06-CPU与Load/)。

## Q10

**★★★☆☆｜fork 一个子进程报 ENOMEM，但宿主机内存明明够？COW 是什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：fork、exec 与进程树](知识点.md)

### 场景

和 Q2 的「占 PID」不同，本题考的是出生段的 COW 预留。

512Mi limit 的 Pod 里 `Runtime.exec("curl ...")` 抛 `error=12, Cannot allocate memory`；宿主机 `free -h` 还剩几十 G。

先自己试试：宿主机 free 还有几十 G，fork 为什么 ENOMEM？

### 完整解答

> 🎯 **一句话**：fork 时内核按「子进程可能写所有页」做 COW 预留，cgroup 的账不够就 ENOMEM——与宿主机 free 无关。

COW（copy-on-write，写时复制）：fork 只复制**页表**，父子指向同一批物理页并标只读；谁先写谁触发缺页、复制那一页各持一份。**省的是「立刻复制物理页」，不省「内核的预留检查」**——fork 时内核仍按最坏情况检查配额。容器里看容器的账，不看宿主机的：

```bash
cat /sys/fs/cgroup/memory.max       # 536870912 = 512Mi
cat /sys/fs/cgroup/memory.current   # 已贴着 max → fork 的预留必失败
# error=12 = ENOMEM ← 不是宿主机没内存，是这个 cgroup 的账不够
```

修法：子进程改 sidecar / 本地 HTTP / IPC，或给 limit 留出 COW 余量（细账见 [10](../10-cgroup与容器/)）。顺带把起进程的链讲全：**fork 复制 + exec 替换**——shell 起命令、`Runtime.exec` 都是这条链；Redis BGSAVE、Nginx 拉 worker 是只 fork 不 exec 的复制品用法。

> 📝 **面试**：COW 按「省什么、不省什么」两段答——省立刻复制物理页，不省内核预留；再用 512Mi Pod ENOMEM 的例子收尾，秒杀只背定义的。

### 再追问

- **起线程也这样吗？**——不会。线程共享地址空间，不走 fork 的页表复制和预留检查；这个坑特指 fork 子进程。不要答成「内存紧张什么都不能起」。
- **COW 之后父子会互相影响吗？**——不会，写时各自持副本；共享的只是未改动的只读页。不要把 COW 说成「父子共用一份数据」。

## Q11

**★★★☆☆｜Nginx reload 用的什么信号？卡在 D 的 worker 换得掉吗？SIGPIPE 为什么要忽略？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [四、挨打：信号怎么递送、谁能挡住](知识点.md)

### 场景

改完配置 `nginx -s reload`，监控显示 Nginx 内存「翻倍」了；另一次自研 C 网关莫名整个进程消失，core 都没有。

先自己试试：HUP / USR2 / TERM 三件事怎么分？SIGPIPE 为什么要 Ign？

### 完整解答

> 🎯 **一句话**：reload 是对 master 发 SIGHUP 换 worker 不是重启；卡 D 的旧 worker 换不掉；SIGPIPE 默认动作是杀进程，网关必须 Ign。

`nginx -s reload` 对 **master** 发 **SIGHUP(1)**：master 重读配置、拉新 worker，**旧 worker 处理完手上连接再退**。两个坑：卡在 **D** 的旧 worker 回不了用户态、退不出，reload 换不掉它，只能修 IO；长连接 + 慢退 → 旧 worker 还挂着一批连接，内存看起来「reload 后翻倍」，退完才回落——配 `worker_shutdown_timeout` 兜底（[19](../19-Nginx/)）。SIGPIPE(13)：对已关闭的管道/socket `write`，内核默认发 SIGPIPE，**默认动作是把进程整个杀掉**——自研 C/C++ 网关「偶发整个进程没了」的头号原因。处理：`signal(SIGPIPE, SIG_IGN)` 忽略，改为检查 `write` 返回 -1 和 `errno=EPIPE`；Go / Java 运行时已默认处理。

> ⚠️ **别混**：**HUP = 重读配置换 worker，USR2 = 热升级二进制，TERM = 停服**——三件事三个信号；「reload 就是重启 Nginx」是错讲法。

### 再追问

- **reload 之后旧 worker 会立刻退吗？**——不会，处理完存量连接才退；有 D 状态的甚至退不掉。不要 reload 完就看内存下结论，等旧 worker 退完再看。
- **Java 服务还要处理 SIGPIPE 吗？**——运行时已默认处理，业务层感知为写异常；要防的是写已断连接时的业务重试风暴。不要在 Java 里再手写 signal handler。

## Q12

**★★★★☆｜现场：给你一台机器，你怎么用 ps/pstree/kill 定位进程问题？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：STAT 第一眼定责](知识点.md)

### 场景

面试官扔给你一台「进程不对」的机器：不带任何上下文，现场敲命令，说结论。

先自己试试：ps / pstree / kill 各管什么？systemctl stop 优于裸 kill 在哪？

### 完整解答

> 🎯 **一句话**：第一刀 `ps` 按 STAT 主字母分堆——D 查 wchan、Z 查 ppid、T 查谁 STOP、进程没了查退出码；杀进程永远从 TERM 开始。

```bash
ps -eo pid,ppid,stat,wchan:30,comm | head   # STAT 主字母分堆，wchan 顺手带上
#  PID  PPID STAT WCHAN:30            COMMAND
# 28451     1 D    nfs_wait_bit_unin… logic-server   ← D：IO，进 wchan 分支
# 28453 28451 Z    -                   [curl] <defunct>← Z：查 ppid 28451 修 wait
# 28454 28451 Rl   -                   logic-server   ← Rl：在跑 + 多线程
pstree -p 28451                            # 谁拉起谁、线程长什么样一眼看全
top -H -p 28451                            # 单线程热点：%CPU 全在一个线程上
```

分堆后按决策树下刀：D → `wchan` 三种字样各修各的 IO；Z → 按 ppid 聚合找不 wait 的父；T → 查谁发的 STOP、`kill -CONT`；R/S 活着 → 看业务正常与否、fd 计数；进程没了 → 退出码分流（137 查 dmesg/memory.events、139 查 core、143 查发版）。杀进程口径：`kill PID` 默认 TERM 就是首选；成组的用 `kill -TERM -<PGID>`（负号进程组）；**有 systemd unit 的优先 `systemctl stop`**——它会管 grace 和收尾，优于裸 kill；`-9` 是最后手段。

> 📝 **面试**：按「第一刀 STAT 分堆 → 每堆一个出口 → kill 从 TERM 开始」三段口述，边敲边说结论——考的就是这套节奏。

### 再追问

- **为什么 systemctl stop 优于裸 kill？**——它按 unit 配置发 TERM、等 grace、超时才升格，还负责日志收尾；裸 kill 容易跳过 grace 直接砸 -9。不要上来就 `kill -9` 显得果断。
- **`kill -9` 的克制清单？**——有状态服务（刷盘）、DB 主库、带子进程要收尸的进程，三者都不该直接 -9。不要答「任何时候都能 -9，反正在容器里」。

## Q13

**★★★★☆｜fd 泄漏和进程数暴涨，第一刀怎么分？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、作战：STAT 第一眼定责](知识点.md)

### 场景

就是 Q8 那位同学踩的坑的升级版——先分型再谈 ulimit。

日志 `Too many open files`，`ss` 连接数正常。有人要 `ulimit -n 65535` 一把梭。

先自己试试：Too many open files，第一刀怎么分型？ulimit 一把梭对不对？

### 完整解答

> 🎯 **一句话**：**先数 fd 类型**——连接泄漏看 `ss`/`lsof` 网络 fd；文件泄漏看 `lsof` 普通文件；线程暴涨看 `pids.current`（→ 10）。

```bash
ls /proc/$PID/fd | wc -l
lsof -p $PID | awk '{print $5}' | sort | uniq -c | sort -rn | head
cat /proc/$PID/limits | grep "open files"
```

| 签名 | 定责 |
|------|------|
| 大量 socket ESTAB/TW | 连接未 close → 12/13 |
| 大量 log/tmp | 文件未 close |
| 线程数≈pids | 线程泄漏 → 10 |

加大 `ulimit` 是缓冲，不修泄漏只会更晚更猛地爆。

### 再追问

- systemd 服务 fd 上限？——`LimitNOFILE`（→ 11），和 shell ulimit 不是一回事。

**★★★★★｜白板：进程一生五阶段 + STAT 决策树 + 优雅停服链？**
