## Q1

**★★★★★｜登主机第一分钟，命令顺序怎么排？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 §6.1 · §2.1

### 场景

告警群喊「登录服慢」。旁边同事已经打开 `top` 在按 P/M，另有人准备 `strace -fp`。面试官问：你的 30 秒怎么敲？

### 完整解答

**一句话**：uptime（对比核数）→ vmstat（丢首行分型）→ 按型补 mpstat/free/iostat → systemctl/df；top/strace 不是首刀。

```text
1. uptime + lscpu/nproc     → Load 尺度
2. vmstat 1 5               → r/b/wa/si/so 分型（丢第一行）
3. 按型：mpstat / free / iostat
4. systemctl is-active|status · df -hT
```

定域后再 3 分钟下钻（top -H、iotop、journalctl…）。机制深排甩给 03～05 / 13；网络甩 02/16。

### 再追问

为什么不能一上来 top？——top 是「找谁」，先要知道忙在 CPU 还是 IO；否则容易对着 idle 70% 的整机平均空转。

## Q2

**★★★★★｜Load=40、idle=70%，要加核吗？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 §5.1 · §7.2 · §4.2

### 场景

8 核机器，uptime 1m=40。有人开单「加 8 核」。你登上去看 top 抬头 `%id=70`、`%wa=18`。

### 完整解答

**一句话**：Load 是队列不是 CPU%；先看 vmstat 的 b/wa——本例是 IO 型，加核常无效，转 iostat。

```text
uptime     → 40 >> 8（确实过载感）
vmstat     → b↑ wa↑ id 仍高 → IO 型
iostat     → await/%util → 08
```

| 型 | 信号 | 别做 |
|----|------|------|
| CPU 型 | r↑ us/sy↑ b≈0 | 不看单核就加核也错 |
| IO 型 | b↑ wa↑ | **加核** |

### 再追问

Load 和 CPU% 两把尺各量什么？——Load 量可运行+不可中断睡眠队列；CPU% 量这一秒时间花在哪一格。深义见 06，本章要能分型挥刀。

## Q3

**★★★★☆｜给你一段 vmstat，怎么分型？**

**覆盖**：核心 · 必会

**对应**：知识点 §4.2

### 场景

```text
 r  b   si  so  us sy id wa st
 1  0    0   0   5  2 93  0  0
 2 18    0   0   5  2 70 18  0
 2 19    0   0   4  2 71 18  0
```

同事说第一行 id=93「很闲」。

### 完整解答

**一句话**：丢掉第一行（开机平均）；后两行 b↑ wa↑ → IO 型，下一刀 iostat/iotop。

口诀：

- `r`↑ + `us/sy`↑ + `b≈0` → CPU → mpstat/top  
- `b`↑ + `wa`↑ → IO → iostat  
- `si/so`≠0 → 内存 → free/dmesg  

### 再追问

`st` 持续偏高怎么办？——虚机超卖嫌疑，出口 03，不是先调 JVM。

## Q4

**★★★★★｜整机 CPU 38%，为什么 P99 还炸？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 §4.4 · §5.4

### 场景

```text
CPU   %usr  %idle
all   38.2   58.2
  3   99.2    0.0
  0    5.0   92.0
```

有人说「机器还有余量」。

### 完整解答

**一句话**：整机平均被闲核稀释；CPU3 单核打满就能把 P99 打爆——必须 `mpstat -P ALL`。

下一刀：`pidstat -u` / `top -H -p` 锁定 TID；热点型拆线程/主循环，不是「整机再加 8 核」。机制与火焰图边界 → 06 / 12。

### 再追问

若是 CPU7 `%soft=45` 呢？——软中断偏核，想 RSS/中断亲和，回 03；别先改 TCP 窗口。

## Q5

**★★★★★｜free 只有 400Mi，要清 cache 吗？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 §4.6 · §5.2

### 场景

```text
total  used  free  buff/cache  available
15Gi   8Gi   400Mi    7Gi         6.1Gi
```

新人准备 `echo 3 > /proc/sys/vm/drop_caches`。

### 完整解答

**一句话**：结案看 available（还有 6.1Gi）；free 小、cache 大常常正常——不要当常规止血清 cache。

清 cache 会把热数据打冷，容易制造 IO 风暴。真告急：available 极低、si/so 跳、或 dmesg 已有 OOM → 进 04，不是先 drop_caches。

### 再追问

Swap used 在涨说明什么？——内存压力实锤方向；找 RSS 大户 + 查是否该加内存/限流，出口 04。

## Q6

**★★★★☆｜iostat 第一组 await=3，第二组 180，听谁的？**

**覆盖**：必会 · 常用 · 常考

**对应**：知识点 §4.8 · §5.3

### 场景

新人把 `iostat -xz 1 2` 的第一组贴进群：「await 才 3，盘没问题」。你看第二组 `%util=98`、`await=180`。

### 完整解答

**一句话**：第一组是开机平均，丢掉；从第二组起读——本例盘忙实锤方向，下一刀 iotop/pidstat -d。

同一铁律适用于 **vmstat**。await 组成公式不在本章展开 → 08。

### 再追问

%util≈100 是否等于必须立刻加盘？——先确认谁在写、是否打错盘、是否网络盘抖动；加盘是选项不是第一反应。

## Q7

**★★★★★｜df 100%，du 根上只有 60G，空间去哪了？**

**覆盖**：必会 · 常用 · 常考

**对应**：知识点 §4.9 · §7.4

### 场景

`/` 100G 盘，`df -h` Use%=100%；`du -xh --max-depth=1 /` 加起来约 60G。写入报 `No space left on device`。

### 完整解答

**一句话**：多半是已 delete 但仍被进程握着的 fd；`lsof | grep deleted`（或 `lsof +L1`），重启/让进程 reopen 才退空间。

```bash
df -hT; df -i          # 也要排除 inode 满
lsof | grep deleted
# 对握 fd 的服务：优雅 reopen / restart（按变更规范）
```

只再 `rm` 同名路径不会吐空间。长期：logrotate 与正确 reopen。

### 再追问

df -h 还有空但写失败？——查 `df -i`；inode 100% 一样写不进。

## Q8

**★★★★☆｜systemctl status 显示 failed，下一步？**

**覆盖**：必会 · 常用

**对应**：知识点 §4.11 · §4.10 · §7.5

### 场景

```text
Active: failed (Result: exit-code)
Main PID: 2341 (code=exited, status=2)
```

有人连续 `systemctl restart` 十次。

### 完整解答

**一句话**：先 `journalctl -u <unit> --since …` 看退出原因；别无限 restart，尤其小心 start-limit-hit。

读 status 三件套：Active / Main PID / 尾部日志。应用 panic → 修应用；若 Result 是 timeout/resources/依赖问题 → 11。本章不改 unit 写法。

### 再追问

Active=active 是否等于玩家能进？——不等于；进程在只是主机侧「没挂」，业务探活/网络另查 12·21·27。

## Q9

**★★★★★｜进程突然没了，怎么确认是不是 OOM？**

**覆盖**：必会 · 常考

**对应**：知识点 §4.6 · §7.3

### 场景

gameserver 没了，重启后「好了」。经理问根因。有人说「可能是 bug 自己退出」。

### 完整解答

**一句话**：`free -h` 看 available；`dmesg -T | grep -iE 'oom|killed process'`（或 `journalctl -k`）留证——有 Killed process 就按 OOM 迹象交接 04，禁止只重启不留证。

```bash
free -h
dmesg -T | grep -iE 'out of memory|oom-killer|Killed process' | tail -20
```

容器场景还要怀疑 cgroup 限额（宿主机 free 可能很胖）→ 07/07。

### 再追问

本章要不要讲清 OOM 计分？——不要；刀法到「发现+贴证」，计分与处置回 04。

## Q10

**★★★★☆｜top 和 mpstat 各回答什么问题？**

**覆盖**：必会 · 常用

**对应**：知识点 §4.3 · §4.4

### 场景

面试白板：已经 vmstat 判成 CPU 型。下一步 top 还是 mpstat？能不能只留一个？

### 完整解答

**一句话**：mpstat 回答「哪颗核、哪一格」；top/htop 回答「哪个 PID/TID」——两刀都要，缺一不可。

```text
mpstat -P ALL  → CPU3 %usr 99%
pidstat/top    → PID 2341
top -H -p      → TID 2360
```

只有 top 的整机 %Cpu 会重蹈「平均 40%」覆辙；只有 mpstat 不知道杀谁/看谁的栈。

### 再追问

htop 和 top 定责口径有区别吗？——没有；htop 更友好，读的仍是同一套信号。

## Q11

**★★★☆☆｜什么时候才上 strace？**

**覆盖**：常用 · 常考

**对应**：知识点 §4.12 · §6.2

### 场景

进程在、CPU 不高、业务「卡住」。新人直接 `strace -fp` 挂上所有线程，机器更慢了。

### 完整解答

**一句话**：已缩到单 PID 后，用 `timeout 15～20s` 短挂确认卡在哪类 syscall；不当首刀，避免无 timeout 的 `-f` 大爆炸。

认四类即可：等锁（futex）、等 IO（read/fsync）、等网（recvfrom）、找文件（ENOENT）。更深 profiling → 21。

### 再追问

`-c` 模式有什么好处？——先看 syscall 时间占比，输出更收敛，适合「一瞥」。

## Q12

**★★★★★｜高 Load / OOM / 盘满 / 服务 down：四条树怎么口述？**

**覆盖**：核心 · 必会 · 常考

**对应**：知识点 §7

### 场景

面试官：「别讲原理，讲你登上去先做和别做。」限时两分钟。

### 完整解答

**一句话**：四条树都是「先定域贴证，再甩邻章」；每条都有明确别做。

| 枝 | 先做 | 别做 |
|----|------|------|
| 高 Load | vmstat 分型 → CPU 走 mpstat/top，IO 走 iostat | IO 型加核；不看单核就扩容 |
| OOM 迹象 | free + dmesg OOM 留证 | 只重启不留证 |
| 盘满 | df/du；对不上 lsof deleted | 乱删系统目录；只 rm deleted 路径 |
| 服务 down | status + journalctl -u | 无限 restart 不看日志 |

总入口永远是 30 秒套餐（§6.1）。

### 再追问

网络慢是否走这四条？——主机套餐扫过一轮若像网，**停**主线转 02/16，不要在 top 里耗死。
