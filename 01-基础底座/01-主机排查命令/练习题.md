## Q1

**★★★★★｜登上一台被告警说「慢」的主机，第一分钟你敲什么命令？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、分型：vmstat 一屏定四型](知识点.md)

### 场景

告警群喊「登录服慢」，你 ssh 上去。旁边同事已经在 top 里按 P/M 来回切，还有人准备直接 `strace -fp` 挂到主进程上。

### 完整解答

> 🎯 **一句话**：一尺 uptime、一屏 vmstat、按型补一刀、排除「挂了/满了」，30 秒定域。

刀序是固定的，不是想到哪敲到哪：

```bash
# ① 尺度：Load 高不高要拿核数当尺子
uptime; lscpu | egrep '^CPU\(s\)'
# Load 35.21, 12.08, 4.02；CPU(s) 8 → 1m≫15m，刚砸上来的忙
# ② 分型：丢第一行
vmstat 1 5
# ③ 按型三选一
mpstat -P ALL 1 2     # r↑ us/sy↑ → CPU 型
free -h               # si/so≠0 → 内存型
iostat -xz 1 2        # b↑ wa↑ → IO 型（丢第一组）
# ④ 排除「根本没在跑 / 盘满了」
systemctl is-active gameserver || systemctl status gameserver --no-pager -l | head -30
df -hT
```

口述版：**Load 对核数（忙不忙）→ vmstat 定型（忙在哪）→ 对型补一刀 → systemctl/df 排除挂了和满了 → 贴证据进机制章**。

> ⚠️ **别混**：`uptime` 的 Load **不是 CPU 利用率**，要对比核数读；`vmstat` / `iostat` 的第一行/第一组是**开机以来的平均值**，必须丢掉——这两条是这套刀序里最容易讲错的地方。

> 📝 **面试**：背「一尺一屏四刀四口」——一尺 uptime、一屏 vmstat、四刀 mpstat/free/iostat/systemctl、四口 06/07/08/11；再补一句「top 翻着玩和裸挂 strace 都不是首刀」，这句是加分项。

### 再追问

- **为什么第一刀不是 top？**——top 抬头是整机平均，单核热点会被闲核稀释；而且没定型就翻进程列表，是拿望远镜一寸寸扫。top 是 CPU 型定域之后的刀。
- **四线全平、指标都正常，但业务就是慢呢？**——停主机刀，转网络刀 [02](../02-网络排查命令/) / 抓包 [16](../16-网络排障与抓包/)；别在 top 里耗死。

## Q2

**★★★★★｜8 核机器 Load 40，但 CPU idle 还有 70%，要加核吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、接警：uptime / lscpu 先拿尺子](知识点.md)

### 场景

活动开始 3 分钟，监控上 Load 冲到 40，群里有人喊「快加核」。你看了一眼 CPU 图，idle 还有 70%。

### 完整解答

> 🎯 **一句话**：不加。Load 是队列不是 CPU%，idle 70% + Load 40 指向 IO 型，下一刀 iostat。

三步讲清：

1. **Load（load average）数的是队列**——「可运行的 R + 不可中断睡眠的 D」任务的长度平均，不是 CPU 被用了多少。等盘的 D 状态进程照样计入 Load。
2. **Load 高不高必须拿核数当尺子**——`lscpu` / `nproc` 拿到 8 个逻辑核，40 是严重排队；但排的可能是「队」不是「CPU」。
3. **idle 70% 说明 CPU 大量空闲**——两者组合的签名是「大量进程在等盘」：CPU 想干活没数据。下一刀 `vmstat 1 5`（丢第一行）会看到 `b` 持续 > 0、`wa` 明显，再 `iostat -xz 1 3`（丢第一组）看 `await` / `%util`，然后 iotop / `pidstat -d` 找是谁在刷盘。

> ⚠️ **别混**：加核对 IO 型无效——队列卡在盘上，加多少核都还是排在同一个盘后面。反过来 `%iowait` 高也不等于 CPU 不够，同一个误区两头踩。

> 📝 **面试**：先给结论「不加核」，再给机制「Load = R+D 队列」，最后给刀序「vmstat 看 b/wa → iostat 看 await/%util → iotop 找进程」。根因（盘为什么慢）甩 [08](../08-磁盘与IO/)。

### 再追问

- **Load 大概等于核数算高吗？**——只是「可能打满」的参考线，还要分是排队算（R，CPU 型）还是排队等盘（D，IO 型），vmstat 一屏定。
- **什么情况真的该加核？**——`r` 持续 > 核数、`us/sy` 高、`b≈0`、mpstat 确认多颗核都忙（不是单核热点）——CPU 型且非热点，加核才是对的处方。

## Q3

**★★★★☆｜vmstat 1 5 的输出你主要看哪几列？怎么用一屏判断瓶颈在哪？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [三、分型：vmstat 一屏定四型](知识点.md)

### 场景

面试官丢出一段 vmstat 输出，让你现场读；也常换皮成「vmstat 和 top 有什么区别，你先用哪个」。

### 完整解答

> 🎯 **一句话**：丢第一行，看 `r`/`b` 定队列、`wa`/`si`/`so` 定方向，三秒分 CPU / IO / 内存型。

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0      0 8123456 123456 9876543   0    0   120   800 4500  9000  5  2 93  0  0   ← 丢
 2 18      0 8123000 123456 9876540   0    0   115  8900 4480 11800  4  2 70 18  0
 2 19      0 8122900 123450 9876500   0    0   110  9100 4490 12000  4  2 71 18  0
```

分型口诀（每行一个签名）：

- `r` 持续 **> 核数** + `us/sy` 高 + `b≈0` → **CPU 型** → `mpstat -P ALL`
- `b` 持续明显 > 0 + `wa` 高 + `id` 仍可观 → **IO 型** → `iostat`
- `si/so` **非 0** → **内存压力** → `free -h` + dmesg 搜 OOM
- 三者都平但服务挂了 → **服务型** → `systemctl`

system 区两列辅助定性：`cs`（context switch，上下文切换）持续 > ~10 万且延迟涨 → 查线程数/锁；`in` 突增且后面 mpstat 见 `%soft` 高 → 网卡/中断。`free` 列只粗看，结案用 `free -h` 的 available。

> ⚠️ **别混**：第一行是**开机以来的平均值**，不代表当前——这是 vmstat 和 iostat 共用的铁律。另注意 `id` 高不能单独证明没事：IO 型可以 id 高、Load 高、业务惨。

### 再追问

- **cs 十几万一定有问题吗？**——要看业务形态：高并发代理类本来切换就多；要配上「延迟涨不涨、nvcswch（非自愿切换）占比高不高」才定性，pidstat `-w` 拆到进程看。
- **vmstat 和 top 先用哪个？**——vmstat 先：它是分型仪（忙在哪一类），top 是定位仪（哪个进程）；定型之前 top 只能瞎翻。

## Q4

**★★★★★｜整机 CPU 才 38%，接口 P99 为什么炸了？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、追凶·CPU：top / mpstat / pidstat](知识点.md)

### 场景

P99 从 40ms 涨到 600ms，监控大屏整机 CPU 使用率 38%，有人据此说「CPU 不是瓶颈，查应用去」。

### 完整解答

> 🎯 **一句话**：整机平均被闲核稀释了，单核打满就够炸 P99——`mpstat -P ALL` 逐核看。

```bash
mpstat -P ALL 1 3
```

```text
21:06:02  CPU    %usr   %sys  %iowait  %soft  %steal  %idle
21:06:02  all    38.20   2.10    0.50    1.00    0.00   58.20
21:06:02    3    99.20   0.80    0.00    0.00    0.00    0.00   ← CPU3 单核打满
21:06:02    7     2.00   1.00    0.00   45.00    0.00   52.00   ← CPU7 %soft 45%
```

38% 是 all 行的平均——8 核里 1 颗 99% + 7 颗闲，平均照样好看。单线程主循环、单队列消费、锁竞争，都只需要一颗核打满就能把依赖它的所有请求拖过 P99。

下一刀连招：`top -H -p <PID>` 或 `pidstat -t -p <PID>` 找到烫的 TID，`pidstat -u` 的 `CPU` 列确认它就跑在 CPU3 上，三条证据串成链——**热点型，拆那个线程，不是整机加核**。

> ⚠️ **别混**：top 抬头的 `%Cpu(s)` 和 mpstat 的 `all` 行是同一个数（整机平均），都会骗人；要看「哪颗核」必须 `-P ALL` 或 top 按 `1`。

> 📝 **面试**：「整机平均会骗人」六个字先说，然后给连招 mpstat -P ALL → top -H →（Java）printf '%x' TID 对 jstack 的 nid。软中断偏核（%soft 单核高）想 RSS/中断亲和 → [06](../06-CPU与Load/)。

### 再追问

- **top 和 mpstat 分工是什么？**（旧题并入）——mpstat 回答「哪颗核、哪一格」（usr/sys/soft/steal/iowait），top/pidstat 回答「哪个 PID/TID」；单核热点两刀都要，缺一个就断链。
- **%steal 持续 12% 说明什么？**——虚机被宿主机抢走时间片，超卖嫌疑；先找云厂商/换宿主机，不是先调应用参数，深排 → [06](../06-CPU与Load/)。
- **top 里某进程 %CPU 250%，正常吗？**——正常，多线程跑满多颗核，是相对单核的百分比。

## Q5

**★★★☆☆｜pidstat 比 top 好在哪？-u -r -d -w 各看什么？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [四、追凶·CPU：top / mpstat / pidstat](知识点.md)

### 场景

面试官看你简历写了「用 sysstat 全家桶」，追问：既然有 top，为什么还要 pidstat？

### 完整解答

> 🎯 **一句话**：pidstat 按采样打印、可贴工单，四把尺把 CPU/内存/IO/切换拆到进程（-t 拆到线程）。

top 是「盯着看」的交互屏，pidstat 是**采样输出**——干净、有时间戳、能直接贴进工单，还能看趋势。四把尺：

```bash
pidstat -u 1 3          # CPU：每进程 %usr/%sys/%CPU，CPU 列 = 最近跑在哪颗核
pidstat -r 1 3          # 内存：RSS 演变，minflt/majflt（major fault 要走盘的缺页）
pidstat -d 1 3          # IO：每进程 kB_rd/s、kB_wr/s、iodelay
pidstat -w 1 3          # 切换：cswch/s（自愿，等资源）、nvcswch/s（非自愿，被抢）
pidstat -t -p 2341 1 3  # 拆到线程
```

典型用法：mpstat 说 CPU3 打满 → `pidstat -u` 看谁的 `CPU` 列停在 3 → `pidstat -t` 拆到线程接 jstack；iostat 说写爆 → `pidstat -d` 看谁 `kB_wr/s` 巨大，交叉 iotop。

> ⚠️ **别混**：pidstat 的 `%wait` 和 mpstat 的 `%iowait` **不是同一把尺**，口径不同别硬换算；`iodelay` 是等 IO 的粗粒度感，定量看 iostat/iotop。

### 再追问

- **nvcswch/s 持续很高说明什么？**——非自愿切换：时间片总被抢，CPU 争用实锤方向；结合 `cs > ~10 万/s` 和延迟，查线程数是否过多，深排 → [06](../06-CPU与Load/)。
- **想知道昨晚 3 点的进程 CPU，pidstat 能做吗？**——不能，它是实时采样工具；历史回看用同家族的 sar（`sar -u`，依赖 sysstat 的 cron 在采）。

## Q6

**★★★★★｜free 显示 free 列只剩 400Mi，要不要执行 echo 3 > drop_caches 清一下？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、追凶·内存：free 与 OOM 痕迹](知识点.md)

### 场景

内存告警「可用不足」，机器上跑着 MySQL 和游戏服。有人提议 drop_caches 止血，有人提议马上重启 MySQL。

### 完整解答

> 🎯 **一句话**：不清。结案看 available 不是 free，drop_caches 是制造二次故障。

```text
              total    used    free    shared  buff/cache  available
Mem:           15Gi   8.0Gi   400Mi     200Mi      7.0Gi      6.1Gi
```

- **free 小是常态**：现代内核默认把闲内存拿去做**页缓存（page cache）**，free 列常年小不等于内存爆。
- **buff/cache 可回收**：需要时内核会还给应用，所以结案列是 **available**（对应 `/proc/meminfo` 的 `MemAvailable`，内核估计「不杀进程还能给应用多少」）。这台 available 6.1Gi，不需要任何止血。
- **drop_caches 别当常规操作**：把热缓存打冷，应用紧接着重新从盘读——等于亲手制造一波 IO 风暴；性能只会更差。

正确的内存刀序：`free -h` 看 available → vmstat 看 `si/so` 是否非 0 → dmesg 搜 `Killed process` 留 OOM 证据 → 找 RSS 大户（pidstat -r）→ 真告急才谈加内存/限流，机制深排 → [07](../07-内存与OOM/)。

> ⚠️ **别混**：`free` 命令的 **free 列** ≠ **available**——面试就考这一句；配套还有 `used + free ≠ total`（中间隔着 buff/cache）。

> 📝 **面试**：先说「available 还有 6.1Gi，不用处理」，再讲 free 小是 page cache 正常占位，最后补 drop_caches 的危害（打冷热缓存 + IO 风暴）。三层讲完基本满分。

### 再追问

- **那什么情况才算内存告急？**——available 极低 + `si/so` 非 0（换页在跳）+ dmesg 出现 OOM kill，三证齐全才是真告急。
- **Swap used 一直在涨要管吗？**——要：换页本身就是 IO，持续增长说明内存压力在累积；无 Swap 的机器 OOM 来得更陡（没有缓冲带）→ [07](../07-内存与OOM/)。

## Q7

**★★★★☆｜游戏服进程突然没了，你怎么确认是不是被 OOM 杀的？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、追凶·内存：free 与 OOM 痕迹](知识点.md)

### 场景

凌晨 3 点服务自愈脚本把进程拉起来了，白天复盘时有人说「重启后就好了，先这样」。

### 完整解答

> 🎯 **一句话**：禁止只重启不留证——dmesg / journalctl 搜 OOM 关键字，抓 `Killed process` 那一行。

```bash
dmesg -T | grep -iE 'out of memory|oom-killer|Killed process' | tail -20
journalctl -k -b | grep -iE 'out of memory|oom' | tail -20
```

```text
[Sun Aug 30 21:01:02 2026] Out of memory: Killed process 2341 (gameserver) total-vm:4523000kB ...
# ← Killed process + PID + 名字 = OOM 实锤，贴进工单
```

看到 `Killed process` 就把 PID、名字、时间戳记下来，证据甩 [07](../07-内存与OOM/) 深排（打分机制、为什么杀它不杀 MySQL、cgroup 限额、处置）。`journalctl -k -b` 是内核日志的另一种取法，`-b` 限定本次开机。配合 `free -h` 看当时 available、`pidstat -r` 看 RSS 演变，证据链就齐了。

> ⚠️ **别混**：**%MEM 最高的进程 ≠ OOM 元凶也不一定是受害者**——OOM killer 按打分挑（打分不只看 RSS），结论只能从 dmesg 的 `Killed process` 行读出来。

### 再追问

- **这是容器里的进程，宿主机 free 看着很胖，为什么还被杀？**——容器被杀先怀疑 **cgroup 内存限额**，不是整机内存不够；只看宿主机 free 会误判「内存充足」→ [10](../10-cgroup与容器/) · [07](../07-内存与OOM/)。
- **为什么杀它不杀 RSS 更大的 MySQL？**——OOM killer 的打分还叠加 oom_score_adj 等因素，深排在 [07](../07-内存与OOM/)；本题只需答「打分决定，不看单一 RSS」。

## Q8

**★★★★☆｜iostat 的输出第一行为什么不能信？你主要看哪几列？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、追凶·磁盘：iostat / df / du / lsof](知识点.md)

### 场景

面试官给一段 `iostat -xz 1 3` 输出，指着第一组问「这台盘是不是一直很慢」。

### 完整解答

> 🎯 **一句话**：第一组是开机以来的平均值，整组丢掉；从第二组起看 await、%util、aqu-sz。

```text
Device    r/s    w/s   rkB/s   wkB/s  await  aqu-sz  %util
nvme0n1   10.0   20.0   128.0   256.0    1.2    0.05   3.00   ← 开机平均，丢
nvme0n1   80.0  900.0   500.0  81920   180.0   12.50  98.50   ← 当前：盘忙
```

- **`await`**：每个请求的平均等待（排队 + 服务），高就是「疼」——业务延迟直接相关。
- **`%util`**：设备忙的时间占比，≈100 是「这台设备饱和」的方向感。
- **`aqu-sz`**：平均队列深度，越深说明请求堆得越多。
- `wkB/s` 巨大 → 写方向，下一步 iotop / `pidstat -d` 找进程。

这条铁律与 vmstat 第一行同源：**第一次采样覆盖的区间是「开机到现在」**，不是刚过去这一秒。

> ⚠️ **别混**：**%util ≈ 100% 不自动等于「立刻加盘」**——SSD 并行度高时 %util 100 未必到极限；先问三件事：是不是单进程写爆？是不是打错盘？是不是网络盘/邻居虚拟机吵？加盘是选项不是第一反应。

### 再追问

- **await 多少算高？**——没有绝对数，对比设备档次和基线（NVMe 和机械盘差一个量级）；运维口径是「和它自己平时比」。公式拆解（队列时间 + 服务时间）→ [08](../08-磁盘与IO/)。
- **没有 iotop 权限怎么办？**——`pidstat -d 1 3` 或 `cat /proc/<pid>/io` 凑合同样的答案。

## Q9

**★★★★★｜df 显示盘 100% 满，du 把目录加一遍对不上，少了 40G，怎么回事？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、追凶·磁盘：iostat / df / du / lsof](知识点.md)

### 场景

/var 分区 df 显示 100%，du -xh --max-depth=1 /var 加起来只有 60G。有人提议「再 rm 一遍那个日志试试」。

### 完整解答

> 🎯 **一句话**：文件被 rm 但 fd 还被进程握着（deleted），inode 没释放；lsof 找到进程，重启/ reopen 才退空间。

机制：`rm` 只做 unlink、摘掉目录项，**inode 的回收条件是「没有任何 fd 指着它」**。进程（常是忘了 reopen 的日志进程）还握着 fd 继续写，所以 du（沿目录树走）看不见它，df（数 inode/块）照样计数——两个工具从这一刻起各说各话。

```bash
lsof +L1        # link count=0 却仍被打开的文件
# nginx 1234 ... /var/log/nginx/access.log (deleted)
```

处置三步：① `lsof +L1`（或 `lsof | grep deleted`）确认谁握着；② **重启对应服务**，或让进程 reopen 日志（nginx 类支持 `kill -USR1` 重开日志文件）砍掉 fd，空间才退；③ 长期上 logrotate（copytruncate 或原生 reopen），别无脑 `kill -9`。

> ⚠️ **别混**：对已 deleted 的路径**再 rm 一次不会吐空间**——目录项早就没了。反过来删大日志前先确认没人握着，否则就是主动制造一起 deleted 案。

> 📝 **面试**：一句话机制「unlink 后 inode 活到 fd 关闭」，一句话处置「lsof 找进程 → 重启/reopen → logrotate 防再犯」，最后补「df 数 inode、du 走目录树，口径不同所以对不上」。

### 再追问

- **df -h 显示还有空间，但程序报 No space left on device？**——查 `df -i`：海量小文件把 **inode** 吃光，IUse% 100% 是另一种「满」，加容量没用，深排 → [09](../09-文件系统与inode/)。
- **du 为什么要加 -x？**——不跨文件系统，避免把挂载在下面的其他盘（或伪文件系统）一起算；在 `/` 上无深度狂扫又慢又给正在疼的盘补刀。
- **删大文件的安全姿势？**——先 `lsof` 确认没人握着再 rm；或直接用 `> file` 截断，再让进程 reopen，比裸 rm 稳。

## Q10

**★★★★☆｜进程卡在 D 状态杀不掉，和僵尸进程，分别怎么处理？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [四、追凶·CPU：top / mpstat / pidstat](知识点.md)

### 场景

ps 里一批 `D` 状态进程，`kill -9` 无效，有人建议「重启大法」；同屏还有几个 `[xxx] <defunct>`。

### 完整解答

> 🎯 **一句话**：D 杀不掉是设计如此——先解 IO；僵尸已经死了——修的是父进程。

```bash
ps -eo pid,ppid,stat,wchan:20,cmd --sort=stat | head -50
```

```text
  PID  PPID STAT WCHAN                 CMD
 2360  2341 D    wait_on_page_bit_co  /opt/game/gameserver   ← D：等盘
 2401  2341 Z    -                     [gameserver] <defunct> ← Z：僵尸
```

- **D（uninterruptible sleep，不可中断睡眠）**：几乎都在等盘/页。`kill -9` 无效不是 bug——信号要等进程返回可中断点才递达，D 状态回不来。**先解 IO**（iostat 看哪台盘、NFS 是否抖动），IO 恢复 D 自然退；机制 → [05](../05-进程与信号/)。
- **Z（zombie / defunct，僵尸）**：进程已经死了，尸体没被父进程 `wait` 收走。杀僵尸本身没意义——**修父进程**（让它正确 wait），或杀父进程让僵尸被 init/systemd 收养。

辅助两招：`wchan`（wait channel）指出 D 进程卡在哪个内核等待点，是第一线索；`pstree -ap <PID>` 看进程树归属，`PPID=1` 说明已被收养。

> ⚠️ **别混**：D 是「活着但卡死，治 IO」，Z 是「已经死了，治父进程」。另注意 D 状态进程**照样计入 Load**——Load 高 + 大量 D 也是 IO 型的旁证。

### 再追问

- **大量 D 状态和 Load 高有什么关系？**——D 在「不可中断队列」里，是 Load 的组成部分；看到 Load 高先 vmstat 看 `b` 列，b 高就是这批 D。
- **僵尸进程有危害吗？**——少量只是 PID/进程表项泄漏；海量会耗尽 PID。真正的信号是「父进程的 wait 写错了」，僵尸是症状不是病。

## Q11

**★★★★☆｜systemctl status 显示 failed，你的下一步是什么？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、追凶·服务：systemctl / journalctl / strace](知识点.md)

### 场景

游戏服 unit 显示 `Active: failed (Result: exit-code)`，Main PID exited status=2。有人提议「先把 restart 循环挂上再说」。

### 完整解答

> 🎯 **一句话**：先 journalctl 看退出原因，别无限 restart——重启不修 panic，还可能触发 start-limit-hit。

```bash
systemctl status gameserver --no-pager -l    # 三件套：Loaded / Active / Main PID
journalctl -u gameserver -b --no-pager | tail -30
systemctl show gameserver -p Result -p NRestarts -p ExecMainStatus
```

```text
Aug 30 21:04:12 login-1 gameserver[2341]: panic: runtime error: ...   ← 应用自己炸
Aug 30 21:04:12 login-1 systemd[1]: gameserver.service: Main process exited, code=exited, status=2
```

读法：`status=2` 是退出码非 0；`signal=` 则是被信号杀（配合 dmesg 看是不是 OOM）；行首有应用 panic/堆栈 → 应用层问题修应用。systemd 管的服务 stdout/stderr 默认进 journal，**别只翻应用日志文件**。

无限 restart 的下场是 **start-limit-hit**（重启太勤被 systemd 刹车锁死）——先修崩溃原因，再 `systemctl reset-failed` 解锁，只 reset 不治本没用。

> ⚠️ **别混**：**active ≠ 健康**——systemd 只确认主进程活着，不确认业务能服务玩家。active 但玩家进不去，主机刀扫一轮没异常就转网刀 [02](../02-网络排查命令/) 或应用探活。

### 再追问

- **Active 有哪几种值，各下一刀是什么？**——active running（转性能刀）/ failed（journalctl）/ activating 卡住（查 Type= 和依赖 → [11](../11-Systemd与服务管理/)）/ inactive（是不是被停了、没 enable）。
- **journalctl 日志巨多怎么掐？**——`--since "20 min ago"` 先掐时间窗，`-p err..alert` 只看错误级；`-k` 是内核日志、`-b` 是本次开机。

## Q12

**★★★☆☆｜什么时候可以上 strace？有什么使用纪律？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、追凶·服务：systemctl / journalctl / strace](知识点.md)

### 场景

接口慢，有人直接 `strace -fp 2341` 挂上主进程想「看看到底卡哪」——机器肉眼可见地更卡了。

### 完整解答

> 🎯 **一句话**：strace 是放大镜不是望远镜——缩到单 PID 之后短挂 15~20 秒，必带 timeout。

```bash
timeout 20 strace -p 2341 -T -ttt 2>&1 | tail -100     # 短挂；-T 每次调用耗时
timeout 15 strace -p 2341 -c                              # 统计模式，最安全
timeout 20 strace -p 2341 -e trace=network,file,desc -T   # 收窄范围
```

```text
21:08:01.123500 futex(0x7f.., FUTEX_WAIT, ...) = -1 ETIMEDOUT <2.000001>
# ← 大量 futex WAIT 不前进 = 等锁
```

认四类就够：**等锁**（futex WAIT 一片）→ 锁竞争；**等 IO**（read/fsync 耗时长）→ [08](../08-磁盘与IO/)；**等网**（recvfrom 长时间不返回）→ [02](../02-网络排查命令/)；**找文件**（ENOENT/EACCES）→ 常比性能问题简单。

纪律：① **必带 timeout**（15~20s 封顶）；② 默认别 `-f` 全挂所有线程（输出爆炸）；③ `-c` 统计模式最安全；④ 不当首刀、更不能长期挂着当监控。它天然拖慢目标进程的原因是底层 **ptrace** 机制——被跟踪进程在每个系统调用处都要停一下。

> ⚠️ **别混**：望远镜（uptime/vmstat 30 秒套餐）负责「往哪看」，放大镜（strace）负责「看清这一处」——顺序永远是先望远镜后放大镜，一上来 `-fp` 挂大进程就是拿放大镜当望远镜使。

### 再追问

- **进程在、CPU 不高、就是「卡住」，你还有什么招？**——先 `ps` 看 STAT 和 `wchan`（是不是 D 状态卡在内核等待点），再决定要不要 strace 短挂确认；一步到位比乱挂强。
- **strace 看不到用户态热点怎么办？**——它只看系统调用边界，函数级热点要用 profiler（perf 等），别拿 strace 硬扛。

## Q13

**★★★★☆｜把高 Load、OOM 迹象、盘满、服务 down 四条定责树口述一遍，哪条线该停主机刀？**

**覆盖**：核心 · 常考 ｜ **对应**：知识点 [八、作战：定责与交接](知识点.md)

### 场景

面试官说「不用细讲命令，我要听你的处置框架」——考的是能不能 60 秒讲清「先做/别做/转哪」。

### 完整解答

> 🎯 **一句话**：四条树都是「先定域贴证，再甩机制章」；四线全平但像网络，就停主机刀。

- **高 Load**：先 vmstat 分型再动——`r>核 us/sy↑` 是 CPU 型（mpstat -P ALL，单核热点拆线程 → 06）；`b↑ wa↑` 是 IO 型（iostat → iotop → 08），**别加核**；`%soft` 单核满想 RSS（→ 06）；`%st > ~10%` 找云厂商（→ 06）。
- **OOM 迹象**：进程突然没了——`free -h` + `dmesg` 搜 `Killed process` **留证**再重启，别只重启不留证；容器先查 cgroup 限额（→ 10/07）。
- **盘满**：分层 `du -xh --max-depth=1` 找大户；du 对不上 `lsof +L1` 抓 deleted；`df -h` 有空间仍写失败查 `df -i`；多挂载点看准 `Mounted on` 别清错分区（→ 09/08）。
- **服务 down**：`systemctl status` 三件套 → `journalctl -u` 看退出原因（panic / status=N / signal=）→ 修因再 reset-failed，别无限 restart（→ 11）。

**停主机刀的线**：四线全平（Load 正常、内存正常、盘正常、服务 active）但现象像网络——连接异常、跨机不通——立即转 [02](../02-网络排查命令/) / 抓包 [16](../16-网络排障与抓包/)，别在 top 里耗死。收工口径：定型 + 一句话定域 + 证据片段（uptime/vmstat/对应线的关键输出）甩机制章，**本章只负责定域，不负责根因**。

> 📝 **面试**：60 秒版按「四条树各一句先做一句别做，加一句停刀条件」讲；面试官最想听的是「别做」——IO 型加核、OOM 不留证、服务挂无限 restart，三个坑避雷就赢了。

### 再追问

- **交接工单里贴什么？**——最小证据包：时间、uptime/lscpu、vmstat（注明已丢第一行）、按型的补刀输出、systemctl/df 片段、一句话定域（例「IO 型，nvme0n1 await~180、%util 98，mysqld 写 80MB/s」）。
- **active 但玩家进不去算哪条树？**——不在这四条里：主机刀扫一轮没异常就转网刀或应用探活（[21](../21-性能方法论-USE与RED/) · [22](../22-监控与告警/)），看到 active 就结案是这题的坑。

## Q14

**★★★★★｜白板：主机排查一生 + 60 秒五步 + 四条树各一句「先做/别做」？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图](知识点.md) · [八、作战](知识点.md) · [九、收口](知识点.md)

### 场景

白板综合 90 秒：「从告警进机到甩机制章，完整框架。」

### 完整解答

> 🎯 **一句话**：**接警拿尺 → vmstat 分型 → 四线追凶 → 证据收工**；四线全平转网络；定域≠定根因。

```text
① uptime/lscpu  ② vmstat 1 3  ③ 按型补刀  ④ 一句话+片段甩章
CPU: mpstat/top -H → 06
内存: free+dmesg → 07
盘: iostat/df/du/lsof → 08/09
服务: systemctl/journal → 11
```

翻车：IO 型加核、OOM 不留证、failed 无限 restart、active 当健康。

> 📝 **面试**：strace 是放大镜不是望远镜（Q12）。

### 再追问

- D 和 Z 各治谁？——D 解 IO/NFS；Z 治不 wait 的父进程（Q10）。
