## Q1 文件 777 还是 Permission denied

**★★★★★｜「我把文件都 chmod 777 了，程序还是报 Permission denied，这服务器有鬼吧？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、长相：三组九位怎么读](知识点.md) · [八、结案：排查链、find 审计与 root 特权](知识点.md)

### 场景

游戏服报 `open("/data/game/server.log"): Permission denied`。值班同事已经把 `server.log` 本身 chmod 777 了，报错纹丝不动，现在他准备 `chmod -R 777 /data`。

### 完整解答

> 🎯 **一句话**：挡路的多半是路径上某级**父目录的 x 位**——文件 777 根本没被判定到。

第一反应：别再 chmod，先把整条路径每一级的权限摆出来。

```bash
namei -l /data/game/server.log
```

```text
f: /data/game/server.log
dr-xr-xr-x root root  /
drwxr-x--- root game  /data          # ← 病在这：其他人段没有 x
drwxrwxr-x game game  /data/game
-rwxrwxrwx game game  server.log     # ← 777 白给：根本走不到这一格
```

深挖：内核 open 一个文件要先**逐级穿过**每个父目录（每级都查 x 位），最后才判目标文件的九个位。`/data` 是 `drwxr-x---`，进程身份落在「其他人」段，没有 x，路在倒数第二级就断了。修法是最小改动：

```bash
# 进程是 game 组成员 → 让属组段能过（比 777 小得多）
chmod g+x /data
# 或者进程身份确实该换 → chown 归位（root 执行）
chown root:game /data && chmod 2775 /data   # ← 顺手 SGID，新文件继承 game 组
sudo -u game cat /data/game/server.log      # ← 以报障身份重放验证
```

结案：如果当时 `chmod -R 777 /data` 真敲下去了，等于让全机任何账号可删可换这个目录里的东西——按事故处理，记变更并回滚。

> ⚠️ **别混**：目录的 x 是「走廊通行权」，不是「列名单」（那是 r）；父目录没 x 时文件位再大也到不了。

> 📝 **面试**：口径就是一句「先 namei -l 看每一级，777 治不了父目录的病」。

### 再追问

- 目录只给 r 不给 x 会怎样？——`ls` 能看到文件名，但 stat 不到大小权限、进不去任何文件，输出一排问号；r 和 x 常要成对给。
- 为什么 root 不受这个限制？——uid 0 在内核判定里短路放行（CAP_DAC_OVERRIDE），九个位对它形同虚设；root 也被拒就去查只读文件系统（→ [09](../09-文件系统与inode/)）。

## Q2 为什么能删别人的文件

**★★★★★｜「文件是同事的、权限 600，我怎么 rm 掉了？反过来我 777 的文件怎么被他删了？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、长相：三组九位怎么读](知识点.md)

### 场景

发版机上 ops 删了 deploy 用户 `rw-------` 的旧包，事后复盘有人觉得「这机器权限坏了」。同一晚，ops 自己 777 的临时文件被清理脚本顺走了。

### 完整解答

> 🎯 **一句话**：删文件判定的不是文件自己的位，是**父目录的 w+x**——文件位在删除这件事上不参与。

第一反应：把「删」翻译成内核动作——`rm` 是从父目录的目录项表里摘掉一条名字，改的是**父目录**，所以判定也发生在父目录的 w+x。

```bash
ls -ld /data/release
# drwxrwxrwx 2 root root 4096 /data/release   ← 任何人 w+x：谁都能删里面任何文件
touch /data/release/deploy.test && rm /data/release/deploy.test   # ← 能删，与文件位无关
```

深挖：两个现象是同一条规则的正反面——

```text
能删别人的 600 文件   ← 父目录给了你 w+x
删不动自己的 777 文件 ← 父目录没给你 w+x（或你没过 x 这关）
```

值班启示：**「删不掉」和「读不到」要分开查**——删不掉看父目录 w+x，读不到查整条路径的 x 和文件的 r。想让共享目录「人人能交、没人能撕别人的」，给目录加 Sticky（1777，/tmp 的做法）。

> ⚠️ **别混**：目录 w ≠ 能改文件内容——w 只管目录项（删/建/改名）；改内容要文件自身的 w。「我能删他的文件」和「我能改他的文件」是两个判定。

> 📝 **面试**：「为什么我能删同事 777 的文件」——rm 改的是父目录的目录项，判定在父目录 w+x；这条几乎是必考，答完主动补 Sticky 就是加分。

### 再追问

- 那怎么让 /tmp 人人可写又不互删？——Sticky 位（1777）：w 保留「建」的权利，删只允许属主和 root。
- 改名（mv）和删除是一回事吗？——同一回事：mv 本质是在目录项表里改名字，判定的还是父目录的 w+x。

## Q3 /etc/passwd 七字段与 UID 0

**★★★★☆｜「/etc/passwd 一行七个字段各是什么？UID 0 特殊在哪？」**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出身：UID、GID 与三本账](知识点.md)

### 场景

入职安全检查要你盘点一台老机器的账号。有人指着 `game-serv:x:998:998::/opt/game:/sbin/nologin` 问：这账号 shell 都没有，是不是废号可以直接删？

### 完整解答

> 🎯 **一句话**：七字段「用户名:密码占位:UID:GID:备注:家目录:shell」；内核只认数字，UID 0 就是 root。

```text
game-serv : x : 998 : 998 : (GECOS备注) : /opt/game : /sbin/nologin
用户名      密码占位  UID   主组GID      备注        家目录       登录shell
```

- x 是占位符，真密码哈希在 /etc/shadow（root 才能读）。
- **UID 0 = root**：内核判定 root 身份看数字 0，不看名字——把普通账号 UID 改成 0 就是第二个 root。
- `/sbin/nologin` **不是废号**：它只拒绝交互登录，账号照样能跑服务、持有文件、被 su（会提示 This account is currently not available）。盘点口径：

```bash
grep :0: /etc/passwd
# root:x:0:0:root:/root:/bin/bash     ← 正常只有一个；多出来的按后门处理
ps -o user,uid,gid,cmd -p $(pgrep -f game-server | head -1)
# game-serv 998 998 /opt/game/bin/server   # ← nologin 账号正在跑服务：不能删
```

> ⚠️ **别混**：「不能登录」（nologin）和「不能用」（账号禁用）是两回事；禁用账号是锁 shadow 或设过期，不是改 shell 了事。

> 📝 **面试**：七字段按顺序背；UID 0 与名字无关；附加组在 /etc/group，判定属组段时进程的整串 gid 列表任何命中都算。

### 再追问

- 进程的组身份哪来的？——登录/su/sudo 时确定的一串 gid 列表（主组在前 + 附加组），fork 继承；把人加进组后**服务要重启**才吃到新身份（进程身份 → [05](../05-进程与信号/)）。
- 服务进程的有效身份怎么看？——`ps -o uid,euid`；SUID 程序会让 euid 与 ruid 分家（Q6）。

## Q4 chmod 数字法、符号法与大写 X

**★★★★☆｜「chmod 754 是什么意思？我要递归放开一个目录，怎么写不把日志变成可执行？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [四、易容：chmod 与 chown](知识点.md)

### 场景

发版脚本里写着 `chmod -R u+x /data/game`，跑完运维发现自己把 4000 个 .log/.conf 全变成了可执行，安全扫描当晚告警。

### 完整解答

> 🎯 **一句话**：数字法一次写全（r=4 w=2 x=1 按段相加），递归加 x 用大写 **X**——只给目录和本就可执行的文件加。

```text
rwxr-xr--  →  7 5 4
7 = 4+2+1 (rwx)   5 = 4+1 (r-x)   4 = 4 (r--)
chmod 754 file  →  属主 rwx · 属组 r-x · 其他 r--
```

递归的正确写法：

```bash
chmod -R u=rwX,g=rX,o= /data/game
# ← 大写 X：目录和已有 x 的文件加 x，普通文件只拿 rw —— 日志配置不再变可执行
# ← o= 把其他人清空：比「-R 777」小一个量级的最小授权
stat -c '%a %n' /data/game /data/game/server.log
# 2770 /data/game
# 660 /data/game/server.log       # ← 验收：目录可进、日志不可执行
```

符号法做增量（不动别的位）：`chmod g+w share.log` 只给属组加写；`chmod o-rwx key` 收掉其他人的位。

> ⚠️ **别混**：chmod 改「能怎么用」，chown 改「是谁的」；x 和 X 是两个东西——小写 x 无差别加，大写 X 有条件加，递归场景永远用 X。

> 📝 **面试**：r=4 w=2 x=1 的来历是二进制位掩码（r=100、w=010、x=001）；755/644/700/600 四个组合的场景能随口报出。

### 再追问

- `chmod -R 777` 到底错在哪？——它让全机任何账号可写目录项（可删可换），被打穿的低权限账号就能往里放 SUID 后门（Q6/Q10）；正确做法是 namei 定位后补最小段。
- chown 什么身份才能执行？——改属主只有 root；chgrp 可以是属主本人（且属于目标组）。

## Q5 umask 算术与「服务建出来 600」

**★★★★★｜「umask 022 的时候新建文件、新目录各是什么权限？为什么我手动 touch 是 644、服务写出来却是 600？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、出厂设置：umask 怎么定新文件权限](知识点.md)

### 场景

共享目录里，同事手动建的文件是 664 互相能改，CI 发版服务写出来的却是 600，下一个人编译就 Permission denied。有人怀疑服务代码里「偷偷 chmod 了」。

### 完整解答

> 🎯 **一句话**：新文件权限 = 模板减 umask（文件 0666、目录 0777）——两边进程 umask 不同，落盘的位就不同。

先答算术，主动写出与式：

```text
文件：0666 & ~umask     目录：0777 & ~umask
umask 0022 →  文件 644 (rw-r--r--)   目录 755
umask 0002 →  文件 664 (rw-rw-r--)   目录 775
umask 0077 →  文件 600 (rw-------)   目录 700
```

深挖现场：手动 shell 是 0022/0002，systemd 服务看 unit 的 `UMask=`，CI 跑在 gitlab-runner 之类的服务里，umask 是**进程属性**：

```bash
grep -i UMask /etc/systemd/system/ci-runner.service
# UMask=0077                      # ← 病根：服务进程被要求 0077，建出来全是 600
sudo -u ci-runner sh -c 'umask; touch /tmp/probe && stat -c %a /tmp/probe'
# 0077
# 600                             # ← 以服务身份重放，对上账
```

修法：unit 里改 `UMask=0002`（或去掉），`systemctl daemon-reload && systemctl restart ci-runner`（→ [11](../11-Systemd与服务管理/)）。umask **只影响新建**，已落盘的 600 要 chmod 补。

> ⚠️ **别混**：umask 是「摘除」不是「赋予」——文件永远不可能因 umask 天生带 x（模板 0666 本就无 x）；目录有 x 是因为模板 0777。

> 📝 **面试**：「umask 022 新文件/新目录权限」答 644/755 并写出 `0666 & ~0022`；追问「为什么新文件不可执行」——掩码只减不加。

### 再追问

- 为什么改完 umask 老文件没变？——umask 只在 create 那一刻参与计算，存量文件要 chmod。
- root 和普通用户的 umask 一样吗？——默认都是 0022，但启用用户私有组（UPG）的环境普通用户常是 0002（同组可写）；「同事改不了我的文件」先各查 umask。

## Q6 passwd 凭什么写 shadow

**★★★★★｜「/etc/shadow 是 root 才能写的，普通用户改密码怎么做到的？我自己写个程序加 SUID 行不行？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、特权：SUID、SGID 与 Sticky](知识点.md)

### 场景

新人问：既然权限位说了 shadow 只有 root 能写，那每个用户自助改密码是不是后台有个 root 守护进程代写？有人说不是，是 passwd 自己「有特权」。

### 完整解答

> 🎯 **一句话**：passwd 带着 SUID（4755）——任何人执行它的那一瞬间，进程的**有效身份**变成属主 root。

```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x. 1 root root 28K ... /usr/bin/passwd   # ← 属主段 x 位是 s：SUID 签名
```

机制（能上白板的图）：

```text
用户 ops（ruid=1002, euid=1002）
   └─ exec /usr/bin/passwd（属主 root · SUID）
        进程变成 ruid=1002, euid=0      ← 只有 euid 分家，真实身份不变、日志仍记 ops
        以 euid=0 写 /etc/shadow        ← 只在这一单有效
   进程退出 → 特权收回
```

判定用的是 euid（effective UID，有效身份）——SUID 之外正常进程 euid=ruid，`ps -o uid,euid` 可以当场验证。

追问「自己加 SUID 行不行」：技术上行、工程上是发后门——SUID 程序里起一个 shell，任何低权限账号执行它就拿到 root；所以基线要求无关 SUID 一律摘位（`chmod u-s`）、数据盘 `nosuid` 挂载（→ [27](../27-Linux安全加固/)）。

> ⚠️ **别混**：小写 s = 该段同时有 x、位生效；大写 S = 位设了但 x 没设，白设（`-rwSr-xr-x` 的 SUID 不生效）。SUID 只认二进制可执行文件——脚本上的 SUID 基本被现代系统忽略，放目录上无意义。

> 📝 **面试**：「passwd 为什么是 rws」答 SUID + euid 机制；再补一句「SUID 是程序自带的钥匙，sudo 是登记过的代办」就齐了（Q8）。

### 再追问

- 为什么不干脆给 shadow 加个组写？——那等于把 root 密码库对一组人敞开，粒度完全失控；SUID 把「能写 shadow」收缩到「能跑这一个程序」。
- 怎么盘点全机有哪些 SUID？——`find / -xdev -type f -perm /4000`，对基线（Q10）。

## Q7 共享目录与 SGID、/tmp 与 Sticky

**★★★★☆｜「多人往一个目录发版，怎么让新文件自动属于同一个组？/tmp 为什么是 1777？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、特权：SUID、SGID 与 Sticky](知识点.md)

### 场景

deploy 组三人共用 /data/release，每人的新文件属组是各自的主组，别人编译时读不了。有人提议「建个 crontab 每 5 分钟 chmod -R 一遍」。

### 完整解答

> 🎯 **一句话**：共享目录三件套 = **SGID（2775）+ 属组可写 + 合适 umask**——新文件自动继承目录的组，不用人肉追着 chmod。

```bash
mkdir /data/release && chgrp deploy /data/release && chmod 2775 /data/release
#                          2 = SGID ↑
touch /data/release/v1.2.5.tar && ls -l /data/release/
# -rw-rw-r--. 1 ops deploy 0 v1.2.5.tar
#                    ↑ 建文件的 ops 主组是 ops，落盘属组却是 deploy
```

`ls -ld` 里属组段的 x 位显示成 `s`（rwxrwsr-x）就是 SGID 目录的签名。crontab 补 chmod 的方案别上——它在治存量，SGID 在治源头，而且 cron 还有自己的 umask 环境问题（→ [30](../30-定时任务与Cron/)）。

/tmp 一并答：`drwxrwxrwt` = **1777**——人人可写，但 Sticky 保证**只有文件属主和 root 能删**；w 位只保留「建」的权利。没有它，/tmp 里任何人的临时文件任何人都能清掉。

> ⚠️ **别混**：SGID 文件与 SGID 目录是两件事——前者让**执行进程**的组身份变成文件属组，后者让**新建文件**继承目录属组。运维日常说的是后者。

> 📝 **面试**：数字 4/2/1 顶在权限最前：SUID=4（passwd 4755）、SGID=2（共享目录 2775）、Sticky=1（/tmp 1777）；两个 s 一个 t 的签名能当场认出。

### 再追问

- 组员之间还是互相写不了怎么办？——查两处：属组段有没有 w（2775 的 g=rwx）；建文件那方的 umask 是不是把组 w 摘了（0022 会摘——UPG 环境 0002 才留）。
- Sticky 位在文件上有用吗？——现代 Linux 上无实义，只在目录上生效。

## Q8 su vs sudo 与最小授权

**★★★★★｜「su 和 sudo 有什么区别？发版机要给一个只能重启服务的账号授权，怎么写 sudoers？」**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [七、代办：sudo 与 sudoers](知识点.md)

### 场景

主管要求：发版机只许 deploy 账号免密重启 game-server 一个服务，别的什么都不给。有人图快写了 `deploy ALL=(ALL) NOPASSWD: ALL` 准备交差。

### 完整解答

> 🎯 **一句话**：su 要目标用户的密码、切整个会话、没有逐条审计；sudo 用自己的密码、授权到单条命令、每条进日志——`ALL` 等于发 root，不给。

su vs sudo 三点（必背）：**密码归属**（su 问 root 密码 vs sudo 问你自己的）、**粒度**（会话级 vs 命令级）、**审计**（su 只知道谁变成了谁 vs sudo 逐条记录「谁以谁的身份跑了什么」）。发版机的正确写法：

```text
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart game-server
```

四个字段读法：`谁(host)=(以谁的身份) 能跑哪些命令`——NOPASSWD 只罩住这一条命令，别的 sudo 仍要密码。落地三步：

```bash
visudo -f /etc/sudoers.d/deploy      # ← 用 visudo 编辑 drop-in 文件（权限 440）
visudo -c                            # ← 全量语法校验
sudo -l -U deploy                    # ← 验证 deploy 到底拿到了什么
# User deploy may run the following commands:
#     (root) NOPASSWD: /usr/bin/systemctl restart game-server
```

> ⚠️ **别混**：sudoers 直接用 vi 改——写错一个字符全机 sudo 瘫痪，必须 visudo（保存时语法检查）；`su -` 的 `-` 要带上（login shell 重置环境），不带会带着旧 PATH 切过去，制造「root 下正常、su 下不正常」。

> 📝 **面试**：三点区别 + 「授权到命令级、NOPASSWD 只给脚本的最小命令集」+ visudo，这套口径就是满分。

### 再追问

- sudo 的日志在哪看？——RHEL 系 `/var/log/secure`、Debian 系 `/var/log/auth.log`，出事故回放逐条有记录。
- 免密缓存多久？——默认约 15 分钟（`timestamp_timeout`），同一终端连续 sudo 只问一次密码。

## Q9 sudo 重定向失败与 sudo cd

**★★★★☆｜「sudo echo xxx > /root/f 为什么还是 Permission denied？sudo cd 为什么说找不到命令？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、代办：sudo 与 sudoers](知识点.md)

### 场景

排障要往 /root/blacklist.conf 追加一行，值班敲 `sudo echo 'blacklist nouveau' > /root/blacklist.conf` 弹了 Permission denied；换个思路 `sudo cd /root` 又报 command not found。两连击之后他准备 sudo -i 常驻 root。

### 完整解答

> 🎯 **一句话**：sudo 只提权它后面那个**程序**——重定向是当前 shell 干的、cd 是 shell 内建的，都不归 sudo 管。

```bash
sudo echo 'blacklist nouveau' > /root/blacklist.conf
# -bash: /root/blacklist.conf: Permission denied
# ← sudo 提权了 echo（root 身份的 echo，输出到stdout 没问题）
#   但 > 是「你的 shell」以你的身份打开文件 → 拒绝
echo 'blacklist nouveau' | sudo tee -a /root/blacklist.conf
# ← 正解：让 root 身份的 tee 来写文件；-a 追加

sudo cd /root
# sudo: cd: command not found
# ← cd 是 shell 内建命令，磁盘上没有这个程序，sudo 无从提权
sudo -u root ls /root    # ← 真要「以 root 看目录」，用具体命令
sudo -i                  # ← 确实需要完整会话时才用，用完即退
```

深挖：「常驻 sudo -i 干活」不是好习惯——审计日志只剩一条「某人变成了 root」，之后干了什么全靠自觉；正确姿势是每条命令单独 sudo，让日志逐条可回放。

> ⚠️ **别混**：`sudo cmd > file` 失败时，是 **shell** 没权限开 file，不是 sudo 没生效；把 file 松到 777 去「修复」是双重错误（文件位和命令语义都搞错了）。

> 📝 **面试**：这两个翻车点是 sudo 的高频追问；答完补一句「sudo 提权的单位是磁盘上的程序，重定向和内建命令都不在它的辖区」，理解就到位了。

### 再追问

- 管道左边 sudo、右边普通命令呢？——`sudo cat /root/f | grep x`：cat 是 root 身份，grep 是你的身份，只是处理文本，通常没问题；但 `sudo cat /root/f > /tmp/out` 又是 shell 开文件，要看 /tmp 权限。
- 想授权「只能看某日志」怎么写？——`ops ALL=(root) /usr/bin/tail -f /var/log/game/server.log`，命令带参数写进白名单，参数不对的调用照样拒。

## Q10 SUID 后门审计

**★★★★☆｜「安全通报一台机器被放了 SUID 后门，你怎么把全盘的 SUID 文件找出来？-perm 后面的 / 和 - 是什么区别？」**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [八、结案：排查链、find 审计与 root 特权](知识点.md)

### 场景

安全组通报：某台混部了 Web 业务的机器被植入了一个属主 root 的 SUID shell，低权限 www-data 拿它提权。要求你半小时内给出全量 SUID 清单和差异。

### 完整解答

> 🎯 **一句话**：`find / -xdev -type f -perm /4000` 一条命令列出全盘 SUID，和基线快照对比找新增。

```bash
find / -xdev -type f -perm /4000 -ls 2>/dev/null
# 33554994 16 -rwsr-xr-x 1 root root 14328 ... /usr/bin/passwd
# 33555012 16 -rwsr-xr-x 1 root root 14328 ... /usr/bin/su
# 50331657 32 -rwsr-xr-x 1 root root 34568 ... /tmp/.cache/upd   ← 基线里没有的：后门
```

参数逐个说清：`-xdev` 不跨文件系统（快而稳，/proc、挂载的数据盘不混进来）；`-perm /4000` = **模式里任意一位命中**就匹配（SUID 位立着）。

三种写法一句话区分：`/mode` 任一命中、`-mode` 全部包含、裸 `mode` 精确等于。审计用 `/`，查「包含危险位」用 `-`（如 `-0002` 找 world-writable 目录）；裸 `4000` 只匹配「恰好 4000、其他位全空」，基本空手而归——最常犯的错。

处置：新增的 SUID 文件**先摘位再取证**：`chmod u-s /tmp/.cache/upd` 让它立即失效，文件本身留证据，植入路径和关联进程移交安全（→ [27](../27-Linux安全加固/)）。

> ⚠️ **别混**：`-perm /4000` 找的是「SUID 位在」，不代表它就是后门——正常系统本来就有几十个；**判定靠对基线的 diff**，不是看到 s 就紧张。

> 📝 **面试**：「怎么审计 SUID」答 find 命令 + 基线对比；追问三种 -perm 写法能立刻报出语义差异。

### 再追问

- 顺带把危险目录也扫一遍？——`find / -xdev -type d -perm -0002` 列所有 world-writable 目录（含 /tmp 这类合法的和不该松的）。
- 长效防什么？——数据盘 `nosuid` 挂载、定期快照对基线、清理不需要的 SUID（→ [27](../27-Linux安全加固/)）。

## Q11 换用户跑服务后的 Permission denied

**★★★★☆｜「把服务从 root 迁到 game 用户跑之后，写日志报 Permission denied——完整排查一遍给我看。」**

**覆盖**：核心 · 常用 ｜ **对应**：知识点 [八、结案：排查链、find 审计与 root 特权](知识点.md)

### 场景

安全整改把 game-server 从 root 迁到 game 用户（unit 里 `User=game`），重启后服务起不来，日志一行 `open("/data/game/server.log"): Permission denied`。有人开始怀疑「迁移白做了」。

### 完整解答

> 🎯 **一句话**：四步链走一遍——身份 → 路径 x → 目标位 → 特权——这条链 30 秒内能定位 90% 的迁移后拒绝。

```bash
# ① 你是谁：进程身份真的是 game 吗
ps -o user,uid,gid,cmd -p $(pgrep -f game-server)
# game 1002 1000 /opt/game/bin/server     # ← 注意 gid=1000：主组没跟上，属组段可能判不中
# ② 路过哪：整条路径逐级
namei -l /data/game/server.log
# drwxr-x--- root game /data/game         # ← game 组成员才有过路权
# -rw-r----- root game server.log         # ← 属主属组都还是 root:game
# ③ 目标位：属组 r，能不能「写」？
#    game 组只有 r 没有 w → 写拒绝，病根在这
# ④ 该不该特权：不该——这就是归属问题，走 chown 而不是 sudo
```

深挖与修复：迁移改的是**进程身份**，但文件世界里留下的是 root 时代的一大堆归属。修法按最小化：

```bash
chown -R game:game /data/game             # ← 存量归属归位（root 执行，记变更单）
chmod -R u=rwX,g=rX,o= /data/game         # ← 大写 X 只给目录/程序加执行位
sudo -u game touch /data/game/probe       # ← 以新身份重放，通了才算修完
systemctl restart game-server && journalctl -u game-server -n 20
```

结案别忘两件事：`find /data/game -perm /4000` 确认没把 root 时代的 SUID 程序留给 game；unit 里顺手检查 `UMask=`（→ [11](../11-Systemd与服务管理/)），别让新文件落盘就是 600（Q5）。

> ⚠️ **别混**：四步的**顺序不能反**——先看身份再看路径最后看位；上来就 ls 文件位，看到 `-rw-r-----` 对着九宫格猜半天，是因为跳过了前两步。

> 📝 **面试**：背口径「一 id、二 namei、三 ls、四 sudo」；这条链本身就是「排查 Permission denied」的标准答案。

### 再追问

- 修完通了，但过几天新日志又写不了？——查 umask：game 的 shell 是 0022，新建文件 644 组员写不了；共享写场景配 0002 或 SGID 目录。
- root 时代遗留的 capability 程序怎么办？——迁移后服务不再有 root 特权，依赖 CAP_* 的老二进制会静默降级，回归测试要覆盖（→ [10](../10-cgroup与容器/)）。

## Q12 接到权限报障的第一分钟

**★★★☆☆｜「值班第一分钟，权限类报障你按什么顺序敲命令？」**

**覆盖**：必会 ｜ **对应**：知识点 [九、作战：60 秒定责](知识点.md)

### 场景

交接班第一天，工单系统弹进来一条：「游戏服更新后报 Permission denied」。你还没登录机器，问你第一分钟干什么。

### 完整解答

> 🎯 **一句话**：先定现象分型（读不进/删不掉/sudo 拒/root 拒），再按四步链敲命令，每一步都为下一步缩小范围。

```text
① 0–10s   定分型 + 身份：报错原文是哪一种？ps -o uid,gid 看进程身份
② 10–30s  namei -l <完整路径>：逐级找挡路的目录（x 位、属组）
③ 30–45s  对症最小修：目录补 x · chown 归位 · sudoers 加一条 · SGID 共享目录
④ 45–60s  验证 + 结案：sudo -u <user> 重放一次；记变更单；find -perm /4000 对基线
```

分型速查（能背下来的程度）：

```text
读/进不去        → namei -l 逐级看 x
删不掉/建不了    → ls -ld 父目录看 w+x
sudo not allowed → sudo -l + visudo 补最小一条
777 还不行       → 停止 chmod：父目录 x / SELinux（→ 27）
root 也被拒      → 只读 FS（→ 09）/ chattr（→ 27）
通报 SUID        → find -perm /4000 对基线
```

底线一条：**60 秒剧本里没有任何一步是 `chmod -R 777`**——最小改动 + 可回滚 + 结案审计，才是值班动作。

> 📝 **面试**：这题考的是「有没有形成肌肉记忆」；答出分型 + 四步 + 验证重放，并主动说出「每步都在为下一步缩小范围」，就和背题的人区分开了。

### 再追问

- 修完怎么确认没引入新问题？——以报障身份重放原操作（`sudo -u <user> cat <file>`）+ `find -perm /4000`、`find -perm -0002` 快照对基线。
- 报障里只有「更新后」三个字，还要查什么？——变更单：更新包可能带了权限覆盖（tar 解包覆盖归属/位）或改了运行用户（Q11）。

## Q13

**★★★★☆｜777 还不行、root 也被拒——什么时候转出本章？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [八、结案：排查链](知识点.md) · 交叉 [27](../27-Linux安全加固/) · [09](../09-文件系统与inode/)

### 场景

共享目录已 chmod 777，应用仍 Permission denied。有人要继续 chmod -R。

### 完整解答

> 🎯 **一句话**：**namei 仍挡路 → 父目录 x；777 仍不行 → SELinux / 只读 FS / ACL**，本章 chmod 到此停刀。

| 分型 | 转出 |
|------|------|
| `namei` 某级无 x | 本章补目录权限 |
| `ls -Z` 有 context | SELinux → 27 |
| `mount` ro | 只读 FS → 09 |
| `getfacl` 有额外 ACE | ACL 专项 |

```bash
namei -l /data/game/log/app.log
ls -ldZ /data/game/log
mount | grep /data
```

### 再追问

- 为什么禁止 -R 777？——掩盖真实缺权，审计无法收敛（Q12）。

## Q14

**★★★★★｜白板：Permission denied 一生 + 60 秒剧本 + SUID/SGID/Sticky 各一例？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图](知识点.md) · [十、收口](知识点.md)

### 场景

白板综合：「画 denied 主图，举 SUID passwd、SGID 共享目录、/tmp sticky 各一个场景。」
