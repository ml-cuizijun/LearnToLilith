## Q1：Load 很高、CPU 很低，你怎么查？

**★★★★★**

**场景**  
活动中 8 核机 Load=40，`top` 里 `%id` 还有 80%。群里有人要加 CPU。

**完整解答**

Load 数的是 **R + D**，不是 CPU%。CPU 闲而 Load 高，先找不可中断睡眠：

```
  Load 高、CPU 闲
       |
       +-- vmstat：b / wa 高  --> IO 排队
       +-- iostat：await 高   --> 本地盘 / 云盘
       +-- 本地盘闲、仍 D 多  --> NFS / 远程盘（看 wchan）
       +-- 不要加 CPU
```

1. `vmstat 1 5`（丢掉第一行）看 `b`、`wa`。
2. `iostat -x 1 5` 看 await、aqu-sz；本地盘闲再 `ps -eo pid,stat,wchan:32,cmd | grep D`。
3. 卡 NFS / 远程盘时 iostat 的本地 %util 可以很低，加核没用。

**再追问：D 状态能 kill -9 吗？**  
不能。信号要等回用户态才交付，SIGKILL 只进 pending。先看 wchan，修 IO / NFS。

## Q2：8 核 Load=30，接口超时，完整排查顺序。

**★★★★★**

**场景**  
登录接口大面积超时。监控 Load=30，有人已经准备重启逻辑服。

**完整解答**

先定影响面，再分型，最后才碰进程：

```
  1. 影响面 / 最近变更（发版、限流、扩容）
  2. vmstat：分 CPU 型 vs IO 型
        |
        +-- r 高、us 高 --> top / perf（CPU）
        +-- b 高、wa 高 --> iostat / iotop（IO）
  3. 止血：回滚 / 限流 / 扩容
  4. 留证据：日志、sar、变更单
```

1. 8 核满载大约 Load≈8；Load=30 是在排队或卡 IO，当故障，不是「还能再扛」。
2. CPU 型再 `top` / `perf`；IO 型看 await，不要一上来火焰图。
3. 游戏逻辑服先摘流量或回滚，不要无证据重启（内存态会丢）。

**再追问：wa 高但 iostat %util 低？**  
远程盘 / NFS / 云盘 QoS。本地 %util 看不见对面，看 wchan 和云监控 IOPS。

## Q3：从 CPU 高到具体代码怎么走？

**★★★★★**

**场景**  
整机 CPU 看起来高，要你指到函数。有人直接 `perf` 十分钟。

**完整解答**

先排除单核和 IO，再下钻线程，最后才对代码：

```
  mpstat -P ALL     是不是单核 100%、其余闲？
        |
        v
  进程 top  -->  top -H 线程
        |
        +-- Java：TID 转 hex，对 jstack
        +-- Go / C：perf record -g -p PID
```

1. `mpstat -P ALL`：单核打满扩核没用，要拆热点或绑核。
2. `top` 找进程，`top -H` 找线程。
3. Java：`printf '%x\n' $TID`，去 jstack 里找 nid。
4. 先 `vmstat` 排除 wa/b，IO 型做 On-CPU 火焰图是浪费窗口。

**再追问：平均 CPU 不高，P99 却炸，还要这条链吗？**  
要。先 mpstat / cgroup throttle，再决定要不要下钻代码。平均利用率不能结案。

## Q4：free 的 available 和 free 列哪个判断内存够不够？

**★★★★★**

**场景**  
`free` 里 used 占 80%，free 列只剩几百 M。有人要 `drop_caches`。

**完整解答**

**看 available，不看 free 列。**

```
  物理内存
    +-- 进程 RSS（真正占用）
    +-- Cache / Buffer（内核缓存，压力下可回收）
    +-- free 列（长期很小往往正常）

  决策：available 估算「还能给新进程的」
```

1. used 高经常只是 cache；available 还充裕就不是缺内存。
2. `drop_caches` 不是运维手段，会制造读风暴；脏页也 drop 不掉。
3. 脏页极多时 available 会偏乐观，交叉看 `Dirty`（Q23）。

**再追问：available 高，进程还是 137 了？**  
可能是 cgroup `memory.max`，不是整机没内存。见 Q6。

## Q5：进程 137 退出怎么查？不要只说加内存。

**★★★★★**

**场景**  
逻辑服突然没了，exit 137。有人说「加内存再观察」。

**完整解答**

137 = 128+9，先当 SIGKILL，再分是谁杀的：

```
  exit 137
     |
     +-- dmesg：整机 OOM Killer
     +-- cgroup memory.events：容器到顶（宿主机可能还有很多）
     +-- 人手 kill -9 / kubelet 强杀
```

1. 整机：`dmesg -T | grep -i oom`。容器：`memory.events` 的 `oom_kill`，节点 dmesg 常常没有经典 OOM 行。
2. 分泄漏斜线 vs 容量台阶：RSS 慢慢爬是泄漏；热更后台阶是预算不够。
3. 游戏热更全量 load 玩家把 RSS 打满，是**发布问题**，可回滚，不是先买内存。

**再追问：OOM 能靠 SIGTERM handler 刷盘吗？**  
不能。OOM Killer 发的就是 SIGKILL，没有优雅退出。靠 limit 余量和探针。

## Q6：容器 OOM，宿主机还有 20G，为什么？

**★★★★★**

**场景**  
Pod OOMKilled、exit 137。节点 `free` 还剩 20G。容器里 `free` 看起来也很大。

**完整解答**

碰到的是 **cgroup `memory.max`**，不需要整机没内存。容器内 `free` 读的是宿主机 `/proc/meminfo`，会撒谎：

```
  宿主机 64G，还剩 20G
       |
       +-- 这个 cgroup memory.max = 2G
              working_set 到顶 --> 杀组内 --> 137
```

1. 核 `memory.max` / `memory.current`，不要信容器里的 `free`。
2. Java：`-Xmx` 等于 limit 几乎必炸（Metaspace、线程栈、DirectByteBuffer、JNI）。经验：**limit ≥ Xmx × 1.3～1.5**，堆外留 **30%+**。
3. 游戏服常见堆外杀手：Netty DirectByteBuffer、JNI 音视频。jmap 只看堆会误判。

**再追问：Xmx 已经小于 limit，还会 OOM 吗？**  
会。堆外没预算、泄漏、或 limit 含了 pause 后的 working_set。看 cgroup 不看堆。

## Q7：D 状态为什么杀不掉？僵尸呢？

**★★★★★**

**场景**  
`kill -9` 一个 D 进程没反应。另一个列表里全是 Z，PID 快耗尽。

**完整解答**

两件不同的事，不要混：

```
  D：人还在内核等 IO（盘 / NFS / writeback）
     信号 pending，回不了用户态 --> kill -9 无效
     看 wchan，修底层 IO

  Z：人已经死了，父进程没 wait
     kill 僵尸 PID 无效（杀尸体）
     杀父或修 wait；init 收养后会收尸
```

1. D 先 `wchan`，不要循环 `-9`。
2. Z 不占 RSS，占 PID；容器里应用当 PID 1 又不处理 SIGCHLD，子进程会变僵尸。
3. PID 耗尽后连登录都 fork 失败，比「多几个 Z」严重。

**再追问：D 会不会自己变成 Z？**  
IO 返回后才回用户态。卡死在 NFS 上可以挂很久，不是僵尸。

## Q8：SIGTERM vs SIGKILL？容器里 docker stop 为何变强杀？

**★★★★★**

**场景**  
`docker stop` 逻辑服，每次都像被一刀砍掉，玩家掉线、状态没刷盘。

**完整解答**

TERM 可捕获做优雅退出；KILL 不能捕获，内核直接拆。

```
  docker stop / kubelet
       |
       v
  SIGTERM（请你收尾） -- grace 内退完 --> 正常
       |
       +-- PID 1 没注册 TERM handler --> 内核丢掉 TERM
       +-- grace 到点 --> SIGKILL
```

1. 应用自己当 PID 1 且不 Listen SIGTERM，TERM 被丢，默认 **10s** 后 KILL。看起来像「停服总是强杀」。
2. 游戏逻辑服：**tini / dumb-init** 转发信号 + **足够 grace**（刷盘、踢人、等补偿）。
3. OOM 也是 KILL，handler 救不了。exit 143 才是 TERM。

**再追问：preStop 和 SIGTERM 谁先？**  
K8s 里两者同时开始。细节回 02 和 K8s 生命周期，本章答到「TERM 先、KILL 是超时第二枪」即可。

## Q9：df 100% 但 du 只有一半？

**★★★★★**

**场景**  
日志盘 `df -h` 100%，`du -sh /var/log` 只有一半。有人 `rm` 了几个 G 的日志，空间没回来。

**完整解答**

文件删了，进程还握着 **deleted fd**。`df` 看文件系统，`du` 看不见已删仍占用的 inode：

```
  rm 大日志
     |
     +-- 进程还 open 着 --> 空间不释放（lsof +L1 / grep deleted）
     +-- 截断 echo > /proc/PID/fd/N  或重启进程
     +-- 只 rm 没用
```

1. `lsof +L1` 或 `lsof | grep deleted` 找 PID。
2. 止血：截断或重启持有者；长期靠 logrotate reopen / copytruncate（Q44）。
3. 加盘不是根因。

**再追问：截断会丢日志吗？**  
会丢当前这块。比盘满死机便宜。能 USR1 reopen 就不要盲截断。

## Q10：iostat：SSD 看 %util 还是 await？

**★★★★★**

**场景**  
SSD `%util` 100%，有人说盘满载要换。接口 P99 其实还好。

**完整解答**

**SSD / 云盘看 await 和 aqu-sz，不要用 %util 定瓶颈。** SSD 可并发，%util 100% 仍可能不是上限。

```
  await 高 + aqu-sz 低  --> 盘/云盘本身慢（介质、QoS）
  await 高 + aqu-sz 高  --> 提交太多，在排队
  HDD %util ≈ 100%     --> 饱和信号
  SSD %util 100%       --> 不一定满，仍看 await
```

1. `iostat -x 1 5`。NVMe 常见 await **小于 1–5ms**；20ms 要查。
2. `svctm` 已不可靠。云盘 burst 耗尽：await 从 2ms 变 50ms。
3. `%wa` 是 CPU 视角；CPU 打满时 wa 可能为 0，磁盘慢必须以 iostat 为准。

**再追问：盘用到多少算故障？**  
**85%** 就要当故障处理，不要等 100%。写放大和 GC 会先把 await 抬起来。

## Q11：TIME_WAIT 多 vs CLOSE_WAIT 多？

**★★★★★**

**场景**  
网关 `ss -s` 里 TIME_WAIT 几十万。另一台 CLOSE_WAIT 持续涨。

**完整解答**

TW 在**主动关闭方**，短连接正常现象；CW 是应用收到 FIN 没 `close()`。

```
  主动关 --> FIN_WAIT --> TIME_WAIT（2MSL，常 60s）  正常
  被动关 --> 收 FIN、应用不 close --> CLOSE_WAIT     泄漏，修代码
```

1. 游戏网关与逻辑服是长连接，TW 通常不多；**短连接 HTTP 登录、支付回调**才会堆 TW。先连接池 / Keep-Alive，再考虑 `tw_reuse`（要 timestamps）。
2. **`tcp_tw_recycle` 已删除**，不要再当药方。乱降 2MSL 有串会话风险。
3. CW 持续增长：修代码，不调内核。

**再追问：TW 会占满本地端口？**  
会。客户端短连接扫爆 `ip_local_port_range`。看 `ss -s`，先复用连接。

## Q12：ss LISTEN 的 Recv-Q 是什么？

**★★★★★**

**场景**  
新玩家连不上，`ss -lnt` 看到 LISTEN 上 Recv-Q 顶满。有人说应用没读数据。

**完整解答**

LISTEN 和 ESTAB 的 Q **不是同一个数**：

```
  半连接队列（SYN）     tcp_max_syn_backlog
  全连接队列（等 accept） min(listen backlog, somaxconn)
                              ^
                     LISTEN Recv-Q = 已握手未 accept 的个数
                     LISTEN Send-Q = backlog
```

1. Recv-Q 逼近 Send-Q → accept 太慢或 backlog 太小。
2. 有效队列 = **`min(listen(), somaxconn)`**。只改应用 `listen(1024)` 不改 `somaxconn` 等于没改。默认 somaxconn 常 128，生产过小。
3. ESTAB Recv-Q 涨才是应用不 `read()`。不要把 accept 慢说成读慢。

**再追问：容器里改宿主机 somaxconn 有用吗？**  
不一定。容器是自己的 net ns。要在 Pod sysctl 或进程自己 `listen(65535)`。

## Q13：conntrack 满什么现象？

**★★★★★**

**场景**  
活动高峰新玩家进不去，在线长连接还在打。安全组没改。

**完整解答**

表满：**新连接失败，旧长连接还在。** 这是签名，不要先改安全组（安全组通常新旧一起死）。

```
  新 SYN --> PREROUTING conntrack 满 --> 丢
  已 ESTAB 长连接 --> 还在走

  K8s：Service DNAT、Pod 出站 MASQUERADE 都占表
```

1. `conntrack -C` vs `nf_conntrack_max`；dmesg 有 `table full, dropping packet`。
2. 止血调 max（如 `nf_conntrack_max=1048576`）；长期降 established 超时、**告警 80%**。
3. 游戏活动短连鉴权打满表，表现就是「新进不去、在线还在跑」。

**再追问：调大 max 就完了吗？**  
内存换容量。根因常是短连接没复用、超时过长。要告警，不要等表满才发现。

## Q14：三次握手为什么不是两次？TIME_WAIT 为什么 2MSL？

**★★★★★**

**场景**  
有人说两次就够了，再问为什么不把 TIME_WAIT 改成 5 秒。

**完整解答**

第三次握手让两端都确认「对方收到了我的初始序号」，并**防历史 SYN 幽灵连接**（旧 SYN 迟到，两次会建成脏连接）。

```
  客户端 SYN --> 服务端 SYN-ACK --> 客户端 ACK
                                      |
                                      没有这次 ACK：旧 SYN 可骗出半开连接

  主动方最后 ACK 后进 TIME_WAIT（2MSL）
    ① 最后 ACK 丢了，对端会重传 FIN，还能再回 ACK
    ② 同一四元组上旧包消散，不污染新连接
```

1. 2MSL 常见 **60s**。短连接 TW 爆炸 → 连接池，不是关 TIME_WAIT。
2. `tw_recycle` 已删除。把 2MSL 改成 5s 有串话风险。
3. 游戏网关应被动关闭或统一由一方关，避免两端同时主动关。

**再追问：四次挥手能合成三次吗？**  
对端没有待发数据时，ACK+FIN 可合并。有半关闭需求时仍是四次。细节回 08。

## Q15：502 vs 504 vs 499？

**★★★★★**

**场景**  
登录入口刷 5xx。有人把 Nginx 超时改成 300s。APP 其实 8s 就放弃了。

**完整解答**

谁先断开、上游有没有合法 HTTP，三码不同：

```
  上游挂 / RST / 非法响应     --> 502
  已转发，等上游读超时        --> 504
  客户端先走（APP 超时更短）  --> 499
```

1. **502**：进程没了、没听端口、响应中途 RST/OOM（`prematurely closed`）。
2. **504**：上游慢。先测绕过网关的 RT，不要先把 timeout 改成 300s。
3. **499**：超时链常是 APP 更短。活动 SQL 慢：网关 60s、APP 8s → 玩家失败、网关记 499、DB 还在跑。
4. 超时必须 **外短内长**。只看网关 5xx 会漏掉 APP 侧失败。

**再追问：499 算服务端 bug 吗？**  
先对谁超时更短。上游 P99 高就是真慢；上游很快才像网络或玩家取消。

## Q16：curl -w 五段？tcp 段含 DNS 吗？

**★★★★★**

**场景**  
登录慢。`time_connect` 很大，网络组被喊去背锅。

**完整解答**

五段时间戳是**从开始累计**的。tcp 段含 DNS，本段要用减法：

```
  0 ── namelookup ── connect ── appconnect ── starttransfer ── total
       |    dns      |   tcp    |    tls     |     ttfb      | body
```

```bash
curl -o /dev/null -s -w \
  'dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n' \
  https://example.com
```

1. dns = namelookup。tcp 本段 = connect − dns。tls = appconnect − connect。ttfb = starttransfer − appconnect。
2. connect 2ms、ttfb 3.5s → 不是公网，是应用/DB。
3. HTTP 无 tls 段。

**再追问：dns 段高先查谁？**  
劫持、TTL、K8s ndots（短名补后缀多次查询）。见 Q30、Q40。

## Q17：抓包最小闭环？生产禁止什么？

**★★★★★**

**场景**  
有人 `tcpdump -i any` 打到终端，机器 load 先炸了。

**完整解答**

先分层定责，再抓；抓就要能离机分析：

```
  过滤 IP + 端口
  -nn     不反解 DNS
  -c      限包数
  -w      写 pcap，不要打终端
```

```bash
tcpdump -i eth0 host 10.0.0.5 and port 8080 -nn -s0 -c 1000 -w /tmp/a.pcap
```

1. **禁止**：无过滤、长时间 `-i any`、输出打到终端。
2. Wireshark / tshark 看重传、RST 源 IP、ZeroWindow。
3. 本机看到 `incorrect checksum`、巨大帧，对端却正常 → TSO/校验卸载，假的。

**再追问：RST 看什么？**  
RST **源 IP**。本机应用、内核、还是中间 LB/WAF，决定找谁。NAT 后两端同时抓。

## Q18：超时和 refused 抓包差别？

**★★★★★**

**场景**  
玩家「连不上」。一张单写 timeout，一张写 refused。安全组刚改过。

**完整解答**

先分开现象，再抓 SYN：

```
  超时：SYN 重传，没有 SYN-ACK     ← 黑洞 / drop
  拒绝：SYN → 立刻 RST             ← 没监听 / reject
```

1. 安全组 **drop** = 超时；**reject** = RST。不要混。
2. ping 不通 TCP 通 → ICMP 被禁，正常。ping 通不能证明 TCP 通。
3. 本机 SYN 已出网卡仍超时 → `ip route get`、mtr、conntrack，不是先改应用。

**再追问：半连接队列满像哪种？**  
像丢 SYN（超时/Cookie），不像立刻 RST。全连接满才 Recv-Q 顶满，客户端 RST 或超时。见 Q24。

## Q19：%steal 和 CPU throttle 是一回事吗？

**★★★★**

**场景**  
容器 P99 爆炸，宿主机很闲。有人看了 `mpstat` 的 `st` 说是超卖。

**完整解答**

**不是一回事。** 一个换机，一个加 limit / 对齐 GOMAXPROCS。

```
  %st（mpstat）     Hypervisor 超卖，把 vCPU 给了别人  --> 换规格 / 迁宿主机
  throttle          cgroup quota（cpu.stat）            --> 加 limit 或降并发
```

1. steal 持续 **> 10%** 且延迟涨：自己优化代码解决不了。
2. throttle 看 `nr_throttled / nr_periods` 增量；宿主机可以很闲。
3. K8s 里 st 高不是 throttle，别改错旋钮。

**再追问：request 等于 limit 还会 throttle 吗？**  
会。只有 limit（quota）是硬顶；高峰打满 quota 就 throttle。细节回 07 / K8s。

## Q20：容器 nproc=32、limit=1 核对 Go 意味着什么？

**★★★★**

**场景**  
匹配服 P99 飙，宿主机 CPU 60% idle。容器里 `nproc` 显示 32。

**完整解答**

`nproc` / `free` 读宿主机视图，**mount ns 不隔离**这两份。Go 按 32 核配 `GOMAXPROCS`，limit=1 核会把自己 throttle 死：

```
  谎言：nproc=32  --> GOMAXPROCS=32 个 P
  现实：cpu limit=1 --> cgroup 周期内只能跑 1 核
              --> throttle --> P99 飙，宿主机还闲
```

1. 用 `uber-go/automaxprocs`（或手动对齐 limit）。Java 用 `-XX:ActiveProcessorCount`。
2. 扩节点没用，要加 limit 或去 limit，并改运行时并发。
3. 读 `/sys/fs/cgroup/cpu.stat`，不要信容器里的 `top`。

**再追问：Java GC 线程也会中招吗？**  
会。按 32 核拉 GC 线程，1 核 limit 一样 throttle。堆外预算见 Q6。

## Q21：cgroup 和 namespace 各管什么？

**★★★★**

**场景**  
「容器是小虚机吧？里面 free 64G 说明 limit 没生效。」

**完整解答**

容器是普通进程 + 两套内核设施。共用同一个内核；内核 panic 全机一起死。

```
  namespace：看见什么（PID/NET/MNT/UTS/USER/IPC）  --> 视图
  cgroup   ：能用多少（CPU/内存/IO/pids）          --> 配额

  超配额：throttle、OOM、fork 失败
  容器内 free / nproc / top 经常在撒谎
```

1. 配额不够看 cgroup 文件；逃逸、PID 1 语义看 namespace。
2. `free`/`nproc` 不可信。从 `/proc/<hostpid>/cgroup` 找路径再读。
3. 不是安全硬墙：突破 ns 仍是同一内核。

**再追问：cgroup 能挡住内核漏洞吗？**  
不能。隔离的是配额和部分视图，不是 hypervisor 那种硬边界。

## Q22：inode 满和磁盘空间满怎么分？

**★★★★**

**场景**  
`df -h` 还有空间，`touch` 失败。日志目录里无数小文件。

**完整解答**

```
  df -h     块空间
  df -i     inode
  有空间 touch 失败 --> inode 满（小文件海）
```

1. 游戏日志按请求切文件、或 core / 临时文件没清，最常见。
2. 空间满和 inode 满都能把 Nginx / 游戏日志写挂；告警两套都要。
3. 清理小文件或改大文件滚动，加盘解决不了 inode。

**再追问：du 和 df 差一截呢？**  
先想 deleted fd（Q9），不是 inode。inode 满时 df -h 往往还空。

## Q23：dirty_ratio 到了会怎样？

**★★★★**

**场景**  
CPU 没事，接口全超时，Load 很高。刚开始全量备份。

**完整解答**

脏页超过 `dirty_ratio`（约 20%）后，**写进程阻塞在 `write()`**，全机卡：

```
  应用 write() --> page cache（Dirty）
                      |
                      +-- 低于阈值：异步刷盘
                      +-- 到 dirty_ratio：同步卡住 write()
                            --> Load 高、接口超时、CPU 可以很闲
```

1. 看 `/proc/meminfo` 的 `Dirty`。治理是限写、独立日志盘，不是盲目加大 ratio（加大只是推迟爆炸）。
2. 日志狂写、备份打满盘是游戏机房经典故事。
3. 交叉 D 状态 / wchan=writeback。

**再追问：available 这时准吗？**  
不准，会偏乐观。脏页要 writeback 才能回收，盘慢时回收卡住写入。

## Q24：半连接队列满 vs 全连接队列满？

**★★★★**

**场景**  
开服涌入，有的客户端超时，有的 RST。要你判断是哪条队列。

**完整解答**

```
  SYN --> 半连接队列（握手中）
            满：像丢 SYN / SYN Cookie，抓包多见 SYN 重传

  握手完 --> 全连接队列（等 accept）
            满：LISTEN Recv-Q 顶满；客户端 RST 或超时
            netstat -s | grep overflow
```

1. 半连接：`tcp_max_syn_backlog`、SYN flood 防护。
2. 全连接：`min(listen, somaxconn)`，加快 accept 或加大 backlog（Q12）。
3. 不要把两种「连不上」写成同一个内核参数。

**再追问：SYN Cookie 开了还算队列满吗？**  
Cookie 是半连接满时的降级，能连上但信息丢失、性能差。要看是不是真在抗洪，还是 backlog 过小。

## Q25：游戏长连接为什么还要应用心跳？

**★★★★**

**场景**  
战斗长连接「无故」断。内核 keepalive 是开的。抓包看到中间设备 RST。

**完整解答**

内核 `tcp_keepalive_*` 默认 **7200s（2h）**，当不了游戏心跳。NAT / LB / conntrack 空闲超时常常是**分钟级**：

```
  应用心跳 15–45s  <  中间空闲超时（有的 5min）  <  内核 keepalive 2h

  心跳太慢 --> 中间先 RST，本端还以为 ESTAB
```

1. 心跳间隔必须短于最小中间超时。
2. 心跳还能检测逻辑死（进程活着不读包）。只看 TCP ESTAB 看不出业务卡死。
3. 手机 NAT 杀空闲连接是高频现场，不是内核 bug。

**再追问：加大 tcp_keepalive_time 能替代心跳吗？**  
不能。它只能清死连接，清不了 NAT。改内核默认还可能伤其他短连接。

## Q26：何时 UDP、何时 KCP、何时 TCP？

**★★★★**

**场景**  
策划要「全部改 KCP 降延迟」。支付回调也想走同一通道。

**完整解答**

```
  可丢（位置、特效）          --> UDP
  弱网要可靠、TCP 尾延迟不可接受 --> KCP（用户态可靠 UDP，必须限速）
  登录 / 支付 / 公告          --> TCP / HTTPS
```

1. KCP 更激进重传，代价是带宽和 CPU；不限速会自己打爆链路，更卡。
2. 不要当银弹。先测 RTT/丢包下的尾延迟。
3. 支付回调仍走 HTTPS，不走 KCP。跨海技能同步卡 200ms 才是 KCP 的典型故事。

**再追问：同一条 TCP 复用移动和可靠指令？**  
移动丢包会拖指令（队头阻塞）。拆 UDP+TCP 或 KCP 多通道。

## Q27：ZeroWindow 是谁的问题？

**★★★★**

**场景**  
本端 Send-Q 涨，抓包 ZeroWindow。有人要调大 `sndbuf`。

**完整解答**

**接收方不 `read()`。** 对端 rwnd=0，本端只能堆 Send-Q。

```
  对端 Recv-Q 堆满 --> 通告窗口 0
  本端看到 ZeroWindow、Send-Q 涨
  治对端消费（线程卡、GC、逻辑死循环）
  不先调本端 sndbuf
```

1. 游戏网关 Recv-Q 涨：逻辑线程没读 socket，玩家感觉延迟，包在内核里。
2. 两边 Q 都大于 0 是双向都堵。
3. 交叉 06 的 ESTAB Recv-Q，不要先当带宽不够。

**再追问：调大 rcvbuf 能根治吗？**  
只能推迟。应用不读，窗口终究会再打满。

## Q28：Keep-Alive 不开的代价？TLS 高峰怎么办？

**★★★★**

**场景**  
登录高峰网关 `%us` 打满，TIME_WAIT 爆炸。每条请求都在重新握手。

**完整解答**

不开 Keep-Alive：每次请求都是 **TCP + TLS**，TW 和 CPU 一起炸。

```
  短连接：TCP 握手 + TLS 握手 + 业务 + 挥手 --> TW
  Keep-Alive：握手一次，复用多条 HTTP
```

1. 入口对客户端开 Keep-Alive；过长占 fd，过短等于短连接。
2. TLS 高峰标配：**ECDSA + TLS 1.3 + session 复用**。先用 curl -w 确认慢在 tls 段（appconnect − connect）。
3. RSA 证书在高峰吃 CPU。支付禁止 0-RTT。

**再追问：upstream keepalive 只写 keepalive 32 够吗？**  
不够。还要 HTTP/1.1 和 `Connection ""`。见 Q50。

## Q29：证书链缺中间证 vs 过期？

**★★★★**

**场景**  
部分玩家登录失败，浏览器自己访问却是绿锁。`openssl s_client` 有告警。

**完整解答**

```
  过期     --> 几乎全挂（所有校验证书的客户端）
  缺中间证 --> 部分客户端挂（有的会下中间证，有的不会）
```

1. `openssl s_client -connect host:443 -servername host` 看链和 `Not After`。`unable to verify the first certificate` = 缺中间。
2. 入口证书和回源证书是两套。CDN 回源 HTTPS 过期只打 502，边缘仍然绿锁。
3. 到期告警至少提前 **14 天**，测真正握手路径，不要只看磁盘文件日期。

**再追问：双向 TLS 客户端证过期长什么样？**  
偶发失败，像「部分用户不行」。支付客户端证要单独监控。

## Q30：改 DNS 后部分用户仍旧 IP？

**★★★★**

**场景**  
开服把登录域名切到新 VIP。你电脑已经是新 IP，部分渠道还打旧服。

**完整解答**

TTL 和运营商缓存。国内运营商常常**不守 TTL**：

```
  ① TTL 3600 → 60，等一个旧 TTL
  ② 改 A 记录
  ③ 旧 IP 保留，反代到新 IP（托底）
  ④ 旧 IP 流量归零再回收
  ⑤ TTL 调回
```

1. 不要只 ping 自己电脑当验证。连接池、客户端缓存也会留旧 IP。
2. 开服当天不要把登录域名 TTL 和 CDN 规则叠在一起改。
3. 摘流量要 VIP 级（LB 摘）+ DNS，只改 DNS 会有 TTL 窗口打到死 VIP。

**再追问：TTL 已经 60s，几小时还有人打旧 IP？**  
运营商缓存、客户端缓存、连接池。HTTPDNS 可缩短不可控缓存（Q40）。

## Q31：CDN 502，源站本机 curl 正常？

**★★★★**

**场景**  
包体下载 502。你 ssh 到源站 `curl localhost` 200。边缘浏览器有时绿锁。

**完整解答**

先分 HIT 还是回源失败：

```
  绕过 CDN：源站 IP + Host 头
       |
       +-- 源站失败 --> 源的事
       +-- 源站正常 --> 回源白名单 / 回源证书 / 回源超时
  X-Cache: HIT 的 502 才像 CDN 自身
```

1. 安全组要放行 CDN 回源网段；源站只允许办公网是经典坑。
2. 回源证书过期 → 502，边缘证仍绿。交叉 Q29。
3. 本机 curl 不经回源路径，不能当「CDN 没问题」的证据。

**再追问：整站 Purge 会怎样？**  
回源风暴，打爆源站。Purge 指定 URL，监控回源带宽。

## Q32：ip route get vs show？mtr 某跳丢包？

**★★★★**

**场景**  
双网卡机器。`ip route show` 看着对，流量却走了另一张网卡。mtr 第 5 跳 30% Loss。

**完整解答**

**`ip route get` = 内核真实决策**（含策略路由、源 IP、出接口）。`show` 只是表，不一定是这一包走的路。

```
  ip route get $IP     这一包会从哪走
  ip route show        主表长什么样（可能不是最终决策）

  mtr 中间跳丢、后面跳不丢 --> 常常只是 ICMP 限速
  后面跳同样丢            --> 才像真丢
```

1. 双网卡、策略路由必须 get，不要用 show 结案。
2. mtr 优于 ping+traceroute：逐跳 Loss% + RTT。
3. ping 不通 TCP 通可以正常（ICMP 被禁）。

**再追问：ARP FAILED 呢？**  
同网段 IP 不回应 ARP。先 get 再 `ip neigh`。路由失败是 get 无路由。

## Q33：大包失败小包成功？

**★★★★**

**场景**  
ping 通，TLS 握手偶发挂死。小包 API 正常，上传大包失败。

**完整解答**

MTU / PMTUD。以太网 MTU 1500。PMTUD 靠 ICMP「需要分片」；防火墙丢 ICMP → **小包通、大包死**：

```
  默认 ping 56B  --> 「网络好」（会骗你）
  ping -M do -s 1472  --> DF 大包；不通就是 MTU/PMTUD
```

1. 不要用默认小 ping 宣称网络好。
2. 隧道、VPN、云网关叠封装后有效 MTU 更小。
3. TLS 握手挂死有时是大包被黑洞，不是证书。

**再追问：把 DF 关掉当修复？**  
中间分片更脆，且有的路径仍丢分片。正确做法是发现路径 MTU 并调低，或放行 ICMP。

## Q34：30 秒全景命令？USE vs RED？

**★★★★**

**场景**  
告警响了，有人已经对着 `top` 翻了五分钟。要你开口第一套命令。

**完整解答**

用来定域，不是根因：

```bash
uptime
vmstat 1 5
free -h
df -h && df -i
mpstat -P ALL 1 2
ss -s
```

```
  玩家疼不疼？ --> RED：QPS / 错误 / P99
  哪块资源炸？ --> USE：利用率 / 饱和（队列） / 错误
  P99 涨      --> 先 RED 确认影响面，再 USE 定资源
```

1. USE 看 CPU/盘/网/内存是否饱和；RED 看网关速率、5xx/499、耗时。
2. Load 是饱和度，不是利用率。平均 CPU 40% 不能结案（Q41）。
3. 游戏网关用 RED；机器用 USE。只有 USE 没有 RED 会空谈资源。

**再追问：火焰图什么时候不要做？**  
Load 是 IO、`%us` 不高、进程在等锁/盘/网。On-CPU 火焰图浪费窗口。

## Q35：Nginx 日志 TOP IP 和 5xx 占比？

**★★★★**

**场景**  
入口被扫或上游刚挂。要你一分钟从 access.log 拿出证据。

**完整解答**

```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
awk '{c++; if($9~/^5/) s++} END{print s,c,100*s/c}' access.log
```

1. 第一句：TOP 客户端 IP（扫源、NAT 出口、异常集中）。
2. 第二句：5xx 次数、总请求、占比。再按 `$9` 拆 502/504。
3. 499/504 还要对 `$request_time` 和 `$upstream_response_time`，不要只看 status。
4. 结合 Q15：499 多可能是超时链，不是「没 5xx 就没问题」。

**再追问：按 URL 拆 5xx？**  
`awk '$9 ~ /^5/ {print $7}' access.log | sort | uniq -c | sort -rn | head`。先定位接口再下钻上游。

## Q36：strace -p 对逻辑服安全吗？看到大量 futex？

**★★★**

**场景**  
战斗服延迟尖刺。有人准备 `strace -p` 跟十分钟。

**完整解答**

长时间全量跟踪会拖延迟，生产默认不要这么干：

```
  strace -c -p PID          短窗口统计，生产默认
  全量 -p 长时间            逻辑服会拖 P99
  大量 futex                锁竞争，不是「系统调用很多就加核」
```

1. 用 `-c` 短窗口，或 eBPF / `perf`。战斗服不要长时间全量跟。
2. futex 多 = 锁竞争（匹配锁、全局排行榜锁都常见）。
3. strace 看「正在发什么调用」；fd 泄漏用 `lsof` / `/proc/PID/fd`。

**再追问：-e trace=network 可以一直挂着吗？**  
高峰仍慎用。跟子进程再加 `-f` 开销更大。能复现再短窗口采。

## Q37：systemd After/Requires/Wants？Restart=always RestartSec=0？

**★★★**

**场景**  
逻辑服 OOM 后疯狂重启，把节点打满。unit 里写了 `Restart=always` 和 `RestartSec=0`。

**完整解答**

```
  After=      只控制顺序，不共生死
  Requires=   强依赖：B 挂 A 也挂，会拉 B
  Wants=      软依赖：B 挂了 A 还跑
```

1. 「A 启动前 B 必须在」：After=B **且** Requires=B。只要顺序用 After。
2. **`always` + RestartSec=0 = OOM 死亡螺旋**（起不来立刻再起）。生产用 `on-failure` + `RestartSec` + **StartLimit**。
3. 崩溃循环先 `systemctl status` / journal，不要把间隔改成 0。

**再追问：改了 unit 为什么不生效？**  
要 `daemon-reload` 再 restart。只 reload 定义、只 restart 进程，缺一步都会用旧配置。

## Q38：journal vs dmesg？

**★★★**

**场景**  
进程 137 没了。有人只翻了 `journalctl -u game`，说没 OOM。

**完整解答**

两者看的层不一样，137 必须交叉：

```
  journalctl   服务 stdout/stderr、退出码、unit 状态
  dmesg        内核：OOM Killer、IO error、NFS、hang
```

1. 退出码在 journal；整机 OOM 在 dmesg。容器 137 还要看 cgroup `memory.events`（Q5），节点 dmesg 可能没有经典行。
2. `journalctl -u nginx -n 100 --no-pager`。不要无限 `-f` 当采集。
3. journald 要设 `SystemMaxUse`，否则吃光 `/var` 或 tmpfs。

**再追问：只有 journal 里的 137 就能结案 OOM？**  
不能。137 还可能是人手 `-9` 或 kubelet 强杀。必须对 dmesg / cgroup / 事件。

## Q39：HTTP/2 还解决不了什么阻塞？手机切网 TCP 怎样？

**★★★**

**场景**  
「上了 HTTP/2 就不会堵了吧？」手机玩家切 4G/Wi-Fi 必须重登。

**完整解答**

HTTP/2 解决的是**应用层**队头阻塞（多 stream 并行）。**TCP 丢包仍堵整条连接上的所有 stream。**

```
  HTTP/1.1 : 一条连接一个响应排队
  HTTP/2   : 一条 TCP，多 stream；丢包仍堵整条 TCP
  HTTP/3   : QUIC / UDP，丢包只堵那条 stream；支持连接迁移
```

1. 手机切网：四元组（IP:port）变了，TCP 连接死，要**重连 + 会话恢复**。
2. QUIC 才有迁移（连接 ID 不绑死四元组）。游戏自研多数仍是 TCP/KCP，答到这一点即可。
3. 内网 gRPC 常用 HTTP/2，延迟已经低时通常够。不要答「上了 HTTP/2 就不会堵」。

**再追问：KCP 解决 TCP 队头阻塞吗？**  
用户态多通道可以避开一条 TCP 堵死。它不自动给你 QUIC 那种切网迁移。

## Q40：HTTPDNS 解决什么？K8s 外网解析慢？

**★★★**

**场景**  
部分地区下载域名被指到广告页。集群里访问 `api.xxx.com` 偶发要几百毫秒。

**完整解答**

HTTPDNS：客户端用 HTTPS 问业务自己的解析接口拿 IP，**绕过运营商 Local DNS 劫持 / 缓存**。证书仍校原域名（SNI/Host）。

```
  同一名字 @权威 / @8.8.8.8 正确
           @运营商 DNS 广告页     <-- 劫持，HTTPDNS 绕开

  K8s ndots:5 + search cluster.local
           短名先补成集群内 FQDN 查好几次才出网
           写成 api.xxx.com. （FQDN 带点）
```

1. 智能 DNS 按地域返回不同合法 VIP，不要和劫持混为一谈。
2. K8s 外网解析慢：ndots 导致多次无效查询，用 **FQDN 带点**，或调 ndots、加 CoreDNS 缓存。
3. 代价：HTTPDNS 自己要做容灾和调度。

**再追问：curl --resolve 测的是哪一段？**  
跳过 DNS，直接打指定 IP。用来拆 dns 段 vs 后面的 tcp/tls/ttfb（Q16）。

## Q41：平均 CPU 40% 但 P99 800ms，还查什么？

**★★★**

**场景**  
活动开始登录 P99 从 50ms 到 800ms。有人甩出整机 CPU 40% 说没问题。

**完整解答**

平均利用率不能结案。P99 涨先 RED 再 USE：

```
  平均 CPU 40%、P99 800ms
       |
       +-- 单核 100%（mpstat -P ALL）
       +-- cgroup throttle（宿主机可以闲）
       +-- 锁 / futex
       +-- 下游 RT（DB / Redis）
       +-- 丢包 / 重传
```

1. 游戏登录常见是 SQL 或 conntrack，不是「服务器平均 40%」。
2. throttle 是 CPU 配额饱和，利用率可以低（Q19、Q20）。
3. 先看谁失败、失败多少（RED），再定点资源（USE）。细节回 12。

**再追问：Load 不高能否排除 CPU 问题？**  
不能。短突发、单核热点、throttle 都可以 Load 不高但 P99 炸。

## Q42：有状态逻辑服能不能「先重启再说」？

**★★★**

**场景**  
一场对局中 Load 升高。群里有人要重启全部逻辑服 Pod。「先重启再说」。

**完整解答**

**未留证据不行。** 重启是变更：内存态会丢，等于踢人，可能要回档。

```
  止血优先：摘流量 / 回滚配置 / 限流
  重启逻辑服 = 踢对局 + 丢内存态
  先：30 秒全景、影响面、变更、日志/sar
  再：按变更窗口重启，并评估回档成本
```

1. 有状态服把重启当最后一刀，不是第一刀。
2. 重启前留证据（Q34），否则根因永远是「重启好了」。
3. 交叉 K8s：不要为了「做点什么」去杀还活着的战斗进程。

**再追问：无状态网关呢？**  
滚动可以，但仍要 readiness 和超时链。也不要无证据同时踢光所有实例。

## Q43：Nginx 499 和 504 怎么配超时？

**★★★**

**场景**  
活动登录慢。Nginx 刷 499，后端还在算。有人只把 `proxy_read_timeout` 调到 300s。

**完整解答**

必须 **客户端 < proxy_read_timeout < 应用**（读超时）。反了就会 499 刷屏，或 504 而浏览器还在转圈。

```
  APP 8s  --> 先走，Nginx 记 499，上游可能还在跑
  Nginx 60s 到点 --> 504
  上游从未连上 / RST / 非 HTTP --> 502
```

1. 504 是等上游超时。先优化/扩上游，再考虑超时是否合理。
2. 只把 Nginx 调到 300s、SLB 还是 60s，玩家侧仍是 499。
3. `$request_time` vs `$upstream_response_time` 对这两列，不要只看 status。

**再追问：支付 POST 能对 502 自动重试吗？**  
非幂等禁止盲目 `proxy_next_upstream`。重试会打成双扣。

## Q44：日志把盘写满第一刀？

**★★★**

**场景**  
`/var` 100%。有人 rm 了 access.log，空间没回来。另一人准备加盘。

**完整解答**

```
  1. df -h / df -i
  2. du -sh /var/log/*
  3. lsof | grep deleted     已删仍占用
  4. 止血：截断 / 重启持有者 / vacuum journal
  加盘不是根因
```

1. logrotate：进程会 reopen 用 create + USR1；**不会 reopen 用 copytruncate**（很多游戏自研服）。
2. 只 rm / 只 truncate 不 reopen，inode 还指着旧文件，du 和 df 对不上（Q9）。
3. journald 设 `SystemMaxUse`；应急 `journalctl --vacuum-size=500M`。

**再追问：copytruncate 有什么代价？**  
短暂重复或丢一行。比盘满死机便宜。能 USR1 就不要 copytruncate。

## Q45：哪些告警该打电话？

**★★★**

**场景**  
半夜 CPU 70% 告警把人叫醒。登录曲线正常。真正的支付失败被淹没在风暴里。

**完整解答**

叫醒线对齐业务损伤，不是对齐「机器有点忙」：

```
  该打：探活失败（入口/登录/支付）、登录跌、支付失败
        磁盘将满（预测 <24h）、inode/fd 打满、OOM 风暴、证书一周内

  不打：单机 CPU 70% 且登录/支付正常
        磁盘 60%、已知维护窗口
```

1. 探活失败是 P0：内部指标可能还绿，入口已经挂了。
2. 同一件事不要既 P0 又 P2。用 `for:` 防抖，CPU 冲 5 秒不要打电话。
3. 告警风暴会让人关通知，支付失败被淹没——根因常是一台机关了 40 条探活。

**再追问：磁盘 60% 要叫吗？**  
不要。predict 24h 内打满才叫。inode 满时 `df -h` 还空，两套都要告。

## Q46：crontab 手动能跑定时不能？

**★★★**

**场景**  
备份脚本你手动一跑就成功。crontab 到点没跑或 command not found。

**完整解答**

cron 环境是空的：**PATH 极短、不读 bashrc**。

```
  手动能跑、定时不能
       |
       +-- PATH / 绝对路径
       +-- 环境变量写在 bashrc 里（cron 不读）
       +-- crond 没起来、时区、邮件丢了报错
```

1. crontab 第一行写 PATH，脚本用绝对路径。
2. 查 `crontab -l`、`/etc/cron.d/`、`systemctl status cron`。
3. **新任务用 systemd timer**（有 journal、可 Persistent 补跑）。存量 crontab 先排障，不要再往里堆 `* * * * *`。

**再追问：timer 和 cron 选哪个？**  
新任务 timer。存量机器上 cron 还在跑，排障必会：绝对路径、不读 bashrc、查 crond。

## Q47：keepalived 双 VIP 是什么？

**★★★**

**场景**  
两台都自称 MASTER，各有一个相同 VIP。心跳网刚刚改过安全组。

**完整解答**

**脑裂。** 两节点 VRRP **没有 quorum**，心跳被墙或网络分区就会双 VIP。

```
  心跳不通（协议 112 被墙） --> 两台都升主 --> 双 VIP
  止血：先停下一台 keepalived，保证只有一个 VIP
  再修网络，不要两台一起改 priority 抢
```

1. VRRP 是 **IP 协议号 112**（常被写成「UDP 112」，抓包应用 `tcpdump -i eth0 proto 112`）。
2. `nopreempt`：主恢复后不抢回，避免二次闪断。
3. 数据平面若已双写，按 20 收场：选真相、评估 RPO。VIP 通 ≠ 后面 HAProxy 活着，要 track_script。

**再追问：云上也能自建 VRRP 吗？**  
很多云「VIP」是产品 SLB，不能自建 VRRP。那是云平台的题；机房双机才是这一问。

## Q48：RTO/RPO 和 3-2-1？

**★★★**

**场景**  
「我们有备份」但没做过 restore。开口问你游戏库能丢多久、要多久拉起来。

**完整解答**

先定目标再选方案。没有演练的备份不算 RPO：

```
  RPO：最多丢这段数据（到最近可恢复点）
  RTO：中断到恢复业务的目标上限

  3-2-1：3 份、2 种介质、1 份异地
  只 backup 成功不算 --> 要演练 restore，记下真实 RTO
```

1. 同步复制 RPO≈0，贵、延迟敏感；异步 RPO=复制延迟。
2. 游戏还要对齐 Redis / 对象存储位点，只回 MySQL 不够（细节 08）。
3. MTTR 是成绩单，长期贴着 RTO 说明没有余量。

**再追问：两节点 keepalived 能当多数派吗？**  
不能。两节点没有 quorum，脑裂要靠 fencing / 人工停一台（Q47），不是 Raft。

## Q49：chmod 777 和 SUID？

**★★★**

**场景**  
为了「先跑起来」，有人把游戏配置目录 chmod 777。`/tmp` 里多了一个不认识的 SUID 二进制。

**完整解答**

```
  777     谁都能改，被植入后门无法追责
  SUID    以文件属主身份跑（passwd 合法；来历不明当后门）
```

1. 游戏配置、密钥、脚本出现 777，当事故处理，不是「先跑起来再说」。配置至少 640。
2. `find /usr/bin /usr/sbin -perm -4000 -ls` 定期审计。多出来的先下线再分析，不要先跑一下「看看是什么」。
3. 最小权限、sudo 白名单、独立账号。`sudo su` 等于放弃追责。

**再追问：SUID 和 SGID 怎么记？**  
SUID 以属主跑；SGID 以属组跑（目录下新建文件继承组）。审计都用 `find -perm`。

## Q50：Nginx keepalive 32 仍 TW 爆？

**★★★**

**场景**  
upstream 已经写了 `keepalive 32`，后端 TIME_WAIT 还是炸。短连接登录高峰。

**完整解答**

只写 `keepalive 32` 不够。HTTP/1.0 代理默认关连接，复用形同虚设。三件套才算长连接复用：

```nginx
upstream backend {
    keepalive 32;
}
server {
    location / {
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_pass http://backend;
    }
}
```

1. 缺 HTTP/1.1 或缺清空 `Connection`，后端仍短连接，TW 爆（Q11、Q28）。
2. 入口对客户端的 Keep-Alive 和 upstream 复用是两段，都要开。
3. 游戏 HTTP 登录/支付走这段；战斗长连接不是 Nginx keepalive 能替代的。

**再追问：keepalive 开太大？**  
占后端 fd。32 是常见起点，按 ESTAB 和 TW 再调。先保证三件套生效，再谈数字。
