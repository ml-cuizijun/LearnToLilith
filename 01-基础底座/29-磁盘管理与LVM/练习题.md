## Q1

**★★★★☆｜服务器重启后数据盘挂载失败，进系统一看盘符从 /dev/sdb 变成了 /dev/sdc，为什么？怎么从根上避免？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [二、认盘：lsblk 与磁盘命名](知识点.md)

### 场景

值班群炸了：昨晚一次重启，今天 /data 没挂上，业务写进了根盘的空目录。有人怀疑盘坏了要报修，有人提议「把 fstab 里的 sdb 全改成 sdc 就好了」。

### 完整解答

> 🎯 **一句话**：盘符是内核按枚举顺序临时分配的，不保证跨重启稳定；持久挂载一律认 UUID。

`/dev/sdb` 这个名字只说明「本次开机它是第二个被枚举的 sd 设备」。热插拔、重启、驱动加载顺序变化，都会让同一块物理盘换名字——fstab 里写死 `/dev/sdb1`，重启后它变成 sdc，挂载自然失败。改回 sdc 只是**把炸弹的引信再拉一次**：下次重启可能又变回来。

从根上避免两件事：**fstab 用 UUID 标识设备**（blkid 取，UUID 在文件系统创建时生成，跟盘走不跟盘符走）；**动手前 lsblk 现场认盘**，别背昨天的盘符。

> 🔍 **现场**：
> ```bash
> lsblk -f                     # ← NAME + FSTYPE + UUID 一屏对齐，现场认盘的标准动作
> blkid /dev/sdc1
> # /dev/sdc1: UUID="a3f2c8d1-5b6e-4c7a-9d21-0123456789ab" TYPE="xfs"
> ```
> 把 fstab 里的 `/dev/sdb1` 换成这个 UUID，`mount -a` 验证，`df -h /data` 验收。

> ⚠️ **别混**：盘符漂移是**正常行为**不是故障，「盘坏了」的判据是 `dmesg -T` 里的 I/O error（→ [08](../08-磁盘与IO/)），不是盘符变了。另外「数据写进根盘空目录、盘回来后文件被藏起来」这半截事故的机制在 [09](../09-文件系统与inode/)（挂载点把文件藏了），关键盘不加 nofail 是防它复发的根子。

### 再追问

**怎么区分 /dev/sda、/dev/vda、/dev/nvme0n1 这三种姓？**——sd* 是 SATA/SCSI/SAS 系，vd* 是 virtio 半虚拟化盘（云主机最常见），nvme*n*p 是 NVMe 盘（n 是 namespace、p 后是分区号）。**不要**凭姓猜性能——虚拟化环境里 virtio 盘可能比宿主 SATA 快得多，性能看 08 章的 await。

**lsblk 里 TYPE=lvm 的节点是分区吗？**——不是。`vg_root-lv_root` 这种长名字、TYPE=lvm，是 LVM 逻辑卷「长在」某个分区上的意思——树形结构的父子关系本身就是答案。

## Q2

**★★★★☆｜新加一块 3TB 盘：MBR 还是 GPT？fdisk 还是 parted？云盘还需要分区吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [三、分割：分区表与 fdisk/parted](知识点.md)

### 场景

装机同事照着老文档用 fdisk 给 3TB 盘分区，建完发现只认到 2TB，准备报「盘是假货」。另一个人问：云上的数据盘他从来没分过区，是不是一直做错了。

### 完整解答

> 🎯 **一句话**：MBR 寻址上限 2TB，3TB 起只能 GPT；parted 是脚本化大盘的标准姿势；纯数据云盘免分区是正统做法不是偷懒。

**MBR（Master Boot Record，主引导记录分区表）** 用 32 位扇区地址，**2TB 就是天花板**——3TB 盘在 MBR 下永远只认出一截，不是盘坏了。**GPT（GUID Partition Table）** 128 个分区、无实际容量限制，新盘一律它。fdisk 新版其实也支持 GPT，但 parted 能 `--script` 进装机脚本、传统上是大盘的标准选择。

```bash
parted /dev/vdb --script mklabel gpt mkpart primary 1MiB 100%
partprobe /dev/vdb          # ← 让内核重读分区表，免 reboot
lsblk /dev/vdb              # ← 验收：vdb1 出现
```

云盘免分区的理由：云数据盘没有引导需求、底层冗余不靠你分区，整盘直接 `pvcreate /dev/vdb` 少一层间接，**日后在线扩容更省事**——免分区的一步 `pvresize` 就吃满新容量，有分区要先 `growpart`（见 Q8）。分区只在「一块盘要切多个用途」时才必要。

> ⚠️ **别混**：`mklabel gpt` 是重写分区表（整盘数据清零），`mkpart` 才是新建分区——parted 的命令顺序错了没有撤销键。回车前对着 `lsblk` 确认设备名。

### 再追问

**partprobe 什么时候必须敲？**——改完分区表后内核可能还持有旧表（正在用的盘尤其），不重读就 `lsblk` 看不到新分区、下一步 pvcreate 报设备不存在。敲了还不行就 `partx -u` 或 reboot。

**系统盘也用 GPT 吗？**——现代发行版默认就是 GPT + UEFI；老机器 BIOS 引导才需要 MBR 兼容。数据盘不用纠结这条。

## Q3

**★★★★☆｜RAID 和 LVM 是什么关系？为什么说「先 RAID 再 LVM」？上了 LVM 还怕坏盘吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、护体：RAID 概览与叠层](知识点.md)

### 场景

评审会上有人提出「都用 LVM 拼池了，盘坏了 LVM 会自动切换备用盘」，准备按这个设计砍掉 RAID 卡预算。DBA 当场反对但没说出原理。

### 完整解答

> 🎯 **一句话**：RAID 管冗余和性能、LVM 管容量弹性，两层叠着用；LVM 自己不提供任何冗余。

叠层关系：多块物理盘先经 RAID（硬 RAID 卡或软 RAID `mdadm`）在 OS 眼里变成**一块**容量更大、更可靠的虚拟盘（`/dev/md0`），LVM 再把这块虚拟盘当普通盘照常 `pvcreate /dev/md0`——LVM 根本不知道脚下是几块物理盘。反过来不成立：**VG 里坏一块 PV，建在它上面的 LV 一起没**，LVM 没有副本、没有校验、没有热备切换。那位同事把 RAID 的职责错记到了 LVM 头上。

| RAID | 容错 | 生产用途 |
|------|------|----------|
| 0 | 无 | 可丢数据拼性能 |
| 1 | 1 块 | 系统盘镜像 |
| 5 | 1 块 | 读多写少，写有校验惩罚 |
| 10 | 每镜像组 1 块 | 库 / 高 IO 推荐 |

> ⚠️ **别混**：云上**不自建 RAID**——云盘底层已有多副本，再叠一层是花双份钱换负优化；云盘路径的冗余交给厂商 SLA（→ [33](../33-高可用与容灾/)）。RAID 也**不是备份**：误删、逻辑坏、整机没了它都救不了，备份另算（→ [31](../31-备份与恢复/)）。

### 再追问

**RAID 5 为什么说「写有惩罚」？**——每写一笔都要先读旧数据、算校验、再写校验，一次逻辑写放大成多次物理 IO；写重的库盘会被惩罚拖垮，所以库用 RAID 10（镜像不需要算校验）。

**RAID 重建期要注意什么？**——换盘补数据的重建期 IOPS 近乎腰斩（→ [08](../08-磁盘与IO/)），要当变更窗口管理，别撞活动高峰；重建本身也 stress 相邻盘，是「第二块盘也坏」的高危窗口。

## Q4

**★★★★★｜为什么需要 LVM？PV/VG/LV/PE 各是什么？直接分区不行吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、成砖：PV 与 LVM 三层结构](知识点.md)

### 场景

面试白板题。候选人说「LVM 就是把盘合起来」，面试官追问「合起来之后 /data 满了怎么办、和 RAID 拼盘差在哪」，开始卡壳。

### 完整解答

> 🎯 **一句话**：分区容量焊死在盘上，LVM 把空间池化——盘成砖、砖入池、池切卷，容量从此可搬家可拉长。

> 💡 **打个比方**：传统分区像**一排焊死的储物柜**——3 号柜塞满了，隔壁 4 号柜空着也放不进去；LVM 把所有柜子拆成同一规格的**乐高积木**（PE），拼一个大池子（VG），要多少从池子里现拼一个箱子（LV），不够长就再抓几块积木接上——在线扩容的全部秘密就这一句。

三层身份 + 一组命令：**PV（Physical Volume，物理卷）** = 被 LVM 打了元数据标记的盘/分区（成砖：`pvcreate`）；**VG（Volume Group，卷组）** = 若干 PV 堆成的空间池（`vgcreate`/`vgextend`）；**LV（Logical Volume，逻辑卷）** = 从池里按 PE 切出的一段逻辑设备，上层 mkfs 它（`lvcreate`/`lvextend`）。**PE（Physical Extent，物理块）** = 池子的最小分配单位，**默认 4MB**，`-L 100G` 会被取整到它的倍数。

和 RAID 拼盘的差别一句话：RAID 把多块盘拼成「一块更好更稳的盘」，目标是冗余/性能；LVM 把多块盘的**空闲容量**拼成池，目标是弹性。前者管「坏不坏」，后者管「够不够」。

> 📝 **面试**：记忆分组报三层——**PV 层（成砖 pvcreate/pvresize）、VG 层（池 vgcreate/vgextend）、LV 层（切卷 lvcreate/lvextend）**，配 pvs/vgs/lvs 三个查看命令。「和 RAID 的分工」这半问一定要主动答，等着被追问就矮一截。

### 再追问

**三层账本怎么看？**——`vgs` 看 VFree（池里还没分出去的空闲）、`lvs` 看 LSize（卷被切了多大）、`df` 看文件系统实际用了多少。三层数字互不相干，这是后面 Q9「df 不变」的病根。

**PV 可以是分区、整盘、RAID 设备吗？**——都可以：`/dev/vdb1`、`/dev/vdb`、`/dev/md0` 都能 pvcreate，LVM 只认「块设备」这一个抽象。

## Q5

**★★★★★｜给我从零讲一遍：新加一块盘，到业务能写 /data，每一步敲什么命令？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、垒池切卷：从 pvcreate 到 mount 的创建全链](知识点.md)

### 场景

值班收到扩容工单：500G 新盘已挂到机器（/dev/vdb），要给 /data 做 LVM 卷。新同事上来就 `mount /dev/vdb /data`，报 `wrong fs type`。

### 完整解答

> 🎯 **一句话**：六步链 pvcreate → vgcreate → lvcreate → mkfs → blkid → mount，一步一个命令、顺序不可换。

```bash
# ① 认盘（永远的第一步）
lsblk                                    # ← 确认 vdb 在、没有孩子、没挂载
# ② 分区（物理机；云盘纯数据可跳过分区直接用 /dev/vdb）
parted /dev/vdb --script mklabel gpt mkpart primary 1MiB 100% && partprobe /dev/vdb
# ③ 成砖入池
pvcreate /dev/vdb1                       #   Physical volume "/dev/vdb1" successfully created.
vgcreate vg_data /dev/vdb1               #   Volume group "vg_data" successfully created
# ④ 切卷
lvcreate -n lv_data -L 400G vg_data      #   Logical volume "lv_data" created.
# ⑤ 格式化
mkfs.xfs /dev/vg_data/lv_data
# ⑥ 挂载 + 持久化（fstab 用 UUID，见 Q7）
blkid /dev/vg_data/lv_data               #   UUID="a3f2c8d1-…" TYPE="xfs"
mkdir -p /data && mount /dev/vg_data/lv_data /data
df -h /data                              # ← 验收：容量、设备名对上才算完
```

顺序不可换的原因就写在报错里：跳过 mkfs 直接 mount，就是开篇那个 `wrong fs type`——块设备上没有文件系统，内核不知道该怎么读它。每一步的预期输出是下一步的入场券，任何一步输出异常就停，别硬走完。

> ⚠️ **别混**：`lvcreate -L 400G` 切多少是**你**定的，不是池里有多少就切多少——留着 VFree 才有日后余地；`-l 100%FREE` 是明确要吃光时的写法。

> 📝 **面试**：背链时主动带出两个分支——**物理机**先分区（MBR 2TB 上限，大盘 GPT）；**云盘**可免分区整盘 pvcreate。收尾补「fstab 用 UUID + mount -a 验证」，把六步链变成七步闭环。

### 再追问

**为什么业务要挂 /dev/vg_data/lv_data 而不是 /dev/vdb1？**——因为 mkfs 做在了 LV 上。整条链里「文件系统在谁身上」只有一处：你 mkfs 的那个设备；mount 的必须是同一个。

**怎么验证这条链做对了？**——`lsblk` 树形图里 vdb1 下面长出 `vg_data-lv_data`（TYPE=lvm），`df -h /data` 显示 400G——树和数字都对上，才是真的挂上了。

## Q6

**★★★☆☆｜LVM 的弹性到底体现在哪？它「不保证」什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、垒池切卷：从 pvcreate 到 mount 的创建全链](知识点.md)

### 场景

技术分享会上有人总结「上了 LVM：容量随便扩、数据不会丢、性能也提升了」。三句里两句半是错的，让你当场纠正。

### 完整解答

> 🎯 **一句话**：LVM 只保证容量弹性——不保证冗余、不保证性能、不等于备份。

收束结构（合上书要能默画）：**砖（PV）→ 池（VG，PE 4MB 积木）→ 卷（LV 切片）**；进砖 `vgextend`、拉卷 `lvextend`，扩容不碰已有数据的物理位置——这就是「弹性」的全部含义。三件它不保证的事：

- **不保证冗余**：VG 里坏一块 PV，上面的 LV 一起没——冗余是 RAID/云盘底层的活（Q3）。
- **不保证性能**：LV 的快慢完全取决于脚下那几块盘，LVM 只是记账不加速——性能定责去 [08](../08-磁盘与IO/)。
- **不等于备份**：快照和原卷同 VG 共生死，误删照样全删——备份是另一门课（→ [31](../31-备份与恢复/)）。

> ⚠️ **别混**：「VG 有空闲（VFree）」不等于「LV 有空间」更不等于「df 会变大」——三层三本账：池的账看 `vgs`、卷的账看 `lvs`、文件系统的账看 `df`。扩容工单里最容易空转的就是只看了其中一本。

> 📝 **面试**：把「保证什么/不保证什么」成对说出来：**保证容量弹性（在线扩、拼池、快照冻结），不保证冗余、性能、备份**——成对表述比单说优点可信一个量级。

### 再追问

**快照算不算 LVM 弹性的一部分？**——算「分身」能力：零拷贝冻结一个时刻视图（Q10 深讲），但快照空间也吃 VG 的 VFree——快照越多，池里能切的卷越少，账还是同一本。

## Q7

**★★★★☆｜/etc/fstab 六个字段各是什么？为什么必须用 UUID？nofail 什么时候能加？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [七、落地：挂载与 fstab 持久化](知识点.md)

### 场景

同事按网上模板把 fstab 写成 `/dev/sdb1 /data xfs defaults 0 0`，reboot 后机器卡在紧急模式起不来。有人开始逐行注释试错，有人在群里问「nofail 是不是加上就稳了」。

### 完整解答

> 🎯 **一句话**：六字段：设备/挂载点/类型/选项/dump/fsck顺序；设备写 UUID，改完必须 mount -a 验证再 reboot。

```text
UUID=a3f2c8d1-5b6e-4c7a-9d21-0123456789ab  /data  xfs  defaults,noatime  0  0
# ↑blkid 取，别写 /dev/sdb1               ↑目录   ↑类型 ↑选项            ↑dump ↑fsck顺序
```

逐字段一句：设备（UUID，盘符会漂——Q1 的病根）；挂载点（目录要先建）；类型（xfs/ext4/nfs/swap）；选项（`defaults` 基础套、`noatime` 少写访问时间戳）；dump（现代全 0）；fsck 顺序（根 1、其他 2、0 不检查；xfs 不走这里，坏了用 xfs_repair → [09](../09-文件系统与inode/)）。

reboot 卡紧急模式就是 fstab 里有行挂不上（盘符漂了/设备写错），系统按表等盘等到超时。**救火顺序**：救援模式进去注释掉那行起机，再按 UUID 重写。**预防就一条**：改完 `mount -a`——它把 fstab 里没挂的行都执行一遍，报错当场暴露，此时还没 reboot，改起来零成本。

**nofail 只给可缺的盘**（挂不上也继续起系统，如临时备份盘）；关键存档盘加 nofail = 盘没挂上业务照跑、数据写进空目录——那场「日志丢了」的完整机制在 [09](../09-文件系统与inode/)，关键盘的正确姿势是**不加 nofail**，挂不上就停下报警。

> 📝 **面试**：问 fstab 必答三件：UUID 的理由（盘符不稳）、`mount -a` 验证后才 reboot、nofail 只给可缺盘。能讲出「写错 fstab 进紧急模式怎么救」直接加分（救援模式 → [04](../04-内核与系统/)）。

### 再追问

**swap 怎么写进 fstab？**——`/dev/vg_data/lv_swap swap swap defaults 0 0`：挂载点位置写 `swap`、类型也是 `swap`。swapfile 则设备写 `/swapfile`。swap 大小与 swappiness 的口径 → [07](../07-内存与OOM/)。

**mount -a 通过了，reboot 还会翻车吗？**——极小概率：`_netdev` 类（NFS）在网络未起时仍可能卡，网络盘要加 `_netdev` 或交给 systemd 的 mount unit（→ [11](../11-Systemd与服务管理/)）。本地块设备盘 `mount -a` 通过基本等于稳了。

## Q8

**★★★★★｜在线扩容怎么做？加新盘和云盘原地扩两条路分别敲什么？-r 是干什么的？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [八、长大：在线扩容与 df 不变的两大坑](知识点.md)

### 场景

/data 用到 85% 告警。两种声音：一种「停服迁数据到新盘，稳妥」；另一种「直接扩」。另一个人昨天 lvextend 完关了工单，今天被告警打回来——df 没变。

### 完整解答

> 🎯 **一句话**：扩容链三步——进砖（vgextend/pvresize）→ 拉卷（lvextend -r）→ df 验收，全程不停业务。

**路径 A：加新盘**——新盘成砖入池，再把池里空闲拉给卷：

```bash
pvcreate /dev/vdc                     # ← 新盘成砖（云盘免分区直上）
vgextend vg_data /dev/vdc             # ← 砖入池：vgs 的 VFree 立刻 +500G
lvextend -r -L +200G /dev/vg_data/lv_data
df -h /data                           # ← 400G → 600G，业务全程在写
```

**路径 B：同一块云盘原地扩**——云控制台把盘从 500G 扩到 1T 后：

```bash
echo 1 > /sys/class/block/vdb/device/rescan   # ← 内核重读盘容量
growpart /dev/vdb 1                            # ← 有分区先把分区顶到新边界；免分区跳过
pvresize /dev/vdb1                             # ← PV 认领新空间；免分区直接 pvresize /dev/vdb
lvextend -r -l +100%FREE /dev/vg_data/lv_data # ← 池里新空间全给这个卷
```

**`-r`（--resizefs）= 拉长 LV 的同时自动扩文件系统**。没有它，手动两步等价于：

```bash
lvextend -L +200G /dev/vg_data/lv_data   # ← 只拉 LV
xfs_growfs /data                         # ← xfs 跟【挂载点】
resize2fs /dev/vg_data/lv_data           # ← ext4 跟【设备】
```

那位「df 没变」的同事就是 `-r` 和手动两步**都没做**的那半截——完整病根见 Q9。停服迁移从来不是扩容的选项，那是二十年前分区时代的姿势。

> ⚠️ **别混**：`xfs_growfs` 跟挂载点、`resize2fs` 跟块设备，跟错对象直接报错（这对比 08/09 已立过案）。扩容在线做、缩容不做——方向别记反。

### 再追问

**扩容前看什么？**——`vgs` 的 VFree（池里本来就闲着就直接 lvextend，不用加盘）+ 使用率口径（85% 当故障处理，→ [08](../08-磁盘与IO/)）。

**云盘扩容没生效，rescan 也认不到新容量？**——先确认云控制台那步真的执行了、目标盘没选错；再 `dmesg -T | tail` 看内核有没有 resize 日志。**不要**反复 pvresize——容量没到内核这层，pvresize 无从认领。

## Q9

**★★★★★｜vgextend/lvextend 都执行成功了，df 却一点没变，为什么？**

**覆盖**：核心 · 必会 · 常用 · 常考 ｜ **对应**：知识点 [八、长大：在线扩容与 df 不变的两大坑](知识点.md)

### 场景

扩容工单被打回：`vgextend` 输出成功、`lvextend` 也输出成功，`df -h /data` 还是 400G。有人怀疑「要重启才生效」，有人想再买一块盘「以量取胜」。

### 完整解答

> 🎯 **一句话**：三层账本有一层没接上——不是池没变大，就是卷没拉长，再不就是文件系统没扩；df 只认最后一层。

扩容的真实链路是四段，df 只在第四段才动：

```text
vgextend ──► VFree（vgs）──► lvextend ──► LSize（lvs）──► growfs ──► 容量（df）
               ↑ 坑1卡在这                     ↑ 坑2卡在这（最常见）
```

**坑 1：扩了 VG 忘了 LV**——砖进了池（`vgs` 的 VFree 一大坨），但 LV 还是旧大小（`lvs` 没变）。药：补 `lvextend -r`。**坑 2：扩了 LV 忘了文件系统**——`lvs` 变大了、df 不变。LV 只是块设备的逻辑长度，文件系统 superblock 里登记的「总块数」还是旧的，不 resize 它就只认旧容量。药：补 `xfs_growfs /data`（ext4 补 `resize2fs /dev/…`）。**「再买一块盘」治不了这两坑**——新砖入池只是把坑 1 的 VFree 堆得更高。

> 💡 **打个比方**：VG 是仓库、LV 是货架、文件系统是账本——**坑 1** 是仓库扩了面积没加新货架，**坑 2** 是货架加长了、账本还按旧长度记库存，收银系统（df）当然显示老数字。`lvextend -r` 的价值 = 加货架的同时自动改账本。

> 🔍 **现场**：定位只要一屏：
> ```bash
> vgs vg_data && lvs vg_data && df -h /data
> ```
> VFree 大 → 坑 1；LSize 已变大而 df 未变 → 坑 2；三层数字都变了 df 也变了 → 工单可以真关了。

> 📝 **面试**：先反问「哪一层」再下结论——`vgs` 看 VFree、`lvs` 看 LSize、`df` 看文件系统；答案落在「lvextend 不带 -r 不会自动扩文件系统」上。分层答题，比背一句「要跑 xfs_growfs」高一档。

### 再追问

**为什么 lvextend 默认不动文件系统？**——历史设计：LV 和文件系统是两层独立软件，lvextend 早期只认块层；`-r` 是后来包办的糖。理解了「两层独立」，就理解了为什么任何一层都可能单独「忘」。

**怎么从根上不再踩？**——扩容 SOP 固化成一条命令：`lvextend -r …` + 验收三连（`vgs && lvs && df`），把「拉卷」和「改账本」焊死在一步里，人没有机会忘。

## Q10

**★★★★★｜LVM 快照是什么原理？为什么做了快照之后 df 比 du 大？快照该给多大？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [九、分身：快照原理与 df 不等于 du](知识点.md)

### 场景

备份同事对着 400G 的 lv_data 建了个 20G 快照再备份，业务照跑。一周后 DBA 问：/data 没删过东西，df 显示的占用却比 du 算出来的多 15G，怀疑「空间泄漏」准备重启机器。

### 完整解答

> 🎯 **一句话**：快照是写时复制——改块前先把旧块搬进快照空间，旧块不释放，df 和 du 从此对不上。

**COW（Copy-on-Write，写时复制）** 三步：创建快照**零拷贝**（几秒完成，不管 LV 多大）→ 业务每次「首次改某块」，先把旧块复制进快照空间 → 再写新块进原卷。读快照时：被改过的块读快照区里的旧版本，没改过的直接读原卷——于是快照永远呈现「拍照那一瞬」。

**df 比 du 大的机制**：快照存在期间，被改写数据块的**旧版本不能释放**——文件系统实际占用的块（df 视角）= 现在的文件 + 快照区里的旧块；而 `du` 顺着目录树只算得出前者。多出来的 15G ≈ 快照 Data% 吃掉的空间，**不是泄漏，重启也消不掉**，删快照（`lvremove`）立即归还。

**快照多大**：取决于快照存活期间的**写入量**，不是 LV 大小——短窗口备份给源 LV 的 10%~20% 是经验起点；`lvs` 的 **Data%** 顶到 100% 快照**失效**（invalid），不是安静躺平，要监控、用完即删。

> 🔍 **现场**：
> ```bash
> lvs
> ```
> ```text
>   LV           VG      Attr       LSize  Origin  Data%
>   lv_data      vg_data owi-aos---- 400.00g
>   lv_data_snap vg_data swi-a-s----  20.00g lv_data  8.42
>   # ↑ Attr 的 s = snapshot；Data% 就是快照空间被旧块吃掉的比例
> ```

> ⚠️ **别混**：快照**不是备份**——它和原卷在同一个 VG 里，盘坏了两个一起没；它是「备份进行时的冻结点」和「改坏前的后悔药」。真备份要落到别的介质（→ [31](../31-备份与恢复/)）。云厂商快照是存储层的另一套东西，别和 LVM 快照混着谈（→ [33](../33-高可用与容灾/)）。

> 📝 **面试**：这条是 [09](../09-文件系统与inode/)「df ≠ du」里快照那条的机制源头——把「COW 持有旧块、删快照即归还、大小看写入量」三句连着说，比单背「df 会变大」高一档。

### 再追问

**为什么说快照是备份的好搭档？**——不快照直接备份，备份期间业务还在写，备份文件是「几分钟跨度里不同时刻的拼盘」，数据库恢复出来可能不一致；先快照（瞬时冻结）再对着快照慢慢备，业务零感知、数据一致。

**Data% 涨太快怎么办？**——说明原卷写入凶而快照给小了：要么尽快完成备份删快照，要么 `lvextend -L +20G` 给快照卷本身扩容（快照也是 LV，可以扩）。**不要**放任它到 100%。

## Q11

**★★★☆☆｜XFS 能缩容吗？ext4 缩容要注意什么？swap 要用分区还是文件？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [十、退场：缩容、umount 忙与安全下线](知识点.md)

### 场景

另一台机器 /data 给了 600G 只用 100G，想把 400G 挪给新的日志卷。有人提议 `lvreduce -L -400G` 一把缩掉，被老值班按住了。

### 完整解答

> 🎯 **一句话**：XFS 根本不支持缩容；ext4 缩容要 umount 且必须先缩文件系统再缩 LV；生产口径是不缩、迁移重建。

**XFS 只扩不缩**是设计决定：元数据结构不支持收缩，唯一路径是「备份 → 删 LV 重建小卷 → 恢复」。**ext4** 技术上可缩，但顺序严苛：umount → `resize2fs` 先把文件系统缩到目标 → `lvreduce` 再把 LV 缩到同一目标——**顺序反了 = 直接从文件系统尾部截断数据**，lvreduce 可不会先问文件系统。这就是老值班按住那把 `lvreduce` 的原因：这个卷是 XFS，命令根本走不通；就算 ext4，在线裸缩也是拿生产数据练手。

要「腾容量」的正路：VG 里另切一个新 LV，数据迁过去，删旧 LV——VFree 回到池里，谁也不用截断谁。

**swap 一句**：做成 LV（`lvcreate -L 8G -n lv_swap vg_data && mkswap && swapon`，fstab 挂载点写 swap）或 swapfile（`fallocate -l 4G /swapfile && chmod 600 && mkswap && swapon`）都行，swapfile 不用动分区表，云上更常用；大小与 swappiness 的口径 → [07](../07-内存与OOM/)。

> ⚠️ **别混**：缩容方向「先 FS 后 LV」，扩容方向「先 LV 后 FS」——正好相反，因为扩是「下面先有空间上面才能长」，缩是「上面先退回去下面才能收」。把两个方向记串就是事故。

### 再追问

**lvreduce 有没有安全姿势？**——有但仍危险：ext4 缩到目标后，`lvreduce -L 200G`（写**目标值**，不写 -200G 减量），并在提示确认时逐字核对。即便如此，生产上仍应优先迁移重建——lvreduce 的确认键按错没有撤销。

**swapfile 为什么要 chmod 600？**——全局可读的 swapfile 是安全漏洞（任何本机进程可读内存换出的内容），mkswap 也会警告。另外 xfs 上 fallocate 可能留空洞，用 `dd` 建更稳。

## Q12

**★★★★☆｜umount 报 target is busy，怎么定位、怎么处理？umount -l 为什么不行？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [十、退场：缩容、umount 忙与安全下线](知识点.md)

### 场景

夜里要下线一块旧数据盘，`umount /data` 报 busy。值班同事 `umount -l` 强行懒卸载后关了工单，第二天发现备份任务还在往「已经卸载的盘」写数据，写丢了一晚上。

### 完整解答

> 🎯 **一句话**：busy 是有进程占着挂载点——fuser -vm 看字母定位，c 是 cwd、f 是打开的文件；umount -l 是糊弄不是解决。

> 🔍 **现场**：
> ```bash
> umount /data
> # umount: /data: target is busy.
> fuser -vm /data
> ```
> ```text
> USER        PID ACCESS COMMAND
> root      12847 ..c.. game-serv      # ← c = cwd：进程工作目录钉在 /data 下
> root      28451 f.... tar            # ← f = 打开着文件：备份正写到这个挂载点
> ```

处理按字母来：**c** = 挪——让进程（或你自己的 shell）`cd` 出去再 umount，最常见的 busy 其实就是操作者自己站在目录里；**f** = 停——找到占用的任务（本例的 tar）协调停止或等它跑完，`lsof +D /data` 能列出目录树里被打开的文件清单。**任何一步都不包括 kill 业务进程**——信号语义与「kill -9 对 D 进程无效」→ [05](../05-进程与信号/)。

**umount -l（lazy，懒卸载）的问题**：它让挂载点从命名空间里「看起来卸了」，但**占用的进程还握着旧句柄继续写**——数据写进一个再也无法通过挂载点访问的旧引用里。本例一晚备份全丢，就是 -l 把「占用未解决」这个事实藏起来的代价。busy 的正解永远是「解决占用」，不是「让报错消失」。

> 📝 **面试**：「umount busy 三连」——`fuser -vm`（谁、什么类型的占用）→ `lsof +D`（具体哪个文件）→ 解决占用后重试；结尾补一句「不用 umount -l，它让占用进程继续写旧句柄」，这一句就是区分背题和踩过坑的标记。

### 再追问

**安全下线一块数据盘的完整顺序？**——倒着走施工链：**停写入（业务/定时任务）→ umount → 注释 fstab 那行 → lvremove/vgreduce → pvremove**。先 umount 再动 fstab——顺序反了，下次 reboot 直接进紧急模式（→ [04](../04-内核与系统/)）。

**lsof +D 为什么慢？**——它递归 walk 整个目录树，百万文件的目录要跑很久；所以先用 `fuser -vm`（按挂载点查，瞬时）拿到 PID，再 `lsof -p <PID>` 精查，别一上来就 +D。

## Q13

**★★★★☆｜值班 60 秒：一条「/data 要扩容」的工单，你怎么走？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [十一、作战：加盘扩容定责](知识点.md)

### 场景

周一早上告警：三台逻辑服 /data 全到 86%。工单只有一句「扩容」。还有一条背景：上周有人扩过其中一台，今天告警里它的 df 显示还是旧容量。

### 完整解答

> 🎯 **一句话**：先看三层账本定砖从哪来，再走 lvextend -r 一条链，最后 df 验收——顺序错了就是白干。

```text
① 0–10s   lsblk + df -h /data        ← 对上设备树和水位：是 LV 吗、还差多少
② 10–30s  pvs && vgs && lvs          ← 三层账本：池里有没有 VFree（有就直接拉卷，不用买盘）
③ 30–45s  补缺的一步：
            有 VFree / 加了新盘 → lvextend -r -L +N（一步到位）
            lvs 已变大 df 没变（上周那台）→ 补 xfs_growfs /data
④ 45–60s  验收 + 收尾：df -h 数字真的变了；
          新做的挂载走 fstab(UUID) + mount -a；
          「慢」的诉求转 08 iostat，别在这单里硬抠
```

上周那台是**坑 2**（扩了 LV 忘了文件系统）的标准签名：`lvs` 大、`df` 旧——30 秒内 `xfs_growfs /data` 收工，**不需要**再买盘。三台的口径统一成 SOP：`lvextend -r` + `vgs && lvs && df` 验收三连，把「拉卷」和「改账本」焊死在一步里。

> ⚠️ **别混**：这单里最容易走错的两步——VFree 明明有却去申请新盘（多花钱多干活）；df 不变却反复 vgextend「以量取胜」（把坑 1 的 VFree 堆得更高，df 依然不动）。

### 再追问

**如果告警不是「满」而是「慢」呢？**——换战场：await/aqu-sz/Dirty 是 [08](../08-磁盘与IO/) 的定责链，LVM 只管容量形状。**不要**在这单里顺手「扩容解决慢」——空间和 IOPS 是两个维度。

**扩容后要不要顺手做快照？**——扩容本身是低风险操作，不需要；但**大变更前**（数据库升级、批量 DDL）建快照当后悔药是好习惯——记得删（Q10 的 df≠du 就是被遗忘的快照）。

## Q14

**★★★★★｜白板：裸盘一生 + PV/VG/LV + 扩容两坑 + 与 08/09 分界？**

白板：「从 lsblk 到 mount，画 LVM 主线并说 df 不变两大坑。」

```text
慢→08  满/inode→09  权限→25
```
