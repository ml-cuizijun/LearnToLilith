## 1. 能力模型与定级

## Q1：考官凭什么把你定在高级而不是中级？

**★★★★★**

**场景**  
总监问：「你觉得自己现在是哪一级？」有人答「我干了 8 年，应该是高级」。工龄被当成证据。

**完整解答**

按四维证据定级，不按工龄。只过技术题只说明会干活。没有数字、主语是「我们」、有状态战斗服讲成随便滚，都会压级。

```
                 7-10 年游戏运维 / SRE
                           |
                           v
              +---- 四维证据是否齐 ----+
              | 稳定性 容量 工程化 故障指挥 |
              +-----------+------------+
                          |
         +----------------+----------------+
         |                |                |
         v                v                v
  四维都有 Owner     只会救火/无数字     工龄 10 年仍扛自己几台
  一条业务能独立扛   主语「我们」         无标准复用、无演练
         |                |                |
         v                v                v
  高级 band          压成中级            停滞，65 万都紧
  65-75 万可谈       年包按下沿
```

四维最低证据：

1. **稳定性**：登录 / 掉线 / 支付 SLO，以及错误预算（或等价门禁）怎么停发布。不是「我们有 Prometheus」。
2. **容量**：CCU 口径、分层水位、活动前扩什么、现场不能扩什么。
3. **工程化**：别人在用的流水线——开服/发布失败能停、能回滚到确定版本。笔记本里的脚本不算。
4. **故障领导力**：war room 里选止血动作、对外同步、复盘 action 有人和截止日期。只讲「定位到 Redis 然后重启」停在执行层。

阿里还要看变更能不能冻结；字节看数字和复杂度；腾讯/游戏厂看开服、热更、活动。P6/2-1/T9 最低线：一条业务的稳定性和容量你能独立扛。10 年如果还在讲重启，不如 6 年能讲清 SLO 和一次 war room 决策。

**再追问：你四维里最弱的是哪维？怎么补？**  
对照缺口说现有证据，例如容量模型有、跨业务规范还没有。补法要具体（连续测 2 周核心 SLI、把一次活动扩容写成口径），不要说「我肯定高级」。

## Q2：游戏厂和字节/阿里定级差异是什么？

**★★★★★**

**场景**  
K8s + Argo 讲得很顺。游戏厂对方问：「战斗服滚动时探针怎么配？开放目录是不是流水线最后一步？」答成和 Web 一样。

**完整解答**

互联网厂认集群、容量、可观测的 impact。游戏厂必须再认开合服门禁、热更回滚、活动时有状态扩什么不能扩什么。缺后者，按「会容器的 Web 运维」定级。

```
  同一套 GitOps / K8s
           |
           +--> 阿里：变更可审计、冻结发布、容量模型、窗口纪律
           +--> 字节：告警有效率、水位、MTTR、多集群复杂度
           +--> 腾讯：海量或游戏 BG，发布与故障闭环
           +--> 游戏厂：开合服、热更、活动高峰、有状态门禁
                      缺这些 = 中级 Web 运维，K8s 再熟也压级
```

同一套 GitOps，互联网厂听变更故障率、谁有权 sync。游戏厂会追：开放目录是不是最后开关、合服失败为什么不能反向再迁、liveness 会不会集体踢战斗服、活动现场能不能扩逻辑服。投谁就把谁的证据放项目深挖第一题。

**再追问：只有 Web 业务经验投游戏 SRE 怎么办？**  
诚实讲边界：无状态、发布、容量你能扛到哪；游戏约束（有状态、开服开关、热更）准备用同类原则怎么做，并点名你缺哪块生产经历。不要把电商大促直接说成开服 Owner。

## Q3：「我处理过很多故障」为什么不够高级？

**★★★★★**

**场景**  
复盘会上你讲「我处理过很多故障，这次定位到 Redis 连接池然后重启」。对方问：下次你不在场呢？

**完整解答**

次数不是领导力。救火英雄是第一个发现问题、靠熟练重启恢复。高级看你是否选择止血动作、对外同步、把 action 变成门禁或演练，下次不靠你在场。

```
  发现 --> 影响面（区服 / CCU / 支付）
       --> 止血（回滚/切流/降级，谁有权）
       --> 对外（群时间线、运营公告口径）
       --> 根因（技术 + 流程）
       --> action（有人、有截止日期）
```

高级口述要能补：为什么先止血不先查代码、谁有权回滚、5 分钟内有没有拉群。指挥过 3 人以上、和运营对过玩家公告、复盘里有你签字的改进项，才像 7–10 年。只讲定位到 Redis 然后重启，停在执行层。

**再追问：根因是别人的变更，你的 Owner 怎么体现？**  
如实讲协作：你负责止血、时间线和推动复盘；根因归「变更未灰度」，不点名羞辱，也不把别人的设计说成自己的。Owner 体现在决策和落地，不体现在抢归因。

## Q4：容量和稳定性你各准备哪一条证据上定级对话？

**★★★★★**

**场景**  
「我们有监控，大促会加机器。」对方皱眉，开始追 SLO 口径和 CCU 模型。

**完整解答**

两条都要有数字。稳定性：登录/掉线/支付 SLO + 一次错误预算停发布或等价门禁。容量：CCU 模型 + 活动前扩了什么、现场不能扩什么。

```
  稳定性证据                         容量证据
  登录 / 掉线 / 支付 分 SLI          先定口径：CCU ≠ DAU ≠ 注册
  窗口 + 灰度 + 预算耗尽冻结         按层建模：网关 / 大厅 / 逻辑 / DB
  叫醒：登录跌破、支付失败、         能扩：网关/大厅（活动前做完）
        CCU 腰斩、开服验收失败       不能扩：逻辑服 --> 排队/分服/降级
  没有正式 SLO --> 自建 SLI          压测：登录洪峰 ≠ 平稳在线
  和叫醒规则，不要假装有错误预算     活动前 1.2× 找第一瓶颈
```

没有正式 SLO 就讲自建 SLI 和叫醒规则，不要假装有错误预算。容量口径不要把注册和 CCU 混用。压测要对齐登录洪峰。阿里追全链路压测；字节追你用哪个水位决策；游戏厂追活动前你提前扩了什么。

**再追问：从来没做过全链路压测怎么说？**  
承认范围：做过登录脉冲或单层压测就讲那一层的第一瓶颈和结论。没做过就不要写「全链路压测 Owner」，改讲活动前的水位检查和现场不能扩逻辑服的纪律。

## Q5：技术题怎样答才不像 3 年？

**★★★★**

**场景**  
「登录 P99 从 200ms 到 2s。」有人一上来 `kubectl top` 和重启战斗服。答题停在命令。

**完整解答**

技术题用六段，停在命令会被判中级：

```
  原理 --> 生产现象（带规模）--> 看哪个指标/日志
       --> 止血 --> 根因 --> 治理（防复发）
```

以登录延迟为例：

1. **原理**：登录 = 排队 + 鉴权 + 目录 + 逻辑服分配 + 下游。延迟升、错误率未升，先看下游和排队，不是先重启战斗服。
2. **现象带规模**：哪几个区、峰值 CCU、持续多久、是否刚发版/热更。
3. **指标**：RED、网关耗时、Redis/DB、逻辑服人数、目录健康。
4. **止血**：限流/排队放缓、扩无状态、熔断慢下游。**不先重启有状态战斗服。**
5. **根因**：例如连接池或目录未扩、新 key 无 TTL。
6. **治理**：水位告警、开服/活动前容量检查、runbook 改顺序。

没有生产数字就用可公开量级，并声明假设。没有规模的「我 top 了一下」像 3 年。

**再追问：止血和根因调查怎么并行？**  
war room 拆两人：一人执行已授权的止血（回滚/切流/限流），一人拉变更单和慢查询。先恢复业务，根因放到影响面稳住之后；现场抠代码、不回滚，会被问「当时为什么不回」。

## Q6：7 年被压成中级 band，最常见的三句话是什么？

**★★★★**

**场景**  
HR 回来说「职级按中级，年包到不了 65」。技术轮其实过了。

**完整解答**

三句分别缺 Owner、深度、领导力：

| 原话 | 缺什么 | 改成 |
|------|--------|------|
| 「我们团队做了监控平台。」 | Owner | 我负责哪一截、规模数字、别人是否在用 |
| 「K8s 我都熟悉。」 | 深度 | 集群数、有状态怎么滚、一次失败 |
| 「故障我重启就好了。」 | 领导力 | 选了哪个止血、复盘留下什么机制 |

```
  技术轮炫架构  +  深挖讲不清自己改过哪段配置  --> 包装
  定级骂前司 / 规划与 JD 无关                 --> 材料作废
```

改法：主语「我」、规模数字、一次失败、留下什么机制。简历删不会的。对话里不要骂前司。答题停在命令、游戏履历讲成可随意滚动的 Web、事故里自己毫无责任，都会把 7 年压成中级。

**再追问：你简历上哪句最像这三句，准备怎么改？**  
当场点名一句真实弱 bullet，改成动词 + 技术 + 规模 + 数字。不要说「简历没有问题」。

## 2. 简历与项目深挖

## Q7：2 分钟讲开服或从 0 到 1 的运维体系。

**★★★★★**

**场景**  
开场：「做个自我介绍，重点讲一个项目。」有人从入职第一年讲到现在，超时还没数字，也没说对玩家可见的开关是哪一步。

**完整解答**

选开服。规模（区服/CCU）→ 痛点数字 → 你的门禁设计 → 失败怎么拆 → 两个结果数字。超时砍背景，留动作和数字。

```
  规模+痛点 --> 你的目标 --> 2-4 个动作（含 rejected）--> 两个数字

  预检（镜像钉死 / 配额 / server_id 未占用）
    --> 数据面（建库、静态表、Redis 默认关活动）
    --> 服务面（Gate/大厅/逻辑，尚未进目录）
    --> 验收（登录冒烟、支付沙箱、核心 RPC）
    --> 唯一开关：写服列表（建议人工确认）
  验收失败 --> 拆除 job，禁止半成品挂出去
```

口述骨架（数字换成你的）：N 个区服、日均开 M 服，手工复制环境，失败残留脏 server_id。我负责把开服做成可停可回滚的流水线：预检阻断；数据面和服务面分段，未挂目录前玩家不可见；验收失败整服拆掉不开放。淘汰「复制一台模板再改配置」。结果：单服耗时 X→Y，脏环境从 A 次/月到 0。合服不要混进开服故事：合服失败走备份恢复。

**再追问：开放给玩家的开关具体是哪一步？失败谁有权停？**  
目录写入是唯一对玩家开关，建议独立审批。验收失败流水线必须停，Owner 有权不开放；运营催着开也不能修脏环境凑合挂出去。

## Q8：把一个项目按五层追问过一遍（现场选你简历上的）。

**★★★★★**

**场景**  
对方顺着简历一条 bullet 往下挖。L1 数字很漂亮，L3 说不出流水线阶段名。

**完整解答**

答完一层停，让对方决定往哪钻。L3 说不出细节，L1 的数字作废。L5 禁止「没什么要改」。只深挖 2–3 个真主导过的，模板填 02/03/04/05/07。

```
  L1 电梯版：规模 + 职责 + 1 个结果数字
  L2 rejected：为什么不复制模板机 / 不自动跑完
  L3 亲手：阶段名、镜像禁 latest、拆除 job、命令
  L4 一次失败：漏预检 --> 阻断开放、拆环境、补项
  L5 重来和 ×10：目录做成唯一开关；按大区拆 worker
```

开服五层口述（数字改成你的）：

1. **L1**：日开 N 服，我做流水线 Owner，单服 X→Y 分钟，脏环境从每月 A 到 0。
2. **L2**：不用复制模板——残留 server_id 和配置漂移清不干净；不用一套大流水线自动跑完——失败会把半成品挂到目录。
3. **L3**：五段门禁；镜像禁 latest；验收没过不写服列表；失败走拆除 job，不手删。
4. **L4**：一次预检漏了 Redis 规格，验收登录超时；阻断开放、拆环境、补预检项，当天改用备份窗口重开。
5. **L5**：重来会把「目录写入」做成唯一开关并加人工确认；规模 ×10 按大区拆流水线 worker，不要一条 Jenkins 打全球。

**再追问：现场写一条当时的命令或 PromQL。**  
准备真的：开服 job 失败退出码、`kubectl describe` 事件、Argo sync policy、燃烧率 PromQL。编的命令会在下一问穿。

## Q9：这个百分比/MTTR 怎么统计的？

**★★★★★**

**场景**  
简历写「变更故障 40%→12%，MTTR 从 47 分钟降到 8 分钟」。对方问分母。说不出，开始改口。

**完整解答**

说清窗口、分母、标签、发现到恢复还是告警到恢复。口径不一致就改成量级表述。编 47 分钟这种假精确必穿。

```
  数字从哪来
     |
     +--> 故障复盘表 / 发布单 / 监控月报 / on-call 记录
     +--> 同一口径前后对比（改造前 12 个月 vs 后 6 个月）
     +--> 说不清算法 --> 「四十分钟级到十分钟内」+ 定义
```

示例口径：「按 P0/P1 复盘标签，变更类包括配置错误、未灰度、requests 设错。改造前 12 个月 25 起 P1+ 里 10 起变更相关≈40%；上线后 6 个月 17 起里 2 起≈12%。」主动承认还有审批、演练等并行因素，流水线是主因之一。MTTR 先定义：发现到恢复，还是告警到恢复，是否含等开发。口径变了就不要和简历混用。

**再追问：除了你的项目，还有什么同时让故障下降了？**  
承认并行因素：审批加严、演练、人员变动。把你的模块讲成主因之一，不要把全集群变好都写成个人功劳。

## Q10：简历写了 K8s 网络 / Kafka / AWS，你能讲到哪？

**★★★★**

**场景**  
简历「精通 K8s 网络 / Kafka / AWS」。对方开始问 CNI、再均衡、IRSA。实际只会 apply、看 lag、开 EC2。

**完整解答**

写了就要到 L3。只能 apply / 只会看 lag / 只会开 EC2，这些词删掉或降成「用过」。

| 写了 | 会被问到 | 不会就删或降级 |
|------|---------|----------------|
| K8s 网络 | CNI、Service 空 Endpoints、CoreDNS ndots | 只会 apply → 删「精通 K8s 网络」 |
| Kafka | 积压、再均衡、重复消费 | 只用过积压告警 → 写「用过，处理过 lag」 |
| AWS | VPC / NLB / IAM / IRSA | 只会开 EC2 → 不要写「熟悉 AWS 网络」 |

技能分档：**熟练**（生产 Owner）/ **使用**（跟过项目）/ 不写。ATS 可以对齐 JD 关键词，但对齐的必须是你真做过的。现场被问倒：承认边界，给推理和下一步，把话题拉回你扛过的开服或告警。编「我们用 Cilium Hubble 排过」而实际没有，下一层命令就死。

**再追问：为什么投递时要对齐 JD 关键词？**  
筛过但深挖穿更亏。用真实做过的 CNI/Service/排障词对齐 JD，比假词安全。已经投出的版本误写了，深挖开场主动收口，比被问 Hubble 再编强。

## Q11：主导和参与怎么向考官证明？

**★★★★**

**场景**  
团队 8 个人简历都写了主导同一平台。对方怀疑夸大。

**完整解答**

方案你定、落地你推、结果你复盘 = 主导。模块或执行 = 参与。当场展开 L3，并指出同事模块。8 个人不能都写主导整个平台。背调口径要和自述一致。

```
  平台（监控 + 开服 + GitOps）
       |
       +-- 你：开服五段门禁、拆除 job、失败可停
       +-- 同事 A：采集 / Helm chart
       +-- 同事 B：权限和节点池
  不要写成「从 0 到 1 全是我」
```

GitOps：架构和 Argo 你调、培训你组织、指标你盯，Helm 同事写，可以说协作但不把 Owner 让掉。团队人数、你写过哪段流水线，如实答。把全组平台写成个人从 0 到 1，L3 一问就穿。拆：你开服门禁，他采集。

**再追问：你经理会怎么评价你在这个项目里的角色？**  
用经理会认的模块边界说：门禁和回滚是我 Owner，采集不是。口径和背调一致，比争「整个项目都是我」安全。

## Q12：游戏经历如何用 SRE 词重组且不假？

**★★★★**

**场景**  
JD 要 SLO、GitOps。真实工作是手工开服和 Jenkins。有人写成「落地了错误预算驱动发布」，实际从未冻结过发布。

**完整解答**

用稳定性/变更/容量/回滚重组真实工作，不发明项目。没做过的词不写。

```
  手工开服     --> 分段门禁 + 失败拆除（可停流水线）
  Jenkins 发版 --> 制品不可变 + 灰度 + 回滚 RTO
  加机器过活动 --> 能扩的层 vs 排队（扩容边界）
  改库救数据   --> 禁止直接改库，走回档审批
```

互联网厂听得懂 GitOps、SLO；游戏厂还要听懂有状态、开合服、热更、活动、回档。没有错误预算就不要写「用错误预算停发布」。有登录成功率和掉线告警，就如实讲自建 SLI。关键词给 JD 可以，每个词后面要有你做过的动作。

**再追问：合服你是 Owner 还是当晚值班？**  
能讲停写、双备份、映射冲突、失败恢复备份而不是反向再迁——再写进简历。只会「跟过一次合服当晚值班」就不要写主导合服。

## Q13：经历碎、没有明星项目，项目深挖怎么打？

**★★★**

**场景**  
换过几条业务线，每段都是救火和脚本，没有从 0 到 1 的平台。有人按时间流水报 10 个浅需求。

**完整解答**

按稳定性/工程化/规模三条线聚合，只深挖一个最有发言权的故障或流水线。10 个浅需求没有记忆点。禁止把别人的平台拼成自己的从 0 到 1。小而完整的自动化可以作加分，不抢主线。

```
  碎经历
     |
     +--> 稳定性线：几次故障闭环（发现→止血→治理）
     +--> 工程化线：脚本/流水线总人天、别人是否在用
     +--> 规模线：区服/机器加总
     |
     v
  答题只深挖 1 个你最有发言权的点（L1-L5）
```

仍要动词+数字。没有 SLO 就讲自建指标和告警治理。换工作频繁用发展叙述，不抱怨。空间不够就砍早期无关经历，不要缩小字号塞两页。

**再追问：你还做过什么没写在简历上？**  
准备 1 个小而完整、和岗位相关的（ChatOps、巡检自动化）。不主动展开 GPU/LLM，除非对方岗需要。

## Q14：设计开服系统（每天 N 服，失败可回滚）。

**★★★★★**

**场景**  
「画一个每天能开 5 个新区的系统。」有人直接画 Jenkins 连 K8s，没有对玩家开关，失败继续跑完并已进目录。

**完整解答**

开口先问：每天几服、单服目标 CCU、对玩家可见的开关是哪个、失败 RTO、镜像是否钉死。假设写在角上：「按日开 5 服、单服峰值 CCU 8000、开服失败玩家不可见来设计。」

```
  运营/GM 点击开服（server_id, 规格, 开服窗口）
                    |
                    v
  +------------- 流水线（失败即停）---------------+
  |  1 预检                                          |
  |     镜像 tag 钉死（禁 latest）                     |
  |     配额 / 节点池 / Redis 规格                      |
  |     server_id 未占用                               |
  |     中心服 / 目录 / 支付沙箱健康                     |
  |                    |                             |
  |                    v                             |
  |  2 数据面                                          |
  |     按 server_id 建库 + 静态表                      |
  |     Redis 默认关活动开关                            |
  |     备份策略挂上                                   |
  |                    |                             |
  |                    v                             |
  |  3 服务面（尚未挂公网目录）                          |
  |     Gate / 大厅 / 逻辑服                            |
  |     只对内网探活                                   |
  |                    |                             |
  |                    v                             |
  |  4 验收                                            |
  |     登录冒烟 / 付费沙箱 / 核心 RPC                   |
  |     失败 --> 拆除 job，禁止修脏环境凑合开             |
  |                    |                             |
  |                    v                             |
  |  5 唯一开放开关                                     |
  |     写入服列表 / 目录  （建议人工确认）               |
  |     此后玩家可见                                   |
  +--------------------------------------------------+
```

SRE 必讲：每段失败阻断，不要流水线吞错继续；开放目录是最后一步；回滚是拆脏环境，不是对玩家「再试一次」。合服不要和开服混：合服失败是恢复备份，禁止反向再迁。

**再追问：某步失败却继续跑完并已进目录，怎么收场？**  
这是事故。立刻从目录摘掉（玩家不可见），拆除脏环境，补门禁和告警。目录写入做成独立审批。当天用干净环境重开，不修半成品凑合开。

## Q15：游戏 SLO 和半夜叫醒标准怎么定？

**★★★★★**

**场景**  
「给我们游戏做一套监控。」有人只画 Prometheus + Grafana，SLO 写 HTTP 99.9%，半夜单机 CPU 90% 也打电话。没有玩家投诉、只有内部指标跌，不知道叫不叫。

**完整解答**

先问协议类型（长连接还是 HTTP）、谁 on-call、保留多久。游戏 SLI 不要只套「HTTP 99.9%」：登录成功率、进战斗/核心协议成功率、掉线率、支付成功率、CCU 10 分钟腰斩。单机 CPU 不叫醒。

```
  游戏服 / 网关 / Redis / MySQL
       |              |           |
   exporter      业务埋点      日志（登录失败码）
       |              |           |
       v              v           v
  +-------- Prometheus 分片（按大区/集群）--------+
  |  高基数禁止 user_id；scrape 超时可见            |
  +-------------------+--------------------------+
                      |
          +-----------+------------+
          |                        |
          v                        v
   长期存储 VM/Thanos         Alertmanager
   （按团队能力选，            分组 / 抑制 / 静默
    淘汰单实例扛全站）              |
                                   v
                            电话 / IM / 升级
                                   |
                                   v
                    Grafana：SLO 燃烧率 + 开服/活动大盘
                    Meta：采集 up、remote write 延迟
```

叫醒：登录跌破 SLO、支付失败、CCU 腰斩、开服验收失败。不叫醒：单机 CPU、已抑制的上游连锁。依赖链：下游库挂抑制上游全员告警，核心路径不误抑制。错误预算烧完停非关键变更。CCU 腰斩但 CPU 正常仍按业务故障处理（登录、网关连接、目录、发版、热更）。Rejected：单实例 Prometheus 扛所有 series；无分级的全量告警。

**再追问：没有玩家投诉、只有内部指标跌，叫不叫？**  
叫。内部 SLI 跌破叫醒线就是 P0 候选，等投诉再叫已经晚了。这正是必须有业务 SLI 的原因。先看登录/支付/CCU，再决定是否升级。

## Q16：峰值 CCU 容量怎么做？现场超了怎么办？

**★★★★★**

**场景**  
运营给了「注册破百万」。有人按注册数给逻辑服做 HPA。活动当晚 CCU 超模型，有人要现场加战斗服副本。

**完整解答**

先定 CCU 口径，分层建模，压测分登录脉冲和平稳在线。注册百万但 CCU 不高，瓶颈往往在登录洪峰和账号/目录，不在逻辑服人数上限。现场超模型：扩无状态、收紧排队，不指望逻辑服立刻接人。

```
  目标峰值 CCU
       |
       v
  × 单玩家资源（CPU / 连接 / Redis QPS / DB QPS）
       |
       v
  +---- 按层拆水位（先满的那一层告警）----+
  |  网关：连接数、新登录 QPS              |
  |  大厅：无状态，可 HPA                  |
  |  逻辑/战斗：人数上限，不能按 CPU 乱扩   |
  |  Redis / MySQL：连接与热点             |
  +------------------+---------------------+
                     |
         +-----------+-----------+
         |                       |
         v                       v
   能水平扩：扩网关/大厅     不能扩：排队 / 分服 / 降级
   活动前做完                现场不要扩逻辑服指望立刻接人

  压测：登录脉冲 与 平稳 CCU 分开打，打到 1.2× 找第一瓶颈
  活动前：freeze 非必要发布；预热 CDN；扩无状态
```

有状态服扩容不自动接人：要讲踢人、迁移 Session、还是只扩无状态接入。成本翻倍则分层 SLO，非核心降级。逻辑服扩容是窗口内、活动前的事。

**再追问：注册百万但 CCU 不高，容量瓶颈会在哪？**  
登录脉冲、账号服、目录、排队网关、支付。按注册给逻辑服做 HPA 是错口径。先把登录路径压到 1.2×，看哪一层先满。

## Q17：发布：灰度、热更、强更、一键回滚。

**★★★★★**

**场景**  
「我们要一键回滚。」有人说 Git revert。战斗服用 Web 的 liveness。配表热更发错准备改库。强更后旧客户端还要玩。

**完整解答**

先问是否改协议、是否踢在线、日发布次数、回滚 RTO、DB schema 是否同发。不可变制品；灰度门禁失败回上一版。

```
  Git（主分支，禁止直接改生产）
       |
       v
  CI：构建 / 单测 / 镜像扫描（失败不打 prod tag）
       |
       v
  不可变制品  registry/app:<gitsha>
       |
       v
  预发  -->  冒烟（登录/支付沙箱）
       |
       v
  灰度：按区服 或 玩家比例（金丝雀 label）
       |
       +-- 门禁：错误率 / 掉线 / 登录 相对 baseline
       |         金丝雀取数，不用集群均值
       |
       +-- 失败 --> 一键回滚到上一制品（分钟级 RTO，演练过）
       |
       v
  全量（错误预算耗尽则冻结 promote）

  游戏约束：
    热更失败能停；配表当制品版本化，禁现场改库
    强更兼容旧客户端（双协议或双目录）
    战斗服滚动：liveness 不能按 Web 套，PDB + 分区
    DB：expand-contract，禁止破坏性 DDL 和代码同发
```

Git revert 或 rollout undo 要演练过才敢称一键回滚。热更发错配表：回上一份制品；必要时关活动开关。不要现场改库「修数据」。

**再追问：强更后旧客户端还要玩怎么办？**  
强更窗口内双协议或双目录：旧包走旧逻辑/旧资源版本，新包走新版本；目录按客户端版本分流。不能强更完立刻拆旧入口。兼容期有截止日期，到期再下线旧协议。

## Q18：K8s 升级，战斗服不能集体掉线。

**★★★★★**

**场景**  
「集群要滚动升级。」有人 drain 全节点，PDB 被删掉赶时间。有人问调度器挂了在线战斗会怎样，答「集群全死了」。

**完整解答**

先问战斗服是否在集群、能否停服、多 AZ 与否、etcd 谁运维。PDB、分区滚动、先无状态后有状态。etcd 有备份演练。

```
  AZ-a                AZ-b                AZ-c
  API+etcd            API+etcd            API+etcd
         \               |               /
                    多数派 = 3 或 5（偶数不要）

  工作负载：
    大厅/网关：Deployment + HPA + PDB + topologySpread
    战斗/逻辑：有状态，分区滚动，先非战斗后战斗
    liveness 过激 --> 集体重启踢人（Rejected）

  升级顺序：
    控制面 --> 无状态 --> 有状态（战斗单独窗口）
    drain 前看 PDB；禁止为赶时间删 PDB

  控制面挂：已有 Pod 仍跑，无法变更
  etcd 挂：失忆，靠备份演练
  调度器挂：新 Pod Pending；已有战斗长连接通常还在
```

控制面挂不影响已有 Pod；etcd 挂靠备份；drain 被 PDB 拦住时禁止删 PDB 赶工。按大区拆集群，禁止一个大集群塞所有大区。发布走 GitOps。生产 `kubectl edit` 不当发布。

**再追问：调度器挂了，在线战斗会怎样？**  
已运行的战斗服进程还在，长连接通常不立刻断。新 Pod 一直 Pending，扩容/自愈/发版停。不要为了「做点什么」去重启还活着的逻辑服。

## Q19：多活怎么设计才不像「两个 AZ 画个圈」？

**★★★★★**

**场景**  
「我们要多活。」有人画两个 AZ 前面一个 LB，战斗服双写 Redis。排行榜也按强一致跨区设计。

**完整解答**

先问同城双活、灾备还是分区多活，以及 RPO/RTO、跨区玩法、玩家是否接受切区。数据层和切流开关才是题眼。画两个 AZ 负载均衡不等于多活。

```
  模式 A：同城双 AZ（机器 / 无状态接入 / etcd）
  +-------- AZ-a --------+     +-------- AZ-b --------+
  | 网关 / 大厅（可切）   |     | 网关 / 大厅           |
  | 战斗 Session 粘滞     |     | 战斗 可重建才可飘     |
  +----------+-----------+     +-----------+----------+
             |                             |
             +--------> MySQL 同步 <-------+
                       Redis：可丢的 Session 才跨 AZ
                       切流开关 / 演练 / 脑裂以谁为准

  模式 B：分区多活（按大区拆集群和数据）── 最常见可落地
  大区-华东 独立集群+库     大区-西南 独立集群+库
  跨区玩法单独设计，不是「流量对半切」

  模式 C：异地灾备 ── RTO 小时级
  主城停写 --> 校验备份 --> 切 DNS/目录 --> 开备用
  日常双写全部游戏库成本极高，多数厂做不到热双活
```

热双活全量游戏库不现实。Redis 跨城不同步当交易权威：延迟和脑裂不可接受就不要当多活数据面。Session 可重建的才可丢；交易和背包以 MySQL 为准，切流前停写。脑裂以谁为准要写进预案。不要一上来上全球同一套战斗服双活。

**再追问：排行榜跨区能强一致吗？代价是什么？**  
能，但代价是跨区同步延迟、写入冲突和切流复杂度。多数玩法用最终一致或分区榜；交易/背包不要和排行榜绑同一套强一致。跨区强一致排行榜要单独设计，不是「流量对半切」顺带送的。

## Q20：为什么必须先问约束再画图？你开口问哪几句？

**★★★★**

**场景**  
45 分钟题，前 10 分钟已经画满微服务。对方改口「我们单服只有 2000 CCU」，图全废。有人被说「规模你定」，卡住不知给哪一档。

**完整解答**

不问则假设错、整题作废，按中级评。开口 2–3 分钟只问、不画。规模口径、SLO、有状态、回滚 RTO、自建/团队，五类必问。

```
  ① 约束（规模/SLO/状态/回滚/预算）     ← 开口只问不画
  ② 容量假设（公式写出来，允许改）
  ③ 数据流（先箭头后盒子）
  ④ 关键组件 + 1 个 rejected
  ⑤ 失败模式：挂了谁疼、怎么停、怎么回
  ⑥ 可观测：SLI、告警分级、on-call
  ⑦ 演进：×10 流量或加一个大区怎么拆
```

开口原话：「这题我按生产系统来设计。先确认几件事：规模（CCU / 日开服数 / 节点）、SLO（什么叫坏了）、是否有状态、失败回滚的 RTO、自建还是云。确认后我写容量假设，再画数据流。」假设写白板角上可改。45 分钟：0–5 问清，5–15 数据流，15–30 失败路径，30–40 SLO/发布，最后权衡。时间不够保数据流 + 失败怎么停 + 谁被叫醒。不会的组件讲原则，不编产品细节。

**再追问：考官说「规模你定」，你给哪一档？**  
自己给一档合理假设并声明可调：例如单服 CCU 8000、日开 5 服、开服失败玩家不可见。对方改数字，你改图，不要争。

## Q21：考官坚持让你设计 LLM 平台，怎么收？

**★★★**

**场景**  
业务 SRE / 游戏 SRE 岗。白板写成 Prompt 链路和 Agent。游戏稳定性一句没有。有人把日志系统也当主设计题展开 40 分钟。

**完整解答**

不当主菜。先确认岗是否 AI Infra。用同一套骨架点到为止——网关限流、队列、GPU 水位、失败降级模型、超时——然后拉回游戏稳定性。不展开 MCP/Prompt/Agent。主线仍是开服和 SLO。

```
  业务/游戏 SRE 岗
       |
       v
  约束：QPS/token、SLA、能否降级
       |
       v
  网关限流 --> 队列 --> GPU 池（水位/显存）
       |                    |
       |                    v
       +--> 超时 / 降级模型 / 计费
       |
       v
  收束：生产主战场是开服、SLO、容量、发布
        GPU 我按容量和故障域这样保
        投纯 AI Infra 再按第九章展开
```

卡住时回到数据流：谁产生、谁存储、谁消费、失败谁停。不要在一个组件上沉默超过 1 分钟。换题用同一骨架重启，不解释上一题为什么没答完。

**再追问：日志系统要不要当主设计题练？**  
SRE 岗频率低于六主菜（开服、SLO、容量、发布、K8s、多活）。被问到讲缓冲、成本、限流、降级，尽快回到可观测和容量，不要当主菜练。

## 4. 行为面与谈薪

## Q22：事故复盘：时间线怎么讲？

**★★★★★**

**场景**  
总监：「讲一次 P0。」有人从根因 Redis 讲起，没有影响面，也没有自己的决策点。被追问「当时为什么不回滚」时开始辩。

**完整解答**

结构固定，临场不要抒情。先恢复后根因。无指责。指挥、同步、推动改进至少占一块。

```
  发现（告警/玩家/运营）--> 影响面（哪几个服、CCU、支付）
       --> 止血（回滚/切流/降级/扩容，选了哪个、谁有权）
       --> 对外（应急群时间线、运营公告口径）
       --> 根因（技术 + 流程，5 Why 到机制）
       --> 改进（监控/门禁/演练，每项有人和截止日期）
       --> 结果（MTTR、是否复发、机制是否还在）
```

口述骨架：「大促/开服前登录错误率 X%，影响 Y CCU，持续 Z 分钟。我是 on-call primary：5 分钟拉 war room，先问有没有变更，有则回滚；没有则看支付/Redis/网关。止血后和运营对齐公告口径。次日复盘主因是新 key 无 TTL / 配表未灰度，我推动规范、水位告警、演练。同类 0 复发。可更快的点：当时先看了 CPU，10 分钟后才看 Redis，runbook 已改顺序。」游戏高频：开服前组件挂、热更协议不兼容、活动配表错误、回档误伤。选你真处理过的。

**再追问：当时为什么不回滚？**  
有变更且可回：应回。当时没回，要承认决策慢或先看了 CPU，并讲后来 runbook 改成「先问变更」。现场有人吵回滚：对事，用错误率和 SLO 先止血，争论放到恢复后。不讲「我赢了那个开发」。

## Q23：研发要跳过预发赶活动，你怎么办？

**★★★★★**

**场景**  
「赶活动要跳过预发。」你若说「我强制落地」或「那就算了」，都偏。对方 TL 仍拒绝。

**完整解答**

用历史跳过预发的回滚率说话；折中压缩验证 + 金丝雀，不跳过；必要时拉 SLO 和双方 TL。结果要有：活动是否准时、有无回滚、规范是否写入。不演强制胜利。

```
  1. 拿出近半年变更类 P0 占比 / 跳过预发的回滚率
  2. 活动：压缩预发窗口 + 金丝雀，不是跳过
  3. 紧急通道保留，热修复 24h 补 Git
  4. 必要时升级：SLO / 变更故障率，拉双方 TL
  5. 对方始终拒：核心链路书面风险请老板拍板
```

线上结果优先、用数据结束争论。不要演「我强制落地」或「我放弃规范」。承认一次没留热修通道导致反弹，后来加例外和补交时限，规范才落地。

**再追问：对方 TL 仍拒绝，你书面记录什么？**  
记录：跳过预发的具体范围、预估影响面（登录/支付/战斗）、回滚预案和 RTO、谁签字接受风险。核心链路书面请老板拍板。先保核心，非核心可以压缩，不是全跳过。

## Q24：主动推进过什么？怎么证明是你推的？

**★★★★**

**场景**  
「除了值班你还做了什么？」答「领导让我做的脚本」。对方听成接单。业务不改告警阈值。

**完整解答**

必须非 KPI：告警治理或开服自动化。要有发现问题的数据、你争取到的时间、落地阻力、结果。证明功劳用时间线和文档口径，不靠「大家觉得我拼」。

```
  采样 top 噪声 --> 方案（分级+抑制）
       --> 要时间（找 TL 要 20%）
       --> 试点一个业务
       --> 铺开，纳入评审
  结果：告警量、周叫醒次数下降，且没有漏掉 P0
```

「日告警 N、有效率低，无人牵头。我做两周采样，出 top 噪声；提 P0–P3 和抑制规则；先一个业务试点再铺。」出现「他们不配合所以没做成」，评语直接降。优先级：P0 永远第一；发版/活动窗口提前锁；其余和经理周对齐。不会默默全接。

**再追问：失败过的推进呢？**  
讲失败：范围过大/没有业务 Owner。后来改成先做开服五段门禁这一条，失败可停，才有人用。业务不改阈值：自助工具 + 占用无效告警的数据，纳入发布评审，先核心链路。

## Q25：反问环节问什么、不问什么？

**★★★★**

**场景**  
结尾「你问我吧」。有人问加班和多久晋升。他们说挑战是活动峰值，接了一句「挺有挑战的」就结束。

**完整解答**

反问是你在验团队，也在给「我是来做稳定性的」信号。准备 3 个，临场选，不要全念。听完接 1 句你的经验。band 留给 HR。

**问：**

1. 团队目前最大的稳定性挑战是容量、变更还是可观测？
2. 这个岗位半年最重要的目标怎么衡量？
3. on-call 轮值、P0 谁指挥、复盘 action 谁盯？
4. SRE 和研发在发布/回滚上的边界是什么？
5. （游戏岗）开服和版本窗口谁有最终否决权？

**不问：** 加班多吗、多久晋升、能不能少 on-call、工资什么时候调。

**再追问：他们说挑战是活动峰值，你怎么接？**  
接 1 句你的经验：「你们卡在活动峰值，我这边是排队 + 提前扩无状态，逻辑服不按 HPA 加副本。」证明你在听，不是背题。不要空夸。

## Q26：年包 65–75 万，HR 问期望怎么答？

**★★★★★**

**场景**  
HR 第一句：「期望薪资？」有人报「最低 60 万，月薪也可以」。对方口头包 62 万且按高级招。又追问「最低能接受多少？」

**完整解答**

先问职级。一线高级 SRE 年包期望 70–75 万，结构可调；保底看 65 万档是否职级对齐。不报最低 60。谈 4 年 Total Comp，不是月薪。前提：定级按高级；四维证据不足会被按中级预算谈。

```
  HR：期望薪资？
  你：想先确认职级和职责。按 7-10 年游戏/SRE 和现在市场，
      年包期望 70-75 万，base 和股票可以调结构。

  HR：我们只能到 62 万。
  你：对团队方向感兴趣。62 万和高级 band 以及我能扛的
      开服/稳定性范围有差距。手头有一条流程在 70 万左右，
      能否争取到 70-72 万？股票比例我可以灵活。
```

按编号走，不要跳步先报底价：

1. 技术/定级结束前不主动报数。
2. 被逼问给区间 70–75，不报最低 60。
3. 当前薪资如实，不虚构（背调风险）。
4. 口头包拆 4 年 TC：Base × 薪数 + 年终期望 + 股票摊 4 年 + 签字费。游戏厂问清项目奖是否进 offer、亏损年有没有保底。
5. 62 万且按高级招：争取 70–72，给竞品锚和 deadline。股票可灵活。
6. 职级明确中级且差距大：礼貌拒，不贬对方 band。
7. 当前司 counter：除非解决离职根本原因，否则向前看。
8. 威胁式「不给到 XX 我就拒」不要用。

**再追问：最低能接受多少？**  
不报保底绝对值。「级别和 package 匹配的话，65–70 万年包我会认真看，更希望按高级 band 定。」

## Q27：为什么离职？3 年规划？

**★★★★**

**场景**  
「上家待一年是不是不稳定？」开始辩性格、骂领导。投 IC 岗却大谈带 20 人，或空喊转 AI。又被问还面了哪些公司。

**完整解答**

向前看要更大容量和完整 SRE。规划对齐 JD。对话里不要骂前司。短呆给业务原因。管理 vs IC：先 IC。不把公司当跳板演讲。

```
  离职：维护期 / 要更大容量和更完整的 SRE 体系 / 城市家庭
        不说领导差、加班多、钱少

  3 年规划：
    第 1 年  熟悉基础设施和 on-call，告警或变更上交出数字
    第 2-3 年  1-2 条核心链路稳定性 Owner（SLO/容量/重大复盘）
    管理还是 IC：先 IC 深度，带项目自然带人
```

选对方：规模或窗口纪律、JD 匹配你的开服/K8s/稳定性，不要「因为是大厂」。短呆：业务线调整 + 你学到什么 + 下一份要对齐什么。其他流程可说类别，强调对本岗兴趣最高。

**再追问：还面了哪些公司？**  
可说类别（同梯队游戏/互联网 SRE），强调对本岗匹配度最高。不报具体竞品薪资除非谈薪阶段用锚。上家待一年：给具体业务变化，承诺交接周期，用 3 年规划对齐本岗，不争辩性格。

## Q28：最大失误 + 能不能接受 on-call？

**★★★★**

**场景**  
「没有犯过」或编成「其实是我救了场」。on-call 答「没问题随叫随到」。被问领导批评了吗、半夜起不来怎么办。

**完整解答**

失误：真实、担责、已改、同类 0。DDL/配表/开服漏预检都可以。瞒报不可。on-call：接受 + 告警/runbook/轮换，用你降过的叫醒次数证明不裸扛。表演「随时打电话」像没干过。

```
  失误：立刻止损 --> 复盘主责写自己流程缺失
       --> checklist / gh-ost / 双人复核 / 门禁
       --> 同类 0

  on-call：接受（职责）
       --> 可持续：告警有效、P0 有 runbook、轮换公平
       --> 用告警量 / MTTR 数字证明不是来裸扛
       --> 太多：先治理无效告警和自动修复，再谈加人
```

好的 on-call 是系统质量问题不是觉悟问题。反问团队现状（一周几次、有无 secondary）。领导批评如实说，重点是系统已改。

**再追问：领导批评你了吗？半夜起不来怎么办？**  
批评如实说，重点是清单/门禁已改、同类 0。半夜：电话升级、secondary 补位，不表演「永远秒醒」。on-call 太多先治理再加人；只要求加人会被认为不会治理。当时想过瞒吗？没有。瞒会使回档和公告出错，伤害更大。
