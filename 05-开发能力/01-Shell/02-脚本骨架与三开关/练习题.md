## Q1

**★★★★★｜`set -euo pipefail` 四个部分分别解决什么？为什么建议一起开？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 · 二、三开关

### 场景

老脚本只有 `set -e`，某次 `HOSTNMAE` 拼写错误把配置同步到空主机名；另一次 `kubectl | tee` 失败 CI 仍绿。——就是开头那个「去掉 -e 好调试」的冲动；Q2、Q3 会继续挖 pipefail 和批处理。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：`-e` 停失败、`-u` 抓未定义变量、`-o pipefail` 管道全链问责、`-o` 是打开选项的语法。

| 开关 | 作用 |
|------|------|
| `-e` / `errexit` | 简单命令非 0 → 脚本退出 |
| `-u` / `nounset` | 未定义变量引用 → 报错退出 |
| `-o pipefail` | 管道任一非 0 → 整条管道非 0 |

只开 `-e`：`false | true` 仍 0；只开 `-u`：`kubectl` 失败仍往下跑。三件套是生产 Bash 默认头。

```bash
#!/usr/bin/env bash
set -euo pipefail
```

### 再追问

`set -e` 和 `bash -e` 一样吗？——`bash -e script.sh` 只影响该次；脚本内还应写 `set -euo pipefail` 防被人 `bash +e` 调用。

## Q2

**★★★★★｜`kubectl apply -f app.yaml | tee deploy.log` 在只有 `set -e` 时 CI 会红吗？怎么改？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 · pipefail · Q2 模板

### 场景

GitLab CI 步骤：`bash deploy.sh`，脚本里 `set -e` 但没有 `pipefail`。故意提交错误 YAML，流水线绿，集群无变更。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**不会红**——管道 `$?` 默认是 `tee` 的 0。

```bash
set -e
kubectl apply -f bad.yaml | tee deploy.log
echo $?   # 0

set -euo pipefail
kubectl apply -f bad.yaml | tee deploy.log
# apply 非 0 → 管道非 0 → -e 退出 → CI 红
```

备选：`kubectl ... | tee ...; exit "${PIPESTATUS[0]}"`（06 章）。

### 再追问

还要把日志上传 artifact？——可以，**先**保证 pipefail，再谈 tee；别为了 artifact 牺牲门禁。

## Q3

**★★★★☆｜哪些情况下 `set -e` 下命令非 0 却**不会**退出脚本？各举一个例子。**

**覆盖**：必会 · 常考 | **对应**：知识点 · -e 例外

### 场景

面试官：「`if kubectl get ns; then` 里 get 失败为什么没整个脚本退出？」

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**测试上下文**和 **`||` 左侧**等例外不触发 `-e`。

| 例外 | 示例 |
|------|------|
| `if` / `while` 条件 | `if false; then echo x; fi` |
| `\|\|` 左侧 | `false \|\| echo ok` |
| `!` 前缀部分情况 | `if ! cmd; then ...` |
| 无 pipefail 的管道 | `false \| true` 整体 0 |

```bash
set -e
if kubectl get ns not-exist 2>/dev/null; then
  echo ok
else
  echo "ns missing — script continues"
fi
echo "still here"
```

### 再追问

`cmd && echo ok` 里 cmd 失败呢？——`&&` 短路，右侧不跑；若 cmd 非 0 且是简单命令，**`-e` 会退出**（除非在 if 里）。

## Q4

**★★★★☆｜`-u` 下 `echo "$DB_HOST"` 和 `echo "${DB_HOST:-}"` 有什么区别？**

**覆盖**：必会 · 常用 | **对应**：知识点 · -u · 衔接 03

### 场景

新环境忘配 `DB_HOST`，无 `-u` 时脚本用空串连数据库；开 `-u` 后脚本第一行就挂——哪种更好？

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：`-u` 让**未定义**即失败；`${var:-}` 提供默认或空串，**不算未定义引用**。

```bash
set -u
echo "$DB_HOST"        # unbound variable — 好，快速失败

echo "${DB_HOST:-}"    # 空行，不报错 — 要配合 [[ -n ... ]] 检查
[[ -n "${DB_HOST:-}" ]] || { echo "DB_HOST required"; exit 1; }
```

SRE 口径：关键变量要么 `-u` 硬失败，要么显式 `:?` 带消息：`${DB_HOST:?DB_HOST not set}`。

### 再追问

`${var-default}` 和 `${var:-default}`？——后者在 var **空串**时也用 default（03 章细讲）。

## Q5

**★★★★☆｜为什么 `mktemp` 后要 `trap 'rm -f "$tmp"' EXIT`？EXIT 在哪些路径会触发？**

**覆盖**：必会 · 常用 | **对应**：知识点 · trap EXIT

### 场景

巡检脚本每天 `mktemp` 写 kubectl 输出，一个月后 `/tmp` 几万个小文件，磁盘告警。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**EXIT trap** 在脚本结束（正常、`exit`、`set -e` 触发退出）时跑清理。

```bash
tmp="$(mktemp)"
trap 'rm -f "$tmp"' EXIT

kubectl get pods -A -o json >"$tmp"
# 处理 $tmp ...
# 无论成功还是中间 set -e 退出，都 rm
```

注意：SIGKILL(9) 拦不住；K8s 超时 SIGKILL 可能留垃圾——要缩短处理时间 + 捕 TERM。

### 再追问

多个临时文件？——一个 cleanup 函数里 rm 全部；或 `trap` 里调 `cleanup`。

## Q6

**★★★★★｜cleanup 里写 `exit` 和不写 `exit "$rc"` 对 CI 有什么影响？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 · cleanup 保留退出码

### 场景

脚本已 `kubectl apply` 失败，cleanup 删了临时文件，Jenkins 却显示 SUCCESS——开发以为发布成功。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：cleanup 里**裸 `exit`** 或最后成功命令会把失败**洗成 0**。

```bash
# 错误
cleanup() {
  rm -f "$tmp"
  exit    # 等价 exit 0 若 cleanup 内命令都成功
}
trap cleanup EXIT

# 正确
cleanup() {
  local rc=$?
  rm -f "${tmp:-}"
  exit "$rc"
}
trap cleanup EXIT
```

`local rc=$?` 要放在 cleanup **第一行**，在 rm 等可能改 `$?` 的命令之前。

### 再追问

cleanup 里 `rm` 失败要不要覆盖 rc？——一般 `rm -f` 忽略；若关键，先存 rc 再 best-effort 清理，仍 `exit "$rc"`。

## Q7

**★★★★☆｜Pod 删除时脚本收到 SIGTERM，你应该怎么做？exit 几？**

**覆盖**：必会 · 常用 · 常考 | **对应**：知识点 · INT/TERM

### 场景

长循环 `while read host; deploy_host`，`terminationGracePeriodSeconds=30`，Pod 一直 Terminating 到被 SIGKILL 137。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**trap TERM**，停接新活、收尾当前、**exit 143**（128+15）。

```bash
trap 'log "TERM: stop accepting new hosts"; exit 143' TERM
trap 'log "INT"; exit 130' INT

while read -r host; do
  deploy_host "$host" || failed+=("$host")
done < hosts.txt
```

配合 `preStop` hook、缩短单台 deploy 时间；别在 TERM 后还开 50 个新 ssh。

### 再追问

`exit 143` 和 `exit 1` 在 CI 里？——都是非 0 失败；143 表示**被 TERM**，便于日志区分「被杀」vs「业务错误」。

## Q8

**★★★★☆｜为什么要 `main "$@"` 而不是在文件顶层直接写逻辑？**

**覆盖**：必会 · 常考 | **对应**：知识点 · main 结构

### 场景

测试想 `source deploy.sh` 只测 `deploy_host` 函数，一 source 就真的连生产 ssh 了。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**定义与执行分离**——source 只加载函数；执行入口唯一在文件末尾 `main "$@"`。

```bash
deploy_host() { ... }

main() {
  deploy_host "$1"
}

# 仅在被直接执行时跑（可选加固）
if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then
  main "$@"
fi
```

`"$@"` 保留参数中的空格；比 `$*` 更安全。

### 再追问

`usage` 为什么 `exit 2`？——惯例 2 表示误用命令行；与业务失败 1 区分（GNU 约定，团队可文档化）。

## Q9

**★★★★★｜100 台循环发布，`set -e` 下为什么第一台失败就停了？怎么改才能跑完并汇总？**

**覆盖**：核心 · 必会 · 常用 | **对应**：知识点 · 批处理 · 模板 2

### 场景

Nginx 批量 reload，第 3 台 `nginx -t` 失败，后 97 台没试；经理要完整 failed 列表。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：`set -e` 下裸调失败命令会**立即退出**；用 `|| failed+=` 或 `if !` **捕获**。

```bash
set -euo pipefail
failed=()
while read -r host; do
  [[ -z "$host" || "$host" =~ ^# ]] && continue
  deploy_host "$host" || failed+=("$host")
done < hosts.txt

if ((${#failed[@]} > 0)); then
  printf 'failed: %s\n' "${failed[*]}" >&2
  exit 1
fi
```

**不是**去掉 `-e`「方便跑完」——那是把别的步骤失败也静默掉。

### 再追问

能否 `set +e` 包一层循环？——可以但易漏恢复 `-e`；`|| failed+=` 更清晰。

## Q10

**★★★★☆｜`DRY_RUN` 为什么默认 `true`？活动前怎么演练？**

**覆盖**：必会 · 常用 · 常考 | **对应**：知识点 · DRY_RUN

### 场景

新人 `DRY_RUN=false ./deploy.sh hosts.txt` 打错文件，把测试配置推到 100 台正式 Nginx。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**默认演练、显式真跑**——防误操作；变更单上写 `DRY_RUN=false`。

```bash
DRY_RUN="${DRY_RUN:-true}"

deploy_host() {
  local host=$1
  if [[ "$DRY_RUN" == "true" ]]; then
    log "[DRY-RUN] $host: scp + nginx -t + reload"
    return 0
  fi
  # 真执行 ...
}
```

演练：`./deploy.sh hosts.txt` 看日志；评审后再 `DRY_RUN=false ./deploy.sh hosts.txt`。

### 再追问

DRY_RUN 要不要测 `nginx -t`？——可以分级：`DRY_RUN=full` 只连 ssh 测 `-t` 不 reload（09 章参数设计）。

## Q11

**★★★★☆｜CI 里 Trivy 扫到 Critical 还 push 了镜像——脚本层怎么拦？**

**覆盖**：必会 · 常用 | **对应**：知识点 · 模板 3 · 05 实战 Q8

### 场景

` trivy image ... || true` 后 `docker push`，Critical CVE 进生产 registry。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**三开关 + 禁止 `|| true`**——trivy `--exit-code 1` 非 0 即停。

```bash
#!/usr/bin/env bash
set -euo pipefail

main() {
  : "${GIT_SHA:?}"
  docker build -t "reg/hall:${GIT_SHA}" .
  trivy image --exit-code 1 --severity CRITICAL "reg/hall:${GIT_SHA}"
  docker push "reg/hall:${GIT_SHA}"
}

main "$@"
```

超时重试要有上限，仍失败当失败；豁免 `SCAN_WAIVER` 默认关并记审批人。

### 再追问

trivy 在 pipe 里？——也要 `pipefail`；或单独一步不管道。

## Q12

**★★★☆☆｜cron 里同一脚本重叠执行怎么防？flock 和 trap 怎么配？**

**覆盖**：常用 · 常考 | **对应**：知识点 · 模板 4

### 场景

同步 job 跑 40 分钟，cron 每 15 分钟触发一次，三台同时写同一目录，数据损坏。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：**`flock -n` 拿不到锁就退出**；`trap` 里 `flock -u` 释放。

```bash
#!/usr/bin/env bash
set -euo pipefail

LOCK=/var/lock/sync.job.lock
exec 9>"$LOCK"
flock -n 9 || { echo "already running" >&2; exit 0; }

trap 'flock -u 9' EXIT

main() {
  /usr/local/bin/sync_data.sh
}

main "$@"
```

`exit 0` 表示「跳过」还是「失败」由团队定义——监控要认日志 `already running`。

### 再追问

NFS 上 flock？——可能不可靠；换 Redis 锁或 systemd timer `OnUnitActiveSec` 防重叠。

## Q13

**★★★★☆｜「我把 set -e 去掉脚本就好调试了」——错在哪？你该建议什么？**

**覆盖**：必会 · 常考 | **对应**：知识点 · 踩坑 · 作战

### 场景

某同事发版脚本去掉三开关，问题「修好了」——其实是第 50 台失败继续 reload 了 50 台坏的。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：去掉 `-e` 是**用静默失败换暂时能跑完**——比第一台就停更危险。

建议：

1. 恢复 `set -euo pipefail`
2. 批处理用 `failed[]` 汇总
3. 调试 `bash -x`（测环境）、`DRY_RUN=true`
4. 单步 `deploy_host one-host` 函数测试

```bash
# 调试不要生产密钥
bash -x ./deploy.sh 2>&1 | tee /tmp/debug.log
```

### 再追问

`set -x` 会泄密？——会打印变量；用 `+x` 包敏感段或 `BASH_XTRACEFD` 定向（11 章）。

## Q14

**★★★★★｜白板：写出一个可上线的 Bash 脚本骨架（含三开关、trap、cleanup 保留 $?、main、DRY_RUN）。**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 · 全章

### 场景

终面：「给你们一个新写的发布脚本，你会要求哪些固定结构？」

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。


### 完整解答

> 🎯 **一句话**：头、开关、清理、信号、main、默认 dry-run、失败 exit 1。

```bash
#!/usr/bin/env bash
set -euo pipefail

DRY_RUN="${DRY_RUN:-true}"
log() { printf '[%s] %s\n' "$(date '+%F %T')" "$*" >&2; }

tmpfile=""
cleanup() {
  local rc=$?
  [[ -n "$tmpfile" && -f "$tmpfile" ]] && rm -f "$tmpfile"
  exit "$rc"
}
trap cleanup EXIT
trap 'log INT; exit 130' INT
trap 'log TERM; exit 143' TERM

deploy_host() {
  local host=$1
  [[ "$DRY_RUN" == "true" ]] && { log "DRY-RUN $host"; return 0; }
  ssh -n "$host" "nginx -t && systemctl reload nginx"
}

main() {
  local failed=() host
  while read -r host; do
    [[ -z "$host" ]] && continue
    deploy_host "$host" || failed+=("$host")
  done <"${1:-hosts.txt}"
  ((${#failed[@]})) && { log "failed: ${failed[*]}"; exit 1; }
}

main "$@"
```

评分点：三开关、cleanup `$?`、`"$@"`、DRY_RUN 默认 true、failed 汇总、日志 stderr。

### 再追问

和 Ansible 比何时还用 Shell？——几十行 CI 门禁、已有 bash 工具链、快速编排 CLI；百台幂等变更优先 Ansible（05 实战）。
