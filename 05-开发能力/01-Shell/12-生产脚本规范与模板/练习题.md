## Q1

**★★★★★｜「能跑的脚本」和「生产脚本」差在哪？面试 30 秒怎么说？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [一、一张图](知识点.md)、[二、出生](知识点.md)

### 场景

面试官：「你们发版脚本放哪？和临时 ssh 一行有何不同？」

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：生产脚本 = **Git 规范目录 + README + 三开关/main + 退出码 + DRY_RUN + CI lint + runbook**；ad-hoc 不入库、无契约。

| 维度 | 生产脚本 | ad-hoc |
|------|----------|--------|
| 位置 | `scripts/<域>/` | 终端历史 |
| 文档 | README + runbook | 无 |
| CI | bash -n + shellcheck | 无 |
| 失败 | exit 1 | 常忽略 |

> 📝 **面试**：「能交接、能审计、能让 Jenkins 真红。」

### 再追问

何时仍用 ad-hoc？——1～2 台紧急只读排查； repeatable 操作必须入库。

## Q3

> 开头「Jenkins 绿着、半套配置」的退出码契约。

**★★★★★｜脚本里 `echo ERROR` 但 `exit 0`，Jenkins 绿着现场配置错了——怎么建立退出码契约？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [五、交卷](知识点.md)

### 场景

批量发布 5 台失败，脚本只打印 ERROR 字符串。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：团队固定 **0 成功 / 1 业务失败 / 2 用法 / 127 缺依赖**；失败必须 **`exit 1`**，禁止 `|| true`。

```bash
if ((${#failed[@]} > 0)); then
  log_err "failed: ${failed[*]}"
  exit 1
fi
```

Jenkins/GitLab 只看进程退出码，不解析 ERROR 文本。

> ⚠️ **别混**：日志级别 ERROR ≠ 进程失败。

### 再追问

`exit 2` 何时用？——参数错、`usage`；与业务失败 1 区分，便于告警路由。

## Q4

**★★★★★｜`DRY_RUN` 应该默认 true 还是 false？为什么？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [六、干活](知识点.md)

### 场景

新人复制命令漏改 `DRY_RUN`，直接在生产 hosts 上 reload。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**默认 true**——复制粘贴只演练；真变更必须 **`DRY_RUN=false` 显式** + runbook 审批。

```bash
DRY_RUN=${DRY_RUN:-true}
if [[ "$DRY_RUN" == true ]]; then
  log "[DRY-RUN] would deploy to $host"
  return 0
fi
```

### 再追问

巡检脚本也要 DRY_RUN 吗？——可以；只读巡检真执行风险低，但仍建议默认演练防打错 hosts 文件。

## Q5

**★★★★☆｜为什么 `log` 要走 stderr，指标 JSON 走 stdout？**

**覆盖**：必会 · 常用 | **对应**：知识点 [四、说话](知识点.md)

### 场景

`./check.sh | tee metrics.json` 把 debug 和 JSON 混在一起，Prometheus 解析失败。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**stdout = 机器交付物**；**stderr = 人读日记**——管道和重定向才不互相污染。

```bash
log() { printf '[%s] %s\n' "$(date '+%F %T')" "$*" >&2; }
check_ok() { printf '{"status":"ok"}\n'; }  # stdout
```

```bash
./check.sh > /var/lib/node_exporter/textfile/check.prom 2>>/var/log/check.log
```

### 再追问

CI 日志主要看哪？——stderr 末尾 + 退出码。

## Q6

**★★★★☆｜`cleanup` trap 里为什么要 `exit "$rc"`？**

**覆盖**：必会 | **对应**：知识点 [三、筑基](知识点.md)

### 场景

脚本业务失败 `exit 1`，trap 清理临时目录后 Jenkins 变绿。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：cleanup 开头 **`local rc=$?`**，末尾 **`exit "$rc"`**——清理不能把失败洗成 0。

```bash
cleanup() {
  local rc=$?
  rm -f "${tmpfile:-}"
  exit "$rc"
}
trap cleanup EXIT
```

### 再追问

只想清理成功路径？——仍保留原 rc；成功时 rc 本就是 0。

**★★★★☆｜设计一个「只读磁盘巡检」脚本，必须包含哪些要素？**

**覆盖**：必会 · 常用 | **对应**：知识点 [七、模板 A](知识点.md)

> 🎯 **一句话**：**hosts + ssh BatchMode + 并发上限 + 只读远程命令 + failed 列表 + exit 1 + stdout 可选 JSON**。

## Q8

**★★★★★｜Nginx 发布脚本最小安全步骤？哪步失败不能 reload？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [八、模板 B](知识点.md)

### 场景

有人 scp 完直接 reload，跳过 `nginx -t`。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**备份 → 下发 → `nginx -t` → reload**；**`-t` 失败绝不 reload**。

```bash
cp -a "$dst" "$bak"
mv "${dst}.new" "$dst"
nginx -t && systemctl reload nginx   # -t 失败则 set -e 停，不 reload
```

顺序：先 bak，再原子 mv，再校验，最后 reload。

> 📝 **面试**：「半套配置比全挂更惨——校验是门禁。」

### 再追问

scp 到 `.new` 再 mv 的好处？——避免半截文件被 nginx 读到。

## Q11

**★★★★☆｜cron 每 5 分钟跑巡检，上次还没跑完又开始——怎么防？**

**覆盖**：常用 | **对应**：知识点 [六、干活](知识点.md)

### 场景

重叠执行导致双倍 SSH 连接打满堡垒机。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**`flock -n` 文件锁**；拿不到锁 **exit 0 跳过** 并打 warn 日志。

```bash
exec 9>/var/lock/check.lock
flock -n 9 || { log_warn "skip overlap"; exit 0; }
main "$@"
```

### 再追问

exit 0 跳过会不会掩盖「跑太慢」？——要监控单次耗时；锁只是防重叠。

## Q12

**★★★★★｜50 台发布 3 台失败——脚本和 oncall 各做什么？**

**覆盖**：核心 · 必会 | **对应**：知识点 [八、模板 B](知识点.md)、[十、作战](知识点.md)

### 场景

失败列表已写 `/tmp/deploy-nginx-failed-*.txt`。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：脚本 **`exit 1` + stderr 打 failed + runbook rollback 链接**；oncall **只对失败机回滚**，不要无脑全量重发。

脚本侧：
```bash
printf '%s\n' "${failed[@]}" | tee "/tmp/deploy-failed-$(date +%s).txt" >&2
log "ROLLBACK: https://wiki.../rb/nginx-deploy#rollback"
exit 1
```

oncall：按 runbook 对列表内主机恢复 bak；成功机不碰。

### 再追问

能否自动回滚全部？——可以写 `rollback.sh`，但默认 manual 更安全；自动回滚要审批。

## Q14

**★★★★★｜白板：从需求到上线，画生产脚本生命周期并口述「入库七件套」。**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [一、一张图](知识点.md)、[八、模板 B](知识点.md)

### 场景

终面系统设计：「如何保证发版脚本可维护、可回滚、CI 可信？」

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**立项→README→骨架→模板→lint/dry-run CI→CR/runbook 演练→执行→失败走 rollback**；七件套：**README/runbook、三开关+main、stderr 日志、退出码、DRY_RUN、CI、failed+回滚指针**。

```mermaid
flowchart LR
    A[需求] --> B[规范目录]
    B --> C[模板实现]
    C --> D[CI]
    D --> E[runbook演练]
    E --> F[DRY_RUN=false执行]
```

与 Ansible 边界：重复、需审计用脚本+Git；更大规模用 Ansible/GitOps。

> 📝 **面试**：「Jenkins 真红靠 exit 码，不靠 echo。」

### 再追问

脚本 Owner 离职怎么办？——README 团队邮箱 + 定期 runbook 演练 + 仓库 CODEOWNERS。
