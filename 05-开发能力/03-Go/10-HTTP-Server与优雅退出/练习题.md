## Q1

**★★★★★｜http.Server.Shutdown(ctx) 具体会做哪些事？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、优雅退出模板](知识点.md)

### 完整解答

> 🎯 **一句话**：**关闭 listener（不接新连接）**、关 idle 连接、**等待**活跃请求 handler 结束（或 ctx 超时）；等待期间 **进行中的 r.Context() 会 cancel**。

不保证 kill handler 里 detach 的 goroutine。

> 📝 **面试**：协作式优雅，不是 SIGKILL。

### 再追问

**Shutdown 能调两次？**——第二次通常很快返回；用 `sync.Once` 包一层更稳。

## Q2

**★★★★★｜ListenAndServe 返回 http.ErrServerClosed 要不要 log.Fatal？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、最小 Server 与 ErrServerClosed](知识点.md)

### 完整解答

> 🎯 **一句话**：**不要 Fatal**——这是 **Shutdown 后的正常退出**。

```go
if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
    log.Fatalf("listen: %v", err)
}
```

> ⚠️ **别混**：只有非 ErrServerClosed 才是真错误（如 port 占用）。

### 再追问

**Serve 同样？**——是，同一 ErrServerClosed 语义。

## Q3

**★★★★★｜r.Context() 在哪些情况下会被 cancel？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [四、Request.Context 与 Shutdown](知识点.md)

### 完整解答

> 🎯 **一句话**：**客户端断开连接**；**Server.Shutdown** 进行 graceful stop 时。

Handler 应把该 ctx 传到 `QueryContext`、`NewRequestWithContext` 等（[08](../08-context取消与超时传播/)）。

> 📝 **面试**：两种 cancel 日志都可能显示 `context canceled`。

### 再追问

**ResponseWriter 写 half 时 cancel？**——可能；要处理 `Err()` 和部分写失败。

## Q4

**★★★★☆｜Shutdown 超时后 Close 会怎样？**

**覆盖**：必会 ｜ **对应**：知识点 [九、Close vs Shutdown](知识点.md)

### 完整解答

> 🎯 **一句话**：**Close 立即关 listener 和连接**，不 wait handler——可能 mid-request 失败。

Shutdown 超时 → 日志 → `Close()` 兜底 → 进程可 exit。

> 📝 **面试**：先优雅后强制，顺序别反。

### 再追问

**只 Close 不 Shutdown？**——发版易 502 和数据半写，**不要**在生产当常规路径。

## Q5

**★★★★★｜为什么必须设 ReadHeaderTimeout？不设有什么风险？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、超时与资源保护](知识点.md)

### 完整解答

> 🎯 **一句话**：防 **slowloris**——恶意客户端慢发 header 占满连接/ goroutine。

```go
ReadHeaderTimeout: 5 * time.Second,
```

Go 1.20+ 默认已有，显式设更清晰。

> 🔍 **现场**：连接数涨但 QPS 低，查 slow client。

### 再追问

**ReadTimeout 与 ReadHeaderTimeout？**——前者含 body；后者只 header 阶段。

## Q6

**★★★★★｜handler 里 `go longJob(context.Background())` 为什么破坏优雅退出？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、Request.Context 与 Shutdown](知识点.md)

### 场景

Shutdown 30s 到了进程 exit，job 还在写 DB。

### 完整解答

> 🎯 **一句话**：**Shutdown 只等 handler 函数返回**，不等 Background goroutine；**Background 无视 cancel**。

修法：绑 app ctx、job 队列 drain、或同步做完再返回。

> 📝 **面试**：202 Accepted 异步模式要设计 lifecycle。

### 再追问

**WaitGroup 在 Shutdown 后 Wait？**——main 在 Shutdown 后 `wg.Wait()` 可以，要有超时。

## Q7

**★★★★★｜K8s terminationGracePeriodSeconds、preStop sleep、Shutdown 30s 怎么配？**

**覆盖**：常用 · 必会 ｜ **对应**：知识点 [七、K8s 与负载均衡摘流](知识点.md)

### 完整解答

> 🎯 **一句话**：**grace ≥ preStop sleep + Shutdown ctx + 缓冲**；例：sleep 5 + Shutdown 30 → grace 至少 40–60s。

preStop 给 Endpoint 摘流时间；Shutdown 等 handler。

> 📝 **面试**：grace 小于 Shutdown 会被 SIGKILL 强杀。

### 再追问

**只加 grace 不 preStop？**——仍可能 502，LB 缓存旧 endpoint。

## Q8

**★★★★☆｜Shutdown 的 ctx 为什么常用 context.Background() 再 WithTimeout，而不是用已 cancel 的 signal ctx？**

**覆盖**：必会 ｜ **对应**：知识点 [八、ListenAndServe 与 errgroup / app ctx](知识点.md)

### 完整解答

> 🎯 **一句话**：收到 SIGTERM 后 **signal ctx 可能已 Done**，但 Shutdown **仍需要独立 grace 窗口** 等 handler。

```go
shutCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(shutCtx)
```

> 📝 **面试**：Shutdown 的 deadline 是「停服预算」，不是「信号 ctx 剩余时间」。

### 再追问

**用 signal ctx 的 Deadline？**——可以算剩余时间，但要保证 ≥ 预期 handler 收尾时间。

## Q9

**★★★★☆｜Server WriteTimeout 对 SSE/WebSocket 有什么影响？**

**覆盖**：常用 ｜ **对应**：知识点 [五、超时与资源保护](知识点.md)

### 完整解答

> 🎯 **一句话**：**WriteTimeout 从 accept 起算**，长连接 streaming 可能被 **误杀**——SSE/WS 路由用 **单独 Server** 或对该 handler **Disable/0**。

普通 API 仍应设 WriteTimeout。

> ⚠️ **别混**：IdleTimeout 管 keep-alive 空闲，不是单次写。

### 再追问

**Handler 内 flusher？**——定期 flush 也可能受 WriteTimeout 影响，要测。

## Q10

**★★★★☆｜滚动发版出现 502 尖峰，按什么顺序查？**

**覆盖**：常用 · 必会 ｜ **对应**：知识点 [十一、作战：发版 502 怎么查](知识点.md)

### 完整解答

> 🎯 **一句话**：对齐 **502 与 pod Terminating** → 查 **preStop/readiness** → 查 **Shutdown 耗时与 handler detach** → 查 **LB draining**。

> 🔍 **现场**：`kubectl describe pod` 看 Last State 与 grace。

### 再追问

**HPA 缩容同样？**——是，SIGTERM 路径相同。

## Q11

**★★★★☆｜HTTP middleware 为什么要 recover panic？放链路的哪一层？**

**覆盖**：必会 ｜ **对应**：知识点 [六、中间件链与 panic recover](知识点.md)

### 完整解答

> 🎯 **一句话**：未 recover 的 panic **可能 crash 整个进程**；**最外层** recover，打栈、返 500。

```go
defer func() {
    if r := recover(); r != nil { ... }
}()
```

> 📝 **面试**：recover 只挡当前请求 goroutine，别指望挡其它 handler。

### 再追问

**panic 后 Shutdown？**——进程若没挂，Shutdown 仍可用；已 crash 则靠 K8s 重启。

## Q12

**★★★★☆｜如何在 Shutdown 开始前让 readiness 失败？**

**覆盖**：常用 ｜ **对应**：知识点 [七、K8s 与负载均衡摘流](知识点.md)

### 完整解答

> 🎯 **一句话**：SIGTERM 后设 **`shuttingDown` 标志**，`/ready` 返回 **503**，再 **短暂 sleep** 等 Endpoint 更新，再 `Shutdown`。

```go
shuttingDown.Store(true)
time.Sleep(2 * time.Second)
srv.Shutdown(shutCtx)
```

> 📝 **面试**：与 preStop sleep 互补，不是二选一。

### 再追问

**liveness 也 503？**——**不要**；liveness 失败会重启 pod，只改 readiness。

## Q13

**★★★★☆｜ListenAndServe 应该阻塞 main 还是放 goroutine？**

**覆盖**：必会 ｜ **对应**：知识点 [三、优雅退出模板](知识点.md)

### 完整解答

> 🎯 **一句话**：常见 **goroutine Listen**，**main 阻塞在 `<-quit`** 或 `signal.NotifyContext`，收到信号后 **Shutdown**。

若 main 阻塞在 ListenAndServe，要先注册 signal 处理再 Listen，或同样用 goroutine。

> 📝 **面试**：关键是 **谁负责等信号、谁调 Shutdown**，两种写法都行。

### 再追问

**errgroup 两个 Go？**——一个 Listen，一个等 ctx 后 Shutdown（见知识点 [八]）。

## Q14

**★★★★★｜读代码找问题**

```go
func main() {
    srv := &http.Server{Addr: ":8080", Handler: mux}
    signal.Notify(sig, syscall.SIGTERM)
    go srv.ListenAndServe()
    <-sig
    srv.Shutdown(context.Background())
}
```

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [三、优雅退出模板](知识点.md)、[五、超时与资源保护](知识点.md)

### 完整解答

> 🎯 **一句话**：**Shutdown 无超时**（Background 永不 deadline）；**未处理 ListenAndServe 错误/ErrServerClosed**；**无 ReadHeaderTimeout**；**sig 未 make/Notify 完整**（片段）。

```go
shutCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
if err := srv.Shutdown(shutCtx); err != nil { ... }
```

> 📝 **面试**：Shutdown 无 timeout 可能 hang 到 K8s SIGKILL。

### 再追问

**Shutdown(context.Background()) 永远等？**——若 handler 不退出，**是**——必须 WithTimeout。
