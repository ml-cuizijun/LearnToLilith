## Q1

**★★★★★｜Go 服务 CPU 高，你怎么开 pprof？最小代码是什么？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、开启：怎么把 pprof 开起来](知识点.md)

### 场景

活动高峰 `game-api` P99 飙高，开发说「我本地复现不了」。你需要在测试 Pod 上先采证，再讨论要不要重启。


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`import _ "net/http/pprof"` + **独立端口** `ListenAndServe("127.0.0.1:6060", nil)`，再 `curl profile?seconds=30` 落盘。

最小代码三行：

```go
import (
    _ "net/http/pprof"   // 副作用注册到 DefaultServeMux
    "net/http"
)
go func() {
    http.ListenAndServe("127.0.0.1:6060", nil) // 只绑 loopback
}()
```

采集 + 分析两步：

```bash
kubectl port-forward pod/game-api-xxx 6060:6060
curl -s 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o cpu.prof
go tool pprof -http=127.0.0.1:0 cpu.prof   # ← 浏览器看火焰图
```

> ⚠️ **别混**：`import _ "net/http/pprof"` 注册到的是 **DefaultServeMux**，若业务路由也在 Default 上会混在一起——更干净的是独立 mux 或独立进程。生产**绝不**把 `/debug/pprof` 挂在公网 8080 与 API 同端口裸奔。

> 📝 **面试**：答完代码补一句「loopback + port-forward 或内网鉴权，不暴露公网」，就比只写代码高一档。

### 再追问

**不用 HTTP 怎么采？**——用 `pprof.StartCPUProfile(f)` 直接写文件，适合定时任务、信号触发（`SIGUSR1`）或测试基准。`go test -bench=. -cpuprofile=cpu.test` 用的就是这个底层 API，格式和线上一样，但**负载不同，别用单测 profile 代表线上**。

**`DefaultServeMux` 和业务路由混用有什么风险？**——路由注册在同一 mux 上可能路径冲突；某条 `/debug/pprof/` 子路径被业务中间件拦截后 pprof 工具无法取 symbol。更干净的是 `mux := http.NewServeMux()` 手动注册，或把 pprof 独立成侧车进程。

## Q2

**★★★★★｜CPU profile 是采样还是追踪？大概什么频率？为什么不是每条函数都记？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、采样：CPU profile 原理](知识点.md)

### 场景

面试官：「pprof CPU 图准吗？为什么不是每条函数都记？」有人答「Go 会记录所有函数调用」，被追问就卡住。


语言最小集命令。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**SIGPROF 定时中断采栈**（约 100Hz），统计各栈出现占比，不是逐条 trace。

Go runtime 设置一个 **SIGPROF** 信号定时器，大约每 10ms 触发一次（≈100Hz）。每次中断时抓取当前正在执行的 goroutine 调用栈，把这条栈作为**一个样本**累加进 profile。30 秒采集约 3000 个样本，按栈聚合后就能看出「哪些栈最常出现在 CPU 上」。

```text
定时器 ~100Hz  ->  SIGPROF 中断  ->  runtime 抓当前 goroutine 栈
                                         |
                                    样本 +1（按栈聚合）
                                         |
                                    30s ≈ 3000 样本
```

**为什么不是逐条记录**：逐条 trace 的开销太大（每个函数调用都记 = 性能被 profiling 搞垮），统计采样在**热点定位**上足够准——哪个函数吃 CPU 多，样本占比就高。代价是**不擅长捕捉极短尖刺**（小于 10ms 的偶发事件可能采不到）。

> ⚠️ **别混**：CPU profile **看不到** IO wait 占满——进程在等 IO 时 CPU 是空闲的，SIGPROF 中断到了也在 `syscall` 里，样本占比很低，看起来「很空」。这时要看 `top` 的 `%wa` 或用 `go tool trace` 看调度延迟。

> 📝 **面试**：「准确吗？」——统计意义上足够定热点；**短于 10s** 易受毛刺影响；**多核**要采够时长覆盖所有 P；不能替代 trace 看调度延迟。

### 再追问

**和 `go test -cpuprofile` 的关系？**——底层都是 `runtime/pprof`，**格式相同、分析命令一样**。但测试负载 ≠ 生产负载，别用单测 profile 代表线上。测试 profile 适合做**优化前后对比**的基线。

**`runtime.SetCPUProfileRate` 能调高频率吗？**——能，但生产别乱调。频率越高开销越大，100Hz 是 Go 团队权衡后的默认值。调到 1000Hz 会让 profiling 自身吃掉不少 CPU，样本里会出现 pprof 自己的栈。

## Q3

**★★★★☆｜`curl profile` 30 秒没返回，是 hang 了吗？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [八、采集与传输：从 Pod 到本地](知识点.md)

### 场景

oncall 执行 `curl .../profile?seconds=30`，终端 20 秒无输出，新人准备 Ctrl+C 重来。


现象决定 profile。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**正常**——CPU profile 要采满 `seconds` 才返回 HTTP body，不是 hang。

```bash
curl -v 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o cpu.prof
# 等待约 30s 后收到 gzip 二进制   # ← 采满 seconds 才 flush
```

CPU profile 的 HTTP handler 在收到请求后启动一个定时采样循环，采满 `seconds` 秒才把聚合好的 profile 二进制写到 HTTP response body。这期间连接一直保持，`curl` 无输出是正常的。

区分其他端点：**heap** 和 **goroutine** 端点应**立即返回**（它们是快照，不是采集过程）。如果 heap 也 hang，那才是真有问题——可能是进程卡在 GC STW 或死锁。

> 🔍 **现场**：需要更快可先 `seconds=10`，但生产定责建议 30s——短于 10s 易受毛刺影响，样本太少不足以定热点。

### 再追问

**能否异步采？**——可用代码里 `pprof.StartCPUProfile(f)` + 信号触发（`SIGUSR1`），或 sidecar 定时采；HTTP 方式是同步等采完。线上常见做法：给进程注册 `signal.Notify(SIGUSR1)`，收到信号后写 profile 到固定路径，运维 `kill -USR1 <pid>` 触发，不阻塞 HTTP。

**全套采集脚本怎么写？**

```bash
PPROF=http://127.0.0.1:6060
STAMP=$(date +%Y%m%d-%H%M%S)
mkdir -p "/tmp/pprof-$STAMP" && cd "/tmp/pprof-$STAMP"
curl -s "$PPROF/debug/pprof/profile?seconds=30" -o cpu.prof
curl -s "$PPROF/debug/pprof/heap" -o heap.prof
curl -s "$PPROF/debug/pprof/goroutine?debug=2" -o goroutine.txt
ls -lh   # ← 一次性拿到 CPU + heap + goroutine 三件套
```

## Q4

**★★★★★｜`top` 里 flat 和 cum 分别是什么？优化看谁？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [七、读图：go tool pprof 与火焰图](知识点.md)

### 场景

火焰图最宽是 `json.Marshal`，`flat` 不高但 `cum` 很高，开发不知道该改哪。


怎么开 pprof。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**flat** = 函数体内耗时（不含子调用）；**cum** = 含下游所有子调用——`cum` 高要 `list` 往下追到 `flat` 最高的那个才是真正该改的。

```text
(pprof) top10
# Showing nodes accounting for 2.10s, 95% of 2.21s total
# flat  flat%   sum%        cum   cum%
# 0.82s 37.10% 37.10%      1.95s 88.24%  encoding/json.Marshal  # ← cum 高，热量在子调用
# 0.41s 18.55% 55.66%      0.41s 18.55%  runtime.mallocgc        # ← flat 高，自身烧 CPU
```

**读图**：`json.Marshal` 的 `cum` 1.95s 但 `flat` 只有 0.82s，说明有 1.13s 花在它调用的子函数上（如 `runtime.mallocgc`）。优化 `Marshal` 本身能省 0.82s，优化子调用（减少分配）能省 1.13s。

交互命令链：

```text
(pprof) top10              # 按 flat 排序，找前 10 热点
(pprof) list Marshal        # 正则匹配函数，带源码行占比
(pprof) peek json          # 看谁调用 json（调用链上游）
(pprof) web                # graphviz 调用图
```

**两种优化策略**：

| 情况 | 信号 | 优化方向 |
|------|------|----------|
| `flat` 高 | 函数自身烧 CPU | 换算法、减少循环、用 `[]byte` 池化 |
| `cum` 高但 `flat` 低 | 热量在下游子调用 | `list` 往下追到 `flat` 最高的子函数，减调用次数或优化它 |

### 再追问

**`runtime.mallocgc` cum 高怎么办？**——转 **heap profile** 看分配热点，可能是对象创建过多。`mallocgc` 本身不可优化，要减少的是**谁在分配**——`list` 往上看调用方，通常是 `json.Marshal`、`fmt.Sprintf`、`make([]byte, n)` 这类分配大户。

**火焰图里 `runtime.*` 宽条怎么看？**——往上看业务谁触发的（分配多→`mallocgc`、反射多→`runtime.assertE2T`、锁竞争→`runtime.procyield`）。`runtime` 宽不是 Go 的问题，是业务代码选了高开销的操作。

## Q5

**★★★★★｜OOM 前你看 heap 的 inuse 还是 alloc？为什么有人抓了 alloc 说「都是正常的」？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、内存：heap profile 的 inuse 与 alloc](知识点.md)

### 场景

Pod RSS 持续上涨最终被 OOMKilled，有人抓了 `alloc_space` top 全是历史分配，说「都是正常的」。


生产怎么挂 endpoint。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：泄漏查 **`inuse_space` / `inuse_objects`**；分配压力查 **`alloc_space` / `alloc_objects`**——OOM 是泄漏，看 inuse。

四种 heap sample_index 视角：

| 模式 | 含义 | 何时用 |
|------|------|--------|
| `inuse_space` | 当前堆上字节 | OOM、RSS 涨 |
| `inuse_objects` | 当前对象个数 | 小对象泄漏 |
| `alloc_space` | 累计分配字节 | GC 压力、热点分配 |
| `alloc_objects` | 累计分配次数 | 高频 `new` |

```bash
curl -s 'http://127.0.0.1:6060/debug/pprof/heap' -o heap1.prof
# 等 5 分钟
curl -s 'http://127.0.0.1:6060/debug/pprof/heap' -o heap2.prof
go tool pprof -sample_index=inuse_space -top heap2.prof
# 512.10MB 62.01% 62.01%  512.10MB 62.01%  bytes.(*Buffer).Grow  # ← inuse 只增不减 = 泄漏
```

> 💡 **打个比方**：`alloc` 像「这辈子一共买过多少碗面」；`inuse` 像「冰箱里现在还剩几碗」——吃得多不一定胖，剩得多才占地方。同事抓了 `alloc` 说「都正常」，是因为**历史分配**里很多东西早就释放了，不占内存；要看的是 `inuse`——此刻还活着的。

**为什么 alloc 大但 inuse 正常？**——说明**分配频繁但回收及时**，是**分配压力**而非泄漏。对策：优化对象池（`sync.Pool`）、减少分配（`[]byte` 池化、`strings.Builder` 代替 `fmt.Sprintf`），而不是去找泄漏。

> ⚠️ **别混**：mmap、栈、CGO 内存**不一定全在 heap profile 里**——heap profile 只记 Go 堆分配器（`mallocgc`）分配的对象。RSS 比 heap 大很多时，要结合 `GODEBUG=gctrace=1`（看 GC 频率和堆大小）和系统级 `/proc/<pid>/status` 的 `VmRSS` 互证。

### 再追问

**`heap?debug=1` 文本怎么读？**

```text
# heap profile: 847: 120340232 [1923: 280451120] @ heap/1048576
#   1: 67108864 [1: 67108864] @ 0x... 0x... main.leakyCache
        ^ inuse_bytes  ^ alloc_count   # ← 行首是 inuse，括号里是 alloc 累计
```

行首第一个数字是 **inuse 字节数**，方括号里是 `[inuse_count: alloc_bytes]`，`@` 后是分配栈。适合快速肉眼扫重复模式，不用开 `go tool pprof`。

**怎么确认是真泄漏？**——间隔 5 分钟采两次 heap，对比同一栈的 inuse 是否只增不减。如果两次 inuse 差不多、不随负载涨，那不是泄漏；如果每次都涨且不回落，就是泄漏。

## Q6

**★★★★★｜goroutine 从 200 涨到 5 万，怎么查？泄漏的三大经典根因是什么？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、协程与阻塞：goroutine / block / mutex](知识点.md)

### 场景

`curl /metrics` 里 `go_goroutines` 持续涨，CPU 不高，接口偶发超时。


CPU 采样原理。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`goroutine?debug=2` 看**重复栈**——同一 `main.worker:88` 出现上万次即泄漏。

```bash
curl -s 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2' -o gor.txt
grep -c '^goroutine' gor.txt
# 48291   # ← 上万就要警惕

grep -A3 'chan receive' gor.txt | sort | uniq -c | sort -rn | head
# 48291 chan receive
# main.worker(...)
#     /app/worker.go:88   # ← 同一栈重复上万次 = 泄漏
```

**读图**：`debug=2` 输出每个 goroutine 的完整调用栈，带 goroutine 编号和阻塞原因（`[chan receive]`、`[select]`、`[semacquire]`）。同一栈重复成千上万次 = **泄漏**。

**三大经典根因**：

- **context 未 cancel**：启动了 `go func()` 处理请求，请求超时后 context 没传播到 goroutine，它还在等 channel 永远不来的消息。
- **consumer 未退出**：worker pool 的消费者从 channel 读数据，shutdown 时没关闭 channel，consumer 永久阻塞在 `chan receive`。
- **time.Ticker 未 Stop**：`time.NewTicker` 创建后 defer `Stop()` 忘了写，Ticker 内部的 goroutine 一直活着。每次请求创建一个不 Stop，泄漏一个。

> ⚠️ **别混**：**goroutine 多 ≠ 泄漏**——高并发服务常驻数万 goroutine 可能正常（每个 HTTP 请求一个 goroutine）。要看**是否随负载回落**：请求量降下来后 goroutine 数也降，那不是泄漏；只涨不降才是泄漏。

> 📝 **面试**：「怎么查 goroutine 泄漏？」——`goroutine?debug=2` 看重复栈；结合 `pprof` 的 `traces` 视图看聚合；修 **context 取消传播**、**consumer 退出机制**、**Ticker `defer Stop()`**。

### 再追问

**和 block profile 怎么配合？**——栈卡在 `chan receive` 时开 `SetBlockProfileRate(1)` 采 block，量化每个阻塞点的**阻塞时间**。goroutine profile 告诉你「有多少 goroutine 卡在某行」，block profile 告诉你「总共卡了多久」——两个维度合起来才能判断优先修哪个。

**无界 `go func()` 怎么治？**——加 worker pool 或信号量限流（`make(chan struct{}, N)`），别每个请求都 `go` 一个不限量的 goroutine。`errgroup.WithContext` + `SetLimit(N)` 是 Go 标准的限流方案。

## Q7

**★★★★☆｜`/debug/pprof/block` 下载是空的，为什么？mutex 也一样吗？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、协程与阻塞：goroutine / block / mutex](知识点.md)

### 场景

怀疑锁竞争，curl block 得到几乎空文件，`go tool pprof -top` 无输出。mutex 端点也一样。


heap inuse vs alloc。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：block/mutex 默认**未开启采样**——要先 `runtime.SetBlockProfileRate` / `SetMutexProfileFraction`，否则端点返回空 profile。

```go
import "runtime"
func init() {
    runtime.SetBlockProfileRate(1)     // 记录阻塞 >1ns 的事件
    runtime.SetMutexProfileFraction(5) // 每 5 次锁竞争记录 1 次
}
```

两个 API 参数语义不同：

- **`SetBlockProfileRate(n)`**：`n` 是纳秒阈值，阻塞时间 > n 的事件才记录。`1` = 记录所有 >1ns 的阻塞（全量，开销大）；生产可设 `10000`（10us）降开销。
- **`SetMutexProfileFraction(n)`**：`n` 是采样比例，每 `n` 次锁竞争记录 1 次。`5` = 采样 20%。`0` = 关闭。

```bash
curl -s 'http://127.0.0.1:6060/debug/pprof/block' -o block.prof
go tool pprof -top block.prof
# sync.(*Mutex).Lock   # ← 锁竞争热点
# runtime.chanrecv      # ← channel 阻塞热点
```

> ⚠️ **别混**：block profile 的采样本身有**开销**——`rate=1` 时每次 channel 操作、锁操作都记栈，高并发服务会明显变慢。生产建议 `rate=10000`（10us）以上；mutex fraction `5` 也够用，不需要 `1`（全量）。改完后重启服务再采。

### 再追问

**开了 block 后服务变慢？**——说明 `SetBlockProfileRate(1)` 太激进，每次纳秒级阻塞都记栈。调大到 `10000`（10us）或 `100000`（100us），只记长阻塞，开销骤降。

**mutex profile 和 `sync.Mutex` 争用日志区别？**——pprof 给**聚合栈**（哪个 `Lock` 调用竞争最多），适合定位；日志只能点状记录，适合定性后定量。生产用 pprof 定位热点，日志补充时序。

## Q8

**★★★★☆｜火焰图怎么读？什么叫「平顶」？runtime 宽条怎么看？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [七、读图：go tool pprof 与火焰图](知识点.md)

### 场景

`go tool pprof -http` 打开火焰图，开发说「全是色块看不懂」。


就是对着 mallocgc 发呆的拆穿。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**宽 = 热点**；**平顶 = 单函数长时间占 CPU**（忙等、密集计算）；**尖塔深**看最宽那层；`runtime.*` 宽要往上看业务谁触发。

> 💡 **打个比方**：火焰图横轴是 CPU 时间占比（不是时间线！），纵轴是调用栈深度。想象一摞积木，越宽的积木吃 CPU 越多。「平顶」就是一块积木特别宽但上面没叠多少层——这个函数自己在烧 CPU，没怎么调子函数。

四种典型模式：

```text
  宽 = 该栈样本占比大 = CPU 热点
  平顶 = 长时间占 CPU 的单函数（忙等、正则灾难、加密）
  尖塔深 = 调用链深，但看最宽的那层才是优化目标
  runtime.* 宽 -> 往上看业务谁触发（分配、锁、反射）
```

```bash
# 打开 Web UI
go tool pprof -http=127.0.0.1:0 cpu.prof
# View -> Flame Graph
```

常见宽条解读：

- `encoding/json` 宽 → `list Marshal` 看哪一行在分配或反射
- `regexp` 平顶 → 灾难性回溯或超大正则编译
- `runtime.mallocgc` 宽 → 分配多，转 heap profile 看谁在分配
- `runtime.scanobject` 宽 → GC 扫描多，说明堆上对象多，可能泄漏
- `sync.(*Mutex).Lock` 宽 → 锁竞争，开 mutex profile

### 再追问

**`-s -w` 构建的二进制火焰图缺符号？**——用带符号的 debug 构建，或保留 symbol 表的分支制品。`go build -ldflags="-s -w"` 会 strip 符号表，火焰图全是十六进制地址。生产镜像建议用 `-ldflags="-w"`（去掉 DWARF 调试信息但保留符号表），文件略大但 pprof 能读。

**火焰图上下翻转的区别？**——Go pprof 火焰图默认「宽底窄顶」（root 在下、叶子在上），和 Brendan Gregg 原版（root 在上）相反。看的时候注意方向，宽条永远是优化目标，方向不影响判断。

## Q9

**★★★★★｜生产暴露 pprof 有哪些安全做法？pprof 能泄露什么？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [九、生产安全：pprof 暴露的管控](知识点.md)

### 场景

安全审计发现 `game-api` 的 8080 上 `/debug/pprof/heap` 公网可访问，可被拖库式采 heap。


goroutine 泄漏。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**独立端口 + 127.0.0.1 / 内网 + Bearer 鉴权**，绝不与公网 API 同端口裸奔。

三种安全做法：

```go
// 做法 A：仅 loopback
http.ListenAndServe("127.0.0.1:6060", nil)

// 做法 B：内网 + Bearer 鉴权
func pprofHandler(token string) http.Handler {
    mux := http.DefaultServeMux
    if token == "" {
        return mux
    }
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") != "Bearer "+token {
            http.Error(w, "forbidden", http.StatusForbidden)
            return
        }
        mux.ServeHTTP(w, r)
    })
}

// 做法 C：K8s 不暴露到 Ingress，用 NetworkPolicy 限制
```

**pprof 能泄露什么**——属于**敏感调试面**：

- **heap profile**：堆上对象内容（部分可见）、内存布局、数据结构大小。
- **goroutine stack**：完整调用栈，暴露内部包路径、函数名、行号——等于源码地图。
- **CPU profile**：函数占比、调用关系——等于性能画像，攻击者知道你哪里慢就能针对性打。
- **symbol 端点**：直接反查函数名，配合二进制就能定位代码。

按生产密钥级别管控：6060 端口不配 Service、不走 Ingress，用 `kubectl port-forward` 或 NetworkPolicy 限制只有运维网段可达。

> ⚠️ **别混**：pprof 安全靠**网络隔离 + 鉴权**，不靠把端口改大数字（改到 65530 还是会被扫到）。也别靠「没人知道路径」——`/debug/pprof/` 是 Go 社区共识的默认路径，扫描工具会自动尝试。

> 📝 **面试**：「生产怎么暴露 pprof？」——答「独立端口 + loopback / 内网鉴权，K8s 用 port-forward 不走 Ingress」，再补「pprof 暴露堆栈和内存布局属于敏感调试面」，就比只答「开 6060」高一档。

### 再追问

**用 pprof 当健康检查端点行不行？**——**不要**。健康检查是公开的（LB 要探），pprof 是敏感的。混在一起要么健康检查暴露 pprof，要么 pprof 被 LB 探活打乱。分开两个 mux、两个端口。

**Service Mesh 下怎么控？**——Istio/Linkerd 的 mTLS 会加密 mesh 内流量，但 pprof 如果挂 6060 且不在 mesh 策略里，仍可能被旁路访问。最稳的还是**只绑 loopback**，port-forward 时走 kubelet 的 TLS。

## Q10

**★★★★☆｜CPU profile 很空，但 P99 很高，下一步怎么查？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [二、入口：现象决定 profile 选型](知识点.md)

### 场景

profile 30s 后 top 全是 `runtime`，业务函数占比极低，用户仍喊卡。


block/mutex。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：可能是 **IO wait、下游慢、锁等待**——CPU 采样采不到等待时间，SIGPROF 中断到了进程在 `syscall` 里，样本看起来「空」。

排查路径按优先级走：

```text
- top / pidstat 看 %wa、iowait          # ← CPU bound 还是 IO wait
- goroutine?debug=2 看是否大量阻塞      # ← 卡在 chan/锁/IO
- go tool trace（短采 1~5s）看调度与网络  # ← 调度延迟、GC STW
- 日志 + DB/Redis 慢查询                  # ← 下游慢
- 若已开 block/mutex 再采                 # ← 量化阻塞时间
```

CPU profile 空 + P99 高的经典场景：

- **DB 慢查询**：goroutine 全卡在 `database/sql.(*DB).conn` 等连接池，CPU 不高但请求全排队。看 DB 慢日志 + `SHOW PROCESSLIST`。
- **Redis 大 key**：goroutine 卡在 `net.(*conn).Read`，等 Redis 返回大 value。看 Redis `SLOWLOG` + `--bigkeys`。
- **锁竞争**：goroutine 卡在 `sync.(*Mutex).Lock`，一个 goroutine 拿着锁做慢操作，其他全排队。开 mutex profile 量化。
- **GC STW**：`runtime.scanobject` 在 CPU profile 里偶尔出现，但 STW 时间要看 `go tool trace` 或 `GODEBUG=gctrace=1`。

> ⚠️ **别混**：pprof **不能替代**全链路 APM；metrics 的 RED（Rate/Errors/Duration）与 pprof 互证——P99 高是 metrics 说的，pprof 告诉你**为什么高**。如果 pprof 空，说明瓶颈不在 CPU 计算，在**等待**，要换工具。

### 再追问

**何时用 `go tool trace`？**——调度延迟、GC STW、网络阻塞的**毫秒级时序**；开销大，采 1～5 秒即可。trace 能看到「某个 goroutine 在 t=100ms 被 GC STW 挂起，t=130ms 恢复」，这是 pprof 做不到的。

**怎么判断是 IO wait 还是 CPU bound？**——`top -p <pid>` 看 `%wa` 列。`%wa` > 5% 且 `%cpu` 不高 → IO wait；`%cpu` 高且 `%wa` 低 → CPU bound。Go 的 `runtime/trace` 里的 `Syscall` 和 `Network` block 也能区分。

## Q11

**★★★★☆｜怎么对比优化前后的 CPU profile？两次采的 QPS 不同怎么办？**

**覆盖**：常用 ｜ **对应**：知识点 [七、读图：go tool pprof 与火焰图](知识点.md)

### 场景

开发声称「优化了 JSON」，你要验证上线效果。但两次采集的时段 QPS 不一样。


火焰图怎么读。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：发布前后各采 30s，用 **`-base`** 看增量；QPS 不同尽量同负载时段采，或口述承认偏差。

```bash
# 上线前
curl -s 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o cpu-before.prof
# ... 上线优化 ...
curl -s 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o cpu-after.prof

# 对比
go tool pprof -base cpu-before.prof cpu-after.prof
# 看增量：正数 = 优化后占比更高（变差），负数 = 占比下降（变好）
```

**读图**：`-base` 模式下，pprof 显示的是 `after - before` 的**差值**。关注目标函数（如 `json.Marshal`）的 flat 是否变负（占比下降）。同时看 P99 指标，避免只优化 CPU 占比不优化尾延迟。

**QPS 不同时的偏差**：pprof 的 `flat`/`cum` 是**百分比**，不是绝对值。QPS 高时总样本多，但占比分布应该相似——如果热点函数不变，占比应该稳定。如果 QPS 差异大（如 1000 vs 10000），建议：

- 尽量在**相同流量时段**采（如都在午高峰）
- 或结合 `rate(requests)` 指标归一化口述，承认样本偏差
- 关注**火焰图形状**而非绝对百分比——形状变了才是真变化

### 再追问

**除了 `-base` 还有别的对比方式吗？**——`go tool pprof -diff` 是等价的（新版别名）。更直观的是把两次火焰图截图并排放，肉眼看宽度变化。`-http` UI 里也有 `View -> Diff`。

**优化后 CPU 更高了怎么办？**——先看是不是采样偏差（采了不同负载时段）。确认同负载后再采一轮。如果确实更高，可能是优化引入了新热点（如对象池化减少了分配但增加了锁竞争），要看火焰图里**哪个函数变宽了**。

## Q12

**★★★★☆｜K8s 里怎么采 Pod 的 pprof？容器里没有 go tool 怎么办？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [八、采集与传输：从 Pod 到本地](知识点.md)

### 场景

容器里只有 curl（或 wget），没有 `go tool`，要在笔记本上分析。


从 Pod 捞 profile。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**port-forward 6060** → 本机 `curl` 落盘 → 本机 `go tool pprof` 分析，不依赖容器里有 Go 工具链。

```bash
# Step 1: port-forward 到 Pod
kubectl port-forward -n game pod/game-api-7d9f8-abcde 6060:6060
# Forwarding from 127.0.0.1:6060 -> 6060   # ← 建立隧道

# Step 2: curl 采集（另开终端）
curl -s 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o cpu.prof
curl -s 'http://127.0.0.1:6060/debug/pprof/heap' -o heap.prof
curl -s 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2' -o gor.txt

# Step 3: 本机分析
go tool pprof -http=:0 cpu.prof   # ← 浏览器看火焰图
```

**读图**：profile 文件是 gzip 二进制，和容器里有没有 `go tool` 无关——Go 的 profile 格式是跨平台的标准 protobuf/gzip，只要本机有 `go tool pprof` 就能分析。

**若应用未开 6060**：需开发加 `import _ "net/http/pprof"` + 独立端口，或加 sidecar 容器。**不要**在生产镜像里长期装 graphviz——分析在本地做，容器越小越好。

> 🔍 **现场**：port-forward 断了？——K8s 的 port-forward 依赖 kubelet 与 Pod 的隧道，网络波动会断。长采（30s CPU profile）期间断了要重采。建议先 `curl /debug/pprof/` 索引页确认连通，再采。

### 再追问

**Ephemeral debug 容器（K8s 1.23+）能干什么？**——`kubectl debug` 可以临时带工具（`go`、`dlv`、`graphviz`）进 Pod 的 netns，但 pprof 仍要**进程内已暴露 HTTP 端点**——debug 容器进的是网络命名空间，不是进程空间，不能直接读 Go runtime 内存。它可以 curl Pod 的 6060，省掉 port-forward。

**多副本怎么采？**——每个副本各采一份 profile，看是否同栈。同栈 = 代码热点（所有副本都一样的函数宽），不同栈 = 流量倾斜（某个副本被多打或少打）。对比时 `-base` 用副本 A 的 profile 作 baseline。

## Q13

**★★★★☆｜接到「CPU 100%」告警，60 秒内你敲什么？别做什么？**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [十、踩坑清单](知识点.md)

### 场景

告警群炸锅，有人要直接滚动重启，你需要先留证再讨论。


生产暴露管控。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**先 port-forward + profile 落盘，再讨论重启**——采证比快速恢复重要，重启后根因就没了。

60 秒剧本：

```text
0-10s   确认 Pod/进程、port-forward 6060、curl /debug/pprof/ 通
10-40s  curl profile?seconds=30 落盘（同步等待采满）
40-50s  go tool pprof -top 看前三名 flat
50-60s  口述「热点函数 + 建议改法」，留文件路径给开发
```

```bash
kubectl port-forward pod/game-api-xxx 6060:6060 &
curl -s 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30' -o /tmp/cpu-$(date +%H%M).prof
go tool pprof -top /tmp/cpu-1430.prof
# Showing nodes accounting for 2.10s, 95% of 2.21s total
# flat  flat%   sum%        cum   cum%
# 0.82s 37.10% 37.10%      1.95s 88.24%  encoding/json.Marshal   # ← 热点确认
```

**别做**：

- **未采证就 `kill -9`**——重启后指标绿了，根因还在，下次高峰还会炸
- **未确认就调 `GOMAXPROCS`**——GOMAXPROCS 改大可能让 GC 和调度更忙（见 [12](../12-GOMAXPROCS与容器cgroup/)）
- **只看平均 CPU**——P99 抖要看火焰图分布，平均 CPU 不高不代表没有偶发尖刺
- **只调 `GOGC` 不看泄漏**——内存涨可能是泄漏，调 GOGC 只能改 GC 频率，治不了泄漏

### 再追问

**多副本都 100% CPU？**——每个副本各采一份，看是否同栈。同栈 = 代码热点（所有副本都一样的函数宽），改代码；不同栈 = 流量倾斜（某个副本被多打），查负载均衡和 Pod 分布。

**来不及采 30s 怎么办？**——先 `seconds=10` 采短的留证，再 `seconds=30` 采长的。10s 的样本少但能看出最大热点；30s 的才够定细节。**至少留一份**再重启。

## Q14

**★★★★★｜白板：默画「一次 pprof 采样的一生」并标出 CPU/heap/goroutine 三分支。**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [一、一张图：一次 pprof 采样的一生](知识点.md)

### 场景

终面要求「合上书讲清 pprof 全流程」，限时 3 分钟。


本套题收尾：别重启当根因。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**选型 → 开启 → 采样 → 导出 → 分析 → 定责**，三类 profile 在「选型」处分叉，在「分析」处汇合到 `go tool pprof`。

主图六段口述：

```text
入口：CPU高 / 内存涨 / 卡住 -> 选 profile / cpu / heap / goroutine
开启：net/http/pprof 或 runtime API；block/mutex 需 SetRate
采样：CPU 中断采栈（SIGPROF ~100Hz）；heap 分配记栈；goroutine 快照
导出：curl -o 落盘；K8s port-forward
分析：top / list / -http 火焰图；flat vs cum；inuse vs alloc
定责：改代码 -> 再采对比（-base）
```

三分支在「采样」段的不同：

| profile | 触发方式 | 记什么 | 默认开启 |
|---------|----------|--------|----------|
| CPU | SIGPROF 定时中断 | 当前 goroutine 调用栈 | 是（`?seconds=30`） |
| heap | 内存分配器钩子 | 分配时的调用栈 | 是（`?debug=1`） |
| goroutine | 全量快照 | 每个 goroutine 当前栈 | 是（`?debug=2`） |
| block | 阻塞事件钩子 | 阻塞时间和调用栈 | 否（`SetBlockProfileRate`） |
| mutex | 锁竞争采样 | 锁等待的调用栈 | 否（`SetMutexProfileFraction`） |

> 📝 **面试**：收尾一句「metrics 发现病，pprof 找病灶，重启不代替根因」——这句话区分「背过」和「懂了」。

### 再追问

**说出两个 pprof 不能保证的事？**

- **不直接解释外部 IO/DB 慢**——CPU profile 采不到等待时间，要看 goroutine + trace + 日志
- **不代替分布式链路追踪**——pprof 是进程内的，跨服务调用要 APM/OpenTelemetry

**`runtime/pprof` 和 `net/http/pprof` 的区别？**——`runtime/pprof` 是底层库（`StartCPUProfile`、`WriteHeapProfile`），适合写文件、测试基准；`net/http/pprof` 在其上封装了 HTTP handler，注册到 DefaultServeMux，适合线上常驻。两者生成的 profile 文件**格式相同**，分析命令一样。
