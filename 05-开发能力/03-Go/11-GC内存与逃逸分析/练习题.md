## Q1

**★★★★★｜Go 里「逃逸分析」是什么？谁决定对象在栈还是堆？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、出生：编译器逃逸分析决定栈还是堆](知识点.md)

### 场景

面试开场就问。有人答「程序员用 `new` 就堆、用 `var` 就栈」，有人答「小对象栈、大对象堆」。追问「那 `new(int)` 一定堆吗」就卡住。


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**编译器**在编译期分析变量生命周期与引用，能证明不越过函数边界 → 可能栈分配；否则堆分配（逃逸）——程序员没有 `stack`/`heap` 关键字。

Go 没有 `malloc`/`free`，也没有 `stack`/`heap` 关键字。编译器做逃逸分析（escape analysis）：如果一个变量的引用不越过函数边界（不被返回、不存进 global/map/channel、不被闭包捕获逃出），编译器可以把它分配在栈上，函数返回时栈帧弹出自动销毁。否则，编译器必须把它「移动到堆」，由 GC 追踪回收。

```go
func stackOK() int {
    x := 42
    return x // ← 返回值拷贝，x 可栈分配
}

func heapEscape() *int {
    x := 42
    return &x // ← x escapes to heap：调用方仍持有指针
}
```

`new(T)` 返回指针但**不一定**堆分配——编译器能证明不逃逸则栈。`make([]T, n)` 的 slice header 可能栈上，但底层数组往往在堆。别凭「用了 `new` 就堆」的直觉判逃逸，**以 `-m` 输出为准**。

> ⚠️ **别混**：「小对象栈、大对象堆」是粗略直觉，不是规则。决定因素是**引用是否越过函数边界**，不是大小。大局部数组也可能栈分配（看大小阈值和编译器决策）。问「怎么放栈」→ 改代码让编译器不逃逸，不是加语法。

> 📝 **面试**：Go 自动管理内存，优化目标是**少逃逸、少 alloc**。答逃逸分析要说到「编译期决策」和「引用边界」两个关键词，别只答「大的堆小的栈」。

### 再追问

**栈分配能手动 free 吗？**——不能，随栈帧弹出自动销毁，没有 `free()`。这也是 Go 没有 `free` 的原因——栈的不用 free，堆的 GC 管。

**`new` 和 `make` 的区别？**——`new(T)` 返回 `*T` 指向零值；`make` 只用于 slice/map/chan，返回**已初始化**的 T（不是 `*T`）。两者都可能栈或堆，取决于逃逸分析。

## Q2

**★★★★★｜为什么 `return &x`（x 是局部变量）会逃逸到堆？返回值拷贝就不逃逸吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、出生：编译器逃逸分析决定栈还是堆](知识点.md)

### 场景

代码评审发现热路径上大量 `func newUser() *User { u := User{}; return &u }`，每次调一个 newUser 就堆分配一个 User。有人问「为什么返回指针就堆，返回值就不堆」。


诊断命令——承接逃逸主线。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：函数返回后栈帧销毁，**调用方仍持有指针**——编译器必须把 `x` 放到堆上保活，否则指针指向已回收的栈内存。

```go
func f() *int {
    x := 42
    return &x // ← escapes to heap：x 的地址越过函数边界
}

func g() int {
    x := 42
    return x // ← 返回值拷贝，x 可栈分配
}
```

```text
f():  x 在栈上 → 函数返回栈帧弹出 → 但 &x 仍被调用方持有 → 悬空指针！
      编译器发现这个问题 → 把 x 移到堆上 → GC 追踪 → 调用方不再引用后回收

g():  x 在栈上 → return 时拷贝 x 的值给调用方 → 函数返回栈帧弹出 → x 销毁
      调用方拿到的是拷贝，不引用 x 的地址 → 无悬空指针风险 → x 可栈分配
```

这就是逃逸分析的核心逻辑：**变量的地址是否被外部持有**。`return &x` 把 `x` 的地址交给了调用方，`x` 的生命周期超过了函数——必须堆分配。`return x` 只拷贝值，`x` 本身不逃逸。

返回大 struct 值时，值拷贝有成本，但**不逃逸**——权衡 copy vs pointer escape：拷贝贵但不增加 GC 压力，返回指针省拷贝但每次堆分配。热路径上往往选拷贝（或预分配 buffer）。

> ⚠️ **别混**：返回 `&x` 逃逸的是 **x 本身**，不是指针。指针本身可能栈上（作为返回值），但 x 必须在堆上才能被合法引用。

> 📝 **面试**：问「返回指针和返回值的区别」，答三点：① 返回指针 → 局部变量逃逸堆，GC 压力增加；② 返回值 → 值拷贝，可能栈分配但拷贝成本；③ 热路径权衡——小值返回值、大值看场景（预分配或 Pool 比返回指针更好）。

### 再追问

**那 `return &x` 一定逃逸吗？**——几乎一定，除非编译器能证明调用方不持久持有指针（极端内联场景）。**以 `-m` 为准**，别靠口诀。

**返回 `*User` 和返回 `User` 哪个快？**——看场景。小 User 返回值拷贝便宜且零 alloc；大 User 返回指针省拷贝但堆分配。最佳方案往往是**传入 buffer/Pool 复用**，不 new 也不拷贝。

## Q3

**★★★★★｜如何用命令行查看逃逸？输出里看什么？二级 -m 和 -l 各干什么？**

**覆盖**：必会 · 常考 · 🔧 ｜ **对应**：知识点 [三、语法必会：诊断命令与 benchmark](知识点.md)

### 场景

要优化一个热路径函数，有人凭感觉改——把 `fmt.Sprintf` 换成 `strconv`、把返回 `*int` 换成 `int`。改完不知道有没有效果，也不知道还有没有别的逃逸。


-gcflags=-m 怎么读。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`go build -gcflags="-m"` 看 `moved to heap` 和 `escapes to heap`；二级 `-m -m` 给原因链；`-l` 禁内联对比逃逸差异。

```bash
go build -gcflags="-m" ./cmd/...                   # ← 一级 -m：列出逃逸变量
go build -gcflags="-m -m" ./... 2>&1 | tee escape.log  # ← 二级 -m：完整原因链
go test -gcflags="-m" -run=NONE ./pkg 2>&1 | grep 'escapes to heap'  # ← 只看逃逸行
go build -gcflags="-m -l" ./...                    # ← -l 禁内联，对比逃逸差异
```

```text
./main.go:10:2: moved to heap: x              # ← 变量从栈提升到堆
./main.go:15:9: &buf escapes to heap          # ← 取地址操作导致逃逸
./main.go:20:14: fmt.Sprintf(...) escapes to heap  # ← interface 参数逃逸
./main.go:25:7: argument does not escape      # ← 好信号：参数未逃逸
```

**读输出**：`moved to heap` 是变量被提升；`escapes to heap` 是取地址或间接操作导致逃逸；`argument does not escape` 是好信号——参数没逃逸，函数内联后可能栈分配。二级 `-m -m` 更啰嗦，给出完整的分配决策链，能看到编译器「为什么」判定逃逸。

`-l` 禁用内联：小函数内联后，调用方可能不再逃逸（参数不越过函数边界了）。用 `-l` 对比可以分离「内联消除的逃逸」和「真逃逸」——这是面试深度题。

> 🔧 **实操**：优化热路径前**先 -m**，别凭感觉改。改完再跑一次 `-m` 确认逃逸消失，然后跑 `go test -bench -benchmem` 看 allocs/op 是否归零。

> 📝 **面试**：让解释「为什么 `go test -gcflags=-m` 和 `go build -gcflags=-m` 对同一段代码逃逸结果可能不同」——答**内联阈值和调用上下文不同**。test 编译时内联预算可能不同。

### 再追问

**-m 输出太多看不过来怎么办？**——`grep 'escapes to heap'` 只看逃逸行，或 `grep -v 'does not escape'` 排除好信号。先定位热路径包，`go build -gcflags=-m ./hotpath/...`，别全项目扫。

**benchmark 怎么验证？**——`b.ReportAllocs()` + `go test -bench -benchmem`，看 allocs/op。优化前 1 allocs/op、优化后 0 allocs/op 就是成功。`testing.AllocsPerRun` 可以写断言。

## Q4

**★★★★★｜三色标记是什么？写屏障干什么？STW 在哪？Go GC 完全没有 STW 吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [五、干活：三色标记与写屏障](知识点.md)

### 场景

面试官让你画三色标记。有人画完三色被问「标记的时候程序还在跑，怎么保证不漏标」就卡住。还有人声称「Go GC 完全没有 STW」。


返回 &local——经典逃逸。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：白→灰→黑三色标记可达对象，写屏障在标记期间防漏标，STW 只在栈扫描和标记终止——极短但非零。

三色不变式：

| 色 | 含义 | GC 动作 |
|----|------|---------|
| 白 | 未访问 | 清扫阶段回收 |
| 灰 | 已发现，子引用未扫完 | 继续扫描子引用 |
| 黑 | 已扫完 | 保留，不回收 |

```text
白 → 灰 → 黑   单向推进
                    ↑
            写屏障：标记期间往黑对象写入指向白对象的指针时
            把白色标灰 → 防止漏标
```

> 💡 **打个比方**：GC 是清洁工在大扫除——白是还没看的房间，灰是正在翻的房间（翻完里面的柜子才算完），黑是翻完确认有人用的房间（不扫）。问题是清洁工翻房间时你还在往房间里塞东西——写屏障就是强制你把新塞的东西标成「灰」（还没翻完），否则清洁工扫完才发现你偷偷塞了个白色包裹，已经扫走扔了。

**写屏障（write barrier）** 是编译器在每次指针写入处插入的一小段代码。Go 用混合写屏障（Dijkstra + Yuasa 混合）。关键：写屏障**只在 GC 标记阶段开启**，平时不开——所以正常代码的指针写没有额外开销。但 GC 期间写屏障代价是真实的，这是 GC 占 CPU 的一部分。

**STW 在哪**：

```text
① STW: 栈扫描准备（极短，~10us 级）
② 并发标记: 写屏障开 → 扫灰 → 全黑（大部分时间在这，不 STW）
③ STW: 标记终止 + 清扫准备（极短）
④ 并发清扫: 回收白色对象（不 STW）
```

> ⚠️ **别混**：Go GC 的 STW 是**亚毫秒级**但**不是零**——栈扫描和标记终止仍需 STW。说「Go GC 完全没有 STW」是错的。GC CPU 占比高不是因为 STW 长，而是**标记阶段写屏障 + 扫描成本**。

> 📝 **面试**：画三色标记要写出白→灰→黑的单向推进、写屏障回灰的箭头，再说清 STW 只在①③。被问「Go GC 没有 STW 吗」时纠正：STW 有但极短（亚毫秒级），不是零。

### 再追问

**写屏障有几种？**——Dijkstra（插入式，新引用标灰）、Yuasa（删除式，旧引用标灰）。Go 1.8 起用**混合写屏障**（Dijkstra + Yuasa），兼顾正确性和性能。面试答「混合写屏障」即可，不要求推演算法。

**GC 只回收堆 Go 对象，CGO 的内存呢？**——C 侧 `malloc` 的内存 GC 不管，要 `C.free` 或 Go 侧管理。文件/conn/DB 同理——GC 不管，要 `defer Close()`。`runtime.SetFinalizer` 时机不确定，不推荐依赖它释放资源。

## Q5

**★★★★★｜GOGC=100 表示什么？调大调小有什么 trade-off？GOGC=off 能用吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [六、调优：GOGC 与 GOMEMLIMIT](知识点.md)

### 场景

线上 GC 占 CPU 40%，有人提议把 GOGC 调大到 200「让 GC 少跑点」。另一台容器 OOM 了，有人提议 GOGC=off「干脆关掉 GC」。都没想清楚代价。


interface/闭包逃逸。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`GOGC=100` 表示 live heap 到上次 GC 后 live 的 2 倍触发 GC；调大 → GC 少、内存高；调小 → GC 频、CPU 高；`GOGC=off` 须配 GOMEMLIMIT，否则必 OOM。

```text
GOGC=100  → live heap 到 baseline × 2.0 触发   （默认）
GOGC=200  → live heap 到 baseline × 3.0 触发   （GC 更少，内存更高）
GOGC=50   → live heap 到 baseline × 1.5 触发   （GC 更频，CPU 更高）
GOGC=off  → 不按增长率触发 GC（须配 GOMEMLIMIT，否则必 OOM）
```

```bash
GODEBUG=gctrace=1 ./app 2>&1 | head -5
# ← 看 GC 间隔和 CPU 占比，判断是太频还是单次太贵
```

调大 GOGC 的代价：GC 轮次减少，CPU 占比下降——但 live heap 允许涨得更高，峰值 RSS 更大，容器 OOM 风险增加。调小的代价：GC 更频，CPU 占比上升——但内存控制更好。

本例的答案不是直接调大 GOGC：GC CPU 40% 说明**alloc rate 太高**或**live heap 太大**。先查 `gctrace` 看 GC 间隔和 heap 趋势——如果 GC 间隔很短（每几秒一轮），说明 alloc 猛，去查热路径逃逸和 Pool；如果 live heap 持续涨不回落，说明有泄漏，去查 map/goroutine。**调 GOGC 是最后手段**，不是第一刀。

> ⚠️ **别混**：GOGC 调大不是「优化」——它用内存换 CPU，不是消除问题。真正的优化是**减少 alloc**。GOGC=off 几乎不自动 GC，只在**配合 GOMEMLIMIT 且监控到位**时可以用。

> 📝 **面试**：「GOGC 怎么调」先答「先查 alloc 和 live，别直接调参」。被追问 trade-off 时答「调大内存高 CPU 低、调小内存低 CPU 高」。被问 GOGC=off 时答「须配 GOMEMLIMIT，否则必 OOM」。

### 再追问

**历史上 ballast 是什么？**——用大 `make([]byte, N)` 撑高 baseline heap，让 GOGC=100 的 2 倍阈值更高，减少 GC 频率。Go 1.19+ GOMEMLIMIT 直接设上限，效果更好且不浪费 cgroup 配额——**ballast 已过时**，面试提到要说「已被 GOMEMLIMIT 替代」。

**容器 512Mi 该怎么设？**——`GOMEMLIMIT=460MiB`（留 10% 缓冲）。GOMEMLIMIT 是软限，Go 运行时触及上限时更积极 GC。两个条件（GOGC 增长率 + GOMEMLIMIT 绝对值）谁先满足谁触发。与 [12](../12-GOMAXPROCS与容器cgroup/) 配合：memory limit 和 CPU limit 是两条线。

## Q6

**★★★★☆｜GOMEMLIMIT 和 GOGC 有什么区别？容器里怎么设？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、调优：GOGC 与 GOMEMLIMIT](知识点.md)

### 场景

容器 memory limit 512Mi，进程 OOM 被杀。有人只调了 GOGC 没用，有人不知道 GOMEMLIMIT。还有人说「Go 1.19 之前容器里没法控内存」。


三色标记。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`GOGC` 按增长率触发 GC（live heap 翻倍），`GOMEMLIMIT` 按绝对上限触发更积极 GC——容器必设后者，两者谁先满足谁触发。

| | GOGC | GOMEMLIMIT |
|---|---|---|
| 触发依据 | live heap 增长率（默认 100% = 2 倍） | 绝对内存上限 |
| 默认值 | 100 | off（不限） |
| Go 版本 | 1.0+ | 1.19+ |
| 适合 | 一般场景 | 容器、内存敏感 |
| 调大效果 | 内存高、CPU 低 | — |

容器 `memory limit 512Mi` 的标准配置：

```bash
export GOMEMLIMIT=460MiB   # ← 留 10% 缓冲，让 Go 在接近 cgroup limit 时更积极 GC
```

```text
cgroup memory limit 512Mi  ← 硬限：超过被 OOM kill
GOMEMLIMIT       460MiB  ← 软限：Go 运行时触及更积极 GC
GOGC             100     ← 默认：live heap 翻倍触发
                          三个层次，从外到内
```

> ⚠️ **别混**：GOMEMLIMIT 是**软限**不保证不被 cgroup OOM kill——它让 GC 更积极，但如果 live heap 真的超了（泄漏），GC 也救不了。cgroup OOM kill 是硬限，GOMEMLIMIT 是软限，**软限不能替代修泄漏**。与 GOMAXPROCS 无关——一个管内存 GC，一个管 CPU 线程，详见 [12](../12-GOMAXPROCS与容器cgroup/)。

> 📝 **面试**：「Go 1.19 之前容器里怎么控内存」——答「只能靠 GOGC 调小或 ballast hack，都不理想；1.19+ 用 GOMEMLIMIT 是标准做法」。被追问「不设会怎样」——Go 可能不知道容器内存 limit，RSS 涨过 cgroup limit 被 OOM kill。

### 再追问

**GOMEMLIMIT 和 GOGC 同时设，谁优先？**——两个条件**谁先满足谁触发**。live heap 增长率到 GOGC 阈值先触发；如果 GOMEMLIMIT 先被触及（live heap 没翻倍但总量接近上限），则更积极 GC。两者不冲突。

**GOMEMLIMIT 设太大会怎样？**——等于没设，Go 不会在接近 cgroup limit 时加速 GC，可能直接被 OOM kill。设太小（远低于实际 live）会 GC 过于频繁，CPU 浪费。**留 10% 缓冲**是经验值。

## Q7

**★★★★★｜sync.Pool 适合什么场景？Put 时要注意什么？为什么不能当缓存？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [七、复用：sync.Pool 与 alloc vs live heap](知识点.md)

### 场景

有人把 `sync.Pool` 当 session 缓存用——Get 出一个 User 对象、填上数据、Put 回去下次复用。GC 一清池子，下一次 Get 拿到的可能是脏数据。还有人把 Pool 当连接池用。


写屏障——承接 Q6。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：sync.Pool 复用**临时对象**降 alloc——Put 前必须 Reset、GC 可能清空 Pool、不能当长期缓存或连接池。

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        b := make([]byte, 0, 4096)
        return &b
    },
}

func process() {
    bp := bufPool.Get().(*[]byte)
    buf := (*bp)[:0]                // ← 复用前重置长度（但容量保留）
    defer func() {
        *bp = buf                   // ← 归还前确保状态干净
        bufPool.Put(bp)
    }()
    // 用 buf 组装...
}
```

**三条规则**：

- **Put 前重置**状态——`buf[:0]` 清零长度，别泄漏上请求数据到下一个 Get。带 PII 的对象如果没清干净，下一个人 Get 到的就是脏数据。
- **Pool 对象可能随时被 GC 清空**——Go 1.13+ Pool 在 GC 时不是全清（保留少量），但仍不保证命中。Get 时可能走 `New`，别假设一定能复用。
- **适合临时 buffer、解码器、压缩器**——不适合连接池、有状态 session、长期缓存。连接池用 `database/sql` 的 pool；缓存用 LRU 库。

为什么不能当缓存：GC 时 Pool 的对象可能被全部回收——这是设计意图，Pool 的目的是**降低临时对象的 alloc 压力**，不是持久存储。如果当缓存用，GC 一清池子就空了，缓存命中率归零，逻辑可能出错（脏数据/空引用）。

> ⚠️ **别混**：连接池 ≠ sync.Pool。连接池长期持有连接，有生命周期管理；Pool 临时复用对象，GC 可清。把带 PII 的 User 对象 Pool 当 session 缓存——脏读 + GC 清空后逻辑错误。

> 📝 **面试**：问「sync.Pool 怎么用」，答「临时对象复用降 alloc，三条规则：Put 前 Reset、GC 可清空不保证命中、只适合无状态临时对象」。被追问「Pool 当缓存」时答「GC 清空后缓存失效，别当长期缓存」。

### 再追问

**Go 1.13+ Pool 有什么改进？**——GC 时不全清，保留少量对象，命中率提升。但仍非严格 LRU、不保证命中。别因为「改进了」就当缓存用。

**Pool 里放 *[]byte 还是 []byte？**——放 `*[]byte`（指针），因为 `Get` 返回 `interface{}`，放值类型会逃逸到堆（interface 装箱），放指针则只装一次。Get 后 `.(*[]byte)` 类型断言。

## Q8

**★★★★☆｜alloc rate 高和 live heap 高，优化方向有何不同？两者都高怎么办？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、复用：sync.Pool 与 alloc vs live heap](知识点.md)

### 场景

GC CPU 占 40%，有人要上 sync.Pool，有人要查泄漏。先搞清是 alloc 猛还是 live 大，方向不同。


GOGC 调什么。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**高 alloc** → 少 New、Pool、预分配、改热路径 API；**高 live** → 缩缓存、查 map/goroutine 泄漏、数据结构瘦身——方向不同，别一套药方治两种病。

```text
高 alloc、低 live → 少 New · 复用 buffer · Pool        # ← GC CPU 高但 RSS 不大
低 alloc、高 live → 缩缓存 · 查 map/goroutine 泄漏    # ← RSS 高但 GC 不频
两者都高         → 先砍 alloc，再查 live 泄漏
```

高 alloc rate 的特征：GC 频繁（gctrace 间隔短）、CPU 高、但 GC 后 live heap 不大——对象分配得快、回收得也快。治法：`-gcflags=-m` 找热路径逃逸、sync.Pool 复用 buffer、预分配 slice `make([]T, 0, cap)`、strconv 替代 Sprintf、codegen 替代 json.Marshal。

高 live heap 的特征：RSS 持续涨、GC 后 live 不回落——对象分配不多但回收不掉。Go 里的「泄漏」常是：

```go
// map 只增不减
cache := map[string][]byte{}
cache[key] = val // ← 永不 delete → live heap 涨

// subslice 引用大数组
big := make([]byte, 1<<20)
sub := big[:100] // ← big 的整个 backing array 仍 live

// goroutine 挂住大 struct
ch := make(chan *Big, 10)
ch <- &Big{} // ← channel buffer 里的对象 live 直到消费方丢弃
```

> 🔍 **现场**：pprof `alloc_space`（累计分配）看 alloc rate，`inuse_space`（常驻）看 live heap。两个 profile 都要跑，别只看一个。详见 [13](../13-pprof与性能排查/)。

> 📝 **面试**：GC CPU 高不一定是 live 大，可能是 alloc 猛——先分清。答「先跑 pprof alloc_space 和 inuse_space，前者高砍 alloc、后者高查泄漏，两者都高先砍 alloc」。

### 再追问

**两者都高怎么办？**——先砍 alloc（更容易见效：热路径 -m + Pool + 预分配），再查 live 泄漏（更难定位：map TTL、goroutine 泄漏、subslice 引用）。alloc 砍完后 GC CPU 下降，live 的比例就更清晰了。

**map 泄漏怎么治？**——加 TTL 过期清理、限大小用 LRU 库（如 `github.com/hashicorp/golang-lru`）、定期换 map（双 buffer：新建一个空 map，遍历旧的只拷活跃条目，旧的丢弃）。

## Q9

**★★★★☆｜为什么 `fmt.Sprintf` 和 `interface{}` 在热路径上差？怎么改？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [四、出生：编译器逃逸分析决定栈还是堆](知识点.md)

### 场景

热路径上大量 `fmt.Sprintf("id=%d", id)` 和 `log.Println(v)`。`-gcflags=-m` 满屏 `escapes to heap`。有人觉得「可读性比性能重要」不愿意改。


GOMEMLIMIT。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`fmt.Sprintf` 内部走 `interface{}` 装箱 + 反射 + buffer 分配——每次调用多个堆对象；热路径用 `strconv.AppendInt` 到复用 `[]byte`，零 alloc。

```go
// 差：每次 heap 分配
func labels(id int) string {
    return fmt.Sprintf("id=%d", id) // ← Sprintf interface 装箱 + buffer alloc
}

// 较好：栈上 buffer，零 alloc
func labels(b []byte, id int) []byte {
    return append(strconv.AppendInt(b[:0], int64(id), 10), "id="...) // ← 复用 b
}
```

```text
fmt.Sprintf("id=%d", id) 的开销链：
  ① id → interface{} 装箱 → 堆分配（小整数可能优化，不保证）
  ② fmt 内部创建 buffer → 堆分配
  ③ 格式化 → 反射读类型 → 临时对象
  ④ 返回 string → 堆分配
  总计：每次调用 2-4 次堆分配

strconv.AppendInt(b, id, 10) 的开销：
  ① 直接写数字到 b 的底层数组
  ② b 复用 → 0 alloc
  总计：0 次堆分配（Pool 命中时）
```

interface 装箱的本质：`fmt.Sprintf(format string, args ...interface{})` 的可变参数是 `interface{}` 类型。传入 `int` 时，编译器必须把 `int` 装箱到 `interface{}`——这是堆分配（小整数有时优化但不保证）。加上 `fmt` 内部反射读类型、创建 buffer，每次调用多个堆对象。

热路径的改法：
- `strconv.AppendInt` / `strconv.Itoa` 替代 `fmt.Sprintf` 格式化数字
- `strings.Builder` 替代循环 `+=` 拼接
- `log/slog` 结构化日志替代 `fmt.Println`
- codegen（easyjson、protobuf）替代 `encoding/json` 的反射

> ⚠️ **别混**：不是所有路径都值得改——**热路径**才改。冷路径的 `fmt.Sprintf` 可读性更好，alloc 几次无所谓。benchmark 用 `b.ReportAllocs()` 验证 allocs/op 归零才算成功。

> 📝 **面试**：问「热路径 fmt.Sprintf 怎么改」答「strconv.AppendInt 到复用 []byte，零 alloc」。被追问「为什么 interface 装箱堆分配」答「interface{} 内部是 (type, pointer) 对，具体类型大小未知，编译器无法证明栈安全」。

### 再追问

**泛型能减少 interface 装箱吗？**——部分场景可以。Go 泛型是 monomorphization（部分），类型参数在编译期确定，不需要装箱。但不是所有 `interface{}` 都能被泛型替代——`fmt.Sprintf` 的可变参数仍是 `interface{}`。

**errors.New 和 fmt.Errorf 的区别？**——`errors.New("fixed string")` 不做格式化，固定串可能不 alloc 动态部分；`fmt.Errorf("id=%d", id)` 走 Sprintf，每次 alloc。热路径用 `errors.New` 或预定义 sentinel error。

## Q10

**★★★★☆｜闭包为什么导致外部变量逃逸？闭包不逃出函数也会逃逸吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [四、出生：编译器逃逸分析决定栈还是堆](知识点.md)

### 场景

代码里有大量 `func() { _ = x }` 形式的闭包。`-gcflags=-m` 显示 `x escapes to heap`。有人不理解「我明明没 return 闭包，为什么也逃逸」。


开头那个 Pool 当缓存。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：闭包**逃出函数**后仍引用外部变量，变量生命周期延长 → 堆分配；闭包不逃出函数时**可能不逃逸**——以 `-m` 为准。

```go
// 闭包逃出函数 → n 逃逸
func counter() func() int {
    n := 0
    return func() int { n++; return n } // ← n escapes：闭包引用 n 且逃出
}

// 闭包不逃出函数 → 可能不逃逸
func caller() int {
    n := 0
    f := func() int { n++; return n } // ← n 可能不 escape（f 不逃出）
    f()
    return n
}
```

```text
counter():   闭包被 return → 逃出函数 → n 必须堆分配（栈帧弹出后闭包仍引用 n）
caller():    闭包赋给 f → f 不逃出 → n 可能栈分配（编译器证明 f 的生命周期在 caller 内）
```

闭包本质上是一个**结构体**，捕获了外部变量的引用。如果闭包逃出函数，捕获的变量生命周期也要延长到闭包的生命周期——所以变量必须堆分配。如果闭包不逃出函数（只在本函数内调用），编译器可能证明变量不逃逸，栈分配。

`go func() { _ = s[0] }()` 是特殊场景——`go` 关键字启动 goroutine，闭包一定「逃出」当前函数（goroutine 的生命周期不确定），所以捕获的变量逃逸。

> ⚠️ **别混**：闭包结构体本身可能在栈上（不逃出时）或堆上（逃出时），捕获的变量是另一回事——**以 `-m` 为准**，别靠口诀。`go func()` 一定逃逸，因为 goroutine 的执行时机不确定。

> 📝 **面试**：问「闭包为什么逃逸」答「闭包捕获外部变量引用，逃出函数后变量生命周期延长 → 堆」。被追问「不逃出也逃逸吗」答「不一定，看 `-m`；`go func()` 一定逃逸」。

### 再追问

**怎么改？**——如果闭包只是为了在当前函数内复用逻辑，提取成普通函数传参数，不捕获外部变量。如果确实需要闭包逃出，接受逃逸，用 Pool 或预分配减少其他 alloc。

**goroutine 启动的闭包一定逃逸吗？**——是的。`go func() { ... }()` 的闭包一定逃逸到堆——goroutine 可能在当前函数返回后才执行，捕获的变量必须堆分配。这也是「百万 goroutine」内存压力的原因之一。

## Q11

**★★★★☆｜GODEBUG=gctrace=1 输出怎么读？GC CPU 40% 怎么查？**

**覆盖**：必会 · 常用 · 🔧 ｜ **对应**：知识点 [五、干活：三色标记与写屏障](知识点.md)

### 场景

线上 GC CPU 占 40%，有人不知道从哪开始查。有人直接上 sync.Pool，有人调 GOGC，有人要抓 pprof。


alloc vs live heap。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：先 `GODEBUG=gctrace=1` 看 GC 间隔和 CPU 占比——间隔短是 alloc 猛，live 涨是泄漏；再 pprof 定位热路径，最后 -m 改逃逸。

```bash
GODEBUG=gctrace=1 ./app 2>&1 | head -5
```

```text
gc 1 @0.015s 2%: 0.12+0.85+0.003 ms clock, 4->4->1 MB, 0 MB goal, 0 stacks
#  ↑   ↑     ↑    ↑              ↑
#  轮次  距启动  CPU%  STW+标记+STW  heap: GC前→GC中→GC后
```

**读输出**：

- `2%`：GC 占总 CPU——超 10% 就该查
- `0.12+0.85+0.003 ms`：第一个和第三个是 STW（短），中间是并发标记（长）
- `4->4->1 MB`：GC 前 live → GC 中 peak → GC 后 live——如果 GC 后 live 不回落，说明有泄漏
- GC 间隔：连续几行的 `@` 时间差——间隔短 = alloc 猛

**60 秒剧本**：

```text
0-10s   GODEBUG=gctrace=1 采样 → 看 GC CPU% 和间隔
10-30s  pprof alloc_space top → 找 alloc 最大的函数
30-45s  热函数 -gcflags=-m → 看逃逸原因
45-60s  改逃逸（strconv/Pool/预分配）→ benchmark 验证 allocs/op
```

GC CPU 40% 的常见原因：
- 热路径大量 `fmt.Sprintf` / `json.Marshal` / `interface{}` 装箱 → 改 strconv / codegen / typed API
- 每次请求 new 大 buffer 不复用 → sync.Pool 或预分配
- map 只增不减 → 加 TTL / LRU / 定期换 map
- goroutine 泄漏挂住大 struct → 与 [05](../05-goroutine与调度模型/) 联查

> 🔍 **现场**：发布前后对比 gctrace——GC 间隔突变说明新代码 alloc 猛涨。`alloc_space` 和 `inuse_space` 两个 profile 都要跑：前者看 alloc rate，后者看 live heap。

> ⚠️ **别混**：GC CPU 高不一定是 STW 长——STW 是亚毫秒级，40% 的 CPU 花在**并发标记阶段的写屏障和扫描**，不是 STW。调 GOGC 是最后手段，不是第一刀。

### 再追问

**scavenge 是什么？**——GC 清扫后把内存归还给 OS 的过程。gctrace 里 scavenge 行表示归还了多少。RSS 可能仍高于 heap——OS 不一定立刻收回归还的页。

**GC 后 live 不回落怎么办？**——有泄漏。跑 pprof `inuse_space` 看常驻对象，找 map 只增不减、goroutine 挂住、subslice 引用大数组。Go 的「泄漏」不是 malloc 忘了 free，是引用没释放。

## Q12

**★★★★★｜下面哪些更可能逃逸？简述原因，并用 -gcflags=-m 验证思路**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、出生：编译器逃逸分析决定栈还是堆](知识点.md)

### 场景

面试官给四段代码让你判断逃逸。有人全答「逃逸」，有人靠直觉猜。

```go
func a() int { x := 1; return x }
func b() *int { x := 1; return &x }
func c() { s := []byte{1}; go func() { _ = s[0] }() }
func d() interface{} { return 3 }
```


踩坑对照。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：a 通常不逃逸（值拷贝）；b 逃逸（返回局部指针）；c 逃逸（goroutine 闭包捕获）；d 可能逃逸（interface 装箱）。

| 函数 | 逃逸？ | 原因 |
|------|--------|------|
| `a` | 通常否 | 返回值拷贝，x 不越过函数边界 |
| `b` | **是** | 返回 `&x`，x 的地址被调用方持有 |
| `c` | **是** | `go func()` 闭包捕获 `s`，goroutine 生命周期不确定 |
| `d` | **可能** | `interface{}` 装箱，小整数有时优化但不保证 |

```text
a:  x := 1; return x
    → return 拷贝 x 的值给调用方 → x 本身不逃逸 → 可能栈分配

b:  x := 1; return &x
    → return &x 把 x 的地址交给调用方 → 栈帧弹出后指针悬空 → x 必须堆分配

c:  s := []byte{1}; go func() { _ = s[0] }()
    → go func() 一定逃出函数（goroutine 时机不确定）
    → 闭包捕获 s → s 的 backing array 逃逸到堆

d:  return 3
    → 返回值类型 interface{} → 3 需要装箱到 (type, value) 对
    → 小整数有时被编译器优化（不保证），以 -m 为准
```

验证方法：

```bash
go build -gcflags="-m" ./... 2>&1 | grep -E 'func_a|func_b|func_c|func_d'
# ← 看每个函数里哪些变量 escapes to heap
```

> ⚠️ **别混**：以 `-m` 输出为准，别靠口诀。同一函数在不同编译选项下（内联 vs 不内联）逃逸结果可能不同。c 如果不用 `go` 只用普通闭包且不逃出函数，可能不逃逸——但 `go func()` 一定逃逸。

> 📝 **面试**：口述理由后补一句「以 `-m` 为准」——这比靠口诀靠谱。被追问「d 一定逃逸吗」答「interface 装箱不保证逃逸，小整数有时优化，但不依赖编译器优化——热路径避免 `interface{}`」。

### 再追问

**c 如果不用 go，只定义闭包不调用？**——仍可能逃逸，看闭包是否逃出函数。定义了但不逃出 → 可能不逃逸；赋给变量传出 → 逃逸。`go func()` 一定逃逸。

**怎么改 c 不逃逸？**——把 `s` 作为参数传入闭包而不是捕获：`go func(s []byte) { _ = s[0] }(s)`——但 `s` 仍可能因为传入 goroutine 而逃逸。根本解法是避免在 goroutine 里引用外部变量，传值拷贝或用 Pool。

## Q13

**★★★★☆｜RSS 持续涨、GC 后 live 不回落，Go 里常见哪两种「泄漏」？怎么查？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [七、复用：sync.Pool 与 alloc vs live heap](知识点.md)

### 场景

网关进程 RSS 从 2Gi 涨到 8Gi，`GODEBUG=gctrace=1` 显示 GC 后 live heap 仍 6Gi+。有人只调 `GOGC=50`，没用。


作战定责。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：高 **live heap** 常见 **map 只增不减**、**subslice 引用大 backing array**、channel/goroutine 挂住大对象——先 `pprof inuse_space`，不是先调 GOGC。

```go
// ① map 缓存无 TTL
cache := map[string][]byte{}
cache[key] = val   // ← 永不 delete

// ② subslice 引用整段数组
big := make([]byte, 1<<20)
sub := big[:100]   // ← 1MB backing array 仍 live

// ③ channel buffer 里的指针
ch := make(chan *Big, 10)
ch <- &Big{}       // ← 直到消费方丢弃
```

修法：map 加 TTL/LRU 或定期换 map；subslice 前先 `copy` 小片；channel 背压 + 限长。`alloc_space` 看 alloc rate，`inuse_space` 看 live——两者都跑（链 [13](../13-pprof与性能排查/)）。

> ⚠️ **别混**：Go「泄漏」多是 **引用未释放**，不是 malloc 忘了 free。调 GOGC 只改变 GC 频率，不缩小 live heap。

### 再追问

**map 怎么治理？**——限大小用 LRU、`sync.Map` + 定期重建空 map 双 buffer 迁移活跃 key。

## Q14

**★★★★☆｜热路径字符串拼接和 JSON，除了 strconv 还能怎么降 alloc？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [四、出生：编译器逃逸分析](知识点.md) · [八、模板](知识点.md)

### 场景

热路径上循环 `s += w` 拼 HTTP header，以及每次 `json.Marshal` 打日志。`-m` 显示大量 `escapes to heap`，allocs/op 很高。


本套题收尾综合口述。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：循环拼接用 **`strings.Builder`**；JSON 用 **codegen（easyjson/protobuf）** 替代反射 `encoding/json`；验证用 **`b.ReportAllocs()` / `AllocsPerRun`**。

```go
// 差：每次新 string + 拷贝
s := ""
for _, w := range words { s += w }

// 好：内部 buffer 扩容 amortized
var b strings.Builder
for _, w := range words { b.WriteString(w) }

// 差：反射 + 大量临时对象
data, _ := json.Marshal(v)

// 好：生成代码，零反射
data, _ := v.MarshalJSON()
```

配合 Q9：`fmt.Sprintf` → `strconv.AppendInt` 到复用 `[]byte`；大 buffer → sync.Pool。优化后 benchmark 目标：**allocs/op 归零或明显下降**，不只盯 ns/op。

> 📝 **面试**：ballast 撑 GOGC 已被 **GOMEMLIMIT** 替代——别背 ballast 当最佳实践。

### 再追问

**unsafe.String 呢？**——仅懂边界时用，生产慎用；优先 Builder + Pool + codegen。
