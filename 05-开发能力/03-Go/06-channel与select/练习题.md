## Q1

**★★★★★｜无缓冲 channel 和有缓冲 channel 在 send 时行为有什么不同？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、发送：无缓冲 vs 有缓冲](知识点.md)

### 场景

同事用 `make(chan Task, 0)` 做流水线，抱怨「一发就卡死」，想改成无缓冲「更同步」。

### 完整解答

> 🎯 **一句话**：**无缓冲** send 必须等 **recv 同时就位** 才完成拷贝；**有缓冲** 在 `len < cap` 时 send **立即入队** 不等人。

```go
ch := make(chan int)     // 无缓冲：握手
ch2 := make(chan int, 10) // 最多堆 10 个再堵 send
```

无缓冲建立 **happens-before**：send 完成先于 recv 看到值。有缓冲在满之前是异步，满后 send 与无缓冲一样等 recv。

> 📝 **面试**：无缓冲 = 同步点；有缓冲 = 队列深度 = 你愿意积压多少。

### 再追问

**cap=1 算无缓冲吗？**——不是，有一个槽。**不要**把 `make(chan T)` 和 `make(chan T,1)` 混为一谈。

## Q2

**★★★★★｜channel 关闭后，继续 recv 和 send 分别会怎样？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、接收：`<-ch`、`ok` 与 `range`](知识点.md)、[五、关闭：`close` 的语义与事故](知识点.md)

### 完整解答

> 🎯 **一句话**：**recv** 得类型零值且 `ok=false`（**不 panic**）；**send** → **panic: send on closed channel**。

```go
close(ch)
v, ok := <-ch // v=0, ok=false（int 零值）
ch <- 1       // panic
```

`range ch` 会把缓冲 drain 完后自然退出。

> ⚠️ **别混**：读 closed 安全；写 closed 故意 crash 防丢数据。

### 再追问

**重复 close？**——`panic: close of closed channel`。**不要**多处无协调 `close`。

## Q3

**★★★★☆｜应该由发送方还是接收方 close channel？为什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、关闭：`close` 的语义与事故](知识点.md)

### 完整解答

> 🎯 **一句话**：惯例 **发送方 close**，表示「不会再 send」；接收方 `range` 等这个信号退出。

接收方 close 时发送方可能仍在 `ch <-`，下一行就 panic。多生产者要么 **单点 merge 后 close**，要么用 `ctx` 取消不用 close 传数据。

> 📝 **面试**：close 是广播「结束」，不是删 channel；语言保证 recv 能 drain。

### 再追问

**只有接收方怎么停？**——用 `ctx.Done()` 或单独 `done chan struct{}`，别乱 close 数据 channel。**不要** recv 方 `close` 除非 API 文档写明。

## Q4

**★★★★☆｜对 nil channel 执行 send、recv、close 各会怎样？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、出生：make 与 nil channel](知识点.md)

### 完整解答

> 🎯 **一句话**：nil channel 上 **send/recv 永久阻塞**；**close panic**。

```go
var ch chan int
<-ch       // 阻塞
ch <- 1    // 阻塞
close(ch)  // panic: close of nil channel
```

`select` 里设 `case <-ch` 且 ch 为 nil，该 case **永不选中**——用于动态关掉某路输入。

> 📝 **面试**：nil channel 不是「空队列」，是「未初始化/已禁用」。

### 再追问

**和 closed channel 比？**——closed 能读零值；nil 永远等。**不要**用 nil 代替 close。

## Q5

**★★★★☆｜select 里多个 case 同时就绪，执行哪一个？**

**覆盖**：常考 ｜ **对应**：知识点 [六、select：多路仲裁](知识点.md)

### 完整解答

> 🎯 **一句话**：Go **伪随机** 选一个就绪 case，保证长期公平，**无固定优先级**。

要优先级：外层优先 `select` 高优 case，或独立 goroutine 分流。不要依赖「总是先走 case 1」做正确性。

> ⚠️ **别混**：`switch` 按顺序匹配值；`select` 按就绪集合随机。

### 再追问

**都没有就绪？**——阻塞，除非有 `default`。**不要**在需要背压时用 `default` 吞掉阻塞。

## Q6

**★★★★☆｜这段为什么 CPU 100%？**

```go
for {
    select {
    case v := <-ch:
        handle(v)
    default:
    }
}
```

**覆盖**：常用 · 必会 ｜ **对应**：知识点 [六、select：多路仲裁](知识点.md)

### 完整解答

> 🎯 **一句话**：`default` 在 **无就绪 case 时立即执行** → 空循环 **忙等**，烧 CPU。

改法：去掉 `default` 阻塞等；或 `default` 里 `time.Sleep`；或非阻塞场景用 `select`+`default` 但别包在裸 `for` 里无 sleep。

> 🔍 **现场**：`pprof cpu` 见 `select`/`runtime.selectgo` 热点。

### 再追问

**何时用 default？**——单次非阻塞试探，如 `select { case ch<-x: ... default: 缓存本地 }`。**不要**当轮询主循环。

## Q7

**★★★★★｜`for v := range ch` 什么时候退出？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [四、接收：`<-ch`、`ok` 与 `range`](知识点.md)

### 完整解答

> 🎯 **一句话**：**channel 被 close 且缓冲已 drain 空** 后退出；不 close 则 **永远阻塞**。

```go
go func() {
    for v := range ch {
        fmt.Println(v)
    }
    fmt.Println("done")
}()
ch <- 1
close(ch) // 必须 close，否则 range 永不结束
```

> 📝 **面试**：range 是语法糖：反复 recv 直到 ok=false。

### 再追问

**只 close 不 send？**——range 立即结束（零次循环）。**不要**指望 range 自己猜「没数据了」。

## Q8

**★★★★★｜什么情况下会向 closed channel 发送？线上怎么防？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、关闭：`close` 的语义与事故](知识点.md)

### 场景

多 goroutine 写结果到 `results`，主 goroutine `close(results)` 后仍有 worker 在 send，间歇 panic。

### 完整解答

> 🎯 **一句话**：**close 与 send 竞态**——recv 方/协调者已 close，慢 worker 还在 send。

防法：

- 单点 close：`WaitGroup` 等所有 sender 停再 close  
- `sync.Once` 包 close  
- 用 `ctx` 取消 worker，不再 send  
- 每 worker 独立 channel，merge 方 close `out`

> ⚠️ **别混**：recover 不能当协议；要从设计上消灭竞态。

### 再追问

**buffered 能缓解吗？**——不能，closed 后 send 照样 panic。**不要**靠 panic recover 做流控。

## Q9

**★★★★★｜用 channel 实现固定 8 个 worker 处理 jobs，写出骨架。**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、模式：fan-in、fan-out、pipeline](知识点.md)

### 场景

Kafka 消费要限并发，禁止「一条消息一个 go」。

### 完整解答

> 🎯 **一句话**：**N 个 goroutine `range jobs`**，主流程 `close(jobs)` + `WaitGroup.Wait()`。

```go
jobs := make(chan Job, 64)
var wg sync.WaitGroup
for i := 0; i < 8; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs {
            handle(j)
        }
    }()
}
for _, j := range all {
    jobs <- j
}
close(jobs)
wg.Wait()
```

缓冲 `jobs` 削峰；worker 数 = 并发上限。

> 📝 **面试**：比 semaphore 更显式；错误处理可加 err channel 或 errgroup（[09](../09-errgroup与并发限流/)）。

### 再追问

**worker 动态扩缩？**——用 `ctx` 停旧 worker、调 N 再起。**不要**不 close jobs 就 Wait。

## Q10

**★★★★☆｜`chan struct{}` 做信号量限并发，怎么写？**

**覆盖**：常用 ｜ **对应**：知识点 [八、方向与容量设计](知识点.md)

### 完整解答

> 🎯 **一句话**：**带缓冲的 struct{} channel**，send 占坑、recv 还坑，容量 = 最大并发。

```go
sem := make(chan struct{}, 50)
sem <- struct{}{}        // acquire
defer func() { <-sem }() // release
```

`struct{}` 零字节，只表达「占位」。与 [05](../05-goroutine与调度模型/) 限流一节一致。

> 📝 **面试**：和 `sync/semaphore` 包等价思想；channel 版面试常考。

### 再追问

**和无缓冲区别？**——无缓冲 semaphore 每次 acquire 都要有人 release 才继续，不适合「先占 50 坑」。**要用** buffered。

## Q11

**★★★☆☆｜`chan<- int` 和 `<-chan int` 有什么用？**

**覆盖**：必会 ｜ **对应**：知识点 [七、模式：fan-in、fan-out、pipeline](知识点.md)

### 完整解答

> 🎯 **一句话**：**编译期约束** 只写或只读，防止 recv 方误 send、API 更清晰。

```go
func produce(out chan<- int) { out <- 1 }
func consume(in <-chan int) { <-in }
```

双向 `chan int` 可隐式转成单向传入。

> 📝 **面试**：运行时无差别，纯类型安全。

### 再追问

**能从 `<-chan` 转成 `chan<-` 吗？**——不能，只能收窄。**不要**在内部偷偷强转破坏约定。

## Q12

**★★★★☆｜fan-in merge 多个 channel 到 out，为什么容易死锁？**

**覆盖**：常考 ｜ **对应**：知识点 [七、模式：fan-in、fan-out、pipeline](知识点.md)

### 场景

多个 goroutine 往无缓冲 `out` send，彼此等对方读，merge 卡死。

### 完整解答

> 🎯 **一句话**：**无缓冲 out** + 多个 sender 可能 **环形等待**；或 merge 与 consumer 速度不匹配堵满。

修法：`out := make(chan T, 合理深度)`；或单 goroutine 用 `select` 多路读再写 out（标准 fan-in）；consumer 持续 `<-out`。

> 📝 **面试**：fan-in 经典实现是 **一个 goroutine select 多输入**，不是多 goroutine 抢写同一无缓冲 ch。

### 再追问

**wg.Wait 后 close out 为什么要再包一层 go？**——避免 merge 里 `out<-` 阻塞时无法 Wait。**不要**在持有锁时 send。

## Q13

**★★★★★｜输出是什么？**

```go
ch := make(chan int, 1)
ch <- 1
ch <- 2
fmt.Println(<-ch)
```

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [三、发送：无缓冲 vs 有缓冲](知识点.md)

### 完整解答

> 🎯 **一句话**：缓冲 1：第一次 send 成功；**第二次 send 阻塞**——若单 goroutine 运行则 **死锁**（没有另一个 goroutine recv）。

若改成先 `<-ch` 再第二次 send，则打印 `1`。面试题常考「单线程填满 buffer 再 send」死锁。

```text
fatal error: all goroutines are asleep - deadlock!
```

> ⚠️ **别混**：`cap=1` 不是「能存两个」。

### 再追问

**加 `go func(){ ch<-2 }()`？**——主 goroutine 第二次 send 仍可能先死锁。**要**先 recv 或加大缓冲/异步。

## Q14

**★★★★★｜如何用 select 同时等 job 和 ctx 取消？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [六、select：多路仲裁](知识点.md)

### 场景

长循环 `for { job := <-jobs }` 无法优雅退出，发布时要等 30 分钟。

### 完整解答

> 🎯 **一句话**：**同一 select** 里 `case <-ctx.Done()` 与 `case job := <-jobs`。

```go
for {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case job, ok := <-jobs:
        if !ok {
            return nil
        }
        if err := handle(job); err != nil {
            return err
        }
    }
}
```

取消优先于收 job（多 case 就绪时随机，但 `Done` 关闭后迟早选中）。完整 ctx 链见 [08](../08-context取消与超时传播/)。

> 📝 **面试**：别用两个 goroutine 一个等 ctx 一个等 job——竞态难维护。

### 再追问

**jobs 不 close 只 cancel？**——可以，`ctx` 分支 return 即可。**不要**只 close jobs 不传 ctx 给下游 RPC。
