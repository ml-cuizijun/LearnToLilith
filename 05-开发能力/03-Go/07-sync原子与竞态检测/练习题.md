## Q1

**★★★★★｜什么是 data race？四个条件是什么？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [二、诞生：什么是 data race](知识点.md)

### 场景

面试官：「并发就不安全吗？两个 goroutine 同时读 int 算不算 race？」


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**并发**访问**同一内存**，**至少一方写**，且**没有 happens-before** → data race，结果未定义。

两 G **只读**同一变量：**不算** data race（但仍可能读到中间态若另有写者）。一写一读或两写且无同步 → race。

```go
// race
var x int
go func() { x = 1 }()
go func() { _ = x }()
```

> 📝 **面试**：Go 内存模型用 happens-before 定义合法顺序；channel/Mutex/atomic 建立 hb。

### 再追问

**int 赋值原子吗？**——对齐的 word 可能单条指令，但 `++` 不是；且语言仍禁止无同步并发写。**不要**靠「碰巧」。

## Q2

**★★★★☆｜data race 和 race condition 有什么区别？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、诞生：什么是 data race](知识点.md)

### 场景

库存 1 件，两请求都通过 `if stock>0` 检查——无 data race 仍超卖。


承接 Q1 定义——happens-before 从哪来。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**data race** = 内存模型非法，`-race` 能抓；**race condition** = 业务时序依赖，要靠幂等/事务/锁语义。

超卖可能是：

- 有 data race（`stock--` 非原子）  
- 无 race 但 check-then-act 窗口（要用 DB `UPDATE ... WHERE stock>0` 或 Mutex 包整个「查+改」）

> ⚠️ **别混**：`-race` 绿 ≠ 业务无竞态。

### 再追问

**怎么防 race condition？**——唯一键、乐观锁、分布式锁。**不要**以为加 Mutex 就自动防超卖（要锁整个不变量）。

## Q3

**★★★★★｜Go 的 Mutex 可重入吗？同 goroutine 连 Lock 两次会怎样？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、Mutex：互斥锁的一生](知识点.md)


Mutex 一生——护住所有读写路径。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**不可重入**；同 G 第二次 `Lock` **死锁**（阻塞在自己持有的锁上）。

```go
mu.Lock()
mu.Lock() // 永久阻塞
```

Java `ReentrantLock` 可重入，Go **没有**。拆分函数用 `lockedAdd()` 假定调用方已持锁，或统一入口 `Lock` 一次。

> 📝 **面试**：defer Unlock 只释一次；递归调用要带锁设计。

### 再追问

**RWMutex 能 RLock 再 Lock 升级吗？**——不能，死锁。**要**先 `RUnlock` 再 `Lock`（窗口期别人可能改）。

## Q4

**★★★★★｜「写的时候加了锁，读的时候没加」会怎样？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [三、Mutex：互斥锁的一生](知识点.md)

### 场景

配置 `map` 写路径 `mu.Lock()`，读路径直接 `m[k]`，压测偶发 panic。


就是 Q3「漏读路径」的现场版。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**读也是访问共享内存**——写锁只护写不护读，仍 **data race** / map **concurrent read and write**。

```go
func Get(k string) int {
    mu.RLock()
    defer mu.RUnlock()
    return m[k]
}
```

所有 goroutine 的读写必须走同一套锁。

> 🔍 **现场**：panic 栈 `fatal error: concurrent map read and map write`。

### 再追问

**返回 map 内部指针？**——调用方改仍 race。**要**返回拷贝或不可变快照。

## Q5

**★★★★★｜全局 QPS 计数用 atomic 还是 Mutex？为什么？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、atomic：无锁改一个字](知识点.md)、[九、选型：锁、atomic、channel 怎么选](知识点.md)


RWMutex——读多写少才换。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**单变量** `++` / 读 → **atomic** 更轻；多字段一致快照 → **Mutex**。

```go
var total atomic.Int64
total.Add(1)
```

Mutex 也能护 `int64`，但原子指令无锁竞争路径更短。若还要 `if total > limit { reject }` 整段是业务原子 → Mutex 或 CAS 循环。

> 📝 **面试**：atomic 不替代锁保护结构体。

### 再追问

**float 计数？**——`atomic` 无 float，用 Mutex 或分开存 int 刻度。**不要** `unsafe` 转 float 除非你真懂。

## Q6

**★★★★★｜多个 goroutine 并发写 map 会怎样？怎么修？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [七、map 与并发：必炸](知识点.md)


atomic 边界，别当万能锁。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：运行时检测到会 **fatal**；必须 **Mutex 包 map**、**sync.Map**、或 **不共享**（channel 合并）。

```go
type Safe struct {
    mu sync.RWMutex
    m  map[string]int
}
```

`sync.Map` 适合读多、key 集合稳定；一般业务 `RWMutex+map` 更清晰。

> ⚠️ **别混**：`make(map)` 无任何内置锁。

### 再追问

**分片 map 减锁？**——每 shard 一把锁，key hash 到 shard。**不要**以为分片就不算并发写同一 shard。

## Q7

**★★★★★｜如何在 CI 里启用竞态检测？有什么代价？**

**覆盖**：必会 · 常用 · 常考 ｜ **对应**：知识点 [八、-race：从插桩到报告](知识点.md)


Q6 的加深：哪些操作才是原子的。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`go test -race ./...` 或 `go build -race`；**约 5–10×** CPU/内存，**仅测试环境**。

```bash
go test -race -count=1 -timeout 5m ./...
```

生产二进制**不要** `-race` 发布。夜间压测 job 可另跑 race 构建复现。

> 📝 **面试**：没跑到冲突路径不报；通过不代表零 race。

### 再追问

**集成测试怎么开？**——测试二进制 `-race` 编译。**不要**只对单元测开小范围却漏 integration。

## Q8

**★★★★☆｜`-race` 报告里 Write 和 Previous read 两行栈怎么看？**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [八、-race：从插桩到报告](知识点.md)

### 场景

```text
Write at 0x... by goroutine 12:
  main.(*Cache).Set()
Previous read at 0x... by goroutine 8:
  main.(*Cache).Get()
```


Once/Pool 边界。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：同一**地址**上，**先**发生的访问与**后**发生的访问**无同步**——按栈修 **Get/Set 都加同一把锁**。

步骤：认变量（有时带名）→ 看谁写谁读 → 检查中间有无 Mutex/channel → 补锁或改 channel 所有权。

> 🔍 **现场**：GORACE=log_path 可落盘长压测。

### 再追问

**只报 Write-Write？**——两写同样 race。**不要**只护读不护写。

---

## Q9

**★★★★☆｜什么场景用 RWMutex 比 Mutex 好？什么时候反而更差？**

**覆盖**：常考 ｜ **对应**：知识点 [四、RWMutex：读多写少](知识点.md)


开头那个 concurrent map writes。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**读远多于写**（配置、路由表）用 `RWMutex`；**写频繁**或临界区极短，Mutex 更简单。

`RWMutex` 实现更重，写会阻塞所有读。返回数据要 **拷贝**，避免调用方持读锁时改内部。

> 📝 **面试**：读锁不是「免费」，高写仍串行。

### 再追问

**读锁里能调可能阻塞的函数吗？**——能但会拖住所有写者。**不要** RLock 里调慢 RPC。

## Q10

**★★★★☆｜sync.Once 解决什么问题？panic 了还会再执行吗？**

**覆盖**：必会 ｜ **对应**：知识点 [六、sync.Once 与 sync.Pool](知识点.md)


CI 必开 -race——检测怎么读报告。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**并发懒初始化**只跑一次；`Do` 内 **panic 也算执行过**，不会自动重试。

```go
var once sync.Once
once.Do(initDB)
```

适合单例 client、注册表。比 `if initialized` 双重检查更稳（无 race）。

> ⚠️ **别混**：`Once` 不能 reset；要重建用新 `Once` 或显式生命周期。

### 再追问

**多个 Once？**——各管各的初始化。**不要**在 `Do` 里再调同一 `Once` 的 `Do` 嵌套死锁。

## Q11

**★★★★★｜这段有 race 吗？怎么改？**

```go
if limit > 0 && atomic.LoadInt64(&n) < limit {
    atomic.AddInt64(&n, 1)
}
```

**覆盖**：核心 · 常考 ｜ **对应**：知识点 [五、atomic：无锁改一个字](知识点.md)


报告怎么读——承接 Q10。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**check 和 act 不是一体**——多 G 可能都通过 `< limit`，**超发**；有 **data race 风险**于 `n` 与业务语义。

修法：

```go
mu.Lock()
defer mu.Unlock()
if n < limit {
    n++
}
```

或 CAS 循环 / `semaphore` 占坑。限流语义见 [09](../09-errgroup与并发限流/)。

> 📝 **面试**：atomic 单操作原子，复合逻辑要整体设计。

### 再追问

**只用 Add 不管 limit？**——会无限涨。**不要**把 atomic 当分布式限流。

## Q12

**★★★☆☆｜sync.Map 适合什么场景？为什么不默认替代 map+Mutex？**

**覆盖**：常考 ｜ **对应**：知识点 [七、map 与并发：必炸](知识点.md)


选型题，串锁/atomic/channel。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**读多写少、key 稳定** 的缓存型；API 别扭、类型 `any`、统计困难，多数业务 **RWMutex+map** 更清晰。

`Load`/`Store`/`Range` 并发安全，但 `Range` 与 `Store` 同时要小心业务语义。

> 📝 **面试**：不是银弹；面试说清 trade-off。

### 再追问

**Delete 并发？**——`sync.Map` 支持。**不要** Range 里 Delete 同一 map 无设计。

## Q13

**★★★★☆｜持 Mutex 调下游 HTTP 有什么问题？**

**覆盖**：常用 ｜ **对应**：知识点 [三、Mutex：互斥锁的一生](知识点.md)

### 场景

`mu.Lock(); resp := http.Get(...); mu.Unlock()` 导致 P99 暴涨。


作战定责。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：锁护 **内存**，不护 **IO**——持锁等网络 = 全员排队，易死锁级联。

```go
mu.Lock()
cfg := snapshot()
mu.Unlock()
resp := callWith(cfg) // IO 在锁外
```

> 📝 **面试**：临界区越小越好；只包共享状态读写。

### 再追问

**锁内起 goroutine？**——若 goroutine 还要同锁 → 易死锁。**要**锁外起任务，结果 channel 回传。

## Q14

**★★★★★｜读代码：哪些行有 data race？**

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }
func (c *Counter) Val() int { return c.n }

func main() {
    var c Counter
    go c.Inc()
    go c.Inc()
    fmt.Println(c.Val())
}
```

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [二、诞生：什么是 data race](知识点.md)、[三、Mutex：互斥锁的一生](知识点.md)


本套题收尾综合口述。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`Inc` 写、`Val` 读、`Inc` 与 `Inc` 写-写 均无同步 → **多处 race**。

修法：结构体内嵌 `sync.Mutex` 或 `atomic.Int64`；方法内 `Lock/defer Unlock` 或 `atomic`。

```go
type Counter struct {
    mu sync.Mutex
    n  int
}
func (c *Counter) Inc() {
    c.mu.Lock()
    c.n++
    c.mu.Unlock()
}
```

> 🔍 **现场**：`go test -race` 一次报全。

### 再追问

**接收器是值还是指针？**——`go c.Inc()` 若值接收器会复制 struct，仍可能 race 在复制体上——方法集要统一用指针接收器。**不要**混用。
