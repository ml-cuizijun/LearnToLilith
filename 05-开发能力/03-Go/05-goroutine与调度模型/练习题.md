## Q1

**★★★★★｜口述 GMP 模型，G、M、P 各干什么？为什么 M 必须绑 P 才能跑 Go 代码？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、调度：GMP 模型怎么转](知识点.md)

### 场景

面试官白板画三个圈，让你填 G/M/P，并追问「P 没了 M 在干嘛」。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**G** 是 goroutine 任务，**M** 是 OS 线程，**P** 是逻辑处理器带本地 G 队列；**无 P 的 M 不能执行 Go 用户代码**。

- **G**：含栈、PC、状态；`go` 创建的就是 G  
- **M**：真正跑在 CPU 上的内核线程；阻塞在 syscall 时可能占着 M  
- **P**：`GOMAXPROCS` 个；持有本地 runq、`mcache`；调度基本单位  

M 执行 Go 代码前必须 ` acquire P`；P 被抢走或 G 阻塞时 M 可释放 P 去接别的 G。全局队列 + work stealing 平衡负载。

> 📝 **面试**：并行度 ≈ P 的个数，不是 G 的个数；G 可以成千上万排队。

### 再追问

**P 个数谁定？**——默认逻辑 CPU 数，`runtime.GOMAXPROCS`；容器场景见 [12](../12-GOMAXPROCS与容器cgroup/)。**不要**把 P 说成「goroutine 池大小」。

## Q2

GMP 之后——和 OS 线程比。

**★★★★★｜goroutine 和 OS 线程有什么本质区别？为什么 Go 能开很多 goroutine？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [二、诞生：go 到底做了什么](知识点.md)

### 场景

同事说「一个 goroutine 就是一个线程，所以不能开太多」，准备把并发改成单线程。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：goroutine **用户态调度、KB 级栈、阻塞不占线程干等**；线程内核调度、MB 栈、数量成本高。

| 维度 | goroutine | OS 线程 |
|------|-----------|---------|
| 调度 | runtime | 内核 |
| 栈 | ~2KB 起，可扩 | 通常 MB |
| 阻塞 I/O | netpoller 挂 G 释 M | 常占一整线程 |
| 典型数量 | 10⁴–10⁶ | 10²–10³ |

因此百万 goroutine 阻塞在 HTTP 等待是常态；百万线程会先把内核打挂。

> ⚠️ **别混**：能开很多 ≠ 应该无限 `go`；下游和资源仍是瓶颈。

### 再追问

**1:1 线程模型呢？**——如早期 NGINX worker；Go 选择 M:N 换更低创建成本和更好 I/O 多路复用。**不要**在面试里说「goroutine 就是绿色线程」而不提 GMP。

## Q3

循环闭包坑。

**★★★★★｜下面代码输出什么？怎么改？**

```go
for i := 0; i < 3; i++ {
    go func() {
        fmt.Print(i)
    }()
}
time.Sleep(time.Second)
```

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [二、诞生：go 到底做了什么](知识点.md)

### 场景

Code review 里循环里直接 `go func(){ use(i) }()`，测试环境偶发全打同一个数。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：闭包捕获 **变量 i 的地址**；并发读写在 Go 1.22 前常全看到最终值 `3`，且可能有 data race。

修法：

```go
for i := 0; i < 3; i++ {
    go func(n int) {
        fmt.Print(n)
    }(i)
}
```

Go 1.22+ 每轮 `for` 有独立 `i`，但传参仍是可读性最好的写法。

> 📝 **面试**：闭包抓的是外层变量，不是循环那一刻的快照。

### 再追问

**输出顺序？**——不确定，`go` 不保证顺序。**不要**用 `Sleep` 做同步，用 `WaitGroup` 或 channel。

## Q4

main 退出对后台 G。

**★★★★☆｜main 函数 return 了，里面 `go` 出去的任务还会执行吗？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [六、结束：正常退出与 WaitGroup](知识点.md)

### 场景

脚本式 `main` 里 `go uploadLogs()` 没 `Wait`，进程偶尔丢日志，同事以为是上传慢。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：`main` 结束 → **整个进程退出**，所有 G 被干掉，**不保证**后台 `go` 跑完。

```go
func main() {
    go func() {
        time.Sleep(2 * time.Second)
        fmt.Println("never seen")
    }()
} // 进程在此结束
```

必须 `sync.WaitGroup`、`chan` 收工，或服务里 `graceful shutdown`（[10](../10-HTTP-Server与优雅退出/)）。

> ⚠️ **别混**：`defer` 在 main 里会执行；别的 G 的 defer 不一定来得及。

### 再追问

**daemon 怎么写？**——常驻服务 `for {}` 或 `http.ListenAndServe`；一次性 CLI 必须显式等待。

## Q5

WaitGroup 正确用法。

**★★★★★｜WaitGroup 的正确用法？Add 能放在 goroutine 里面吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、结束：正常退出与 WaitGroup](知识点.md)

### 场景

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    go func() {
        wg.Add(1)  // 同事写在这里
        defer wg.Done()
        work()
    }()
}
wg.Wait()
```

偶发 `panic: sync: negative WaitGroup counter`。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：`Add` 必须在 `Wait` 之前、且与将要启动的 G **次数匹配**；推荐在 `go` **之前** `Add(1)`。

```go
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        work()
    }()
}
wg.Wait()
```

`Add` 在 `go` 内与 `Wait` 竞态，可能 `Wait` 先返回或计数错乱。

> 📝 **面试**：`Done` 等价 `Add(-1)`；`Wait` 阻塞到 counter 为 0。

### 再追问

**能重用吗？**——`Wait` 返回后可以新一轮 `Add`，但进行中不能乱 `Add`。**不要** `Done` 次数多于 `Add`。

## Q6

GOMAXPROCS 不能限 G 个数。

**★★★★☆｜线上 goroutine 太多，设 `GOMAXPROCS=1` 能解决吗？**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [三、调度：GMP 模型怎么转](知识点.md)

### 场景

压测时 G 涨到八万，运维在 systemd 里写 `Environment=GOMAXPROCS=1`，QPS 掉了但内存仍涨。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：`GOMAXPROCS` 只限 **同时执行的 P 数**，不限 **已创建的 G 数**；排队更严重，泄漏照旧。

限 goroutine 数量要用 semaphore、worker pool、或 errgroup+限流（[09](../09-errgroup与并发限流/)）。调 `GOMAXPROCS` 是调 CPU 并行度，不是背压。

> ⚠️ **别混**：容器 CPU 配额应配合 automaxprocs（[12](../12-GOMAXPROCS与容器cgroup/)），与「少开 goroutine」是两件事。

### 再追问

**何时改 GOMAXPROCS？**——CPU 密集且 P 过多导致上下文切换；或容器 quota 与默认不符。**不要**用它挡下游过载。

## Q7

就是开头暴涨现场。

**★★★★★｜生产 goroutine 只升不降，你怎么查？**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [七、泄漏：从「多」到「永远不回来」](知识点.md)

### 场景

活动结束两小时后 `go_goroutines` 指标仍比活动前高 3 万，heap 缓慢爬升。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：`pprof goroutine` 找 **重复栈** → 看阻塞点（chan/mutex/循环）→ 追谁该 cancel/recv/close 没做。

```bash
curl -s localhost:6060/debug/pprof/goroutine?debug=2 | head -100
# ← 同一 chan receive 出现上万次 = 典型泄漏栈
```

对比活动前后两次 profile 差分，定位新增栈。代码侧搜 `go func` 创建点与对应 channel/context。

> 🔍 **现场**：`runtime.NumGoroutine()` 打点 + Prometheus 告警阈值。

> 📝 **面试**：泄漏 ≠ goroutine 多；是 **永久阻塞** 导致 G 不回收。

### 再追问

**-race 能查泄漏吗？**——不能，`-race` 查 data race（[07](../07-sync原子与竞态检测/)）。**不要**重启当修复。

## Q8

这是 Q7 的读代码版。

**★★★★☆｜这段为什么会泄漏？**

```go
func leak() {
    ch := make(chan int)
    go func() {
        ch <- 42
    }()
}
```

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [七、泄漏：从「多」到「永远不回来」](知识点.md)

### 场景

热路径里「发结果到 channel 就返回」，调用方从不读。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：无缓冲 channel **发送阻塞直到有人接收**；无接收者 → 发送 G **永久阻塞**。

修法：调用方 `v := <-ch`；或 `go func(){ <-ch }()` 专门消费；或 `buffered` + 明确丢弃策略；或不用 channel 改 `sync`/`errgroup`。

> ⚠️ **别混**：`ch <-` 阻塞是特性不是 bug；设计要配对收发。

### 再追问

**buffered 就不会漏？**——缓冲满且无人读照样堵在 send。**不要**以为 `make(chan,1)` 万能。

## Q9

异步抢占与死循环。

**★★★★☆｜Go 1.14 前后调度有什么区别？死循环还会占满 CPU 吗？**

**覆盖**：常考 ｜ **对应**：知识点 [三、调度：GMP 模型怎么转](知识点.md)

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：1.14 前主要靠 **协作式** 抢占（函数调用边界）；1.14+ **异步抢占**，死循环 G 也会被 sysmon 打断。

老版本 `for {}` 可占死一个 P；新版本仍会占 CPU 时间片但别的 G 能跑。根治仍是 `ctx` 取消或 `runtime.Gosched()` 协作。

> 📝 **面试**：抢占在 **安全点** 注入，不是随时杀；CGO/部分路径仍可能延迟抢占。

### 再追问

**sysmon 是什么？**——独立 M 做 GC、抢占、netpoller 调度。**不要**说「每个 G 一个监控线程」。

## Q10

无界 go 的修法。

**★★★★★｜十万条消息每条 `go handle(msg)`，会怎样？怎么改？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [八、生产写法：别无限 go](知识点.md)

### 场景

Kafka 消费里 `for msg := range ch { go process(msg) }`，下游 MySQL 连接池打满、OOM。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：瞬间创建十万 G，**下游和内存先挂**；用 **固定 worker 池** 或 **semaphore** 限并发。

```go
sem := make(chan struct{}, 50)
for msg := range ch {
    sem <- struct{}{}
    go func(m Msg) {
        defer func() { <-sem }()
        process(m)
    }(msg)
}
```

或 N 个长期 worker 从 `jobs` channel 取活（[06](../06-channel与select/)）。

> 📝 **面试**：并发度 = 同时活跃任务数，不是 `go` 调用次数。

### 再追问

**errgroup 呢？**——带错误传播与 `SetLimit`（[09](../09-errgroup与并发限流/)）。**不要**在 consumer 里无界 `go` 当「异步」。

## Q11

G 内 panic 与 recover 位置。

**★★★★☆｜goroutine 里 panic 了，整个进程会怎样？recover 写在哪有效？**

**覆盖**：必会 ｜ **对应**：知识点 [四、运行：栈、defer 与 panic 边界](知识点.md)

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：未 recover 的 panic **向上杀当前 G**，若冒到 `main` 则 **整个进程崩溃**；`recover` 只在 **同一 G 的 defer** 里有效。

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Println(r)
        }
    }()
    panic("boom")
}()
```

别的 G 的 panic 你 recover 不到。HTTP 靠 `net/http` 每层 recover 隔离请求。

> ⚠️ **别混**：`recover` 在 defer 外无效；在父 goroutine defer 里 recover 子 G panic 无效。

### 再追问

**panic 后 defer 还跑吗？**——当前 G 上已注册的 defer 仍 LIFO 执行。**不要**用 panic 当流程控制。

## Q12

pprof 大量 chan receive。

**★★★★☆｜pprof 里大量 `chan receive`，说明什么？下一步查什么？**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [五、阻塞：G 在哪卡住](知识点.md)

### 场景

`debug=2` 输出里 80% 栈顶是 `runtime.chanrecv`。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：大量 G **等在收 channel**——要么上游没 send/close，要么消费者挂了，要么 buffer 设计错误。

下一步：从栈里找 **哪一行 `<-ch`** → 搜 channel 创建点 → 查谁负责 send/close → 看是否缺 `ctx` 超时退出。

对比 `chan send`：那是等接收者，根因对称。

> 🔍 **现场**：

```bash
go tool pprof -top http://localhost:6060/debug/pprof/goroutine
```

### 再追问

**和 mutex 阻塞怎么分？**——栈顶 `sync.(*Mutex).Lock`。**不要**把正常 I/O 等待（`poll`）当泄漏。

## Q13

多 G 的 defer 顺序。

**★★★☆☆｜多个 goroutine 各注册 defer，执行顺序是什么？**

**覆盖**：必会 ｜ **对应**：知识点 [四、运行：栈、defer 与 panic 边界](知识点.md)

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**每个 G 独立 defer 栈**，只在 **该 G return/panic** 时 **LIFO** 执行；G 之间无全局顺序。

```go
go func() {
    defer fmt.Println("A")
    defer fmt.Println("B")
}() // 该 G 内打印 B 然后 A
```

`main` 的 defer 与 worker 的 defer 互不干扰。

> 📝 **面试**：defer 注册时有参数会立刻求值（如 `defer f(i)`），函数调用延迟。

### 再追问

**main 没 Wait 时 worker 的 defer 会跑吗？**——进程退出可能来不及。**不要**依赖未等待的 G 做清理。

## Q14

读代码找泄漏点。

**★★★★★｜读代码找泄漏点**

```go
func start(ctx context.Context) {
    ticker := time.NewTicker(time.Second)
    go func() {
        for range ticker.C {
            report()
        }
    }()
}
```

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [七、泄漏：从「多」到「永远不回来」](知识点.md)

### 场景

每次调用 `start` 部署一个定时上报，调用几十次后 goroutine 和 ticker 堆着。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：`go` 里 **无限 `for range ticker.C`**，且 **没用传入的 `ctx`**，`start` 返回后 G 永不退出；`ticker` 也未 `Stop`。

修法：

```go
go func() {
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            report()
        case <-ctx.Done():
            return
        }
    }
}()
```

或返回 `stop func()` 给调用方。模式见 [08](../08-context取消与超时传播/)。

> 📝 **面试**：带生命周期的后台任务必须绑 **ctx 或显式 stop**。

### 再追问

**只 Stop ticker 够吗？**——`Stop` 后 G 仍可能卡在 `range`，仍需 `ctx` 或 `done` channel 退出循环。**不要**以为 `Stop` 会杀 goroutine。
