## Q1

**★★★★★｜errgroup 相比手写 WaitGroup + errCh，主要解决什么？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [二、基础 Group：WaitGroup + error](知识点.md)

### 完整解答

> 🎯 **一句话**：把 **启动 goroutine、等结束、收集第一个 error** 打包；`WithContext` 版还自动 **首错 cancel**。

样板代码少、不易漏 `wg.Add/Done`、错误路径统一 `Wait()` 返回。适合批处理 fan-out。

> 📝 **面试**：不是万能——QPS 限流、优先级队列还要别的工具。

### 再追问

**能替代 channel 吗？**——不能；数据流仍靠 channel，errgroup 管**生命周期和错误**。

## Q2

**★★★★★｜errgroup.WithContext 何时 cancel？子任务该用哪个 ctx？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、WithContext：首错取消](知识点.md)

### 完整解答

> 🎯 **一句话**：任一 `Go` 的函数 **`return err != nil`** 时 cancel 派生 ctx；子任务必须用 **`WithContext` 返回的 ctx`** 调下游。

```go
g, ctx := errgroup.WithContext(parent)
g.Go(func() error {
    return httpGet(ctx, url) // 不是 parent
})
```

> ⚠️ **别混**：`return nil` 不 cancel；`Wait()` 返回第一个 error。

### 再追问

**一个任务失败要其它继续？**——别用 WithContext，用裸 Group 或子任务 return nil 只记日志。

## Q3

**★★★★★｜SetLimit(10) 表示什么？Go 1.19 没有怎么办？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、SetLimit：并发上限](知识点.md)

### 完整解答

> 🎯 **一句话**：最多 **10 个子任务同时执行**；其余排队等槽位。Go 1.19 用 **semaphore** 或 **worker pool** 自实现。

```go
g.SetLimit(10)
for _, item := range millionItems {
    g.Go(func() error { ... })
}
```

> 📝 **面试**：不是「总共只能 Go 10 次」，是**并发度**上限。

### 再追问

**SetLimit(0)？**——表示不限（默认行为）。

## Q4

**★★★★☆｜errgroup 和 sync.WaitGroup 怎么选？**

**覆盖**：必会 ｜ **对应**：知识点 [能力边界](知识点.md)

### 完整解答

> 🎯 **一句话**：要 **error 返回 + 可选首错 cancel** → errgroup；只等结束、错误自己处理 → WaitGroup。

WaitGroup 无 error 聚合；手写 errCh 易漏 cancel。

> 📝 **面试**：两者可组合——errgroup 内部就是 wg。

### 再追问

**Wait 返回后还能 Go 吗？**——**不要**；应新建 Group。

## Q5

**★★★★★｜用 GOMAXPROCS=4 能否限制 errgroup 启动的 goroutine 数量？**

**覆盖**：核心 · 常考 ｜ **对应**：知识点 [四、SetLimit：并发上限](知识点.md)

### 完整解答

> 🎯 **一句话**：**不能**；GOMAXPROCS 只限 **同时跑在 CPU 上的 OS 线程数**，goroutine 仍可海量创建，**连接/内存照样爆**。

限并发用 `SetLimit` / semaphore / worker pool（[12](../12-GOMAXPROCS与容器cgroup/)）。

> ⚠️ **别混**：调度并行度 ≠ 应用并发度。

### 再追问

**I/O 密集还要 SetLimit 吗？**——**要**；I/O 也会占连接、FD、下游配额。

## Q6

**★★★★★｜这段代码有什么问题？**

```go
for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
```

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [十三、踩坑清单](知识点.md)

### 完整解答

> 🎯 **一句话**：**闭包捕获循环变量**——全部可能请求最后一个 url。

```go
for _, url := range urls {
    url := url
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
```

> 📝 **面试**：Go 1.22+ 循环变量语义改了，老代码/面试仍考 `url := url`。

### 再追问

**传参 Go？**——`g.Go(func() error { return fetch(ctx, url) })` 在 1.22+ 可能 OK，生产仍建议显式复制保可读。

## Q7

**★★★★☆｜errgroup.SetLimit 和 semaphore.Weighted 怎么选？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、semaphore.Weighted：更通用的槽位](知识点.md)

### 完整解答

> 🎯 **一句话**：**同质批任务 + errgroup** → 优先 `SetLimit`；**嵌套占多槽、非 errgroup 结构** → `semaphore`。

```go
sem.Acquire(ctx, 1)
defer sem.Release(1)
```

Acquire 阻塞时 respect ctx cancel。

> 📝 **面试**：可组合——SetLimit 粗调，sem 细调子资源。

### 再追问

**Weighted(10) Acquire(ctx, 3)？**——一次占 3 槽，适合大任务占更多资源。

## Q8

**★★★★☆｜需要跑完所有分片并收集全部错误，怎么用 errgroup？**

**覆盖**：常用 · 常考 ｜ **对应**：知识点 [九、fan-out / fan-in 模板](知识点.md)

### 完整解答

> 🎯 **一句话**：**别用 WithContext**（首错 cancel）；用裸 Group + `mutex` 收集 `[]error`，或每任务 `return nil` 只 append err。

fail-fast 用 WithContext；best-effort 全跑要换语义。

> 📝 **面试**：两种产品需求要说清再写代码。

### 再追问

**既要全跑又要最后 return 一个？**——`errors.Join(errs...)`（Go 1.20+）自己聚合。

## Q9

**★★★★☆｜errgroup 子任务 panic 会怎样？**

**覆盖**：必会 ｜ **对应**：知识点 [七、panic 与错误处理](知识点.md)

### 完整解答

> 🎯 **一句话**：**Wait 会 panic**（传播 panic）——fn 内应 **defer recover** 转成 error。

```go
defer func() {
    if r := recover(); r != nil {
        err = fmt.Errorf("panic: %v", r)
    }
}()
```

> ⚠️ **别混**：普通 goroutine panic 杀进程；errgroup 实现会 re-panic 到 Wait 调用栈。

### 再追问

**HTTP middleware recover 够吗？**——够 handler 层；errgroup 在 service 层仍要 recover。

## Q10

**★★★★★｜WithContext 后子任务仍用 parent 调 DB，会怎样？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [三、WithContext：首错取消](知识点.md)

### 场景

分片 A 失败 cancel，分片 B 的 Query 仍用 parent 跑满 30s。

### 完整解答

> 🎯 **一句话**：**首错 cancel 传不到 B**——B 占连接、拖慢 Shutdown/批处理结束。

修法：`QueryContext(ctx,...)` 且 ctx 来自 errgroup。

> 🔍 **现场**：看 cancel 尖峰后 DB active conn 是否仍高。

### 再追问

**parent 带 Value/trace？**——派生 ctx 继承 Value；应用 errgroup 的 ctx 即可，一般不必 parent。

## Q11

**★★★★★｜批量任务后 MySQL too many connections，怎么改 errgroup 用法？**

**覆盖**：常用 · 必会 ｜ **对应**：知识点 [十一、作战：429 / 连接池耗尽怎么查](知识点.md)

### 完整解答

> 🎯 **一句话**：**SetLimit ≤ max_open_conns 留余量**；确认每任务 **defer rows.Close**；子 timeout 别长于连接持有时间。

```go
g.SetLimit(15) // pool 20
```

> 📝 **面试**：连接池是全局的，errgroup 只是批处理入口之一。

### 再追问

**HTTP 出站？**——对齐 `MaxConnsPerHost` / Transport 限制。

## Q12

**★★★★☆｜持续从 channel 读任务，用 errgroup 还是固定 worker pool？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、worker pool 与 errgroup 选型](知识点.md)

### 完整解答

> 🎯 **一句话**：**长驻消费** → N 个 `g.Go(worker)` 读同一 channel；**有限列表批处理** → for range + SetLimit。

流式要处理 `ctx.Done()` 和 channel close。

> 📝 **面试**：百万级任务别百万 Go，用 queue + 固定 worker。

### 再追问

**worker 数怎么定？**——压测 P99、下游限额、CPU；常 2×~10× 核数起步调。

## Q13

**★★★★☆｜SetLimit(32) 和 rate.Limiter 100/s 有什么区别？**

**覆盖**：常考 ｜ **对应**：知识点 [十五、标准库与扩展对照](知识点.md)

### 完整解答

> 🎯 **一句话**：**SetLimit** = 同时占用槽位数（并发连接）；**rate** = 每秒启动/通过请求数（QPS）。

大促可能 **SetLimit 20 + rate 500/s** 组合。

> ⚠️ **别混**：只 SetLimit 仍可能瞬时打满 burst。

### 再追问

**漏桶 vs 令牌桶？**——`x/time/rate` 是令牌桶；严格平滑用别的实现。

## Q14

**★★★★★｜读代码找问题**

```go
func syncAll(parent context.Context, ids []int) error {
    g, _ := errgroup.WithContext(parent)
    for _, id := range ids {
        g.Go(func() error {
            return call(parent, id)
        })
    }
    return g.Wait()
}
```

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [三、WithContext：首错取消](知识点.md)、[十三、踩坑清单](知识点.md)

### 完整解答

> 🎯 **一句话**：至少两处：**丢弃 ctx 应用派生 ctx**；**闭包 id 未复制**；`_` 忽略 ctx 变量导致无法用派生 ctx。

```go
g, ctx := errgroup.WithContext(parent)
for _, id := range ids {
    id := id
    g.Go(func() error {
        return call(ctx, id)
    })
}
return g.Wait()
```

> 📝 **面试**：`_, _` 丢 ctx 是标配坑。

### 再追问

**没 SetLimit？**——ids 上万可能打穿下游，应 `SetLimit`。
