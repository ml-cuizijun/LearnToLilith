## Q1

**★★★★☆｜context.Background() 和 context.TODO() 有什么区别？什么时候用哪个？**

**覆盖**：必会 ｜ **对应**：知识点 [二、根：Background 与 TODO](知识点.md)


先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**行为几乎相同**（永不过期、无 Value）；**语义**上 Background 是正式根，TODO 是「父 ctx 未定」占位。

- `main`、测试根、`ListenAndServe` 外层 → `Background()`  
- 重构中、接口暂时接不到上游 → `TODO()`  

需要取消/超时的任务应用 `WithCancel`/`WithTimeout` 从 Background **派生**，别长期裸 Background 跑后台。

> 📝 **面试**：两者不能互相替代的是**代码审查信号**，不是运行时差异。

### 再追问

**nil ctx 传库函数？**——panic 或未定义。**不要**传 nil，用 Background 或真实 ctx。

## Q2

**★★★★★｜WithCancel / WithTimeout 为什么必须 defer cancel()？不 defer 会怎样？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、派生：WithCancel](知识点.md)、[四、派生：WithTimeout 与 WithDeadline](知识点.md)


Background vs TODO——承接 Q1 根。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`cancel()` **释放 timer 和子树资源**；`WithTimeout` 不 defer 且未到期 → **timer 泄漏**。

```go
ctx, cancel := context.WithTimeout(parent, time.Second)
defer cancel() // 即使正常返回也要调，幂等
```

任务已完成也 defer——早释放比等 deadline 更省。`cancel()` 多次调用安全。

> ⚠️ **别混**：忘了 defer 不等于 goroutine 泄漏，但 **timer/子 ctx 节点** 可能堆着。

### 再追问

**子函数里 WithCancel 谁 defer？**——**创建派生的那层** defer。**不要**把 cancel 传给调用方除非 API 约定 ownership。

## Q3

**★★★★★｜父 context 被 cancel，子 context 会怎样？子 cancel 会取消父吗？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [三、派生：WithCancel](知识点.md)


WithCancel——谁 defer cancel。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**父死子必死**（子 `Done` 也关）；**子死父不受影响**。

```text
cancel(parent) → 整棵子树 Done 关闭
cancel(child)  → 仅该子树
```

设计时把「要一起停的任务」挂在同一棵子树下。

> 📝 **面试**：树形单向传播，不是双向。

### 再追问

**多个兄弟子 ctx？**——父 cancel 全死。**不要**以为 cancel 一个兄弟会影响另一个（除非共享父）。

## Q4

**★★★★★｜父 WithTimeout 10s，子 WithTimeout 30s，子任务最多能跑多久？反过来的话？**

**覆盖**：核心 · 必会 · 常考 ｜ **对应**：知识点 [四、派生：WithTimeout 与 WithDeadline](知识点.md)


就是 Q3 漏 cancel 的泄漏版。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：deadline 取**更早**的那个——父 10s 子 30s → **~10s**；父 10s 子 3s → **~3s**。

子不能获得比父更长的生命；子只能更严。调超时从外向内画链，别在底层盲目加大。

> 📝 **面试**：这是 interview 白板高频算术题。

### 再追问

**只有 WithCancel 无 deadline？**——子跟父活一样久，直到任一 cancel。**不要**在子再 WithTimeout 想「延长」父。

## Q5

**★★★★★｜调用 cancel() 后，goroutine 会自动退出吗？**

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [六、接收端：怎么听取消](知识点.md)

### 场景

`cancel()` 后 worker 还在写 DB，发布拖 30s。


WithTimeout 与父超时谁更紧。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**不会**；cancel 只 **关闭 Done channel**，goroutine 必须 **`select <-ctx.Done()`** 或调支持 ctx 的阻塞 API。

```go
select {
case <-ctx.Done():
    return
default:
    // 长计算不检查 → cancel 无效
}
```

还要 `WaitGroup` 等真退出（[05](../05-goroutine与调度模型/)）。

> ⚠️ **别混**：context 是协作式取消，不是 `kill`。

### 再追问

**CPU 密集循环？**——定期 `ctx.Err()` 或 `select default`+Done。**不要**假设 cancel 能打断纯计算。

## Q6

**★★★★☆｜能把 context.Context 存在 struct 字段里吗？**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [五、传播：函数签名与 HTTP](知识点.md)


Q5 的数字题版。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**不要**；ctx 绑定**单次请求生命周期**，存 struct 易跨请求泄漏或用到已 cancel 的 ctx。

```go
// 反模式
type Service struct { ctx context.Context }

// 正模式
func (s *Service) Do(ctx context.Context, id string) error
```

> 📝 **面试**：ctx 作第一参数传递，不当作依赖注入单例字段。

### 再追问

**Server 级 shutdown ctx？**——`main` 里单独变量可以，别和 `*Service` 业务 struct 混。**要**分清应用生命周期与请求 ctx。

## Q7

**★★★★★｜HTTP handler 如何把取消传到 database/sql？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [五、传播：函数签名与 HTTP](知识点.md)


函数签名必须带 ctx。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`r.Context()` → 层层参数 → `db.QueryContext(ctx, sql, args...)`。

```go
func handler(w http.ResponseWriter, r *http.Request) {
    rows, err := db.QueryContext(r.Context(), "SELECT ...")
}
```

客户端断连 → `r.Context()` cancel → DB 驱动尽量中断等待。换成 `Query` 或 `Background()` 就断不了。

> 🔍 **现场**：发布时看 DB 活跃连接是否随 QPS 降。

### 再追问

**http.Client 出站？**——`NewRequestWithContext(ctx, ...)`。**不要**只设 `Client.Timeout` 不传 ctx。

## Q8

**★★★★☆｜context.Canceled 和 context.DeadlineExceeded 各表示什么？日志怎么处理？**

**覆盖**：必会 · 常用 ｜ **对应**：知识点 [六、接收端：怎么听取消](知识点.md)


HTTP 传播——承接 Q7。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**Canceled** = 主动 cancel 或客户端断开；**DeadlineExceeded** = 超时到了。

```go
if errors.Is(err, context.Canceled) {
    // 常降级日志，不当 5xx
}
if errors.Is(err, context.DeadlineExceeded) {
    // 常要调 SLA / 优化慢查询
}
```

> 📝 **面试**：用 `errors.Is`，别字符串比较。

### 再追问

**两者能同时？**——`Err()` 只返回一个，超时触发的 cancel 路径可能都是 DeadlineExceeded。**不要**混用 `==` 和 wrapped err。

## Q9

**★★★★☆｜WithValue 应该传什么？为什么不要用 string 做 key？**

**覆盖**：常考 ｜ **对应**：知识点 [七、WithValue：能不用就不用](知识点.md)


接收端怎么听 Done。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：只传 **请求级元数据**（trace id）；用 **未导出类型** 作 key 防包之间冲突；**不传**业务对象。

```go
type ctxKey struct{}
ctx = context.WithValue(ctx, ctxKey{}, traceID)
```

string key `"user"` 易被第三方库撞车。业务数据用函数参数。

> ⚠️ **别混**：Value 不参与取消，也不替代参数。

### 再追问

**链路上多处 WithValue？**——可以，查 Value 向上走祖先。**不要**塞大 struct 导致隐式依赖。

## Q10

**★★★★★｜业务函数收到 ctx，内部却用 context.Background() 调下游，有什么问题？**

**覆盖**：核心 · 必会 · 常用 ｜ **对应**：知识点 [五、传播：函数签名与 HTTP](知识点.md)

### 场景

发布时入口已 cancel，DB 连接仍满，因为 repo 层全用 Background。


WithValue 红线。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：**上游取消传不下去**——客户端走了、发布摘流了，下游仍跑满超时，占连接、拖 Shutdown。

修法：全链路 `QueryContext(ctx,...)` / gRPC `Ping(ctx,...)`。Code review 用 `rg 'Background\(\)'` 扫业务包。

> 📝 **面试**：Background 只出现在 main 根和测试，不在请求路径。

### 再追问

**库函数没 ctx 参数？**——换库或包一层；长期看提 PR 加 `*Context` 变体。**不要**在业务里永久 Background 补丁。

## Q11

**★★★★★｜写一段同时等 job channel 和 ctx 取消的 select。**

**覆盖**：必会 · 常考 ｜ **对应**：知识点 [六、接收端：怎么听取消](知识点.md)、[八、与 goroutine、channel 协作](知识点.md)


与 channel/select 协作。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：

```go
for {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case job, ok := <-jobs:
        if !ok {
            return nil
        }
        if err := handle(job); err != nil {
            return err
        }
    }
}
```

`jobs` 关闭和 `ctx` 取消都要处理；只监听 ctx 不 close jobs 会泄漏 consumer（[06](../06-channel与select/)）。

> 📝 **面试**：一个 select 块，别拆两个 goroutine 竞态。

### 再追问

**default 分支？**——除非非阻塞试探，否则别 busy loop。**不要**去掉 ctx 分支只靠 close jobs。

## Q12

**★★★★☆｜滚动发布时日志突然大量 context canceled，怎么排查？**

**覆盖**：常用 · 必会 ｜ **对应**：知识点 [十一、作战：context canceled 泛滥怎么查](知识点.md)


生产超时链。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：先分 **Canceled（摘流/客户端断）** vs **DeadlineExceeded（太慢）** → 看是否与 **Shutdown 时间线** 重合 → 查 **handler 是否把 ctx 传到底**。

正常发布：入口 `Shutdown` → 进行中的 `r.Context()` cancel → 下游报 Canceled **预期内**。异常：Background 路径仍在跑拖住退出。

> 🔍 **现场**：对齐 `kubectl delete pod` 时间与 canceled 尖峰。

### 再追问

**要全告警吗？**——Canceled 在发布窗口可采样。**不要**一律当 500。

## Q13

**★★★★☆｜errgroup.WithContext 和裸 WithCancel 有什么关系？**

**覆盖**：必会 ｜ **对应**：知识点 [八、与 goroutine、channel 协作](知识点.md)


开头那个 canceled 泛滥现场。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：`errgroup.WithContext(parent)` 返回的 ctx 在 **任一子任务返回 error 时自动 cancel**，并 `Wait()` 收束——省手写 cancel+wg+errCh。

```go
g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return taskA(ctx) })
g.Go(func() error { return taskB(ctx) })
return g.Wait()
```

细节与限流见 [09](../09-errgroup与并发限流/)。

> 📝 **面试**：首错取消是常见模式，context 提供信号，errgroup 提供编排。

### 再追问

**一个任务失败要全停吗？**——默认是；要独立失败用 separate ctx 或 errgroup 变体。**不要**混用共享 ctx 又期望互不影响。

## Q14

**★★★★★｜读代码找问题**

```go
func fetch(ctx context.Context, url string) error {
    ctx, _ := context.WithTimeout(ctx, 5*time.Second)
    req, _ := http.NewRequest("GET", url, nil)
    _, err := http.DefaultClient.Do(req)
    return err
}
```

**覆盖**：核心 · 必会 ｜ **对应**：知识点 [四、派生：WithTimeout 与 WithDeadline](知识点.md)、[五、传播：函数签名与 HTTP](知识点.md)


本套题收尾综合口述。

先自己试试，再往下看解答。

### 完整解答

> 🎯 **一句话**：至少三处 bug：**丢弃 cancel 未 defer**；**NewRequest 未绑 ctx**；**忽略 NewRequest 错误**。

```go
func fetch(ctx context.Context, url string) error {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return err
    }
    _, err = http.DefaultClient.Do(req)
    return err
}
```

> 📝 **面试**：`_, _` 丢 cancel 是面试题标配。

### 再追问

**DefaultClient 无 Timeout？**——还应设 `Client` 或只靠 ctx。**不要**假设 Do 会尊重未传入的 ctx。
