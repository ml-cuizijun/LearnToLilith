## Q1

**★★★★★｜等 Deployment Ready 的 `while` 循环必须有什么，否则 CI 会怎样？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [二、出生：为什么要 deadline](知识点.md)

### 场景

`while not ready: sleep(5)` 无上限，镜像拉取失败 CI 挂 6 小时。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**必须有总 deadline（budget）**，超时明确失败 `return 1`。

```python
deadline = time.monotonic() + budget
while time.monotonic() < deadline:
    if is_ready():
        return
    time.sleep(interval)
raise TimeoutError(f"not ready after {budget}s: {last_reason}")
```

> 📝 **面试**：「等价 `kubectl rollout status --timeout=600s`。」

### 再追问

budget 谁定？——CLI `--wait-timeout`、README、CI 阶段上限。

## Q3

这是 Q1 的间隔版：短等固定、长等退避。

**★★★★☆｜短 CI 门禁（小于 5 分钟）与长等外部恢复（>15min），poll 间隔怎么选？**

**覆盖**：必会 · 常用 | **对应**：知识点 [三、间隔：固定 vs 退避](知识点.md)

### 场景

长任务仍 `sleep(1)`，apiserver audit 日志暴涨。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**短等固定 3–10s**；**长等指数退避 + cap（如 60s）+ jitter**。

```python
time.sleep(backoff_interval(attempt, base=1.0, cap=60.0))
```

固定 1s 适合本地调试，不适合大规模生产 poll。

### 再追问

cap 太大太小？——太大响应慢，太小仍压 API；60s 是常见起点。

## Q4

循环有了，条件写错仍假绿。

**★★★★★｜怎样定义 Deployment「Ready」才不算假绿？**

**覆盖**：核心 · 必会 | **对应**：知识点 [四、条件：什么叫「成功」](知识点.md)

### 场景

`ready_replicas=1`、`spec.replicas=3`，脚本继续部署下一步。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**`ready_replicas >= spec.replicas` 且 spec>0**；可选 generation 对齐。

```python
spec = dep.spec.replicas or 0
ready = dep.status.ready_replicas or 0
if ready < spec:
    return False, f"ready={ready}/{spec}"
```

还要排除 CrashLoop 仅 Running 等（结合 Ready condition）。

### 再追问

Job 完成呢？——`status.succeeded == 1` 且 `Failed` 无。

## Q5

就是 09 与 11 分层——别两层都 aggressive。

**★★★★★｜外层 poll 与 09 HTTP 重试如何分工？为何不能都 aggressive？**

**覆盖**：核心 · 必会 · 常考 | **对应**：知识点 [五、与 HTTP 重试分层](知识点.md)

### 场景

外层 100 轮 × 内层 5 次 retry × 32 线程 = apiserver 灾难。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**09 管单次 call 瞬态（2–3 次）**；**11 管条件未真时的轮次与间隔**；避免重试相乘。

```python
def check_once():
    resp = request_with_retry(session, "GET", url, max_attempts=3)  # 09
    ...

while monotonic() < deadline:  # 11
    ok, reason = check_once()
    ...
    sleep(backoff_interval(attempt))
```

### 再追问

watch 替代 poll？——长连接省 QPS，断线要重连与 deadline。

## Q6

和 Q3 呼应——jitter 打散惊群。

**★★★★☆｜轮询退避的 jitter 与 09 HTTP 退避的 jitter 目的相同吗？**

**覆盖**：必会 | **对应**：知识点 [三、六](知识点.md)

### 场景

故障恢复后 200 脚本同时从 sleep 醒来。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**相同——打散同步重试/poll 峰值**（thundering herd）。

### 完整解答

> 🎯 **一句话**：**用 Ready condition 或 HTTP readiness**，对齐 K8s 语义而非仅 Running。

## Q9

手写循环的库封装版。

**★★★☆☆｜tenacity 的 `stop_after_delay(600)` 对应手写什么？**

**覆盖**：常用 | **对应**：知识点 [六、tenacity 与手写](知识点.md)

### 场景

团队引入 tenacity 统一等待策略。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**从首次调用起累计 600s 内可 retry**，等价于带 deadline 的 poll/retry 组合。

```python
@retry(stop=stop_after_delay(600), wait=wait_exponential_jitter(initial=1, max=60))

    if not check():
        raise NotReadyError("...")
```

复杂 reason 仍建议手写 loop 可读。

### 再追问

`retry_if_result`？——可用来判 `ok is False` 时 retry。

## Q14

读代码找缺 deadline / 假绿。

**★★★★★｜读代码找 bug：**

```python
def wait_ready(get_status):
    while True:
        status = get_status()
        if status == "Running":
            return True
        time.sleep(1)

def main():
    wait_ready(lambda: kubectl_get_phase())
    print("deploy ok")
    return 0
```

**覆盖**：核心 · 必会 | **对应**：知识点 [二、四、七](知识点.md)

### 场景

CrashLoop BackOff 仍 Running，无 timeout CI 挂死。

先自己试试：不看下面，你能口述答案吗？讲完再对「完整解答」。

### 完整解答

> 🎯 **一句话**：**无 deadline**；**success=Running 假绿**；应 Ready/replicas + TimeoutError + return 1。

```python
def wait_ready(get_status, budget=600) -> None:
    deadline = time.monotonic() + budget
    last = "unknown"
    while time.monotonic() < deadline:
        ok, last = get_status()
        if ok:
            return
        time.sleep(5)
    raise TimeoutError(last)

def main() -> int:
    try:
        wait_ready(check_deployment_ready, budget=600)
    except TimeoutError as e:
        log.error("wait failed: %s", e)
        return 1
    return 0
```

> 📝 **面试**：「两 bug：无限 loop + Running 非 Ready。」

### 再追问

get_status 内 HTTP 应用 09 重试——可以，但 max_attempts 要小。
