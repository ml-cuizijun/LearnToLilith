# 09｜HTTP 客户端与重试 · SRE 开发能力

> 大家好，欢迎来到这次分享。开讲之前，先带大家回到一个很多值班同学都踩过的现场：
> 巡检脚本调 Prometheus API，`requests.get(url)` 没设 timeout——挂 30 分钟 cron 重叠；502 立刻连打 100 次把网关打挂；POST 创建工单失败重试导致重复单——群里已经有人在喊「把接口打爆了先限流」。
> 这一章讲完，你会知道当时那几个人各自错在哪——HTTP 不是「发出去就完」：超时、幂等、退避、状态码分层处理才是运维脚本的契约。
> **本章回答的问题**：一次 HTTP 请求从构造、发出、读响应、判失败到重试退出的完整链路。
> **本章不讲**：logging 字段规范 → [05 logging日志规范](../05-logging日志规范/)；轮询等待总预算 → [11 轮询超时与退避](../11-轮询超时与退避/)；退出码汇总 → [04 异常与退出码](../04-异常与退出码/)。

**怎么听这场分享**：先把「HTTP 请求一生」主图装进脑子——构造 → Session → 状态码 → 异常 → 重试；放慢可重试边界与退避；作战节回到开头那个 502 风暴现场。每一节讲完会提示对应练习题，趁热打铁。


## 面试怎么考

| 标记 | 考点 |
|------|------|
| **核心** | `requests`/`httpx`；`timeout=(connect, read)`；`raise_for_status()`；可重试 vs 不可重试 |
| **必会** | 必须设 timeout；5xx/429/连接错误可重试；4xx（除 429）一般不重试；GET 幂等 |
| **常用** | `Session` 连接池；`Retry`/`urllib3.util.retry`；指数退避 + jitter；自定义 Header |
| **常考** | POST 重试幂等；`timeout=None` 危害；重试放大流量；TLS verify |

**30 秒怎么说**：运维脚本用 `requests` 或 `httpx`，**永远设 timeout**（connect + read）。成功看 2xx，`response.raise_for_status()`。可重试：超时、连接失败、429、5xx；不可重试：4xx 参数错。重试用**指数退避 + 上限 + jitter**，POST 要么幂等键要么别盲重试。用 `Session` 复用连接。失败最终 `raise` 或 `return 1`，别吞。

## 能力边界

| 维度 | requests + 手写重试 | curl 一行 | SDK（K8s/boto） |
|------|---------------------|-----------|-----------------|
| **适合** | REST 巡检、Webhook、Prometheus | 临时验证 | 云/K8s 原生 API |
| **不适合** | 超大流式下载无分块 | 复杂重试逻辑 | 简单 HTTP 探活 |
| **契约** | timeout + 状态码 + 重试边界 | 人眼 | SDK 自带重试策略 |

| 机制 | 管什么 | 不管什么 |
|------|--------|----------|
| `timeout` | 单次请求最长等待 | 业务逻辑正确性 |
| 重试 | 瞬态故障 | 永久性 404 |
| `Session` | TCP/TLS 复用 | API 限流配额（要读 Header） |

> ⚠️ **别混**：**没 timeout 的 HTTP 客户端是 cron 杀手**——进程挂住比失败更糟。

## 一、一张图：HTTP 请求从发起到重试的一生

> 🎯 **一句话**：**构造（URL/Header/Body）→ 发出（DNS/TCP/TLS）→ 等响应（timeout 守门）→ 判成败（状态码/body）→ 可重试? → 退避再试或失败退出**。

```mermaid
flowchart LR
    A[构造 Request] --> B[Session.send]
    B --> C{timeout?}
    C -->|超时| D[ConnectTimeout / ReadTimeout]
    C -->|收到响应| E{status}
    E -->|2xx| F[解析 body 成功]
    E -->|429/5xx| G{重试预算?}
    E -->|4xx| H[不可重试 失败]
    D --> G
    G -->|有| I[sleep 退避+jitter]
    I --> B
    G -->|无| J[raise / return 1]
    H --> J
    F --> K[return 数据]
```

**读图**：**H 岔路**是参数/权限错——重试无意义还浪费配额。**G→I** 必须有上限，否则 502 风暴变 DDoS。

## 二、出生：构造一次请求

> 🎯 **一句话**：**URL + 方法 + Header + Body + timeout** 五件套，缺 timeout 等于没写完。

```python
import os
import requests

PROM_URL = os.environ.get("PROMETHEUS_URL", "http://prom:9090")
TIMEOUT = (3.05, 27)

headers = {
    "Accept": "application/json",
    "Authorization": f"Bearer {os.environ['API_TOKEN']}",
}

resp = requests.get(
    f"{PROM_URL}/api/v1/query",
    params={"query": "up"},
    headers=headers,
    timeout=TIMEOUT,
)
```

### timeout 两层含义（⭐常考）

| 参数 | 含义 | 典型值 |
|------|------|--------|
| connect | TCP/TLS 建立上限 | 3s |
| read | 首字节后读 body 上限 | 27s |
| 单数字 | 同时作用于 connect+read | 10s |

```python
# 反模式
requests.get(url)              # timeout=None，永久阻塞
requests.get(url, timeout=999) # 一个数过大，connect 也拖死
```

> 📝 **面试**：「connect 短、read 略长——连不上快失败，慢查询给读时间。」

## 三、发出：Session 与连接池（必会）

> 🎯 **一句话**：**循环里用 `Session`**，避免每条请求新建 TCP/TLS。

```python
def check_all_targets(urls: list[str]) -> list[str]:
    failures: list[str] = []
    with requests.Session() as session:
        session.headers.update({"User-Agent": "sre-check/1.0"})
        for url in urls:
            try:
                r = session.get(url, timeout=(3, 10))
                r.raise_for_status()
            except requests.RequestException as e:
                failures.append(f"{url}: {e}")
    return failures
```

`Session` 内部 `urllib3` 连接池：`pool_connections`、`pool_maxsize` 对高并发巡检可调。

```python
# 高并发巡检调池
adapter = HTTPAdapter(pool_connections=10, pool_maxsize=50, max_retries=0)
session.mount("https://", adapter)
session.mount("http://", adapter)
# ← pool_connections=10：对 10 个不同 host 保留连接
# ← pool_maxsize=50：同一 host 最多 50 条并发连接
```

> 🔍 **现场**：`ss -tn | grep :9090 | wc -l` 百 URL 巡检后连接数——裸 get 会看到大量 TIME-WAIT，Session 稳定在池大小以内。

> 💡 **打个比方**：Session 像 keep-alive 的长电话线；裸 `get` 每次重新拨号。

## 四、读响应：状态码与 raise_for_status（⭐常考）

> 🎯 **一句话**：**2xx 成功；`raise_for_status()` 把 4xx/5xx 变成异常**。

```python
resp = session.get(url, timeout=TIMEOUT)
resp.raise_for_status()
data = resp.json()
```

| 码段 | 含义 | 运维脚本默认策略 |
|------|------|------------------|
| 200/201/204 | 成功 | 解析 body（注意 204 无 body） |
| 301/302 | 重定向 | 默认 follow，关注 redirect 链 |
| 400/422 | 请求/参数错 | **不重试**，修 payload |
| 401/403 | 认证/授权 | 修 token，别重试 |
| 404 | 资源不存在 | **不重试**，查路径 |
| 408 | 请求超时 | 可重试 |
| 429 | 限流 | 退避 + 读 `Retry-After` |
| 500–599 | 服务端瞬态 | 有限重试 |

```python
try:
    resp.raise_for_status()
except requests.HTTPError as e:
    if e.response is not None and e.response.status_code == 404:
        raise ResourceNotFound(url) from e
    raise
```

> ⚠️ **别混**：`status_code == 200` 不够——204、201 也成功；用 `resp.ok` 或 `raise_for_status`。


本节对应练习题 Q3、Q4。

## 五、判失败：RequestException 家族（必会）

> 🎯 **一句话**：**网络层、超时、HTTP 错误都继承 `RequestException`**——分层 catch。

```mermaid
graph TD
    A["RequestException"] --> B["ConnectionError<br/>DNS、拒绝连接"]
    A --> C["Timeout<br/>ConnectTimeout, ReadTimeout"]
    A --> D["HTTPError<br/>raise_for_status 抛出"]
    A --> E["TooManyRedirects"]
```

```python
import requests
from requests.exceptions import ConnectTimeout, HTTPError, RequestException

try:
    resp = session.get(url, timeout=TIMEOUT)
    resp.raise_for_status()
except ConnectTimeout:
    log.warning("connect timeout %s", url)
    raise
except HTTPError as e:
    code = e.response.status_code if e.response else "?"
    log.error("http %s %s", code, url)
    raise
except RequestException:
    log.exception("request failed %s", url)
    raise
```

## 六、重试：可重试边界与退避（🔥难点）

> 🎯 **一句话**：**只重试瞬态故障；次数有上限；间隔指数增长 + jitter**。

🔥 **幂等（idempotent）** = 同一操作执行一次和执行十次，最终结果一样。大白话：按一次电梯按钮和按十次，电梯还是来一趟；但「创建工单」按十次会出十张单。⭐ 这是面试必考。

很多人会答「失败就重试」——错了。先问：这个请求重试会不会制造副作用？

> 💡 **打个比方**：你打电话对方没接——可能是信号差（瞬态），重打几次合理；但如果是号码错了（永久），打 100 次也没用。退避就是「每次等久一点再打」，jitter 就是「别跟所有人同一秒重打」。

### 什么该重试

| 条件 | 重试? | 原因 |
|------|:-----:|------|
| ConnectTimeout | 是 | 网络瞬态 |
| ReadTimeout | 视情况 | 可能服务端慢，限次数 |
| 502/503/504 | 是 | 网关/上游瞬态 |
| 429 | 是 | 配合 Retry-After |
| 400/404/422 | 否 | 请求本身错 |
| POST 创建资源 | **谨慎** | 可能重复创建 |

### POST 重试的幂等边界（⭐常考 🔥难点）

POST 是**非幂等**方法——服务端收到请求但响应丢失时，客户端无法判断「创建了没」。盲重试可能：
- **重复创建**工单、告警、订单
- **重复扣款**或触发副作用

三种对策：

```python
# ① Idempotency-Key：服务端用 key 去重
headers = {"Idempotency-Key": str(uuid.uuid4())}
session.post(url, json=payload, headers=headers, timeout=TIMEOUT)

# ② 先 GET 查再 POST（读后写）
existing = session.get(f"{url}?ref={ref}", timeout=TIMEOUT)
if existing.status_code == 404:
    session.post(url, json=payload, timeout=TIMEOUT)  # ← 确认不存在才建

# ③ 只重试连接层失败（未收到任何响应），不重试 5xx
except requests.ConnectionError:
    retry()  # ← 连接没建立，服务端不可能已处理
except requests.HTTPError:
    raise    # ← 收到了响应，说明服务端已处理，不能盲重试
```

> ⚠️ **别混**：PUT 带**固定资源 ID** 时可设计为幂等（`PUT /items/42` 重复执行结果不变），但 POST `CREATE` 每次生成新 ID——必须靠 Idempotency-Key。

### 手写重试模板

```python
import random
import time

RETRYABLE_STATUS = {429, 500, 502, 503, 504}
MAX_ATTEMPTS = 5
BASE = 0.5
CAP = 30.0

def request_with_retry(session: requests.Session, method: str, url: str, **kwargs):
    kwargs.setdefault("timeout", TIMEOUT)
    last_exc: Exception | None = None
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            resp = session.request(method, url, **kwargs)
            if resp.status_code in RETRYABLE_STATUS:
                resp.raise_for_status()  # 进入 HTTPError 或下面处理
            resp.raise_for_status()
            return resp
        except (requests.ConnectionError, requests.Timeout) as e:
            last_exc = e
            log.warning("attempt %s/%s transient: %s", attempt, MAX_ATTEMPTS, e)
        except requests.HTTPError as e:
            code = e.response.status_code if e.response else 0
            if code not in RETRYABLE_STATUS:
                raise
            last_exc = e
            retry_after = e.response.headers.get("Retry-After")
            if retry_after and retry_after.isdigit():
                time.sleep(min(int(retry_after), int(CAP)))
                continue
            log.warning("attempt %s http %s", attempt, code)
        if attempt == MAX_ATTEMPTS:
            break
        sleep = min(CAP, BASE * (2 ** (attempt - 1)))  # ← 指数退避 0.5, 1, 2, 4, 8...
        sleep *= random.uniform(0.5, 1.5)  # ← jitter 打散，防 thundering herd
        time.sleep(sleep)
    raise RuntimeError(f"failed after {MAX_ATTEMPTS} attempts") from last_exc
```

> 🔍 **现场**：`grep "attempt" /var/log/ops/check.log | tail -20`——看 attempt 编号与间隔，无退避会看到 0.1s 间距连续打满。

> 🔥 **难点**：**thundering herd**——发布窗口 50 个脚本同时 502，若退避无 jitter，所有实例在同一秒重试，第二拨峰值比第一拨还高。jitter 是唯一解。

> 📝 **面试**：「POST 重试要么 API 支持 Idempotency-Key，要么先查再建，要么只重试连接层失败。」

### urllib3 Retry 适配器（⭐常用）

```python
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

retry = Retry(
    total=3,
    connect=3,
    read=3,
    status=3,
    backoff_factor=0.5,
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET", "HEAD", "OPTIONS", "PUT", "DELETE"],  # 默认不含 POST
    raise_on_status=False,
)
adapter = HTTPAdapter(max_retries=retry)
session = requests.Session()
session.mount("https://", adapter)
session.mount("http://", adapter)
```

**注意**：适配器重试后仍要 `raise_for_status()`；且 **POST 默认不在 allowed_methods**——这是对的。

### TLS 证书校验（⭐常考 🔥难点）

生产环境 `verify=True` 是铁律。内网企业 CA 签发的证书常报 `SSLError: certificate verify failed`，正确做法是**指定 CA bundle**，不是关校验：

```python
# 正确：指定企业 CA
resp = session.get(url, timeout=TIMEOUT, verify="/etc/ssl/certs/company-ca.pem")
# ← verify 路径可以是文件或目录
# ← 也可设 REQUESTS_CA_BUNDLE 环境变量

# 错误：关校验（仅本地临时）
# requests.get(url, verify=False)  # ← InsecureRequestWarning，生产禁止
```

> ⚠️ **别混**：TLS 错不是重试能解决的——证书过期/不信任是永久错误，重试 100 次也一样。唯一例外：证书刚轮换的中间态（秒级）。

mTLS 双向认证（客户端证书）：

```python
resp = session.get(url, timeout=TIMEOUT, cert=("/path/client.pem", "/path/key.pem"))
# ← cert=(证书, 私钥)，客户端证书用于服务端验证调用方身份
```

## 八、收束：失败交给 main 与退出码

```mermaid
flowchart TB
    subgraph HTTP层
        R[重试耗尽]
        H[4xx 不重试]
    end
    subgraph 脚本
        M[main catch]
        E[return 1]
    end
    R --> M
    H --> M
    M --> E
```

**可背清单（六件套）**：

1. 所有请求带 `timeout=(connect, read)`
2. `raise_for_status()` 或显式检查 `resp.ok`
3. 429/5xx/连接/超时：有限重试 + 退避 + jitter
4. 4xx（除 429）：不重试，修请求
5. POST 重试考虑幂等
6. 循环用 `Session`；失败 `raise`/`return 1`，不吞

> ⚠️ **别混**：HTTP 重试解决**单次调用**瞬态；**等 Pod Ready** 是外层轮询（11 章），两层不要混为一谈。

## 九、作战：502 风暴、脚本挂死、重复工单

**现象 · 先做 · 别做**

| 现象 | 先做 | 别做 |
|------|------|------|
| cron 重叠挂死 | 查是否缺 timeout | 加大 cron 间隔掩盖 |
| 网关 502 雪崩 | 看重试次数与间隔 | 无退避紧循环 |
| 重复 POST 工单 | 查幂等键/重试方法 | 盲重试 POST |
| TLS 证书错 | 修 CA 或 cert 路径 | 长期 verify=False |
| 401 一直重试 | 停重试，换 token | 加到 100 次 |

**60 秒剧本** 🔧：

| 时段 | 动作 |
|------|------|
| 0–10s | `curl -v -m 5 URL` 对比 Python |
| 10–25s | grep `timeout` / `retry` / `sleep` |
| 25–40s | 故意断网看是否快速失败 |
| 40–60s | 日志是否有 attempt 与 status |

```bash
curl -sS -m 10 -w "\nhttp_code=%{http_code}\n" "$URL"

```

## 生产模板

### 模板 1：Session + timeout + raise

```python
def build_session() -> requests.Session:
    s = requests.Session()
    s.headers.update({"User-Agent": "ops-check/1.0"})
    return s

def fetch_health(session: requests.Session, base: str) -> dict:
    url = f"{base.rstrip('/')}/healthz"
    resp = session.get(url, timeout=(3.05, 15))
    resp.raise_for_status()

```

### 模板 2：urllib3 Retry + 显式 raise

```python
def build_retry_session(total: int = 3) -> requests.Session:
    retry = Retry(total=total, backoff_factor=0.5,
                  status_forcelist=[429, 502, 503, 504])
    s = requests.Session()
    s.mount("https://", HTTPAdapter(max_retries=retry))
    return s
```

### 模板 3：GET 幂等 + 手写退避

```python
def get_with_backoff(session, url: str) -> requests.Response:
    return request_with_retry(session, "GET", url)
```

### 模板 4：main 边界

```python
def main() -> int:
    try:
        with build_session() as s:
            run_checks(s)
    except requests.RequestException as e:
        log.error("http checks failed: %s", e)
        return 1
    return 0
```

### 🔧 测试重试行为

用 `httpbin.org` 端点验证退避与上限：

```bash
# 模拟 503，观察重试间隔与最终失败
python -c "
import requests, time
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry
s = requests.Session()
retry = Retry(total=3, backoff_factor=0.5, status_forcelist=[503])
s.mount('https://', HTTPAdapter(max_retries=retry))
t0 = time.time()
try:
    r = s.get('https://httpbin.org/status/503', timeout=5)
    r.raise_for_status()
except Exception as e:
    print(f'failed in {time.time()-t0:.1f}s: {e}')
"
# ← 预期 ~3.5s 后失败（0.5+1+2 退避）
# ← 如果秒级失败说明重试没生效
```

## 踩坑清单

| 现象 | 原因 | 修法 |
|------|------|------|
| cron 挂死 | 无 timeout | `(connect, read)` |
| 502 放大 | 无退避紧重试 | 指数 + jitter + cap |
| 重复资源 | POST 重试 | Idempotency-Key / 禁 POST 重试 |
| JSON 解析崩 | 未 check 2xx | 先 raise_for_status |
| 连接泄漏 | 未 close Response | `with` 或 Session |
| 证书错误 | 企业 CA | 指定 verify 路径 |
| 重试 404 | status_forcelist 过大 | 只列 5xx/429 |
| 日志泄密 | 打印 headers | 只打 url/status |
| 重试无上限 | `total=None` 或 `MAX_ATTEMPTS` 缺失 | 硬编码上限 |
| 401 紧循环重试 | 把 401 当瞬态 | 401 不重试，修 token |
| 204 取 body 崩 | 对 204 调 `.json()` | 先判 `resp.content` |

## 必会 · 常考

| 说法 | 对错 | 口径 |
|------|:----:|------|
| requests 默认有 timeout | 错 | 默认 None |
| 5xx 应无限重试 | 错 | 有限 + 退避 |
| GET 重试相对安全 | 对 | 仍要防放大 |
| 404 应重试 | 错 | 路径/资源错 |
| Session 可复用连接 | 对 | 循环必备 |
| verify=False 可上生产 | 错 | 仅临时调试 |
| 429 看 Retry-After | 对 | 优先遵守 |
| raise_for_status 后才是 2xx | 对 | 否则 HTTPError |
